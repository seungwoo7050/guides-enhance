# 네트워크, 세션과 오류 처리

모바일 기기가 Wi-Fi나 이동통신망 네트워크에 연결돼 있다는 사실은 API 요청이 성공한다는 뜻이 아닙니다. DNS, TLS, 접속 인증 포털, VPN, 무선망 전환, 서버 시간 초과와 앱 백그라운드 전환이 한 요청 중에도 바뀔 수 있습니다.

이 문서는 HTTP 자체를 다시 설명하지 않습니다. 연결이 자주 바뀌고 프로세스가 중단될 수 있는 모바일 클라이언트에서 요청, 인증 정보와 outbox를 어떻게 보존할지 정리합니다. `05-local-data-offline-and-sync.md`를 읽을 때 재시도, 처리 여부를 모르는 결과, 401 처리나 오래된 응답이 익숙하지 않다면 먼저 확인합니다.

## 이 문서에서 확인할 내용

- 연결 상태와 실제 API 도달 가능성을 구분합니다.
- 전송, HTTP 응답, 응답 본문 파싱, 업무 결과, 로컬 커밋을 나눕니다.
- 인증 정보를 일반 로컬 데이터와 다른 저장 위치와 수명으로 관리합니다.
- 자동 재시도가 가능한 작업과 위험한 작업을 구분합니다.
- 시간 초과, 취소와 늦은 응답 거절을 함께 사용합니다.
- 오프라인, 인증되지 않음, 권한 없음, 충돌, 형식이 잘못된 응답을 다른 상태로 처리합니다.
- 포그라운드 복귀 뒤 세션과 원격 상태를 다시 확인합니다.

## 연결 상태는 참고 정보입니다

네트워크 API가 `connected`를 반환해도 다음 항목은 보장되지 않습니다.

- 특정 호스트 이름의 DNS 조회
- TLS 핸드셰이크
- VPN, 프록시, 방화벽 통과
- 접속 인증 포털 인증
- 서버 응답
- 업로드가 끝날 때까지 연결 유지

따라서 연결 신호만 보고 성공 상태를 미리 표시하지 않습니다. 연결이 없다는 신호는 불필요한 요청을 줄이고 대기 중인 상태를 설명하는 데 사용할 수 있습니다.

```text
네트워크 참고 정보
+ 실제 요청 결과
+ 로컬 outbox 상태
→ 사용자에게 보여 줄 상태
```

## 한 요청의 단계를 나눕니다

```text
요청 준비
→ DNS, 연결, TLS
→ HTTP 상태와 헤더
→ 본문 읽기
→ JSON 해석
→ 런타임 스키마 검증
→ 업무 결과 해석
→ 로컬 트랜잭션
```

각 단계에서 다른 실패가 발생합니다.

| 결과 | 예 | 기본 처리 |
|---|---|---|
| 취소 | 화면 변경, 최신 검색 시작 | 사용자 오류로 표시하지 않을 수 있습니다. |
| 전송 실패 또는 시간 초과 | 연결 단절, 응답 지연 | 작업이 안전하면 같은 명령으로 재시도합니다. |
| 401 | 인증 정보 만료 | 명령을 보존하고 인증 회복 전 자동 실행을 멈춥니다. |
| 403 | 현재 계정에 권한 없음 | 재시도하지 않고 계정이나 권한을 확인할 동작을 제공합니다. |
| 404 | 삭제 또는 범위 변경 | 로컬 상태와 대상 존재 여부를 다시 확인합니다. |
| 409 또는 업무 충돌 | 원격 버전 변경 | 로컬, 원격, 최초 시도 명령을 함께 보존합니다. |
| 5xx | 서버 장애 | 최대 횟수와 점차 늘어나는 재시도 간격을 적용합니다. |
| 형식이 잘못된 본문 | 필드 누락, 잘못된 열거 값 | 기존 안전 상태를 유지하고 성공으로 기록하지 않습니다. |
| 오래된 응답 | 이전 요청의 늦은 결과 | 현재 상태에 반영하지 않습니다. |

모든 상태를 `네트워크 오류` 하나로 표시하면 사용자가 해결할 수 있는 다음 동작을 제공하기 어렵습니다.

## 외부 응답을 런타임에서 검증합니다

TypeScript 타입은 네트워크 본문을 검사하지 않습니다.

```ts
const raw: unknown = await response.json();
const result = parseSyncResponse(raw);
```

다음 항목을 실제 값에서 확인합니다.

- 필수 필드와 허용한 열거 값
- 명령 ID와 기록 ID
- 버전이 정수인지, 이전 값보다 감소하지 않는지
- `null` 허용과 필드 누락의 차이
- 측정 시각과 숫자 범위
- 삭제 결과에서 데이터가 실제로 `null`인지
- 성공 본문과 오류 본문이 상태와 일치하는지

파싱이 끝나기 전에 일부 필드를 SQLite에 저장하지 않습니다. 응답 전체가 유효할 때만 한 트랜잭션에 처리 결과를 기록합니다.

## 인증 정보를 일반 데이터와 분리합니다

일반적인 역할은 다음과 같습니다.

```text
액세스 토큰
- 짧은 수명
- 메모리 우선
- 요청 인증에 사용

갱신 토큰 또는 장기 인증 정보
- 플랫폼 보안 저장소
- 교체와 폐기 고려
- 일반 로그와 SQLite 기록에서 제외

사용자·계정 메타데이터
- 로컬 캐시 가능
- 현재 인증 정보와의 일치 여부 확인
```

SecureStore 계열 저장소는 작은 인증 정보를 위한 것입니다. 큰 기록이나 이미지를 넣지 않습니다. 반대로 일반 SQLite나 설정 값 저장소에 Bearer 토큰을 평문으로 넣지 않습니다.

생체 인증 대화 상자는 서버 인가를 대신하지 않습니다. 로컬 인증 정보 사용 전에 사용자를 확인할 수는 있지만, 서버에서 토큰의 유효성과 권한을 다시 확인해야 합니다.

## 세션 복원을 상태로 표현합니다

```ts
type SessionState =
  | { kind: "unknown" }
  | { kind: "anonymous" }
  | { kind: "restoring" }
  | { kind: "authenticated"; accountId: string; expiresAt: string }
  | { kind: "reauth-required"; reason: string };
```

시작 절차에서 인증 정보 문자열이 있다는 이유만으로 보호된 경로를 열지 않습니다.

```text
보안 저장소 읽기
→ 묶음 버전과 필드 검증
→ 필요하면 인증 정보 갱신
→ 응답 검증
→ 새 인증 정보 저장
→ 인증된 상태 확정
```

여러 보안 저장소 키 쓰기는 하나의 트랜잭션이 아닐 수 있습니다. 액세스 토큰, 갱신 토큰과 생성 단계를 각각 덮어쓰면서 원자적 교체라고 부르지 않습니다. 버전 정보를 포함한 하나의 값을 교체하거나 `prepared → active` 생성 단계를 사용해 중단 뒤에도 어느 값을 쓸지 결정할 수 있어야 합니다.

일부 iOS Keychain 값은 앱을 삭제하고 다시 설치해도 남을 수 있습니다. 앱을 다시 설치했다는 사실을 로그아웃이나 인증 정보 제거의 근거로 사용하지 않습니다.

Field Notes의 현재 구현은 인증 정보 발급과 갱신 전체를 구현하지 않습니다. 401을 받았을 때 최초 시도 명령을 `blocked-auth`로 보존하는 지점까지만 확인합니다.

## 401을 무한 재시도하지 않습니다

인증을 사용하는 제품에서는 여러 요청이 동시에 401을 받을 수 있습니다. 각 요청이 별도 갱신을 시작하지 않도록 하나의 갱신 작업을 공유해야 합니다.

Field Notes의 기본 처리 순서는 다음과 같습니다.

```text
401
→ 최초 시도 명령과 outbox 상태를 인증 차단 상태로 저장
→ 자동 재시도 중단
→ 외부 세션 처리에서 인증 정보 회복
→ 회복 사실을 확인
→ 인증 회복을 확인한 뒤 명시적으로 재개
→ 같은 최초 시도 명령을 다시 선점
```

`resumeBlockedAuth()`를 호출했다는 사실은 인증 정보가 실제로 회복됐다는 증거가 아닙니다. 호출 전에 인증을 담당하는 코드가 새 인증 정보를 확인해야 합니다.

## 재시도는 작업 의미에 따라 결정합니다

자동 재시도가 비교적 안전한 경우:

- 같은 리소스를 읽는 `GET`
- 같은 요청을 반복해도 결과가 달라지지 않는 `PUT`
- 고유 명령 ID로 서버가 중복을 제거하는 변경 요청
- 서버에서 확인한 조각부터 이어 보내는 업로드

자동 재시도가 위험한 경우:

- 결제, 주문, 메시지처럼 중복 생성이 가능한 `POST`
- 시간 초과 뒤 새 ID로 같은 변경 요청을 다시 생성
- 파괴적인 작업
- 사용자의 현재 의도와 달라진 오래된 명령

재시도 설정에는 최소한 다음 값이 필요합니다.

```text
재시도 가능한 결과 종류
최대 시도
재시도 간격과 무작위 지연
같은 업무 의도를 나타내는 명령 ID
다음 시도 시각
중단 조건
사용자에게 표시할 대기 중인 상태
```

Field Notes는 변경 명령마다 `commandId`, `baseVersion`, `localRevision`과 데이터 사본을 보존합니다.

## 시간 초과 뒤에는 서버 처리 여부를 모를 수 있습니다

클라이언트 시간 초과는 기다리기를 멈췄다는 뜻입니다. 서버가 처리하지 않았다는 뜻이 아닙니다.

```text
요청 전송
→ 서버가 명령 적용
→ 응답이 클라이언트에 도착하기 전에 연결 종료
```

이 경우 새 명령 ID를 만들면 같은 변경이 두 번 적용될 수 있습니다. 같은 최초 시도 명령을 다시 보내고 서버가 명령 ID로 이전 결과를 반환해야 합니다.

로컬 작업자도 결과를 성공으로 추측하지 않습니다. `retry_wait` 상태를 기록한 뒤 lease 만료 시각과 재시도 간격을 적용합니다.

## 취소와 오래된 결과 확인을 함께 사용합니다

새 화면이나 새 쿼리가 시작되면 이전 요청을 취소할 수 있습니다. 하지만 이미 응답이 도착했거나 취소를 지원하지 않는 API도 있습니다. 요청 생성 단계를 함께 확인합니다.

```ts
const request = coordinator.begin();
const response = await api.fetchRecords({ signal: request.signal });
const records = parseRecordList(await response.json());

if (!coordinator.isCurrent(request.generation)) return;
await repository.replaceRemoteSnapshot(records);
```

취소는 불필요한 작업을 줄입니다. 요청 생성 번호를 확인하면 늦은 결과가 현재 상태를 덮지 않습니다. 둘은 서로 대체되지 않습니다.

변경 요청은 화면 마운트 해제와 함께 무조건 취소하지 않습니다. 사용자가 확정한 저장은 컴포넌트보다 오래 살아야 하며 outbox가 처리합니다.

## 업로드는 메타데이터와 바이트를 따로 다룹니다

사진 첨부 파일에는 최소 두 종류의 상태가 있습니다.

```text
로컬 첨부 파일
- 앱 소유 파일 URI
- 체크섬, 크기와 MIME
- 업로드 상태

원격 첨부 파일
- 원격 ID
- 원격 버전 또는 URL
```

대표 실패:

- 파일 복사 전에 프로세스 종료
- 메타데이터 행은 있지만 파일이 없음
- 파일은 있지만 메타데이터 트랜잭션이 실패함
- 업로드 완료 응답이 유실됨
- 원격 업로드는 끝났지만 기록 연결이 실패함
- 캐시 URI를 영구 파일 경로로 잘못 저장함

선택기가 반환한 URI를 앱 전용 저장 경로로 복사한 뒤 체크섬과 크기를 확인합니다. 메타데이터 커밋과 파일 정리는 재시작 뒤에도 조정할 수 있게 설계합니다.

## 포그라운드 복귀 시 필요한 상태만 다시 확인합니다

백그라운드 동안 다음 값이 바뀔 수 있습니다.

- 토큰 만료와 폐기
- 계정 전환
- 권한 철회
- 네트워크 종류
- 원격 기록 버전
- 알림으로 알려진 충돌

앱이 활성화되면 관련 작업을 요청합니다.

```text
필요한 세션 확인
→ 대기 중인 outbox 처리 요청
→ 현재 화면의 오래된 데이터 갱신
→ 사용 중인 기기 기능과 권한 재조회
```

여러 활성화 이벤트가 짧은 시간에 들어와도 같은 작업을 중복 실행하지 않게 합칠 수 있습니다.

## 사용자에게 다음 동작을 제공합니다

| 상태 | 제공할 동작 |
|---|---|
| 오프라인에서 동기화 대기 | 로컬 작업 계속, 수동 동기화, 연결 뒤 자동 재시도 설명 |
| 인증 만료 | 다시 로그인, 보존된 동기화되지 않은 데이터 설명 |
| 권한 없음 | 계정 확인 또는 안전한 화면으로 이동 |
| 충돌 | 로컬과 원격 비교, 해결 방법 선택 |
| 형식이 잘못된 응답 | 기존 데이터 유지, 다시 시도하거나 진단 정보 확인 |
| 저장 공간 부족 | 불필요한 파일 정리, 텍스트 기록 보존 |

모든 오류에 같은 `다시 시도` 버튼을 넣지 않습니다.

## 기록할 정보와 제외할 정보

기록할 수 있는 값:

- 요청 ID와 명령 ID의 제한된 표현
- 작업 종류
- 시도 횟수와 걸린 시간
- 앱, 빌드와 런타임 버전
- 네트워크 참고 정보
- HTTP 상태와 정규화한 결과 종류
- 응답 스키마 버전
- outbox 상태

기록하지 않을 값:

- 액세스 토큰과 갱신 토큰
- 인가 헤더
- 기록 제목과 메모
- 정확한 위치
- 서명된 업로드 URL 전체

## 완료 기준

- 연결 상태와 실제 요청 결과를 구분합니다.
- 외부 응답을 SQLite 반영 전에 런타임에서 검증합니다.
