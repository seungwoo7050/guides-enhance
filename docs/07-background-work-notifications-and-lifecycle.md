# 백그라운드 작업, 알림과 앱 수명

모바일 운영체제는 배터리, 네트워크, 사용 패턴과 할당량을 보고 백그라운드 작업의 실행 시각과 실행 시간을 결정합니다. 작업을 등록했다고 정확한 시각에 실행되는 것도 아니며, 사용자가 앱을 종료한 뒤에도 계속 실행된다는 보장도 없습니다.

따라서 백그라운드 실행은 데이터 보존의 필수 조건이 아니라 이미 저장된 작업을 조금 더 빨리 처리할 수 있는 기회로 사용합니다. 알림도 최신 업무 상태가 아니라 앱을 다시 열게 하는 입력으로 처리합니다.

## 이 문서에서 확인할 내용

- 포그라운드, 백그라운드, 프로세스가 종료된 상태에서 사용할 수 있는 기능을 구분합니다.
- 백그라운드 작업을 짧고 중단·중복에 안전하게 만듭니다.
- 백그라운드 작업이 실행되지 않아도 다음 포그라운드 실행에서 대기 중인 작업을 처리합니다.
- 포그라운드와 백그라운드가 같은 동기화 작업자를 사용하게 합니다.
- 알림 데이터를 검증하고 현재 데이터베이스 상태로 경로를 다시 결정합니다.
- 권한, 채널, 푸시 토큰, 백엔드 등록, 전달을 구분합니다.
- Android와 iOS 실제 기기에서 스케줄러와 알림 차이를 기록합니다.

## 백그라운드 실행은 보장된 일정이 아닙니다

운영체제는 다음 조건을 고려할 수 있습니다.

- 배터리와 충전 상태
- 저전력 모드
- 네트워크 종류
- 시스템 할당량
- 앱 사용 빈도
- 제조사 배터리 제한
- 사용자의 강제 종료 또는 최근 앱 목록 제거

다음 설계는 안전하지 않습니다.

```text
기록 저장
→ 15분 뒤 백그라운드 동기화가 반드시 실행
→ 서버에 반드시 반영됨
```

다음처럼 설계합니다.

```text
기록 저장 트랜잭션
→ 로컬 기록과 outbox가 즉시 남음
→ 포그라운드에서 동기화 요청
→ 백그라운드 기회가 오면 같은 작업자 실행
→ 다음 앱 활성화에서도 대기 중인 outbox 처리
```

백그라운드 작업이 한 번도 실행되지 않아도 사용자가 저장한 데이터와 재시도 근거는 남아 있어야 합니다.

## 작업을 작고 다시 시작할 수 있게 만듭니다

```text
실행 시작
→ 저장소 준비
→ 현재 마감 시각과 취소 확인
→ 명령 한 개 선점
→ 제한 시간을 둔 요청
→ 결과를 저장
→ 다음 명령을 시작할 시간 확인
→ 종료
```

운영체제가 시간을 회수하면 새 명령을 시작하지 않습니다. 이미 보낸 요청의 결과를 모르는 경우에는 성공으로 추측하지 않고 재시도 가능한 상태로 남깁니다.

콜백이 오지 않는 비정상 종료도 견뎌야 합니다. `finally`에서만 정확성을 보장하는 설계를 피하고 명령 선점 상태와 처리 결과를 SQLite에 저장합니다.

## 작업 정의와 등록을 구분합니다

백그라운드 프레임워크는 보통 두 작업을 나눕니다.

```text
정의
- 어떤 코드가 작업 이름을 처리하는지 등록
- 화면 없는 실행에서 React보다 먼저 필요할 수 있음

등록
- 운영체제에 실행 기회를 요청
- 사용자가 기능을 켠 뒤 수행할 수 있음
```

Field Notes는 `TaskManager.defineTask`를 모듈 범위에서 한 번 실행합니다. React 컴포넌트 안에서 조건부로 정의하지 않습니다. 등록은 설정 화면의 명시적인 사용자 동작으로 수행합니다.

`minimumInterval`은 정확한 주기가 아니라 운영체제에 전달하는 최소 간격 요청입니다.

## 포그라운드와 백그라운드가 같은 작업자를 사용합니다

```ts
type SyncTrigger =
  | "manual"
  | "app-active"
  | "background"
  | "notification";
```

실행 계기는 실행을 시작한 이유를 기록하는 값입니다. 명령을 선점하고 응답 결과를 기록하는 규칙은 바뀌지 않습니다.

- 백그라운드 콜백은 React 상태를 직접 바꾸지 않습니다.
- 결과는 SQLite에 저장합니다.
- 화면은 앱 활성화나 포커스 시 저장소를 다시 읽습니다.
- 포그라운드와 백그라운드가 동시에 실행돼도 같은 선점과 lease 규칙을 사용합니다.
- 같은 프로세스에서 여러 실행 계기가 겹치면 하나의 실행 결과를 공유할 수 있습니다.

프로세스가 다르거나 프로세스가 다시 만들어진 경우에는 메모리 잠금이 아니라 SQLite lease가 중복 실행을 막아야 합니다.

## 마감 시각과 취소 신호를 전달합니다

백그라운드 실행에는 보수적인 로컬 마감 시각을 둡니다. 운영체제가 전달하는 만료 콜백과 상위 `AbortSignal`을 같은 작업자 중단 신호로 전달합니다.

```text
운영체제 만료 신호 또는 로컬 마감 시각
→ AbortController 취소
→ 작업자가 새 명령 선점 중단
→ 진행 중인 요청의 결과를 모르면 재시도 상태로 기록
```

백그라운드 실행에 포그라운드 실행 계기가 합쳐졌다고 마감 시각을 늘리지 않습니다. 대기열이 남으면 다음 포그라운드 기회가 다시 작업자를 실행합니다.

## 화면 없는 실행에서 UI를 호출하지 않습니다

백그라운드 또는 프로세스가 종료된 상태에서 다음 값을 기대하면 안 됩니다.

- 현재 화면에 마운트된 컴포넌트
- 준비된 라우터
- 모달이나 알림창
- 메모리에만 있는 세션
- 이미 만들어진 의존성 컨테이너
- 즉시 응답할 사용자

화면 없는 작업은 필요한 SQLite 저장소와 런타임을 직접 열어야 합니다. 사용자 입력이 필요한 상태는 `blocked-auth`, `conflict`처럼 SQLite에 저장하고 포그라운드 화면에서 처리합니다.

## 알림은 최신 데이터가 아닙니다

알림은 지연, 중복, 순서 역전될 수 있습니다. 사용자가 이미 충돌을 해결한 뒤 오래된 알림을 누를 수도 있습니다.

```text
알림 데이터
→ 스키마와 ID 검증
→ 데이터베이스 준비
→ 현재 계정 확인
→ 메시지 선점
→ 현재 기록, 충돌과 동기화 상태 조회
→ 경로 또는 안전한 대체 경로 적용
→ 처리 완료 기록
```

데이터의 제목이나 본문을 기록의 최신 값으로 사용하지 않습니다. 불투명 ID와 요청 종류만 전달하고 현재 저장소를 다시 읽습니다.

Field Notes가 허용하는 예는 다음과 같습니다.

```ts
type NotificationEnvelope = {
  schemaVersion: 1;
  messageId: string;
  accountId: string;
  intent:
    | { kind: "record-conflict"; recordId: string }
    | { kind: "record-updated"; recordId: string }
    | { kind: "sync-blocked" };
};
```

추가 업무 필드가 들어오면 거부합니다. 알림 본문에 기록 내용이나 정확한 위치를 넣지 않습니다.

## 메시지를 선점한 뒤 경로를 적용합니다

알림 응답은 여러 번 전달될 수 있으므로 `messageId`를 저장합니다.

```text
선점(messageId, owner, lease)
→ 현재 상태 확인
→ 경로 적용
→ acknowledge
```

- 살아 있는 선점이 있으면 다른 처리 코드는 `in-progress`로 종료합니다.
- 프로세스가 경로 적용 전에 종료되면 lease 만료 뒤 다시 처리할 수 있습니다.
- 경로 적용이 끝난 뒤에만 완료로 기록합니다.
- 이미 완료한 메시지는 중복으로 처리합니다.
- 삭제된 기록이나 다른 계정의 메시지는 더 처리하지 않는 결과와 안전한 대체 경로를 남깁니다.

저장하지 않은 초안이 있으면 외부 알림이 현재 편집을 덮지 않게 선점을 해제합니다. 네이티브 마지막 응답을 남겨 사용자가 편집을 끝낸 뒤 다시 처리할 수 있게 합니다.

## 권한, 채널, 토큰, 등록을 나눕니다

다음 값은 서로 다른 상태입니다.

- OS 알림 권한
- Android 알림 채널
- 기기 또는 Expo 푸시 토큰
- 백엔드 설치 등록
- 제공자가 알림을 받았는지 여부
- 운영체제가 실제로 표시했는지 여부
- 사용자가 눌렀는지 여부

권한이 `granted`라고 토큰 발급이나 백엔드 등록이 성공한 것은 아닙니다. 토큰이 있다고 전달이 보장되는 것도 아닙니다.

Android에서는 다음 순서를 고정합니다.

```text
채널 생성
→ 현재 권한 확인
→ 사용자가 알림 기능을 켠 경우 권한 요청
→ 권한 허용 또는 권한 요청이 필요 없는 상태 확인
→ 푸시 토큰 요청
→ 설치·계정 연결 저장
```

채널 생성에 실패하면 토큰 요청으로 넘어가지 않습니다. 권한이 거절됐거나 사용이 제한되면 토큰을 요청하지 않습니다.

## 설치와 계정 연결을 관리합니다

푸시 토큰은 현재 설치와 계정에 연결합니다.

```ts
type NotificationInstallationBinding = {
  installationId: string;
  accountId: string;
  token: string;
  updatedAt: number;
};
```

`installationId`는 앱이 만든 불투명 ID입니다. 하드웨어 식별자를 사용하지 않습니다.

등록 결과를 구분합니다.

- 처음 생성됨
- 같은 토큰으로 그대로 유지됨
- 토큰이 회전함
- 다른 계정으로 전환됨

로그아웃할 때는 저장된 계정 ID가 요청한 계정 ID와 같은 경우에만 연결을 제거합니다. 이전 계정의 늦은 로그아웃이 새 계정 연결을 지우지 않게 합니다.

등록 저장소 업데이트가 실패하면 기존 연결을 그대로 보존해야 합니다. 토큰 원문은 로그와 외부 공개 결과에 넣지 않습니다.

## 토큰 교체를 별도 사건으로 처리합니다

네이티브 푸시-토큰 리스너는 토큰이 바뀌었다는 신호를 줍니다. Field Notes가 Expo 토큰 종류를 사용한다면 리스너 원본 토큰을 그대로 저장하지 않고 `getExpoPushTokenAsync()`를 다시 호출해 최초 등록과 같은 종류의 토큰을 얻습니다.

```text
네이티브 토큰 변경 신호
→ Expo 프로젝트 토큰 다시 요청
→ 현재 설치와 계정에 등록
→ 생성, 변경 없음, 교체 또는 계정 전환 결과 저장
```

이 과정이 성공했다고 제공자의 이전 토큰 정리나 실제 전달까지 확인된 것은 아닙니다.

## 알림 종류를 구분합니다

### 로컬 알림

- 기기 안에서 예약
- 시간대와 시계 변경 고려
- 기록 삭제나 완료 시 취소

### 원격 표시되는 알림

- 운영체제가 제목과 본문 표시
- 포그라운드와 백그라운드 상태에 따라 표시 방식이 달라짐
- 사용자 탭으로 응답 전달

### 데이터 또는 백그라운드 알림

- 화면 없이 데이터를 전달하거나 작업을 요청할 수 있음
- 플랫폼 제한과 권한 설정이 필요할 수 있음
- 전달과 실행을 보장하지 않음

화면을 표시하지 않는 푸시 알림을 주기적인 동기화 스케줄러처럼 사용하지 않습니다.

## 포그라운드에서 중복 안내를 피합니다

앱이 활성화일 때 알림 배너와 화면 내부 메시지를 모두 표시하면 같은 내용을 두 번 알릴 수 있습니다.

Field Notes에서 사용할 수 있는 기본 처리 예:

- 현재 보고 있는 기록 업데이트: 저장소를 다시 읽고 화면에서 표시
- 다른 기록 충돌: 동기화 화면의 배지 또는 요약
- 단순 동기화 완료: 별도 배너 없이 상태 갱신
- 사용자 동작이 필요한 오류: 화면에 남는 설명과 동기화 화면 링크

스크린 리더 음성 알림도 같은 상태를 여러 곳에서 반복하지 않게 합니다.

## 실제 기기에서 확인합니다

시뮬레이터와 에뮬레이터는 스케줄러, 배터리, 강제 종료, 푸시 전달을 완전히 재현하지 못합니다.

최소 검사 조합:

```text
앱 활성화
앱 백그라운드
화면 잠금
최근 앱 목록에서 제거
OS 프로세스 종료
네트워크 없음과 복구
알림 권한 거절과 허용
알림 콜드 스타트와 웜 상태에서 알림 누르기
백그라운드 작업 미실행
가능하면 저전력 모드와 재부팅
```

`최근 앱 목록에서 제거`와 강제 종료의 의미는 플랫폼과 제조사에 따라 다를 수 있습니다. 한 기기의 결과를 모든 환경에 일반화하지 않고 기기 검사표에 기록합니다.

## 관찰할 정보

- 작업 ID와 시도 ID
- 실행 계기
- 시작과 종료 시각
- 앱, 빌드와 런타임 버전
- 선점한 명령 수
- 저장한 처리 결과의 수와 종류
- 마감 시각 도달 여부와 취소 신호
- 다음 대기 중인 수
- 정규화한 실패 종류

기록 데이터, 인증 정보와 알림 원문은 기록하지 않습니다.

## 검증 시나리오

- 백그라운드 작업이 한 번도 실행되지 않음
- 작업 시작 직후 마감 시각 도달
- 수동 실행과 백그라운드 실행 계기가 겹침
- 서로 다른 프로세스의 작업자가 같은 명령을 요청함
- 백그라운드에서 인증 정보 만료
- 중복 알림 응답
- 오래된 충돌 알림
- 다른 계정의 알림
- 삭제된 기록을 가리키는 알림
- 콜드 스타트 알림 + DB 마이그레이션 지연
- 초안이 있는 상태의 알림
- 토큰 발급 실패
- 토큰 교체
- 계정 전환 뒤 이전 로그아웃
- 등록 저장소 업데이트 실패

## 완료 기준

- 백그라운드 실행 없이 포그라운드 복귀만으로 대기 중인 outbox를 다시 처리할 수 있습니다.
- 작업은 제한된 명령만 처리하고 각 명령 뒤 결과를 저장합니다.
- 포그라운드와 백그라운드가 같은 작업자를 사용합니다.
- 마감 시각 이후 새 명령을 선점하지 않습니다.
- 프로세스 종료 뒤 lease 만료로 작업을 다시 시작할 수 있습니다.
- 알림 데이터를 검증하고 현재 데이터베이스 상태를 다시 읽습니다.
- 메시지 선점은 경로 적용 뒤에만 완료됩니다.
- Android 채널, 권한, 토큰과 설치 등록을 구분합니다.
- 토큰 교체와 오래된 로그아웃을 처리합니다.
- Android와 iOS 실제 기기에서 콜드 스타트와 웜 상태의 알림과 백그라운드 제한을 기록했습니다.
