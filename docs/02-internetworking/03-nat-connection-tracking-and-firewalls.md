# NAT, 연결 추적과 방화벽

NAT는 패킷의 주소나 포트를 바꾸고, 응답 방향에서 원래 값으로 되돌릴 매핑을 저장합니다. 방화벽은 어떤 트래픽을 허용하거나 거부할지 판단합니다. 두 기능이 같은 장비에서 연결 추적 상태를 공유할 수는 있지만 수행하는 일은 다릅니다.

## 학습 목표

- NAT 매핑, 연결 추적, 방화벽 판정을 구분합니다.
- 요청과 응답의 주소·포트 튜플이 방향별로 어떻게 바뀌는지 추적합니다.
- 매핑 제한 시간과 장비 재시작에 따른 상태 소실을 애플리케이션의 복구 동작과 연결합니다.

## 대표적인 주소 변환

| 종류 | 주로 바꾸는 값 | 대표 사용 사례 |
|---|---|---|
| SNAT | 출발지 주소와 포트 | 내부 호스트가 외부로 연결할 때 |
| DNAT | 목적지 주소와 포트 | 외부 요청을 내부 서비스로 전달할 때 |
| PAT/NAPT | 여러 통신의 포트까지 변환 | 여러 내부 주소가 한 외부 주소를 공유할 때 |
| Hairpin NAT | 내부에서 공개 주소를 거쳐 내부 서비스로 다시 진입 | 내부와 외부에서 같은 서비스 이름을 사용할 때 |

예를 들어 다음 UDP 통신을 생각할 수 있습니다.

```text
원래 요청:      10.202.1.2:53000 → 198.18.0.2:9000
변환된 요청:    198.18.0.1:41000 → 198.18.0.2:9000
서버의 응답:    198.18.0.2:9000  → 198.18.0.1:41000
복원된 응답:    198.18.0.2:9000  → 10.202.1.2:53000
```

NAT 장비는 외부 튜플을 원래 내부 튜플로 되돌릴 상태를 유지합니다. 여러 통신이 하나의 외부 주소를 공유하면 포트 공간, 충돌 처리, 매핑 제한 시간이 제한 자원이 됩니다.

## 연결 추적

TCP는 SYN, ACK, FIN, RST를 관찰해 연결 상태를 비교적 구체적으로 추정할 수 있습니다. UDP에는 연결 수립 핸드셰이크가 없으므로 최근 양방향 데이터그램과 제한 시간으로 임시 상태를 관리합니다.

UDP 매핑은 애플리케이션이 기대하는 유휴 시간보다 먼저 사라질 수 있습니다. keepalive나 재등록 주기를 정할 때 모든 NAT 장비가 같은 제한 시간을 사용한다고 가정해서는 안 됩니다.

ICMP 오류도 원래 패킷의 일부를 포함하므로 관련 NAT 상태를 찾아 주소와 체크섬을 올바르게 변환해야 할 수 있습니다.

## 상태 기반 방화벽과 NAT의 차이

상태 기반 방화벽은 먼저 허용된 외부 방향 통신의 응답을 `ESTABLISHED` 또는 관련 상태로 허용할 수 있습니다. 이는 NAT가 주소를 바꿨기 때문에 안전해진 것이 아니라 방화벽 규칙과 연결 추적 상태가 응답 방향을 허용했기 때문입니다.

다음 설명은 정확하지 않습니다.

- 사설 주소를 사용하므로 방화벽이 필요 없습니다.
- NAT를 제거하면 모든 내부 서비스가 자동으로 외부에 공개됩니다.
- IPv6는 NAT가 없으므로 보안이 약합니다.
- 포트 전달이 애플리케이션 인증을 대신합니다.

IPv6에서 NAPT의 필요성이 줄어도 인바운드 허용 규칙, 호스트 방화벽, 서비스 바인드 주소, 인증과 인가는 여전히 필요합니다.

## NAT가 만드는 운영 비용

- 외부에서 내부로 새 통신을 시작하려면 명시적인 매핑이나 NAT traversal이 필요합니다.
- 페이로드 안에 주소와 포트를 넣는 프로토콜은 별도 처리가 필요할 수 있습니다.
- 장애를 조사하려면 외부 튜플을 내부 통신과 연결할 로그가 필요합니다.
- 매핑 테이블과 포트 공간이 고갈될 수 있습니다.
- 장비 재시작이나 장애 조치 과정에서 상태가 사라질 수 있습니다.
- NAT 구현 차이 때문에 피어 간 직접 연결 성공률이 달라질 수 있습니다.

Carrier-grade NAT에서는 여러 사용자가 외부 주소를 공유하므로 주소뿐 아니라 포트와 시각까지 기록해야 통신을 식별할 수 있습니다. 원격 IP 주소 하나를 사용자 신원으로 취급해서는 안 됩니다.

## 격리된 SNAT 실험

[linux-routing-nat](../../exercises/linux-routing-nat/README.md)은 문서용 시험 주소만 사용해 SNAT와 응답 복원을 확인합니다.

```sh
cd exercises/linux-routing-nat
sudo ./scripts/run-nat.sh
```

클라이언트 `10.202.1.2`가 UDP 요청을 보내면 라우터가 출발지 주소를 `198.18.0.1`로 바꿉니다. 서버가 기록한 상대 주소와 클라이언트가 받은 응답을 함께 확인합니다.

이 실험은 NAT 테이블만 변경합니다. 방화벽의 필터 규칙이나 애플리케이션 인가를 검증하지 않습니다.

## 설정을 바꾸기 전에 확인할 항목

1. 어느 방향에서 누가 새 통신을 시작할 수 있습니까?
2. 적용할 프로토콜, 주소, 포트, 인터페이스는 무엇입니까?
3. 응답과 관련 ICMP 오류는 어떤 연결 상태로 허용합니까?
4. 유휴 제한 시간이 지난 뒤 애플리케이션은 어떻게 다시 연결합니까?
5. NAT 매핑과 방화벽 판정을 어떤 로그로 추적합니까?
6. 장비 재시작과 장애 조치 과정에서 상태를 어떻게 처리합니까?
7. IPv4와 IPv6 규칙이 같은 의도를 구현합니까?

## 완료 기준

- SNAT 요청과 응답의 원래 튜플과 변환된 튜플을 표로 작성합니다.
- NAT 매핑 존재 여부와 방화벽 허용 여부를 따로 판정합니다.
- 제한 시간과 장비 재시작 뒤 상태 소실을 애플리케이션의 재연결 동작과 연결해 설명합니다.
