# 라우팅 알고리즘과 프로토콜

라우팅 테이블 조회는 이미 설치된 경로 가운데 목적지와 가장 잘 맞는 항목을 고르는 데이터 평면의 작업입니다. 라우팅 프로토콜은 여러 라우터가 도달 가능성, 비용, 운영 규칙을 교환해 경로를 계산하고 전달 테이블에 설치하는 제어 평면의 작업입니다. 두 작업을 구분해야 경로를 배우지 못한 문제와 패킷을 전달하지 못한 문제를 따로 조사할 수 있습니다.

## 학습 목표

- 경로 학습, 선택, 설치, 실제 패킷 전달을 따로 기록합니다.
- distance-vector, link-state, path-vector 방식이 교환하는 정보를 구분합니다.
- 수렴 중에 발생할 수 있는 전달 루프와 블랙홀을 설명합니다.

## 데이터 평면과 제어 평면

```text
제어 평면
이웃 관계와 토폴로지 정보 수집
→ 후보 경로 계산
→ 선호도와 반입·반출 규칙 적용
→ 전달 테이블에 경로 설치

데이터 평면
패킷 목적지 확인
→ 최장 프리픽스 일치
→ 다음 홉과 출력 인터페이스 선택
→ 패킷 전달
```

제어 평면이 잠시 불안정해도 기존에 설치된 경로로 패킷이 계속 전달될 수 있습니다. 반대로 제어 평면이 경로를 알고 있어도 하드웨어 전달 테이블에 설치하지 못하면 패킷을 전달할 수 없습니다. 두 상태를 각각 확인해야 합니다.

## 정적 경로

정적 경로는 경로가 단순하고 변화가 적을 때 예측하기 쉽습니다. 장비와 링크가 늘어나면 다음 문제가 생깁니다.

- 도달 가능한 프리픽스를 사람이 직접 추가하고 제거해야 합니다.
- 링크 장애 뒤 우회 경로로 자동 전환되지 않습니다.
- 잘못된 다음 홉과 중복 경로가 쌓일 수 있습니다.
- 여러 관리자가 같은 프리픽스의 의도를 다르게 해석할 수 있습니다.

동적 라우팅은 경로 계산과 갱신을 자동화하지만 이웃 상태, 타이머, 인증, metric, 수렴 과정, 경로 반출 규칙이라는 추가 상태를 관리해야 합니다.

## Distance-vector

Distance-vector 방식은 이웃에게 특정 목적지까지의 비용을 알립니다. 각 라우터는 이웃까지의 링크 비용과 이웃이 광고한 거리를 합쳐 더 나은 경로를 선택합니다.

```text
D_x(y) = min_v { cost(x, v) + D_v(y) }
```

전체 토폴로지를 직접 저장하지 않아도 되지만 장애 정보가 느리게 퍼지면 라우팅 루프와 count-to-infinity 문제가 생길 수 있습니다. split horizon, poison reverse, hold-down은 일부 문제를 줄이지만 모든 수렴 오류를 없애지는 않습니다.

## Link-state

Link-state 방식은 각 라우터가 자신의 인접 링크 상태를 영역 안에 전달하고, 라우터마다 동기화된 토폴로지 데이터베이스에서 최단 경로 트리를 계산합니다.

```text
이웃 관계 형성
→ 링크 상태 광고 전달
→ 토폴로지 데이터베이스 동기화
→ SPF 계산
→ 다음 홉 설치
```

정보를 빠르게 공유하고 영역의 토폴로지를 볼 수 있지만 데이터베이스 동기화, 순서 번호, 만료 처리, 재계산 부하를 관리해야 합니다. 링크가 반복해서 활성화와 비활성화를 오가면 경로가 자주 바뀔 수 있습니다.

OSPF는 자율 시스템 내부에서 사용하는 대표적인 link-state 프로토콜입니다. Area로 토폴로지와 광고 범위를 나누고 링크 비용으로 경로를 계산합니다.

## BGP와 path-vector

서로 다른 자율 시스템 사이에서는 단순한 지연보다 사업 관계, 경로 반출 규칙, 안정성, 트래픽 조정이 중요할 수 있습니다. BGP는 프리픽스와 AS_PATH를 포함한 속성을 교환하고 각 운영자가 정한 규칙에 따라 경로를 선택합니다.

다음과 같이 단정해서는 안 됩니다.

- BGP는 항상 물리적으로 가장 짧은 경로를 고릅니다.
- AS_PATH 길이만 비교합니다.
- 모든 라우터가 같은 경로를 즉시 선택합니다.
- 경로가 보이면 데이터 평면도 반드시 통합니다.

구현은 Local Preference, AS_PATH, Origin, MED, eBGP/iBGP 관계, IGP 비용, 동률 처리 규칙을 정해진 순서로 적용합니다. 장애 기록에는 어떤 속성과 운영 규칙이 선택 결과를 만들었는지 적어야 합니다.

## 수렴 중의 일시적 불일치

링크 장애가 발생해도 모든 라우터가 같은 순간에 같은 정보를 갖지는 않습니다. 장애 탐지, 광고, 계산, 테이블 설치가 순서대로 진행되므로 다음 현상이 나타날 수 있습니다.

- 일시적인 전달 루프
- 블랙홀
- 패킷 순서 뒤바뀜
- ECMP 구성원 변경
- 반복적인 경로 변동

애플리케이션의 재시도 간격이 경로 수렴 시간보다 지나치게 짧으면 같은 실패를 반복하고 부하만 늘릴 수 있습니다.

## ECMP

동일 비용 경로가 여러 개면 Equal-Cost Multi-Path로 트래픽을 나눌 수 있습니다. 일반적으로 통신 튜플을 해시해 같은 통신의 패킷 순서를 유지하려고 합니다.

ECMP 구성원이 바뀌면 일부 통신이 다른 경로로 이동할 수 있습니다. 경로마다 MTU, 지연, 방화벽 상태, NAT 상태가 다르면 특정 통신만 실패할 수 있습니다.

## 조사할 때 확인할 질문

1. 프리픽스를 어느 이웃과 프로토콜에서 배웠습니까?
2. 후보 경로 가운데 어떤 선호도와 규칙이 선택 결과를 만들었습니까?
3. 선택한 경로가 전달 테이블에 실제로 설치되었습니까?
4. 다음 홉과 출력 인터페이스가 실제로 패킷을 전달할 수 있습니까?
5. 장애 탐지와 경로 철회에 얼마나 걸렸습니까?
6. 같은 프리픽스를 여러 출처에서 배웠을 때 비교 순서는 무엇입니까?
7. 경로 광고를 어느 이웃에게 내보낼 수 있습니까?

[protocol-inspector](../../exercises/protocol-inspector/README.md)는 전달 테이블에서 수행하는 최장 프리픽스 조회만 구현합니다. 동적 라우팅 프로토콜 자체는 구현하지 않습니다. 제어 평면이 만든 결과와 데이터 평면이 사용하는 경로를 구분하는 데 초점을 둡니다.

## 완료 기준

- 프리픽스가 학습되어 전달 테이블에 설치되는 단계를 나열합니다.
- 선택되지 않은 경로와 설치되었지만 전달에 실패하는 경로를 구분합니다.
- 제어 평면 상태만으로 데이터 평면 성공을 주장하지 않고 패킷 캡처나 계수기로 확인합니다.
