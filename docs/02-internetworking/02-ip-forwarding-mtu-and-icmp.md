# IP 전달, MTU와 ICMP

라우터는 패킷을 다른 포트로 단순히 복사하지 않습니다. 입력 헤더가 유효한지 확인하고, TTL 또는 Hop Limit을 줄이고, 경로와 출력 인터페이스를 선택한 뒤 출력 링크의 MTU와 다음 홉 상태를 확인합니다. 전달할 수 없을 때는 가능한 경우 ICMP 메시지로 원인을 알립니다.

## 학습 목표

- 라우터가 IP 패킷을 받은 뒤 수행하는 처리를 순서대로 설명합니다.
- TTL 만료, 경로 누락, MTU 초과, 이웃 조회 실패를 서로 다른 관찰 결과로 구분합니다.
- ICMP가 제공하는 기능과 무차별 차단의 영향을 설명합니다.

## 패킷 전달 순서

개념적인 처리 순서는 다음과 같습니다.

```text
입력 프레임 수신
→ 링크 헤더와 IP 버전 확인
→ IP 헤더 길이, 전체 길이, 체크섬 확인
→ TTL 또는 Hop Limit 감소
→ 방화벽 등 허용 조건 확인
→ 경로 조회
→ 출력 MTU 확인
→ 다음 홉 이웃 조회
→ 출력 링크용 새 프레임 생성
→ 전송
```

실제 구현은 하드웨어 오프로딩, 빠른 처리 경로, ACL, QoS, 터널 처리 등을 포함할 수 있습니다. 장애를 조사할 때는 패킷이 어느 단계까지 도달했고 어디에서 더 진행하지 못했는지 확인합니다.

## IPv4 헤더에서 확인할 값

- Version과 IHL은 헤더 형식과 길이를 정합니다.
- Total Length는 헤더와 페이로드를 포함한 전체 바이트 수를 나타냅니다.
- Identification, Flags, Fragment Offset은 단편화와 재조립에 사용합니다.
- TTL은 라우팅 루프에서 패킷이 무한히 남지 않도록 홉마다 감소합니다.
- Protocol은 TCP, UDP, ICMP 같은 상위 프로토콜을 나타냅니다.
- Header Checksum은 IPv4 헤더만 보호합니다.
- Source와 Destination은 출발지와 목적지 주소입니다.

TTL이 바뀌므로 IPv4 라우터는 헤더 체크섬을 다시 계산합니다. TCP와 UDP 체크섬에는 TTL이 포함되지 않으므로 일반적인 라우팅만으로 다시 계산하지 않습니다. NAT가 주소나 포트를 바꾸면 해당 체크섬도 함께 갱신해야 합니다.

IPv6 기본 헤더는 40바이트이며 헤더 체크섬이 없습니다. IPv4의 TTL에 해당하는 필드는 Hop Limit입니다.

## MTU와 경로 MTU

MTU는 한 링크가 페이로드로 전달할 수 있는 IP 패킷의 최대 크기입니다. 종단 간 통신에서 사용할 수 있는 크기는 경로에서 MTU가 가장 작은 구간의 영향을 받습니다.

IPv4에서는 DF가 설정되지 않았다면 라우터가 패킷을 단편화할 수 있습니다. DF가 설정되었거나 단편화할 수 없는 경우에는 패킷을 버리고 ICMP fragmentation needed 메시지를 보낼 수 있습니다.

IPv6 라우터는 전달 중인 패킷을 단편화하지 않습니다. 패킷이 너무 크면 ICMPv6 Packet Too Big을 보내고 출발지가 더 작은 패킷을 만들도록 합니다.

각 단편은 독립적으로 손실될 수 있고 목적지가 원래 패킷을 재조립해야 하므로 처리 비용과 공격 표면이 늘어납니다. 가능한 경우 출발지가 경로 MTU를 확인해 적절한 크기로 전송하는 편이 낫습니다.

## MTU 블랙홀

전통적인 Path MTU Discovery는 너무 큰 패킷에 대한 ICMP 오류를 사용합니다. 중간 방화벽이 필요한 ICMP 메시지를 차단하면 작은 요청은 성공하지만 큰 응답이나 특정 크기의 TLS 레코드에서 통신이 멈출 수 있습니다.

터널과 VPN은 추가 헤더만큼 실제 페이로드에 사용할 수 있는 MTU를 줄입니다. 특정 크기 이상에서만 실패한다면 다음 항목을 함께 확인합니다.

- 인터페이스 MTU
- 터널 헤더 크기
- TCP MSS 조정 여부
- ICMP 또는 ICMPv6 전달 여부
- 작은 패킷과 큰 패킷의 결과 차이

`ping` 한 번이 성공했다는 사실은 모든 패킷 크기와 전송 프로토콜이 정상이라는 뜻이 아닙니다.

## ICMP의 역할

ICMP와 ICMPv6는 Echo Request와 Echo Reply 외에도 다음 정보를 전달합니다.

- Destination Unreachable
- Time Exceeded
- Parameter Problem
- Redirect
- IPv6 Packet Too Big
- IPv6 Neighbor Discovery 메시지

ICMP 메시지 자체도 전달을 보장하지 않습니다. 다른 ICMP 오류에 다시 오류를 생성하지 않도록 제한하는 규칙도 있습니다.

보안상 모든 ICMP를 무조건 허용할 필요는 없습니다. 그러나 필요한 type과 code까지 막으면 Path MTU Discovery, IPv6 Neighbor Discovery, 장애 진단이 제대로 동작하지 않습니다. 필요한 메시지 종류와 전송률 제한을 기능별로 정해야 합니다.

## 인터넷 체크섬

IPv4 헤더 체크섬과 TCP·UDP 체크섬은 16비트 1의 보수 합을 사용합니다. 바이트 수가 홀수이면 계산할 때 오른쪽에 0바이트를 덧붙이고, 16비트를 넘은 올림은 하위 16비트에 다시 더합니다.

TCP 체크섬은 TCP 헤더와 페이로드만 계산하지 않습니다. IPv4 출발지와 목적지, 0, 프로토콜 번호, TCP 길이로 만든 의사 헤더를 앞에 붙입니다.

[protocol-inspector](../../exercises/protocol-inspector/README.md)에서 체크섬과 패킷 파서를 검증합니다.

```sh
cd exercises/protocol-inspector
python3 -m unittest tests.test_checksum tests.test_packet -v
```

송신 호스트에서 체크섬 오프로딩이 켜져 있으면 캡처 시점에 체크섬이 아직 채워지지 않아 잘못된 체크섬처럼 보일 수 있습니다. 캡처 위치와 방향, 오프로딩 설정을 함께 기록해야 합니다.

## 격리된 라우팅 실험

[linux-routing-nat](../../exercises/linux-routing-nat/README.md)의 라우팅 실험은 클라이언트와 서버 사이에 라우터 네임스페이스 하나를 둡니다.

```sh
cd exercises/linux-routing-nat
sudo ./scripts/run-routing.sh
```

TTL이 1인 패킷은 라우터에서 만료되고, TTL이 2인 패킷은 한 홉을 지나 서버에 도달합니다. 클라이언트의 기본 경로를 제거하면 연결이 실패하고, 경로를 복구하면 다시 성공하는지도 확인합니다.

## 실패 지점별 관찰

| 지점 | 확인할 자료 | 대표 원인 |
|---|---|---|
| 입력 인터페이스 | 패킷 캡처와 계수기 | 이전 홉, VLAN, 링크 문제 |
| IP 헤더 검사 | 폐기 사유와 체크섬 | 잘린 패킷, 잘못된 헤더 |
| TTL 또는 Hop Limit | Time Exceeded 메시지 | 전달 루프, 지나치게 긴 경로 |
| 경로 조회 | 선택된 프리픽스와 다음 홉 | 경로 누락, 정책 기반 라우팅 차이 |
| MTU | 패킷 크기, DF, ICMP | 터널 헤더, PMTUD 차단 |
| 출력 인터페이스 | 이웃 상태와 계수기 | ARP/NDP, 출력 필터, 링크 중단 |

## 완료 기준

- IPv4 패킷이 라우터를 지날 때 수행되는 처리를 순서대로 설명합니다.
- TTL 만료, 경로 누락, MTU 초과를 서로 다른 관찰값으로 구분합니다.
- ICMP가 보이지 않는다는 사실만으로 중간 방화벽을 원인으로 확정하지 않습니다.
