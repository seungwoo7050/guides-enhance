# IP 주소, 서브넷과 라우팅 조회

IP 주소는 호스트의 영구 이름이 아니라 특정 네트워크 인터페이스가 통신에 사용하는 논리적 위치입니다. CIDR 프리픽스는 주소의 앞쪽 몇 비트를 네트워크 범위로 사용할지 정합니다. 라우팅 테이블은 목적지 주소와 일치하는 경로 가운데 프리픽스가 가장 긴 항목을 먼저 선택합니다.

## 학습 목표

- IPv4와 IPv6 주소에서 프리픽스 범위를 계산합니다.
- 직접 연결된 경로와 게이트웨이를 거치는 경로를 구분합니다.
- 최장 프리픽스 일치와 동률 처리 순서를 적용합니다.

## 주소와 프리픽스를 함께 읽기

`192.0.2.10/24`에서 `/24`는 앞 24비트가 네트워크 프리픽스라는 뜻입니다.

```text
주소:      192.0.2.10
네트워크:  192.0.2.0
프리픽스:  /24
마스크:    255.255.255.0
```

CIDR에서는 Class A/B/C 이름으로 주소 범위를 추측하지 않습니다. `/20`, `/27`, `/31`, `/32`처럼 실제 프리픽스 길이를 사용합니다. 두 주소가 같은 서브넷에 속하는지 확인할 때도 문자열 앞부분이 같은지 비교하지 않고, 프리픽스 마스크를 적용한 네트워크 주소를 비교합니다.

일반적인 LAN에서 네트워크 주소와 브로드캐스트 주소를 호스트에 배정하지 않는 규칙을 `/31` 지점 간 링크나 `/32` 호스트 경로에 그대로 적용해서는 안 됩니다. 프리픽스 길이와 링크 용도를 함께 확인해야 합니다.

## 직접 연결 경로와 게이트웨이 경로

다음 라우팅 테이블을 가정합니다.

```text
10.20.30.0/24 dev lan0
0.0.0.0/0 via 10.20.30.1 dev lan0
```

- `10.20.30.50`은 직접 연결된 경로와 일치하므로 목적지 주소 자체를 이웃 조회 대상으로 사용합니다.
- `203.0.113.9`는 기본 경로를 사용하므로 게이트웨이 `10.20.30.1`을 이웃 조회 대상으로 사용합니다.

Ethernet 목적지 MAC 주소는 IP 경로를 선택한 뒤에야 정할 수 있습니다. 원격 목적지의 MAC 주소를 첫 링크에서 조회하지 않습니다.

## 최장 프리픽스 일치

다음 경로가 있다고 가정합니다.

```text
0.0.0.0/0       via 203.0.113.1 dev wan0    metric 10
10.0.0.0/8      via 10.0.0.1    dev core0   metric 100
10.20.0.0/16    via 10.20.0.1   dev branch0 metric 50
10.20.30.0/24   dev lan0                    metric 500
```

목적지 `10.20.30.8`은 네 경로와 모두 일치하지만 `/24`가 가장 길기 때문에 `lan0`이 선택됩니다. 기본 경로의 metric이 더 낮더라도 구체적인 `/24` 경로보다 먼저 선택되지 않습니다.

기본적인 비교 순서는 다음과 같습니다.

```text
1. 프리픽스 길이가 더 긴 경로
2. 프리픽스 길이가 같으면 metric이나 구현별 선호도가 더 높은 경로
3. 두 값도 같으면 구현이 정한 동률 처리 규칙
```

실제 운영체제와 라우터는 출발지 주소, 정책 기반 라우팅, VRF, 여러 라우팅 테이블, 관리 거리 같은 조건을 추가로 적용할 수 있습니다. 전체 테이블만 보는 것보다 특정 목적지에 대해 실제로 선택된 경로를 조회하는 편이 정확합니다.

## 기본 경로

IPv4의 `0.0.0.0/0`과 IPv6의 `::/0`은 별도의 예외 처리가 아니라 모든 주소에 일치하는 가장 짧은 프리픽스입니다. 더 구체적인 경로가 있으면 그 경로가 우선합니다.

기본 경로가 없으면 직접 연결된 네트워크 밖의 일반 목적지로 나갈 경로가 없습니다. DNS가 외부 주소를 정상적으로 반환했더라도 라우팅 조회에서 실패할 수 있습니다.

## IPv6에서 추가로 확인할 항목

IPv6는 128비트 주소와 프리픽스를 사용합니다. 한 인터페이스에 링크 로컬 주소, 전역 주소, 고유 로컬 주소가 함께 존재할 수 있으며, 출발지 주소 선택 절차가 실제 송신 주소를 정합니다.

링크 로컬 주소 `fe80::/10`은 같은 값이 여러 인터페이스에 존재할 수 있으므로 인터페이스 범위 ID를 함께 지정해야 할 수 있습니다.

IPv6에는 일반적인 서브넷 브로드캐스트가 없으며 멀티캐스트를 사용합니다. 또한 라우터가 전달 중인 IPv6 패킷을 단편화하지 않습니다. 너무 큰 패킷은 다음 장에서 다루는 ICMPv6 Packet Too Big 처리로 이어집니다.

## 코드로 경로 선택 확인하기

[protocol-inspector](../../exercises/protocol-inspector/README.md)의 `fixtures/routes.json`에서 목적지별 후보를 손으로 계산한 뒤 CLI 결과와 비교합니다.

```sh
cd exercises/protocol-inspector
python3 -m protocol_inspector route \
  --table fixtures/routes.json \
  --destination 10.20.30.8
```

경로 입력에 호스트 비트가 남아 있을 때 이를 네트워크 주소로 정규화할지 오류로 거부할지도 명시해야 합니다. 이 프로젝트는 `strict=False`를 사용해 입력 프리픽스를 네트워크 주소로 정규화합니다.

## 운영체제에서 확인하기

Linux:

```sh
ip address show
ip route show table all
ip route get 203.0.113.9
ip -6 route get 2001:db8::10
```

macOS:

```sh
ifconfig
netstat -rn
route -n get 203.0.113.9
route -n get -inet6 2001:db8::10
```

## 자주 발생하는 오류

- 문자열 접두사를 비교해 서브넷 포함 관계를 판단합니다.
- metric을 프리픽스 길이보다 먼저 비교합니다.
- 기본 게이트웨이가 항상 하나라고 가정합니다.
- 호스트 주소를 네트워크 프리픽스로 저장한 뒤 호스트 비트까지 비교합니다.
- IPv6 링크 로컬 주소에서 인터페이스 범위를 빠뜨립니다.

## 완료 기준

- 임의의 IPv4 주소와 프리픽스에서 네트워크 주소와 포함 범위를 계산합니다.
- 여러 경로 가운데 프리픽스 길이를 metric보다 먼저 적용해 선택 결과를 구합니다.
- 선택된 경로에서 다음 홉, 출력 인터페이스, 직접 연결 여부를 설명합니다.
