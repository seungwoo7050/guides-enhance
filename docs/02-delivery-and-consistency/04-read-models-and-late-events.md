# 조회 모델, 늦은 이벤트와 재구축

## 목표

원본 이벤트와 조회 모델 사이의 지연, 중복과 순서 역전을 처리합니다. 이벤트 적용과 checkpoint 저장 순서를 지키고, 빈 저장소에서 조회 모델을 다시 만들 수 있게 합니다.

## 조회 모델은 정본이 아닙니다

조회 모델은 여러 데이터의 검색과 조회를 빠르게 하기 위한 복제본입니다. 다음 상황은 정상적으로 발생할 수 있습니다.

- 생성 이벤트보다 상태 변경 이벤트가 먼저 도착합니다.
- consumer가 중단된 동안 이벤트가 쌓입니다.
- 적용 뒤 checkpoint 저장 전에 중단되어 같은 이벤트를 다시 읽습니다.
- 오래된 이벤트가 늦게 전달됩니다.
- projection 코드가 바뀌어 전체 재구축이 필요합니다.

재고 차감처럼 최신 상태가 필요한 명령을 조회 모델로 판단하면 지연된 값으로 잘못된 결정을 내릴 수 있습니다. 쓰기 여부는 원본 상태를 소유한 서비스가 판단해야 합니다.

## 조회 모델의 진행 위치를 노출합니다

조회 결과와 함께 필요에 따라 다음 정보를 제공하거나 내부 지표로 기록합니다.

- 원본 aggregate의 version 또는 sequence
- 마지막으로 처리한 log position
- 마지막 갱신 시각
- 재구축 중인지 여부
- 보류 중인 이벤트 수와 가장 오래된 대기 시간

이 값이 있어야 조회 결과가 얼마나 늦었는지와 재구축이 어디까지 진행되었는지 판단할 수 있습니다.

## 앞선 이벤트가 없다고 버리지 않습니다

대상이 아직 없는데 상태 변경 이벤트가 먼저 오면 다음 중 하나를 선택합니다.

- aggregate별 보류 목록에 저장합니다.
- 원본 log position을 남기고 나중에 다시 읽습니다.
- 일정 시간이 지나면 정본을 조회해 전체 상태를 다시 만듭니다.
- 잘못된 event로 분류해 운영 확인 대상으로 보냅니다.

보류 목록에는 최대 크기와 보존 시간, 다시 처리할 작업이 필요합니다. 계속 쌓이기만 하는 보류 목록은 복구 방법이 아닙니다.

## 적용 뒤 checkpoint를 저장합니다

at-least-once consumer에서는 다음 순서를 사용합니다.

```text
이벤트 읽기
→ 중복 없이 조회 모델에 적용
→ 적용 결과 저장
→ checkpoint 전진
```

checkpoint를 먼저 전진시키면 적용 전에 중단된 이벤트를 다시 읽을 수 없습니다. 반대로 적용 뒤 checkpoint 저장 전에 중단되면 같은 이벤트가 다시 들어오므로 적용 코드는 event ID를 기준으로 중복을 막아야 합니다.

## 전체 로그로 다시 만들 수 있어야 합니다

조회 모델은 파생 데이터이므로 필요할 때 새 저장소에 다시 구축할 수 있어야 합니다.

1. 빈 조회 저장소를 준비합니다.
2. 고정한 시작 위치부터 이벤트를 재생합니다.
3. 현재 처리 위치와 lag를 기록합니다.
4. 원본과 핵심 합계·개수를 비교합니다.
5. 새 조회 모델이 따라잡으면 읽기 트래픽을 전환합니다.
6. 이전 저장소는 문제가 없는지 확인할 때까지 보존합니다.

재구축 중 새 이벤트가 계속 들어오는 경우에는 snapshot이 포함한 마지막 log position과 이후 재생 시작 위치를 연결해야 합니다.

## 흔한 잘못

- 대상이 없다는 이유로 이벤트를 버립니다.
- 적용 전에 checkpoint를 저장합니다.
- 재전달된 이벤트가 집계 값을 다시 늘립니다.
- 마지막 처리 위치와 갱신 시각을 알 수 없습니다.
- 빈 저장소에서 다시 만드는 경로가 없습니다.
- 행 수 하나만 비교하고 재구축 완료로 판단합니다.
- 조회 모델을 최신 정본처럼 사용해 쓰기 여부를 결정합니다.

## 검증 방법

다음 두 중단 지점을 구분해 검사합니다.

```text
적용 뒤 checkpoint 저장 전 중단
→ 같은 event 재처리
→ 최종 합계는 한 번만 증가
```

```text
checkpoint 저장 뒤 적용 전 중단
→ 잘못된 구현에서는 event 유실
→ 테스트가 유실을 검출
```

전체 로그를 새 Projection에 재생한 결과도 정상 Projection과 같아야 합니다.
