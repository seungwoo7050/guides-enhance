# 멱등성과 단일 업무 효과

## 목표

같은 request나 event가 여러 번 들어와도 상태 변경과 외부 효과가 한 번만 남게 합니다. 전달 횟수를 줄이는 것과 업무 효과 횟수를 제한하는 것을 구분합니다.

## 재전달은 피할 수 없습니다

다음 순서에서는 같은 입력이 다시 들어올 수 있습니다.

```text
상태 변경 성공
→ 응답 또는 ACK 유실
→ 호출자나 Broker가 같은 입력을 다시 전달
```

전송 도구가 한 번만 전달한다고 주장하더라도 데이터베이스, 외부 API와 프로세스 재시작까지 하나의 원자 작업으로 묶어 주지는 않습니다. 업무 효과가 한 번만 남는지는 상태를 바꾸는 코드가 보장해야 합니다.

멱등성은 같은 HTTP 상태 코드를 반환하는 것만 뜻하지 않습니다. 같은 업무 입력을 다시 받아도 최종 상태와 외부 효과가 늘어나지 않고, 호출자가 이전 결과를 다시 확인할 수 있어야 합니다.

## ID의 범위를 업무 입력과 맞춥니다

ID는 문자열만 비교해서는 부족합니다. 적어도 다음 항목과 함께 해석합니다.

```text
요청 주체
명령 종류
대상 자원
입력 지문
보존 기간
```

예를 들어 `op-123`을 예약 생성과 예약 취소에 함께 사용하거나, 같은 ID에 다른 수량을 넣으면 이전 결과를 잘못 재사용할 수 있습니다. 서버는 ID와 입력 지문을 함께 저장하고, 같은 ID에 다른 입력이 오면 충돌로 거절합니다.

event ID와 업무 효과 ID가 다른 경우도 있습니다.

```text
event_id      = Broker가 전달하는 이벤트 한 건
operation_id  = 실제로 한 번만 적용해야 하는 업무 한 건
```

하나의 업무 효과가 여러 이벤트를 통해 요청될 수 있다면 event ID 중복 제거만으로는 충분하지 않습니다.

## 중복 기록과 상태 변경을 함께 저장합니다

다음 순서는 안전하지 않습니다.

```text
업무 상태 변경
→ commit
→ 다른 transaction에서 processed_event 저장
```

첫 commit 뒤 프로세스가 멈추면 재전달된 이벤트가 상태를 다시 바꿀 수 있습니다.

다음 중 하나를 사용합니다.

- 상태 변경과 processed event 삽입을 같은 transaction에서 수행합니다.
- 업무 테이블의 unique key가 중복 효과 자체를 막게 합니다.
- 현재 version을 조건으로 update해 이미 바뀐 상태를 다시 변경하지 않습니다.
- 외부 효과는 Outbox에 기록하고 같은 operation ID로 전달합니다.

## 이전 결과를 보관합니다

중복 요청을 그냥 무시하면 호출자는 결과를 알 수 없습니다. 처리 기록에는 필요에 따라 다음 값을 저장합니다.

- 입력 지문
- 현재 처리 상태
- 결과 자원의 ID
- 생성·완료 시각
- 다시 시도할 수 있는 실패인지 여부
- 기록을 지울 수 있는 시각

완료된 요청은 이전 결과를 반환합니다. 처리 중인 요청은 `PENDING`을 반환하고, 같은 ID가 동시에 두 번 실행되지 않게 합니다.

## 외부 효과도 별도로 확인합니다

결제, 이메일과 다른 서비스 호출은 local DB transaction에 들어오지 않습니다. 외부 서비스가 멱등성 키를 지원하면 같은 operation ID를 전달합니다. 지원하지 않으면 Outbox 상태와 외부 조회 API로 실제 적용 여부를 확인해야 합니다.

DB 행이 하나라는 사실만으로 결제가 한 번 실행되었다고 보장할 수는 없습니다.

## 흔한 잘못

- 재시도마다 새 ID를 만듭니다.
- ID만 비교하고 입력 지문을 확인하지 않습니다.
- 상태 변경과 중복 기록을 다른 transaction에 저장합니다.
- 중복 요청을 무시하지만 이전 결과를 반환하지 않습니다.
- 기록을 너무 빨리 지워 늦은 재전달을 새 요청으로 처리합니다.
- event ID 중복 제거만으로 모든 업무 효과가 안전하다고 가정합니다.
- local DB만 확인하고 외부 효과 횟수는 검사하지 않습니다.

## 검증 방법

다음 실패 지점을 직접 만듭니다.

```text
업무 효과 적용
→ ACK 직전에 중단
→ 같은 event ID 재전달
→ 효과 횟수와 최종 값이 그대로인지 확인
```

같은 ID를 동시에 처리하는 경우도 검사합니다. 실행 하나만 값을 바꾸고 다른 실행은 저장된 결과를 읽어야 합니다.

## 관련 프로젝트

- [`duplicate-delivery`](../../exercises/duplicate-delivery/)는 ACK 유실과 재전달만 작게 확인합니다.
- 필수 프로젝트인 [`outbox-reconciliation`](../../exercises/outbox-reconciliation/)은 Outbox 재발행과 소비자 중복 처리를 함께 다룹니다.

## 완료 기준

- ID가 식별하는 업무 입력의 범위를 정할 수 있습니다.
- 같은 ID와 다른 입력을 상태 변경 전에 거절합니다.
- 중복 기록과 상태 변경을 함께 저장해야 하는 이유를 설명할 수 있습니다.
- local 상태뿐 아니라 외부 효과 횟수도 검사합니다.
