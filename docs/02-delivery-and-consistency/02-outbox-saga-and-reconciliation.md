# Outbox, Saga와 재조정

## 목표

local transaction과 원격 전송 사이의 누락을 Outbox로 막고, 여러 서비스가 일부만 성공한 상태를 Saga와 재조정으로 마무리합니다.

## 상태 저장과 메시지 전송은 한 번에 끝나지 않습니다

다음 순서는 메시지를 잃을 수 있습니다.

```text
DB commit 성공
→ 프로세스 중단
→ Broker 전송 미실행
```

순서를 바꾸면 반대 문제가 생깁니다.

```text
Broker 전송 성공
→ DB commit 실패
```

Outbox는 서비스가 소유한 상태 변경과 발행할 이벤트를 같은 local transaction에 저장합니다. commit되면 둘 다 남고 rollback되면 둘 다 사라집니다.

## Outbox가 보장하는 범위를 제한합니다

Outbox를 저장했다고 메시지가 한 번만 전달되는 것은 아닙니다.

```text
Broker 전송 성공
→ published 표시 전에 중단
→ 같은 Outbox 행을 다시 전송
```

따라서 다음이 필요합니다.

- 전송할 때마다 바뀌지 않는 event ID
- 소비자의 멱등 처리
- 전송 시도 횟수와 마지막 오류
- 가장 오래된 미발행 행의 대기 시간
- 여러 발행기가 같은 행을 처리하지 않게 하는 lease 또는 row lock
- 계속 실패하는 행을 따로 분리하는 기준

Outbox는 local DB와 Broker 사이의 누락 가능성을 줄이지만 여러 서비스의 transaction을 하나로 만들지는 않습니다.

## Saga는 상태와 다음 행동을 저장합니다

Saga를 “실패하면 반대 API를 호출한다”로만 이해하면 위험합니다. 원래 명령이 실제로 적용되었는지 모르는 상태에서 보상하면 없던 효과를 새로 만들 수 있습니다.

단계마다 다음을 정합니다.

```text
실행할 명령
성공 상태
거절 상태
결과를 알 수 없는 상태
보상을 시작할 조건
보상에 사용할 operation ID
다시 시도할 조건과 종료 조건
```

읽기 모델 갱신처럼 원본 상태를 되돌릴 필요가 없는 작업은 보상보다 전진 복구가 낫습니다. 빠진 이벤트를 다시 발행해 조회 모델을 따라잡게 하면 됩니다.

## 중간 상태를 데이터로 남깁니다

분산 처리에서는 중간 상태가 필요합니다.

```text
PENDING
UNKNOWN
ACCEPTED
REJECTED
COMPENSATING
COMPLETED
RECONCILIATION_REQUIRED
```

이를 예외나 로그에만 남기면 프로세스가 재시작된 뒤 무엇을 해야 할지 알 수 없습니다. 각 상태에 다음 정보를 연결합니다.

- 다음으로 바꿀 수 있는 상태
- 현재 상태를 변경할 서비스
- 다시 확인할 시각
- 처음 사용한 operation ID
- 마지막으로 확인한 정본과 결과

## 재조정은 정상 실행에 포함합니다

재조정 작업은 오래 남은 `PENDING`, `UNKNOWN`, `COMPENSATING` 상태를 찾아 정본을 확인합니다. 결과가 있으면 같은 operation ID로 상태를 마무리하고, 결과를 확인할 수 없으면 다음 시각을 기록하거나 운영자에게 넘깁니다.

여러 인스턴스가 재조정을 실행할 수 있으므로 다음을 지킵니다.

- lease나 조건부 update로 같은 건을 동시에 처리하지 않습니다.
- 다른 인스턴스가 이어받아도 operation ID를 바꾸지 않습니다.
- 어떤 정본을 확인했고 왜 상태를 바꿨는지 기록합니다.
- 성공, 거절, 다시 확인할 상태와 수동 확인이 필요한 상태를 구분합니다.
- 처리 건수뿐 아니라 가장 오래된 대기 시간도 측정합니다.

## 흔한 잘못

- 상태와 Outbox를 다른 transaction에 저장합니다.
- Broker로 보내기 전에 Outbox를 완료로 표시합니다.
- 전송 성공 뒤 표시 실패로 같은 event가 다시 갈 수 있다는 점을 무시합니다.
- 보상할 때 새 operation ID를 만듭니다.
- `PENDING`에 다시 확인할 시각과 담당 작업이 없습니다.
- 재조정이 원래 ID 대신 새 요청을 만듭니다.
- 미발행 행 수만 보고 가장 오래된 대기 시간은 보지 않습니다.

## 검증 방법

다음 상황을 각각 재현합니다.

1. 상태와 Outbox가 함께 저장됩니다.
2. Broker가 중단되면 Outbox가 미발행 상태로 남습니다.
3. 전송 뒤 완료 표시 전에 중단되면 같은 event가 다시 전달됩니다.
4. 소비자는 재전달에도 업무 효과를 한 번만 적용합니다.
5. Broker가 복구되면 남은 Outbox가 모두 전송됩니다.
6. 보상 중 중단되면 `COMPENSATING`이 남고 다음 재조정이 이어서 처리합니다.

## 관련 프로젝트

[`outbox-reconciliation`](../../exercises/outbox-reconciliation/)은 Outbox 재발행과 소비자 중복 처리, 결제 거절 뒤 재고 보상 실패를 한 모델에서 확인합니다.

## 완료 기준

- Outbox가 보장하는 local 저장과 보장하지 않는 원격 처리를 구분할 수 있습니다.
- Saga 단계마다 성공·거절·미확정·보상 상태를 정의할 수 있습니다.
- 오래 남은 중간 상태를 누가 언제 다시 확인할지 정할 수 있습니다.
- 전송 뒤 중단과 보상 중단을 테스트할 수 있습니다.
