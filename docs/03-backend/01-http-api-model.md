# HTTP API 모델

HTTP API는 단순히 JSON을 주고받는 함수 호출이 아닙니다. HTTP 메서드, 경로, 상태 코드, 헤더, 본문이 함께 하나의 외부 계약(contract)을 만듭니다. 클라이언트는 이 계약을 기준으로 요청을 만들고, 성공과 실패를 구분하고, 재시도 여부를 판단합니다.

따라서 정상 응답만 설계해서는 충분하지 않습니다. 입력 오류, 인증 실패, 권한 부족, 리소스 없음, 현재 상태와의 충돌, 요청 과다, 일시적인 장애와 예상하지 못한 서버 오류도 서로 구분해야 합니다.

## 목표

- 리소스와 작업의 성격에 맞는 HTTP 메서드와 경로를 선택합니다.
- 경로·쿼리·헤더·본문이 각각 어떤 정보를 표현하는지 구분합니다.
- 실패 원인에 맞는 상태 코드와 오류 응답 형식을 정합니다.
- 페이지네이션, 동시 수정 충돌과 멱등성의 기본 원리를 이해합니다.
- HTTP 요청 해석과 업무 규칙 처리를 서로 다른 코드에 둡니다.

## HTTP API를 외부 계약으로 봅니다

예를 들어 다음 API가 있다고 가정합니다.

```text
GET    /boards
POST   /boards
GET    /boards/:id
PATCH  /boards/:id
DELETE /boards/:id
GET    /boards/:id/activity
```

각 요소는 서로 다른 의미를 가집니다.

```text
GET /boards/42?include=members
```

- `GET`: 무엇을 할 것인지 나타내는 HTTP 메서드
- `/boards/42`: 어떤 리소스를 대상으로 하는지 나타내는 경로
- `include=members`: 조회 방식을 조정하는 쿼리
- 요청 헤더: 인증 정보, 콘텐츠 형식, 조건부 요청 등의 메타데이터
- 요청 본문: 생성하거나 변경할 실제 데이터

이 중 어느 하나라도 클라이언트가 의존하고 있다면 API의 공개 규칙입니다. 서버 구현을 바꾸더라도 이 규칙을 임의로 바꾸면 기존 클라이언트가 깨질 수 있습니다.

## 경로와 리소스

경로에는 주로 **대상 리소스와 리소스 사이의 관계**를 표현합니다.

```text
GET    /boards
POST   /boards
GET    /boards/:id
PATCH  /boards/:id
DELETE /boards/:id
GET    /boards/:id/activity
```

예를 들어 `/boards/42`는 `42`라는 식별자를 가진 board를 뜻하고, `/boards/42/activity`는 그 board와 관련된 activity 컬렉션을 뜻합니다.

조회 조건은 보통 쿼리에 둡니다.

```text
GET /boards?role=editor&cursor=abc&limit=20
```

여기서 `role`, `cursor`, `limit`은 어떤 board 컬렉션을 어떤 방식으로 조회할지 조정합니다.

다음과 같은 구분이 일반적입니다.

```text
/boards/42
```

특정 리소스를 식별합니다.

```text
/boards?role=editor
```

리소스 목록에 필터 조건을 적용합니다.

모든 동작을 다음처럼 만들 수도 있습니다.

```text
POST /getBoards
POST /createBoard
POST /deleteBoard
```

하지만 이렇게 하면 HTTP 메서드 자체가 제공하는 조회, 생성, 삭제, 캐시 가능성, 재시도 특성과 같은 의미를 활용하기 어렵습니다.

반대로 모든 업무 동작을 억지로 CRUD(Create, Read, Update, Delete)에 끼워 맞출 필요도 없습니다. 업무상 독립적인 명령이 명확하다면 명령을 리소스나 하위 리소스로 모델링할 수 있습니다.

예를 들어 주문 취소가 단순한 필드 수정이 아니라 별도의 업무 규칙을 가진 동작이라면 다음과 같은 형태도 가능합니다.

```text
POST /orders/42/cancellations
```

중요한 것은 URL 모양 자체보다 API 전체에서 의미가 일관되는 것입니다.

## 메서드의 의미

| 메서드 | 일반적인 용도 | 반복 요청의 성질 |
|---|---|---|
| `GET` | 리소스 조회 | 서버의 의미 있는 상태를 변경하지 않아야 합니다. |
| `POST` | 리소스 생성 또는 명령 실행 | 기본적으로 같은 요청을 반복하면 효과가 중복될 수 있습니다. |
| `PUT` | 지정한 리소스의 전체 표현을 생성하거나 대체 | 같은 요청을 여러 번 보내도 같은 최종 상태를 목표로 합니다. |
| `PATCH` | 리소스 일부 변경 | 패치의 정의에 따라 멱등할 수도, 아닐 수도 있습니다. |
| `DELETE` | 리소스 삭제 | 여러 번 실행해도 삭제된 최종 상태를 목표로 합니다. |

### 안전성과 멱등성은 다른 개념입니다

`GET`은 일반적으로 **safe method**, 즉 리소스의 의미 있는 상태 변경을 목적으로 하지 않는 메서드입니다.

반면 `PUT`과 `DELETE`는 상태를 변경할 수 있지만 **idempotent method**, 즉 같은 요청을 여러 번 적용했을 때 한 번 적용한 것과 같은 최종 상태를 만들도록 정의된 메서드입니다.

예를 들어 다음 `PUT` 요청을 여러 번 보내더라도 최종 이름은 계속 `"alpha"`입니다.

```http
PUT /boards/42
Content-Type: application/json

{
  "name": "alpha"
}
```

반면 다음처럼 호출할 때마다 카운터를 1 증가시키는 `PATCH`는 멱등하지 않습니다.

```http
PATCH /boards/42
Content-Type: application/json

{
  "incrementViewCount": 1
}
```

### GET으로 상태를 변경하지 않습니다

`GET` 요청으로 서버 데이터를 변경하는 API는 피해야 합니다.

```text
GET /boards/42/delete
```

이런 설계는 위험합니다. 브라우저, 프록시, 검색 엔진, 링크 미리보기 도구 등이 사용자의 명시적인 실행 의도 없이 `GET` 요청을 보낼 수 있기 때문입니다.

조회 과정에서 접근 로그, 캐시 갱신처럼 부수적인 내부 효과가 발생할 수는 있지만, 사용자가 기대하는 업무 상태를 변경하는 동작을 `GET`에 두어서는 안 됩니다.

## 입력이 들어오는 위치

HTTP 요청의 입력은 여러 위치에서 들어옵니다.

- 경로 매개변수: 대상 리소스 식별
- 쿼리: 필터, 정렬, 검색 옵션, 페이지네이션
- 헤더: 인증, 조건부 요청, 콘텐츠 형식, 추적 정보
- 본문: 생성하거나 변경할 값

예를 들어 다음 요청을 봅니다.

```http
PATCH /boards/42?notify=true
Authorization: Bearer ...
If-Match: "12"
Content-Type: application/json

{
  "title": "Backend Study"
}
```

각 값의 역할은 다음과 같습니다.

- `42`: 변경할 board 식별자
- `notify=true`: 변경 과정의 선택적 동작
- `Authorization`: 인증 정보
- `If-Match`: 클라이언트가 알고 있는 리소스 버전에 대한 조건
- `Content-Type`: 본문 표현 형식
- `title`: 실제로 변경할 값

어느 위치에 있든 모두 **외부 입력**입니다. 서버는 신뢰하지 않고 검증해야 합니다.

TypeScript 클라이언트가 다음 타입을 사용한다고 해도 서버 검증은 필요합니다.

```ts
type UpdateBoardRequest = {
  title: string;
};
```

TypeScript 타입은 해당 클라이언트 프로그램의 컴파일 과정에서만 검사됩니다. 다른 프로그램은 직접 HTTP 요청을 보낼 수 있고, 기존 클라이언트의 버그나 변조된 요청도 들어올 수 있습니다.

따라서 서버는 최소한 다음을 확인해야 합니다.

- 필요한 값이 존재하는가
- 값의 타입과 형식이 올바른가
- 길이나 범위 제한을 만족하는가
- 허용되지 않은 값을 포함하지 않는가
- 현재 사용자에게 해당 작업 권한이 있는가
- 현재 리소스 상태에서 해당 작업이 가능한가

## HTTP 처리와 업무 처리를 분리합니다

HTTP 계층은 HTTP 요청을 해석하고 HTTP 응답으로 변환하는 책임을 가집니다.

예를 들어 다음 작업이 HTTP 계층의 책임입니다.

```text
경로 매개변수 읽기
쿼리 읽기
헤더 읽기
JSON 본문 파싱
입력 검증
인증 정보 추출
서비스 호출
업무 오류를 HTTP 상태 코드로 변환
응답 헤더와 본문 작성
```

반면 다음과 같은 규칙은 업무 계층에 두는 편이 좋습니다.

```text
board 이름 중복 금지
소유자만 board 삭제 가능
마감된 board는 수정 불가
현재 version과 baseVersion이 같을 때만 수정
```

예를 들어 handler 안에서 모든 업무 규칙을 직접 처리하면 다음 문제가 생깁니다.

```ts
async function patchBoard(req, res) {
  // 파싱
  // 인증
  // 권한 검사
  // DB 조회
  // 버전 검사
  // 업무 규칙
  // DB 수정
  // 오류 매핑
  // 응답 생성
}
```

HTTP 코드와 업무 규칙이 뒤섞여 테스트와 재사용이 어려워집니다.

대신 개념적으로 다음과 같이 나눌 수 있습니다.

```text
HTTP handler
    ↓
application/service
    ↓
domain/repository
```

HTTP handler는 요청과 응답 형식에 집중하고, 서비스는 실제 업무 규칙을 처리합니다.

## 상태 코드

상태 코드는 클라이언트가 요청 결과를 기계적으로 구분할 수 있게 합니다.

| 상태 | 의미 |
|---:|---|
| `200 OK` | 요청 성공, 보통 응답 본문이 있음 |
| `201 Created` | 새 리소스 생성 성공 |
| `204 No Content` | 요청 성공, 응답 본문 없음 |
| `400 Bad Request` | 요청 구문, 형식 또는 입력 값이 올바르지 않음 |
| `401 Unauthorized` | 유효한 인증 정보가 없거나 인증에 실패함 |
| `403 Forbidden` | 사용자는 식별되었지만 해당 작업 권한이 없음 |
| `404 Not Found` | 경로나 공개 가능한 대상 리소스를 찾을 수 없음 |
| `409 Conflict` | 현재 리소스 상태, 버전 또는 고유성 규칙과 요청이 충돌함 |
| `412 Precondition Failed` | `If-Match` 같은 HTTP 조건부 요청의 조건이 만족되지 않음 |
| `429 Too Many Requests` | 요청 빈도 제한을 초과함 |
| `500 Internal Server Error` | 서버가 예상하지 못한 오류를 만남 |
| `503 Service Unavailable` | 서버 또는 의존 서비스가 일시적으로 요청을 처리할 수 없음 |

### 200

조회 성공이나 일반적인 작업 성공에 사용합니다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id": 42,
  "title": "Backend Study"
}
```

### 201

새 리소스를 생성한 경우 사용합니다.

가능하다면 생성된 리소스의 위치를 `Location` 헤더로 알려줄 수 있습니다.

```http
HTTP/1.1 201 Created
Location: /boards/42
Content-Type: application/json

{
  "id": 42,
  "title": "Backend Study"
}
```

### 204

성공했지만 반환할 본문이 없는 경우 사용할 수 있습니다.

```http
HTTP/1.1 204 No Content
```

`204` 응답에는 응답 본문을 넣지 않습니다.

### 400

요청 자체의 형식이나 입력 값이 잘못된 경우 사용합니다.

예:

```text
필수 필드 누락
잘못된 JSON
허용되지 않는 enum 값
limit이 허용 범위를 벗어남
날짜 형식 오류
```

### 401

클라이언트가 인증되지 않은 경우입니다.

예:

```text
Authorization 헤더 없음
토큰 만료
서명이 올바르지 않은 토큰
```

이름은 `Unauthorized`이지만 실제 의미는 일반적으로 **인증(authentication)이 필요함**에 가깝습니다.

### 403

사용자는 누구인지 확인되었지만 해당 작업을 수행할 권한이 없는 경우입니다.

예:

```text
일반 사용자가 관리자 전용 API 호출
다른 사용자의 공개 리소스에 대한 수정 시도
```

### 404

요청한 경로나 리소스를 찾을 수 없거나, 보안 정책상 존재 여부를 공개하지 않기로 한 경우 사용할 수 있습니다.

### 409

요청 형식 자체는 올바르지만 현재 서버 상태와 충돌할 때 사용합니다.

예:

```text
이미 존재하는 고유 이름 생성
현재 상태에서는 허용되지 않는 상태 전이
애플리케이션 수준의 버전 충돌
```

### 500

서버 내부에서 예상하지 못한 오류가 발생했을 때 사용합니다.

다음과 같은 입력 오류를 단순히 `500`으로 반환해서는 안 됩니다.

```text
필수 값 누락
잘못된 날짜
리소스 없음
권한 없음
버전 충돌
```

이런 오류는 예상 가능한 실패이며 각각 적절한 4xx 상태로 표현해야 합니다.

### 503

서버 또는 필수 의존 서비스가 일시적으로 사용 불가능한 경우 사용할 수 있습니다.

예:

```text
필수 데이터베이스가 일시적으로 사용 불가능
점검으로 서비스를 잠시 제공할 수 없음
과부하 때문에 요청을 일시적으로 받을 수 없음
```

`500`은 예상하지 못한 서버 오류이고, `503`은 현재 일시적으로 서비스를 제공할 수 없다는 의미를 전달하는 데 더 적합합니다.

## 모든 실패를 200으로 반환하지 않습니다

다음과 같은 응답 형식은 피하는 것이 좋습니다.

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "success": false,
  "error": "not_found"
}
```

HTTP 상태는 성공이지만 본문에서는 실패라고 말하고 있습니다.

이렇게 하면 브라우저, 프록시, HTTP 클라이언트, 모니터링 시스템이 응답을 성공으로 판단할 수 있습니다. 클라이언트 코드도 모든 요청마다 본문을 직접 읽어 실패 여부를 다시 판단해야 합니다.

대신 HTTP 상태와 본문의 오류 정보를 일치시킵니다.

```http
HTTP/1.1 404 Not Found
Content-Type: application/json

{
  "code": "board_not_found",
  "message": "보드를 찾을 수 없습니다."
}
```

## 오류 응답 형식

API 전체에서 오류 응답 형식을 일정하게 유지하면 클라이언트 구현이 단순해집니다.

```json
{
  "code": "invalid_request",
  "message": "요청 형식이 올바르지 않습니다.",
  "details": [
    { "path": "title", "reason": "too_long" }
  ],
  "requestId": "req_01..."
}
```

각 필드의 역할을 구분합니다.

### code

클라이언트 코드가 분기할 수 있는 안정적인 식별자입니다.

```text
invalid_request
board_not_found
version_conflict
permission_denied
```

사람에게 보여 주는 문장과 분리해야 합니다.

예를 들어 클라이언트가 다음처럼 분기할 수 있습니다.

```ts
if (error.code === "version_conflict") {
  showReloadDialog();
}
```

오류 메시지의 표현이 바뀌더라도 `code`가 유지되면 클라이언트 코드는 영향을 덜 받습니다.

### message

사용자 또는 개발자에게 보여 줄 수 있는 설명입니다.

```json
{
  "message": "보드가 다른 사용자에 의해 변경되었습니다."
}
```

보안상 외부에 공개해도 되는 정보만 포함합니다.

### details

특정 입력 필드나 여러 검증 오류에 대한 추가 정보를 제공할 수 있습니다.

```json
{
  "details": [
    {
      "path": "title",
      "reason": "too_long"
    },
    {
      "path": "visibility",
      "reason": "invalid_value"
    }
  ]
}
```

### requestId

로그와 요청을 연결하기 위한 추적 식별자입니다.

사용자가 오류를 신고했을 때 다음 값을 통해 서버 로그에서 같은 요청을 찾을 수 있습니다.

```text
requestId = req_01...
```

오류 응답에는 다음과 같은 내부 정보를 직접 노출하지 않습니다.

- SQL 문장
- 데이터베이스 접속 정보
- 서버 파일 경로
- 인증 토큰
- 개인정보
- 전체 스택 트레이스
- 내부 서비스 구조를 과도하게 드러내는 메시지

외부 응답에는 안전한 오류 정보를 제공하고, 상세 원인은 내부 로그에 남깁니다.

## 401, 403과 404

세 상태는 자주 혼동됩니다.

```text
401
누구인지 유효하게 인증되지 않음

403
누구인지는 알지만 이 작업을 할 권한이 없음

404
요청한 리소스를 찾을 수 없거나 존재 여부를 공개하지 않음
```

예를 들어 사용자가 자신의 비공개 board를 조회한다고 가정합니다.

```text
GET /boards/42
```

인증 토큰이 없다면:

```text
401 Unauthorized
```

인증된 사용자가 board의 존재는 알 수 있지만 읽기 권한이 없다면:

```text
403 Forbidden
```

보안 정책상 다른 사용자의 비공개 board가 존재하는지조차 알려 주지 않기로 했다면:

```text
404 Not Found
```

따라서 권한이 없는 사용자가 비공개 리소스의 존재 자체를 알아서는 안 되는 경우 `403` 대신 `404`를 반환할 수 있습니다.

이는 절대 규칙이 아니라 **어떤 정보를 외부에 공개할 것인지에 대한 API 정책**입니다. 같은 종류의 API에서는 일관되게 적용해야 합니다.

외부 응답은 `404`로 숨기더라도 내부 로그에는 실제 판정 이유를 남길 수 있습니다.

```text
response: 404
internal reason: board exists but caller has no visibility
```

## 페이지네이션

목록 API가 모든 항목을 한 번에 반환하면 데이터가 커질수록 응답 크기와 처리 시간이 계속 증가합니다.

따라서 목록에는 일반적으로 반환 개수 제한을 둡니다.

```text
GET /activity?cursor=evt_42&limit=50
```

서버는 `limit`에 최대값을 둘 수 있습니다.

```text
기본 limit = 20
최대 limit = 100
```

클라이언트가 다음처럼 요청하더라도:

```text
GET /activity?limit=1000000
```

서버가 임의의 대용량 응답을 만들지 않도록 제한합니다.

## 오프셋 페이지네이션

가장 단순한 방식은 offset과 limit을 사용하는 것입니다.

```text
GET /activity?offset=0&limit=20
GET /activity?offset=20&limit=20
```

이 방식은 이해하기 쉽고 특정 페이지로 이동하기도 쉽습니다.

하지만 페이지를 읽는 동안 데이터가 추가되거나 삭제되면 문제가 생길 수 있습니다.

처음 데이터가 다음과 같다고 가정합니다.

```text
A B C D E F
```

클라이언트가 첫 두 개를 읽습니다.

```text
offset=0, limit=2
→ A B
```

그 사이 맨 앞에 `X`가 추가됩니다.

```text
X A B C D E F
```

이제 다음 페이지를 읽습니다.

```text
offset=2, limit=2
→ B C
```

`B`가 중복되었습니다.

삭제가 발생하면 반대로 항목을 건너뛸 수도 있습니다.

데이터가 작고 변경이 적다면 오프셋 방식도 충분할 수 있습니다. 다만 이런 특성을 알고 선택해야 합니다.

## 커서 페이지네이션

변경이 많은 목록에서는 커서를 사용할 수 있습니다.

```text
GET /activity?cursor=evt_42&limit=50
```

서버는 현재 페이지와 다음 페이지를 함께 반환할 수 있습니다.

```json
{
  "items": [
    { "id": "evt_41" },
    { "id": "evt_40" }
  ],
  "nextCursor": "evt_40"
}
```

다음 요청은 다음과 같습니다.

```text
GET /activity?cursor=evt_40&limit=50
```

커서는 단순히 임의의 문자열이 아니라 **정렬 기준과 함께 의미가 결정되어야 합니다**.

예를 들어 activity를 다음 순서로 정렬한다고 가정합니다.

```text
createdAt DESC
```

`createdAt` 값이 같은 항목이 여러 개 있을 수 있다면 정렬 순서가 불안정할 수 있습니다.

따라서 다음처럼 고유한 보조 정렬 기준을 추가할 수 있습니다.

```text
createdAt DESC, id DESC
```

커서도 이 정렬 순서를 기준으로 만들어야 합니다.

```text
cursor = (createdAt, id)
```

핵심은 같은 데이터에 대해 페이지를 넘기는 기준이 명확하고 안정적이어야 한다는 것입니다.

## 버전 충돌

여러 클라이언트가 같은 리소스를 동시에 수정하면 **lost update**, 즉 한 사용자의 변경이 다른 사용자의 변경으로 덮어써지는 문제가 생길 수 있습니다.

예를 들어 두 사용자가 모두 version 12를 읽었다고 가정합니다.

```text
사용자 A: version 12 읽음
사용자 B: version 12 읽음
```

A가 먼저 수정합니다.

```text
version 12
→ 수정
→ version 13
```

B가 자신이 읽었던 version 12를 기준으로 수정하면, 아무 검사 없이 저장할 경우 A의 변경을 덮어쓸 수 있습니다.

이를 막으려면 클라이언트가 읽은 버전과 현재 서버 버전이 같은 경우에만 변경하도록 할 수 있습니다.

HTTP 조건부 요청을 사용하면 다음과 같이 표현할 수 있습니다.

```http
PATCH /boards/42/items/7
If-Match: "12"
```

서버의 현재 버전도 `"12"`이면 변경을 허용합니다.

```text
client version = 12
server version = 12
→ 수정 허용
```

서버 버전이 이미 `"13"`이라면:

```text
client version = 12
server version = 13
→ 수정 거부
```

`If-Match` 조건이 실패한 경우 HTTP 의미에 맞게 `412 Precondition Failed`를 사용할 수 있습니다.

```http
HTTP/1.1 412 Precondition Failed
```

애플리케이션 자체의 버전 필드를 본문에 전달하는 방식도 가능합니다.

```json
{
  "title": "New title",
  "baseVersion": 12
}
```

이 방식에서 애플리케이션 수준의 상태 충돌로 다룬다면 `409 Conflict`를 사용할 수 있습니다.

즉 다음을 구분할 수 있습니다.

```text
If-Match 같은 HTTP 조건 실패
→ 412 Precondition Failed

업무 규칙 또는 애플리케이션 버전 충돌
→ 409 Conflict
```

오래된 요청을 거부할 때는 최신 상태를 다시 조회하거나 충돌을 해결할 방법도 제공해야 합니다.

마지막으로 도착한 요청을 무조건 저장하는 방식은 구현은 단순하지만 다른 사용자의 변경이 조용히 사라질 수 있습니다.

## ETag와 If-Match

HTTP 조건부 요청에서는 리소스 버전을 `ETag`로 표현할 수 있습니다.

조회 응답:

```http
HTTP/1.1 200 OK
ETag: "12"
Content-Type: application/json

{
  "id": 42,
  "title": "Backend Study"
}
```

클라이언트는 이후 변경 요청에서 이 값을 보냅니다.

```http
PATCH /boards/42
If-Match: "12"
Content-Type: application/json

{
  "title": "HTTP Study"
}
```

서버가 현재 ETag가 `"12"`인지 검사한 뒤 변경을 수행합니다.

변경 후에는 새 버전을 반환할 수 있습니다.

```http
HTTP/1.1 200 OK
ETag: "13"
Content-Type: application/json

{
  "id": 42,
  "title": "HTTP Study"
}
```

이 방식은 HTTP가 제공하는 조건부 요청 의미를 그대로 활용한다는 장점이 있습니다.

## 멱등성

네트워크 요청에서는 클라이언트가 응답을 받지 못했다고 해서 서버가 요청을 처리하지 않았다고 단정할 수 없습니다.

예를 들어 결제 생성 요청을 보냈다고 가정합니다.

```text
client
  |
  | POST /payments
  v
server
  |
  | 결제 생성 성공
  |
  X 응답 전달 중 네트워크 단절
```

클라이언트 입장에서는 결과를 알 수 없습니다.

```text
요청이 서버에 도착하지 않았는가?
서버가 처리했지만 응답만 사라졌는가?
```

이 상황에서 같은 `POST`를 무조건 다시 보내면 결제가 두 번 생성될 수 있습니다.

이런 중복 실행이 위험한 작업에는 멱등성 키를 사용할 수 있습니다.

```http
POST /payments
Idempotency-Key: 3f3c...
Content-Type: application/json

{
  "amount": 10000
}
```

클라이언트는 같은 논리적 작업을 재시도할 때 같은 키를 사용합니다.

```text
첫 요청
Idempotency-Key: abc123

재시도
Idempotency-Key: abc123
```

서버는 이미 처리한 키라면 같은 작업을 다시 실행하지 않고 이전 결과를 재사용할 수 있습니다.

개념적으로는 다음과 같습니다.

```text
if idempotency key is new:
    execute operation
    store result
    return result

if idempotency key already exists:
    return stored result
```

하지만 헤더를 받는 것만으로 멱등성이 자동으로 생기는 것은 아닙니다. 서버가 키와 실행 결과를 실제로 관리해야 합니다.

서버는 최소한 다음 정책을 정해야 합니다.

- 키가 적용되는 사용자 또는 계정 범위
- 키가 적용되는 API 작업 범위
- 키를 얼마나 오래 보관할지
- 같은 키와 같은 요청이 들어왔을 때 무엇을 반환할지
- 같은 키와 다른 본문이 들어왔을 때 어떻게 처리할지
- 처리 중인 요청에 동일 키 요청이 다시 들어오면 어떻게 할지

예를 들어 같은 키로 다른 요청 본문이 들어오면 충돌로 처리할 수 있습니다.

```text
Idempotency-Key: abc123
amount: 10000
```

이 요청을 처리한 뒤:

```text
Idempotency-Key: abc123
amount: 50000
```

이 들어오면 같은 논리 작업으로 볼 수 없으므로 거부하는 정책을 둘 수 있습니다.

## 재시도 가능성을 상태 코드만으로 판단하지 않습니다

재시도 여부는 메서드, 작업의 성질, 오류 원인을 함께 고려해야 합니다.

예를 들어:

```text
GET /boards
```

일시적인 네트워크 오류가 발생했다면 일반적으로 다시 시도하기 쉽습니다.

반면:

```text
POST /payments
```

응답을 받지 못했다고 무조건 다시 보내면 중복 결제가 발생할 수 있습니다. 이런 작업은 멱등성 키와 같은 별도 보호 장치가 필요합니다.

또한 `500`이나 `503`을 받았다고 해서 모든 요청을 즉시 무한 재시도해서는 안 됩니다. 재시도 횟수, 지연 시간, 서버의 `Retry-After` 정책 등을 함께 고려해야 합니다.

## 흔한 실수

- `GET` 요청으로 업무 상태를 변경합니다.
- 모든 작업을 의미 구분 없이 `POST /doSomething` 형태로 만듭니다.
- 모든 오류를 `200`과 `{ success: false }`로 반환합니다.
- 예상 가능한 입력 오류나 권한 오류까지 모두 `500`으로 반환합니다.
- 검증 도구나 데이터베이스의 내부 오류 메시지를 그대로 외부에 노출합니다.
- 클라이언트의 TypeScript 타입만 믿고 서버 입력 검증을 생략합니다.
- 목록 API에 최대 반환 개수 제한이 없습니다.
- 페이지네이션 정렬 기준이 불안정합니다.
- 동시에 같은 리소스를 수정할 때 충돌 처리 규칙이 없습니다.
- `If-Match` 조건 실패와 일반적인 업무 충돌을 구분하지 않습니다.
- 타임아웃 뒤 멱등성이 보장되지 않은 `POST`를 무조건 다시 전송합니다.
- `Idempotency-Key` 헤더만 받고 실제 중복 실행 방지 로직은 구현하지 않습니다.

## 완료 기준

다음 질문에 설명할 수 있으면 이 문서의 핵심을 이해한 것입니다.

- 왜 특정 경로와 HTTP 메서드를 선택했는가?
- 경로, 쿼리, 헤더와 본문에는 각각 어떤 정보를 넣어야 하는가?
- `GET`의 안전성과 `PUT`·`DELETE`의 멱등성은 어떻게 다른가?
- `400`, `401`, `403`, `404`, `409`, `412`, `500`을 어떤 기준으로 구분하는가?
- 클라이언트가 오류 메시지 문자열이 아니라 안정적인 오류 코드로 분기할 수 있는가?
- 목록의 최대 크기와 정렬 기준을 정했는가?
- 오프셋과 커서 페이지네이션의 차이를 설명할 수 있는가?
- 동시에 같은 리소스를 변경할 때 변경 손실을 어떻게 막을 것인가?
- 재시도해도 안전한 작업과 그렇지 않은 작업을 구분할 수 있는가?
- 멱등성 키가 실제로 중복 실행을 막으려면 서버가 무엇을 저장해야 하는가?
- HTTP handler와 업무 규칙이 한 코드에 뒤섞이지 않았는가?
