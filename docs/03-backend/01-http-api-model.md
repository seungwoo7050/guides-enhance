# HTTP API 모델

HTTP API는 JSON을 주고받는 함수 호출이 아닙니다. 메서드, 경로, 상태 코드, 헤더와 본문이 함께 외부 사용자가 의존하는 규칙을 만듭니다. 정상 응답뿐 아니라 입력 오류, 인증 실패, 권한 부족, 리소스 없음, 충돌과 내부 오류도 구분해야 합니다.

## 목표

- 리소스와 작업에 맞는 HTTP 메서드와 경로를 선택합니다.
- 경로·쿼리·헤더·본문의 용도를 구분합니다.
- 실패 원인에 맞는 상태 코드와 응답 형식을 정합니다.
- 페이지네이션, 버전 충돌과 멱등성의 기본 원리를 이해합니다.
- HTTP 처리와 업무 처리를 서로 다른 코드에 둡니다.

## 경로와 리소스

```text
GET    /boards
POST   /boards
GET    /boards/:id
PATCH  /boards/:id
DELETE /boards/:id
GET    /boards/:id/activity
```

경로에는 주로 대상 리소스와 관계를 표현합니다. 조회 조건은 쿼리에 둡니다.

```text
GET /boards?role=editor&cursor=abc&limit=20
```

모든 작업을 `/doSomething` 형태의 POST로 만들면 HTTP가 제공하는 조회·변경 의미를 활용하기 어렵습니다. 반대로 업무상 명령이 분명한 작업을 억지로 CRUD 용어에 맞출 필요도 없습니다.

## 메서드의 의미

| 메서드 | 일반적인 용도 | 반복 요청 |
|---|---|---|
| `GET` | 조회 | 서버 상태를 바꾸지 않아야 합니다. |
| `POST` | 생성 또는 명령 실행 | 기본적으로 중복 실행될 수 있습니다. |
| `PUT` | 전체 대체 | 같은 요청이 같은 최종 상태를 만들어야 합니다. |
| `PATCH` | 일부 변경 | 작업 정의에 따라 달라집니다. |
| `DELETE` | 삭제 | 반복해도 같은 최종 상태를 목표로 합니다. |

`GET`으로 서버 데이터를 바꾸지 않습니다. 브라우저나 프록시가 사용자의 명시적인 클릭 없이 GET을 미리 보낼 수 있습니다.

## 입력이 들어오는 위치

- 경로 매개변수: 대상 리소스
- 쿼리: 필터, 정렬, 페이지네이션
- 헤더: 인증, 조건부 요청, 콘텐츠 형식
- 본문: 생성하거나 변경할 값

어느 위치에 있든 외부 입력입니다. TypeScript로 작성한 클라이언트가 보낸 값도 서버에서 다시 검사합니다.

## 상태 코드

| 상태 | 의미 |
|---:|---|
| `200` | 성공, 응답 본문 있음 |
| `201` | 리소스 생성 성공 |
| `204` | 성공, 응답 본문 없음 |
| `400` | 요청 형식이나 값이 올바르지 않음 |
| `401` | 유효한 인증 정보가 없음 |
| `403` | 사용자는 확인했지만 작업 권한이 없음 |
| `404` | 경로나 공개 가능한 리소스를 찾지 못함 |
| `409` | 현재 상태·버전·고유성 규칙과 충돌함 |
| `429` | 요청 빈도 제한을 넘음 |
| `500` | 예상하지 못한 서버 오류 |
| `503` | 서버가 일시적으로 요청을 처리할 준비가 되지 않음 |

모든 실패를 `200`과 `{ success: false }`로 반환하면 브라우저, 프록시와 모니터링 도구가 상태를 정확히 구분하지 못합니다.

## 오류 응답 형식

```json
{
  "code": "invalid_request",
  "message": "요청 형식이 올바르지 않습니다.",
  "details": [
    { "path": "title", "reason": "too_long" }
  ],
  "requestId": "req_01..."
}
```

`code`는 클라이언트가 분기할 수 있도록 안정적으로 유지합니다. `message`에는 외부에 공개해도 되는 문장을 넣습니다. SQL 문장, 파일 경로, 토큰, 개인정보와 전체 스택은 응답에 포함하지 않습니다.

## 401, 403과 404

권한이 없는 사용자가 비공개 리소스의 존재 자체를 알아서는 안 되는 경우 403 대신 404를 반환할 수 있습니다. 이는 절대 규칙이 아니라 어떤 정보를 외부에 공개할지에 대한 선택입니다. 같은 API 안에서는 일관되게 적용하고, 내부 로그에는 실제 판정 이유를 남깁니다.

## 페이지네이션

큰 목록을 제한 없이 반환하지 않습니다.

```text
GET /activity?cursor=evt_42&limit=50
```

커서는 정렬 기준과 함께 정해야 합니다. 오프셋 방식은 중간에 항목이 추가되거나 삭제되면 중복과 누락이 생길 수 있습니다. 데이터가 작다면 오프셋으로 충분할 수 있지만 한계를 알고 사용합니다.

## 버전 충돌

클라이언트가 읽은 버전과 서버의 현재 버전이 같을 때만 변경을 허용할 수 있습니다.

```http
PATCH /boards/42/items/7
If-Match: "12"
```

또는 본문에 `baseVersion`을 넣습니다. 오래된 요청은 409 또는 조건부 요청에 맞는 412로 거부하고, 최신 값을 다시 받을 방법을 제공합니다. 마지막으로 도착한 요청이 항상 이기게 하면 다른 사용자의 변경이 사라질 수 있습니다.

## 멱등성

네트워크 타임아웃 뒤에는 서버가 POST를 처리했는지 알 수 없을 수 있습니다. 중복 실행이 위험한 작업에는 멱등성 키를 사용할 수 있습니다.

```http
Idempotency-Key: 3f3c...
```

서버는 다음을 정해야 합니다.

- 키가 적용되는 사용자와 작업 범위
- 키를 보관할 기간
- 같은 키와 다른 본문이 들어왔을 때의 응답
- 이전 성공 결과를 재사용하는 방식

헤더를 받는 것만으로 중복 효과가 자동으로 사라지지는 않습니다.

## 흔한 실수

- GET 요청으로 서버 데이터를 변경합니다.
- 모든 오류를 200이나 500으로 반환합니다.
- 검증 도구의 내부 오류를 그대로 노출합니다.
- 목록에 개수 제한이 없습니다.
- 동시에 같은 리소스를 바꿀 때의 규칙이 없습니다.
- 타임아웃 뒤 POST를 무조건 다시 전송합니다.

## 완료 기준

- 경로, 메서드, 쿼리, 헤더와 본문을 선택한 이유를 설명합니다.
- 400·401·403·404·409·500을 구분합니다.
- 클라이언트가 분기할 안정적인 오류 코드를 제공합니다.
- 목록의 정렬과 페이지네이션 방식을 정합니다.
- 재시도해도 안전한 작업과 그렇지 않은 작업을 구분합니다.
