# 동시성, 취소와 자원 제한

> 선택 심화 문서입니다. 순차 실행이 완성되고 실제 처리량 문제가 확인된 뒤 적용합니다.

## 학습 목표

동시 실행은 여러 작업의 진행 시간을 겹쳐 전체 처리량을 높이는 방법입니다. 특히 외부 프로세스, 파일, 네트워크처럼 **기다리는 시간이 긴 작업**에서 효과가 큽니다.

이 문서에서는 다음 내용을 다룹니다.

- 순차 동작을 먼저 완성해야 하는 이유
- 동시성과 병렬성의 차이
- 스레드, 프로세스, `asyncio`를 선택하는 기준
- 동시에 실행할 작업 수를 제한하는 방법
- 완료 순서와 결과 순서를 구분하는 방법
- 공유 가변 상태를 줄여 경쟁 상태를 피하는 방법
- 취소 요청과 실제 자원 정리 완료의 차이
- 사례 타임아웃, 전체 타임아웃, 종료 유예 시간을 구분하는 방법
- 작업자 예외를 결과 불일치와 구분하는 방법
- 보고서를 한곳에서 저장해야 하는 이유
- 동시성 테스트를 반복해서 재현하는 방법

연결 프로젝트는 [`command-checker`](../../exercises/command-checker/README.md)입니다.

---

## 선행 개념

이 문서를 읽기 전에 다음 내용이 완성되어 있어야 합니다.

- 외부 프로세스 한 건을 순차적으로 실행할 수 있습니다.
- 각 사례의 `returncode`, `stdout`, `stderr`를 검증할 수 있습니다.
- 타임아웃과 출력 상한을 적용할 수 있습니다.
- 각 작업이 자신이 연 파일, 파이프, 프로세스를 정리할 수 있습니다.
- 여러 실행 흐름이 같은 가변 값을 동시에 읽고 쓰면 경쟁 상태가 생길 수 있음을 이해합니다.

동시성은 기존의 잘못된 순차 로직을 자동으로 고쳐 주지 않습니다. 오히려 실행 순서가 매번 달라질 수 있어 원인을 추적하기 더 어려워집니다.

---

## 동시성과 병렬성 구분하기

두 용어는 비슷하지만 같은 뜻은 아닙니다.

**동시성(concurrency)**은 여러 작업의 진행이 시간상 겹치는 구조를 말합니다.

```text
작업 A: 계산 ─ 대기 ─ 계산
작업 B:     계산 ─ 대기 ─ 계산
```

한 작업이 외부 I/O를 기다리는 동안 다른 작업을 진행하면 전체 대기 시간을 겹칠 수 있습니다.

**병렬성(parallelism)**은 여러 작업이 실제로 같은 시점에 서로 다른 CPU 코어 등에서 실행되는 것을 말합니다.

```text
CPU 코어 1: 작업 A 실행
CPU 코어 2: 작업 B 실행
```

`command-checker`의 사례는 대부분 외부 프로세스가 끝나기를 기다리는 작업이므로 핵심 목적은 CPU 병렬 계산이 아니라 **I/O 대기 시간을 겹치는 동시 실행**입니다.

## 순차 실행 규칙부터 완성하기

동시 실행을 추가하기 전에 다음 동작이 순차 실행에서 항상 같아야 합니다.

- 각 사례에 전달할 입력
- 확인할 `returncode`, `stdout`, `stderr`
- 타임아웃과 출력 상한
- 사례 하나가 실패해도 나머지를 계속 실행할지 여부
- 결과를 표시하는 순서
- 전체 종료 상태
- 실행 환경 오류를 어떻게 처리할지
- 각 사례의 자원을 누가 정리할지

예를 들어 순차 실행의 계약을 다음처럼 먼저 고정합니다.

```text
case 1 실행
→ Result 생성
→ case 2 실행
→ Result 생성
→ case 3 실행
→ Result 생성
→ 입력 순서대로 보고서 작성
```

동시 실행을 추가하더라도 사용자에게 보이는 의미는 가능하면 그대로 유지해야 합니다.

```text
case 1, 2, 3은 동시에 실행될 수 있음
→ 각각 Result 생성
→ 입력 순서대로 정렬
→ 동일한 보고서 작성
```

순차 동작이 잘못된 상태에서 동시성을 추가하면 다음 두 문제를 구분하기 어렵습니다.

```text
업무 규칙 자체의 오류
경쟁 상태나 실행 순서에 따른 오류
```

## 스레드, 프로세스, `asyncio` 선택하기

대표적인 동시 실행 방식은 다음과 같습니다.

| 실행 방식 | 적합한 작업 | 주의점 |
|---|---|---|
| `ThreadPoolExecutor` | 외부 프로세스·파일·네트워크 I/O 대기 | 공유 가변 값, 종료 절차, 예외 수집 |
| `ProcessPoolExecutor` | 서로 독립적인 CPU 집약 계산 | 값 직렬화, 프로세스 시작 비용, 자식 프로세스 수명 |
| `asyncio` | 많은 비동기 I/O 작업 | 호출 경로 전체의 비동기 설계, 협력적 취소와 정리 |

### `ThreadPoolExecutor`

스레드는 하나의 프로세스 안에서 메모리를 공유합니다.

따라서 작업자가 다음 값을 함께 변경하면 경쟁 상태가 생길 수 있습니다.

- `dict`
- `list`
- 전역 변수
- 프로세스 전체 환경 변수
- 같은 파일
- 같은 포트

반대로 외부 프로세스가 종료되기를 기다리는 것처럼 대기 시간이 긴 작업에서는 스레드가 단순한 선택일 수 있습니다.

`command-checker`의 각 사례는 대부분 외부 프로세스 실행과 파이프 I/O를 기다리므로 `ThreadPoolExecutor`가 자연스럽습니다.

### `ProcessPoolExecutor`

각 작업을 별도 Python 프로세스에서 실행합니다.

CPU 집약적인 순수 Python 계산을 실제로 여러 CPU 코어에서 수행해야 할 때 적합할 수 있습니다.

대신 다음 비용이 있습니다.

- 작업과 인자를 프로세스 사이에 직렬화해야 합니다.
- 큰 값을 전달하면 복사 비용이 커질 수 있습니다.
- 작업자 프로세스 시작과 종료 비용이 있습니다.
- 작업자 프로세스 안에서 다시 외부 프로세스를 실행하면 프로세스 수명 구조가 더 복잡해집니다.

### `asyncio`

`asyncio`는 많은 비동기 I/O 작업을 하나의 이벤트 루프에서 관리하는 방식입니다.

단, 호출 경로가 다음처럼 비동기 구조로 이어지는 경우에 가장 자연스럽습니다.

```text
async main()
→ await 작업 A
→ await 작업 B
→ await 작업 C
```

동기 함수가 대부분인데 일부 작업만 억지로 `asyncio`로 감싸면 오히려 구조가 복잡해질 수 있습니다.

또한 `asyncio`의 취소도 즉시 강제 종료가 아니라 보통 `await` 지점에서 협력적으로 전달됩니다. 따라서 취소된 코루틴이 자신이 만든 외부 자원을 정리하도록 설계해야 합니다.

## CPython 스레드와 CPU 집약 작업

CPython에서는 일반적인 Python 바이트코드를 여러 스레드가 동시에 실행할 때 GIL의 영향을 받습니다.

따라서 다음과 같은 CPU 집약적인 순수 Python 작업은 스레드 수를 늘린다고 같은 비율로 빨라지지 않을 수 있습니다.

```text
큰 숫자 계산
대규모 Python 루프
CPU를 계속 사용하는 변환 작업
```

반면 외부 프로세스 대기, 파일 I/O, 네트워크 I/O처럼 Python 스레드가 기다리는 시간이 긴 작업은 다른 스레드가 그동안 진행할 수 있습니다.

따라서 `command-checker`에서 스레드를 사용하는 이유는:

```text
CPU 병렬 계산
```

이 아니라:

```text
여러 외부 프로세스의 대기 시간을 겹치기
```

입니다.

## 동시에 실행할 작업 수 제한하기

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=jobs) as executor:
    results = list(executor.map(run_one, cases))
```

`max_workers`는 동시에 실행할 수 있는 작업자의 최대 수입니다.

`jobs`는 1 이상이어야 합니다.

```python
if jobs < 1:
    raise ValueError("jobs는 1 이상이어야 합니다.")
```

사례 수만큼 작업자를 무제한으로 만들면 다음 자원을 쉽게 소모할 수 있습니다.

- 메모리
- 파일 디스크립터
- 파이프
- 프로세스 수
- 임시 디렉터리
- 네트워크 연결
- 고정 포트
- 외부 서비스의 처리 용량

예를 들어 사례 1개가 외부 프로세스 하나와 세 개의 파이프를 사용한다면, 동시 작업 수를 크게 늘릴수록 운영체제 자원 사용량도 함께 증가합니다.

작업자 수는 다음 요소를 고려해 정합니다.

- 한 작업이 사용하는 메모리
- 한 작업이 사용하는 파일 디스크립터 수
- 작업당 생성하는 자식 프로세스 수
- 외부 서비스나 파일 시스템이 감당할 수 있는 동시 요청 수
- 시스템의 CPU와 메모리
- 전체 실행 시간 목표

동시성의 목적은 "가능한 한 많이 동시에 실행"하는 것이 아니라 **자원 한도 안에서 처리량을 높이는 것**입니다.

---

## `jobs == 1`에서는 순차 경로를 유지하기

`command-checker`에서는 다음처럼 설계할 수 있습니다.

```text
jobs == 1
→ 기존 순차 실행 경로 사용

jobs > 1
→ ThreadPoolExecutor 사용
```

예:

```python
if jobs == 1:
    results = [run_one(case) for case in cases]
else:
    with ThreadPoolExecutor(max_workers=jobs) as executor:
        results = list(executor.map(run_one, cases))
```

이 방식은 다음 장점이 있습니다.

- 순차 실행 코드를 계속 기준 동작으로 사용할 수 있습니다.
- 디버깅할 때 `jobs=1`로 실행 순서를 단순화할 수 있습니다.
- 동시성 자체가 만든 문제인지 쉽게 비교할 수 있습니다.

## 완료 순서와 결과 순서 구분하기

동시에 실행한 작업은 매번 같은 순서로 끝나지 않습니다.

예를 들어 입력 순서가:

```text
case A
case B
case C
```

여도 실제 완료 순서는:

```text
case C
case A
case B
```

가 될 수 있습니다.

사용자가 보는 보고서가 입력 순서를 보장해야 한다면 두 순서를 분리해야 합니다.

```text
실제 완료 순서
→ 먼저 끝난 작업부터 달라질 수 있음

최종 결과 순서
→ 명세 파일에 기록된 입력 순서 유지
```

---

## `executor.map()`은 입력 순서대로 결과를 반환합니다

다음 코드를 봅니다.

```python
with ThreadPoolExecutor(max_workers=jobs) as executor:
    results = list(executor.map(run_one, cases))
```

작업 자체는 동시에 실행될 수 있습니다.

하지만 `executor.map()`이 반환하는 결과의 순서는 `cases`의 입력 순서와 같습니다.

```text
입력:
A, B, C

실제 완료:
C, A, B

map() 결과:
A 결과, B 결과, C 결과
```

따라서 최종 보고서가 입력 순서를 유지해야 한다면 편리합니다.

다만 **결과를 입력 순서대로 꺼낸다는 것과 작업이 입력 순서대로 끝난다는 것은 다른 의미**입니다.

예를 들어 A가 매우 늦게 끝나고 B, C가 먼저 완료되어도, 반복에서 A 결과를 먼저 기다려야 B와 C 결과를 다음 순서로 받을 수 있습니다.

최종 순서 보장이 중요하고 완료 즉시 중간 처리가 필요하지 않다면 이 특성이 단순합니다.

## `as_completed()`를 사용할 때는 원래 인덱스를 보존하기

완료된 작업을 먼저 처리하고 싶다면 `as_completed()`를 사용할 수 있습니다.

```python
from concurrent.futures import as_completed

future_to_index = {
    executor.submit(run_one, case): index
    for index, case in enumerate(cases)
}
```

완료 순서대로 결과를 받습니다.

```python
for future in as_completed(future_to_index):
    index = future_to_index[future]
    result = future.result()
```

하지만 보고서가 입력 순서를 유지해야 한다면 결과를 원래 인덱스에 저장해야 합니다.

```python
results: list[Result | None] = [None] * len(cases)

for future in as_completed(future_to_index):
    index = future_to_index[future]
    results[index] = future.result()
```

핵심은 다음 두 목적을 분리하는 것입니다.

```text
완료 즉시 처리
≠
최종 출력 순서
```

## 공유 가변 값 줄이기

동시에 실행한다고 해서 작업이 자동으로 격리되지는 않습니다.

다음 자원을 여러 작업이 함께 사용하면 충돌할 수 있습니다.

- 같은 작업 디렉터리
- 같은 출력 파일
- 같은 고정 포트
- 프로세스 전체가 공유하는 환경 변수
- 가변 `dict`
- 가변 `list`
- 상태를 가지는 난수 생성기
- 전역 카운터

가장 단순한 구조는 **작업자끼리 값을 직접 공유하지 않는 것**입니다.

```text
주 스레드
→ 불변 Case 전달

작업자
→ 자기 전용 작업 디렉터리 사용
→ 자기 프로세스와 파이프 생성
→ Result 생성

주 스레드
→ Result 수집
→ 최종 보고서 작성
```

## 프로세스 전체 환경 변수를 작업자에서 바꾸지 않기

다음 코드는 현재 Python 프로세스 전체의 환경을 바꿉니다.

```python
import os

os.environ["MODE"] = "test"
```

여러 스레드가 서로 다른 값을 동시에 설정하면 충돌할 수 있습니다.

```text
작업 A: MODE=A 설정
작업 B: MODE=B 설정
작업 A: 외부 프로세스 실행
```

작업 A가 실제로 어떤 값을 상속받을지 의도와 달라질 수 있습니다.

따라서 작업자마다 별도 환경 `dict`를 만들어 `subprocess`에 직접 전달합니다.

```python
env = os.environ.copy()
env.update(case.environment)

run_process(
    command,
    env=env,
)
```

이렇게 하면 부모 프로세스의 `os.environ` 자체를 작업자들이 서로 변경하지 않아도 됩니다.

## 작업 디렉터리와 출력 파일을 격리하기

두 사례가 같은 디렉터리에서 같은 파일을 만들면 서로 덮어쓸 수 있습니다.

예:

```text
case A → ./output.txt
case B → ./output.txt
```

동시에 실행하면 어느 결과가 최종 파일에 남을지 예측하기 어렵습니다.

가능하면 사례마다 별도 임시 디렉터리를 사용합니다.

```text
/tmp/checker/case-a/
/tmp/checker/case-b/
```

그러면 각 대상 프로그램이 같은 상대 파일 이름을 사용해도 실제 경로는 서로 다릅니다.

```text
case A → /tmp/checker/case-a/output.txt
case B → /tmp/checker/case-b/output.txt
```

고정 포트도 같은 문제가 있습니다. 여러 사례가 동시에 같은 포트를 열려고 하면 한쪽이 실패할 수 있으므로 테스트 설계에서 별도 포트를 배정하거나 운영체제가 빈 포트를 선택하도록 하는 정책이 필요합니다.

---

## 불변 입력과 반환값 중심으로 설계하기

공유 상태를 줄이는 가장 좋은 방법 중 하나는 작업자 함수가 입력을 받아 결과를 반환하도록 만드는 것입니다.

```python
def run_one(case: Case) -> Result:
    ...
    return result
```

개념적으로:

```text
주 스레드가 불변 Case 전달
→ 작업자가 자신의 자원만 생성
→ 작업자가 불변 Result 반환
→ 주 스레드가 Result를 수집
```

이 구조에서는 작업자가 공용 `list`에 직접 `append()`하거나 공용 보고서 파일을 수정할 필요가 없습니다.

동기화해야 할 공유 상태 자체가 줄어들기 때문에 락을 추가하는 것보다 설계가 단순해집니다.

---

## 취소 요청과 정리 완료 구분하기

동시성 API에서 "취소를 요청했다"는 사실은 "실행 중인 작업과 그 자원이 모두 사라졌다"는 뜻이 아닙니다.

특히 `Future.cancel()`은 이미 실행 중인 작업을 강제로 중단하지 못합니다.

```python
cancelled = future.cancel()
```

`False`가 반환될 수 있는 대표적인 경우는 작업이 이미 실행을 시작한 경우입니다.

```text
Future가 아직 실행 전
→ cancel()로 취소 가능

Future가 이미 실행 중
→ cancel()이 작업 함수 내부 실행을 강제 종료하지 못함
```

작업 함수가 외부 프로세스를 만들었다면 그 프로세스도 자동으로 종료되지 않습니다.

---

## 취소는 협력적으로 전달해야 합니다

실행 중인 작업을 중단해야 한다면 작업자가 확인할 수 있는 취소 상태나 전체 마감 시각을 전달하는 방식이 필요합니다.

개념적인 흐름은 다음과 같습니다.

```text
상위 실행기에서 취소 결정
→ 새 작업 제출을 중단
→ 아직 시작하지 않은 Future 취소
→ 실행 중인 작업에 취소 신호 또는 마감 시각 전달
→ 각 작업이 자신이 만든 프로세스와 파일 정리
→ 작업자가 종료
→ 완료·실패·취소 상태 수집
```

중요한 원칙은 **자원을 만든 코드가 그 자원을 정리한다**는 것입니다.

---

## 상위 실행기가 작업자의 파이프를 직접 닫지 않기

다음 구조는 위험할 수 있습니다.

```text
작업자 스레드
→ stdout 파이프를 읽는 중

주 스레드
→ 같은 stdout 파이프를 강제로 닫음
```

주 스레드와 작업자 스레드가 같은 자원을 동시에 조작하면 경쟁 상태가 생길 수 있습니다.

따라서 일반적으로:

```text
상위 실행기
→ 취소 의사만 전달

작업자
→ 자신이 만든 프로세스와 파이프 정리
```

구조를 유지하는 것이 안전합니다.

프로세스 그룹 종료 역시 `run_case()`처럼 해당 프로세스를 소유한 함수가 수행하도록 두는 편이 책임이 명확합니다.

---

## `Executor` 종료와 작업 취소를 구분하기

`with ThreadPoolExecutor(...)` 블록을 빠져나가면 실행기는 종료 절차를 수행합니다.

기본적으로 이미 제출된 작업이 끝날 때까지 기다립니다.

따라서 다음 코드는:

```python
with ThreadPoolExecutor(max_workers=jobs) as executor:
    ...
```

블록을 빠져나갔다고 해서 실행 중인 작업이 즉시 강제로 사라진다는 의미가 아닙니다.

`shutdown(cancel_futures=True)`를 사용하면 아직 시작하지 않은 작업을 취소할 수 있지만, 이미 실행 중인 작업 함수는 여전히 스스로 종료해야 합니다.

즉:

```text
executor 종료 요청
≠
실행 중 함수 강제 종료
≠
그 함수가 만든 외부 프로세스 강제 종료
```

입니다.

---

## 시간 제한의 종류 구분하기

동시 실행에서는 여러 종류의 시간 제한이 함께 존재할 수 있습니다.

### 사례 타임아웃

한 사례 하나가 허용된 시간 안에 끝나야 하는 제한입니다.

```text
case A: 최대 2초
case B: 최대 2초
case C: 최대 2초
```

각 `run_case()`가 자기 프로세스의 수명을 관리합니다.

### 전체 타임아웃

모든 사례를 포함한 전체 검증 작업이 끝나야 하는 제한입니다.

```text
전체 command-checker 실행: 최대 10초
```

각 사례가 개별 제한 안에 있어도 작업 수가 많다면 전체 실행 시간이 더 길 수 있습니다.

### 종료 유예 시간

타임아웃이나 취소가 발생한 뒤 `SIGTERM`을 보내고 정상 정리를 기다리는 시간입니다.

```text
SIGTERM
→ 0.2초 유예
→ 여전히 살아 있으면 SIGKILL
```

이 시간은 사례 실행 허용 시간과 의미가 다릅니다.

따라서 다음 값을 하나로 무조건 재사용하지 않습니다.

```text
case_timeout
overall_timeout
termination_grace
```

---

## 전체 타임아웃은 절대 마감 시각으로 관리하기

전체 작업 제한이 있다면 남은 시간을 반복해서 계산하는 편이 안전합니다.

```python
import time

deadline = time.monotonic() + overall_timeout
```

각 단계에서는:

```python
remaining = deadline - time.monotonic()
```

을 계산합니다.

```python
if remaining <= 0:
    ...
```

이렇게 해야 여러 단계가 각각 동일한 전체 타임아웃 값을 새로 사용하는 실수를 피할 수 있습니다.

예를 들어 잘못된 방식은:

```text
작업 제출에 최대 10초
→ 결과 대기에 다시 최대 10초
→ 정리에 다시 최대 10초
```

처럼 전체 제한이 실제로는 10초보다 훨씬 길어지는 경우입니다.

전체 제한은 하나의 절대 마감 시각을 기준으로 관리해야 합니다.

---

## 작업자 예외 처리

동시 실행에서는 작업자 하나의 예외를 어떻게 전체 결과로 반영할지 명확히 해야 합니다.

다음 세 종류를 구분합니다.

### 예상 가능한 결과 불일치

대상 프로그램은 정상적으로 실행되었지만 기대와 결과가 다릅니다.

예:

```text
expected returncode = 0
actual returncode = 1
```

이런 경우는 일반적으로 예외보다 `Result`로 표현하는 편이 좋습니다.

```python
Result(
    passed=False,
    ...
)
```

### 실행 환경 오류

해당 사례를 정상적으로 시작하거나 관찰할 수 없습니다.

예:

- 실행 파일을 찾을 수 없음
- 작업 디렉터리를 만들 수 없음
- 파일 디스크립터 생성 실패
- 대상 프로세스를 시작할 수 없음

이런 문제는 단순한 테스트 결과 불일치와 구분해서 예외로 전달할 수 있습니다.

### 구현 자체의 오류

작업자 코드 안의 버그입니다.

예:

```text
KeyError
AssertionError
예상하지 못한 TypeError
```

이런 오류를 "대상 프로그램 실패"처럼 숨기면 안 됩니다. 검증 도구 자체의 실패로 처리해야 합니다.

---

## 첫 예외만 보고 즉시 빠져나갈 때의 문제

동시에 여러 작업이 실행 중인데 첫 번째 예외가 나오자마자 상위 함수가 즉시 종료하면 다음 문제가 생길 수 있습니다.

- 이미 실행 중인 다른 작업의 상태를 잃음
- 아직 실행 중인 외부 프로세스가 남음
- 다른 사례의 중요한 오류를 보지 못함
- 보고서가 부분 상태로 끝남

따라서 먼저 정책을 정합니다.

예:

```text
정책 A:
첫 실행 환경 오류가 나면 전체 취소 시작

정책 B:
가능한 모든 사례를 끝까지 실행하고 오류를 모두 수집
```

어느 쪽이 맞는지는 프로젝트 요구사항에 따라 다릅니다.

여러 오류를 모은다면 사례 식별자와 원래 예외를 함께 보존해야 합니다.

```text
case "alpha": PermissionError(...)
case "beta": FileNotFoundError(...)
```

그래야 어느 작업에서 무슨 문제가 발생했는지 알 수 있습니다.

---

## 보고서는 한곳에서 저장하기

각 작업자가 같은 JSON이나 JUnit 파일을 직접 수정하게 하면 경쟁 상태가 발생하기 쉽습니다.

예:

```text
worker A → report.json 쓰기
worker B → report.json 쓰기
worker C → report.json 쓰기
```

락을 사용해 직렬화할 수도 있지만 구조가 불필요하게 복잡해집니다.

더 단순한 방식은 작업자가 결과만 반환하는 것입니다.

```text
각 작업자가 Result 반환
→ 주 스레드가 전체 Result 수집
→ 입력 순서로 결과 확정
→ 주 스레드가 JSON 생성
→ 주 스레드가 JUnit 생성
→ 완성된 임시 파일을 최종 경로로 교체
```

이 구조의 장점은 다음과 같습니다.

- 보고서 쓰기에 별도 락이 필요하지 않습니다.
- JSON과 JUnit이 정확히 같은 `Result` 목록을 사용합니다.
- 파일 쓰기 실패를 한곳에서 처리할 수 있습니다.
- 결과 순서를 확정한 뒤 파일을 만들 수 있습니다.

---

## 보고서 저장 실패는 작업자 실패와 다릅니다

모든 사례가 성공적으로 끝났더라도 마지막 보고서 저장이 실패할 수 있습니다.

예:

```text
모든 run_case() 성공
→ Result 목록 완성
→ report.json 기록 시 PermissionError
```

이는 개별 사례의 실행 결과가 실패한 것이 아니라 **검증 작업의 출력 단계가 실패한 것**입니다.

따라서 다음을 구분하는 것이 좋습니다.

```text
사례 실행 결과
보고서 생성/저장 결과
```

작업자가 보고서 파일까지 직접 쓰지 않도록 하면 이 구분도 자연스럽게 유지됩니다.

---

## 동시성 테스트를 재현 가능하게 만들기

동시성 버그는 실행 순서에 의존하므로 테스트를 반복했을 때 같은 상황을 만들 수 있어야 합니다.

단순히 `sleep()` 값만 다르게 주는 방식은 환경 부하에 영향을 받습니다.

예:

```python
# 취약한 테스트 예
if case == "A":
    time.sleep(0.1)

if case == "B":
    time.sleep(0.05)
```

빠른 환경에서는 의도한 순서가 나올 수 있지만, 느린 CI나 부하가 높은 시스템에서는 예상과 다른 순서가 생길 수 있습니다.

가능하면 다음처럼 명시적인 동기화 수단을 사용합니다.

- `threading.Event`
- `threading.Barrier`
- 테스트용 프로그램의 준비 완료 신호
- 파이프를 통한 명시적인 `ready` 메시지

---

## `Event`로 순서를 명시적으로 제어하기

예를 들어 작업 B가 특정 지점에 도착한 뒤 작업 A를 진행시키고 싶다면 `Event`를 사용할 수 있습니다.

```python
from threading import Event

ready = Event()
```

작업 B:

```python
ready.set()
```

작업 A:

```python
ready.wait()
```

이 방식은 "대략 0.1초 뒤" 같은 시간 추측보다 "B가 준비되면 A가 진행"이라는 조건을 직접 표현합니다.

---

## `Barrier`로 여러 작업의 시작 지점을 맞추기

여러 작업이 모두 특정 지점에 도달한 뒤 동시에 다음 단계로 진행하게 만들고 싶다면 `Barrier`를 사용할 수 있습니다.

```python
from threading import Barrier

barrier = Barrier(2)
```

각 작업:

```python
barrier.wait()
```

두 작업이 모두 `wait()`에 도달해야 다음 단계가 진행됩니다.

이를 사용하면 공유 자원 충돌 같은 특정 경쟁 조건을 더 안정적으로 재현할 수 있습니다.

---

## 동시성에서 검증할 대표 상황

최소한 다음 상황을 테스트합니다.

### 완료 순서가 입력 순서와 반대

```text
입력:
A, B

실제 완료:
B, A

최종 결과:
A, B
```

동시 실행 완료 순서와 보고서 순서가 분리되어 있는지 확인합니다.

### 작업자 하나가 예외 발생

```text
A → 정상 Result
B → 실행 환경 예외
C → 정상 Result
```

정책에 따라 나머지 작업을 계속할지, 취소할지 확인합니다.

### 타임아웃 작업과 정상 작업이 함께 존재

```text
A → 정상 종료
B → timeout
C → 정상 종료
```

B를 정리하는 과정이 A와 C의 자원을 건드리지 않는지 확인합니다.

### 보고서 저장 실패

```text
모든 Result 수집 성공
→ 최종 파일 저장 실패
```

사례 결과와 보고서 오류를 구분하는지 확인합니다.

### 공유 파일이나 디렉터리 격리

서로 다른 사례가 같은 상대 파일 이름을 사용해도 별도 작업 디렉터리에서 충돌하지 않는지 확인합니다.

---

## 실행 시간이 줄었다는 사실만으로 순서 보장을 검증할 수 없습니다

예를 들어 순차 실행이 4초이고 동시 실행이 2초가 되었다고 해서 다음 사실이 자동으로 검증되는 것은 아닙니다.

- 최종 결과가 입력 순서를 유지함
- 각 사례의 결과가 올바른 사례에 연결됨
- 타임아웃 작업이 다른 작업을 방해하지 않음
- 보고서가 동일한 `Result` 목록을 사용함

성능 테스트와 의미 보장 테스트는 별도입니다.

```text
처리량 검증
≠
정확성 검증
```

따라서 결과 순서는 직접 비교해야 합니다.

---

## `command-checker`에 적용하기

프로젝트에서는 다음 구조를 사용할 수 있습니다.

### `jobs == 1`

기존 순차 실행 경로를 그대로 사용합니다.

```text
case 1 실행
→ case 2 실행
→ case 3 실행
```

### `jobs > 1`

`ThreadPoolExecutor`를 만듭니다.

```python
with ThreadPoolExecutor(max_workers=jobs) as executor:
    results = list(executor.map(run_one, cases))
```

`executor.map()`을 사용하므로 작업의 실제 완료 순서와 관계없이 최종 결과는 입력 순서를 유지합니다.

### 각 작업자

작업자는 자기 사례만 책임집니다.

```text
Case 받음
→ 자기 cwd/env 구성
→ 자기 외부 프로세스 시작
→ 자기 파이프 관리
→ timeout/output limit 적용
→ 자기 프로세스 그룹 정리
→ Result 반환
```

다른 작업자의 자원을 직접 수정하지 않습니다.

### 주 스레드

주 스레드는 결과 전체를 책임집니다.

```text
Result 수집
→ 입력 순서 확정
→ 전체 성공/실패 계산
→ JSON 생성
→ JUnit 생성
→ 보고서 저장
```

작업자는 보고서 파일을 직접 쓰지 않습니다.

---

## 전체 설계 흐름

```text
순차 실행 동작 완성
        │
        ▼
Case를 불변 입력으로 정의
        │
        ▼
run_case(Case) -> Result 완성
        │
        ▼
jobs == 1
  └─ 순차 실행

jobs > 1
  └─ 제한된 ThreadPoolExecutor
        │
        ▼
각 작업자가 자기 자원만 소유
        │
        ▼
완료 순서는 자유롭게 달라짐
        │
        ▼
Result는 입력 순서로 확정
        │
        ▼
주 스레드가 전체 상태 계산
        │
        ▼
주 스레드가 보고서 저장
```

핵심은 다음 세 가지입니다.

```text
작업의 실행 순서는 자유롭게
자원의 소유권은 명확하게
사용자에게 보이는 결과 순서는 안정적으로
```

## 완료 기준

다음 항목을 설명하고 구현할 수 있으면 이 문서의 목표를 달성한 것입니다.

- 동시성과 병렬성을 구분할 수 있습니다.
- 순차 실행의 동작과 오류 처리가 먼저 완성되어 있습니다.
- I/O 대기 중심 작업에서 `ThreadPoolExecutor`가 적합한 이유를 설명할 수 있습니다.
- CPU 집약 작업에서 스레드가 항상 성능 향상을 보장하지 않는 이유를 설명할 수 있습니다.
- 동시에 실행하는 작업 수를 `max_workers`로 제한합니다.
- `jobs == 1`에서는 순차 경로를 유지할 수 있습니다.
- 실제 완료 순서와 사용자에게 보여 줄 결과 순서를 구분합니다.
- `executor.map()`이 입력 순서대로 결과를 반환한다는 점을 이해합니다.
- `as_completed()`를 사용할 때 원래 인덱스를 보존할 수 있습니다.
- 작업자들이 같은 작업 디렉터리, 파일, 포트, 환경 상태를 불필요하게 공유하지 않도록 설계합니다.
- 프로세스 전체의 `os.environ`을 작업자 스레드에서 직접 변경하지 않고 사례별 환경 `dict`를 전달합니다.
- 불변 `Case`를 입력으로 받고 `Result`를 반환하는 구조를 사용할 수 있습니다.
- `Future.cancel()`이 이미 실행 중인 작업을 강제로 종료하지 않는다는 점을 이해합니다.
- 취소 요청과 실제 자원 정리 완료를 구분합니다.
- 작업자가 자신이 만든 프로세스, 파이프, 파일을 정리하도록 유지합니다.
- 사례 타임아웃, 전체 타임아웃, 종료 유예 시간을 구분합니다.
- 전체 타임아웃을 절대 마감 시각으로 관리할 수 있습니다.
- 결과 불일치, 실행 환경 오류, 구현 오류를 구분합니다.
- 여러 작업자 오류를 수집할 때 사례 식별자와 원래 예외를 보존합니다.
- 작업자가 공유 보고서 파일을 직접 수정하지 않습니다.
- 주 스레드가 하나의 확정된 `Result` 목록으로 JSON과 JUnit을 만듭니다.
- 동시성 테스트에서 `sleep()` 추측보다 `Event`, `Barrier`, 명시적인 신호를 우선합니다.
- 처리량 향상과 결과 순서 보장이 서로 다른 검증 대상임을 이해합니다.
