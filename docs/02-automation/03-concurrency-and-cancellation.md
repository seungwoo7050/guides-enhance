# 동시성, 취소와 자원 제한

> 선택 심화 문서입니다. 순차 실행이 완성되고 실제 처리량 문제가 확인된 뒤 적용합니다.

## 학습 목표

동시 실행은 독립된 작업의 대기 시간을 겹쳐 처리량을 높이는 방법입니다. 이 문서에서는 다음 내용을 다룹니다.

- 순차 동작을 먼저 완성해야 하는 이유
- 스레드, 프로세스, `asyncio`를 선택하는 기준
- 동시에 실행할 작업 수를 제한하는 방법
- 완료 순서와 결과 순서를 구분하는 방법
- 취소 요청과 자원 정리 완료의 차이
- 동시성 테스트를 반복해서 재현하는 방법

연결 프로젝트는 [`command-checker`](../../exercises/command-checker/README.md)입니다.

## 선행 개념

- 외부 프로세스 한 건을 순차적으로 실행하는 동작이 완성되어 있어야 합니다.
- 가변 값을 여러 스레드가 함께 바꾸면 경쟁 상태가 발생할 수 있음을 이해해야 합니다.
- 각 작업이 자신이 연 파일과 프로세스를 정리해야 합니다.

## 순차 실행 규칙부터 완성하기

동시 실행을 추가하기 전에 다음 동작이 순차 실행에서 항상 같아야 합니다.

- 각 사례에 전달할 입력
- 확인할 `returncode`, `stdout`, `stderr`
- 사례 하나가 실패해도 나머지를 계속 실행할지 여부
- 결과를 표시하는 순서
- 전체 종료 상태

순차 동작이 잘못된 상태에서 동시성을 추가하면 업무 규칙의 오류와 경쟁 상태를 구분하기 어렵습니다.

## 스레드, 프로세스, `asyncio` 선택하기

| 실행 방식 | 적합한 작업 | 주의점 |
|---|---|---|
| `ThreadPoolExecutor` | 외부 프로세스·파일·네트워크 I/O 대기 | 공유 가변 값, 종료 절차, 예외 수집 |
| `ProcessPoolExecutor` | 서로 독립적인 CPU 집약 계산 | 값 직렬화, 프로세스 시작 비용, 자식 프로세스 수명 |
| `asyncio` | 많은 비동기 I/O 작업 | 호출 경로 전체의 비동기 함수, 취소 전달과 정리 |

`command-checker`의 각 사례는 대부분 외부 프로세스가 끝나기를 기다리므로 스레드 풀이 가장 단순한 선택입니다. CPython에서 Python 바이트코드로 수행하는 CPU 집약 작업은 스레드 수만 늘린다고 같은 방식으로 빨라지지 않습니다.

## 동시에 실행할 작업 수 제한하기

```python
from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=jobs) as executor:
    results = list(executor.map(run_one, cases))
```

`max_workers`는 1 이상이어야 합니다. 사례 수만큼 스레드나 프로세스를 제한 없이 만들면 파일 디스크립터, 메모리, 프로세스 수 제한을 쉽게 초과할 수 있습니다.

작업자 수는 다음 값을 고려해 정합니다.

- 한 작업이 사용하는 메모리와 파일 디스크립터 수
- 작업당 자식 프로세스 수
- 외부 서비스나 파일 시스템이 감당할 수 있는 동시 요청 수
- 전체 실행 시간 목표

## 완료 순서와 결과 순서 구분하기

동시에 실행한 작업은 매번 다른 순서로 끝날 수 있습니다. 보고서가 입력 순서를 보장해야 한다면 실제 완료 순서와 최종 결과 순서를 분리합니다.

```text
실제 완료 순서: 먼저 끝난 작업부터
최종 결과 순서: 명세 파일에 기록된 순서
```

`executor.map()`은 내부 작업의 완료 순서와 관계없이 입력 순서대로 결과를 반환합니다. `as_completed()`를 사용한다면 각 `Future`와 원래 인덱스를 함께 저장한 뒤 최종 결과를 다시 정렬해야 합니다.

## 공유 가변 값 줄이기

각 작업이 다음 자원을 공유하면 충돌할 수 있습니다.

- 같은 작업 디렉터리
- 같은 출력 파일
- 같은 고정 포트
- 프로세스 전체가 공유하는 환경 변수
- 가변 `dict`나 `list`
- 하나의 난수 생성기

동시에 실행한다고 해서 작업이 자동으로 격리되지는 않습니다. 사례마다 별도 임시 디렉터리를 사용하고, 입력은 불변 값으로 전달하며, 결과는 작업자 함수의 반환값으로 수집합니다.

다음 형태가 단순합니다.

```text
주 스레드가 불변 `Case`를 전달합니다.
→ 작업자가 자신의 프로세스와 파이프를 만듭니다.
→ 작업자가 불변 `Result`를 반환합니다.
→ 주 스레드가 `Result`를 정해진 순서로 저장합니다.
```

## 취소 요청과 정리 완료 구분하기

`Future.cancel()`을 호출해도 이미 실행 중인 함수나 그 함수가 시작한 외부 프로세스가 자동으로 종료되지는 않습니다.

```text
상위 실행기에서 취소를 요청합니다.
→ 새 작업 제출을 중단합니다.
→ 실행 중인 작업에 취소 신호나 마감 시각을 전달합니다.
→ 각 작업이 자신이 연 파일과 프로세스를 정리합니다.
→ 완료·실패·취소 결과를 모읍니다.
```

상위 실행기가 작업자가 사용 중인 파이프를 직접 닫으면 작업자 스레드와 충돌할 수 있습니다. 자원을 만든 함수가 정리하도록 유지합니다.

## 시간 제한의 종류 구분하기

- 사례 타임아웃: 한 사례가 끝나야 하는 시각
- 전체 타임아웃: 모든 사례를 포함한 작업 전체의 상한
- 종료 유예 시간: `SIGTERM` 뒤 정상 정리를 기다리는 시간

의미가 다른 시간 제한에 하나의 숫자를 무조건 재사용하지 않습니다.

## 작업자 예외 처리

첫 번째 작업자 예외를 즉시 다시 발생시키면 아직 실행 중인 작업의 상태나 다른 실패 원인을 잃을 수 있습니다. 다음 상황을 구분해야 합니다.

- 예상 가능한 결과 불일치: `Result`로 반환합니다.
- 해당 사례를 시작하거나 관찰할 수 없는 실행 환경 오류: 예외로 전달합니다.
- 구현 자체의 오류: 숨기지 않고 전체 검증 실패로 처리합니다.

여러 예외를 모아야 한다면 사례 이름과 원래 예외를 함께 보존합니다.

## 보고서는 한곳에서 저장하기

각 작업자가 같은 JSON이나 JUnit 파일을 직접 수정하게 해서는 안 됩니다.

```text
각 작업자가 `Result`를 반환합니다.
→ 입력 순서에 맞춰 전체 결과를 확정합니다.
→ 주 스레드가 JSON과 JUnit을 만듭니다.
→ 완성한 임시 파일을 최종 경로로 교체합니다.
```

이렇게 하면 파일 잠금이 필요한 범위가 줄고 JSON과 JUnit이 정확히 같은 결과 목록을 사용합니다.

## 동시성 테스트를 재현 가능하게 만들기

`sleep()` 시간만 조절해 작업 순서를 추측하면 느린 환경이나 부하가 높은 환경에서 테스트가 간헐적으로 실패할 수 있습니다. 가능하면 배리어, `Event`, 테스트용 프로그램의 명시적인 신호를 사용합니다.

검증할 상황은 다음과 같습니다.

- 두 작업이 입력 순서와 반대로 끝납니다.
- 작업자 하나가 예외를 발생시킵니다.
- 타임아웃에 걸린 작업과 정상 작업이 함께 있습니다.
- 보고서 저장이 실패합니다.
- 완료 순서와 관계없이 최종 결과는 입력 순서를 유지합니다.

작은 테스트용 프로그램에서 지연을 사용할 때도 결과를 입력 순서로 반환하는지 직접 확인해야 합니다. 단순히 전체 실행 시간이 짧아졌다는 사실만으로 순서 보장을 검증할 수는 없습니다.

## `command-checker`에 적용하기

- `jobs == 1`일 때 순차 실행을 그대로 사용합니다.
- `jobs > 1`일 때만 `ThreadPoolExecutor(max_workers=jobs)`를 만듭니다.
- `executor.map()`으로 결과를 입력 순서대로 받습니다.
- 작업자는 `Result`만 반환하고 보고서 파일을 직접 쓰지 않습니다.
- 각 `run_case()`가 자신이 시작한 프로세스 그룹과 파이프를 정리합니다.

## 완료 기준

- 순차 실행의 동작과 오류 처리가 먼저 완성되어 있습니다.
- 동시에 실행하는 작업 수가 제한되어 있습니다.
- 작업자가 공유 보고서 파일을 직접 수정하지 않습니다.
- 실제 완료 순서와 사용자에게 보여 줄 결과 순서를 구분합니다.
- 각 작업이 자신이 만든 프로세스와 파일을 정리합니다.
- 취소 요청과 자원 정리가 끝난 상태를 구분합니다.
