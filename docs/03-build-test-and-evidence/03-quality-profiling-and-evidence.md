# 품질 검사·프로파일링과 검증 근거

“테스트가 통과했습니다.”라는 문장만으로는 무엇을 확인했는지 알 수 없습니다. 사용한 소스, 명령, 환경, 실행한 검사와 확인하지 못한 범위를 함께 남겨야 다른 개발자가 같은 결과를 다시 만들 수 있습니다.

이 문서는 필수 학습 경로를 마친 뒤 참고하는 자료입니다.

## 검증 결과를 세 상태로 구분합니다

```text
PASS        실제로 실행했고 정한 조건을 만족했습니다.
FAIL        실제로 실행했고 정한 조건을 위반했습니다.
UNVERIFIED  필요한 도구나 환경이 없어 실행하지 못했습니다.
```

실행하지 못한 검사를 성공으로 기록하지 않습니다. 필수 검사에 `UNVERIFIED`가 남아 있다면 전체 검증을 완료했다고 말할 수 없습니다.

## 명령마다 확인하는 범위가 다릅니다

예를 들어 Maven 명령은 다음처럼 서로 다른 범위를 확인합니다.

| 명령 | 확인하는 내용 |
| --- | --- |
| `mvn compile` | 실행 코드를 컴파일할 수 있습니다. |
| `mvn test` | 테스트 코드를 컴파일하고 단위 테스트를 실행합니다. |
| `mvn package` | 앞 단계가 성공한 뒤 JAR 같은 산출물을 만듭니다. |
| `mvn verify` | POM에 연결한 추가 검사까지 실행합니다. |

`javac` 성공은 JUnit 테스트 성공을 뜻하지 않습니다. formatter나 정적 검사 성공도 프로그램 동작이 올바르다는 뜻은 아닙니다. 각 도구가 찾는 오류 종류를 따로 기록합니다.

## 검증 기록에 포함할 내용

최소한 다음 내용을 남깁니다.

- 소스 버전 또는 정확한 소스 압축 파일
- JDK와 Maven 버전
- 운영체제와 CPU 종류
- 실행 명령
- 입력 데이터와 환경 변수
- 테스트 결과
- 생성한 산출물
- 실행하지 못한 검사와 이유

원시 로그 전체를 항상 커밋할 필요는 없습니다. 같은 결과를 다시 만드는 명령과 필수 입력을 정본으로 남기고, 큰 로그는 필요한 위치에 별도로 보관합니다.

## 형식 검사와 정적 검사

formatter는 들여쓰기와 줄바꿈 같은 형식을 일정하게 맞춥니다. Checkstyle, Error Prone, SpotBugs 같은 도구는 설정에 따라 의심스러운 코드를 찾습니다.

자동 수정 명령을 실행한 뒤에는 diff를 확인합니다.

```sh
mvn spotless:apply
git diff --check
mvn test
```

formatter가 소스 의미를 바꾸지 않는다고 가정하지 않습니다. import 제거와 annotation 정렬처럼 컴파일 결과에 영향을 줄 수 있는 변경도 있으므로 테스트를 다시 실행합니다.

정적 검사가 찾을 수 있는 오류는 설정과 분석 방식에 제한됩니다. 통과했다고 해서 입력 검증, 동시성이나 resource cleanup까지 증명되는 것은 아닙니다.

## debugger와 스택 확인

문제가 생겼을 때 로그를 무작정 추가하기 전에 debugger로 다음을 확인할 수 있습니다.

- breakpoint 직전의 변수값
- 호출 스택
- step over와 step into 결과
- 예외가 발생한 실제 위치
- 여러 스레드의 현재 상태

실행 중인 JVM에는 JDK 도구를 사용할 수 있습니다.

```sh
jstack <pid>
jcmd <pid> VM.command_line
jcmd <pid> Thread.print
```

한 번의 thread dump만 보고 교착 상태나 장시간 대기를 단정하지 않습니다. 일정 간격으로 여러 번 확인하고 업무 상태, 대기열 크기와 외부 시스템 상태를 함께 봅니다.

## JFR로 실행 상황을 기록합니다

JDK Flight Recorder는 CPU sample, allocation, thread, lock과 I/O event를 비교적 낮은 overhead로 기록합니다.

```sh
jcmd <pid> JFR.start \
  name=profile \
  settings=profile \
  duration=60s \
  filename=profile.jfr
```

JFR 파일이 생성되었다는 사실만으로 병목을 찾았다고 말할 수는 없습니다. 먼저 느린 위치에 대한 가설을 세우고 관련 event를 확인합니다.

프로파일링은 다음 순서로 진행합니다.

```text
정확성 확인
→ 병목 가설 작성
→ 같은 조건에서 기준 측정
→ 한 가지 변경
→ 같은 조건에서 다시 측정
→ 정확성 재확인
```

잘못된 결과를 더 빨리 만드는 변경은 최적화가 아닙니다.

## 성능 수치에 필요한 조건

성능 결과에는 최소한 다음 조건을 적습니다.

- 소스 버전과 JDK
- 운영체제, CPU와 메모리
- JVM option과 heap 크기
- warm-up 여부
- 입력 크기와 데이터 분포
- 동시 작업 수와 대기열 크기
- 반복 횟수와 오류 수
- p50, p95, p99 같은 분포

평균 하나만 기록하면 일부 요청이 매우 오래 걸리는 현상을 숨길 수 있습니다. 개발 컴퓨터에서 얻은 숫자를 운영 환경의 용량으로 그대로 사용하지 않습니다.

## Java 코드 검토 항목

### 타입과 값

- 생성할 수 있는 모든 record와 클래스 상태가 유효합니까?
- `null`, 빈 값, 0과 음수의 의미가 분명합니까?
- 가변 컬렉션을 그대로 보관하거나 반환합니까?
- 값 동등성과 객체 식별을 구분합니까?
- 실제로 교체할 필요가 없는 클래스마다 인터페이스를 만들고 있지 않습니까?

### 컬렉션과 숫자

- 결과 순서가 우연한 `HashMap` 순회 순서에 기대고 있지 않습니까?
- 중복을 허용할지 명시했습니까?
- 정수 오버플로를 조용히 넘기고 있지 않습니까?
- `BigDecimal`의 scale과 반올림 방식을 정했습니까?
- Stream 안에서 외부 상태를 바꾸며 실패 위치를 숨기고 있지 않습니까?

### 오류와 시간

- 입력 조건 위반과 현재 상태에서의 거절을 구분합니까?
- 예외를 바꿀 때 원인을 보존합니까?
- 실패 전에 새 값을 모두 계산합니까?
- `Clock`을 주입해 시간에 의존하는 테스트를 반복할 수 있습니까?
- 오류 메시지에 비밀값이나 개인정보가 포함되지 않습니까?

### 동시성

- 함께 바뀌어야 하는 값을 같은 잠금으로 보호합니까?
- 잠금 안에서 파일이나 네트워크 I/O를 실행합니까?
- 모든 `Future` 결과와 예외를 확인합니까?
- 시간 초과 뒤 실제 작업에 취소를 요청합니까?
- 인터럽트 상태를 잃고 있지 않습니까?
- 종료 뒤 대기 중인 Future와 작업자 스레드가 남습니까?

### 빌드와 테스트

- JDK, Maven, dependency와 plugin 버전을 확인했습니까?
- 테스트 의존성이 `test` scope에 있습니까?
- 로컬 Maven 저장소의 오래된 `SNAPSHOT`이 결과를 바꾸지 않습니까?
- 정상 사례뿐 아니라 실패 뒤 상태를 확인합니까?
- 동시성 테스트가 `sleep`과 컴퓨터 속도에 의존하지 않습니까?

## 프로젝트별 확인 예시

### Number Report

```sh
cd exercises/number-report
mvn clean test
```

확인 범위:

- 입력 변환과 합계 계산
- `BigDecimal` 반올림
- 오류 시 부분 출력 방지
- 실제 프로세스 종료 상태

### Counter Race와 Bounded Task Runner

```sh
cd exercises/counter-race
mvn clean test

cd ../bounded-task-runner
mvn clean test
```

확인 범위:

- barrier로 재현한 손실 갱신
- 잠금 적용 후 값 보존
- 대기열 포화와 작업 거절
- 시간 초과 취소와 종료 정리

### Concurrent Job Ledger

```sh
cd exercises/concurrent-job-ledger
mvn clean test
```

확인 범위:

- 생성 조건과 정확한 정수 연산
- 중복 요청의 단일 적용
- 실패 뒤 잔액과 적용 횟수 보존
- 제한된 실행기와 종료 처리

## 완료 기준

- 실행한 검사와 실행하지 못한 검사를 구분해 기록합니다.
- 명령 하나의 성공을 더 넓은 범위의 성공으로 과장하지 않습니다.
- debugger, thread dump, 정적 검사와 JFR이 각각 무엇을 보여 주는지 설명합니다.
- 성능 수치와 함께 재현 조건을 남깁니다.
- 최적화 뒤 정확성 테스트를 다시 실행합니다.
