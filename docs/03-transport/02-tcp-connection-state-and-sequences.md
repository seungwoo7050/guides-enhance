# TCP 연결 상태와 순서 번호

TCP 연결은 두 소켓이 존재한다는 사실만으로 설명할 수 없습니다. 각 종단점은 SYN, ACK, FIN, RST와 타이머 사건에 따라 상태를 바꾸고, 순서 번호로 바이트 스트림의 위치를 추적합니다. 상태와 순서 번호를 함께 봐야 핸드셰이크, 단방향 종료, 재전송을 이해할 수 있습니다.

## 학습 목표

- 능동 열기와 수동 열기의 상태 전이를 종단점별로 추적합니다.
- SYN, FIN, 페이로드가 사용하는 순서 번호 범위를 계산합니다.
- 누적 ACK가 확인한 바이트 범위를 설명합니다.

## 순서 번호와 ACK

TCP 헤더의 Sequence Number는 세그먼트 페이로드 첫 바이트의 번호입니다. Acknowledgment Number는 상대에게서 다음에 받을 것으로 기대하는 순서 번호입니다.

```text
seq 1000에서 100바이트 전송
→ 수신자가 1000..1099를 연속으로 수신
→ ACK 1100
```

ACK는 기본적으로 누적됩니다. `ACK 1100`은 1099번까지의 바이트를 연속으로 받았다는 뜻입니다. 그보다 뒤에 도착한 순서가 뒤바뀐 데이터는 SACK 옵션으로 따로 알릴 수 있습니다.

SYN과 FIN은 페이로드가 없어도 순서 번호 공간을 각각 1씩 사용합니다. 클라이언트의 SYN이 `seq 5000`이면 정상적인 SYN/ACK의 ACK는 `5001`입니다.

순서 번호는 32비트에서 순환합니다. 운영용 구현에서는 일반 정수 비교가 아니라 순환을 고려한 순서 번호 비교를 사용해야 합니다.

## 3단계 핸드셰이크

능동 열기를 수행하는 클라이언트의 일반적인 상태는 다음과 같습니다.

```text
CLOSED
→ SYN 전송
SYN-SENT
→ SYN/ACK 수신, ACK 전송
ESTABLISHED
```

수동 열기를 수행하는 서버의 일반적인 상태는 다음과 같습니다.

```text
CLOSED
→ passive open
LISTEN
→ SYN 수신, SYN/ACK 전송
SYN-RECEIVED
→ ACK 수신
ESTABLISHED
```

서버의 정상 경로를 `LISTEN → SYN-SENT`로 적으면 능동 열기와 수동 열기를 섞은 것입니다. SYN/ACK만 관찰했다고 양쪽 애플리케이션이 연결을 사용할 수 있는 상태라고 단정해서는 안 됩니다. 마지막 ACK까지 확인해야 합니다.

두 종단점이 동시에 능동 열기를 수행하면 양쪽이 `SYN-SENT`에서 SYN을 받고 `SYN-RECEIVED`로 이동할 수 있습니다. 일반적인 클라이언트·서버 경로는 아니지만 TCP 상태 기계가 단순한 직선이 아닌 이유를 보여 줍니다.

## 연결 종료

TCP의 두 송신 방향은 따로 닫을 수 있습니다. 한쪽이 FIN을 보내도 상대는 반대 방향으로 데이터를 계속 보낼 수 있습니다.

능동 종료 측의 대표 경로는 다음과 같습니다.

```text
ESTABLISHED
→ FIN-WAIT-1
→ FIN-WAIT-2
→ TIME-WAIT
→ CLOSED
```

수동 종료 측의 대표 경로는 다음과 같습니다.

```text
ESTABLISHED
→ CLOSE-WAIT
→ LAST-ACK
→ CLOSED
```

`CLOSE-WAIT`가 오래 남아 있다면 상대의 FIN을 커널이 받았지만 로컬 애플리케이션이 소켓을 닫지 않았을 가능성을 먼저 확인합니다. 이 상태만으로 네트워크에서 FIN이 손실되었다고 판단해서는 안 됩니다.

`TIME-WAIT`는 마지막 ACK를 다시 보낼 수 있게 하고, 이전 연결의 늦은 세그먼트가 같은 튜플의 새 연결과 섞일 위험을 줄입니다. TIME-WAIT 수가 많다는 이유만으로 자원 누수라고 결론 내리지 말고 능동 종료 주체와 연결 생성률을 확인해야 합니다.

## RST

RST는 정상 종료와 의미가 다릅니다. 수신 대기하지 않는 포트에 SYN이 도착하거나, 존재하지 않는 연결의 세그먼트를 받거나, 애플리케이션이 연결을 즉시 중단할 때 볼 수 있습니다.

RST를 받았다고 모든 상태에서 무조건 `CLOSED`로 이동하지 않습니다. 현재 상태와 순서 번호가 허용되는 범위인지 확인해야 합니다. `LISTEN`에서는 RST를 무시하고, 수동 열기 중인 `SYN-RECEIVED`는 유효한 RST를 받은 뒤 `LISTEN`으로 돌아갈 수 있습니다. 이미 동기화된 연결에서 유효한 RST를 받으면 연결을 중단합니다.

중간 장비가 RST를 만들 수도 있으므로 출발지 주소만 보고 애플리케이션 프로세스가 직접 보냈다고 확정해서는 안 됩니다.

## 상태 기계 프로젝트

[protocol-inspector](../../exercises/protocol-inspector/README.md)는 핵심적인 연결 수립, 종료, reset 처리만 포함하는 제한된 상태 기계를 제공합니다.

```sh
cd exercises/protocol-inspector
python3 -m unittest tests.test_tcp_state -v
```

허용하지 않은 사건은 상태를 바꾸지 않고 `InvalidTransition`을 발생시킵니다. 이 모델은 모든 TCP 타이머, 동시 종료, 재전송, 순서 번호 유효성 검사를 구현하지 않습니다.

CLI 예시는 다음과 같습니다.

```sh
python3 -m protocol_inspector tcp \
  --role server \
  --events passive-open,receive-syn,receive-ack,receive-fin,app-close,receive-ack
```

## 캡처에서 확인할 내용

1. 첫 SYN의 sequence와 SYN/ACK의 ACK 차이가 1인지 확인합니다.
2. SYN/ACK의 sequence와 마지막 ACK의 차이가 1인지 확인합니다.
3. 데이터 세그먼트의 `seq start:end` 길이가 페이로드 길이와 같은지 확인합니다.
4. ACK가 연속으로 받은 마지막 바이트 다음을 가리키는지 확인합니다.
5. 같은 SYN sequence가 다시 보이면 시각 정보와 캡처 위치를 기록합니다.

패킷 분석기가 상대 순서 번호를 표시할 수 있습니다. 보고서에는 상대 번호인지 실제 전송된 32비트 값인지 명시해야 합니다.

## 완료 기준

- 클라이언트와 서버의 핸드셰이크 상태를 따로 작성합니다.
- SYN, FIN, 페이로드가 소비한 순서 번호 범위와 다음 ACK를 계산합니다.
- RST를 역할과 현재 상태를 무시한 단일 전이로 처리하지 않습니다.
