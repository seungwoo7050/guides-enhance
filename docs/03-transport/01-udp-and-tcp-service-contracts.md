# UDP와 TCP의 서비스 특성

UDP를 빠른 프로토콜, TCP를 느린 프로토콜로만 나누면 실제 선택 기준을 놓칩니다. 메시지 경계, 순서, 중복, 손실, 연결 상태, 혼잡 제어 가운데 무엇을 전송 계층에 맡길지 먼저 정해야 합니다.

## 학습 목표

- UDP 데이터그램과 TCP 바이트 스트림의 전달 단위를 구분합니다.
- 손실, 순서 뒤바뀜, 중복, 메시지 프레이밍을 누가 처리해야 하는지 설명합니다.
- 애플리케이션 요구에 맞는 전송 프로토콜을 선택합니다.

## UDP 데이터그램

UDP에서 한 번의 전송은 하나의 데이터그램을 만듭니다. 수신 버퍼가 데이터그램보다 작으면 데이터가 잘리거나 API가 오류 또는 플래그로 알릴 수 있지만, 여러 데이터그램이 TCP처럼 하나의 연속된 바이트 스트림으로 합쳐지지는 않습니다.

UDP 자체는 다음 항목을 보장하지 않습니다.

- 전달
- 순서
- 중복 제거
- 혼잡 상태에 따른 자동 전송률 조절
- 연결 수립과 종료 핸드셰이크

애플리케이션에 이러한 기능이 필요하다면 메시지 ID, 순서 번호, ACK, 제한 시간, 재전송, 중복 억제, 전송률 조절을 직접 설계해야 합니다. 일부 기능을 추가했다고 자동으로 TCP와 같은 의미가 되지는 않습니다.

UDP 체크섬은 IPv4에서 0으로 두어 사용하지 않음을 나타낼 수 있지만, IPv6에서는 일반적으로 필수입니다. 체크섬은 전송 중 손상을 검출하는 데 도움을 줄 뿐 전달이나 순서를 보장하지 않습니다.

## TCP 바이트 스트림

TCP는 애플리케이션이 나눈 메시지 경계를 보존하지 않습니다.

```text
send 40바이트 + send 60바이트
≠ 상대가 recv 40바이트 + recv 60바이트로 읽는다는 보장
```

상대는 한 번에 100바이트를 읽거나 여러 번 나누어 읽을 수 있습니다. 따라서 애플리케이션 프로토콜은 다음과 같은 방법으로 메시지 경계를 정해야 합니다.

- 고정 길이
- 구분자
- 길이 프리픽스
- 자기 서술 형식
- 연결 종료

TCP가 제공하는 주요 기능은 다음과 같습니다.

- 두 종단점 사이의 순서 있는 바이트 스트림
- 손실된 바이트의 재전송
- 중복 바이트 제거
- 체크섬을 이용한 손상 검출
- 수신자 흐름 제어
- 네트워크 혼잡 제어
- 양방향을 따로 닫을 수 있는 full-duplex 연결

TCP가 바이트를 신뢰성 있게 전달한다고 해서 업무 처리가 정확히 한 번 실행되는 것은 아닙니다. 서버가 상태를 바꾼 뒤 응답이 사라지면 클라이언트의 재시도가 같은 작업을 다시 실행할 수 있습니다. 멱등성과 중복 요청 처리는 애플리케이션에서 따로 설계해야 합니다.

## 종단점과 연결 튜플

전송 종단점을 설명할 때는 다음 값을 함께 적습니다.

```text
프로토콜
출발지 IP:출발지 포트
목적지 IP:목적지 포트
```

TCP 수신 대기 소켓 하나는 같은 로컬 포트에서 많은 연결을 받을 수 있습니다. `accept`가 반환한 소켓마다 원격 튜플과 TCP 상태가 다릅니다.

NAT, 로드 밸런서, 프록시가 있으면 애플리케이션이 관찰한 상대 주소가 원래 클라이언트 주소와 다를 수 있습니다. 전달 헤더나 Proxy Protocol을 신뢰할 대상을 명시해야 합니다.

## 포트 번호

Well-known 포트는 상호 운용을 위한 기본 약속일 뿐입니다. 443번 포트가 열려 있어도 해당 종단점이 반드시 TLS나 HTTP를 제공하는 것은 아닙니다. TLS 연결에 성공했더라도 애플리케이션 프로토콜이 HTTP라고 단정할 수 없습니다.

짧은 연결을 대량으로 만들면 로컬 임시 포트, NAT 포트, TIME-WAIT 상태가 제한 자원이 될 수 있습니다.

## 실패 관찰의 차이

| 상황 | UDP에서 흔한 관찰 | TCP에서 흔한 관찰 |
|---|---|---|
| 대상 프로세스가 없음 | ICMP 오류 또는 제한 시간 초과 | RST 또는 연결 오류 |
| 중간 경로에서 손실 | 응답 없음 | 재전송 뒤 성공 또는 제한 시간 초과 |
| 상대가 비정상 종료 | 다음 요청에서 제한 시간 초과 가능 | RST, EOF 또는 쓰기 오류 |
| 메시지가 너무 큼 | 단편화, ICMP 또는 폐기 | 스트림이 여러 세그먼트로 나뉨 |
| 수신자가 느림 | 커널 버퍼에서 폐기될 수 있음 | `rwnd` 감소와 송신자 역압 |

정확한 API 오류와 발생 시점은 운영체제, 소켓 상태, 패킷이 도착한 시점에 따라 달라집니다. "UDP는 오류가 없고 TCP는 즉시 오류를 알려 줍니다"라고 단정해서는 안 됩니다.

## 프로토콜을 선택할 때 확인할 질문

1. 메시지 하나의 최대 크기와 프레이밍 방식은 무엇입니까?
2. 늦게 도착한 데이터도 가치가 있습니까?
3. 순서가 필요한 범위는 연결 전체입니까, 스트림별입니까, 메시지별입니까?
4. 애플리케이션이 중복 처리를 감당할 수 있습니까?
5. 혼잡 제어와 공정성은 누가 구현합니까?
6. NAT 매핑이나 방화벽 유휴 제한 시간이 지난 뒤 어떻게 복구합니까?
7. 연결 이동이나 여러 독립 스트림이 필요합니까?

실시간 미디어는 늦은 패킷을 버리고 다음 프레임으로 넘어갈 수 있습니다. 파일 전송은 모든 바이트의 정확한 순서를 요구합니다. 같은 낮은 지연 요구라도 손실을 처리하는 방식은 다를 수 있습니다.

QUIC은 UDP 위에서 신뢰성 있는 전달, 혼잡 제어, 암호화, 여러 스트림을 구현합니다. UDP 자체가 해당 기능을 제공하는 것이 아니라 QUIC이 UDP 데이터그램을 사용해 별도의 전송 프로토콜을 구현한 것입니다.

- 재시도 뒤 중복 처리가 발생할 가능성을 바이트 전달 성공 여부와 분리합니다.
- 프로토콜 선택 근거에 손실 허용 범위, 순서, 혼잡 제어, NAT 제한 시간을 포함합니다.
