# 재전송, RTT와 슬라이딩 윈도

TCP 송신자는 전송했지만 아직 누적 ACK를 받지 못한 바이트를 추적합니다. 손실을 직접 확인하는 것이 아니라 ACK 패턴과 타이머로 추정합니다. 너무 일찍 재전송하면 중복 트래픽이 늘고, 너무 늦게 재전송하면 복구가 지연됩니다.

## 학습 목표

- `send_base`, `next_sequence`, 전송 중인 바이트 수를 계산합니다.
- 누적 ACK, 중복 ACK, SACK의 의미를 구분합니다.
- RTT 표본, RTO, 제한 시간 백오프를 계산합니다.

## 송신자 상태

```text
send_base      가장 오래 ACK되지 않은 바이트
next_sequence  새 데이터에 사용할 다음 순서 번호
in_flight      next_sequence - send_base
```

ACK가 `send_base`보다 커지면 그 사이의 바이트가 새로 확인됩니다. 같은 ACK가 반복되면 새 바이트가 확인되지 않았다는 뜻입니다. 패킷 순서 뒤바뀜도 중복 ACK를 만들 수 있으므로 중복 ACK 한 번만으로 손실을 확정해서는 안 됩니다.

## 슬라이딩 윈도

Stop-and-wait처럼 세그먼트 하나의 ACK를 받은 뒤 다음 세그먼트를 보내면 대역폭-지연 곱이 큰 경로를 충분히 사용하지 못합니다. 슬라이딩 윈도는 일정 범위의 미확인 바이트를 동시에 전송합니다.

```text
[ACK 완료][전송했지만 미확인][지금 전송 가능][윈도 밖]
          ^ send_base       ^ next_sequence
```

실제 송신 상한은 수신자가 광고한 `rwnd`와 혼잡 제어의 `cwnd` 가운데 작은 값입니다. 이 값에서 이미 전송 중인 바이트를 빼면 새로 보낼 수 있는 양이 나옵니다.

## 누적 ACK와 SACK

수신자가 `1000..1999`와 `3000..3999`를 받았지만 중간의 `2000..2999`를 받지 못한 경우를 생각해 봅니다.

```text
누적 ACK:   2000
SACK block: 3000..4000
```

누적 ACK만으로는 뒤쪽 블록이 이미 도착했다는 사실을 표현할 수 없습니다. SACK을 협상했다면 수신자가 추가 블록을 알리고 송신자가 빠진 범위를 우선 재전송할 수 있습니다.

## RTT와 RTO

RTT는 세그먼트를 보낸 시점부터 해당 바이트를 확인하는 ACK를 받은 시점까지의 관찰값입니다. 큐 대기와 지연 ACK 때문에 매번 달라질 수 있으므로 평활한 추정값을 사용합니다.

RFC 6298의 기본 계산은 첫 표본 `R`에서 다음처럼 시작합니다.

```text
SRTT = R
RTTVAR = R / 2
RTO = SRTT + max(G, 4 * RTTVAR)
```

이후 표본 `R'`에는 일반적으로 `alpha = 1/8`, `beta = 1/4`를 사용합니다.

```text
RTTVAR = (1 - beta) * RTTVAR + beta * |SRTT - R'|
SRTT   = (1 - alpha) * SRTT + alpha * R'
RTO    = SRTT + max(G, 4 * RTTVAR)
```

`G`는 시계 해상도입니다. 실제 운영체제는 RFC의 기본값과 구현별 하한·상한을 함께 적용할 수 있습니다. 패킷 몇 개만 보고 커널의 최종 RTO를 정확히 역산했다고 주장해서는 안 됩니다.

## 재전송된 세그먼트의 RTT 모호성

같은 순서 번호 범위를 두 번 보낸 뒤 ACK가 오면 그 ACK가 첫 전송과 재전송 가운데 무엇을 확인했는지 누적 ACK만으로 알기 어렵습니다. Karn 알고리즘은 재전송된 세그먼트의 모호한 RTT 표본을 사용하지 않고, 제한 시간이 지나면 RTO를 지수적으로 늘립니다.

TCP Timestamp 옵션을 사용하면 추가 정보를 얻을 수 있지만 옵션 협상 여부와 구현 규칙을 확인해야 합니다.

## 제한 시간과 빠른 복구

RTO가 만료되면 가장 오래 확인되지 않은 데이터를 재전송합니다. 제한 시간이 반복되면 백오프로 재시도 간격을 늘려 장애 중 트래픽 폭증을 줄입니다.

여러 중복 ACK와 SACK은 타이머가 만료되기 전에 손실을 추정해 빠른 재전송과 복구를 시작할 수 있게 합니다. 정확한 임계값과 상태 전이는 혼잡 제어 알고리즘과 TCP 확장 기능에 따라 달라집니다.

TCP RTO와 애플리케이션 요청 제한 시간은 서로 다릅니다. 커널이 재전송을 계속하는 동안 애플리케이션은 더 짧은 마감 시간으로 요청을 포기할 수 있습니다.

## 결정적 윈도 모델

[window-model](../../examples/window-model/README.md)은 RTT 평활값, RTO 백오프, Reno 느린 시작, 혼잡 회피, 중복 ACK를 결정적인 상태 전이로 계산합니다.

```sh
cd examples/window-model
python3 window_model.py
python3 -m unittest -v
```

이 모델은 32비트 순서 번호 순환, SACK scoreboard, 실제 패킷 전송을 구현하지 않습니다. 계산 관계를 분리해 확인하기 위한 자료입니다.

## 실제 SYN 재전송

[linux-routing-nat](../../exercises/linux-routing-nat/README.md)은 라우터의 서버 방향 출력에 `netem loss 100%`를 적용합니다.

```sh
cd exercises/linux-routing-nat
sudo ./scripts/run-loss-retransmission.sh
```

클라이언트 캡처에서 같은 튜플, SYN 플래그, 순서 번호가 반복되면 손실 설정을 제거합니다. 다음 재전송이 서버에 도달하면 연결을 수립하고 페이로드를 교환합니다.

이 실험은 손실을 직접 만들었기 때문에 반복된 SYN과 원인의 관계를 알고 있습니다. 일반적인 캡처에서는 중복 수집, 미러링, 오프로딩, 패킷 순서 뒤바뀜, 중간 장비의 영향을 따로 확인해야 합니다.

## 완료 기준

- 순서 번호 범위에서 ACK된 구간과 아직 확인되지 않은 구간을 표시합니다.
- 첫 RTT 표본과 제한 시간 백오프 뒤의 RTO를 계산합니다.
- 반복된 패킷을 관찰한 사실과 실제 손실 원인을 확정하는 일을 구분합니다.
