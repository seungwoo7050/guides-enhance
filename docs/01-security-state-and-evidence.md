# 보안 상태와 증거

보안 문제를 도구 이름이나 공격 기법부터 살펴보면 가장 중요한 질문이 빠집니다.

```text
무엇을 지켜야 합니까?
어떤 상태가 실패입니까?
누가 그 상태를 만들 수 있습니까?
그 사실을 무엇으로 확인합니까?
```

이 장에서는 이후 모든 문서와 실습에서 사용할 판단 기준을 정리합니다.

## 1. “안전하다”를 검사 가능한 문장으로 바꾸기

“이 시스템은 안전합니다”라는 문장은 그대로 검사할 수 없습니다. 어떤 주체가 어떤 자원에 어떤 행동을 할 수 있어야 하는지 적어야 합니다.

```text
인증된 사용자 A는 자신이 소유한 완료된 보고서만 읽을 수 있습니다.
```

이 문장에는 다음 정보가 있습니다.

- 주체: 사용자 A
- 자원: 보고서
- 허용 행동: 읽기
- 허용 조건: A가 소유하고 상태가 `completed`임
- 금지 상태: 다른 사용자의 보고서나 미완료 보고서를 읽음

반면 “보고서 API는 인증을 사용합니다”라는 문장은 사용자 identity를 확인한다는 사실만 말합니다. 그 사용자가 요청한 보고서를 읽을 권한이 있는지는 설명하지 않습니다.

## 2. 보호할 속성을 실제 상태로 내리기

기밀성·무결성·가용성은 출발점입니다. 실제 시스템에서는 더 구체적으로 적어야 합니다.

| 속성 | 확인할 질문 |
|---|---|
| 기밀성 | 누가 데이터의 존재, 내용과 metadata를 볼 수 있습니까? |
| 무결성 | 누가 어떤 상태를 어떤 조건에서 바꿀 수 있습니까? |
| 가용성 | 어떤 사용자가 어느 시간 안에 어떤 기능을 계속 사용할 수 있어야 합니까? |
| 진위성 | 요청, event와 artifact가 주장한 출처에서 왔음을 어떻게 확인합니까? |
| 책임 추적 | 누가 무엇을 했는지 나중에 다시 확인할 수 있습니까? |
| 격리 | 한 사용자·service·job의 실패가 어디까지 영향을 줍니까? |
| 복구 가능성 | 손상 뒤 어떤 정본에서 안전한 상태를 다시 만들 수 있습니까? |

암호화 하나로 모든 문제가 해결되지는 않습니다. 저장된 데이터가 암호화돼 있어도 잘못된 사용자에게 정상적으로 복호화해 준다면 object authorization 실패는 그대로 남습니다.

## 3. 자산 이름보다 지켜야 할 상태를 적기

“데이터베이스를 보호합니다”는 범위가 너무 넓습니다. 다음처럼 실제 상태를 나눕니다.

```text
사용자 record의 내용
schema와 migration 이력
backup 파일
DB credential
audit event
삭제 요청의 완료 여부
```

각 상태는 지켜야 할 조건이 다릅니다.

- 사용자 record는 허가된 업무 요청으로만 변경됩니다.
- migration은 승인한 release artifact로만 실행됩니다.
- backup은 production host가 손상돼도 함께 삭제되지 않습니다.
- audit event는 조사 대상 process가 임의로 고칠 수 없습니다.

### 소유자를 한 칸으로 끝내지 않기

`owner` 하나만 적으면 누가 업무 영향을 판단하고, 누가 실제 요청을 허용하며, 누가 근거를 보관하는지 알 수 없습니다. 필요한 경우 다음 역할을 분리합니다.

| 역할 | 맡는 일 |
|---|---|
| 업무·위험 소유자 | 영향, 복구 우선순위와 처리 기한을 결정합니다. |
| 상태 정본 소유자 | authoritative record와 허용된 상태 변경을 관리합니다. |
| 판정 구현 소유자 | 요청의 identity·resource·action을 확인해 허용 또는 거절합니다. |
| 증거 보관 담당자 | event·test 결과·artifact의 수집, 접근, 보존과 폐기를 관리합니다. |
| 위험 수용 권한자 | 남은 위험을 정해진 범위와 기간 동안 공식적으로 승인합니다. |

한 사람이 여러 역할을 맡을 수는 있습니다. 다만 어떤 권한으로 결정했는지는 남겨야 합니다. 기술 검토자가 근거를 확인했다는 사실만으로 업무 위험까지 수용할 권한을 얻지는 않습니다.

## 4. 보안 불변식

보안 불변식은 공격, 장애와 재시도 중에도 유지돼야 하는 조건입니다.

```text
모든 report read는 요청한 actor와 report owner를 비교합니다.
worker credential은 발급된 tenant와 job 밖에서 사용할 수 없습니다.
release는 승인한 digest의 artifact만 실행합니다.
credential 원문은 log와 오류 응답에 남지 않습니다.
```

좋은 불변식은 다음 조건을 만족합니다.

- 주체, 자원과 행동이 구체적입니다.
- 특정 framework 함수 이름 하나에만 묶이지 않습니다.
- 정상 사례와 거절 사례를 모두 검사할 수 있습니다.
- 실패했을 때 관찰할 수 있는 결과가 있습니다.

정상 사례만 검사하면 `deny-all`처럼 사용자를 모두 막는 구현도 통과할 수 있습니다. 정상, 해석이 갈리는 경계값과 대표 실패를 함께 확인해야 합니다.

| 종류 | 예 | 확인할 결과 |
|---|---|---|
| 정상 | 소유자가 완료된 자신의 보고서를 읽음 | 읽기가 성공하고 allow event가 남음 |
| 경계 | 정확한 만료 시각, 누락된 tenant, `job-81`과 `job-81x` | 정한 규칙대로 일관되게 판정함 |
| 대표 실패 | 다른 소유자나 다른 job의 자원에 접근함 | 내용을 반환하지 않고 상태를 바꾸지 않으며 deny event를 남김 |

## 5. 통제와 증거를 구분하기

통제는 위험을 줄이는 장치이고, 증거는 그 장치가 실제로 적용됐음을 뒷받침하는 자료입니다.

| 주장 | 통제 예 | 필요한 증거 예 |
|---|---|---|
| 다른 tenant의 데이터를 읽을 수 없음 | object-level authorization | allow·deny 통합 테스트, resource 정본, audit event |
| 승인한 artifact만 실행함 | digest 고정과 검증 | release manifest, 검증 결과, runtime digest |
| 탈취 credential의 영향이 제한됨 | 짧은 수명과 job scope | 발급 정보, 실제 claim, 만료·scope 거절 event |
| 사고 뒤 복구 가능함 | 별도 backup과 restore 절차 | checksum, restore 실행 결과, 복구 시간 측정 |

설정 파일에 옵션이 있다는 사실만으로 실행 중인 service에도 적용됐다고 결론 내리지 않습니다. 설정, 배포 결과와 실제 요청 결과는 서로 다른 근거입니다.

## 6. 사실, 가설과 결론

보안 조사에서는 관찰한 내용과 원인 추정을 분리합니다.

### 사실

직접 관찰했거나 신뢰할 수 있는 자료에서 확인한 내용입니다.

```text
2026-08-09T01:02:03Z에 subject=user-17이 report-82를 요청했습니다.
응답 상태는 200이었습니다.
report-82의 owner는 user-44입니다.
```

### 가설

사실을 설명할 수 있지만 아직 확인하지 않은 원인입니다.

```text
다운로드 함수에서 report owner를 확인하지 않았을 수 있습니다.
```

### 결론

가설을 반박할 수 있는 검사를 수행한 뒤 채택한 판단입니다.

```text
일반 사용자 session을 가진 actor가 다른 사용자의 report ID를 알면 내용을 읽을 수 있습니다.
```

한 줄의 log, scanner 경고나 코드 일부만 보고 바로 결론을 내리지 않습니다.

## 7. 증거의 품질

증거를 사용할 때 다음을 확인합니다.

| 기준 | 질문 |
|---|---|
| 직접성 | 주장한 상태를 직접 보여 줍니까, 다른 사실에서 추정합니까? |
| 대상 식별 | 어느 service·version·request의 결과입니까? |
| 시간 | 사건 전·중·후 어느 시점이며 clock 차이는 얼마입니까? |
| 완전성 | 필요한 시작·종료·거절 event가 모두 수집됐습니까? |
| 무결성 | 조사 대상이 이 자료를 고칠 수 있습니까? |
| 재현성 | 같은 초기 상태와 입력에서 다시 확인할 수 있습니까? |
| 최소 영향 | 실제 사용자 데이터나 불필요한 상태 변경 없이 충분합니까? |

### 증거가 보장하지 않는 범위

| 증거 | 확인할 수 있는 것 | 단독으로 확인할 수 없는 것 |
|---|---|---|
| unit test | 선택한 함수와 입력에서 기대 결과가 나옴 | 다른 route, framework 연결, 실제 배포 상태 |
| 합성 행동 검사 | 정한 합성 상태에서 allow·deny와 상태 불변성이 재현됨 | 실제 tenant 데이터, 운영 topology와 모든 우회 경로 |
| audit event | 해당 producer가 특정 판정을 기록함 | 누락 event가 없다는 사실, producer가 손상되지 않았다는 사실 |
| signature·provenance | 특정 identity가 특정 bytes나 build statement에 서명함 | source가 안전함, builder가 침해되지 않음, runtime이 같은 digest를 실행함 |
| restore 실행 | 선택한 backup으로 목표 상태를 복원함 | 다른 시점의 backup과 실제 운영 부하에서 같은 결과가 남음 |

가능하면 서로 다른 실패 원인을 가진 근거를 함께 사용합니다. 예를 들어 API 응답, report owner를 가진 정본과 별도 audit event를 연결합니다. 같은 service가 만든 응답과 log 두 개는 형태가 달라도 같은 bug나 clock 오류에 함께 영향을 받을 수 있습니다.

## 8. 보안 주장 작성 형식

다음 형식을 기본으로 사용합니다.

```text
[주체]가 [전제]를 가진 상태에서
[행동]을 시도하면
시스템은 [허용·거절·격리·기록]해야 하며
[증거]로 결과를 확인합니다.
```

예:

```text
일반 사용자 token을 가진 subject가
다른 tenant의 report ID로 download를 요청하면
API는 내용을 반환하지 않고 거절해야 하며
audit event에는 subject·resource·decision·reason이 남아야 합니다.
```

같은 문장 형식을 threat, requirement, test와 detection에 사용하면 무엇이 빠졌는지 추적하기 쉬워집니다.

## 9. 예방, 탐지와 복구

예방 통제만으로 안전을 증명할 수 없습니다.

```text
예방: 금지된 상태 변경을 거절합니다.
탐지: 시도와 통제 실패를 알아챕니다.
대응: 추가 영향을 줄이기 위해 권한이나 기능을 제한합니다.
복구: 신뢰할 수 있는 정본과 credential로 정상 상태를 다시 만듭니다.
```

짧은 수명의 credential도 발급 범위가 잘못되면 문제가 됩니다. 따라서 scope를 벗어난 요청을 거절하고 event를 남기며, 필요하면 credential을 폐기하고 영향받은 자원을 조사해야 합니다.

## 완료 질문

- 인증과 object authorization은 왜 다른 문제입니까?
- 설정 파일과 실행 중 근거를 왜 구분해야 합니까?
- 같은 사건을 여러 log가 기록했다는 사실만으로 근거가 독립적이라고 할 수 없는 이유는 무엇입니까?
- 정상 사례가 없는 보안 테스트가 `deny-all` 구현을 통과시킬 수 있는 이유는 무엇입니까?
- 합성 행동 검사가 통과해도 production 전체가 안전하다고 말할 수 없는 이유는 무엇입니까?
