# 정렬, 안정성과 비교 하한

## 학습 목표

- 정렬의 key, 방향, 동점 처리, 안정성, 입력 변경 여부를 명확히 정합니다.
- comparison sort와 key의 값·표현 범위를 직접 이용하는 정렬을 구분합니다.
- merge sort, quicksort, heapsort, insertion sort의 시간·공간·안정성 특성을 비교합니다.
- decision tree를 이용해 comparison sort의 최악 경우 `Ω(n log n)` 비교 하한을 설명합니다.
- 전체 정렬이 필요하지 않은 문제에서는 더 적합한 선택을 판단합니다.

## 선행지식

[점근 분석](../01-foundations/02-asymptotic-analysis.md), 비교 관계, 반복 불변식을 알고 있어야 합니다.

특히 다음 표기법을 구분할 수 있어야 합니다.

- `O(f(n))`: 해당 함수의 상한을 나타냅니다.
- `Ω(f(n))`: 해당 함수의 하한을 나타냅니다.
- `Θ(f(n))`: 상한과 하한이 같은 점근적 성장률을 나타냅니다.
- **최악 시간**은 가능한 입력 중 가장 오래 걸리는 경우의 시간입니다.
- **기대 시간**은 알고리즘의 무작위성 또는 입력에 대한 확률 모델을 가정하여 평균적으로 얻는 시간 보장입니다.

## 핵심 관점

“정렬합니다”라는 문장만으로는 결과와 비용이 완전히 정해지지 않습니다.

```text
어떤 key를 기준으로 정렬합니까?
오름차순입니까, 내림차순입니까?
같은 key를 가진 원소의 순서를 보존해야 합니까?
입력 배열을 직접 변경해도 됩니까?
추가 메모리는 얼마나 사용할 수 있습니까?
최악 시간과 기대 시간 중 어떤 보장이 필요합니까?
```

예를 들어 다음 record가 있다고 합시다.

```text
A: (department=2, name="Kim")
B: (department=1, name="Lee")
C: (department=2, name="Park")
```

`department`를 기준으로 안정 정렬하면 결과는 다음과 같습니다.

```text
B, A, C
```

`A`와 `C`는 같은 `department=2`를 가지므로 원래의 `A → C` 순서가 유지됩니다.

정렬 알고리즘을 선택하기 전에 **정렬 순서와 필요한 보장**을 먼저 정해야 합니다.

## 1. 안정 정렬

**안정 정렬(stable sort)**은 같은 key를 가진 원소들의 **정렬 전 상대 순서**를 정렬 후에도 보존하는 정렬입니다.

예를 들어 다음처럼 `name` 순서가 이미 정해진 데이터가 있다고 합시다.

```text
A: (name="Kim",  department=2)
B: (name="Lee",  department=1)
C: (name="Park", department=2)
```

먼저 `name`으로 정렬한 뒤 `department`로 **안정 정렬**하면 결과는 다음과 같습니다.

```text
B: (Lee,  1)
A: (Kim,  2)
C: (Park, 2)
```

같은 `department=2`인 `A`, `C` 사이에서는 이전 정렬인 `name`의 순서가 유지됩니다.

따라서 여러 key를 우선순위 순으로 처리할 때 안정성이 유용합니다. 예를 들어

```text
1. name으로 정렬
2. department로 안정 정렬
```

하면 최종적으로 `department`가 주 정렬 기준이고, 같은 department 안에서는 `name` 순서가 유지됩니다.

반대로 안정성이 필요하지 않다면 불안정한 알고리즘을 선택해 더 작은 메모리나 더 나은 상수 비용 등의 이점을 얻을 수 있습니다. 다만 안정성 자체가 항상 추가 메모리를 요구하는 것은 아닙니다. **안정성과 공간 사용량은 알고리즘과 구현 방식에 따라 별도로 판단해야 합니다.**

## 2. 대표 comparison sort

**Comparison sort**는 원소 사이의 비교 결과를 통해 정렬 순서를 결정하는 정렬입니다. 예를 들어 comparator가 두 원소 `a`, `b`에 대해 어느 쪽이 먼저 와야 하는지를 판단합니다.

대표적인 알고리즘의 특성은 다음과 같습니다.

| 알고리즘 | 최악 시간 | 기대/평균 시간 | 추가 공간 | 안정성 | 주의점 |
| --- | --- | --- | --- | --- | --- |
| merge sort | `O(n log n)` | `O(n log n)` | 보통 `O(n)` | 안정 구현 가능 | 병합용 buffer가 필요할 수 있습니다. |
| quicksort | `O(n²)` | 기대 `O(n log n)` | 재귀 stack | 보통 불안정 | pivot과 partition 방식에 따라 성능이 크게 달라집니다. |
| heapsort | `O(n log n)` | `O(n log n)` | `O(1)` 구현 가능 | 불안정 | 추가 메모리는 작지만 cache locality 등의 상수 비용을 고려해야 합니다. |
| insertion sort | `O(n²)` | 입력에 따라 `O(n²)` | `O(1)` | 안정 구현 가능 | 작은 입력이나 거의 정렬된 입력에서 유리할 수 있습니다. |

여기서 `merge sort`의 추가 공간은 구현에 따라 달라집니다. 일반적인 배열 기반 구현에서는 병합을 위해 `O(n)` 정도의 buffer를 사용합니다. 따라서 “merge sort는 항상 `O(n)` 공간”이라고 단정하기보다 **사용한 구현의 공간 보장**을 확인해야 합니다.

`quicksort`의 재귀 stack 공간도 분할이 균형적인지에 따라 달라집니다. 균형 잡힌 경우 재귀 깊이는 `O(log n)` 정도이지만, 최악의 분할이 반복되면 `O(n)`까지 증가할 수 있습니다. 따라서 표의 “재귀 stack”만으로 공간을 고정된 하나의 복잡도로 표현해서는 안 됩니다.

표준 library의 정렬은 한 가지 알고리즘만 사용하는 것이 아니라 여러 알고리즘을 조합하거나 입력 특성에 따라 선택할 수 있습니다. 실제 프로그램에서는 **안정성, 최악 시간 보장, 추가 공간, comparator 요구사항을 library 문서에서 확인**해야 합니다.

## 3. merge sort의 병합 불변식

merge sort는 정렬된 두 구간을 하나의 정렬된 구간으로 병합하는 과정을 반복합니다.

예를 들어 다음 두 구간이 이미 정렬되어 있다고 합시다.

```text
왼쪽:  [1, 4, 7]
오른쪽: [2, 3, 8]
```

각 구간의 아직 소비하지 않은 첫 원소를 가리키는 pointer를 두 개 유지합니다. 매번 두 원소를 비교하여 더 작은 원소를 출력으로 이동합니다.

병합 중 다음 불변식을 유지할 수 있습니다.

```text
출력에 들어간 prefix는
두 입력 구간에서 지금까지 소비한 원소들을 정렬한 결과이다.

각 pointer는
자신의 입력 구간에서 아직 소비하지 않은 첫 원소를 가리킨다.
```

예를 들어 첫 비교에서 `1`을 선택하면 출력은

```text
[1]
```

이 되고 왼쪽 pointer가 다음 원소 `4`를 가리킵니다. 다시 `4`와 `2`를 비교하여 `2`를 선택하는 식으로 진행합니다.

### 안정성

두 key가 같을 때 왼쪽 구간의 원소를 먼저 선택하면 안정성을 유지할 수 있습니다.

예를 들어 다음처럼 값은 같지만 원래 순서가 다른 원소가 있다고 합시다.

```text
왼쪽:  (key=5, id=A)
오른쪽: (key=5, id=B)
```

같은 key에서 왼쪽 원소를 먼저 선택하면

```text
A, B
```

순서가 유지됩니다. 반대로 오른쪽 원소를 먼저 선택하면 이 상대 순서를 바꿀 수 있습니다.

### 시간

하나의 merge 단계에서는 두 정렬 구간의 모든 원소를 최대 한 번씩 처리하므로 `n`개 원소를 합치는 비용은 `Θ(n)`입니다.

merge sort의 재귀 깊이는 `Θ(log n)`이고 각 레벨에서 전체 원소에 대해 `Θ(n)`의 병합이 수행되므로 전체 시간은

```text
Θ(n log n)
```

입니다.

## 4. quicksort partition

quicksort는 하나의 pivot을 선택한 뒤 배열을 여러 구간으로 나누고 각 구간을 재귀적으로 정렬합니다.

중요한 것은 **partition 함수의 반환값과 구간의 의미를 정확히 정의하는 것**입니다.

예를 들어 특정 partition 구현에서 다음 조건을 사용한다고 합시다.

```text
pivot의 왼쪽 구간의 값은 pivot 이하이다.
pivot의 오른쪽 구간의 값은 pivot 이상이다.
pivot은 최종 위치에 있다.
```

이 조건이 성립한다고 가정하고 이후 재귀 호출의 범위를 결정해야 합니다.

하지만 이것이 모든 partition 구현에 공통된 규칙은 아닙니다. 대표적으로 **Hoare partition과 Lomuto partition은 pointer 이동 방식과 반환 index의 의미가 다릅니다.** 따라서 한 구현의 반환값 해석을 다른 partition 방식에 그대로 적용하면 경계 조건이 틀릴 수 있습니다.

### 최악의 경우

pivot이 매번 최솟값이나 최댓값처럼 선택되어 한쪽 구간만 거의 남으면 분할 크기가 다음처럼 될 수 있습니다.

```text
n-1, 0
n-2, 0
n-3, 0
...
```

이 경우 각 단계에서 많은 원소를 다시 검사하므로 전체 시간은 `O(n²)`가 됩니다.

반대로 분할이 계속 균형에 가깝다면 재귀 깊이가 `O(log n)` 정도가 되고 기대 시간은 `O(n log n)`이 될 수 있습니다. 무작위 pivot 선택 등을 사용하면 적절한 가정 아래 이러한 기대 성능을 얻을 수 있습니다.

따라서 quicksort의 **기대 `O(n log n)`을 최악 시간 보장인 것처럼 표현하면 안 됩니다.**

### 중복 key

같은 값이 매우 많이 존재하는 경우 일반적인 2-way partition은 동일한 값들을 여러 재귀 단계에서 다시 처리할 수 있습니다.

이때 3-way partition을 사용하여 다음 세 구간으로 나눌 수 있습니다.

```text
< pivot | == pivot | > pivot
```

`== pivot` 구간은 이미 서로 같은 key이므로 다시 재귀적으로 나눌 필요가 없습니다. 따라서 중복 key가 많은 입력에서 불필요한 재귀를 줄이는 데 도움이 될 수 있습니다.

## 5. comparison sort의 하한

서로 다른 `n`개 원소를 생각하면 가능한 입력 순서는 모두 `n!`개입니다.

예를 들어 원소가 3개라면 가능한 순열은

```text
3! = 6
```

개입니다.

comparison sort는 비교할 때마다 일반적으로 두 가지 결과를 구분합니다.

```text
a < b
a > b
```

서로 다른 원소만 다루는 경우 `a = b`는 발생하지 않습니다. 따라서 비교 과정을 이진 decision tree로 나타낼 수 있습니다.

- 내부 노드: 두 원소를 비교하는 연산
- 간선: 비교 결과
- leaf: 지금까지의 비교 결과를 바탕으로 결정된 입력의 순서

모든 `n!`개 입력 순열을 정확하게 구분하려면 서로 다른 순열에 대응할 수 있도록 최소 `n!`개의 leaf가 필요합니다.

높이가 `h`인 이진 tree가 가질 수 있는 leaf 수는 최대 `2^h`이므로

```text
2^h >= n!
```

이어야 합니다.

양변에 `log2`를 취하면

```text
h >= log2(n!)
```

입니다.

이제 `log2(n!)`의 성장률을 살펴보면

```text
log2(n!)
= log2(1 · 2 · ... · n)
= Σ(i=1..n) log2(i)
```

이고, 예를 들어 뒤쪽 절반의 항만 사용해도

```text
log2(n!)
>= (n/2) log2(n/2)
= Ω(n log n)
```

이므로

```text
log2(n!) = Ω(n log n)
```

입니다.

따라서 모든 comparison sort에는 **최악의 경우 `Ω(n log n)`번의 비교가 필요합니다.**

중요한 점은 이 하한이 “모든 정렬 알고리즘은 반드시 `n log n` 시간이 걸린다”는 뜻이 아니라는 것입니다. 이 결과는 **원소 사이의 비교 결과만으로 정렬 순서를 알아내는 일반적인 comparison sort 모델**에 대한 하한입니다.

또한 이 하한은 최악 경우의 비교 횟수에 대한 것입니다. 특정 입력에 대해서 더 적은 비교를 수행하는 알고리즘이 존재하는 것과 모순되지 않습니다.

## 6. counting sort와 radix sort

comparison sort의 하한을 피할 수 있는 정렬은 원소의 key가 가진 추가 정보를 이용합니다. 대표적으로 counting sort와 radix sort가 있습니다.

### counting sort

key가 작은 정수 범위에 있다고 합시다.

```text
0, 1, 2, ..., K
```

그러면 각 key가 몇 번 등장하는지를 저장하는 빈도 배열을 만들 수 있습니다.

예를 들어 입력이

```text
[2, 0, 2, 1, 0]
```

이라면 빈도는

```text
0 → 2
1 → 1
2 → 2
```

입니다.

이 방식은 원소끼리 비교하여 순서를 알아내는 대신 **key의 값 자체를 배열 index로 사용**합니다.

시간 복잡도는 일반적인 구현에서

```text
O(n + K)
```

이고, 빈도 배열을 위한 추가 공간은

```text
O(K)
```

입니다.

따라서 `K`가 `n`에 비해 매우 크면 비효율적일 수 있습니다. 예를 들어 원소가 몇 개뿐인데 key가 `0`부터 `10^12`까지 넓게 퍼져 있다면 거대한 빈도 배열을 만드는 방식은 적합하지 않습니다.

key가 음수인 경우에는 최소 key를 기준으로 offset을 적용하는 등 별도의 변환이 필요합니다. 이때도 실제 key 범위가 얼마나 큰지를 확인해야 합니다.

counting sort를 **안정적으로 구현할 수 있는지**는 별도의 구현 문제입니다. 단순히 빈도만 세는 구현과 원래 순서를 보존하는 안정 구현은 처리 방식이 다를 수 있습니다.

### radix sort

radix sort는 key를 여러 개의 digit 또는 부분 key로 나누어 여러 번 정렬합니다.

예를 들어 10진수의 각 자릿수를 사용하는 LSD(Least Significant Digit) radix sort는

```text
일의 자리
→ 십의 자리
→ 백의 자리
→ ...
```

순서로 처리합니다.

LSD radix sort에서는 **각 pass가 안정적이어야 합니다.** 이전 pass에서 같은 현재 digit을 가진 원소들의 순서를 유지해야 다음 pass가 상위 digit의 정렬 결과를 망가뜨리지 않기 때문입니다.

예를 들어 먼저 일의 자리로 안정 정렬한 결과가 다음과 같다고 합시다.

```text
12, 22, 31, 41
```

이제 십의 자리로 안정 정렬하면 십의 자리를 기준으로 재배치하면서도 같은 십의 자리를 가진 원소 사이에서는 이전 일의 자리 정렬 순서를 보존할 수 있습니다.

radix sort의 시간은 단순히 `n`만으로 결정되지 않습니다. 일반적으로

- 원소 수 `n`
- 처리할 digit/pass 수 `d`
- 각 pass에서 사용하는 base 또는 key 범위

등에 따라 달라집니다.

따라서 radix sort가 comparison sort보다 항상 빠르다고 말해서는 안 됩니다. key 표현과 구현 비용이 실제 입력에 적합한지를 확인해야 합니다.

### 왜 comparison 하한과 모순되지 않는가?

counting sort와 radix sort는 원소 사이의 비교만으로 순서를 결정하지 않습니다.

```text
comparison sort
→ key를 비교하여 정보를 얻음

counting/radix sort
→ key의 값 또는 표현을 직접 이용함
```

따라서 comparison sort의 decision-tree 하한을 그대로 적용할 수 없습니다.

## 7. 전체 정렬이 필요하지 않은 경우

문제에서 요구하는 정보가 전체 순서가 아니라면 전체 정렬을 수행할 필요가 없을 수 있습니다.

- **최솟값 하나만 필요**하면 모든 원소를 한 번 순회하여 `O(n)`에 찾을 수 있습니다.
- **상위 `k`개만 필요**하면 크기 `k`의 heap을 사용하는 방법을 검토할 수 있습니다.
- **`k`번째 원소만 필요**하면 selection 알고리즘을 검토할 수 있습니다.
- **membership 질의만 필요**하면 정렬 대신 hash set이 더 적합할 수 있습니다.
- **정렬된 순서에서 경계를 찾는 질의가 반복**된다면 먼저 정렬한 뒤 binary search 계열의 방법을 사용할 수 있습니다.

핵심은 문제에서 실제로 필요한 순서 정보만 계산하는 것입니다.

예를 들어 최솟값 하나만 필요한데 전체 배열을 정렬하면

```text
필요한 것: 최솟값 1개
수행한 것: 전체 순서 계산
```

이 되어 불필요한 작업을 하게 됩니다.

## 8. 정렬 결과 검증

정렬 결과는 “순서가 맞다”는 것만 검사해서는 충분하지 않습니다.

다음 조건을 각각 확인합니다.

### 8.1 정렬 순서

모든 인접한 원소가 정해진 순서를 만족하는지 확인합니다.

오름차순이라면 대략 다음 조건을 검사합니다.

```text
a[i] <= a[i+1]
```

comparator를 사용하는 경우에는 해당 comparator가 정의하는 순서에 맞는지를 검사해야 합니다.

### 8.2 원소 보존

정렬은 일반적으로 원소의 순서만 바꾸어야 하므로 결과는 입력과 같은 **multiset**을 가져야 합니다.

multiset은 각 값이 몇 번 등장하는지를 포함한 원소들의 집합입니다. 따라서 다음 두 결과는 같은 집합(set)이지만 같은 multiset은 아닙니다.

```text
입력: [1, 1, 2]
결과: [1, 2]
```

`1` 하나가 사라졌기 때문입니다.

마찬가지로

```text
입력: [1, 2]
결과: [1, 1, 2]
```

는 원소가 하나 추가되었으므로 올바른 정렬 결과가 아닙니다.

따라서 테스트에서는 **정렬 순서와 multiset 보존을 별도로 검사**하는 것이 좋습니다.

### 8.3 안정성

안정성이 요구된다면 key 값만 확인해서는 부족합니다.

예를 들어

```text
(A, key=5)
(B, key=5)
```

가 입력으로 들어왔을 때 결과가

```text
(B, key=5)
(A, key=5)
```

라면 key만 보면 정렬되어 있지만 안정 정렬의 조건은 만족하지 않습니다.

### 8.4 comparator

comparator를 사용하는 정렬에서는 comparator가 일관된 순서를 정의해야 합니다.

특히 다음을 확인해야 합니다.

- 동일한 원소의 비교 결과가 일관적인가?
- `a < b`라고 판단한 뒤 `b < a`도 참이 되는 모순이 없는가?
- 여러 원소의 비교 관계가 서로 모순되지 않는가?

정렬 알고리즘 자체가 올바르더라도 comparator가 일관된 순서를 제공하지 않으면 결과를 정상적인 정렬 순서로 해석하기 어렵습니다.

### 8.5 경계 입력

최소한 다음 입력을 테스트합니다.

```text
[]
[1]
[1, 1, 1]
이미 정렬된 입력
역순 입력
중복이 많은 입력
```

또한 입력을 직접 변경하는지 여부가 API 계약에 포함되어 있다면 원본 배열이 변경되었는지도 확인합니다.

## 9. 정렬과 탐색의 연결

정렬은 그 자체의 비용뿐 아니라 이후 질의의 비용까지 함께 고려해야 합니다.

예를 들어 `n`개의 값을 정렬한 뒤 여러 번 `lower_bound` 질의를 수행한다고 합시다.

먼저 정렬하는 데 `O(n log n)`이 필요하고, 정렬된 배열에서는 각 `lower_bound` 질의를 binary search 방식으로 `O(log n)`에 처리할 수 있습니다.

즉 질의가 충분히 많다면

```text
정렬 비용을 한 번 지불
→ 이후 각 질의를 빠르게 처리
```

하는 것이 유리할 수 있습니다.

반대로 질의가 한 번뿐이라면 정렬 비용을 추가로 지불하지 않고 선형 탐색을 하는 편이 더 단순하고 빠를 수 있습니다.

정렬된 배열에서 **원래 index가 필요한 경우**에는 값만 정렬하지 않고 다음처럼 원래 위치를 함께 저장할 수 있습니다.

```text
(value, original_index)
```

예를 들어

```text
입력:
index 0 → 5
index 1 → 2
index 2 → 5
```

를

```text
(5, 0)
(2, 1)
(5, 2)
```

처럼 표현합니다.

같은 값에 대한 원래 index 순서가 결과 조건에 영향을 준다면 이때도 안정성 또는 명시적인 tie-breaker가 필요한지 확인해야 합니다.

## 연결 구현

[`verified-algorithms`](../../exercises/verified-algorithms/)은 정렬 알고리즘 자체를 공개 API로 제공하지 않습니다. 대신 다음 함수가 정렬 결과에 의존합니다.

- `lower_bound`: 입력이 오름차순으로 정렬되어 있다는 호출자 전조건이 있습니다.
- `select_intervals`: `(end, start)` 순서로 정렬합니다.
- `kruskal_mst`: `(weight, source, target)` 순서로 정렬합니다.

따라서 merge sort 또는 stable multi-key sort를 별도의 작은 구현으로 작성하고 다음을 확인합니다.

- 결과가 요구된 정렬 순서를 만족하는가
- 원본 multiset을 보존하는가
- 같은 key에서 `original_id`의 상대 순서를 보존하는가
- 비교 횟수가 예상한 범위에 있는가
- 이미 정렬된 입력, 역순 입력, 중복이 많은 입력에서 동작하는가
- 최악의 분할이 발생할 수 있는 경우 quicksort의 시간과 재귀 깊이를 어떻게 보장하는가

특히 `lower_bound`처럼 정렬된 입력을 전제로 하는 함수에서는 정렬 자체의 결과가 잘못되면 탐색 함수의 구현이 맞더라도 전체 결과가 틀릴 수 있습니다.

## 완료 기준

- 정렬의 key, 방향, 동점 처리, 안정성, 입력 변경 여부를 명시할 수 있습니다.
- merge sort, quicksort, heapsort, insertion sort의 최악 시간과 추가 공간 특성을 비교할 수 있습니다.
- quicksort의 기대 `O(n log n)`과 최악 `O(n²)`을 구분할 수 있습니다.
- `n!`개의 순열과 decision tree의 높이에서 comparison sort의 `Ω(n log n)` 하한을 유도할 수 있습니다.
- 이 하한이 comparison sort 모델에 적용되며 counting sort와 radix sort에 그대로 적용되지 않는 이유를 설명할 수 있습니다.
- counting sort에서 `K`가 시간과 공간에 미치는 영향을 설명할 수 있습니다.
- LSD radix sort에서 각 pass의 안정성이 필요한 이유를 설명할 수 있습니다.
- 정렬 결과에서 순서 조건과 multiset 보존을 별도로 검사할 수 있습니다.
- 전체 정렬이 필요한지, 아니면 최소값·상위 `k`개·`k`번째 원소·membership 질의 등 더 직접적인 방법이 적합한지 판단할 수 있습니다.

## 실패 신호

- 안정성이 필요한데 key 값만 확인합니다.
- 안정 정렬이 항상 추가 메모리를 필요로 한다고 단정합니다.
- quicksort의 기대 `O(n log n)`을 최악 시간 보장처럼 표현합니다.
- quicksort의 재귀 stack 공간을 입력과 무관하게 하나의 고정된 복잡도로 표현합니다.
- Hoare와 Lomuto partition의 반환 index 의미를 동일하게 취급합니다.
- counting sort에서 key 범위 `K`의 시간·공간 비용을 빠뜨립니다.
- radix sort의 시간 복잡도에서 digit 수나 base의 영향을 무시합니다.
- comparison sort 하한을 모든 정렬 알고리즘에 적용합니다.
- 정렬 결과가 순서상 맞다는 이유만으로 원소 유실이나 중복 삽입을 확인하지 않습니다.
- `lower_bound`처럼 정렬된 입력을 요구하는 함수의 호출 전조건을 확인하지 않습니다.
