# 디버거 참고

이 문서는 **재현 가능한 실행 오류**가 있을 때 GDB 또는 LLDB를 사용해 프로그램의 상태를 확인하는 기본 절차를 정리합니다.

디버거의 목적은 프로그램을 처음부터 끝까지 한 줄씩 따라가는 것이 아니라, **오류가 생긴 원인에 대한 가설을 세우고 그 가설을 실행 중 상태로 검증하는 것**입니다.

예를 들어 프로그램이 `buffer[index]`에서 충돌했다면 단순히 그 줄에서 멈추는 것으로 끝내지 않습니다.

- `index`가 언제 범위를 벗어났는가?
- `buffer`가 여전히 유효한 객체를 가리키는가?
- 잘못된 `index`를 어느 호출자가 전달했는가?
- 다른 스레드가 해당 값을 변경했는가?

와 같은 질문을 정한 뒤, 그 질문에 답할 수 있는 위치에 중단점이나 watchpoint를 설정합니다.

---

## 기본 용어

- **중단점(breakpoint)**: 프로그램 실행을 특정 함수나 소스 위치에서 멈추게 하는 지점입니다.
- **프레임(frame)**: 현재 호출 스택에 있는 함수 호출 하나를 의미합니다. 각 프레임에는 해당 호출의 인자, 지역 변수, 실행 위치 등이 있습니다.
- **호출 스택(call stack)**: 현재 함수가 어떤 함수들을 거쳐 호출되었는지를 나타내는 프레임의 연속입니다.
- **watchpoint**: 특정 메모리 위치의 값이 변경될 때 실행을 멈추게 하는 기능입니다.
- **core dump**: 프로그램이 비정상 종료했을 때 당시의 메모리와 레지스터 등의 상태를 저장한 파일입니다.
- **sanitizer**: 잘못된 메모리 접근, 정의되지 않은 동작 등을 실행 중 탐지하도록 컴파일러가 프로그램에 검사 코드를 삽입하는 기능입니다.

---

## 디버그 정보 포함하기

디버거가 소스 코드의 줄 번호, 함수 이름, 지역 변수 등을 표시하려면 실행 파일에 디버그 정보가 포함되어 있어야 합니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -g -O0 source.c -o program
```

각 옵션의 의미는 다음과 같습니다.

- `-g`: 소스 위치, 함수 이름, 변수 정보 등 디버거가 사용하는 디버그 정보를 실행 파일에 포함합니다.
- `-O0`: 컴파일러 최적화를 끕니다. 최적화가 활성화되면 코드가 재배치되거나 변수가 제거·병합되어 소스 코드와 실제 실행 흐름이 다르게 보일 수 있으므로, 원인 조사 단계에서는 `-O0`이 이해하기 쉽습니다.
- `-Wall -Wextra -Wpedantic`: 컴파일 경고를 넓게 활성화합니다. 디버깅 중에도 경고 옵션을 제거하지 않습니다.

`-O0`은 **조사를 쉽게 하기 위한 설정**이지 실제 배포 환경을 대신하는 설정이 아닙니다. 문제를 수정한 뒤에는 실제 사용할 최적화 수준에서도 다시 빌드하고 테스트해야 합니다. 최적화 수준에 따라 드러나는 정의되지 않은 동작이나 타이밍 문제가 있을 수 있기 때문입니다.

## GDB 시작

실행 파일을 지정하여 GDB를 시작합니다.

```sh
gdb ./program
```

GDB가 시작된 뒤 프로그램 인자를 바로 전달할 수 있습니다.

```text
(gdb) run one two
```

이 경우 프로그램에는 대략 다음과 같은 인자가 전달됩니다.

```c
argc == 3
argv[0] == "./program"
argv[1] == "one"
argv[2] == "two"
```

인자를 미리 지정한 뒤 여러 번 같은 조건으로 실행할 수도 있습니다.

```text
(gdb) set args one two
(gdb) run
```

`set args`는 이후의 `run`에서도 같은 인자를 사용하므로, 같은 입력으로 오류를 반복 재현할 때 편리합니다.

---

## LLDB 시작

실행 파일을 지정하여 LLDB를 시작합니다.

```sh
lldb ./program
```

프로그램 인자는 `run` 뒤에 전달할 수 있습니다.

```text
(lldb) run one two
```

같은 오류를 조사할 때는 실행 파일, 프로그램 인자, 입력 파일, 환경 변수 등 **재현 조건을 가능한 한 고정**해야 합니다. 실행할 때마다 조건이 달라지면 관찰한 값의 변화가 버그 때문인지 입력 차이 때문인지 구분하기 어렵습니다.

## 중단점

중단점은 프로그램을 조사하려는 위치에서 멈추게 합니다.

오류가 발생한 줄 자체보다 **잘못된 값이 만들어지기 직전**에 중단점을 두는 것이 일반적으로 더 유용합니다.

### 함수 이름으로 설정

GDB:

```text
(gdb) break main
```

LLDB:

```text
(lldb) breakpoint set --name main
```

이 명령은 `main` 함수에 진입할 때 실행을 멈춥니다.

### 파일과 줄 번호로 설정

GDB:

```text
(gdb) break parser.c:120
```

LLDB:

```text
(lldb) breakpoint set --file parser.c --line 120
```

예를 들어 `parser.c:125`에서 배열 범위를 벗어난 접근이 발생한다면, 125번째 줄만 보는 대신 `index`나 `length`가 계산되는 120번째 줄 부근에서 멈춰 값이 어떻게 만들어지는지 확인하는 편이 좋습니다.

---

## 실행 제어

프로그램이 중단점에서 멈춘 뒤에는 다음 명령으로 실행 범위를 조절합니다.

| 동작 | GDB | LLDB |
| --- | --- | --- |
| 현재 함수의 다음 소스 줄까지 실행 | `next` | `next` |
| 현재 줄에서 호출되는 함수 안으로 들어감 | `step` | `step` |
| 다음 중단점 또는 종료까지 계속 실행 | `continue` | `continue` |
| 현재 함수를 끝내고 호출자에게 돌아감 | `finish` | `finish` |
| 실행 중인 프로그램 종료 | `kill` | `process kill` |

`next`와 `step`의 차이가 중요합니다.

예를 들어 현재 줄이 다음과 같다고 가정합니다.

```c
result = parse(input);
```

- `next`: `parse()` 내부로 들어가지 않고 이 호출 전체를 실행한 뒤 다음 소스 줄에서 멈춥니다.
- `step`: `parse()` 함수 안으로 들어가 첫 실행 가능한 소스 위치에서 멈춥니다.

처음부터 모든 함수에 `step`으로 들어가면 표준 라이브러리나 관심 없는 보조 함수까지 추적하게 되어 조사 범위가 지나치게 커질 수 있습니다. 기본적으로 `next`를 사용하고, **문제가 해당 호출 안에서 생긴다고 판단될 때만 `step`으로 들어가는 방식**이 효율적입니다.

## 변수와 표현식 확인

### GDB

```text
(gdb) print index
(gdb) print *pointer
(gdb) print values[3]
(gdb) print/x flags
```

### LLDB

```text
(lldb) frame variable index
(lldb) expression *pointer
(lldb) expression values[3]
(lldb) expression --format x -- flags
```

예를 들어 다음 코드가 있다고 가정합니다.

```c
if (index < length) {
    value = values[index];
}
```

중단점에서 다음 값을 확인할 수 있습니다.

```text
index = 4
length = 4
```

유효한 인덱스는 `0`부터 `length - 1`까지이므로 `index == length`는 범위를 벗어납니다. 따라서 이 경우에는 `values[index]`가 충돌한 위치만 조사할 것이 아니라 **`index`가 4가 된 시점과 그 값을 만든 코드**를 찾아야 합니다.

### 포인터를 역참조하기 전에 확인할 것

다음과 같은 명령은 포인터가 유효하다는 전제가 필요합니다.

```text
(gdb) print *pointer
(lldb) expression *pointer
```

먼저 다음 조건을 확인합니다.

```text
pointer가 NULL입니까?
pointer가 가리키는 객체가 아직 살아 있습니까?
접근하려는 index가 length보다 작습니까?
이 메모리를 누가 할당했습니까?
누가 해제할 책임을 가지고 있습니까?
현재 코드가 그 메모리를 읽을 권한이 있는 시점입니까?
```

특히 C에서 포인터 값이 `NULL`이 아니라고 해서 반드시 유효한 객체를 가리키는 것은 아닙니다. 이미 `free()`된 메모리의 주소가 포인터에 남아 있을 수도 있기 때문입니다.

## 호출 스택

현재 실행 위치까지 어떤 함수들이 호출되었는지 확인합니다.

GDB:

```text
(gdb) backtrace
```

LLDB:

```text
(lldb) bt
```

예를 들어 호출 스택이 다음과 같을 수 있습니다.

```text
main
└── handle_request
    └── parse_record
        └── copy_field
```

충돌이 `copy_field`에서 발생했다고 해서 반드시 `copy_field` 자체가 원인인 것은 아닙니다. `parse_record`가 잘못된 길이를 전달했거나, `handle_request`가 이미 해제된 버퍼를 넘겼을 수도 있습니다.

따라서 호출 스택을 사용할 때는 다음 순서로 생각합니다.

1. 현재 충돌한 함수에서 잘못된 값이 무엇인지 확인합니다.
2. 그 값이 인자라면 호출자 프레임으로 이동합니다.
3. 호출자가 그 값을 어떻게 계산하거나 전달했는지 확인합니다.
4. 잘못된 값이 처음 만들어진 프레임까지 거슬러 올라갑니다.

특정 프레임으로 이동할 수 있습니다.

GDB:

```text
(gdb) frame 2
```

LLDB:

```text
(lldb) frame select 2
```

프레임을 변경하면 현재 선택된 함수의 인자와 지역 변수를 조사할 수 있습니다. **프레임 번호는 실행할 때마다 동일하다고 가정하지 말고 현재 `backtrace` 결과를 기준으로 선택**합니다.

## 메모리 확인

변수 단위의 출력만으로 부족할 때는 특정 주소의 원시 메모리를 직접 읽을 수 있습니다.

### GDB

```text
(gdb) x/16bx buffer
(gdb) x/s text
(gdb) x/8gx pointer
```

GDB의 `x`는 메모리를 검사하는 명령입니다.

예를 들어:

```text
x/16bx buffer
```

은 `buffer`가 가리키는 위치부터

- `16`: 16개 항목을
- `b`: 1바이트 단위로
- `x`: 16진수 형식으로

출력합니다.

따라서 바이너리 버퍼의 앞 16바이트를 확인할 때 유용합니다.

```text
x/s text
```

는 `text` 주소부터 메모리를 C 문자열처럼 출력합니다.

```text
x/8gx pointer
```

는 `pointer` 위치부터 8개의 큰 단위 값을 16진수로 확인할 때 사용할 수 있습니다.

### LLDB

```text
(lldb) memory read --format x --size 1 --count 16 buffer
(lldb) memory read --format c --size 1 --count 16 text
```

첫 번째 명령은 `buffer`부터 1바이트 크기의 값을 16개 읽어 16진수로 표시합니다.

두 번째 명령은 `text`부터 1바이트 크기의 값을 문자 형식으로 읽습니다. 문자 수를 지정했으므로 **NUL 종료 여부와 관계없이 지정한 범위만 조사할 수 있습니다.**

### 문자열과 임의 바이트 데이터 구분

C 문자열은 마지막에 값이 `0`인 바이트, 즉 **NUL 문자(`'\0'`)**가 있다는 전제에서 다뤄집니다.

따라서 다음과 같은 상황에서는 문자열 출력 명령을 그대로 사용하지 않는 편이 안전합니다.

- 버퍼가 문자열이 아니라 바이너리 데이터인 경우
- NUL 종료가 보장되지 않는 경우
- 메모리가 손상되어 종료 위치를 신뢰할 수 없는 경우

이때는 `주소 + 읽을 길이`를 명시하여 필요한 범위만 검사합니다.

## Watchpoint

특정 변수가 **언제 변경되는지** 모를 때 watchpoint를 사용할 수 있습니다.

GDB:

```text
(gdb) watch account.balance
```

LLDB:

```text
(lldb) watchpoint set variable account.balance
```

일반적인 중단점은 "이 코드 위치에 도달하면 멈춘다"는 조건인 반면, watchpoint는 "이 메모리의 값이 변경되면 멈춘다"는 조건입니다.

예를 들어 `account.balance`가 어느 함수에서 잘못 변경되는지 모른다면 watchpoint를 설정하고 실행을 계속합니다. 값이 바뀌는 순간 디버거가 멈추므로, 그 시점의 호출 스택을 확인해 변경한 코드를 찾을 수 있습니다.

다만 watchpoint에는 제약이 있습니다.

- CPU가 제공하는 하드웨어 watchpoint 개수가 제한될 수 있습니다.
- 감시 범위와 플랫폼에 따라 실행 속도가 느려질 수 있습니다.
- 지역 변수처럼 수명이 끝나는 객체를 계속 감시할 수는 없습니다.

따라서 "값이 잘못되었다"는 사실은 알지만 **어디에서 변경되었는지 모를 때** 특히 유용합니다.

## 자식 프로세스 디버깅

프로그램이 `fork()`를 호출하면 부모와 자식이라는 두 프로세스가 생깁니다. 이때 디버거가 어느 프로세스를 추적할지 결정해야 합니다.

### GDB

자식 프로세스를 따라가려면:

```text
(gdb) set follow-fork-mode child
```

부모와 자식 중 추적하지 않는 쪽도 디버거 관리 아래 남기려면:

```text
(gdb) set detach-on-fork off
```

`follow-fork-mode child`는 `fork()` 이후 기본 추적 대상을 자식으로 선택합니다. `detach-on-fork off`는 다른 프로세스에서 자동으로 분리하지 않도록 합니다.

다중 프로세스 프로그램을 조사할 때는 다음 정보를 섞지 않도록 주의합니다.

- 현재 선택된 PID
- 각 프로세스의 stdout
- 각 프로세스의 stderr
- 각 프로세스의 종료 상태
- 부모와 자식이 상속하거나 새로 연 파일 디스크립터(FD)

**FD(file descriptor)** 는 열린 파일, 파이프, 소켓 같은 입출력 자원을 프로세스 내부에서 식별하는 정수 번호입니다.

### LLDB

`fork()` 이후의 추적 기능은 운영체제와 LLDB 버전에 따라 지원 범위가 다를 수 있습니다. 단순한 경우에는 자식 프로세스의 PID를 확인한 뒤 별도의 LLDB 세션에서 attach하여 조사하는 방법도 사용할 수 있습니다.

다중 프로세스 문제에서는 "어느 프로세스에서 관찰한 값인가?"를 항상 명확히 해야 합니다.

## 스레드 확인

여러 스레드가 있는 프로그램에서는 현재 선택된 스레드 하나만 보고 원인을 판단하면 안 됩니다.

### GDB

```text
(gdb) info threads
(gdb) thread 3
(gdb) thread apply all backtrace
```

- `info threads`: 현재 프로세스의 스레드 목록을 표시합니다.
- `thread 3`: 3번 스레드를 선택합니다.
- `thread apply all backtrace`: 모든 스레드의 호출 스택을 출력합니다.

### LLDB

```text
(lldb) thread list
(lldb) thread select 3
(lldb) thread backtrace all
```

교착 상태(deadlock)를 조사할 때는 **모든 스레드가 무엇을 기다리고 있는지** 확인해야 합니다.

예를 들어:

```text
Thread A: mutex_1을 보유한 채 mutex_2를 기다림
Thread B: mutex_2를 보유한 채 mutex_1을 기다림
```

이라면 두 스레드가 서로 상대방이 가진 mutex를 기다리므로 진행할 수 없습니다.

따라서 교착 상태에서는 각 스레드의 호출 스택뿐 아니라 다음도 함께 확인합니다.

- 현재 기다리는 mutex
- 이미 보유한 mutex
- lock을 획득한 순서
- condition variable, semaphore, I/O 등 다른 대기 원인

## Core dump

core dump가 활성화되어 있다면 프로그램이 충돌한 순간의 상태를 파일로 저장하고, 프로그램이 종료된 뒤에도 디버거로 조사할 수 있습니다.

셸에서 core dump 크기 제한을 해제하는 일반적인 예는 다음과 같습니다.

```sh
ulimit -c unlimited
./program
```

생성된 core 파일을 GDB로 열 수 있습니다.

```sh
gdb ./program core
```

LLDB에서는 다음과 같이 열 수 있습니다.

```sh
lldb -c core ./program
```

core dump에서는 프로그램을 다시 실행하는 것이 아니라 **충돌 당시 저장된 상태를 조사**합니다. 따라서 다음과 같은 정보가 특히 유용합니다.

- 충돌한 스레드
- 호출 스택
- 함수 인자
- 당시의 지역 변수
- 레지스터
- 접근하려던 메모리 주소

core 파일의 생성 여부, 저장 위치, 파일 이름은 운영체제와 배포 환경 설정에 따라 다릅니다. `ulimit -c unlimited`만으로 항상 현재 디렉터리에 `core`라는 파일이 생성된다고 가정해서는 안 됩니다.

## 디버거와 sanitizer 함께 사용하기

Sanitizer는 잘못된 접근을 탐지하는 데 강하고, 디버거는 그 접근이 생기기 전의 상태를 자세히 추적하는 데 유용합니다. 두 도구를 함께 사용하면 조사 범위를 빠르게 줄일 수 있습니다.

기본 흐름은 다음과 같습니다.

```text
1. sanitizer가 활성화된 빌드로 실패를 재현한다.
2. sanitizer가 처음 보고한 잘못된 접근의 파일과 줄 번호를 확인한다.
3. 그 위치보다 앞에서 관련 값이 만들어지거나 변경되는 지점에 중단점을 둔다.
4. 포인터, 길이, 인덱스, 객체 수명과 소유자를 확인한다.
5. 필요하면 watchpoint나 호출 스택을 사용해 잘못된 값의 최초 발생 지점을 찾는다.
6. 수정한 뒤 같은 입력으로 다시 실행한다.
7. 전체 테스트와 실제 사용할 최적화 설정에서도 다시 검사한다.
```

중요한 점은 sanitizer가 표시한 **마지막 증상 위치가 항상 최초 원인은 아니라는 것**입니다.

예를 들어 이미 해제된 메모리를 나중에 읽어서 오류가 보고되었다면, 읽은 줄뿐 아니라 그 객체가 어디에서 너무 일찍 `free()`되었는지도 조사해야 합니다.

## 조사 기록

디버깅은 같은 조건을 다시 재현할 수 있어야 결과를 비교하기 쉽습니다. 문제를 해결할 때 다음 정보를 기록합니다.

```text
실행 명령
프로그램 인자
입력
환경 변수
컴파일 옵션
재현되는 오류 메시지
중단점 위치
잘못된 값이 처음 관찰된 frame
그 값을 만든 것으로 확인한 코드
수정 내용
수정 후 실행한 테스트
```

예를 들어 "포인터 오류 수정"처럼 결과만 적는 것보다 다음처럼 원인과 검증 조건을 함께 기록하는 편이 유용합니다.

```text
입력: tests/case17.bin
증상: parser.c:125에서 범위를 벗어난 읽기
원인: parse_length()가 종료 바이트까지 길이에 포함함
최초 잘못된 값: parse_record()의 length
수정: 종료 바이트를 길이에서 제외
검증: case17.bin 재실행 + 전체 테스트 + sanitizer 재실행
```

이 기록은 같은 오류가 다시 나타났을 때 이전 조사와 비교하는 기준이 됩니다.

## 권장 조사 순서

재현 가능한 오류라면 다음 순서로 접근할 수 있습니다.

```text
1. 같은 입력과 실행 조건으로 오류가 반복되는지 확인한다.
2. 경고와 디버그 정보를 포함해 빌드한다.
3. 충돌 위치와 호출 스택을 확인한다.
4. 잘못된 값이 무엇인지 구체적으로 정한다.
5. 그 값이 만들어지기 직전 위치에 중단점을 둔다.
6. next를 중심으로 실행하면서 값의 변화를 확인한다.
7. 필요한 함수에만 step으로 들어간다.
8. 값의 변경 위치가 불분명하면 watchpoint를 사용한다.
9. 포인터 문제라면 주소, 길이, 객체 수명과 소유권을 함께 확인한다.
10. 원인을 수정한 뒤 같은 입력과 전체 테스트로 검증한다.
```

이 순서의 핵심은 **증상에서 원인 방향으로 거슬러 올라가는 것**입니다.

## 사용 기준

디버거는 다음과 같은 구체적인 질문에 답하기 위해 사용합니다.

- 값이 언제 처음 잘못되었습니까?
- 이 포인터는 어느 객체를 가리킵니까?
- 그 객체는 아직 유효합니까?
- 어떤 호출자가 잘못된 인자를 전달했습니까?
- 배열 인덱스와 길이는 어느 시점부터 불일치했습니까?
- 어느 코드가 이 값을 변경했습니까?
- 어느 스레드가 어떤 mutex를 기다립니까?
- 자식 프로세스는 어떤 FD와 프로그램 인자를 받았습니까?

단순히 "어느 줄에서 충돌했는가?"를 찾는 데서 끝내지 않습니다.

충돌한 줄은 **오류가 관찰된 위치**일 뿐, **오류가 만들어진 위치**와 같다는 보장은 없습니다. 디버거의 핵심 목적은 잘못된 상태가 처음 생성된 시점을 찾아 그 원인을 확인하는 것입니다.
