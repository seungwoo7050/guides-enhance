# Unix 텍스트 출력 검사

작은 CLI 프로그램을 테스트할 때는 프로그램 내부 구현보다 **외부에서 관찰할 수 있는 계약**을 검사하는 것이 중요합니다. 텍스트를 출력하는 CLI라면 대표적인 관찰 대상은 다음 세 가지입니다.

```text
stdout   정상 결과를 출력하는 표준 출력
stderr   오류·진단 정보를 출력하는 표준 오류
status   프로세스의 종료 상태
```

프로그램에 따라 파일 생성이나 다른 프로세스 실행 같은 부수 효과도 계약에 포함될 수 있지만, 이 문서는 stdout, stderr와 종료 상태를 정확하게 검사하는 방법에 집중합니다.

셸 도구를 사용하면 이 세 결과를 서로 분리해 저장하고, 공백·줄바꿈·보이지 않는 문자·바이트 단위 차이까지 확인할 수 있습니다.

## stdout, stderr와 종료 상태 저장하기

stdout과 stderr는 서로 다른 파일로 리다이렉션합니다.

```sh
./program arg1 arg2 >"$tmp/out" 2>"$tmp/err"
status=$?
```

여기서:

```text
>"$tmp/out"   stdout을 파일에 저장
2>"$tmp/err"  stderr를 파일에 저장
$?            바로 직전에 실행한 명령의 종료 상태
```

`$?`는 **다음 명령을 실행하기 전에 즉시 저장해야 합니다.**

다음 코드는 잘못된 예입니다.

```sh
./program >"$tmp/out" 2>"$tmp/err"
printf '실행 완료\n'
status=$?
```

이 경우 `status`에는 `./program`이 아니라 `printf`의 종료 상태가 들어갑니다.

### `set -e`를 사용하는 스크립트

`set -e`가 활성화되어 있으면 테스트 대상 프로그램이 의도적으로 0이 아닌 상태를 반환하는 경우에도 셸이 먼저 종료할 수 있습니다.

다음처럼 잠시 `set +e`로 해제할 수도 있습니다.

```sh
set +e
./program arg1 arg2 >"$tmp/out" 2>"$tmp/err"
status=$?
set -e
```

하지만 이 방식은 함수나 공용 테스트 코드에서 사용하면 **호출자가 원래 `set -e`를 사용하고 있었는지와 관계없이 마지막에 강제로 활성화한다는 문제**가 있습니다.

종료 상태를 직접 검사하려는 명령은 `if`의 조건으로 실행하는 방법이 더 명확합니다.

```sh
if ./program arg1 arg2 >"$tmp/out" 2>"$tmp/err"; then
    status=0
else
    status=$?
fi
```

`if`의 조건으로 사용한 명령은 실패 여부를 직접 분기에서 처리하므로 `set -e`와 함께 사용하는 테스트 코드에서도 의도를 표현하기 쉽습니다.

기대한 종료 상태가 2라면 다음처럼 검사할 수 있습니다.

```sh
[ "$status" -eq 2 ] ||
    fail "종료 상태: 기대=2 실제=$status"
```

종료 상태 `0`은 일반적으로 성공을 뜻하고, 0이 아닌 값은 실패나 별도 결과를 나타냅니다. 각 숫자의 구체적인 의미는 프로그램의 인터페이스 계약에서 정해야 합니다.

## 예상 출력 만들기

정확한 출력을 만들 때는 `echo`보다 `printf`를 사용하는 편이 안전합니다.

`echo`는 셸과 구현에 따라 다음 요소의 해석이 달라질 수 있습니다.

- `-n`
- backslash escape
- `\c` 같은 특수 문자열

예상 출력이 다음과 같다면:

```text
count=2
sum=7
```

`printf`로 정확히 만들 수 있습니다.

```sh
printf 'count=2\nsum=7\n' >"$tmp/expected"
```

실제 출력과 비교합니다.

```sh
diff -u "$tmp/expected" "$tmp/out"
```

`diff -u`는 줄 단위 차이를 사람이 읽기 좋은 unified diff 형식으로 보여 줍니다.

예상 파일과 실제 파일이 다르면 `diff`의 종료 상태는 일반적으로 1입니다. 파일을 읽을 수 없는 등의 오류에서는 다른 비정상 상태가 나올 수 있으므로, 테스트에서는 단순히 화면 출력만 보는 것이 아니라 비교 명령의 성공 여부도 사용합니다.

예:

```sh
diff -u "$tmp/expected" "$tmp/out" ||
    fail 'stdout이 예상 출력과 다릅니다.'
```

### 여러 줄은 here-document 사용하기

긴 예상 출력은 here-document가 읽기 쉽습니다.

```sh
cat >"$tmp/expected" <<'EXPECTED'
count=2
sum=7
EXPECTED
```

delimiter인 `EXPECTED`를 작은따옴표로 감싸면 본문에 있는 다음 표현을 셸이 확장하지 않습니다.

```text
$variable
$(command)
`command`
backslash를 이용한 일부 셸 처리
```

따라서 예상 문자열을 코드에 적힌 그대로 파일에 넣을 수 있습니다.

### here-document의 마지막 줄바꿈

일반적인 here-document 본문은 줄 단위로 작성되므로 위 예제의 예상 파일은 마지막 `sum=7` 뒤에도 줄바꿈을 포함합니다.

**마지막 줄바꿈이 없어야 하는 출력**을 검사하려면 `printf`처럼 바이트를 직접 지정할 수 있는 방법을 사용합니다.

```sh
printf 'sum=7' >"$tmp/expected"
```

이 차이는 다음 두 출력을 구분할 때 중요합니다.

```text
"sum=7\n"
"sum=7"
```

## 빈 출력 확인

파일 크기가 0인지 확인할 때 흔히 다음 검사를 사용합니다.

```sh
[ ! -s "$tmp/err" ] ||
    fail '정상 입력이 stderr를 출력했습니다.'
```

`-s file`은 **파일이 존재하고 크기가 0보다 클 때 참**입니다.

따라서 `! -s file`은 다음 두 경우 모두 참이 됩니다.

```text
파일이 존재하며 크기가 0
파일이 존재하지 않음
```

즉 `! -s`만으로는 "파일이 존재하면서 비어 있다"까지 보장하지 않습니다.

다만 다음처럼 명령 실행 전에 리다이렉션으로 파일을 만들었다면:

```sh
./program >"$tmp/out" 2>"$tmp/err"
```

셸이 `out`과 `err` 파일을 생성하므로 이후의 `! -s` 검사는 실용적으로 빈 출력 검사에 사용할 수 있습니다.

파일 존재 자체도 계약이라면 두 조건을 명시적으로 검사합니다.

```sh
[ -e "$tmp/err" ] ||
    fail 'stderr 캡처 파일이 생성되지 않았습니다.'

[ ! -s "$tmp/err" ] ||
    fail '정상 입력이 stderr를 출력했습니다.'
```

오류 발생 시 stdout이 반드시 비어 있어야 한다는 규칙도 같은 방식으로 검사할 수 있습니다.

## 부분 문자열과 정확한 줄

오류 메시지 전체가 아니라 안정적인 접두어만 검사하려면 고정 문자열 검색을 사용할 수 있습니다.

```sh
grep -F '오류:' "$tmp/err" >/dev/null
```

`-F`는 검색 패턴을 정규식이 아니라 **그대로의 문자열**로 취급합니다.

정확히 `sum=7`인 줄이 하나 이상 존재하는지 확인하려면:

```sh
grep -Fx 'sum=7' "$tmp/out" >/dev/null
```

`-x`는 문자열 일부가 아니라 **줄 전체가 패턴과 일치해야 한다**는 뜻입니다.

따라서 다음 출력은 일치합니다.

```text
sum=7
```

하지만 다음 출력은 일치하지 않습니다.

```text
result: sum=7
sum=7 extra
```

### `grep -Fx`가 보장하지 않는 것

다음 명령:

```sh
grep -Fx 'sum=7' "$tmp/out" >/dev/null
```

은 "`sum=7`과 정확히 같은 줄이 적어도 하나 있다"는 사실만 검사합니다.

다음까지 보장하지는 않습니다.

```text
그 줄이 정확히 한 번만 존재함
파일에 다른 줄이 없음
파일 전체가 오직 "sum=7\n"임
```

파일 전체가 정확히 한 줄이어야 한다면 예상 파일과 전체 비교하는 편이 분명합니다.

```sh
printf 'sum=7\n' >"$tmp/expected"

cmp -s "$tmp/expected" "$tmp/out" ||
    fail 'stdout 전체가 기대한 한 줄과 다릅니다.'
```

### 얼마나 엄격하게 검사할지 정하기

출력 테스트는 프로그램이 실제로 보장하는 계약만 고정해야 합니다.

예를 들어 오류 설명 문구를 자주 개선할 수 있다면:

```text
오류: 파일을 열 수 없습니다: data.txt
```

전체 문장 대신 안정적인 요소만 검사할 수 있습니다.

```sh
grep -F '오류:' "$tmp/err" >/dev/null
```

반대로 CLI의 출력 형식 자체가 외부 프로그램이 의존하는 API라면 전체 바이트를 정확히 비교하는 것이 적절합니다.

## 공백과 보이지 않는 문자 확인

화면에서 비슷하게 보이는 출력도 실제 바이트는 다를 수 있습니다.

다음 명령은 이런 차이를 조사할 때 유용합니다.

```sh
sed -n 'l' "$tmp/out"
od -An -tx1 -c "$tmp/out"
```

확인할 수 있는 대표적인 문제는 다음과 같습니다.

- 마지막 줄바꿈 문자 누락
- 예상하지 않은 carriage return(`\r`)
- 탭(`\t`)과 공백의 차이
- NUL 바이트(`\0`)
- UTF-8 인코딩 바이트 차이
- 줄 끝의 불필요한 공백

예를 들어 다음 두 문자열은 화면에서 비슷하게 보일 수 있습니다.

```text
"sum=7\n"
"sum=7\r\n"
```

하지만 바이트로 보면 다릅니다.

```text
0a        LF
0d 0a     CR LF
```

`od`를 사용하면 이런 차이를 직접 확인할 수 있습니다.

## 텍스트와 임의 바이트 데이터 구분하기

`grep`, 셸 변수, `%s` 같은 텍스트 중심 도구는 NUL 바이트를 포함한 임의 데이터 검사에 적합하지 않을 수 있습니다.

바이너리 출력은 파일로 저장한 뒤 `cmp`로 비교하는 것이 단순합니다.

```sh
cmp -s "$tmp/expected.bin" "$tmp/out.bin" ||
    fail '바이너리 출력이 예상과 다릅니다.'
```

`cmp`는 두 파일의 내용뿐 아니라 길이가 다른 경우도 차이로 판단합니다. 따라서 정확한 동일성 검사에는 별도의 길이 검사가 반드시 필요한 것은 아닙니다.

다만 실패 원인을 더 자세히 표시하고 싶다면 길이를 따로 구할 수 있습니다.

```sh
expected_size=$(wc -c <"$tmp/expected.bin")
actual_size=$(wc -c <"$tmp/out.bin")

[ "$actual_size" -eq "$expected_size" ] ||
    fail "출력 크기: 기대=$expected_size 실제=$actual_size"
```

그 뒤 `cmp`를 사용하면 "길이가 다른가"와 "길이는 같지만 내용이 다른가"를 구분하기 쉽습니다.

### 셸 변수에 바이너리 데이터를 넣지 않기

다음 형태는 텍스트에는 편리하지만 임의 바이트 데이터를 보존하는 용도로는 적합하지 않습니다.

```sh
output=$(./program)
```

명령 치환은 마지막 줄바꿈을 제거하며, 셸 변수는 일반적으로 NUL 바이트를 안전하게 표현하는 데이터 구조가 아닙니다.

정확한 바이트 검사가 필요하면 처음부터 파일로 리다이렉션합니다.

```sh
./program >"$tmp/out.bin"
```

## 임시 디렉터리 정리

테스트가 고정된 파일 이름을 현재 디렉터리에 만들면 여러 테스트를 동시에 실행할 때 서로 덮어쓸 수 있습니다.

예:

```text
test A → ./out
test B → ./out
```

대신 테스트 실행마다 별도 임시 디렉터리를 만듭니다.

```sh
tmp=$(mktemp -d) ||
    exit 1
```

종료할 때 정리합니다.

Bash와 여러 일반적인 셸에서는 다음처럼 사용할 수 있습니다.

```sh
cleanup() {
    rm -rf "$tmp"
}

trap cleanup EXIT
```

시그널로 종료할 때도 정리가 필요하다면 해당 시그널 처리 정책을 함께 정합니다.

```sh
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
```

`exit`가 실행되면 `EXIT` trap이 동작해 `cleanup`이 호출됩니다.

### 이식성을 고려한 trap

`EXIT`라는 이름 대신 POSIX 계열 셸에서 종료를 의미하는 `0`을 사용할 수 있습니다.

```sh
trap cleanup 0
```

시그널 번호에 128을 더한 종료 상태는 Unix 셸에서 널리 사용하는 관례이지만 모든 환경의 독립적인 표준 인터페이스로 가정해서는 안 됩니다.

또한 `mktemp` 자체는 모든 POSIX 환경에 반드시 존재하는 명령이 아니므로, 테스트가 요구하는 도구 집합을 문서에 명시해야 합니다.

## 실패 함수

테스트 실패를 한 형식으로 보고하려면 함수를 만들 수 있습니다.

```sh
fail() {
    printf '검사 실패: %s\n' "$1" >&2
    exit 1
}
```

실패 메시지는 단순히 "실패"라고 쓰기보다 다음 정보를 가능한 범위에서 알려주는 것이 좋습니다.

```text
어떤 입력을 사용했는가
무엇을 검사했는가
기대한 값은 무엇인가
실제 값은 무엇인가
차이를 확인할 파일은 어디에 있는가
```

예:

```text
검사 실패: 종료 상태: 기대=2 실제=0
```

또는:

```text
검사 실패: 빈 입력에서 stderr가 비어 있어야 합니다.
```

정확한 텍스트 차이는 메시지에 모두 넣기보다 `diff -u` 결과를 함께 보여 주는 편이 읽기 쉽습니다.

## 종료 상태 실행 함수

같은 검사를 반복한다면 함수로 묶을 수 있습니다.

```sh
run_status() {
    expected=$1
    shift

    if "$program" "$@" >"$tmp/out" 2>"$tmp/err"; then
        actual=0
    else
        actual=$?
    fi

    [ "$actual" -eq "$expected" ] ||
        fail "종료 상태: 기대=$expected 실제=$actual 인자=$*"
}
```

`"$@"`가 중요합니다.

예를 들어 호출이 다음과 같다면:

```sh
run_status 0 "hello world" "a*b"
```

`"$@"`는 두 인자를 원래 경계 그대로 전달합니다.

```text
argv[1] = "hello world"
argv[2] = "a*b"
```

반면 따옴표 없는 `$@`나 `$*`를 실행 인자 전달에 사용하면 공백 분리와 pathname expansion 때문에 인자 경계가 깨질 수 있습니다.

위 예제의 오류 메시지에서 `$*`는 **사람이 읽는 간단한 진단용 문자열**일 뿐 원래 인자 경계를 정확하게 재현하지는 않습니다. 인자 구분 자체가 중요하다면 각 인자를 별도로 출력하는 진단 함수를 사용합니다.

## Timeout

프로세스, pipe, 시그널, 동시성 테스트는 버그가 있을 때 프로그램이 종료되지 않을 수 있습니다.

따라서 테스트에는 최대 실행 시간을 정해 두는 것이 좋습니다.

일부 시스템에는 다음과 같은 `timeout` 명령이 있습니다.

```sh
timeout 5 ./program
```

하지만 `timeout`의 존재 여부와 옵션은 환경에 따라 다를 수 있습니다.

Python을 테스트 의존성으로 허용한다면 `subprocess`를 사용할 수 있습니다.

정확한 stdout/stderr 바이트도 검사하려면 `text=True`를 사용하지 않고 bytes로 받는 편이 안전합니다.

```python
import subprocess

result = subprocess.run(
    [program, *args],
    capture_output=True,
    timeout=5.0,
    check=False,
)

stdout = result.stdout   # bytes
stderr = result.stderr   # bytes
status = result.returncode
```

`text=True`를 사용하면 bytes가 문자열로 디코딩되고 텍스트 줄바꿈 처리가 적용됩니다. 따라서 `\r\n`과 `\n` 같은 바이트 차이까지 검사해야 하는 테스트에서는 원시 bytes를 유지하는 편이 적절합니다.

### timeout은 실패 경로다

제한 시간이 지나면 `subprocess.run()`은 정상적인 `CompletedProcess`를 반환하는 대신 `subprocess.TimeoutExpired` 예외를 발생시킵니다.

```python
try:
    result = subprocess.run(
        [program, *args],
        capture_output=True,
        timeout=5.0,
        check=False,
    )
except subprocess.TimeoutExpired:
    raise AssertionError("프로그램이 제한 시간 안에 종료되지 않았습니다.")
```

### 자식 프로세스까지 남는 경우

테스트 대상이 다시 자식이나 손자 프로세스를 만든다면 최상위 프로세스 하나만 종료해도 다른 프로세스가 남을 수 있습니다.

이 경우에는 다음 문제를 일으킬 수 있습니다.

- 테스트가 끝난 뒤에도 프로세스가 실행됨
- pipe의 쓰기 끝이 열린 채 남아 EOF가 오지 않음
- 다음 테스트가 같은 포트나 파일을 사용할 수 없음

POSIX 환경에서는 테스트 대상을 새 session 또는 process group으로 시작한 뒤 timeout 시 **그 그룹 전체를 종료하는 방식**을 고려할 수 있습니다.

이 동작은 운영체제별 차이가 크므로 단순한 `subprocess.run(timeout=...)`과 "프로세스 트리 전체 정리"를 같은 기능으로 가정하지 않습니다.

## 순서에 의존하지 않는 검사

동시성이나 시그널 테스트에서는 **운영체제나 프로그램 계약이 보장하지 않는 순서**를 테스트가 임의로 요구하면 안 됩니다.

예를 들어 두 작업이 병렬로 다음 줄을 출력한다고 가정합니다.

```text
worker-a done
worker-b done
```

프로그램 요구 사항이 "두 작업 모두 완료 메시지를 남긴다"일 뿐이라면:

```text
worker-a done
worker-b done
```

만 정답으로 고정하고 반대 순서를 실패시키면 테스트가 실제 계약보다 강해집니다.

반대로 프로그램 자체가 순서를 보장해야 한다면 정렬해서 비교하면 안 됩니다. 정렬은 실제 순서 오류를 숨기기 때문입니다.

### 검사하려는 성질을 먼저 정의하기

동시성 결과를 검사할 때는 다음 중 무엇을 요구하는지 구분합니다.

```text
존재:
    특정 결과가 최소 한 번 나타나면 됨

횟수:
    정확히 N번 나타나야 함

집합:
    여러 결과가 모두 나타나면 되며 순서는 무관함

순서:
    결과가 지정된 순서로 나타나야 함

전체 바이트:
    출력 전체가 정확히 동일해야 함
```

이 정의에 따라 `grep`, 개수 세기, 정렬 후 비교, `diff`, `cmp` 중 적절한 방법을 선택합니다.

### 정렬할 때 locale 주의

문자열 정렬 순서는 locale의 영향을 받을 수 있습니다.

테스트가 바이트 기반의 안정적인 정렬 순서를 원한다면 필요에 따라 locale을 고정합니다.

```sh
LC_ALL=C sort "$tmp/out" >"$tmp/sorted"
```

프로그램 자체가 locale에 따라 다른 출력을 내는 것이 요구 사항이라면 오히려 locale을 테스트 입력의 일부로 명시해야 합니다.

## 시그널 테스트에서 주의할 점

서로 다른 시그널이나 여러 동시 이벤트가 발생할 때, 운영체제가 항상 테스트 코드가 보낸 순서 그대로 애플리케이션 수준에서 관찰되리라고 가정하면 안 됩니다.

특히 표준 시그널은 동일 종류의 시그널이 여러 번 발생해도 모든 발생 횟수가 개별적으로 큐에 보존된다고 일반화할 수 없습니다.

따라서 다음과 같은 요구 사항은 구분해야 합니다.

```text
SIGUSR1을 최소 한 번 처리했는가
SIGUSR1을 정확히 N번 처리했는가
SIGUSR1 뒤 SIGUSR2를 반드시 처리했는가
```

프로그램과 운영체제가 보장하지 않는 횟수나 순서를 테스트에 넣으면 간헐적으로 실패하는 테스트가 될 수 있습니다.

## 파일 디스크립터 누수 검사

FD(file descriptor)는 열린 파일, pipe, socket 등을 프로세스가 참조하는 정수 식별자입니다.

한 번 실행했을 때 FD 하나를 닫지 않는 버그는 즉시 보이지 않을 수 있습니다. 따라서 단순히 프로그램을 한 번 실행하는 테스트만으로는 FD 누수를 검출할 수 있다고 가정하면 안 됩니다.

FD 누수를 검사하려면 버그의 결과가 관찰되도록 테스트를 설계해야 합니다.

예를 들면:

```text
같은 작업을 충분히 반복해 열린 FD 수가 계속 증가하는지 확인
pipe의 불필요한 쓰기 끝이 남아 reader가 EOF를 받지 못하는지 확인
낮은 FD 제한에서 반복 실행해 자원 고갈이 발생하는지 확인
```

`/proc`를 사용해 열린 FD 수를 검사하는 방법은 Linux에 의존합니다. 다른 운영체제에서는 별도 방법이 필요합니다.

## 알려진 잘못된 구현 검출하기

좋은 테스트는 올바른 구현에서 성공하는 것뿐 아니라 **의도적으로 잘못된 구현에서 실제로 실패해야 합니다.**

테스트를 작성한 뒤 다음과 같은 변형을 생각해 봅니다.

- 마지막 줄바꿈 문자를 빼면 테스트가 실패합니까?
- stdout과 stderr를 서로 바꾸면 실패합니까?
- 종료 상태를 항상 0으로 반환하면 실패합니까?
- 입력 하나를 무시하면 실패합니까?
- 출력에 공백 하나를 추가하면 필요한 테스트가 실패합니까?
- 결과 순서를 뒤집으면, 순서를 보장해야 하는 테스트에서 실패합니까?
- FD를 닫지 않으면 그 누수의 결과를 관찰하도록 만든 테스트가 실패합니까?
- 프로그램이 멈추면 timeout 테스트가 실패합니까?

이 방식은 테스트가 실제 요구 사항을 검증하는지 확인하는 간단한 **mutation 관점의 점검**입니다.

예를 들어 다음 테스트가 있다고 가정합니다.

```sh
grep -F 'sum=7' "$tmp/out" >/dev/null
```

잘못된 구현이 다음을 출력해도 테스트는 성공합니다.

```text
garbage
sum=7
unexpected
```

프로그램의 계약이 정확히 `sum=7\n` 하나만 출력하는 것이라면 이 테스트는 충분하지 않습니다. 전체 파일 비교로 강화해야 합니다.

테스트 주석도 다음처럼 목적을 설명하는 편이 좋습니다.

좋지 않은 예:

```text
program을 실행한다.
```

더 유용한 예:

```text
오류 입력에서 stdout에 부분 결과를 남기는 구현을 검출한다.
```

## 이식성

Unix 계열 환경이라고 해도 모든 명령과 옵션이 동일하지는 않습니다.

다음 항목은 플랫폼 또는 도구 구현에 따라 차이가 있을 수 있습니다.

- `mktemp`
- `timeout`
- `sed -n 'l'`의 출력 형식
- `stat` 옵션
- `/proc` 파일 시스템
- `grep`의 비표준 확장 옵션
- `diff`와 `sort`의 세부 출력
- locale에 따른 문자 분류와 정렬
- 시그널과 process group 처리

따라서 프로젝트 문서에는 테스트 환경의 최소 요구 사항을 적습니다.

예:

```text
POSIX shell만 요구
```

또는:

```text
Bash + GNU coreutils 요구
```

또는:

```text
POSIX 계열 환경 + Python 3 요구
```

이 요구 사항이 분명해야 "프로그램이 실패한 것인지 테스트 도구가 없는 것인지"를 구분할 수 있습니다.

## 권장 기본 구조

작은 CLI 테스트 스크립트는 다음과 같이 구성할 수 있습니다.

```sh
#!/bin/sh

fail() {
    printf '검사 실패: %s\n' "$1" >&2
    exit 1
}

tmp=$(mktemp -d) ||
    fail '임시 디렉터리를 만들 수 없습니다.'

cleanup() {
    rm -rf "$tmp"
}

trap cleanup 0

program=./program

if "$program" arg1 arg2 >"$tmp/out" 2>"$tmp/err"; then
    status=0
else
    status=$?
fi

[ "$status" -eq 0 ] ||
    fail "종료 상태: 기대=0 실제=$status"

[ ! -s "$tmp/err" ] ||
    fail '정상 입력이 stderr를 출력했습니다.'

printf 'count=2\nsum=7\n' >"$tmp/expected"

diff -u "$tmp/expected" "$tmp/out" ||
    fail 'stdout이 예상 출력과 다릅니다.'
```

이 구조에서는 다음 세 계약을 서로 독립적으로 확인합니다.

```text
종료 상태
stderr가 비어 있는지
stdout 전체 내용
```

하나의 검사만 통과한다고 다른 계약도 올바르다고 가정하지 않습니다.

## 완료 기준

1. stdout, stderr와 종료 상태를 서로 분리해 저장합니다.
2. 종료 상태는 대상 명령 직후 저장하며 `set -e`와의 상호작용을 고려합니다.
3. `printf`, here-document와 `diff -u`를 용도에 맞게 사용해 예상 텍스트를 비교합니다.
4. 마지막 줄바꿈 유무까지 계약에 포함되는 경우 정확히 검사합니다.
5. `grep -Fx`가 "정확히 같은 줄의 존재"를 검사할 뿐 파일 전체나 정확한 횟수를 보장하지 않는다는 점을 구분합니다.
6. `! -s`가 존재하지 않는 파일에도 참이 될 수 있음을 이해하고 필요한 경우 존재 여부를 별도로 검사합니다.
7. 공백, CR, LF, 탭, NUL과 인코딩 차이는 `sed`, `od` 또는 바이트 비교로 확인합니다.
8. 임의 바이트 데이터는 셸 변수나 텍스트 변환을 거치지 않고 파일과 `cmp`로 검사합니다.
9. 임시 파일은 실행별 디렉터리에 만들고 종료 시 `trap`으로 정리합니다.
10. 테스트 대상 인자는 `"$@"`로 전달해 원래 인자 경계를 보존합니다.
11. timeout을 두고, 프로세스 트리를 만드는 프로그램이라면 남은 자식 프로세스 처리까지 고려합니다.
12. 운영체제가 보장하지 않는 이벤트 순서나 시그널 횟수를 테스트가 임의로 요구하지 않습니다.
13. 순서가 의미 없는 결과를 정렬할 때는 locale의 영향을 고려합니다.
14. FD 누수처럼 한 번의 실행으로 드러나지 않는 오류는 결과가 관찰되도록 반복 또는 자원 제한 테스트를 설계합니다.
15. 테스트가 의도적으로 잘못된 구현을 실제로 검출하는지 확인합니다.
16. 필요한 셸, Unix 도구, GNU 확장, Python 등의 환경 요구 사항을 문서화합니다.

핵심은 **테스트가 프로그램의 실제 외부 계약과 정확히 같은 강도로 검사하도록 만드는 것**입니다. 너무 약한 검사는 잘못된 구현을 통과시키고, 너무 강한 검사는 프로그램이 보장하지 않는 공백·문구·순서까지 고정해 불필요하게 깨지기 쉬운 테스트를 만듭니다.
