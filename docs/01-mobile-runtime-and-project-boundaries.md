# 모바일 런타임과 프로젝트 구성

모바일 앱은 하나의 JavaScript 프로세스가 계속 실행되는 프로그램이 아닙니다. 화면이 보이는 동안에도 네이티브 UI, 운영체제, 시스템 선택기, 저장소와 네트워크 작업은 서로 다른 수명으로 움직입니다.

운영체제는 프로세스 생성과 종료, 권한, 시스템 UI, 백그라운드 실행 기회를 결정합니다. 앱은 이 사건을 막을 수 없습니다. 대신 사용자가 확정한 변경을 언제 저장할지, 프로세스가 다시 시작될 때 무엇을 복원할지 결정해야 합니다.

## 이 문서에서 확인할 내용

- JavaScript 번들, 설치된 네이티브 바이너리, 운영체제 상태를 구분합니다.
- 포그라운드, 백그라운드와 프로세스 종료 상태를 업무 상태와 혼동하지 않습니다.
- 프로세스 종료 뒤에도 남아야 하는 값을 저장소로 옮깁니다.
- Expo 설정, 생성된 네이티브 프로젝트, 직접 작성한 네이티브 코드의 역할을 구분합니다.
- Expo Go와 개발용 빌드가 확인할 수 있는 범위를 설명합니다.
- 경로, 애플리케이션 코드, 상태 형식, SQLite와 기기 API 호출 위치를 나눕니다.

## 먼저 소유자를 정합니다

Field Notes에서 자주 다루는 상태를 기준으로 보면 다음과 같습니다.

| 상태 또는 자원 | 실제 소유자 | 바뀌는 사건 | 반드시 지켜야 할 조건 |
|---|---|---|---|
| 프로세스와 포그라운드 실행 기회 | 운영체제 | 실행, 백그라운드, 메모리 부족, 사용자 종료 | 콜백 없이 종료돼도 이미 커밋한 데이터를 잃지 않습니다. |
| 네이티브 모듈과 운영체제 기능 | 설치된 바이너리와 운영체제 | 빌드와 설치, OS 업데이트, 권한이나 설정 변경 | JavaScript가 바이너리에 없는 메서드를 호출하지 않습니다. |
| 화면 이동 요청 | 시작 절차와 화면 이동 처리 코드 | 실행 아이콘, 링크, 알림, 복원 | 데이터베이스와 세션이 준비되기 전에 보호된 경로를 확정하지 않습니다. |
| `Record`, outbox, 첨부 파일 메타데이터 | 로컬 저장소 | 저장, 동기화 결과, 마이그레이션 | 기록 변경과 재시도 근거를 함께 복원합니다. |
| 화면의 로딩, 모달, 누름 상태 | 컴포넌트 | 포커스, 누름, 렌더링, 마운트 해제 | 프로세스 종료 뒤 버려도 저장된 업무 상태는 달라지지 않습니다. |

이 표에서 중요한 것은 이름이 아니라 질문입니다.

```text
이 값은 누가 보관합니까?
어떤 사건이 값을 바꿉니까?
지금 프로세스가 종료되면 잃어도 됩니까?
다음 시작에서 어디서 다시 읽습니까?
```

## 세 실행 영역을 구분합니다

```text
JavaScript와 React
- 경로와 컴포넌트
- 화면에서 호출하는 애플리케이션 작업
- 기록과 동기화 상태 계산
- 네이티브 모듈 호출

네이티브 애플리케이션
- Android `Application`과 `Activity`
- iOS 애플리케이션과 `scene`
- 네이티브 모듈과 화면
- 매니페스트, plist, 권한 설정, 서명

운영체제
- 프로세스 생성과 종료
- 권한 대화 상자와 시스템 선택기
- 백그라운드 스케줄러
- 알림 전달
- 저장소, 네트워크, 메모리 부족
```

React 컴포넌트가 마운트 해제되는 것과 프로세스가 종료되는 것은 다릅니다. 앱이 백그라운드로 갔다고 반드시 프로세스가 사라지는 것도 아니며, 화면이 다시 보인다고 JavaScript 메모리가 남아 있다는 보장도 없습니다.

## 화면 상태와 저장할 상태를 나눕니다

Field Notes의 상태를 다음처럼 분류할 수 있습니다.

| 상태 | 예 | 권장 저장 위치 |
|---|---|---|
| 일시적인 화면 상태 | 열린 메뉴, 눌림 표시, 현재 로딩 | 컴포넌트 메모리 |
| 현재 화면 위치 | 기록 ID, 편집 또는 상세 경로 | 라우터 |
| 저장하지 않은 초안 | 제목, 메모 입력값 | 화면 또는 별도 초안 저장소 |
| 저장한 업무 상태 | `Record`, outbox, 충돌 | SQLite |
| 사진 원본 | 앱이 복사해 소유하는 파일 | 앱이 소유한 디렉터리 |
| 인증 정보 | 갱신 토큰, 작은 기기 비밀값 | 플랫폼 보안 저장소 |
| 서버가 정하는 값 | 원격 버전, 인가 | 서버 |
| 진단 정보 | 앱, 빌드와 런타임, 동기화 시도 | 제한된 로그와 관찰 정보 |

`useState`에 값이 있다는 사실은 프로세스 재시작 뒤 복원된다는 뜻이 아닙니다. 반대로 모든 화면 상태를 SQLite에 넣으면 오래된 모달과 로딩 상태까지 마이그레이션 대상이 됩니다.

저장 위치는 값의 크기와 수명에 맞춰 정합니다.

- 기록, outbox처럼 함께 갱신해야 하는 값은 SQLite에 둡니다.
- 큰 사진은 파일로 저장하고 SQLite에는 URI, 체크섬, 크기와 상태만 둡니다.
- 작은 인증 정보는 일반 DB와 분리된 보안 저장소에 둡니다.
- 삭제돼도 다시 만들 수 있는 썸네일은 캐시에 둘 수 있습니다.

## AppState는 저장 완료 신호가 아닙니다

`AppState`는 앱이 활성화인지 백그라운드인지 알려 주는 입력입니다. 포그라운드 복귀 시 다음 작업을 요청하는 데 사용할 수 있습니다.

- 세션과 원격 데이터 다시 확인
- 권한과 로케일 다시 읽기
- 대기 중인 outbox 처리 요청
- 민감 화면 다시 잠그기

하지만 백그라운드 콜백에서 모든 상태를 마지막으로 저장하는 설계는 안전하지 않습니다.

- 운영체제가 콜백을 끝까지 실행할 시간을 주지 않을 수 있습니다.
- 비정상 종료와 강제 종료에는 콜백이 없습니다.
- Android와 iOS가 같은 순서로 상태를 전달하지 않을 수 있습니다.

사용자가 저장을 확정한 시점에 `Record`와 outbox를 바로 커밋해야 합니다. 백그라운드 이벤트는 이미 저장된 작업을 조금 더 진행하는 기회일 뿐입니다.

## 프로세스 종료를 정상 입력으로 다룹니다

기본 검증 시나리오는 다음과 같습니다.

```text
기록 저장
→ 시스템 선택기 실행 또는 다른 앱으로 이동
→ 프로세스 종료
→ 실행 아이콘, 딥 링크 또는 알림으로 다시 시작
```

다시 시작한 뒤 확인할 내용은 다음과 같습니다.

- 저장 완료된 기록이 남아 있습니다.
- 완료되지 않은 외부 작업을 성공으로 표시하지 않습니다.
- 대기 중인 outbox를 다시 처리할 수 있습니다.
- 경로가 가리키는 기록이 없으면 안전한 목록 화면으로 이동합니다.
- 이전 프로세스의 비동기 작업, 토스트, 로딩 상태를 복원하려 하지 않습니다.

Android에서는 다른 Activity를 여는 동안 기존 Activity가 재생성되거나 프로세스가 종료될 수 있습니다. 이미지 선택기처럼 대기 중인 결과 조회 API가 제공되는 경우에만 시작 절차에서 결과를 확인합니다. 이 동작을 모든 플랫폼과 모든 선택기에 일반화하지 않습니다.

## 네이티브 바이너리와 JavaScript를 구분합니다

모바일 배포에는 적어도 두 종류의 결과물이 있습니다.

```text
네이티브 바이너리
- 네이티브 모듈
- 매니페스트, plist, 권한 설정
- 앱 식별자
- 서명
- 운영체제 기능

JavaScript와 리소스
- 경로와 컴포넌트
- 기록과 동기화를 처리하는 코드
- 이미지와 기타 리소스
```

JavaScript가 새 네이티브 메서드를 호출하지만 설치된 바이너리에 그 메서드가 없으면 실행 중 오류가 발생합니다. 소스 리비전만 기록해서는 이 문제를 찾기 어렵습니다. 앱 버전, 빌드 번호, runtimeVersion과 네이티브 의존성 결과를 함께 기록해야 합니다.

## Expo 설정과 생성된 네이티브 프로젝트

CNG를 사용하면 `android/`와 `ios/`는 다음 입력으로 다시 만들 수 있는 결과물입니다.

```text
Expo SDK 템플릿
+ 앱 설정
+ 패키지와 자동 연결
+ 설정 플러그인
+ 로컬 네이티브 모듈
→ 생성된 Android와 iOS 프로젝트
```

이 방식을 선택했다면 생성된 파일을 직접 고쳐 기준 파일로 삼지 않습니다. 필요한 변경은 `app.json`, `app.config.js`, 설정 플러그인 또는 로컬 모듈에 작성하며, 초기 상태에서 네이티브 프로젝트를 다시 생성해도 같은 결과가 나와야 합니다.

기존 네이티브 프로젝트를 직접 관리하는 앱이라면 `android/`, `ios/`를 버전 관리에 포함하고 Gradle과 Xcode 설정을 직접 관리합니다. 두 방식이 섞인 경우에는 다음 질문에 답할 수 있어야 합니다.

- `android/`, `ios/`를 커밋합니까?
- 권한과 앱 식별 정보의 기준 파일은 무엇입니까?
- 초기 상태에서 다시 생성하는 작업이 직접 수정한 내용을 지우지 않습니까?
- 네이티브 변경을 재현하는 명령은 무엇입니까?

## Expo Go와 개발용 빌드

Expo Go는 JavaScript 화면과 포함된 일부 네이티브 모듈을 빠르게 확인하는 용도입니다. 다음 항목을 확인하지 못합니다.

- 프로젝트가 실제로 포함할 네이티브 의존성
- 커스텀 권한 메시지와 권한 설정
- 로컬 네이티브 모듈
- 설정 플러그인 결과
- 실제 푸시 알림 환경
- 제품 앱 식별자와 서명

개발용 빌드는 해당 프로젝트가 선택한 네이티브 모듈과 설정을 포함합니다. 따라서 이 저장소에서는 처음부터 개발용 빌드를 기준으로 사용합니다. Expo Go에서 화면이 보였다는 이유로 카메라 권한, 백그라운드 작업, 푸시 토큰, 서명을 완료했다고 판단하지 않습니다.

## 코드 배치 기준

Field Notes는 다음 방향을 사용합니다.

```text
앱 경로와 화면
→ 애플리케이션 작업
→ 상태 형식과 저장소 호출 형식
← SQLite, FileSystem, HTTP, 권한, 알림 어댑터
```

- 경로 파일은 매개변수를 읽고 화면을 조합합니다.
- 애플리케이션 코드는 저장, 동기화, 기기 기능 호출 순서를 정합니다.
- 상태 형식은 기록, outbox, 충돌과 결과 종류를 표현합니다.
- 어댑터는 Expo 또는 OS가 반환한 값을 애플리케이션이 처리할 수 있는 값으로 바꿉니다.

상태 계산 코드가 `expo-sqlite`, `AppState`, 카메라 API를 직접 호출하면 프로세스 종료나 권한 실패를 독립적으로 검사하기 어렵습니다. 반대로 작은 화면 컴포넌트마다 저장소와 네이티브 API를 직접 만들면 동일한 상태를 서로 다르게 처리하게 됩니다.

## 시작 절차 순서

다음 순서를 기본으로 둡니다.

```text
네이티브 런타임 사용 가능 여부 확인
→ SQLite 열기와 마이그레이션
→ 필요한 세션 정보 읽기
→ 중단된 파일 작업과 선택기 결과 조정
→ 최초 링크와 알림 입력 검증
→ 대상 기록과 현재 계정 확인
→ 경로 적용
→ 포그라운드 재검증과 동기화 요청
```

모든 작업을 무조건 직렬로 실행할 필요는 없습니다. 다만 결과를 사용하기 전에 필요한 전제를 기다려야 합니다. 예를 들어 기록 데이터가 필요 없는 초기 화면은 데이터베이스 준비 전에 표시할 수 있지만, 기록 상세 화면은 데이터베이스에서 대상 기록을 확인한 뒤 열어야 합니다.

## 오류를 발생 위치별로 좁힙니다

| 증상 | 먼저 확인할 위치 | 필요한 첫 근거 |
|---|---|---|
| 시작 직후 앱 종료 | 네이티브 바이너리와 설정 | 기기 비정상 종료 로그, 앱과 빌드 버전 |
| 화면이 비어 있음 | JavaScript 경로와 렌더링 | 런타임 오류, 현재 경로 |
| 카메라 버튼을 사용할 수 없음 | 기기 기능과 권한 | 정규화된 기기 기능 값과 권한 상태 |
| 촬영 뒤 사진이 사라짐 | 선택기와 파일 복사 | 대기 중인 결과, 임시 파일과 앱 소유 파일 상태 |
| 저장한 기록이 없음 | SQLite와 마이그레이션 | 스키마 버전, 트랜잭션 결과 |
| 동기화가 멈춤 | outbox와 작업자 | 명령 상태, lease, 시도 횟수와 저장된 처리 결과 |

모든 문제를 `모바일 버그` 또는 `네트워크 오류`로 묶지 않습니다.

## 완료 기준

- JavaScript 프로세스, 네이티브 바이너리, 운영체제가 소유하는 값을 구분할 수 있습니다.
