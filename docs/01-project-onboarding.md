# 프로젝트 합류와 첫 기능

처음 보는 React·Next.js 저장소에 들어가면 새 파일부터 만들지 않습니다. 먼저 어떤 Node.js와 패키지 관리자를 쓰는지, 코드는 어디에서 실행되는지, 사용자의 요청이 어떤 파일을 거치는지 확인해야 합니다. 첫 변경은 화면 일부만 고치는 작업보다 URL, 데이터 읽기, 사용자 입력과 검증이 이어지는 작은 기능 하나가 적합합니다.

이 문서는 어떤 React·Next.js 프로젝트를 선택해도 먼저 알아야 할 내용을 다룹니다.

## 목표

이 문서를 읽은 뒤에는 다음 작업을 수행할 수 있어야 합니다.

- 저장소가 요구하는 Node.js와 패키지 관리자를 그대로 재현합니다.
- 개발 서버와 운영 서버의 차이를 확인합니다.
- URL 하나가 어느 route, 데이터 읽기 함수, 컴포넌트와 테스트를 거치는지 추적합니다.
- 기능 요청을 사용자가 확인할 수 있는 결과로 바꿉니다.
- URL의 `searchParams`로 서버 첫 화면을 구성하는 방법을 설명합니다.

## 실행 방법부터 확인합니다

다음 파일은 단순한 설정 모음이 아닙니다. 다른 개발자와 CI가 같은 조건에서 코드를 실행하기 위한 기준입니다.

| 파일 또는 항목 | 확인할 내용 |
| --- | --- |
| `.nvmrc`, `package.json#engines` | 지원하는 Node.js 버전 |
| `packageManager` | 사용할 패키지 관리자와 버전 |
| 잠금 파일 | 의존성 해석 결과 |
| `scripts` | 개발, 형 검사, 단위 테스트, 빌드, E2E와 smoke 명령 |
| `next.config.*` | output, header, redirect, image와 runtime 설정 |
| `.env.example` | 필요한 환경 변수와 공개 가능한 값 |
| CI workflow | 저장소가 실제로 실행하는 명령과 환경 |

저장소가 pnpm 잠금 파일을 사용한다면 임의로 `npm install`을 실행하지 않습니다. 패키지 관리자를 바꾸면 코드와 관계없는 의존성 변경이 함께 생겨 실패 원인을 구분하기 어려워집니다.

먼저 저장소가 제공하는 명령을 그대로 확인합니다.

```sh
nvm use
corepack enable
pnpm install --frozen-lockfile
pnpm check
pnpm build
pnpm test:e2e
```

위 명령은 예시입니다. 실제 프로젝트에서는 `package.json`, 잠금 파일과 CI 설정을 기준으로 사용해야 합니다.

개발 서버가 실행되어도 운영 빌드는 실패할 수 있습니다. route type, Server/Client module 분리, 환경 변수 치환과 정적 렌더링 판단은 빌드 과정에서 추가로 검사됩니다. 프로젝트에 합류한 첫날부터 운영 빌드와 실제 시작 명령을 한 번 실행해 보는 편이 좋습니다.

## 코드의 실행 위치를 구분합니다

같은 저장소 안의 코드도 서로 다른 시점과 환경에서 실행됩니다.

```text
브라우저
- event handler
- 초점과 history
- localStorage
- 클라이언트 요청

Next.js 서버
- Server Component
- Route Handler
- 서버 전용 환경 변수
- 데이터베이스 또는 파일 접근

빌드 시점
- module graph 생성
- route/type 생성
- 공개 환경 변수 치환
- 정적·동적 렌더링 판단
```

파일 이름만 보고 실행 위치를 단정하지 않습니다. import 관계와 사용하는 API를 함께 확인합니다.

- `"use client"`가 선언된 파일과 그 파일이 불러오는 module은 브라우저 bundle에 들어갈 수 있습니다.
- Server Component가 Client Component에 넘기는 값은 직렬화할 수 있어야 합니다.
- 서버 전용 값은 Client Component가 불러오는 module에서 읽지 않습니다.
- `NEXT_PUBLIC_` 계열 환경 변수는 브라우저에 노출된다고 가정합니다.
- Route Handler는 HTTP 요청을 처리하는 함수이며 화면을 렌더링하는 page와 역할이 다릅니다.

실행 위치를 잘못 판단하면 비밀값 노출, bundle 증가, hydration 오류와 운영 환경에서만 발생하는 실패로 이어질 수 있습니다.

## URL에서 사용자 동작을 끝까지 따라갑니다

기존 기능 하나를 다음 순서로 추적합니다.

1. 사용자가 여는 URL을 확인합니다.
2. 해당 segment의 `page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`를 찾습니다.
3. Server Component가 읽는 입력과 데이터 읽기 함수를 찾습니다.
4. URL이나 외부 응답을 검사하고 화면에 사용할 값으로 바꾸는 위치를 찾습니다.
5. Client Component가 시작되는 파일과 전달받는 props를 확인합니다.
6. 사용자 이벤트가 호출하는 함수와 HTTP 요청을 따라갑니다.
7. 정상 결과, 빈 결과와 실패가 어느 코드에서 화면 상태로 바뀌는지 확인합니다.
8. 이 동작을 검사하는 단위 테스트, Route Handler 테스트와 브라우저 테스트를 찾습니다.

디렉터리 소개만 읽는 것보다 실제 동작 하나를 끝까지 따라가면 값이 어디에서 만들어지고 변경되는지 빠르게 파악할 수 있습니다.

## 기능 요청을 확인 가능한 결과로 바꿉니다

“검색 추가”, “반응형 수정”, “캐시 적용” 같은 문장만으로는 완료 여부를 판단하기 어렵습니다. 사용자, 조건, 행동과 결과를 포함해 다시 적습니다.

```text
방문자가 프로젝트 목록에서 "network"를 검색하면
URL에 같은 조건이 기록되고 목록이 갱신됩니다.
새로 고침하거나 뒤로 이동해도 조건과 결과가 복원됩니다.
```

좋은 결과 문장은 사용한 라이브러리 이름에 의존하지 않습니다. router API나 요청 라이브러리를 바꾸더라도 같은 사용자 결과를 확인할 수 있어야 합니다.

### 입력

- 값은 URL, 폼, cookie, API 중 어디에서 들어옵니까?
- 빈 값, 알 수 없는 값과 지나치게 긴 값을 어떻게 처리합니까?
- 서버 첫 화면과 브라우저에서 같은 정규화 규칙을 사용합니까?

### 출력

- 화면, URL과 서버 데이터 중 무엇이 바뀝니까?
- 키보드와 보조 기술이 인식할 이름과 상태 알림은 무엇입니까?
- 새로 고침하거나 link를 공유한 뒤 무엇이 복원됩니까?

### 실패

- 빈 결과와 요청 실패를 어떻게 구분합니까?
- 마지막 정상 데이터와 사용자가 입력한 값을 유지합니까?
- 다시 시도하거나 안전하게 이동할 방법이 있습니까?

### 완료 순서

- 여러 응답의 완료 순서가 요청 순서와 달라질 수 있습니까?
- 같은 저장 명령이 반복될 수 있습니까?
- 사용자가 다른 화면으로 이동한 뒤 도착한 결과는 버려야 합니까?

## 첫 기능의 범위를 작게 잡습니다

검색 목록을 예로 들면 첫 변경은 다음 정도면 충분합니다.

1. `/`의 `searchParams`에서 `q`, `status`, `page`를 읽습니다.
2. 알 수 없는 값은 안전한 기본값으로 바꿉니다.
3. 서버에서 첫 결과를 읽습니다.
4. Client Component에 직렬화 가능한 검색 조건과 결과를 전달합니다.
5. 새로 고침해도 입력값과 첫 결과가 같은 조건을 나타내게 합니다.

이 단계에서 요청 취소, 낙관적 갱신과 성능 예산까지 한꺼번에 구현하지 않습니다. 먼저 URL과 서버 첫 화면이 같은 입력을 사용하도록 만듭니다.

```tsx
export default async function Page({
  searchParams,
}: {
  searchParams: Promise<Record<string, string | string[] | undefined>>;
}) {
  const raw = await searchParams;
  const query = parseProjectQuery(toURLSearchParams(raw));
  const initialResult = searchProjects(query);

  return <ProjectCatalog initialQuery={query} initialResult={initialResult} />;
}
```

구체적인 route signature는 프로젝트가 사용하는 Next.js 버전과 생성된 route type을 따릅니다. 중요한 점은 URL 입력을 서버에서 한 번 정규화하고, 같은 값으로 첫 데이터와 입력 화면을 구성하는 것입니다.

## 모르는 부분을 작은 실험으로 확인합니다

한 번에 authentication, cache, 상태 관리 library와 design system을 모두 바꾸지 않습니다. 확인할 질문마다 가장 작은 실험을 만듭니다.

| 질문 | 확인 방법 |
| --- | --- |
| 이 page는 서버에서 실행됩니까? | 서버와 브라우저에서 각각 로그를 한 번 확인합니다. |
| 쿼리 기본값은 어디에서 정합니까? | 잘못된 URL을 직접 열어 첫 입력과 결과를 확인합니다. |
| 브라우저 bundle에는 무엇이 들어갑니까? | 작은 Client Component를 만들고 운영 빌드 결과를 비교합니다. |
| 화면 이동이 전체 새로 고침입니까? | Network 기록과 컴포넌트 상태를 확인합니다. |
| 운영 환경에서만 실패합니까? | 빌드한 서버를 실제 시작 명령으로 실행합니다. |

실험 전에 예상 결과를 적고, 실제 결과가 달랐던 부분만 기록합니다.

```text
질문: URL의 status 값이 허용 목록에 없으면 첫 화면은 무엇을 보여 줍니까?
예상: any로 바꾸고 전체 결과를 보여 줍니다.
관찰: 입력은 any였지만 서버 결과는 빈 목록이었습니다.
결정: 서버와 브라우저가 같은 query parser를 사용하게 합니다.
```

## 프로젝트 진입 완료 기준

다음 항목을 직접 확인할 수 있으면 실제 구현을 시작할 준비가 된 것입니다.

- 저장소가 요구하는 Node.js, 패키지 관리자와 잠금 파일을 확인했습니다.
- 개발, 형 검사, 테스트, 운영 빌드와 시작 명령을 찾았습니다.
- 브라우저, 서버와 빌드 시점에 실행되는 코드를 구분했습니다.
- 사용자 URL 하나를 page, 데이터 읽기 함수, Client Component와 HTTP 요청까지 추적했습니다.
- 첫 변경의 입력, 결과, 실패와 완료 순서를 적었습니다.
- 첫 기능을 운영 빌드와 해당 기능에 맞는 테스트로 확인할 방법을 정했습니다.
