# 프로젝트 합류와 첫 기능

처음 보는 React·Next.js 저장소에 들어가면 새 파일부터 만들지 않습니다. 먼저 **어떤 실행 환경을 전제로 하는지**, **코드가 브라우저·서버·빌드 중 어디에서 실행되는지**, **사용자의 요청이 어떤 파일과 함수들을 거쳐 결과가 되는지**를 확인합니다.

첫 변경은 화면 일부만 고치는 작업보다 URL, 데이터 읽기, 사용자 입력과 검증이 연결되는 작은 기능 하나가 적합합니다. 이런 기능을 따라가면 라우팅, 서버와 클라이언트의 경계, 상태 저장 위치, 테스트 방법을 한 번에 파악할 수 있기 때문입니다.

이 문서는 특정 저장소의 디렉터리 구조를 외우는 방법이 아니라, 처음 보는 React·Next.js 프로젝트에 진입할 때 반복해서 사용할 수 있는 확인 순서를 다룹니다.

## 목표

이 문서를 읽은 뒤에는 다음 작업을 수행할 수 있어야 합니다.

- 저장소가 요구하는 Node.js와 패키지 관리 환경을 그대로 재현합니다.
- 개발 서버, 운영 빌드와 운영 서버가 서로 다른 조건에서 실패할 수 있는 이유를 설명합니다.
- 브라우저, Next.js 서버와 빌드 시점에 실행되는 코드를 구분합니다.
- URL 하나가 어느 route, 데이터 읽기 함수, 컴포넌트와 테스트를 거치는지 추적합니다.
- 모호한 기능 요청을 사용자가 확인할 수 있는 결과와 실패 조건으로 바꿉니다.
- URL의 `searchParams`를 정규화하여 서버 첫 화면과 브라우저 상태가 같은 조건을 사용하게 만드는 방법을 설명합니다.

## 실행 방법부터 확인합니다

다음 파일과 항목은 단순한 설정 모음이 아닙니다. 로컬 개발자, CI와 운영 환경이 최대한 같은 조건에서 코드를 실행하기 위한 기준입니다.

| 파일 또는 항목 | 확인할 내용 |
| --- | --- |
| `.nvmrc`, `.node-version`, `package.json#engines` | 프로젝트가 기대하거나 지원하는 Node.js 버전 |
| `packageManager` | 의도한 패키지 관리자와 버전 |
| `pnpm-lock.yaml`, `package-lock.json`, `yarn.lock` 등 | 실제로 고정된 의존성 해석 결과 |
| `scripts` | 개발, 형 검사, lint, 단위 테스트, 빌드, E2E, smoke, 운영 시작 명령 |
| `next.config.*` | output, header, redirect, image, runtime 등 Next.js 동작에 영향을 주는 설정 |
| `.env.example` 등 | 필요한 환경 변수의 이름과 용도 |
| CI workflow | 저장소가 실제 검증에 사용하는 Node.js 버전, 설치 방법과 실행 명령 |
| Dockerfile 또는 배포 설정 | 운영 환경에서 어떤 빌드 결과와 시작 명령을 사용하는지 |

`.nvmrc`와 `package.json#engines`가 모두 존재한다고 해서 반드시 같은 의미는 아닙니다. `.nvmrc`는 개발자가 사용할 구체적인 Node.js 버전을 지정하는 경우가 많고, `engines`는 지원 범위를 표현할 수도 있습니다. 둘이 다르면 CI와 배포 설정까지 확인해 실제 기준을 찾습니다.

`packageManager` 필드는 예를 들어 다음과 같이 작성될 수 있습니다.

```json
{
  "packageManager": "pnpm@10.0.0"
}
```

이 값은 프로젝트가 의도한 패키지 관리자와 버전을 알려 주지만, 필드가 존재한다는 사실만으로 모든 환경에서 자동 강제된다고 가정하지 않습니다. Corepack 사용 여부, CI 설정과 잠금 파일을 함께 확인합니다.

저장소가 `pnpm-lock.yaml`을 사용한다면 특별한 이유 없이 `npm install`을 실행하지 않습니다. 다른 패키지 관리자를 사용하면 코드와 관계없는 잠금 파일 변경이나 의존성 버전 차이가 생길 수 있고, 그 결과 기능 오류와 환경 차이를 구분하기 어려워집니다.

먼저 저장소가 제공하는 명령을 확인한 뒤 그대로 실행합니다.

```sh
nvm use
corepack enable
pnpm install --frozen-lockfile
pnpm check
pnpm build
pnpm test:e2e
```

위 명령은 예시입니다. 실제 프로젝트에서는 `package.json`, 잠금 파일, README와 CI 설정을 기준으로 사용해야 합니다.

`--frozen-lockfile`과 같은 옵션은 설치 과정에서 잠금 파일을 임의로 다시 계산하지 않도록 하여 CI와 같은 의존성 집합을 재현하는 데 도움이 됩니다. 프로젝트가 다른 패키지 관리자나 다른 옵션을 사용한다면 그 저장소의 방식에 따릅니다.

### 개발 서버가 실행된다고 검증이 끝난 것은 아닙니다

개발 서버는 빠른 피드백을 위해 필요한 파일을 요청 시점에 변환하거나 일부 검사를 지연할 수 있습니다. 반면 운영 빌드는 전체 module graph, route와 type 생성, 정적·동적 렌더링 가능 여부, 환경 변수 사용 방식처럼 개발 중에는 드러나지 않았던 문제를 발견할 수 있습니다.

따라서 다음 세 단계는 서로 다른 검증으로 취급합니다.

```text
개발 서버
→ 기능을 빠르게 실행하고 수정 결과를 확인

운영 빌드
→ 배포 가능한 산출물을 만들 수 있는지 확인

운영 시작 명령
→ 실제 빌드 산출물이 운영 방식으로 실행되는지 확인
```

예를 들어 개발 서버에서는 정상처럼 보여도 다음 문제는 운영 빌드나 운영 서버에서 처음 드러날 수 있습니다.

- 서버 전용 module이 Client Component 쪽 import graph에 들어간 경우
- 빌드 시 필요한 환경 변수가 없는 경우
- 정적 렌더링이 예상되던 route에서 요청 시점 API를 사용하는 경우
- 운영 시작 명령이나 output 설정이 배포 방식과 맞지 않는 경우

프로젝트에 합류한 초기에 운영 빌드와 실제 시작 명령을 한 번 실행해 두면 이후 실패가 자신의 변경 때문인지 원래 환경 문제였는지 구분하기 쉬워집니다.

## 코드의 실행 위치를 구분합니다

같은 저장소 안의 코드도 서로 다른 시점과 환경에서 실행됩니다. 실행 위치를 구분할 때는 파일 이름보다 **module 경계, import 관계와 사용하는 API**를 봅니다.

```text
브라우저
- 클릭, 입력 같은 event handler
- DOM, focus, history
- localStorage, sessionStorage
- 브라우저에서 시작하는 HTTP 요청

Next.js 서버
- Server Component
- Route Handler
- 서버 전용 환경 변수
- 데이터베이스, 파일 시스템, 내부 서비스 접근

빌드 시점
- module graph 생성
- route/type 생성
- 일부 환경 변수 처리
- 정적·동적 렌더링 가능 여부 판단
- 배포용 산출물 생성
```

모든 코드가 세 위치 중 정확히 하나에서만 실행된다고 단순화해서는 안 됩니다. 어떤 module은 빌드 과정에서도 처리되고 서버에서도 실행될 수 있습니다. 중요한 것은 **그 코드가 브라우저에 포함될 수 있는지**, **요청마다 서버에서 실행되는지**, **빌드 과정에서 값이 결정되는지**를 구분하는 것입니다.

### `"use client"`는 클라이언트 경계를 만듭니다

App Router에서 파일 상단에 `"use client"`가 있으면 그 파일은 Client Component 진입점이 됩니다.

```tsx
"use client";

export function SearchInput() {
  // 브라우저 event handler와 browser API를 사용할 수 있습니다.
}
```

이 경계에서 중요한 점은 다음과 같습니다.

- `"use client"`가 선언된 module과 그 module이 가져오는 의존성은 클라이언트 쪽 module graph에 포함될 수 있습니다.
- 따라서 Client Component가 서버 전용 module, 비밀 환경 변수나 Node.js 전용 API를 import하면 안 됩니다.
- Server Component는 Client Component를 렌더링할 수 있습니다.
- Client Component를 사용한다고 해서 상위 Server Component 전체가 자동으로 Client Component가 되는 것은 아닙니다.
- 서버에서 Client Component로 전달하는 props는 서버와 클라이언트 경계를 넘을 수 있는 형태여야 합니다. 일반적인 데이터는 문자열, 숫자, 배열, plain object처럼 직렬화 가능한 값으로 구성하는 편이 안전합니다.

예를 들어 데이터베이스 연결 객체를 Client Component의 prop으로 직접 넘기는 방식은 올바른 경계가 아닙니다.

```tsx
// Server Component
const projects = await readProjects();

return <ProjectCatalog projects={projects} />;
```

여기서는 데이터베이스 연결 자체가 아니라 화면에 필요한 결과 데이터만 전달합니다.

### 환경 변수의 공개 범위를 확인합니다

서버에서만 사용하는 비밀값과 브라우저에 공개되어도 되는 값을 구분합니다.

```text
DATABASE_URL
API_SECRET
→ 서버 전용으로 취급

NEXT_PUBLIC_ANALYTICS_ID
→ 브라우저에 포함될 수 있는 공개 값으로 취급
```

`NEXT_PUBLIC_` 계열 변수에 비밀값을 넣지 않습니다. 이름이 공개용 접두사를 사용한다는 것은 브라우저 bundle에 포함될 가능성을 전제로 설계해야 한다는 뜻입니다.

반대로 접두사가 없다고 해서 어떤 코드에서든 안전한 것은 아닙니다. 서버 전용 환경 변수를 읽는 module이 Client Component의 import graph에 들어가지 않도록 module 경계를 유지해야 합니다.

### page와 Route Handler의 역할을 구분합니다

App Router를 사용하는 프로젝트에서는 보통 다음 역할을 구분합니다.

```text
page.tsx
→ URL에 대응하는 UI를 렌더링

route.ts
→ HTTP 요청과 응답을 직접 처리
```

예를 들어 다음 Route Handler는 JSON 응답을 반환합니다.

```ts
export async function GET() {
  return Response.json({ ok: true });
}
```

반면 `page.tsx`는 사용자가 보는 React 화면을 구성합니다.

```tsx
export default function Page() {
  return <main>Projects</main>;
}
```

프로젝트가 Pages Router를 사용한다면 `pages/`와 API Routes 등 다른 규칙을 따를 수 있습니다. 따라서 먼저 해당 저장소가 App Router, Pages Router 또는 두 방식을 함께 사용하는지 확인합니다.

실행 위치를 잘못 판단하면 비밀값 노출, 불필요한 bundle 증가, hydration 문제와 운영 환경에서만 발생하는 실패로 이어질 수 있습니다.

## URL에서 사용자 동작을 끝까지 따라갑니다

기존 기능 하나를 선택하여 **입력 → 변환 → 데이터 접근 → 화면 → 사용자 이벤트 → 다시 상태 변경** 순서로 추적합니다.

예를 들어 `/projects?q=network`라는 URL이 있다면 다음 질문에 답할 수 있어야 합니다.

```text
URL의 q는 어디에서 읽습니까?
→ 어떤 함수가 "network"를 검색 조건으로 바꿉니까?
→ 어떤 서버 함수가 데이터를 읽습니까?
→ 어떤 컴포넌트가 결과를 렌더링합니까?
→ 사용자가 검색어를 바꾸면 URL은 어디에서 갱신됩니까?
→ 새 URL로 이동했을 때 서버와 클라이언트는 어떤 값을 다시 읽습니까?
```

기존 기능 하나를 다음 순서로 추적합니다.

1. 사용자가 여는 URL과 HTTP method를 확인합니다.
2. 해당 route segment의 `page.tsx`, `layout.tsx`와 필요한 경우 `loading.tsx`, `error.tsx`, `not-found.tsx`를 찾습니다.
3. Server Component가 읽는 `params`, `searchParams`, cookie, header 등 입력을 확인합니다.
4. 외부 입력을 검사하고 애플리케이션에서 사용할 값으로 정규화하는 함수를 찾습니다.
5. 서버에서 데이터를 읽는 함수, repository, service 또는 외부 API 호출을 찾습니다.
6. Client Component가 시작되는 경계와 전달받는 props를 확인합니다.
7. 사용자 이벤트가 호출하는 함수와 이후 발생하는 navigation 또는 HTTP 요청을 따라갑니다.
8. 정상 결과, 빈 결과와 실패가 어느 코드에서 화면 상태로 바뀌는지 확인합니다.
9. 이 동작을 검사하는 단위 테스트, Route Handler 테스트, integration 테스트와 브라우저 테스트를 찾습니다.

여기서 **정규화**는 외부에서 들어온 여러 표현을 애플리케이션이 다루는 하나의 일관된 형태로 바꾸는 작업입니다.

예를 들어 URL에 다음 값이 들어올 수 있습니다.

```text
?page=
?page=0
?page=-2
?page=abc
?page=3
```

애플리케이션이 page 번호를 1 이상의 정수로 사용한다면 앞의 네 입력은 모두 기본값 `1`로 바꾸는 규칙을 둘 수 있습니다.

```ts
function parsePage(value: string | null): number {
  const page = Number(value);

  if (!Number.isInteger(page) || page < 1) {
    return 1;
  }

  return page;
}
```

디렉터리 구조만 읽는 것보다 실제 동작 하나를 끝까지 따라가면 값이 **어디에서 만들어지고, 검증되고, 변환되고, 다시 URL이나 화면 상태로 기록되는지** 빠르게 파악할 수 있습니다.

## 기능 요청을 확인 가능한 결과로 바꿉니다

“검색 추가”, “반응형 수정”, “캐시 적용” 같은 문장만으로는 완료 여부를 판단하기 어렵습니다. 사용자, 조건, 행동과 관찰 가능한 결과를 포함해 다시 적습니다.

```text
방문자가 프로젝트 목록에서 "network"를 검색하면
URL에 같은 조건이 기록되고 목록이 갱신됩니다.
새로 고침하거나 뒤로 이동해도 조건과 결과가 복원됩니다.
```

이 문장은 구현 방법이 아니라 사용자에게 관찰되는 계약을 설명합니다. router API나 요청 라이브러리를 바꾸더라도 같은 결과를 확인할 수 있어야 합니다.

기능을 구현하기 전에 최소한 **입력, 출력, 실패, 완료 순서**를 확인합니다.

### 입력

- 값은 URL, 폼, cookie, API 중 어디에서 들어옵니까?
- 문자열의 앞뒤 공백은 제거합니까?
- 빈 값은 "조건 없음"입니까, 잘못된 입력입니까?
- 허용 목록에 없는 값은 거부합니까, 기본값으로 바꿉니까?
- 지나치게 긴 문자열이나 허용 범위를 벗어난 숫자는 어떻게 처리합니까?
- 같은 query key가 여러 번 들어오면 무엇을 선택합니까?
- 서버 첫 화면과 브라우저에서 같은 정규화 규칙을 사용합니까?

마지막 질문은 중요합니다. 다음 URL처럼 같은 key가 여러 번 존재할 수 있기 때문입니다.

```text
/projects?status=open&status=closed
```

단일 값만 허용하는 기능이라면 첫 값, 마지막 값 또는 기본값 중 무엇을 사용할지 명시해야 합니다. 여러 값을 지원한다면 배열로 처리해야 합니다. 규칙을 정하지 않으면 서버와 브라우저가 서로 다른 값을 사용할 수 있습니다.

### 출력

- 화면, URL과 서버 데이터 중 무엇이 바뀝니까?
- URL에 검색 조건을 남기는 이유는 무엇입니까?
- 새로 고침 후 같은 결과가 복원되어야 합니까?
- URL을 다른 사람에게 공유했을 때 같은 조건이 재현되어야 합니까?
- 뒤로/앞으로 이동했을 때 어떤 상태가 복원되어야 합니까?
- 키보드와 보조 기술이 인식할 label, focus 이동과 상태 알림은 무엇입니까?

검색 조건을 URL에 저장하면 보통 새로 고침, 공유와 브라우저 history 복원이 쉬워집니다. 반대로 hover 여부나 임시 modal animation 상태처럼 URL과 관계없는 짧은 UI 상태까지 query parameter로 만들 필요는 없습니다.

### 실패

"결과가 없다"와 "결과를 가져오지 못했다"는 서로 다른 상태입니다.

```text
검색 성공 + 결과 0개
→ 빈 결과

서버 또는 네트워크 오류
→ 요청 실패
```

두 상태를 같은 메시지로 처리하면 사용자는 검색 조건을 바꿔야 하는지 다시 시도해야 하는지 판단할 수 없습니다.

다음을 정합니다.

- 빈 결과와 요청 실패를 어떻게 구분합니까?
- 마지막 정상 데이터를 유지할지 제거할지 결정했습니까?
- 사용자가 입력한 검색 조건은 실패 후에도 유지합니까?
- 다시 시도할 방법이 있습니까?
- 실패 후 안전하게 다른 화면으로 이동할 수 있습니까?

### 완료 순서

비동기 요청은 시작한 순서대로 끝난다는 보장이 없습니다.

```text
요청 A 시작
요청 B 시작
요청 B 완료
요청 A 완료
```

사용자가 `net`을 검색한 직후 `network`로 바꿨는데 오래 걸린 `net` 요청이 나중에 완료되면, 잘못 구현된 화면은 이전 결과로 되돌아갈 수 있습니다.

따라서 다음을 확인합니다.

- 여러 응답의 완료 순서가 요청 순서와 달라질 수 있습니까?
- 이전 요청 결과가 최신 상태를 덮어쓰지 않게 해야 합니까?
- 같은 저장 명령이 두 번 실행되어도 안전해야 합니까?
- 사용자가 다른 화면으로 이동한 뒤 늦게 도착한 결과는 무시해야 합니까?

첫 기능에서는 이 모든 문제를 한 번에 해결할 필요는 없습니다. 다만 기능 범위를 정할 때 어떤 문제가 아직 범위 밖인지 명시하면 이후 변경에서 놓치기 어렵습니다.

## 첫 기능의 범위를 작게 잡습니다

검색 목록을 예로 들면 첫 변경은 다음 정도면 충분합니다.

1. `/`의 `searchParams`에서 `q`, `status`, `page`를 읽습니다.
2. 외부 입력을 하나의 parser에서 정규화합니다.
3. 알 수 없거나 유효하지 않은 값은 정해 둔 기본값으로 바꿉니다.
4. 정규화된 조건으로 서버에서 첫 결과를 읽습니다.
5. Client Component에 직렬화 가능한 검색 조건과 결과를 전달합니다.
6. 새로 고침해도 입력값과 첫 결과가 같은 검색 조건을 나타내게 합니다.

이 단계에서 요청 취소, 낙관적 갱신, 복잡한 cache 정책과 성능 예산까지 한꺼번에 구현하지 않습니다. 먼저 **URL, 서버 데이터와 첫 화면이 같은 정규화된 입력을 사용한다**는 계약을 만듭니다.

### 서버에서 URL 입력을 한 번 정규화합니다

예를 들어 다음과 같은 흐름을 만들 수 있습니다.

```text
searchParams
    ↓
raw URL 입력
    ↓
parseProjectQuery()
    ↓
정규화된 ProjectQuery
    ├─→ searchProjects()
    └─→ ProjectCatalog의 초기 입력값
```

핵심은 데이터 조회와 화면 초기값이 서로 다른 parser를 사용하지 않는 것입니다.

```tsx
export default async function Page({
  searchParams,
}: {
  searchParams: Promise<Record<string, string | string[] | undefined>>;
}) {
  const raw = await searchParams;
  const query = parseProjectQuery(toURLSearchParams(raw));
  const initialResult = await searchProjects(query);

  return (
    <ProjectCatalog
      initialQuery={query}
      initialResult={initialResult}
    />
  );
}
```

위 예제의 `searchParams`가 `Promise`인 형태는 특정 Next.js 버전의 App Router 사용 방식을 가정한 예시입니다. 프로젝트에 따라 동기 object 형태이거나 생성된 route type을 사용할 수 있습니다.

따라서 다음처럼 외우지 않습니다.

```text
"Next.js의 searchParams는 항상 Promise다."
```

대신 다음 순서로 확인합니다.

1. 프로젝트의 Next.js 버전을 확인합니다.
2. 기존 page의 signature를 확인합니다.
3. 생성된 route type이나 프로젝트의 type helper가 있다면 그것을 따릅니다.
4. framework upgrade 중이라면 migration 문서를 확인합니다.

중요한 것은 `Promise` 여부가 아니라 **URL 입력을 서버에서 정규화한 뒤 같은 값으로 데이터와 화면을 구성한다는 구조**입니다.

### `string | string[] | undefined`를 그대로 도메인 로직에 넘기지 않습니다

URL query는 애플리케이션의 도메인 타입보다 느슨합니다.

```ts
type RawSearchParams =
  Record<string, string | string[] | undefined>;

type ProjectQuery = {
  q: string;
  status: "any" | "active" | "archived";
  page: number;
};
```

외부 입력과 내부 타입 사이에 parser를 두면 이후 코드는 `status`가 허용된 값인지, `page`가 양의 정수인지 매번 다시 검사할 필요가 없습니다.

```ts
function parseStatus(
  value: string | null,
): ProjectQuery["status"] {
  if (value === "active" || value === "archived") {
    return value;
  }

  return "any";
}
```

이런 parser를 서버 첫 렌더링과 브라우저 URL 갱신 양쪽에서 재사용하거나, 적어도 동일한 규칙을 공유하게 만드는 것이 중요합니다.

## 모르는 부분을 작은 실험으로 확인합니다

처음 보는 저장소에서는 추측을 크게 만들지 않습니다. authentication, cache, 상태 관리 library와 design system을 한꺼번에 이해하거나 바꾸려 하지 말고, 질문 하나마다 가장 작은 실험을 만듭니다.

| 질문 | 확인 방법 |
| --- | --- |
| 이 page의 렌더링 로직은 서버에서 실행됩니까? | 서버 로그와 브라우저 콘솔을 구분하여 확인합니다. |
| 쿼리 기본값은 어디에서 정합니까? | 유효하지 않은 URL을 직접 열어 입력값과 결과를 확인합니다. |
| 중복 query parameter는 어떻게 처리합니까? | 같은 key를 두 번 넣은 URL을 직접 열어 parser 결과를 확인합니다. |
| 브라우저 bundle에는 무엇이 들어갑니까? | 작은 Client Component 경계를 만든 뒤 운영 빌드 산출물과 bundle 분석 도구가 있다면 결과를 비교합니다. |
| 화면 이동이 전체 새로 고침입니까? | DevTools Network와 컴포넌트 상태 변화를 함께 확인합니다. |
| 뒤로 이동하면 검색 조건이 복원됩니까? | 검색 조건을 두 번 변경한 뒤 브라우저 Back을 사용합니다. |
| 운영 환경에서만 실패합니까? | 운영 빌드 후 저장소의 실제 시작 명령으로 실행합니다. |

로그를 사용할 때는 **서버 터미널에 찍힌 로그와 브라우저 DevTools console에 찍힌 로그를 구분**합니다. 같은 `console.log()`처럼 보여도 실행 위치에 따라 출력 위치가 다를 수 있습니다.

실험 전에는 예상 결과를 적습니다.

```text
질문: URL의 status 값이 허용 목록에 없으면 첫 화면은 무엇을 보여 줍니까?

예상:
status를 any로 정규화하고 전체 결과를 보여 줍니다.

관찰:
입력 UI는 any를 표시했지만 서버 결과는 빈 목록이었습니다.

원인:
서버 조회 함수와 입력 UI가 서로 다른 정규화 규칙을 사용했습니다.

결정:
서버와 브라우저가 같은 query parser 규칙을 사용하게 합니다.
```

예상과 관찰을 분리하면 "원래 이렇게 동작할 것"이라는 추측이 현재 구현의 사실처럼 굳어지는 것을 막을 수 있습니다.

## 테스트 위치를 기능 흐름과 함께 찾습니다

테스트 파일의 이름만 찾지 말고 무엇을 검증하는지 기능 흐름과 연결합니다.

```text
query parser 단위 테스트
→ 잘못된 status, page, 중복 값의 정규화 검증

데이터 읽기 함수 테스트
→ 정규화된 조건이 올바른 조회 조건으로 변환되는지 검증

Route Handler 또는 integration 테스트
→ HTTP 입력과 응답 계약 검증

브라우저/E2E 테스트
→ URL 변경, 새로 고침, 뒤로 이동과 실제 화면 결과 검증

smoke 테스트
→ 배포된 애플리케이션의 핵심 경로가 최소한 실행 가능한지 검증
```

모든 기능에 모든 종류의 테스트가 필요한 것은 아닙니다. 첫 변경에서는 실패했을 때 가장 중요한 계약을 잡아 주는 테스트를 선택합니다.

예를 들어 URL 검색 기능의 핵심이 정규화와 history 복원이라면 다음 두 검증의 가치가 큽니다.

1. parser 단위 테스트에서 잘못된 URL 값을 안전한 기본값으로 바꾸는지 확인합니다.
2. E2E 테스트에서 검색 후 새로 고침과 뒤로 이동에도 조건과 결과가 일치하는지 확인합니다.

## 첫 변경에서 피할 일

프로젝트 진입과 첫 기능 구현을 동시에 어렵게 만드는 변경은 피합니다.

- 기능과 무관한 패키지 관리자 변경
- 잠금 파일 전체 재생성
- formatter나 lint 규칙 전체 변경
- 인증 방식과 상태 관리 방식을 함께 교체
- 대규모 디렉터리 재구성
- "정리"를 이유로 기능과 관계없는 파일까지 대량 수정
- 충분한 측정 없이 cache나 memoization을 광범위하게 추가

첫 변경의 목적은 저장소 전체를 이상적인 구조로 바꾸는 것이 아니라 **프로젝트의 실제 실행 경로를 이해하고, 작은 사용자 결과 하나를 안전하게 완성하는 것**입니다.

## 프로젝트 진입 완료 기준

다음 항목을 직접 확인할 수 있으면 실제 구현을 시작할 준비가 된 것입니다.

- 저장소가 기대하는 Node.js 버전과 패키지 관리자를 확인했습니다.
- 잠금 파일과 CI가 사용하는 설치 방식을 확인했습니다.
- 개발, 형 검사, lint, 테스트, 운영 빌드와 운영 시작 명령을 찾았습니다.
- 개발 서버가 성공하는 것과 운영 빌드가 성공하는 것이 다른 검증임을 설명할 수 있습니다.
- 브라우저, 서버와 빌드 시점에 실행되는 코드를 구분했습니다.
- `"use client"`가 만드는 module 경계와 서버 전용 값이 넘어가면 안 되는 이유를 설명할 수 있습니다.
- 사용자 URL 하나를 page, query parser, 데이터 읽기 함수, Client Component와 HTTP 요청까지 추적했습니다.
- 첫 변경의 입력, 결과, 실패와 완료 순서를 적었습니다.
- 중복되거나 유효하지 않은 `searchParams`를 어떻게 정규화할지 정했습니다.
- 서버 첫 화면의 데이터와 입력 UI가 같은 정규화된 값을 사용하도록 설계했습니다.
- 첫 기능을 운영 빌드와 해당 기능에 맞는 테스트로 확인할 방법을 정했습니다.

이 기준을 충족했다면 다음으로 [`02-ui-and-state-architecture.md`](02-ui-and-state-architecture.md)를 읽고, 상태를 URL, 서버, 브라우저 중 어디에 저장할지 결정합니다.
