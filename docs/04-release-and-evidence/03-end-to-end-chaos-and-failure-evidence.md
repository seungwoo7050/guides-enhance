# 종단 간 장애 실험과 근거

## 목표

장애를 무작위로 발생시키는 데서 끝내지 않고, 하나의 실패 가설을 장애 전·중·복구 후의 업무 상태로 검증합니다. 업무 검증 결과와 cleanup 결과도 따로 기록합니다.

이 문서는 필수 경로를 마친 뒤 장애 실험 방법을 더 자세히 확인할 때 사용하는 보충 자료입니다.

## 단위 테스트가 통과해도 조합에서는 실패할 수 있습니다

서비스별 테스트가 모두 성공해도 실제 조합에는 다음 문제가 남을 수 있습니다.

- 설정 이름과 channel이 다릅니다.
- migration과 application 시작 순서가 맞지 않습니다.
- 여러 계층의 retry가 요청 수를 크게 늘립니다.
- Broker 복구 뒤 Outbox가 줄지 않습니다.
- 조회 모델 프로세스는 실행 중이지만 event를 잃었습니다.
- cleanup 실패가 원래 테스트의 종료 상태를 덮습니다.

여러 장애를 한 번에 넣으면 어느 실패가 결과를 만들었는지 판단하기 어렵습니다.

## 먼저 검증할 문장을 작성합니다

실험은 다음 형식의 가설로 시작합니다.

```text
[조건]에서
[업무 영향]이 발생하지만
[바뀌면 안 되는 상태]는 유지되고,
[복구 작업] 뒤
[최종 상태]에 [시간 한도] 안에 도달합니다.
```

예:

```text
Broker가 30초 중단되면 새 예약의 Outbox가 쌓이지만
예약 상태와 event ID는 보존됩니다.
Broker 복구 뒤 60초 안에 조회 모델의 예약 수가 원본과 같아집니다.
```

가설에 시간과 바뀌면 안 되는 값을 포함하지 않으면 결과를 임의로 해석하게 됩니다.

## 한 번에 장애 하나만 넣습니다

다음 순서를 고정합니다.

1. 빈 상태나 고정 fixture로 시작합니다.
2. 장애 전 기준 값을 기록합니다.
3. 장애 하나를 발생시킵니다.
4. 장애 중 요청 결과와 저장 상태를 기록합니다.
5. 복구하기 전에 로그와 DB 상태를 보존합니다.
6. 장애를 제거합니다.
7. 자동 복구나 재조정을 실행합니다.
8. 최종 값과 경과 시간을 검사합니다.
9. 이 실행이 만든 자원을 정리합니다.

여러 장애의 조합은 각 장애를 따로 검증한 뒤에만 추가합니다.

## 복구 전에 상태를 남깁니다

실패 직후 프로세스를 재시작하거나 queue를 비우면 원인을 확인할 자료가 사라질 수 있습니다. 먼저 다음을 저장합니다.

- 요청 결과와 operation ID
- 관련 로그와 trace
- 원본 DB의 상태와 행 수
- Outbox, DLQ와 조회 모델 checkpoint
- container와 process 상태
- 발생시킨 장애와 시작·종료 시각
- 사용한 release manifest

일부 자료를 수집하지 못하더라도 원래 실패 결과를 성공으로 바꾸면 안 됩니다.

## 업무 결과와 cleanup 결과를 분리합니다

실험 본문이 실패한 뒤 cleanup도 실패할 수 있습니다. 두 결과를 따로 남깁니다.

```text
primary_status = FAIL
cleanup_status = FAIL
final_status = FAIL
```

반대로 업무 검증이 성공하고 cleanup만 실패했다면 업무 결과는 성공으로 남기되 정리 실패를 별도로 보고합니다. cleanup 성공이 잘못된 업무 결과를 통과시키면 안 됩니다.

## 복구는 업무 상태로 판단합니다

프로세스가 다시 실행되었다는 사실만으로 복구를 완료했다고 볼 수 없습니다.

예를 들어 Broker 장애 뒤에는 다음을 확인합니다.

- 원본 예약 수가 유지됩니다.
- 미발행 Outbox가 0으로 줄어듭니다.
- 조회 모델의 예약 수와 상태가 원본과 같아집니다.
- 같은 event의 재전달이 중복 효과를 만들지 않습니다.
- 가설에 적은 시간 안에 수렴합니다.

## 흔한 잘못

- 여러 서비스를 동시에 중단하고 하나의 실험으로 처리합니다.
- 바뀌면 안 되는 값을 적지 않습니다.
- 장애 직후 자료를 모으지 않고 재시작부터 합니다.
- process health만 보고 업무 복구를 성공으로 판단합니다.
- cleanup 오류가 원래 실패를 덮습니다.
- 이전 volume과 cache가 남은 상태에서 실험을 반복합니다.
- 실패한 실행의 commit, manifest와 ID를 기록하지 않습니다.

## 검증 방법

장애 실험 도구 자체도 검사합니다.

- 장애 전 기준 값이 없으면 실행하지 않습니다.
- 지원하지 않는 장애나 두 개 이상의 장애를 거절합니다.
- 장애 중 Snapshot을 cleanup 전에 저장합니다.
- 업무 결과와 cleanup 결과를 따로 반환합니다.
- 최종 상태가 다르면 process health가 정상이어도 실패합니다.
- 시간 한도를 넘긴 수렴은 실패로 판정합니다.

## 관련 프로젝트

[`chaos-evidence`](../../exercises/chaos-evidence/)는 `BROKER_DOWN` 한 가지 장애를 대상으로 `BEFORE`, `DURING`, `AFTER` Snapshot과 독립된 판정 결과를 검사합니다.

## 완료 기준

- 실패 가설에 업무 영향, 유지할 값, 복구 작업, 최종 상태와 시간을 넣을 수 있습니다.
- 장애 전·중·복구 후의 값을 같은 operation ID로 연결할 수 있습니다.
- 복구 전에 필요한 자료를 저장할 수 있습니다.
- 업무 결과와 cleanup 결과를 서로 덮어쓰지 않게 할 수 있습니다.
