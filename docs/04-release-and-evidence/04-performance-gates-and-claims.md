# 성능 기준과 측정 결과 판정

## 목표

성능 목표, 특정 환경에서 얻은 측정값과 아직 근거가 부족한 주장을 구분합니다. 요청을 누락하거나 효과를 중복 적용한 실행은 빠르더라도 실패로 판정합니다.

이 문서는 분산 서비스의 필수 경로가 아니라 성능 검증과 릴리스 판정을 다루는 심화 자료입니다.

## 빠른 결과가 항상 올바른 결과는 아닙니다

처리량이 높아도 일부 요청을 버리거나 같은 결제를 두 번 적용했다면 성능이 좋은 것이 아닙니다. 평균만 보면 긴 꼬리 지연과 첫 실행 실패도 숨길 수 있습니다.

한 번 실행한 개발 노트북 결과를 운영 용량으로 일반화하거나 환경과 오류 수를 기록하지 않고 “초당 만 건”이라고 쓰면 다시 검증할 수 없습니다.

## 목표, 측정값과 판정을 나눕니다

```text
목표: p95 < 200ms, 오류율 < 0.1%, 중복 효과 0
측정: 특정 commit, JDK, CPU와 부하에서 얻은 값
판정: PASS / FAIL / UNVERIFIED
```

목표는 만족해야 할 기준이고 측정은 특정 조건에서 관찰한 값입니다. 환경이 다르면 같은 표에 넣더라도 직접 비교하지 않습니다.

## 실행 조건을 함께 기록합니다

다음 정보가 있어야 결과를 다시 만들 수 있습니다.

- release manifest 또는 commit
- JDK와 운영체제
- CPU 종류와 사용할 수 있는 core 수
- heap과 container 제한
- instance, worker와 connection pool 수
- 데이터 크기와 시작 상태
- 요청 수, 동시 실행 수와 유입 방식
- warm-up 포함 여부
- 반복 횟수와 실행 순서
- timeout과 retry 설정
- 장애 주입 여부

한 번의 비교에서는 가설과 직접 관련된 설정 하나만 바꿉니다.

## 정확성을 먼저 확인합니다

각 실행에서 다음 합계를 확인합니다.

- 제출한 고유 operation 수
- 완료, 거절과 실패 수
- 중복 효과 수
- 결과가 없는 요청 수
- queue에서 버린 작업 수
- 외부 효과 수
- 정본과 조회 모델의 차이

합계가 맞지 않으면 실행 시간이 기준보다 짧아도 `FAIL`입니다.

## PASS, FAIL, UNVERIFIED를 구분합니다

- `PASS`: 필요한 실행 횟수와 정확성 자료가 있고 시간 기준도 만족합니다.
- `FAIL`: 측정 자료는 충분하지만 정확성이나 시간 기준을 만족하지 못합니다.
- `UNVERIFIED`: 실행 횟수, 환경 정보나 완료 수가 부족해 판정할 수 없습니다.

근거가 부족한 상태를 임의로 성공이나 실패로 단정하지 않습니다. warm-up 실행을 제외하려면 측정 전에 규칙을 정하고, 실제 시작 직후 성능은 별도로 확인합니다.

## 병목 주장은 측정 자료와 연결합니다

“DB가 병목이다”라고 판단하려면 다음과 같은 자료가 필요합니다.

- CPU, allocation, lock과 I/O profile
- connection pool 대기 시간
- query plan과 실행 시간
- Broker lag
- queue age
- 의존 서비스 latency
- 같은 workload에서 변경 전후 결과

여러 설정을 동시에 바꾸면 어느 변경이 결과에 영향을 줬는지 알기 어렵습니다.

## 흔한 잘못

- 정확성을 확인하지 않고 처리량만 기록합니다.
- 평균만 보고 p95, p99와 최대값을 숨깁니다.
- 첫 실행이 실패한 뒤 제외 규칙을 바꿉니다.
- 오류와 버린 작업을 완료 수에 포함합니다.
- 환경과 release 조합을 기록하지 않습니다.
- sample이 부족한데 PASS나 FAIL로 단정합니다.
- 여러 설정을 한꺼번에 바꾸고 한 설정의 효과라고 주장합니다.

## 검증 방법

판정기는 다음을 구분해야 합니다.

- 필요한 반복 수, 정확한 효과 수와 시간 조건을 만족함: `PASS`
- 중복 효과, 누락, 오류나 시간 초과가 있음: `FAIL`
- 반복 수나 환경 정보가 부족함: `UNVERIFIED`
- 서로 다른 환경의 실행이 섞임: `UNVERIFIED`

실제 percentile을 판단한다면 모든 run의 원시 지연 값이나 사전에 정한 집계값도 보존해야 합니다.

## 관련 프로젝트

[`performance-gate`](../../exercises/performance-gate/)는 반복 수, 동일 환경, 업무 효과 수와 최대 경과 시간을 사용해 `PASS`, `FAIL`, `UNVERIFIED`를 반환합니다.

## 완료 기준

- 목표와 측정값을 별도로 기록할 수 있습니다.
- 측정 결과를 commit과 실행 환경에 연결할 수 있습니다.
- 정확성 검사를 시간 검사보다 먼저 수행할 수 있습니다.
- 근거가 부족한 경우 `UNVERIFIED`로 남길 수 있습니다.
