# 마이그레이션과 트랜잭션

애플리케이션 코드와 데이터베이스 스키마는 항상 같은 순간에 바뀌는 것이 아닙니다. 배포 중에는 이전 코드와 새 코드가 잠시 함께 실행될 수 있고, 데이터베이스에는 이미 운영 데이터가 들어 있습니다.

이때 스키마 변경 순서가 사람의 기억이나 문서에만 남아 있으면 환경마다 데이터베이스 구조가 달라질 수 있습니다. 또한 하나의 비즈니스 작업을 이루는 여러 쓰기가 각각 따로 커밋되면 중간 실패 뒤 일부만 반영된 상태가 남을 수 있습니다.

이 문서에서는 두 가지 문제를 구분합니다.

```text
마이그레이션
→ 데이터베이스 구조와 데이터의 변경 이력을 순서대로 관리

트랜잭션
→ 하나의 작업에 속한 여러 데이터베이스 연산의 원자성을 관리
```

예시는 PostgreSQL과 Kysely를 사용하는 애플리케이션을 기준으로 합니다.

## 목표

- 마이그레이션 파일을 순서가 있는 변경 이력으로 관리합니다.
- 이미 적용된 마이그레이션을 임의로 수정하면 안 되는 이유를 설명합니다.
- 빈 데이터베이스와 기존 데이터가 있는 데이터베이스의 업그레이드 경로를 모두 검사합니다.
- 스키마 변경과 데이터 보정을 안전한 단계로 나눕니다.
- 큰 데이터 보정을 재시작 가능한 배치 작업으로 설계합니다.
- 함께 성공해야 하는 여러 쓰기를 하나의 트랜잭션으로 묶습니다.
- 트랜잭션을 너무 넓거나 너무 좁게 잡을 때의 문제를 설명합니다.
- 조건부 `UPDATE`, 제약 조건, 행 잠금과 격리 수준의 역할을 구분합니다.
- 교착 상태와 직렬화 실패를 트랜잭션 전체 단위로 제한적으로 재시도합니다.
- 코드 배포와 파괴적인 스키마 변경을 호환 가능한 단계로 나눕니다.

## 마이그레이션은 변경 이력입니다

마이그레이션(migration)은 데이터베이스를 이전 상태에서 다음 상태로 변경하는 **순서가 있는 변경 기록**입니다.

예를 들어 다음 파일들이 있다고 가정합니다.

```text
001_create_users.sql
002_create_notes.sql
003_add_note_version.sql
```

이 파일들은 단순히 현재 스키마를 설명하는 문서가 아닙니다.

```text
빈 데이터베이스
    ↓ 001
users 생성
    ↓ 002
notes 생성
    ↓ 003
notes.version 추가
    ↓
현재 스키마
```

새 환경은 이 변경들을 처음부터 순서대로 적용할 수 있고, 이전 버전까지 적용된 환경은 아직 적용하지 않은 변경만 이어서 적용할 수 있습니다.

### 현재 스키마와 변경 이력은 다릅니다

현재 스키마 덤프만 있으면 "현재 테이블이 어떻게 생겼는가"는 알 수 있지만 기존 환경을 현재 상태까지 **어떤 순서로 안전하게 변경할지**는 알 수 없습니다.

```text
현재 스키마
→ 지금의 최종 구조

마이그레이션 이력
→ 이전 구조를 최종 구조로 바꾸는 과정
```

운영 환경에서는 이미 존재하는 데이터, 잠금 시간, 이전 코드와의 호환성이 중요하므로 최종 구조만 아는 것으로는 충분하지 않습니다.

## 적용된 마이그레이션을 수정하지 않습니다

한 번 여러 환경에 적용된 마이그레이션 파일은 변경 이력의 일부로 취급합니다.

예를 들어 `003_add_note_version.sql`이 이미 운영에 적용된 뒤 파일 내용을 바꾸면 다음 상황이 생길 수 있습니다.

```text
오래된 운영 DB
→ 예전 003을 이미 적용함

새로 만든 개발 DB
→ 수정된 003을 적용함
```

두 환경은 파일 이름과 적용 번호는 같지만 실제 스키마가 달라질 수 있습니다.

따라서 이미 적용된 마이그레이션에 문제가 발견되면 일반적으로 기존 파일을 고치는 대신 **새 마이그레이션을 추가하여 현재 상태에서 바로잡습니다.**

```text
003_add_note_version.sql
004_fix_note_version_default.sql
```

이 원칙은 모든 환경이 같은 변경 순서를 따라갈 수 있게 합니다.

### 체크섬

마이그레이션 도구에 따라 적용한 파일의 체크섬을 기록하기도 합니다.

```text
migration id
+ 적용 시각
+ 파일 checksum
```

나중에 파일 내용이 바뀌면 기록된 체크섬과 현재 파일이 달라져 변경을 감지할 수 있습니다.

체크섬 기능이 없더라도 이미 배포된 파일을 불변 이력으로 취급하는 규칙은 유지하는 편이 안전합니다.

## 마이그레이션 실행기가 기록하는 정보

마이그레이션 실행기는 보통 별도의 메타데이터 테이블을 사용하여 어떤 변경이 이미 적용되었는지 기록합니다.

개념적으로 다음 정보가 있을 수 있습니다.

```text
식별자 또는 파일 이름
적용 순서
적용 시각
필요하면 체크섬
도구가 관리하는 기타 상태
```

예를 들어 현재 데이터베이스에 다음 이력이 있다면

```text
001_create_users.sql  applied
002_create_notes.sql  applied
```

실행기는 다음 배포에서 `001`, `002`를 다시 적용하는 대신 아직 적용되지 않은 `003`부터 실행합니다.

따라서 "마이그레이션을 여러 번 실행해도 안전해야 한다"는 말은 보통 **이미 적용된 파일을 실행기가 인식하고 다시 적용하지 않아야 한다**는 의미입니다.

모든 SQL 파일을 다음처럼 만들라는 뜻은 아닙니다.

```sql
-- 무조건 이렇게 만들 필요는 없음
create table if not exists ...
```

`IF NOT EXISTS`를 무분별하게 사용하면 예상과 다른 기존 객체가 있는데도 오류 없이 지나가 스키마 차이를 감출 수 있습니다.

## 마이그레이션은 한 곳에서 실행합니다

애플리케이션 서버 인스턴스가 여러 개라면 모든 인스턴스가 시작하면서 동시에 같은 마이그레이션을 실행하지 않도록 해야 합니다.

예를 들어 서버가 네 개 동시에 시작하면 다음 경쟁이 생길 수 있습니다.

```text
instance A ─┐
instance B ─┼─ 003 실행 시도
instance C ─┤
instance D ─┘
```

대표적인 방법은 다음과 같습니다.

- 배포 파이프라인의 별도 단계에서 한 번만 실행
- 마이그레이션 전용 작업(job)에서 실행
- 마이그레이션 도구가 제공하는 데이터베이스 잠금 사용

핵심은 **동일한 데이터베이스에 대한 스키마 변경 순서를 하나로 직렬화하는 것**입니다.

## 두 경로를 모두 검사합니다

마이그레이션은 최소한 두 종류의 경로에서 검사해야 합니다.

### 새 설치

```text
빈 데이터베이스
→ 001
→ 002
→ 003
→ ...
→ 현재 스키마
```

이 경로는 전체 이력이 처음부터 끝까지 정상적으로 적용되는지 확인합니다.

### 기존 환경 업그레이드

```text
이전 버전의 실제 스키마와 데이터
→ 새 마이그레이션만 적용
→ 현재 스키마
```

새 설치가 성공한다고 업그레이드도 성공하는 것은 아닙니다.

예를 들어 빈 테이블에서는 다음 변경이 문제가 없어 보일 수 있습니다.

```sql
alter table users
add column display_name text not null;
```

그러나 이미 행이 있는 테이블에서는 기존 행의 `display_name`에 어떤 값을 넣을지 정해져 있지 않으므로 실패하거나 안전하지 않은 변경이 될 수 있습니다.

```text
기존 행:
id = 1
email = "a@example.com"

새 NOT NULL 열 추가
display_name = ?
```

따라서 운영 데이터가 있는 환경을 고려한 변경 순서가 필요합니다.

## 스키마 변경과 데이터 변경을 구분합니다

마이그레이션에는 두 종류의 작업이 섞일 수 있습니다.

```text
스키마 변경
→ 테이블, 열, 제약 조건, 인덱스 변경

데이터 변경
→ 기존 행의 값을 새 구조에 맞게 보정
```

작은 테이블에서는 한 파일에서 함께 처리해도 충분할 수 있습니다. 그러나 큰 운영 테이블에서는 데이터 보정을 한 번의 거대한 트랜잭션으로 실행하는 것이 위험할 수 있습니다.

이때 스키마 변경과 대량 데이터 이관을 여러 단계로 분리합니다.

## 확장–이관–축소

이전 코드와 새 코드가 배포 중 동시에 실행될 가능성이 있다면 스키마 변경도 두 버전 모두 사용할 수 있는 상태를 거쳐야 합니다.

이를 흔히 **확장–이관–축소(expand–migrate–contract)** 방식으로 생각할 수 있습니다.

예를 들어 `users.name`을 `display_name`으로 바꾸려 한다고 가정합니다.

한 번에 다음 SQL만 실행하면

```sql
alter table users
rename column name to display_name;
```

새 코드에는 맞을 수 있지만 아직 실행 중인 이전 코드는 `name` 열을 찾다가 실패합니다.

보다 호환 가능한 변경은 여러 단계로 나눌 수 있습니다.

```text
1. 확장
   새 display_name 열 추가

2. 호환 코드 배포
   이전 열과 새 열을 함께 처리할 수 있게 함

3. 이관
   기존 행의 값을 display_name으로 보정

4. 쓰기 전환
   모든 새 쓰기를 display_name 기준으로 전환

5. 읽기 전환
   새 열만 읽도록 변경

6. 이전 코드 제거 확인

7. 축소
   더 이상 쓰지 않는 name 열 제거
```

각 단계 사이에는 실제 배포가 하나 이상 존재할 수 있습니다.

## 확장 단계에서는 이전 코드를 깨뜨리지 않습니다

확장 단계의 변경은 일반적으로 이전 코드가 계속 실행되어도 문제가 없어야 합니다.

예를 들어 새 열을 먼저 nullable로 추가할 수 있습니다.

```sql
alter table users
add column display_name text;
```

이전 코드는 이 열을 모르지만 기존 열을 계속 사용할 수 있습니다.

새 코드도 보정이 끝날 때까지 `display_name`이 `NULL`일 가능성을 처리합니다.

```text
이전 데이터
→ display_name = NULL 가능

새 데이터
→ 새 쓰기 정책에 따라 display_name 채움
```

## 데이터 이관 뒤 제약을 강화합니다

최종 목표가 `display_name NOT NULL`이라면 보통 순서를 다음처럼 잡습니다.

```text
1. nullable 열 추가
2. 새 쓰기에서 값을 채우기 시작
3. 기존 행 backfill
4. NULL이 남지 않았는지 검증
5. NOT NULL 제약 강화
```

중요한 것은 제약을 먼저 강하게 만들고 나서 데이터를 맞추려고 하지 않는 것입니다.

데이터가 이미 조건을 만족하는지 검증한 뒤 제약을 추가해야 배포 중 실패 가능성을 줄일 수 있습니다.

## 파괴적인 변경은 마지막에 합니다

다음 변경은 이전 코드와 호환되지 않을 가능성이 큽니다.

- 사용 중인 열 삭제
- 사용 중인 테이블 삭제
- 이전 코드가 기대하는 타입을 호환 불가능하게 변경
- 이전 코드가 사용하는 제약 의미를 갑자기 변경

따라서 이런 **축소(contract)** 단계는 새 코드가 충분히 배포되어 이전 코드가 더 이상 실행되지 않는다는 사실을 확인한 뒤 수행합니다.

```text
새 코드 배포
→ 안정성 확인
→ 이전 버전 인스턴스 없음 확인
→ 파괴적 스키마 변경
```

롤백 가능성을 유지해야 하는 환경에서는 특히 중요합니다.

## 코드 롤백과 데이터베이스 롤백은 같지 않습니다

애플리케이션 바이너리는 이전 버전으로 되돌리기 쉬울 수 있지만 데이터베이스 변경은 그렇지 않을 수 있습니다.

예를 들어 다음 작업 뒤에는

```text
열 삭제
→ 데이터도 함께 사라짐
```

단순히 이전 마이그레이션을 역순으로 실행한다고 원래 데이터를 되살릴 수 없습니다.

따라서 운영에서는 항상 "down migration이 있으니 안전하다"고 가정하지 않습니다.

변경에 따라 다음 전략을 선택할 수 있습니다.

```text
호환 가능한 확장 단계 유지
→ 코드만 이전 버전으로 롤백 가능

문제가 있는 스키마 변경
→ 새 forward migration으로 수정

파괴적 변경
→ 백업/복구 전략까지 필요
```

다운 마이그레이션은 개발과 테스트에서 유용할 수 있지만 실제 운영 데이터 손실 가능성을 별도로 평가해야 합니다.

## PostgreSQL DDL도 잠금을 얻습니다

스키마 변경 SQL도 다른 쿼리와 독립적으로 실행되는 것이 아닙니다. PostgreSQL의 여러 `ALTER TABLE` 작업은 테이블 수준의 강한 잠금을 필요로 할 수 있습니다.

따라서 큰 운영 테이블에서 다음과 같은 변경은 단순히 SQL 문법이 맞는지만 확인해서는 충분하지 않습니다.

```sql
alter table notes
...
```

검토해야 할 항목은 다음과 같습니다.

- 어떤 잠금을 획득하는가
- 잠금을 얼마나 오래 유지하는가
- 기존 읽기·쓰기를 얼마나 차단하는가
- 테이블 전체 재작성 여부가 있는가
- 운영 데이터 규모에서 실행 시간이 어느 정도인가

작은 개발 데이터베이스에서 즉시 끝난 DDL이 운영에서는 오랫동안 잠금을 기다리거나 다른 요청을 막을 수 있습니다.

## 마이그레이션의 트랜잭션 경계

PostgreSQL의 많은 DDL은 트랜잭션 안에서 실행할 수 있습니다.

예를 들어 도구가 다음처럼 하나의 마이그레이션을 트랜잭션으로 감싸면

```text
BEGIN
  ALTER ...
  CREATE ...
COMMIT
```

중간 SQL이 실패했을 때 앞선 변경도 함께 롤백할 수 있습니다.

그러나 **모든 PostgreSQL 작업을 항상 하나의 일반 트랜잭션 안에서 실행할 수 있는 것은 아닙니다.**

대표적으로 `CREATE INDEX CONCURRENTLY`는 일반적인 트랜잭션 블록 안에서 실행할 수 없습니다.

```sql
create index concurrently ...
```

따라서 마이그레이션 도구가 파일마다 자동 트랜잭션을 사용하는지, 특정 마이그레이션에서 트랜잭션을 끌 수 있는지 확인해야 합니다.

```text
일반 migration
→ 가능하면 트랜잭션으로 원자적으로 적용

CONCURRENTLY 등 특수 작업
→ 해당 명령의 트랜잭션 제약을 따름
```

트랜잭션을 사용할 수 없는 마이그레이션에서는 중간 실패 뒤 어떤 상태가 남는지와 재실행·복구 절차를 더 명확히 설계해야 합니다.

## 인덱스 추가도 운영 영향을 고려합니다

큰 테이블에서 일반 `CREATE INDEX`가 쓰기나 다른 작업에 주는 영향을 줄여야 할 때 PostgreSQL의 동시 인덱스 생성 기능을 고려할 수 있습니다.

```sql
create index concurrently
  notes_owner_updated_idx
on notes (owner_id, updated_at desc);
```

`CONCURRENTLY`는 일반 인덱스 생성보다 운영 중 차단을 줄이기 위한 기능이지만 다음과 같은 대가가 있습니다.

- 더 오래 걸릴 수 있음
- 추가 작업이 필요함
- 일반 트랜잭션 블록 안에서 실행할 수 없음
- 실패했을 때 남는 인덱스 상태를 점검해야 할 수 있음

따라서 "인덱스 생성은 항상 안전하고 즉시 끝난다"고 가정하지 않습니다.

## 대량 데이터 보정

기존 데이터가 많은 테이블을 한 트랜잭션에서 모두 수정하면 여러 문제가 생길 수 있습니다.

```text
긴 트랜잭션
→ 많은 행 잠금
→ 다른 요청 대기 증가
→ WAL 증가
→ 복제 지연 가능
→ 실패 시 큰 작업 전체 재시도
```

따라서 큰 backfill은 작은 배치로 나누고 중단 뒤 다시 시작할 수 있게 설계합니다.

예를 들어 다음 작업은 아직 `display_name`이 없는 사용자를 일정 개수씩 선택해 보정합니다.

```sql
with batch as (
  select id
  from users
  where id > $1
    and display_name is null
  order by id
  limit $2
  for update skip locked
)
update users as u
set display_name = u.name
from batch
where u.id = batch.id
returning u.id;
```

여기서 `$1`은 이전 배치에서 처리한 마지막 기준 키, `$2`는 배치 크기입니다.

## 배치 기준 키는 안정적이어야 합니다

재시작 위치를 저장하려면 기준 키가 안정적인 전체 순서를 만들 수 있어야 합니다.

```text
batch 1
id > cursor
order by id
limit 500

마지막 id 저장
    ↓
batch 2
id > saved_cursor
...
```

기준 키가 중복될 수 있다면 고유한 보조 키까지 함께 사용해야 합니다.

예를 들어 시간 열이 중복될 수 있다면

```sql
order by created_at, id
```

처럼 `(created_at, id)` 조합을 커서로 사용할 수 있습니다.

중요한 것은 기준 키가 "생성 순서"를 뜻해야 한다는 것이 아니라 **배치 진행 위치를 빠뜨리거나 반복하지 않고 표현할 수 있는 안정적인 정렬 기준**이어야 한다는 점입니다.

## 보정 작업은 가능하면 멱등적으로 만듭니다

배치 작업이 중간에 중단되면 일부 행은 이미 처리되었고 나머지는 처리되지 않았을 수 있습니다.

다시 실행해도 이미 처리된 행을 망가뜨리지 않도록 조건을 명확히 둡니다.

```sql
where display_name is null
```

이 조건이 있다면 이미 값을 채운 행은 다음 실행에서 제외됩니다.

이처럼 같은 작업을 다시 수행해도 이미 완료된 결과를 깨뜨리지 않는 성질을 **멱등성(idempotency)**이라고 합니다.

대량 이관에서는 재시작 가능성을 높이는 중요한 속성입니다.

## `SKIP LOCKED`의 의미

다음 절은 선택한 행을 잠급니다.

```sql
for update skip locked
```

`FOR UPDATE`는 다른 트랜잭션이 같은 행을 동시에 수정하지 못하도록 행 잠금을 얻습니다.

`SKIP LOCKED`는 이미 다른 트랜잭션이 잠근 행을 기다리지 않고 건너뜁니다.

따라서 여러 worker가 같은 backfill을 병렬로 수행할 때 유용할 수 있습니다.

```text
worker A
→ rows 1~500 잠금

worker B
→ A가 잠근 행은 건너뛰고 다른 행 선택
```

다만 `SKIP LOCKED`는 일반 조회에서 "현재 존재하는 모든 행을 정확히 읽는다"는 의미를 보장하기 위한 기능이 아닙니다. 잠긴 행을 의도적으로 누락시키므로 작업 큐나 병렬 배치처럼 누락된 행을 나중에 다시 처리할 수 있는 용도에 적합합니다.

worker가 하나뿐이라면 반드시 필요한 것은 아닙니다.

## 배치 사이에서 커밋합니다

대량 보정의 목적은 거대한 트랜잭션 하나를 만드는 것이 아니라 작은 단위로 진행하는 것입니다.

```text
500행 선택
→ UPDATE
→ COMMIT
→ cursor 저장
→ 다음 500행
```

한 배치가 실패하면 마지막으로 성공한 지점부터 다시 시작할 수 있습니다.

배치 크기는 무조건 큰 값이나 작은 값이 정답이 아닙니다. 운영 부하, 한 행의 수정 비용, 잠금 시간과 전체 처리 시간을 측정해 조정합니다.

## 트랜잭션

트랜잭션(transaction)은 여러 SQL 작업을 하나의 논리적 작업 단위로 묶습니다.

메모 수정과 활동 기록이 항상 함께 존재해야 한다고 가정합니다.

```ts
await db.transaction().execute(async (trx) => {
  const note = await updateNoteIfCurrent(
    trx,
    command
  );

  if (!note) {
    throw new VersionConflict();
  }

  await appendActivity(trx, {
    noteId: note.id,
    actorId: command.actorId,
    version: note.version,
    occurredAt: clock.now()
  });
});
```

정상적으로 콜백이 끝나면 커밋됩니다.

```text
UPDATE note 성공
INSERT activity 성공
→ COMMIT
```

두 번째 쓰기에서 오류가 발생해 콜백이 실패하면 전체 트랜잭션이 롤백됩니다.

```text
UPDATE note 성공
INSERT activity 실패
→ ROLLBACK
→ note 변경도 남지 않음
```

이것이 트랜잭션의 원자성(atomicity)입니다. 작업 전체를 데이터베이스 관점에서 성공 또는 실패 중 하나로 만듭니다.

## 커밋 전 변경은 확정된 결과가 아닙니다

트랜잭션 안에서 `UPDATE`가 성공했다고 그 값이 이미 최종적으로 저장되었다는 뜻은 아닙니다.

```text
BEGIN
UPDATE 성공
INSERT 성공
COMMIT 성공
→ 최종 반영
```

`COMMIT` 전에 오류가 발생해 롤백되면 앞선 변경은 사라집니다.

따라서 트랜잭션 안에서 얻은 중간 성공을 외부 시스템에 "이미 확정된 사실"처럼 알려 버리면 문제가 생길 수 있습니다.

## 트랜잭션 안에서는 같은 `trx`를 사용합니다

Kysely의 관리형 트랜잭션에서는 콜백으로 전달된 `trx` 객체를 사용합니다.

```ts
await db.transaction().execute(async (trx) => {
  await updateNote(trx);
  await appendActivity(trx);
});
```

트랜잭션 안에서 일부 작업을 바깥 `db`로 실행하면 해당 쿼리가 같은 트랜잭션에 포함되지 않을 수 있습니다.

```ts
await db.transaction().execute(async (trx) => {
  await updateNote(trx);

  // 잘못된 경계를 만들 수 있음
  await appendActivity(db);
});
```

이 경우 두 쓰기가 하나의 원자적 작업이라는 보장이 깨집니다.

저장소 함수가 트랜잭션을 받아 실행될 수 있도록 의존성을 설계합니다.

## 너무 짧은 트랜잭션

함께 성공해야 하는 작업을 각각 커밋하면 부분 성공이 남을 수 있습니다.

```text
트랜잭션 A
메모 수정
→ COMMIT

트랜잭션 B
활동 기록
→ 실패
```

최종 상태:

```text
메모는 변경됨
활동 기록은 없음
```

이 두 데이터가 반드시 함께 존재해야 한다는 불변 조건이 있다면 트랜잭션 범위가 너무 짧은 것입니다.

## 너무 긴 트랜잭션

반대로 트랜잭션 안에서 필요하지 않은 긴 작업까지 수행하면 연결과 잠금을 오래 점유합니다.

```text
BEGIN
행 잠금 획득
외부 API 요청
10초 대기
추가 UPDATE
COMMIT
```

그동안 같은 행이나 관련 자원을 사용하려는 다른 트랜잭션은 기다릴 수 있습니다.

긴 트랜잭션은 다음 문제를 키울 수 있습니다.

- 잠금 대기 시간 증가
- 교착 상태 가능성 증가
- 연결 풀 점유 시간 증가
- 실패했을 때 다시 수행할 작업 증가
- 오래된 트랜잭션으로 인한 데이터베이스 유지보수 부담 증가

따라서 트랜잭션은 **데이터베이스 안에서 함께 지켜야 하는 값을 변경하는 가장 짧은 범위**로 제한합니다.

## 트랜잭션 안에서 외부 API를 기다리지 않습니다

다음 작업은 PostgreSQL 트랜잭션이 제어할 수 없습니다.

- HTTP API 호출
- 이메일 발송
- 메시지 브로커 전송
- 파일 업로드
- 다른 데이터베이스의 독립된 트랜잭션

예를 들어 다음 순서라면 문제가 있습니다.

```text
BEGIN
DB UPDATE
이메일 전송 성공
DB INSERT 실패
ROLLBACK
```

데이터베이스 변경은 롤백되었지만 이미 발송된 이메일은 PostgreSQL이 취소할 수 없습니다.

따라서 외부 부수 효과를 데이터베이스 트랜잭션 안에 넣는 것만으로 원자성이 생긴다고 생각하지 않습니다.

## 동시 실행에서 생기는 문제

트랜잭션을 사용한다고 모든 동시성 문제가 자동으로 사라지는 것은 아닙니다.

여러 트랜잭션이 동시에 실행되면 다음 문제가 생길 수 있습니다.

- 같은 값을 읽은 뒤 각각 수정해 한쪽 변경이 사라짐
- 두 행의 조합으로 지켜야 하는 규칙이 깨짐
- 같은 고유 값을 동시에 만들려고 함
- 서로 상대방이 가진 잠금을 기다려 교착 상태가 됨
- 직렬화 가능 격리에서 직렬화 실패가 발생함

어떤 문제를 막으려는지 먼저 정의한 뒤 적절한 데이터베이스 기능을 선택합니다.

## 제약 조건과 잠금은 역할이 다릅니다

예를 들어 "같은 좌석은 한 번만 예약할 수 있다"는 규칙은 데이터베이스의 고유 제약으로 표현할 수 있습니다.

```sql
unique (show_id, seat_id)
```

두 요청이 동시에 같은 좌석을 예약하더라도 최종적으로 중복 상태를 저장하지 못하게 합니다.

반면 "현재 카운터 값을 읽어서 다음 번호를 계산하고 저장"하는 작업은 행을 잠그고 직렬화해야 할 수 있습니다.

```sql
select next_sequence
from board_counters
where board_id = $1
for update;
```

기능별로 생각하면 다음과 같습니다.

```text
UNIQUE / CHECK / FOREIGN KEY
→ 허용되지 않는 최종 상태를 데이터베이스가 거부

조건부 UPDATE
→ 읽었던 버전이 아직 최신인지 쓰는 순간 확인

FOR UPDATE
→ 선택한 행을 다른 트랜잭션의 경쟁 수정과 직렬화

SERIALIZABLE
→ 트랜잭션들의 결과가 어떤 직렬 실행과 일치하도록 검사
```

가장 강한 잠금을 무조건 사용하는 것이 아니라 실제 불변 조건에 맞는 가장 단순한 방법을 선택합니다.

## 조건부 `UPDATE`

오래된 값을 기준으로 한 쓰기를 막는 데에는 버전 조건이 간단하고 효과적일 수 있습니다.

```sql
update notes
set title = $1,
    version = version + 1
where id = $2
  and version = $3;
```

두 요청이 모두 `version = 5`를 읽었다고 가정합니다.

```text
A: version 5로 UPDATE
→ 성공, version 6

B: version 5로 UPDATE
→ 일치하는 행 0개
```

이 방식은 행을 먼저 잠그고 기다리게 하기보다 충돌을 쓰기 시점에 감지하는 낙관적 동시성 제어입니다.

## `FOR UPDATE` 행 잠금

다음 쿼리는 선택한 행에 대한 갱신 목적의 잠금을 획득합니다.

```sql
select next_sequence
from board_counters
where board_id = $1
for update;
```

일반적인 흐름은 다음과 같습니다.

```text
BEGIN

SELECT ... FOR UPDATE
→ 대상 행 잠금

값 계산

UPDATE 같은 행

COMMIT
→ 잠금 해제
```

다른 트랜잭션이 충돌하는 방식으로 같은 행을 잠그려 하면 현재 트랜잭션이 끝날 때까지 기다릴 수 있습니다.

### 잠금은 트랜잭션이 끝날 때까지 유지됩니다

`FOR UPDATE` 쿼리가 끝났다고 잠금이 바로 풀리는 것은 아닙니다.

```text
SELECT ... FOR UPDATE 완료
→ 잠금 유지

다른 SQL 실행
→ 잠금 유지

COMMIT 또는 ROLLBACK
→ 잠금 해제
```

따라서 잠금을 얻은 뒤 외부 API를 기다리는 것처럼 트랜잭션을 오래 유지하면 다른 요청의 대기 시간도 길어집니다.

## 여러 행을 잠글 때 순서를 통일합니다

두 트랜잭션이 서로 반대 순서로 행을 잠그면 교착 상태(deadlock)가 생길 수 있습니다.

```text
트랜잭션 A                트랜잭션 B

row 1 잠금                row 2 잠금
row 2 필요                row 1 필요
    ↓                         ↓
B를 기다림                A를 기다림
```

둘 다 상대방이 잠금을 풀기를 기다리므로 진행할 수 없습니다.

PostgreSQL은 이런 교착 상태를 감지하면 한 트랜잭션을 중단시켜 문제를 해소합니다.

가능하면 여러 자원을 잠그는 모든 코드 경로에서 일관된 순서를 사용합니다.

```text
항상 작은 id부터 잠금
또는
항상 account A → account B 순서
```

잠금 순서를 통일하면 교착 상태 가능성을 줄일 수 있지만 모든 교착 상태를 논리적으로 불가능하게 만든다고 단정할 수는 없습니다. 따라서 오류 처리도 필요합니다.

## 격리 수준

트랜잭션 격리 수준은 동시에 실행되는 트랜잭션이 서로의 변경을 어떤 방식으로 관찰하는지 결정합니다.

PostgreSQL의 기본 격리 수준은 일반적으로 `READ COMMITTED`입니다.

더 강한 격리가 필요한 규칙에서는 `REPEATABLE READ`나 `SERIALIZABLE`을 고려할 수 있습니다.

특히 `SERIALIZABLE`은 여러 트랜잭션을 동시에 실행하더라도 결과가 어떤 직렬 실행 순서와 모순되지 않도록 PostgreSQL이 검사합니다.

그 과정에서 안전하게 직렬화할 수 없다고 판단하면 한 트랜잭션을 실패시킬 수 있습니다.

```text
동시에 실행
A ─────────
B ─────────

PostgreSQL 검사
→ 둘을 모두 성공시키면 직렬 실행 결과와 모순
→ 하나를 serialization failure로 중단
```

따라서 격리 수준을 높인다고 "실패가 절대 일어나지 않는다"는 뜻은 아닙니다. 오히려 특정 동시성 충돌을 오류로 감지하고 애플리케이션이 재시도하도록 만드는 전략이 될 수 있습니다.

## 교착 상태와 직렬화 실패

PostgreSQL에서 대표적인 재시도 후보 오류는 다음과 같습니다.

```text
40P01
→ deadlock_detected

40001
→ serialization_failure
```

두 경우 모두 보통 현재 트랜잭션은 계속 사용할 수 없고 롤백됩니다.

중요한 점은 **실패한 SQL 한 문장만 다시 실행하는 것이 아니라 논리적 트랜잭션 전체를 처음부터 다시 실행해야 한다**는 것입니다.

```text
시도 1

BEGIN
  SELECT ...
  UPDATE ...
  INSERT ...
  → 40001
ROLLBACK

시도 2

BEGIN
  처음부터 다시 SELECT ...
  UPDATE ...
  INSERT ...
COMMIT
```

첫 시도에서 읽었던 값이 재시도 시점에는 달라졌을 수 있기 때문입니다.

## 재시도 가능한 조건

재시도는 다음 조건을 만족할 때만 수행합니다.

- 오류가 실제로 재시도 가능한 종류입니다.
- 트랜잭션 전체를 처음부터 다시 실행할 수 있습니다.
- 첫 시도의 부분 변경은 롤백됩니다.
- 트랜잭션 안에서 되돌릴 수 없는 외부 부수 효과를 만들지 않았습니다.
- 최대 시도 횟수가 정해져 있습니다.
- 전체 시간 제한이 있습니다.
- 여러 요청이 즉시 동시에 재시도하지 않도록 지연 전략이 있습니다.

예를 들어 다음처럼 생각할 수 있습니다.

```text
attempt 1
→ 충돌

짧은 지연 + jitter

attempt 2
→ 충돌

더 긴 지연 + jitter

attempt 3
→ 성공 또는 최종 실패
```

jitter는 여러 요청이 같은 정확한 시간에 다시 실행되어 다시 충돌하는 현상을 줄이기 위한 무작위 지연 요소입니다.

## 모든 오류를 재시도하지 않습니다

다음 오류는 단순 재시도로 해결되지 않습니다.

```text
NOT NULL 위반
CHECK 위반
잘못된 SQL
인증 실패
애플리케이션 검증 오류
영구적인 UNIQUE 충돌
```

예를 들어 사용자가 이미 존재하는 이메일을 계속 삽입하려 한다면 같은 `INSERT`를 10번 반복해도 성공하지 않습니다.

따라서 "데이터베이스 오류"라는 큰 범주만 보고 재시도하지 않고 SQLSTATE와 애플리케이션 의미를 확인합니다.

## 재시도 함수 안의 코드는 다시 실행됩니다

트랜잭션 전체를 재시도한다는 것은 트랜잭션 콜백 안의 애플리케이션 코드도 다시 실행될 수 있다는 뜻입니다.

예를 들어 다음 값은 재시도마다 달라질 수 있습니다.

```text
현재 시각 읽기
랜덤 ID 생성
외부 카운터 증가
로그 외의 외부 부수 효과
```

재시도 시 같은 값이 필요하다면 트랜잭션 밖에서 미리 생성하거나 의도적으로 다시 계산해야 하는지 정책을 정합니다.

특히 이메일 전송이나 외부 결제 요청처럼 중복 실행이 위험한 작업을 재시도 가능한 트랜잭션 콜백 안에 두지 않습니다.

## 데이터베이스 밖의 작업

PostgreSQL 트랜잭션은 같은 데이터베이스 안의 변경만 원자적으로 커밋하거나 롤백할 수 있습니다.

예를 들어 다음 두 작업은 한 PostgreSQL 트랜잭션만으로 완전한 원자성을 만들 수 없습니다.

```text
1. PostgreSQL에 주문 저장
2. 메시지 브로커에 "주문 생성" 전송
```

가능한 실패 순서는 다음과 같습니다.

```text
DB COMMIT 성공
→ 메시지 전송 실패
```

또는 순서를 바꾸면

```text
메시지 전송 성공
→ DB COMMIT 실패
```

가 될 수 있습니다.

따라서 데이터베이스 밖의 시스템까지 확실한 전달을 보장하려면 실패 상태를 저장하고 재처리할 수 있는 별도의 패턴이 필요합니다.

대표적으로 같은 데이터베이스 트랜잭션 안에 "보내야 할 메시지"를 outbox 행으로 저장한 뒤 별도 worker가 전송하는 방식이 있습니다.

```text
DB transaction
  주문 저장
  outbox 저장
COMMIT

별도 worker
  outbox 읽기
  메시지 전송
  전송 완료 기록
```

이 문서에서는 분산 전달 자체를 깊게 다루지 않지만, **외부 전송을 DB 트랜잭션 안에 넣었다고 원자성이 생기는 것은 아니다**라는 경계는 명확히 이해해야 합니다.

## 마이그레이션과 애플리케이션 배포 순서

스키마와 코드가 서로 의존하면 배포 순서를 명시해야 합니다.

예를 들어 새 열이 필요한 코드를 먼저 배포하면 아직 열이 없는 데이터베이스에서 실패할 수 있습니다.

```text
새 코드
→ display_name SELECT
→ DB에는 display_name 없음
→ 오류
```

반대로 기존 코드가 여전히 사용하는 열을 데이터베이스에서 먼저 제거해도 실패합니다.

```text
DB에서 name 삭제
→ 이전 코드가 name SELECT
→ 오류
```

따라서 배포 계획을 다음처럼 구성할 수 있습니다.

```text
배포 1
호환 가능한 스키마 확장

배포 2
이전·새 스키마를 함께 처리하는 코드

배포 3
데이터 이관

배포 4
새 스키마만 사용하는 코드

배포 5
이전 코드가 사라진 뒤 스키마 축소
```

실제 단계 수는 변경 크기에 따라 줄거나 늘어날 수 있습니다.

## 데이터 보정과 서비스 코드의 경쟁

backfill이 실행되는 동안 애플리케이션도 같은 행을 수정할 수 있습니다.

예를 들어 backfill이 오래된 `name` 값을 읽어 `display_name`에 복사하는 사이에 사용자가 이름을 변경한다면 새 값을 다시 오래된 값으로 덮어쓰는 문제가 생길 수 있습니다.

따라서 이관 기간의 쓰기 정책을 함께 설계해야 합니다.

대표적인 방법은 다음과 같습니다.

```text
dual write
→ 일정 기간 이전 열과 새 열을 함께 갱신

조건부 backfill
→ 아직 새 값이 없는 행만 보정

애플리케이션 쓰기 전환
→ backfill과 충돌하지 않는 순서로 배포
```

단순히 "배치 SQL을 한 번 실행하면 된다"가 아니라 **이관 중에도 서비스 쓰기가 계속 발생한다는 사실**을 고려합니다.

## 마이그레이션 실패 뒤 상태를 확인합니다

마이그레이션이 실패했을 때 남은 상태는 트랜잭션 여부에 따라 달라질 수 있습니다.

트랜잭션으로 완전히 감싸진 마이그레이션이라면

```text
statement A 성공
statement B 실패
→ 전체 ROLLBACK
```

이 될 수 있습니다.

트랜잭션 밖에서 실행해야 하는 작업이 포함되어 있다면

```text
step A 완료
step B 실패
→ A가 이미 남아 있을 수 있음
```

따라서 실패 뒤에는 단순히 같은 명령을 다시 누르기 전에 다음을 확인합니다.

- 어떤 단계까지 실제로 적용되었는가
- 실행기 메타데이터에는 무엇이 기록되었는가
- 부분적으로 만들어진 객체가 있는가
- 새 forward migration이 필요한가
- 안전하게 재실행할 수 있는가

## 검증 항목

마이그레이션과 트랜잭션 기능은 다음 항목을 실제 PostgreSQL에서 검사합니다.

### 마이그레이션

- 빈 데이터베이스에 모든 파일을 처음부터 적용할 수 있는가
- 이전 버전 스키마와 실제 데이터를 현재 버전으로 업그레이드할 수 있는가
- 이미 적용된 파일을 실행기가 다시 적용하지 않는가
- 적용된 마이그레이션 파일이 변경되었을 때 체크섬 정책이 있다면 감지하는가
- 기존 데이터가 있는 상태에서 새 제약 조건을 추가할 수 있는가
- 대량 backfill을 중단한 뒤 안전하게 이어서 실행할 수 있는가
- DDL이 운영 규모의 테이블에 주는 잠금 영향을 검토했는가
- 트랜잭션을 사용할 수 없는 마이그레이션이 실패했을 때 복구 절차가 있는가
- 이전 코드와 새 코드가 배포 중 동시에 실행되어도 호환되는가

### 트랜잭션

- 첫 번째 쓰기 성공 뒤 두 번째 쓰기를 실패시키면 전체가 롤백되는가
- 트랜잭션 안의 모든 쿼리가 같은 `trx`를 사용하는가
- 같은 자원을 수정하는 경쟁 요청에서 불변 조건이 유지되는가
- 버전 조건이 오래된 `UPDATE`를 거부하는가
- 행 잠금이 필요한 작업에서 기대한 순서로 직렬화되는가
- 교착 상태나 직렬화 실패를 올바른 SQLSTATE로 분류하는가
- 재시도 시 SQL 한 문장이 아니라 트랜잭션 전체를 다시 실행하는가
- 최대 재시도 횟수와 시간 제한이 적용되는가
- 테스트 종료 뒤 연결 풀과 테스트 데이터베이스 리소스를 정리하는가

## 흔한 실수

- 이미 적용된 마이그레이션 파일을 수정합니다.
- 현재 스키마 덤프만 보관하고 변경 순서를 남기지 않습니다.
- 모든 마이그레이션 SQL에 무조건 `IF NOT EXISTS`를 붙이면 안전하다고 생각합니다.
- 여러 애플리케이션 인스턴스가 동시에 마이그레이션을 실행하게 둡니다.
- 빈 데이터베이스에서만 마이그레이션을 검사하고 기존 데이터가 있는 업그레이드 경로를 검사하지 않습니다.
- 기존 데이터 보정 전에 바로 `NOT NULL` 같은 강한 제약을 추가합니다.
- 이전 코드가 아직 실행 중인데 열이나 테이블을 제거합니다.
- 애플리케이션 롤백이 가능하므로 파괴적인 데이터베이스 변경도 쉽게 되돌릴 수 있다고 생각합니다.
- 작은 개발 데이터에서 빨리 끝난 `ALTER TABLE`이 운영에서도 무조건 안전하다고 생각합니다.
- 모든 PostgreSQL DDL이 항상 일반 트랜잭션 안에서 실행 가능하다고 생각합니다.
- 큰 데이터 보정을 한 트랜잭션에서 전부 실행합니다.
- backfill이 중간에 실패한 뒤 어디서부터 재시작할지 정하지 않습니다.
- `SKIP LOCKED`를 사용하면 모든 행을 정확히 한 번 읽는 일반 조회가 된다고 생각합니다.
- 트랜잭션 안에서 일부 쿼리를 바깥 `db`로 실행합니다.
- 함께 성공해야 하는 쓰기를 서로 다른 트랜잭션에서 커밋합니다.
- 행 잠금을 얻은 채 외부 API나 이메일 응답을 기다립니다.
- 트랜잭션을 쓰기만 하면 모든 동시성 문제가 자동으로 해결된다고 생각합니다.
- 실제 규칙은 고유 제약으로 표현할 수 있는데 애플리케이션의 선행 조회만 사용합니다.
- 여러 행을 서로 다른 순서로 잠가 교착 상태 가능성을 키웁니다.
- `40001`이나 `40P01`에서 실패한 SQL 문장 하나만 재시도합니다.
- 모든 데이터베이스 오류를 무제한 재시도합니다.
- 재시도 가능한 트랜잭션 안에서 되돌릴 수 없는 외부 부수 효과를 실행합니다.
- PostgreSQL 커밋과 외부 메시지 전송을 하나의 로컬 트랜잭션으로 원자화할 수 있다고 생각합니다.

## 완료 기준

- 마이그레이션이 현재 스키마가 아니라 순서가 있는 변경 이력이라는 점을 설명할 수 있습니다.
- 이미 적용한 마이그레이션 파일을 수정하지 않고 새 파일로 수정 사항을 추가할 수 있습니다.
- 마이그레이션 실행기가 적용 이력을 기록하고 이미 적용된 파일을 구분하는 이유를 설명할 수 있습니다.
- 빈 데이터베이스의 새 설치와 실제 데이터가 있는 업그레이드 경로를 모두 검사할 수 있습니다.
- 확장–이관–축소 방식으로 이전 코드와 새 코드가 공존 가능한 스키마 변경 순서를 설계할 수 있습니다.
- 기존 데이터 보정 뒤에 `NOT NULL` 같은 제약을 강화해야 하는 이유를 설명할 수 있습니다.
- 파괴적인 스키마 변경과 애플리케이션 코드 롤백의 관계를 설명할 수 있습니다.
- PostgreSQL DDL도 잠금을 획득할 수 있으며 운영 데이터 규모에서 영향을 검토해야 한다는 점을 설명할 수 있습니다.
- 일반 트랜잭션 안에서 실행할 수 없는 PostgreSQL 작업이 있을 수 있음을 설명할 수 있습니다.
- 큰 backfill을 안정적인 기준 키와 작은 배치로 나누고 중단 뒤 재시작할 수 있습니다.
- `FOR UPDATE SKIP LOCKED`가 병렬 worker에서 어떤 역할을 하는지 설명할 수 있습니다.
- 함께 성공해야 하는 여러 데이터베이스 쓰기를 하나의 트랜잭션으로 묶을 수 있습니다.
- 트랜잭션 안에서는 같은 `trx`를 사용해야 하는 이유를 설명할 수 있습니다.
- 트랜잭션의 범위가 너무 짧거나 너무 길 때 생기는 문제를 설명할 수 있습니다.
- 제약 조건, 조건부 `UPDATE`, `FOR UPDATE`, 격리 수준의 역할을 구분할 수 있습니다.
- 여러 행의 잠금 순서를 통일하면 교착 상태 가능성을 줄일 수 있는 이유를 설명할 수 있습니다.
- `40001`과 `40P01`을 트랜잭션 전체 단위의 제한적 재시도 후보로 처리할 수 있습니다.
- 재시도 가능한 작업 안에 외부 부수 효과를 넣으면 안 되는 이유를 설명할 수 있습니다.
- PostgreSQL 트랜잭션이 외부 메시지 전송까지 원자적으로 롤백할 수 없다는 경계를 설명할 수 있습니다.
