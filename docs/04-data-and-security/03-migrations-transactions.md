# 마이그레이션과 트랜잭션

애플리케이션 코드와 데이터베이스 스키마는 서로 다른 시점에 배포될 수 있습니다. 스키마 변경 순서가 문서에만 남아 있거나 여러 쓰기가 따로 커밋되면 중간 실패 뒤 일관되지 않은 상태가 남습니다.

## 목표

- 마이그레이션 파일을 순서가 있는 변경 이력으로 관리합니다.
- 빈 데이터베이스와 기존 데이터가 있는 데이터베이스에서 모두 검사합니다.
- 함께 성공해야 하는 쓰기를 하나의 트랜잭션으로 묶습니다.
- 행 잠금, 교착 상태와 제한적인 재시도를 이해합니다.
- 코드 배포와 스키마 변경을 호환 가능한 단계로 나눕니다.

## 마이그레이션은 변경 이력입니다

```text
001_create_users.sql
002_create_notes.sql
003_add_note_version.sql
```

이미 적용한 파일을 나중에 수정하면 오래된 환경과 새 환경의 최종 스키마가 달라질 수 있습니다. 잘못된 변경은 새 파일을 추가해 바로잡습니다.

마이그레이션 실행기는 다음 정보를 기록합니다.

- 식별자와 적용 순서
- 적용 시각
- 필요하면 체크섬
- 실패 여부

여러 서버 인스턴스가 동시에 같은 마이그레이션을 실행하지 않게 잠금을 사용하거나 배포 단계에서 한 번만 실행합니다.

## 두 경로를 검사합니다

```text
빈 데이터베이스
→ 모든 파일 적용
→ 현재 스키마

이전 버전 데이터베이스
→ 새 파일만 적용
→ 현재 스키마
```

새 테이블만 있는 개발 환경에서는 성공해도 실제 행이 있는 운영 환경에서는 실패할 수 있습니다. 기존 값 보정 없이 `NOT NULL` 열을 추가하는 경우가 대표적입니다.

## 확장–이관–축소

하위 호환이 필요한 열 변경은 여러 배포로 나눌 수 있습니다.

1. 새 nullable 열을 추가합니다.
2. 새 코드가 이전 열과 새 열을 함께 읽을 수 있게 합니다.
3. 기존 행을 배치로 보정합니다.
4. 모든 쓰기를 새 열로 바꿉니다.
5. 이전 코드가 사라진 뒤 기존 열을 제거합니다.

한 번에 이름을 바꾸는 SQL은 간단하지만 이전 버전으로 롤백해야 하는 환경에서는 실패할 수 있습니다.

## 대량 데이터 보정

큰 테이블을 한 트랜잭션에서 모두 수정하면 잠금 시간과 WAL 크기가 커질 수 있습니다. 배치 기준 키와 재시작 위치를 저장하고 중단 뒤 이어서 실행할 수 있게 합니다.

```sql
with batch as (
  select id
  from users
  where id > $1
    and display_name is null
  order by id
  limit $2
  for update skip locked
)
update users as u
set display_name = u.name
from batch
where u.id = batch.id
returning u.id;
```

## 트랜잭션

메모 수정과 활동 기록이 함께 성공해야 한다고 가정합니다.

```ts
await db.transaction().execute(async (trx) => {
  const note = await updateNoteIfCurrent(trx, command);
  if (!note) throw new VersionConflict();

  await appendActivity(trx, {
    noteId: note.id,
    actorId: command.actorId,
    version: note.version,
    occurredAt: clock.now()
  });
});
```

두 번째 쓰기가 실패하면 첫 번째 쓰기도 롤백됩니다. 트랜잭션 안에서 외부 API, 이메일과 메시지 브로커 응답을 오래 기다리지 않습니다. 데이터베이스 트랜잭션이 원자적으로 바꿀 수 있는 것은 해당 데이터베이스의 값뿐입니다.

## 너무 짧거나 긴 트랜잭션

너무 짧으면 부분 성공이 남습니다.

```text
메모 수정 커밋
→ 활동 기록 실패
→ 감사 기록이 없는 변경
```

너무 길면 다른 요청이 같은 행의 잠금을 오래 기다립니다.

```text
행 잠금 획득
→ 외부 API 10초 대기
→ 다른 요청도 잠금 대기
```

데이터베이스에서 함께 지켜야 하는 값을 바꾸는 가장 짧은 범위로 제한합니다.

## 동시 실행과 잠금

동시에 실행되는 요청에서는 다음 문제가 생길 수 있습니다.

- 같은 값을 읽고 각각 수정해 한쪽 변경이 사라짐
- 서로 다른 행을 읽고 수정해 전체 규칙을 깨뜨림
- 잠금을 반대 순서로 얻어 교착 상태 발생
- 직렬화 실패

조건부 UPDATE, 고유 제약, `FOR UPDATE`, 직렬화 가능 격리 수준 중 실제로 지킬 규칙에 맞는 방법을 선택합니다.

```sql
select next_sequence
from board_counters
where board_id = $1
for update;
```

잠금은 트랜잭션이 끝날 때까지 유지됩니다. 여러 행을 잠글 때는 모든 코드에서 같은 순서로 처리합니다.

## 재시도 조건

교착 상태나 직렬화 실패를 재시도하려면 다음 조건을 모두 확인합니다.

- 트랜잭션 전체를 처음부터 다시 실행할 수 있습니다.
- 외부 부수 효과가 트랜잭션 안에 없습니다.
- 최대 시도 횟수와 전체 제한 시간이 있습니다.
- 재시도 가능한 데이터베이스 오류만 선택합니다.
- 여러 요청이 동시에 다시 충돌하지 않도록 지연을 둡니다.

모든 오류를 무제한 재시도하지 않습니다.

## 데이터베이스 밖의 작업

커밋과 외부 메시지 전송은 한 PostgreSQL 트랜잭션으로 묶을 수 없습니다. 커밋 뒤 전송이 실패할 수 있으므로 실패 상태를 저장하고 다시 처리할 방법이 필요합니다. 여러 서비스 사이의 확실한 전달은 별도의 분산 시스템 주제로 다룹니다.

## 검증 항목

- 빈 데이터베이스에 전체 파일 적용
- 이전 버전에서 업그레이드
- 같은 파일이 다시 실행될 때의 처리
- 중간 실패 뒤 남은 스키마
- 두 번째 쓰기 실패와 전체 롤백
- 같은 자원을 바꾸는 경쟁 요청
- 교착 상태·직렬화 실패의 처리
- 테스트 종료 뒤 연결 풀 정리

## 흔한 실수

- 이미 적용된 마이그레이션 파일을 수정합니다.
- 현재 스키마 덤프만 보관하고 변경 순서를 남기지 않습니다.
- 기존 데이터가 있는 업그레이드 경로를 검사하지 않습니다.
- 트랜잭션 안에서 외부 API를 호출합니다.
- 모든 데이터베이스 오류를 같은 방식으로 재시도합니다.
- 파괴적인 스키마 변경과 코드 배포를 한 번에 실행합니다.

## 완료 기준

- 적용한 마이그레이션 파일을 수정하지 않고 새 파일로 변경합니다.
- 새 설치와 업그레이드 경로를 모두 검사합니다.
- 여러 쓰기가 함께 성공하거나 롤백됩니다.
- 지킬 규칙에 맞는 제약 조건, 조건부 UPDATE 또는 잠금을 선택합니다.
- 안전하게 재시도할 수 있는 조건을 설명합니다.
