# 비밀번호, 세션과 쿠키

로그인은 크게 두 단계로 나뉩니다.

```text
1. 인증(authentication)
   → 사용자가 주장한 신원이 맞는지 확인

2. 세션 유지(session management)
   → 이후 요청에서도 같은 사용자인지 식별
```

비밀번호는 사용자의 신원을 확인하기 위한 장기 비밀이고, 세션 토큰은 로그인 이후의 요청을 인증하기 위한 임시 자격 증명입니다. 둘 다 유출되면 공격자가 사용자를 가장할 수 있으므로 저장, 전송, 로그 처리와 만료 정책을 명확히 정해야 합니다.

이 문서에서는 서버가 세션 상태를 데이터베이스에 저장하고 브라우저에는 세션 토큰을 쿠키로 전달하는 **서버 세션 방식**을 기준으로 설명합니다.

## 목표

- 검증된 비밀번호 저장용 해시 함수를 사용합니다.
- 비밀번호 해시와 무작위 세션 토큰의 다이제스트를 구분합니다.
- 예측하기 어려운 세션 토큰을 발급하고 서버에는 원문 대신 다이제스트를 저장합니다.
- `HttpOnly`, `Secure`, `SameSite`, `Path`, `Max-Age`와 `Expires`의 역할을 설명합니다.
- 브라우저 쿠키 만료와 서버 세션 만료를 함께 관리합니다.
- 로그인, 로그아웃, 만료, 토큰 교체와 계정 정지 뒤 동작을 정합니다.
- 비밀번호 변경과 재설정 뒤 기존 세션 처리 정책을 정합니다.
- 인증 관련 비밀값을 로그와 오류 응답에 남기지 않습니다.

## 비밀번호는 복호화하지 않습니다

서비스는 로그인할 때 사용자의 원래 비밀번호 문자열을 다시 알아낼 필요가 없습니다.

필요한 것은 다음 질문에 답하는 것입니다.

```text
사용자가 지금 입력한 비밀번호가
가입할 때 사용한 비밀번호와 같은가?
```

따라서 비밀번호는 복호화 가능한 암호문이 아니라 **비밀번호 저장용 해시 결과**로 저장합니다.

```ts
const passwordHash =
  await passwordHasher.hash(password);

const matches =
  await passwordHasher.verify(
    user.passwordHash,
    candidate
  );
```

가입 또는 비밀번호 변경 시에는 `hash()`를 사용합니다.

```text
원문 비밀번호
→ password hashing algorithm
→ 저장할 password hash
```

로그인 시에는 저장된 해시를 복호화하지 않고 `verify()`로 후보 비밀번호와 비교합니다.

```text
입력한 후보 비밀번호
+ 저장된 password hash
→ verify()
→ true / false
```

## 일반 해시와 비밀번호 해시는 목적이 다릅니다

SHA-256 같은 일반적인 암호학적 해시 함수는 매우 빠르게 계산되도록 설계되어 있습니다.

비밀번호 저장에서는 빠르다는 특성이 오히려 문제가 됩니다. 데이터베이스의 비밀번호 해시가 유출되었을 때 공격자가 많은 후보 비밀번호를 매우 빠르게 시험할 수 있기 때문입니다.

따라서 다음처럼 단순한 일반 해시 한 번으로 비밀번호를 저장하지 않습니다.

```text
SHA-256(password)
```

비밀번호에는 계산 비용과 메모리 비용을 의도적으로 높일 수 있는 비밀번호 저장 전용 알고리즘을 사용합니다.

대표적인 선택은 다음과 같습니다.

```text
Argon2id
scrypt
```

프로젝트가 사용하는 라이브러리가 bcrypt를 제공할 수도 있지만, 새 설계에서는 사용하는 플랫폼과 보안 요구사항에 맞는 현대적인 알고리즘과 설정을 검토합니다.

중요한 것은 자체 암호 방식을 만드는 것이 아니라 **널리 검토된 알고리즘과 라이브러리를 사용하는 것**입니다.

## 솔트는 라이브러리가 관리하게 합니다

비밀번호 저장 알고리즘은 일반적으로 각 비밀번호마다 무작위 솔트(salt)를 사용합니다.

솔트는 같은 비밀번호가 항상 같은 해시 결과를 만들지 않게 합니다.

```text
user A password = same-password
user B password = same-password

서로 다른 salt 사용
→ 서로 다른 password hash
```

솔트는 비밀번호처럼 비밀이어야 하는 값은 아닙니다. 보통 해시 결과 안에 알고리즘, 비용 설정과 함께 인코딩됩니다.

따라서 자체적으로 다음과 같은 문자열 형식을 만들지 않습니다.

```text
sha256(password + ":" + homemadeSalt)
```

검증된 비밀번호 해시 라이브러리가 솔트 생성, 저장 형식과 검증을 관리하도록 합니다.

## 비밀번호 해시 비용 설정

Argon2id나 scrypt는 비용 설정을 조절할 수 있습니다.

목표는 두 가지를 균형 있게 만족시키는 것입니다.

```text
정상 로그인
→ 서비스가 감당할 수 있는 시간과 메모리 사용

오프라인 비밀번호 추측 공격
→ 가능한 한 비싸게 만듦
```

비용이 너무 낮으면 공격자도 빠르게 후보를 시험할 수 있습니다.

반대로 비용이 지나치게 높으면 정상 로그인 몇 건만으로 서버 CPU나 메모리가 과도하게 사용될 수 있습니다.

따라서 운영 환경과 비슷한 하드웨어에서 실제 시간을 측정해 설정합니다.

## 비밀번호 입력 규칙

비밀번호 정책은 사용자가 기억하기 어려운 형식만 강제하는 것보다 충분한 길이와 사용성을 확보하는 데 초점을 둡니다.

기본적으로 다음 사항을 정합니다.

- 지나치게 짧은 값은 거부합니다.
- 긴 암호 문구(passphrase)를 사용할 수 있도록 충분한 최대 길이를 둡니다.
- 의미 없이 대문자·소문자·숫자·특수문자 조합만 강제하지 않습니다.
- 앞뒤 공백을 자동으로 제거할지 그대로 비밀번호 일부로 인정할지 정합니다.
- 유니코드 입력을 어떻게 처리할지 정합니다.
- 가입과 비밀번호 변경에 같은 기본 규칙을 적용합니다.
- 원문 비밀번호를 로그, 분석 도구와 오류 추적 시스템에 보내지 않습니다.

### 최대 길이도 필요합니다

최소 길이뿐 아니라 최대 길이도 정하는 편이 좋습니다.

비밀번호 해시는 일부러 비싼 연산이므로 무제한 길이의 문자열을 그대로 처리하게 하면 서버 자원을 과도하게 사용할 수 있습니다.

최대 길이는 짧은 값으로 제한하기 위한 것이 아니라 정상적인 긴 암호 문구를 충분히 허용하면서 비정상적으로 큰 입력을 막기 위한 방어 경계입니다.

## 유니코드 처리 정책을 정합니다

사용자가 입력한 비밀번호 문자열을 저장할 때와 검증할 때 서로 다르게 변환하면 올바른 비밀번호도 일치하지 않을 수 있습니다.

예를 들어 시각적으로 비슷한 문자열이 서로 다른 유니코드 코드 포인트 조합으로 표현될 수 있습니다.

따라서 다음 중 어떤 정책을 사용하는지 프로젝트 전체에서 일관되어야 합니다.

```text
입력 문자열을 그대로 사용
또는
정해진 Unicode normalization 적용
```

한 번 정한 정책을 가입과 로그인에서 다르게 적용하면 안 됩니다.

비밀번호 문자열을 임의로 소문자로 바꾸거나 공백을 제거하는 식의 변환도 사용자가 입력한 비밀 자체를 바꾸므로 명확한 정책 없이 수행하지 않습니다.

## 로그인 실패 응답과 계정 열거

로그인 API가 다음처럼 서로 다른 메시지를 반환하면

```text
"존재하지 않는 이메일입니다."
"비밀번호가 틀렸습니다."
```

공격자가 이메일 주소 목록을 대입해 등록된 계정을 알아내기 쉬워질 수 있습니다. 이를 계정 열거(account enumeration) 문제라고 합니다.

외부 응답에서는 필요한 범위에서 같은 메시지를 사용할 수 있습니다.

```text
이메일 또는 비밀번호가 올바르지 않습니다.
```

내부 로그나 운영 도구에서는 실제 실패 원인을 더 자세히 기록할 수 있지만 비밀값은 포함하지 않습니다.

단, 사용자 경험과 계정 복구 흐름에 따라 어느 정도의 정보 노출을 허용할지는 서비스 정책으로 정합니다. 핵심은 계정 존재 여부를 의도하지 않게 과도하게 공개하지 않는 것입니다.

## 비밀번호 해시 설정 갱신

비밀번호 해시의 비용 설정은 시간이 지나면서 강화될 수 있습니다.

예를 들어 과거에는 낮은 비용으로 Argon2id를 사용했고 현재는 더 높은 비용을 사용한다고 가정합니다.

저장된 비밀번호를 모두 복호화할 수는 없으므로 사용자가 정상 로그인해 원문 비밀번호를 다시 제공하는 시점을 활용할 수 있습니다.

```text
비밀번호 검증 성공
→ 현재 저장된 hash의 설정 확인
→ 현재 정책보다 오래된 설정인지 확인
→ 필요하면 입력한 비밀번호로 새 hash 생성
→ 새 hash 저장
→ 로그인 완료
```

이 과정을 흔히 **rehash on login**이라고 부릅니다.

라이브러리가 `needsRehash()`와 비슷한 기능을 제공한다면 이를 사용할 수 있습니다.

중요한 순서는 다음과 같습니다.

```text
먼저 기존 hash로 비밀번호가 맞는지 검증
→ 성공한 경우에만 새 설정으로 재해싱
```

검증되지 않은 입력을 새 비밀번호처럼 저장하면 안 됩니다.

## 비밀번호 변경

로그인한 사용자가 비밀번호를 변경하는 흐름에서는 일반적으로 다음 정책을 검토합니다.

```text
현재 비밀번호 확인
→ 새 비밀번호 정책 검사
→ 새 password hash 생성
→ 데이터베이스 저장
→ 기존 세션 처리
```

민감한 작업에서는 현재 로그인 세션이 있다는 사실만으로 충분하지 않고 기존 비밀번호를 다시 확인하도록 할 수 있습니다.

비밀번호 변경 뒤 기존 세션을 어떻게 처리할지는 명시적으로 정합니다.

예를 들어 다음 중 하나를 선택할 수 있습니다.

```text
모든 기존 세션 폐기
현재 세션만 유지하고 나머지 폐기
모든 세션 유지
```

계정 탈취 대응을 중요하게 본다면 기존 세션을 폐기하는 정책이 일반적으로 더 안전합니다.

현재 세션을 유지하는 경우에도 새 세션 토큰으로 교체할 수 있습니다.

## 세션이 하는 일

로그인마다 비밀번호를 다시 보내는 대신 로그인에 성공한 뒤 임시 세션 토큰을 발급합니다.

```text
로그인
→ 비밀번호 검증
→ 세션 생성
→ 세션 토큰을 브라우저에 전달

이후 요청
→ 세션 토큰 전달
→ 서버가 세션 조회
→ 사용자 식별
```

세션 토큰을 가진 사람은 일반적으로 해당 세션의 사용자처럼 요청할 수 있습니다.

따라서 세션 토큰은 단순한 랜덤 ID가 아니라 **인증 자격 증명**으로 취급해야 합니다.

## 세션 토큰 생성

토큰은 공격자가 추측하기 어려워야 합니다.

Node.js에서는 암호학적으로 안전한 난수 생성기를 사용할 수 있습니다.

```ts
import { randomBytes } from "node:crypto";

const token =
  randomBytes(32).toString("base64url");
```

`randomBytes(32)`는 32바이트, 즉 256비트의 무작위 값을 생성합니다.

`base64url`은 이 바이트를 쿠키나 URL에서 다루기 쉬운 문자열 형식으로 인코딩합니다.

다음처럼 예측 가능한 값은 세션 토큰으로 사용하지 않습니다.

```text
userId
현재 timestamp
증가하는 숫자
Math.random()
```

세션 토큰의 핵심은 **충분한 엔트로피를 가진 암호학적 난수**라는 점입니다.

## 서버에는 세션 토큰 원문 대신 다이제스트를 저장합니다

브라우저에는 실제 세션 토큰이 필요하지만 데이터베이스에는 원문을 그대로 저장하지 않을 수 있습니다.

```ts
import {
  createHash,
  randomBytes
} from "node:crypto";

const token =
  randomBytes(32).toString("base64url");

const digest =
  createHash("sha256")
    .update(token)
    .digest("hex");
```

저장 구조는 다음과 같습니다.

```text
브라우저
→ token 원문 보관

서버 DB
→ SHA-256(token) 보관
```

세션 테이블은 다음처럼 만들 수 있습니다.

```sql
create table sessions (
  id uuid primary key,
  user_id uuid not null
    references users(id)
    on delete cascade,

  token_digest text not null unique,

  expires_at timestamptz not null,
  created_at timestamptz not null,
  revoked_at timestamptz
);
```

요청이 들어오면 쿠키의 원문 토큰을 다시 같은 방식으로 해시합니다.

```text
cookie token
→ SHA-256
→ token_digest
→ sessions에서 조회
```

## 왜 세션 토큰에는 SHA-256을 써도 되는가

비밀번호와 세션 토큰은 둘 다 비밀이지만 생성 방식이 다릅니다.

### 비밀번호

```text
사람이 선택
→ 짧거나 흔할 수 있음
→ 후보 사전으로 추측 가능
```

따라서 공격자의 추측을 느리게 만드는 비밀번호 저장 전용 해시가 필요합니다.

### 세션 토큰

```text
서버가 암호학적 난수로 생성
→ 충분히 긴 무작위 값
→ 후보 공간이 매우 큼
```

세션 토큰은 원래부터 추측하기 어렵게 만들어졌기 때문에 서버 저장용 식별값을 만들 때 빠른 SHA-256 같은 암호학적 해시를 사용할 수 있습니다.

즉 다음 두 사용은 목적이 다릅니다.

```text
비밀번호 저장
→ Argon2id / scrypt 등 느린 password hash

무작위 세션 토큰 저장
→ SHA-256 같은 digest로 원문 노출 감소
```

세션 토큰을 SHA-256으로 해싱한다고 약한 비밀번호를 안전하게 저장할 수 있게 되는 것은 아닙니다.

## 토큰 다이제스트 저장의 한계

다이제스트만 저장하면 세션 데이터베이스가 유출되었을 때 데이터베이스 값 자체를 그대로 쿠키에 넣어 사용할 수 없게 됩니다.

하지만 이것이 모든 세션 탈취를 막는 것은 아닙니다.

다음 위치에서 원문 토큰이 유출되면 여전히 세션을 탈취할 수 있습니다.

- 브라우저
- 네트워크 또는 잘못된 TLS 종단
- 서버 요청 로그
- 프록시 로그
- 오류 추적 도구
- 악성 브라우저 확장
- 쿠키를 읽을 수 있는 취약점

따라서 토큰 다이제스트 저장과 함께 `Secure`, `HttpOnly`, 로그 마스킹, 세션 만료와 폐기를 모두 적용합니다.

## 세션 조회

요청마다 일반적으로 다음 항목을 확인합니다.

```text
쿠키 존재 여부
→ 토큰 형식 확인
→ token digest 계산
→ 세션 조회
→ revoked_at 확인
→ expires_at 확인
→ 연결된 사용자 확인
→ 계정 상태 확인
→ Actor 생성
```

예를 들어 SQL은 개념적으로 다음과 같이 구성할 수 있습니다.

```sql
select
  s.id as session_id,
  s.user_id,
  s.expires_at,
  s.revoked_at,
  u.status
from sessions as s
join users as u
  on u.id = s.user_id
where s.token_digest = $1;
```

그 뒤 애플리케이션에서 다음 조건을 검사합니다.

```text
session 존재
AND revoked_at IS NULL
AND expires_at > now
AND user.status = active
```

가능하다면 필요한 조건 일부를 SQL의 `WHERE`에 포함해 유효한 세션만 조회할 수도 있습니다.

## `revoked_at`과 삭제의 차이

세션을 무효화할 때 행 자체를 삭제할 수도 있고 `revoked_at`을 기록할 수도 있습니다.

```text
DELETE
→ 행 자체 제거

revoked_at
→ 세션이 언제 폐기되었는지 기록
```

어느 쪽을 사용할지는 감사와 운영 요구사항에 따라 정합니다.

`revoked_at`을 사용하는 경우 다음처럼 유효성 검사에 반드시 포함합니다.

```sql
where revoked_at is null
```

행이 존재한다는 사실만으로 세션이 유효하다고 판단하면 안 됩니다.

## 쿠키로 세션 토큰 전달

브라우저 기반 애플리케이션에서는 세션 토큰을 쿠키로 전달할 수 있습니다.

```ts
reply.setCookie("app_session", token, {
  path: "/",
  httpOnly: true,
  secure: config.production,
  sameSite: "lax",
  maxAge: 60 * 60 * 24 * 14
});
```

각 속성은 서로 다른 목적을 가집니다.

## `HttpOnly`

```text
HttpOnly
→ 브라우저 JavaScript의 document.cookie에서 접근 제한
```

세션 쿠키에 `HttpOnly`를 사용하면 일반적인 클라이언트 JavaScript가 토큰 값을 직접 읽지 못합니다.

이는 XSS의 피해를 줄이는 방어책 중 하나입니다.

하지만 `HttpOnly`가 XSS 자체를 막는 것은 아닙니다. 공격자가 페이지에서 JavaScript를 실행할 수 있다면 쿠키 값을 읽지 못하더라도 사용자의 브라우저를 이용해 인증된 요청을 보낼 수 있습니다.

따라서 다음처럼 이해합니다.

```text
HttpOnly
→ 토큰 원문 탈취 위험 감소

하지만
→ XSS 전체 방어책은 아님
```

## `Secure`

```text
Secure
→ HTTPS 연결에서만 쿠키 전송
```

운영 환경의 인증 쿠키에는 일반적으로 `Secure`를 사용합니다.

개발 환경에서 로컬 HTTP를 사용한다는 이유로 조건부 설정을 둘 수 있지만, 실제 운영에서 HTTPS가 강제되는지 확인해야 합니다.

애플리케이션이 TLS 종료 프록시 뒤에 있다면 프록시와 애플리케이션의 HTTPS 인식 설정도 올바르게 구성해야 합니다.

## `SameSite`

`SameSite`는 다른 사이트에서 시작된 요청에 쿠키가 포함되는 범위를 제한합니다.

대표적인 값은 다음과 같습니다.

```text
Strict
→ 교차 사이트 상황에서 가장 강하게 제한

Lax
→ 일반적인 최상위 탐색 등 일부 상황에서는 허용
   대부분의 상태 변경 교차 사이트 요청에서는 제한

None
→ 교차 사이트 요청에도 전송 가능
   일반적으로 Secure와 함께 사용해야 함
```

`SameSite=Lax`는 많은 일반 웹 애플리케이션의 기본 선택이 될 수 있지만 서비스 구조에 따라 달라집니다.

예를 들어 완전히 다른 사이트의 프론트엔드와 API 사이에서 쿠키를 보내야 한다면 `None`이 필요할 수 있습니다. 이 경우 CSRF 방어를 별도로 더 엄격하게 설계해야 합니다.

`SameSite` 하나만으로 모든 CSRF 문제가 해결된다고 가정하지 않습니다.

## `Path`

```text
Path=/
→ 해당 호스트의 전체 경로에 쿠키 전송
```

더 좁은 경로가 필요한 경우 범위를 제한할 수 있습니다.

```text
Path=/api
```

하지만 `Path`는 브라우저의 쿠키 전송 범위를 제어하는 속성이지 서버의 권한 체계를 대신하는 보안 경계는 아닙니다.

## `Domain`

`Domain`을 생략하면 일반적으로 쿠키를 설정한 호스트에만 적용되는 host-only 쿠키가 됩니다.

필요하지 않다면 넓은 상위 도메인으로 설정하지 않는 편이 좋습니다.

예를 들어 다음처럼 넓게 잡으면

```text
Domain=example.com
```

여러 서브도메인에서 해당 쿠키와 관련된 영향을 받을 수 있습니다.

세션 쿠키를 어느 호스트에서 실제로 사용해야 하는지 기준으로 범위를 최소화합니다.

## `Max-Age`와 `Expires`

이 두 속성은 브라우저가 쿠키를 얼마나 오래 보관할지 정합니다.

```ts
maxAge: 60 * 60 * 24 * 14
```

위 예시는 14일입니다.

브라우저 쿠키 수명과 서버 세션 수명은 서로 별개입니다.

```text
브라우저 쿠키
→ Max-Age / Expires

서버 세션
→ sessions.expires_at
```

둘 중 하나가 만료되면 정상 인증에 사용할 수 없게 설계합니다.

## 서버 만료가 최종 기준입니다

브라우저의 쿠키가 아직 남아 있더라도 서버의 세션이 만료되었다면 요청을 거부합니다.

```text
cookie 존재
하지만
sessions.expires_at <= now()
→ 인증 실패
```

브라우저 쿠키 삭제만 보안 경계로 사용하면 서버가 실제 만료 시점을 강제할 수 없습니다.

따라서 최종 세션 유효성은 서버에서 결정합니다.

## 쿠키 삭제

로그아웃 시 쿠키를 삭제하려면 발급할 때 사용한 쿠키 범위와 일치하도록 삭제해야 합니다.

중요한 속성은 특히 다음과 같습니다.

```text
이름
Path
Domain
```

예를 들어 발급 시

```text
Name = app_session
Path = /
```

였다면 삭제할 때도 같은 이름과 경로를 사용해야 합니다.

다른 `Path`나 `Domain`으로 만료 쿠키를 보내면 기존 쿠키와 별개의 쿠키가 되어 원래 세션 쿠키가 남을 수 있습니다.

프레임워크가 제공하는 `clearCookie()` 같은 기능을 사용할 때도 원래 옵션과 맞는지 확인합니다.

## 쿠키 이름과 `__Host-` 접두사

브라우저가 지원하는 환경에서는 세션 쿠키 이름에 `__Host-` 접두사를 사용하는 방법도 고려할 수 있습니다.

예:

```text
__Host-app_session
```

이 접두사를 올바르게 사용하려면 일반적으로 다음 조건이 필요합니다.

```text
Secure
Path=/
Domain 속성 없음
```

이 규칙은 쿠키가 더 넓은 도메인 범위로 설정되는 것을 제한하는 데 도움이 됩니다.

프로젝트에서 브라우저 호환성과 배포 구성을 확인한 뒤 선택합니다.

## 로그인 순서

일반적인 로그인 흐름은 다음과 같습니다.

```text
이메일·비밀번호 입력 검증
→ 사용자 조회
→ 비밀번호 verify
→ 계정 상태 확인
→ 새 세션 토큰 생성
→ token digest 생성
→ sessions에 저장
→ 세션 쿠키 발급
→ 공개 가능한 사용자 정보 반환
```

인증 실패 시 세션을 만들지 않습니다.

정지된 계정이라면 비밀번호가 맞더라도 애플리케이션 정책에 따라 로그인 세션 생성을 거부합니다.

## 비밀번호 검증의 시간 비용

비밀번호 해시는 의도적으로 비싼 연산입니다.

공격자가 로그인 엔드포인트에 무제한 요청을 보낼 수 있다면 서버 자원과 계정 비밀번호를 동시에 공격할 수 있습니다.

따라서 로그인에는 속도 제한(rate limiting)이 필요합니다.

다만 다음처럼 하나의 단순한 기준만으로 영구 또는 장시간 차단하면 문제가 생길 수 있습니다.

```text
계정 하나
→ 실패 5번
→ 장시간 완전 잠금
```

공격자가 다른 사람의 이메일을 알고 있다면 일부러 실패 요청을 반복해 정상 사용자를 잠글 수 있기 때문입니다.

속도 제한 정책은 다음 신호를 함께 고려할 수 있습니다.

- IP
- 계정 식별자
- 세션 또는 장치 신호
- 짧은 시간의 실패 횟수
- 점진적인 지연
- CAPTCHA나 추가 인증 같은 단계적 대응

어떤 방법이 적합한지는 서비스의 위협 모델과 사용자 규모에 따라 달라집니다.

## 세션 고정과 로그인 뒤 토큰 교체

로그인 전에 존재하던 세션 식별자를 로그인 성공 뒤 그대로 인증 세션으로 승격시키면 세션 고정(session fixation) 위험이 생길 수 있습니다.

따라서 인증 상태가 중요한 방식으로 바뀔 때는 새 토큰을 발급합니다.

대표적인 시점은 다음과 같습니다.

```text
로그인 성공
권한 상승
비밀번호 변경
민감한 인증 단계 완료
```

흐름은 다음처럼 구성합니다.

```text
이전 세션
→ 새 무작위 token 생성
→ 새 session 저장
→ 이전 session 폐기
→ 새 cookie 설정
```

새 토큰 발급과 이전 토큰 폐기의 정확한 순서는 애플리케이션 요구사항에 맞게 트랜잭션과 오류 처리를 고려해 설계합니다.

## 로그아웃

로그아웃은 브라우저와 서버 양쪽의 상태를 모두 무효화해야 합니다.

```text
1. 서버 세션 폐기
2. 브라우저 세션 쿠키 삭제
```

서버 세션은 예를 들어 다음처럼 폐기할 수 있습니다.

```sql
update sessions
set revoked_at = now()
where id = $1
  and revoked_at is null;
```

또는 세션 행을 삭제하는 정책을 사용할 수 있습니다.

브라우저 쿠키만 삭제하면 문제가 남습니다.

```text
공격자가 이미 token을 복사해 둠
→ 사용자의 브라우저에서는 cookie 삭제
→ 서버 session은 여전히 유효
→ 공격자는 복사한 token으로 계속 요청 가능
```

반대로 서버 세션만 폐기하고 브라우저 쿠키를 남기면 서버에서는 안전하게 거부할 수 있지만 브라우저가 계속 쓸모없는 토큰을 보냅니다.

따라서 둘 다 처리합니다.

## 요청에서 사용자 찾기

각 라우트가 직접 쿠키 파싱, 토큰 해시와 세션 조회를 반복하면 규칙이 서로 달라지기 쉽습니다.

공통 인증 훅, 미들웨어 또는 인증 서비스에서 사용자 정보를 만듭니다.

```ts
interface Actor {
  userId: string;
  sessionId: string;
  accountStatus:
    | "active"
    | "suspended";
}
```

개념적인 처리는 다음과 같습니다.

```ts
const token = readSessionCookie(request);

if (!token) {
  return anonymous;
}

const digest = digestSessionToken(token);
const session = await findSessionByDigest(digest);

if (!session) {
  return anonymous;
}

if (session.revokedAt) {
  return anonymous;
}

if (session.expiresAt <= clock.now()) {
  return anonymous;
}

if (session.user.status !== "active") {
  throw new AccountUnavailable();
}

return {
  userId: session.user.id,
  sessionId: session.id,
  accountStatus: session.user.status
};
```

실제 구현에서는 데이터베이스 쿼리에서 유효 조건을 더 좁힐 수도 있습니다.

## 인증과 권한 부여를 구분합니다

세션 검증으로 사용자가 누구인지 알아냈다고 모든 리소스를 사용할 권한이 생기는 것은 아닙니다.

```text
인증(authentication)
→ 이 요청은 user-123이 보냈다

인가(authorization)
→ user-123이 note-456을 수정할 수 있다
```

따라서 `Actor`를 만든 뒤 각 기능에서는 해당 사용자가 실제 리소스에 접근할 권한이 있는지 추가로 검사합니다.

세션 테이블의 `user_id`만 확인하는 것으로 개별 메모, 조직, 프로젝트 권한까지 자동으로 해결되지 않습니다.

## 계정 정지와 기존 세션

사용자의 계정을 정지했는데 기존 세션이 아직 만료되지 않았다면 세션만 확인해서는 요청이 계속 성공할 수 있습니다.

따라서 요청 인증에서 세션 상태뿐 아니라 현재 사용자 계정 상태도 확인합니다.

```text
session valid
BUT
user.status = suspended
→ 요청 거부
```

정지 정책에 따라 계정 상태 변경 시 기존 세션을 일괄 폐기할 수도 있습니다.

예:

```sql
update sessions
set revoked_at = now()
where user_id = $1
  and revoked_at is null;
```

계정 상태를 매 요청 조인해서 확인할지, 상태 변경 시 모든 세션을 폐기할지는 일관성과 조회 비용을 함께 고려해 정합니다.

## 세션 만료

세션에는 최소한 서버 측 만료 시각을 둡니다.

```sql
expires_at timestamptz not null
```

고정 만료는 로그인 시 계산한 시각까지 세션이 유효한 방식입니다.

```text
로그인: 8월 1일
expires_at: 8월 15일
→ 사용 여부와 관계없이 8월 15일 만료
```

이 방식은 세션 최대 수명이 명확합니다.

## 슬라이딩 만료

사용자가 계속 활동하는 동안 세션 만료를 연장하는 방식을 슬라이딩 만료(sliding expiration)라고 합니다.

단순 구현은 요청마다 다음처럼 갱신할 수 있습니다.

```sql
update sessions
set expires_at = now() + interval '14 days'
where id = $1;
```

하지만 모든 요청마다 데이터베이스 쓰기가 발생하면 쓰기 부하가 커질 수 있습니다.

따라서 일정 시간이 지났을 때만 갱신하는 방식을 사용할 수 있습니다.

```text
현재 expires_at이 충분히 멀리 있음
→ 갱신 안 함

만료까지 얼마 남지 않음
→ expires_at 갱신
```

슬라이딩 만료를 사용하더라도 무제한으로 세션이 연장되는 것을 원하지 않는다면 절대 최대 수명도 둘 수 있습니다.

예:

```text
idle timeout
→ 마지막 활동을 기준으로 14일

absolute lifetime
→ 최초 로그인 이후 최대 90일
```

이를 위해 `created_at`이나 별도의 절대 만료 시각을 사용할 수 있습니다.

## 세션 정리

만료되거나 폐기된 세션 행을 영원히 보관할 필요가 없다면 정리 정책을 둡니다.

예:

```sql
delete from sessions
where expires_at < now() - interval '30 days'
   or revoked_at < now() - interval '30 days';
```

정확한 보존 기간은 감사, 운영 분석과 개인정보 정책에 따라 정합니다.

중요한 점은 **정리 작업과 인증 유효성 검사를 구분하는 것**입니다.

```text
만료된 행이 DB에 아직 남아 있음
→ 인증에서는 즉시 거부해야 함

백그라운드 정리
→ 나중에 물리 삭제 가능
```

## 여러 장치의 세션

서버 세션 방식에서는 한 사용자에게 여러 세션 행을 허용할 수 있습니다.

```text
user-1
├─ desktop session
├─ phone session
└─ tablet session
```

이 경우 다음 정책을 정의할 수 있습니다.

- 여러 장치 동시 로그인 허용 여부
- 사용자에게 활성 세션 목록을 보여 줄지
- 특정 세션만 로그아웃할 수 있는지
- "모든 기기에서 로그아웃"을 지원할지
- 비밀번호 변경 후 어떤 세션을 폐기할지

"모든 기기에서 로그아웃"은 사용자 소유의 모든 활성 세션을 폐기하면 구현할 수 있습니다.

## 비밀번호 재설정

사용자가 비밀번호를 잊었을 때는 기존 비밀번호를 알 수 없으므로 별도의 재설정 자격 증명이 필요합니다.

재설정 토큰도 세션 토큰과 마찬가지로 **충분한 무작위 값**이어야 합니다.

```text
암호학적 난수 token 생성
→ 원문 token은 사용자에게 전달
→ 서버에는 digest 저장
```

예를 들어 이메일 링크에는 원문 토큰을 포함하고 서버 데이터베이스에는 SHA-256 다이제스트만 저장할 수 있습니다.

## 재설정 토큰 정책

재설정 토큰에는 일반 세션보다 더 짧은 만료 시간을 두는 것이 일반적입니다.

최소한 다음을 정합니다.

- 만료 시간
- 한 번 사용한 뒤 즉시 폐기
- 새 토큰 발급 시 기존 토큰을 폐기할지
- 사용자가 여러 요청을 만들 수 있는지
- 비밀번호 변경 성공 뒤 기존 로그인 세션을 어떻게 처리할지
- 계정 존재 여부를 응답으로 얼마나 공개할지

예를 들어 재설정 성공 흐름은 다음과 같습니다.

```text
reset token 수신
→ digest 계산
→ token 조회
→ 만료·사용 여부 확인
→ 새 비밀번호 정책 검사
→ 새 password hash 생성
→ 사용자 비밀번호 갱신
→ reset token 사용 처리
→ 기존 세션 폐기
→ 완료
```

가능하다면 비밀번호 변경과 토큰 폐기처럼 반드시 함께 성공해야 하는 데이터베이스 변경은 하나의 트랜잭션으로 묶습니다.

## 재설정 토큰은 한 번만 사용합니다

한 번 성공한 토큰을 다시 사용할 수 있으면 링크가 뒤늦게 유출됐을 때 위험합니다.

따라서 사용 완료 상태를 기록하거나 행을 삭제합니다.

예:

```sql
update password_reset_tokens
set used_at = now()
where token_digest = $1
  and used_at is null
  and expires_at > now()
returning user_id;
```

조건부 `UPDATE`를 사용하면 동시에 같은 토큰을 사용하는 두 요청 중 하나만 성공하게 만들 수 있습니다.

## 재설정 요청에서도 계정 열거를 조심합니다

다음 응답은 계정 존재 여부를 직접 알려 줍니다.

```text
"등록되지 않은 이메일입니다."
```

대신 외부 응답을 다음처럼 통일할 수 있습니다.

```text
해당 주소의 계정이 있다면
비밀번호 재설정 안내를 보냈습니다.
```

실제로 이메일을 보낼지, 속도 제한과 악용 방지를 어떻게 할지는 별도로 정합니다.

## 민감한 작업의 재인증

유효한 세션이 있다고 해서 오랫동안 열어 둔 브라우저에서 모든 민감한 작업을 즉시 허용해야 하는 것은 아닙니다.

서비스 정책에 따라 다음 작업에서는 최근에 다시 비밀번호를 확인하거나 추가 인증을 요구할 수 있습니다.

- 비밀번호 변경
- 이메일 주소 변경
- 결제 정보 변경
- 보안 설정 변경
- 모든 세션 폐기

이를 **재인증(re-authentication)**이라고 생각할 수 있습니다.

세션이 "누구인지"를 알려 주는 것과 "민감한 작업을 지금 수행해도 되는지"는 별개의 정책입니다.

## CSRF와 쿠키 기반 인증

브라우저는 쿠키를 요청에 자동으로 포함할 수 있습니다. 따라서 쿠키 기반 인증에서는 다른 사이트가 사용자의 브라우저를 이용해 상태 변경 요청을 보내는 CSRF(cross-site request forgery)를 고려해야 합니다.

`SameSite`는 중요한 방어 수단이지만 서비스 요구에 따라 별도의 CSRF 토큰이나 요청 출처 검증이 필요할 수 있습니다.

특히 다음 조건에서는 별도 검토가 중요합니다.

```text
SameSite=None 사용
교차 사이트 프론트엔드와 API 구성
민감한 상태 변경 요청
```

`HttpOnly`와 CSRF 방어는 목적이 다릅니다.

```text
HttpOnly
→ JavaScript가 cookie 원문을 읽기 어렵게 함

CSRF 방어
→ 다른 사이트가 사용자 cookie를 이용해
   원하지 않는 요청을 보내는 것을 막음
```

둘을 서로 대체하는 기능으로 생각하지 않습니다.

## XSS와 세션 쿠키

`HttpOnly`를 사용하면 공격자가 JavaScript로 세션 토큰 문자열을 직접 읽는 위험을 줄일 수 있습니다.

하지만 XSS가 있으면 공격자는 사용자의 페이지 컨텍스트에서 인증된 API 요청을 실행할 수 있습니다.

따라서 세션 보안은 다음 방어와 함께 생각합니다.

```text
HttpOnly cookie
Secure cookie
적절한 SameSite / CSRF 방어
XSS 방어
CSP 등 브라우저 보안 정책
짧고 명확한 세션 수명
서버 측 세션 폐기
```

쿠키 속성 하나가 전체 웹 보안을 해결한다고 생각하지 않습니다.

## 기록하지 않을 값

다음 값은 로그에 남기지 않습니다.

- 원문 비밀번호
- 새 비밀번호와 이전 비밀번호
- 세션 토큰 원문
- 세션 쿠키 전체
- `Cookie` 헤더 전체
- `Authorization` 헤더
- 비밀번호 재설정 토큰
- 이메일 인증 토큰 등 일회성 인증 토큰
- 전체 비밀번호 해시

비밀번호 해시는 원문이 아니지만 공격자가 오프라인 비밀번호 추측에 사용할 수 있으므로 일반 로그에 복사할 이유가 없습니다.

## 기록할 수 있는 값

운영과 보안 분석에 필요한 비밀이 아닌 정보는 기록할 수 있습니다.

예:

```text
requestId
userId
sessionId
로그인 성공/실패 결과
실패 사유의 내부 분류
rate limit 적용 여부
IP 또는 네트워크 정보의 정책상 허용된 형태
처리 시간
```

세션 ID 자체도 내부 식별자라면 외부 노출과 로그 보존 정책을 검토합니다.

로그에 무엇을 남길지는 개인정보와 보존 정책까지 함께 고려합니다.

## 오류 응답에 내부 정보를 노출하지 않습니다

클라이언트에게 다음과 같은 값을 그대로 보내지 않습니다.

```text
password hash
token digest
원본 DB 오류
세션 내부 ID가 불필요한 경우 그 값
내부 사용자 상태의 상세 사유
```

외부 API 오류는 사용자가 필요한 행동을 이해할 수 있는 수준으로 제한합니다.

내부 운영 로그에는 더 자세한 오류 분류를 남길 수 있습니다.

## 예제 세션 검증 흐름

전체 흐름을 한 번에 보면 다음과 같습니다.

```text
HTTP request
    ↓
Cookie에서 app_session 읽기
    ↓
없음?
 ┌──┴──┐
yes   no
 │     ↓
익명   token 형식 검사
       ↓
       SHA-256 digest 계산
       ↓
       sessions 조회
       ↓
       존재?
       ↓
       revoked_at IS NULL?
       ↓
       expires_at > now?
       ↓
       user active?
       ↓
       Actor 생성
       ↓
       route authorization 검사
```

각 단계는 다른 질문에 답합니다.

```text
토큰이 있는가?
→ 클라이언트가 자격 증명을 보냈는가

세션이 있는가?
→ 서버가 발급한 자격 증명인가

폐기되지 않았는가?
→ 로그아웃 또는 강제 폐기되지 않았는가

만료되지 않았는가?
→ 허용된 수명 안에 있는가

계정이 활성 상태인가?
→ 현재도 사용 가능한 사용자 계정인가

리소스 권한이 있는가?
→ 이 사용자가 해당 작업을 수행할 수 있는가
```

## 흔한 실수

- 비밀번호를 복호화 가능한 형태로 저장합니다.
- SHA-256 같은 일반 해시를 한 번 적용해 비밀번호를 저장합니다.
- 자체 비밀번호 해시 또는 솔트 형식을 만듭니다.
- 비밀번호 해시의 비용을 실제 운영 환경에서 측정하지 않습니다.
- 무제한 길이의 비밀번호 입력을 비용 큰 해시 함수에 그대로 전달합니다.
- 가입과 로그인에서 비밀번호 문자열을 서로 다르게 정규화합니다.
- 로그인 오류로 계정 존재 여부를 과도하게 공개합니다.
- 비밀번호 해시 비용 설정이 오래되어도 갱신하지 않습니다.
- 세션 토큰을 `Math.random()`이나 순차 ID로 만듭니다.
- 세션 원문 토큰을 데이터베이스에 그대로 저장합니다.
- 비밀번호 저장용 해시와 랜덤 토큰 다이제스트가 같은 문제를 푼다고 생각합니다.
- 쿠키에 `HttpOnly`를 설정했으니 XSS 전체가 해결되었다고 생각합니다.
- `SameSite`만 설정하면 모든 CSRF 문제가 해결된다고 생각합니다.
- 운영 인증 쿠키에 `Secure`를 사용하지 않습니다.
- 필요하지 않은 넓은 `Domain` 범위로 세션 쿠키를 설정합니다.
- 쿠키 삭제 시 발급할 때와 다른 `Path` 또는 `Domain`을 사용합니다.
- 브라우저 쿠키 만료만 확인하고 서버 `expires_at`을 확인하지 않습니다.
- 세션 행이 존재한다는 이유만으로 `revoked_at`과 계정 상태를 검사하지 않습니다.
- 로그인 전과 로그인 후에 같은 세션 토큰을 계속 사용합니다.
- 권한 상승이나 비밀번호 변경 뒤에도 오래된 토큰을 그대로 유지합니다.
- 쿠키만 삭제하고 서버 세션을 남깁니다.
- 서버 세션만 폐기하고 브라우저 쿠키 정리를 하지 않습니다.
- 인증된 사용자라는 사실과 특정 리소스를 수정할 권한이 있다는 사실을 혼동합니다.
- 비밀번호 변경 또는 계정 정지 뒤 기존 세션 정책을 정하지 않습니다.
- 슬라이딩 만료를 위해 모든 요청마다 무조건 데이터베이스를 갱신합니다.
- 슬라이딩 세션에 절대 최대 수명을 두지 않아 사실상 영구 세션이 됩니다.
- 만료된 세션 정리 작업과 요청 시 유효성 검사를 혼동합니다.
- 비밀번호 재설정 토큰을 여러 번 사용할 수 있게 둡니다.
- 재설정 토큰 원문을 데이터베이스나 로그에 저장합니다.
- 재설정 요청 응답으로 계정 존재 여부를 과도하게 드러냅니다.
- 비밀번호, 쿠키, `Authorization` 헤더와 재설정 토큰을 로그에 기록합니다.

## 완료 기준

- 인증과 세션 유지의 차이를 설명할 수 있습니다.
- 비밀번호를 복호화하지 않고 검증해야 하는 이유를 설명할 수 있습니다.
- 비밀번호 저장에 일반 SHA-256 대신 Argon2id나 scrypt 같은 비밀번호 저장용 알고리즘이 필요한 이유를 설명할 수 있습니다.
- 비밀번호 솔트와 비용 설정의 역할을 설명할 수 있습니다.
- 비밀번호 해시와 무작위 세션 토큰 다이제스트의 목적 차이를 설명할 수 있습니다.
- 암호학적으로 안전한 난수로 세션 토큰을 생성할 수 있습니다.
- 서버에는 원문 세션 토큰 대신 다이제스트를 저장할 수 있습니다.
- 요청마다 세션 존재 여부, 폐기, 만료와 사용자 계정 상태를 확인할 수 있습니다.
- `HttpOnly`, `Secure`, `SameSite`, `Path`, `Domain`, `Max-Age`와 `Expires`의 역할을 설명할 수 있습니다.
- 브라우저 쿠키 수명과 서버의 `expires_at`이 별개의 제어라는 점을 설명할 수 있습니다.
- 쿠키 삭제 시 이름, `Path`, `Domain`이 발급 설정과 일치해야 하는 이유를 설명할 수 있습니다.
- 로그인과 권한 상승 시 세션 토큰을 교체해야 하는 이유를 설명할 수 있습니다.
- 로그아웃에서 서버 세션 폐기와 브라우저 쿠키 삭제를 모두 수행할 수 있습니다.
- 인증과 인가를 구분할 수 있습니다.
- 정지되거나 삭제된 사용자에게 유효한 세션이 남아 있어도 요청을 거부할 수 있습니다.
- 고정 만료와 슬라이딩 만료의 차이를 설명할 수 있습니다.
- 비밀번호 변경 뒤 기존 세션 처리 정책을 설명할 수 있습니다.
- 비밀번호 재설정 토큰을 짧은 수명과 일회성 자격 증명으로 처리할 수 있습니다.
- 쿠키 기반 인증에서 `SameSite`와 CSRF 방어가 어떤 관계인지 설명할 수 있습니다.
- 원문 비밀번호, 세션 토큰, 인증 헤더와 재설정 토큰을 로그에 남기지 않을 수 있습니다.
