# 권한, CSRF와 CORS

로그인에 성공했다는 사실은 사용자가 누구인지 확인했다는 뜻일 뿐, 그 사용자가 모든 데이터와 기능을 사용할 수 있다는 뜻은 아닙니다.

웹 애플리케이션에서는 다음 세 문제를 구분해야 합니다.

```text
인증(authentication)
→ 이 요청을 보낸 사용자가 누구인가?

인가(authorization)
→ 이 사용자가 이 리소스에 이 작업을 수행할 수 있는가?

브라우저 요청 경계
→ 다른 출처의 페이지가 사용자의 인증 정보를 이용해
   요청하거나 응답을 읽는 것을 어떻게 제한할 것인가?
```

화면에서 버튼을 숨기는 것은 사용자 인터페이스만 바꿉니다. 공격자는 브라우저 개발자 도구, 직접 만든 HTTP 요청, 다른 클라이언트나 WebSocket 메시지를 통해 서버에 요청할 수 있습니다.

따라서 서버는 HTTP 요청과 WebSocket 메시지를 처리할 때마다 신뢰할 수 있는 서버 측 상태를 기준으로 권한을 판단해야 합니다.

## 목표

- 인증과 인가를 구분합니다.
- 역할, 소유권과 객체 수준 권한을 서버에서 검사합니다.
- UI 권한 표시와 서버 권한 검사의 역할을 구분합니다.
- `401`, `403`, 존재를 숨기기 위한 `404`의 의미를 구분합니다.
- 권한 조건을 데이터 조회와 쓰기 조건에 포함하는 방법을 설명합니다.
- 역할 변경처럼 여러 행의 상태가 필요한 규칙을 트랜잭션 안에서 처리합니다.
- 쿠키 인증에서 CSRF가 발생하는 이유를 설명합니다.
- `SameSite`, `Origin` 검사와 CSRF 토큰의 역할을 구분합니다.
- CORS가 브라우저의 교차 출처 응답 접근을 제어하는 규칙임을 설명합니다.
- CORS와 CSRF가 서로 다른 문제라는 점을 설명합니다.
- WebSocket 연결과 각 메시지에서 현재 권한을 확인합니다.

## 인증과 인가

인증(authentication)과 인가(authorization)는 서로 다른 질문입니다.

```text
인증(authentication)
→ 누가 요청했는가?

인가(authorization)
→ 그 사용자가 이 작업을 수행할 수 있는가?
```

예를 들어 세션 쿠키를 검증해 다음 사용자를 확인했다고 가정합니다.

```text
userId = user-42
```

이것만으로 다음 요청이 허용되는 것은 아닙니다.

```text
PATCH /notes/note-7
```

서버는 추가로 확인해야 합니다.

```text
user-42가 note-7의 구성원인가?
구성원이라면 현재 역할은 무엇인가?
note-7은 수정 가능한 상태인가?
계정이 현재 활성 상태인가?
```

인증은 사용자를 식별하고, 인가는 **특정 리소스에 대한 특정 행동**을 허용할지 판단합니다.

## 역할 기반 권한

예를 들어 메모에 다음 역할이 있다고 가정합니다.

| 역할 | 읽기 | 내용 수정 | 구성원 관리 | 삭제 |
|---|---:|---:|---:|---:|
| owner | 가능 | 가능 | 가능 | 가능 |
| editor | 가능 | 가능 | 불가 | 불가 |
| viewer | 가능 | 불가 | 불가 | 불가 |

이 표는 역할 기반 권한의 기본 규칙입니다.

하지만 실제 권한 판정에는 역할 이외의 조건도 포함될 수 있습니다.

```text
계정 상태
리소스 상태
현재 멤버십 존재 여부
조직 상태
보관 또는 삭제 상태
특정 기능 플래그
```

예를 들어 `editor`라도 보관된 메모는 수정하지 못하게 할 수 있습니다.

## 클라이언트가 보낸 역할을 믿지 않습니다

다음과 같은 요청 본문을 신뢰해서는 안 됩니다.

```json
{
  "noteId": "note-7",
  "role": "owner"
}
```

클라이언트가 `role: "owner"`라고 보냈다는 사실은 아무 권한도 증명하지 않습니다.

권한 판정에 필요한 역할과 소유권은 서버가 신뢰하는 저장소에서 읽습니다.

```text
request
→ actor 확인
→ note와 membership 조회
→ 저장된 membership.role 확인
→ 권한 판정
```

클라이언트 입력은 "무엇을 하려는가"를 표현할 수 있지만 "그 작업을 할 권한이 있다"는 증거가 되어서는 안 됩니다.

## UI 권한과 서버 권한

클라이언트 UI에서는 사용자의 역할에 따라 버튼을 숨길 수 있습니다.

```text
viewer
→ 수정 버튼 숨김

owner
→ 구성원 관리 버튼 표시
```

이것은 좋은 사용자 경험을 위한 기능입니다.

하지만 보안 경계는 아닙니다.

공격자는 화면의 버튼이 없어도 직접 요청을 보낼 수 있습니다.

```http
PATCH /notes/note-7
```

따라서 다음 원칙을 사용합니다.

```text
UI 권한 검사
→ 사용자가 할 수 없는 작업을 화면에서 숨김

서버 권한 검사
→ 실제 요청을 허용하거나 거부
```

서버 검사는 항상 필요합니다.

## 서버에서 하나의 권한 규칙을 사용합니다

같은 규칙을 HTTP 라우트, WebSocket 처리기와 백그라운드 작업에 각각 복사하면 시간이 지나면서 규칙이 달라질 수 있습니다.

예를 들어 다음과 같이 공통 정책 함수를 둘 수 있습니다.

```ts
function assertCanEditNote(
  actor: Actor,
  membership: Membership,
  note: Note
): void {
  if (actor.accountStatus !== "active") {
    throw new Forbidden("account_inactive");
  }

  if (note.archivedAt) {
    throw new Conflict("note_archived");
  }

  if (
    membership.role !== "owner" &&
    membership.role !== "editor"
  ) {
    throw new Forbidden("note_write_forbidden");
  }
}
```

이 함수는 세 종류의 조건을 구분합니다.

```text
actor 상태
→ 현재 사용자 계정이 사용 가능한가

resource 상태
→ 현재 메모가 수정 가능한가

relationship 상태
→ 현재 사용자가 이 메모에서 어떤 역할인가
```

HTTP와 WebSocket이 같은 의미의 작업을 수행한다면 같은 권한 규칙을 재사용합니다.

## 권한 판정과 데이터 조회

권한 검사는 모든 데이터를 읽은 뒤 애플리케이션에서 걸러 내는 방식으로만 구현할 필요는 없습니다.

현재 사용자에게 접근 가능한 행만 데이터베이스에서 조회할 수 있습니다.

```sql
select
  n.id,
  n.title,
  m.role
from notes as n
join note_members as m
  on m.note_id = n.id
where n.id = $1
  and m.user_id = $2;
```

이 쿼리는 다음 두 조건을 동시에 만족하는 경우만 행을 반환합니다.

```text
note id = 요청한 note
AND
membership.user_id = 현재 사용자
```

따라서 해당 사용자가 구성원이 아니면 결과가 없습니다.

이 방식은 다음 장점이 있습니다.

- 접근할 수 없는 행을 불필요하게 애플리케이션으로 가져오지 않습니다.
- 객체 수준 권한 조건이 쿼리에 드러납니다.
- 다른 사용자의 데이터가 우연히 상위 계층으로 전달될 가능성을 줄입니다.

## 객체 수준 권한

다음 API를 생각해 봅니다.

```text
PATCH /notes/{noteId}
```

`noteId`가 UUID 형식으로 올바르다는 것은 입력 형식만 검증한 것입니다.

```text
noteId가 올바른 형식
≠
현재 사용자가 noteId의 메모를 수정할 권한이 있음
```

또한 사용자가 이전 목록 조회에서 메모를 본 적이 있다는 사실도 현재 수정 권한을 보장하지 않습니다.

```text
10:00 viewer로 목록 조회
10:01 권한 제거
10:02 PATCH 요청
```

서버는 `PATCH`를 처리하는 시점의 현재 권한을 다시 검사해야 합니다.

이것이 객체 수준 권한(object-level authorization)의 핵심입니다.

## 쓰기 쿼리에도 권한 조건을 포함할 수 있습니다

간단한 소유권 규칙이라면 `UPDATE` 자체에 사용자 조건을 포함할 수 있습니다.

```sql
update notes
set title = $1
where id = $2
  and owner_id = $3
returning id, title;
```

이 경우 `id`만 맞고 `owner_id`가 다른 행은 수정되지 않습니다.

멤버십 기반 권한이라면 `EXISTS`를 사용할 수도 있습니다.

```sql
update notes as n
set title = $1
where n.id = $2
  and exists (
    select 1
    from note_members as m
    where m.note_id = n.id
      and m.user_id = $3
      and m.role in ('owner', 'editor')
  )
returning n.id, n.title;
```

이런 방식은 권한 검사와 실제 쓰기 사이에 상태가 바뀌는 간격을 줄이는 데 도움이 됩니다.

다만 모든 권한 규칙을 하나의 거대한 SQL로 표현해야 한다는 뜻은 아닙니다. 복잡한 규칙은 트랜잭션 안에서 필요한 상태를 읽고 검증한 뒤 수정할 수 있습니다.

## 인증과 인가 실패의 HTTP 상태

대표적으로 다음 세 상태를 구분합니다.

```text
401 Unauthorized
→ 유효한 인증 정보가 없거나 인증에 실패함

403 Forbidden
→ 사용자는 확인했지만 이 작업을 허용하지 않음

404 Not Found
→ 리소스가 없거나 정책상 존재 자체를 공개하지 않음
```

이름 때문에 혼동하기 쉽지만 HTTP의 `401 Unauthorized`는 실질적으로 **인증이 필요하거나 인증 정보가 유효하지 않음**을 나타냅니다.

## `401`

다음 경우에 사용할 수 있습니다.

```text
세션 쿠키 없음
세션 토큰이 유효하지 않음
세션 만료
세션 폐기
```

예:

```text
GET /me
→ 세션 없음
→ 401
```

API 인증 방식에 따라 표준 인증 challenge 헤더가 필요한 경우도 있으므로 사용하는 인증 프로토콜의 규칙을 따릅니다.

## `403`

사용자를 인증했지만 작업 권한이 없을 때 사용할 수 있습니다.

```text
actor = user-42
role = viewer

PATCH /notes/note-7
→ 403
```

이 응답은 일반적으로 "리소스는 있지만 이 사용자는 이 작업을 할 수 없다"는 정보를 어느 정도 드러냅니다.

관리 도구나 내부 시스템처럼 권한 부족 이유를 명확히 알려야 하는 경우 적합할 수 있습니다.

## 존재를 숨기기 위한 `404`

비공개 객체의 존재 여부 자체가 민감하다면 구성원이 아닌 사용자에게 `403` 대신 `404`를 반환할 수 있습니다.

```text
note-7 존재
하지만 user-42는 구성원이 아님
→ 정책상 404
```

이 방식은 외부 사용자가 ID를 추측해 리소스 존재 여부를 알아내는 정보를 줄입니다.

중요한 것은 실제 데이터베이스에 행이 없다는 뜻으로만 `404`를 사용해야 한다는 것이 아니라, **외부 API가 리소스 존재를 공개하지 않기로 한 정책**으로 사용할 수 있다는 점입니다.

## `403`과 `404` 선택은 일관되어야 합니다

같은 종류의 비공개 리소스에서 일부 엔드포인트는 `403`, 일부는 `404`를 반환하면 공격자가 응답 차이로 존재 여부를 추론할 수 있습니다.

따라서 API 수준에서 정책을 정합니다.

예:

```text
비공개 note
→ 비구성원에게 항상 404

관리 API
→ 인증된 관리자에게 권한 부족을 명시적으로 403
```

권한 오류 메시지와 응답 시간에서도 필요 이상으로 리소스 존재 정보를 노출하지 않는지 검토합니다.

## 역할 변경은 별도의 권한 규칙입니다

메모 내용을 수정하는 권한과 구성원 역할을 바꾸는 권한은 서로 다를 수 있습니다.

예를 들어 다음 규칙을 둘 수 있습니다.

- `owner`만 역할을 변경할 수 있습니다.
- 마지막 `owner`를 `editor`나 `viewer`로 낮출 수 없습니다.
- 사용자는 자신의 권한을 요청 본문으로 임의 상승시킬 수 없습니다.
- 정지된 사용자를 새 구성원으로 추가하지 않습니다.
- 변경 전 역할, 변경 후 역할과 수행자를 감사 기록에 남깁니다.
- 멤버십 변경과 감사 기록은 함께 커밋합니다.

이런 규칙은 단순히 `role = 'owner'` 하나만 확인하는 것보다 더 많은 상태를 필요로 합니다.

## 마지막 소유자 규칙은 동시성을 고려합니다

다음과 같은 애플리케이션 로직만 사용한다고 가정합니다.

```text
1. owner 수를 SELECT
2. 2명 이상이면 현재 owner를 viewer로 변경
```

동시에 두 owner가 각각 자신을 강등하면 둘 다 1단계에서 `owner = 2`를 볼 수 있습니다.

```text
요청 A: owner 수 = 2
요청 B: owner 수 = 2

A: owner → viewer
B: owner → viewer
```

최종적으로 owner가 0명이 될 수 있습니다.

따라서 "항상 최소 한 명의 owner가 있어야 한다"처럼 여러 행에 걸친 규칙은 트랜잭션과 적절한 잠금 또는 데이터 모델을 사용해 경쟁 요청까지 고려해야 합니다.

개념적으로는 다음처럼 처리할 수 있습니다.

```text
BEGIN
→ 관련 membership 행 잠금
→ 현재 owner 수 확인
→ 변경 가능 여부 판정
→ 역할 UPDATE
→ 감사 INSERT
COMMIT
```

구체적인 잠금 전략은 스키마와 수정 패턴에 따라 정합니다.

## 권한 변경과 감사 기록

관리 작업에서는 변경 자체와 감사 기록이 서로 어긋나지 않게 하는 것이 중요할 수 있습니다.

```text
membership 변경 성공
→ audit INSERT 실패
```

이 상태를 허용할 수 없다면 하나의 트랜잭션으로 묶습니다.

```ts
await db.transaction().execute(async (trx) => {
  await changeMembership(trx, command);
  await appendAuditLog(trx, command);
});
```

감사 로그에는 비밀번호, 세션 토큰 같은 인증 비밀값을 기록하지 않습니다.

## CSRF가 생기는 이유

CSRF(cross-site request forgery)는 사용자가 로그인한 브라우저의 인증 정보를 다른 사이트가 의도하지 않은 요청에 이용하는 공격입니다.

쿠키 기반 인증에서 중요한 특징은 **브라우저가 요청에 쿠키를 자동으로 붙일 수 있다는 점**입니다.

예를 들어 사용자가 다음 사이트에 로그인해 있다고 가정합니다.

```text
https://app.example.com
```

브라우저에는 다음 인증 쿠키가 있습니다.

```text
app_session=<secret>
```

그 상태에서 공격자가 만든 다른 사이트를 방문합니다.

```text
https://attacker.example
```

공격자 페이지는 특정 조건에서 사용자의 브라우저가 `app.example.com`으로 요청을 보내도록 유도할 수 있습니다.

공격자가 세션 쿠키의 원문을 직접 읽지 못하더라도 브라우저가 대상 사이트로 쿠키를 자동 전송한다면 상태 변경 요청이 인증된 것처럼 처리될 위험이 있습니다.

## CSRF의 핵심 조건

다음 세 요소를 구분하면 이해하기 쉽습니다.

```text
공격자 사이트
→ 사용자의 브라우저에서 요청 생성

브라우저
→ 대상 사이트에 적용되는 cookie를 자동 첨부할 수 있음

대상 서버
→ 요청이 사용자의 의도에서 시작했는지 확인하지 않으면
   인증된 상태 변경으로 처리할 수 있음
```

따라서 쿠키 인증에서는 "세션 쿠키가 유효하다"만 확인해서는 충분하지 않을 수 있습니다.

## 상태를 바꾸는 `GET`을 만들지 않습니다

HTTP의 `GET`은 조회처럼 안전한 작업에 사용해야 합니다.

다음과 같은 API는 피합니다.

```text
GET /account/delete
GET /notes/123/archive
```

브라우저는 이미지, 링크 탐색, 프리페치 등 여러 상황에서 `GET`을 쉽게 만들 수 있습니다.

상태 변경에는 `POST`, `PUT`, `PATCH`, `DELETE` 같은 적절한 메서드를 사용하고 CSRF 방어를 적용합니다.

메서드 이름 자체가 보안을 보장하는 것은 아니지만 안전한 HTTP 의미와 브라우저 방어를 구성하는 기본 전제가 됩니다.

## 쿠키 인증의 CSRF 방어

쿠키 기반 상태 변경 요청에서는 서비스 구조에 맞게 여러 방어를 조합합니다.

대표적으로 다음을 사용합니다.

1. 적절한 `SameSite` 쿠키
2. HTTPS와 `Secure` 쿠키
3. 신뢰하는 `Origin`의 정확한 검사
4. 필요하면 CSRF 토큰
5. 상태를 바꾸는 `GET` 금지

각 방어는 같은 기능이 아닙니다.

```text
SameSite
→ 교차 사이트 상황에서 cookie 전송 범위를 제한

Secure
→ cookie가 평문 HTTP로 전송되지 않게 함

Origin 검사
→ 요청을 시작한 origin이 허용된 곳인지 확인

CSRF token
→ 공격자 사이트가 알 수 없는 추가 값을 요구
```

`Secure`는 전송 보안에 중요하지만 그 자체가 CSRF 공격의 논리를 막는 것은 아닙니다. 여러 방어를 각각의 목적에 맞게 사용합니다.

## `site`와 `origin`은 같은 개념이 아닙니다

`SameSite`의 **site**와 CORS·`Origin` 검사의 **origin**은 같은 경계가 아닙니다.

origin은 일반적으로 다음 세 요소의 조합입니다.

```text
scheme + host + port
```

예:

```text
https://app.example.com
https://app.example.com:8443
http://app.example.com
```

이들은 서로 다른 origin일 수 있습니다.

반면 브라우저의 SameSite 판정은 site 개념을 사용합니다. 따라서 `SameSite` 정책과 정확한 `Origin` 검사를 같은 것으로 생각하지 않습니다.

## `SameSite`

세션 쿠키에 `SameSite`를 설정하면 교차 사이트 요청에서 쿠키가 전송되는 범위를 제한할 수 있습니다.

대표적인 값은 다음과 같습니다.

```text
Strict
→ 교차 사이트 상황에서 가장 엄격하게 제한

Lax
→ 일부 최상위 탐색 등에서는 전송될 수 있지만
   일반적인 교차 사이트 상태 변경 요청을 줄여 줌

None
→ 교차 사이트에서도 전송 가능
   일반적으로 Secure가 필요
```

많은 일반 웹 애플리케이션에서는 `Lax`가 유용한 기본값이 될 수 있지만 실제 프론트엔드와 API 배치에 따라 달라집니다.

교차 사이트 쿠키가 반드시 필요해 `SameSite=None`을 사용하는 경우에는 `Origin` 검사와 CSRF 토큰 같은 방어가 더 중요해집니다.

## `Origin` 검사

상태 변경 요청이 신뢰하는 브라우저 출처에서 시작했는지 검사할 수 있습니다.

```ts
function requireTrustedOrigin(
  origin: string | undefined,
  allowed: Set<string>
): void {
  if (!origin || !allowed.has(origin)) {
    throw new Forbidden("untrusted_origin");
  }
}
```

허용 목록은 정확한 origin 문자열로 관리합니다.

```ts
const allowedOrigins = new Set([
  "https://app.example.com",
  "https://admin.example.com"
]);
```

다음처럼 접두사나 접미사만 비교하면 안 됩니다.

```text
startsWith("https://trusted.example")
endsWith("example.com")
```

예를 들어 잘못된 접두사 비교는 다음 공격자 주소를 허용할 수 있습니다.

```text
https://trusted.example.attacker.test
```

origin은 정규화된 **scheme, host, port의 정확한 조합**으로 비교합니다.

## `Origin`이 없는 요청

모든 HTTP 클라이언트가 항상 `Origin` 헤더를 보내는 것은 아닙니다.

브라우저 요청의 종류에 따라서도 헤더 존재 조건이 달라질 수 있습니다.

따라서 다음 정책을 명시적으로 정합니다.

```text
브라우저 전용 상태 변경 API
→ Origin 없으면 거부

서버 간 API
→ cookie 인증을 사용하지 않거나
   별도의 인증 방식으로 분리

특수 클라이언트
→ 요구사항에 맞는 별도 정책
```

`Origin`이 없다는 이유만으로 무조건 신뢰해서는 안 됩니다.

필요한 경우 `Referer`를 보조 신호로 사용하는 정책도 있을 수 있지만 민감한 상태 변경에서는 명확한 인증 방식과 요청 출처 정책을 우선 설계합니다.

## CSRF 토큰

세션과 별도로 공격자 사이트가 알기 어려운 값을 상태 변경 요청에 요구할 수 있습니다.

개념적으로 다음 흐름입니다.

```text
서버가 CSRF token 준비
→ 정상 페이지가 token을 얻음
→ 상태 변경 요청에 token 포함
→ 서버가 token 검증
```

공격자 사이트는 사용자의 세션 쿠키가 자동으로 전송되게 만들 수 있더라도 CSRF 토큰을 읽거나 올바른 값을 만들 수 없어야 합니다.

토큰은 다음 조건을 만족해야 합니다.

- 예측하기 어렵습니다.
- 공격자 사이트에서 읽을 수 없습니다.
- 현재 세션과 연결되거나 서버가 검증 가능한 구조입니다.
- 비교할 때 비밀값 비교에 적합한 방법을 사용합니다.
- 로그에 원문을 남기지 않습니다.
- 세션 교체나 로그아웃 정책과 함께 수명 주기를 정합니다.

## CSRF 토큰 전달 위치

CSRF 토큰은 상태 변경 요청의 헤더나 본문에 넣을 수 있습니다.

예:

```http
X-CSRF-Token: <token>
```

공격자 사이트가 단순 HTML 폼만으로 임의의 커스텀 헤더를 붙이지 못한다는 점을 이용할 수 있습니다.

그러나 토큰을 쿠키에만 넣고 브라우저가 자동 전송하게 만들면 "공격자가 알 수 없는 추가 값"이라는 목적을 달성하지 못할 수 있습니다.

사용하는 CSRF 패턴이 무엇인지 명확히 정하고 라이브러리의 검증된 구현을 우선 사용합니다.

## CSRF 토큰과 XSS

CSRF 토큰은 XSS를 막지 않습니다.

공격자가 정상 사이트의 JavaScript 실행 권한을 얻으면 페이지가 접근할 수 있는 CSRF 토큰을 읽고 정상 요청처럼 사용할 수 있을 수 있습니다.

```text
CSRF 방어
→ 다른 사이트에서 시작된 요청을 방어

XSS 방어
→ 신뢰한 사이트 자체에서 공격자 script가 실행되는 것을 방어
```

따라서 둘은 별개의 보안 문제입니다.

## CORS란 무엇인가

CORS(Cross-Origin Resource Sharing)는 브라우저의 same-origin policy를 완화하기 위한 HTTP 기반 규칙입니다.

핵심 질문은 다음과 같습니다.

```text
이 origin에서 실행 중인 JavaScript가
다른 origin의 응답을 읽도록 브라우저가 허용할 것인가?
```

예를 들어

```text
페이지:
https://app.example.com

API:
https://api.example.com
```

는 서로 다른 origin입니다.

브라우저가 교차 origin 응답을 JavaScript에 공개할지 서버의 CORS 응답 헤더를 보고 판단할 수 있습니다.

## CORS는 인증이나 인가가 아닙니다

CORS는 사용자가 누구인지 확인하지 않습니다.

또한 해당 사용자가 어떤 데이터에 접근할 권한이 있는지도 결정하지 않습니다.

```text
CORS
→ 브라우저가 응답을 JavaScript에 공개할지 결정

authentication
→ 사용자가 누구인지 확인

authorization
→ 사용자가 리소스를 사용할 수 있는지 확인
```

따라서 다음처럼 생각하면 안 됩니다.

```text
"허용된 origin에서 왔으니 관리자 요청이다"
```

허용된 origin에서도 권한 없는 사용자가 요청할 수 있습니다.

## CORS는 `curl`이나 서버 간 요청을 막지 않습니다

CORS는 브라우저 보안 모델입니다.

다음 클라이언트는 브라우저의 CORS 정책에 구속되지 않습니다.

```text
curl
서버 프로그램
Postman 같은 API 클라이언트
공격자가 직접 만든 HTTP 클라이언트
```

따라서 CORS 설정을 접근 제어 수단으로 사용할 수 없습니다.

서버는 CORS와 별개로 인증과 권한을 검사해야 합니다.

## CORS가 요청 자체를 항상 막는 것은 아닙니다

이 점은 CSRF와 CORS를 구분할 때 중요합니다.

브라우저는 일부 교차 origin 요청을 실제 서버로 전송할 수 있고, CORS 정책에 따라 **응답을 공격자 JavaScript에 공개하지 않을 수 있습니다.**

즉 다음 상황이 가능합니다.

```text
공격자 페이지
→ 상태 변경 요청 전송
→ 서버가 요청 처리
→ 데이터 변경 발생
→ 브라우저는 CORS 때문에 응답 본문을 공격자에게 숨김
```

서버의 상태가 이미 바뀌었다면 공격자가 응답을 읽지 못한다는 사실만으로 CSRF가 방어된 것은 아닙니다.

따라서 다음 등식은 잘못되었습니다.

```text
CORS 설정
≠
CSRF 방어 전체
```

## CORS 허용 origin

허용할 origin은 명시적으로 관리합니다.

```ts
const allowedOrigins = new Set([
  "https://app.example.com",
  "https://admin.example.com"
]);
```

요청의 `Origin` 값을 아무 검사 없이 그대로 응답에 반영하지 않습니다.

다음과 같은 구현은 위험합니다.

```text
request Origin
→ 그대로 Access-Control-Allow-Origin에 복사
```

이렇게 하면 사실상 임의의 origin을 허용할 수 있습니다.

## 인증 정보를 포함한 CORS 요청

브라우저가 쿠키나 HTTP 인증 정보 같은 credentials를 교차 origin 요청에 포함하도록 허용하는 경우 서버 설정도 그에 맞아야 합니다.

이 경우 임의 출처를 뜻하는 와일드카드 `*`와 credentials 허용을 함께 사용하는 식의 구성은 사용할 수 없습니다.

대신 요청 origin이 허용 목록에 있는지 확인한 뒤 해당 origin을 명시적으로 응답합니다.

개념적으로는 다음과 같습니다.

```text
Origin = https://app.example.com
→ allowlist에 있음
→ Access-Control-Allow-Origin:
   https://app.example.com
→ 필요한 경우 credentials 허용
```

동적으로 origin을 반영한다면 캐시가 서로 다른 origin의 응답 헤더를 잘못 재사용하지 않도록 `Vary: Origin` 같은 캐시 정책도 확인합니다.

## 허용 메서드와 헤더를 좁힙니다

CORS 설정에서는 필요한 범위만 허용합니다.

예를 들어 API가 실제로 다음만 필요하다면

```text
GET
POST
PATCH
DELETE

Content-Type
X-CSRF-Token
```

모든 메서드와 모든 헤더를 불필요하게 허용하지 않습니다.

이는 서버의 인증·인가를 대신하지 않지만 브라우저에서 허용하는 교차 origin 표면을 명확하게 유지하는 데 도움이 됩니다.

## 프리플라이트 요청

일부 교차 origin 요청에서 브라우저는 실제 요청 전에 `OPTIONS` 프리플라이트(preflight) 요청을 보냅니다.

예를 들어 커스텀 헤더나 특정 메서드를 사용하는 요청이 대상이 될 수 있습니다.

개념적인 흐름은 다음과 같습니다.

```text
브라우저
→ OPTIONS preflight

서버
→ 이 origin / method / header를 허용하는지 응답

브라우저
→ 허용되면 실제 요청 전송
```

프리플라이트는 브라우저가 CORS 정책을 확인하기 위한 절차입니다.

CSRF 방어와 같은 개념은 아닙니다.

또한 모든 교차 origin 요청이 반드시 프리플라이트를 거치는 것은 아닙니다. 따라서 "프리플라이트가 있으니 공격 요청은 서버에 도달하지 않는다"고 가정해서는 안 됩니다.

## CORS와 CSRF 비교

두 개념을 나란히 보면 차이가 명확합니다.

| 구분 | CSRF | CORS |
|---|---|---|
| 핵심 문제 | 사용자의 인증 정보를 이용한 원하지 않는 요청 | 다른 origin의 JavaScript가 응답을 읽는 것 |
| 주 대상 | 상태 변경 요청 | 브라우저의 교차 origin 읽기 |
| 대표 방어 | `SameSite`, `Origin` 검사, CSRF 토큰 | `Access-Control-Allow-*` 설정 |
| 인증을 대신하는가 | 아니오 | 아니오 |
| 서버 간 요청을 막는가 | 해당 없음 | 아니오 |
| 요청 부수 효과를 자동 차단하는가 | 방어 구현에 따라 | 아니오 |

두 기능은 함께 사용할 수 있지만 서로를 대체하지 않습니다.

## 정확한 Origin 허용 목록

CSRF 검사와 CORS 설정 모두 origin 허용 목록을 사용할 수 있습니다.

다음처럼 정확한 문자열 집합을 하나의 설정으로 관리하면 정책 차이를 줄일 수 있습니다.

```ts
const trustedOrigins = new Set([
  "https://app.example.com",
  "https://admin.example.com"
]);
```

다만 "CORS에서 허용하는 origin"과 "쿠키 기반 상태 변경을 허용하는 origin"이 반드시 항상 같은 집합이어야 하는 것은 아닙니다.

예를 들어 읽기 전용 공개 API는 더 넓은 CORS 정책을 가질 수 있지만 인증된 관리 요청은 더 좁은 origin만 허용할 수 있습니다.

목적이 다르면 별도 allowlist를 둡니다.

## WebSocket과 인증

브라우저의 WebSocket 연결은 HTTP 업그레이드 요청으로 시작합니다.

쿠키 기반 인증을 사용한다면 브라우저가 해당 서버의 쿠키를 업그레이드 요청에 포함할 수 있습니다.

따라서 연결을 열 때 최소한 다음을 확인합니다.

- 세션이 존재하는가
- 세션이 만료되거나 폐기되지 않았는가
- 사용자 계정이 활성 상태인가
- 브라우저가 보낸 `Origin`이 허용된 값인가

WebSocket은 일반적인 `fetch` CORS 처리와 똑같이 생각하면 안 됩니다. 서버가 업그레이드 요청의 `Origin`을 직접 검증하는 것이 중요합니다.

## WebSocket `Origin`

브라우저 WebSocket 업그레이드 요청에는 일반적으로 `Origin` 헤더가 포함됩니다.

서버는 예상한 정확한 origin인지 검사합니다.

```text
Origin:
https://app.example.com
```

허용되지 않은 origin이면 연결을 승인하지 않습니다.

이 검사는 특히 쿠키가 자동으로 포함되는 WebSocket 인증에서 다른 사이트가 사용자의 브라우저를 통해 연결을 시도하는 위험을 줄이는 데 중요합니다.

## 연결 시 권한만 검사하면 부족합니다

WebSocket은 수 분 또는 수 시간 동안 열려 있을 수 있습니다.

연결 순간에 사용자가 `editor`였더라도 연결 중 역할이 바뀔 수 있습니다.

```text
10:00 WebSocket 연결
      role = editor

10:05 관리자가 viewer로 변경

10:10 기존 socket에서 note.update 전송
```

10:00에 한 검사만 사용한다면 오래된 권한으로 10:10의 쓰기를 허용할 수 있습니다.

따라서 쓰기 메시지를 처리할 때 현재 권한을 다시 확인해야 합니다.

## WebSocket 메시지별 권한 검사

예를 들어 다음 메시지를 받았다고 가정합니다.

```json
{
  "type": "note.update",
  "noteId": "note-7",
  "title": "new title"
}
```

서버는 단순히 "이 socket은 인증됨"만 확인하지 않습니다.

```text
socket의 사용자 식별
→ noteId 형식 검사
→ 현재 membership 조회
→ 현재 note 상태 조회
→ note.update 권한 판정
→ UPDATE
```

HTTP의 `PATCH /notes/{id}`와 같은 의미의 작업이라면 가능한 한 같은 권한 정책을 사용합니다.

## 역할 변경 시 연결 무효화

메시지마다 데이터베이스에서 역할을 다시 읽는 비용이 큰 시스템에서는 다른 전략도 사용할 수 있습니다.

예를 들어 역할 변경 이벤트가 발생했을 때 관련 WebSocket 연결을 끊거나 해당 권한 캐시를 무효화할 수 있습니다.

```text
membership 변경
→ 관련 connection 찾기
→ 권한 cache invalidation
또는
→ connection close
```

이 방법을 사용하려면 누락 없이 무효화 이벤트가 전달되는지 별도의 신뢰성 문제가 생깁니다.

따라서 단순한 시스템에서는 쓰기 시점에 현재 권한을 다시 조회하는 방식이 이해하기 쉽고 안전한 기준이 될 수 있습니다.

## `board.join` 같은 구독도 권한 검사 대상입니다

쓰기 메시지만 위험한 것은 아닙니다.

다른 사용자의 비공개 채널에 가입하면 읽기 권한을 우회할 수 있습니다.

```text
board.join
note.subscribe
room.enter
```

따라서 구독 또는 join 요청에서도 대상 리소스에 대한 현재 읽기 권한을 검사합니다.

```text
socket 인증됨
≠
모든 room에 join 가능
```

## 캐시된 권한의 수명

성능을 위해 멤버십이나 역할을 메모리에 캐시할 수 있습니다.

하지만 캐시를 사용한다면 "권한이 변경된 뒤 얼마 동안 이전 권한을 허용할 수 있는가"라는 문제가 생깁니다.

보안상 즉시 반영이 필요한 규칙이라면 다음 중 하나가 필요합니다.

```text
매 쓰기마다 현재 DB 확인
짧은 TTL
명시적 cache invalidation
역할 변경 시 연결 종료
```

권한 캐시는 일반 데이터 캐시보다 만료 정책을 더 엄격하게 볼 필요가 있습니다.

## 검증 행렬

권한과 브라우저 보안 정책은 역할별 정상 경로만 검사하지 말고 거부 경로도 함께 테스트합니다.

```text
인증 정보 없음
→ 401

만료된 세션
→ 401

폐기된 세션
→ 401

구성원이 아님
→ 403 또는 정책상 404

viewer
→ 읽기 성공
→ 내용 수정 거부
→ 역할 변경 거부

editor
→ 읽기 성공
→ 내용 수정 성공
→ 역할 변경 거부

owner
→ 허용된 관리자 작업 성공

다른 사용자의 리소스 ID
→ 거부

정지된 사용자의 세션
→ 거부

신뢰하지 않는 Origin의 상태 변경 요청
→ 거부

CSRF token이 필요한 API에서 token 없음
→ 거부

잘못된 CSRF token
→ 거부

WebSocket 신뢰하지 않는 Origin
→ 연결 거부

WebSocket join 대상에 읽기 권한 없음
→ 거부

WebSocket 연결 뒤 editor → viewer 변경
→ 이후 쓰기 거부
```

HTTP와 WebSocket에서 같은 비즈니스 작업에는 같은 역할 규칙을 적용합니다.

## 권한 테스트에서 확인할 것

객체 수준 권한 테스트에서는 자신의 리소스만 검사하지 않습니다.

최소한 다음을 포함합니다.

```text
내 리소스
다른 사용자의 리소스
같은 역할이지만 다른 리소스
역할이 다른 사용자
멤버십이 제거된 사용자
정지된 사용자
존재하지 않는 리소스
```

특히 IDOR(Insecure Direct Object Reference) 같은 문제는 공격자가 URL이나 요청 본문의 객체 ID를 다른 값으로 바꿔 접근하는 상황에서 나타납니다.

따라서 다음 테스트가 중요합니다.

```text
정상:
PATCH /notes/my-note

공격 시도:
PATCH /notes/other-users-note
```

ID가 유효한지뿐 아니라 현재 사용자와 대상 객체의 관계를 검사해야 합니다.

## CSRF 테스트에서 확인할 것

쿠키 인증 상태 변경 API에서는 다음을 검사합니다.

```text
신뢰한 Origin + 유효한 session + 유효한 CSRF 조건
→ 성공

신뢰하지 않는 Origin
→ 거부

Origin 없음
→ 정한 정책대로 처리

CSRF token 누락
→ 거부

CSRF token 불일치
→ 거부

GET으로 상태 변경 시도
→ 해당 API 자체가 존재하지 않음
```

테스트에서는 서버가 반환하는 CORS 헤더만 보는 것이 아니라 실제 상태 변경이 일어났는지도 확인합니다.

## CORS 테스트에서 확인할 것

```text
허용 origin
→ 올바른 Access-Control-Allow-Origin

허용하지 않은 origin
→ CORS 허용 응답 없음

credentials 사용
→ wildcard origin 사용하지 않음

필요한 preflight
→ 허용 method/header만 응답

동적 origin
→ 캐시 정책 확인
```

CORS 테스트를 통과했다고 서버 인증과 권한 테스트를 생략하지 않습니다.

## 흔한 실수

- 화면에서 버튼을 숨긴 것으로 권한 검사를 끝냅니다.
- 로그인한 사용자라면 모든 리소스에 접근할 수 있다고 가정합니다.
- 클라이언트가 보낸 `role`, `ownerId`, `userId`를 권한의 근거로 믿습니다.
- ID 형식 검사를 객체 수준 권한 검사로 착각합니다.
- 이전 목록 조회에서 보였다는 이유로 현재 쓰기 권한도 있다고 가정합니다.
- 모든 데이터를 읽은 뒤에야 권한 없는 행을 필터링합니다.
- 권한 검사와 실제 쓰기 사이에 멤버십이 바뀔 수 있다는 점을 무시합니다.
- 마지막 owner 보호 규칙을 단순한 선행 `SELECT`만으로 구현해 경쟁 요청을 놓칩니다.
- 역할 변경과 감사 기록을 서로 다른 트랜잭션에 저장합니다.
- `401`, `403`, `404`를 아무 기준 없이 섞어 사용합니다.
- 비공개 리소스의 존재 여부를 오류 차이로 노출합니다.
- 쿠키가 `HttpOnly`이므로 CSRF가 불가능하다고 생각합니다.
- `SameSite`의 site와 CORS의 origin을 같은 개념으로 생각합니다.
- `Secure` 쿠키 하나만으로 CSRF가 해결된다고 생각합니다.
- 상태를 변경하는 `GET` 엔드포인트를 만듭니다.
- `Origin`을 접두사나 접미사로 비교합니다.
- `Origin`이 없으면 무조건 신뢰합니다.
- CSRF 토큰을 로그에 기록합니다.
- CORS를 인증 또는 권한 제어 수단으로 사용합니다.
- CORS가 `curl`이나 서버 간 요청도 막는다고 생각합니다.
- CORS가 응답을 숨기므로 서버의 상태 변경도 일어나지 않는다고 생각합니다.
- 요청의 `Origin`을 검증 없이 `Access-Control-Allow-Origin`에 그대로 반영합니다.
- credentials를 사용하는 CORS에 임의 origin을 허용합니다.
- 모든 교차 origin 요청이 preflight를 거친다고 생각합니다.
- WebSocket도 일반 `fetch` CORS 설정만 하면 충분하다고 생각합니다.
- WebSocket 연결 순간에만 권한을 확인합니다.
- 인증된 WebSocket이면 모든 room이나 board에 join할 수 있다고 가정합니다.
- 권한 캐시를 사용하면서 역할 변경 뒤 무효화 정책을 정하지 않습니다.

## 완료 기준

- 인증과 인가가 각각 어떤 질문에 답하는지 설명할 수 있습니다.
- 로그인 상태와 객체 수준 권한을 구분할 수 있습니다.
- 역할, 소유권, 계정 상태와 리소스 상태를 서버에서 판정할 수 있습니다.
- 클라이언트가 보낸 역할이나 소유자 ID를 권한의 근거로 신뢰하지 않을 수 있습니다.
- 현재 사용자에게 접근 가능한 행만 조회하거나 쓰기 쿼리에 권한 조건을 포함할 수 있습니다.
- `401`, `403`, 정책상 `404`를 어떤 상황에 사용하는지 설명할 수 있습니다.
- 마지막 owner 보호처럼 여러 행의 상태가 필요한 규칙에서 동시 요청을 고려할 수 있습니다.
- 역할 변경과 감사 기록을 하나의 트랜잭션으로 묶어야 하는 경우를 설명할 수 있습니다.
- 쿠키 기반 인증에서 CSRF가 발생하는 이유를 설명할 수 있습니다.
- `SameSite`, `Secure`, `Origin` 검사와 CSRF 토큰이 각각 어떤 역할을 하는지 설명할 수 있습니다.
- `site`와 `origin`의 개념이 같지 않다는 점을 설명할 수 있습니다.
- 상태 변경을 `GET`으로 구현하면 안 되는 이유를 설명할 수 있습니다.
- origin을 scheme, host, port의 정확한 조합으로 비교할 수 있습니다.
- CORS가 브라우저의 교차 origin 응답 공개를 제어하며 인증·인가를 대신하지 않는다는 점을 설명할 수 있습니다.
- CORS가 `curl`이나 서버 간 요청을 막지 않는다는 점을 설명할 수 있습니다.
- CORS 실패가 서버의 상태 변경 자체를 자동으로 막는 것은 아니라는 점을 설명할 수 있습니다.
- credentials를 허용하는 CORS에서 origin을 명시적으로 제한할 수 있습니다.
- preflight와 실제 요청의 차이를 설명할 수 있습니다.
- WebSocket 업그레이드에서 세션과 정확한 `Origin`을 검사할 수 있습니다.
- WebSocket의 join·subscribe·write 메시지마다 현재 리소스 권한을 확인할 수 있습니다.
- 연결 중 역할이 바뀌었을 때 재조회, 캐시 무효화 또는 연결 종료 정책을 적용할 수 있습니다.
