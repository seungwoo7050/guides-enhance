# DNS, HTTP, TLS와 QUIC

웹 요청 하나는 이름 해석, 주소 후보 선택, 경로 조회, 전송 연결, 암호화 협상, HTTP 처리를 차례로 거칩니다. 이 문서는 HTTP 애플리케이션 설계보다 각 프로토콜이 다음 단계에 어떤 값을 넘기고, 실패했을 때 어떤 관찰값을 남기는지 설명합니다.

## 학습 목표

- DNS, IP, 전송, TLS, HTTP의 성공 여부를 따로 기록합니다.
- 여러 주소 후보와 대체 프로토콜이 최종 결과를 만드는 과정을 추적합니다.
- TLS 인증 성공과 HTTP 인증·인가 성공을 구분합니다.

## DNS

애플리케이션의 stub resolver는 재귀 리졸버에 질의합니다. 캐시에 답이 없으면 재귀 리졸버가 루트, TLD, 권한 서버를 따라가 답을 얻을 수 있습니다. 실제 환경에서는 전달 리졸버, split-horizon DNS, hosts 파일, 프로세스별 캐시가 개입할 수 있습니다.

대표적인 레코드는 다음과 같습니다.

| 레코드 | 의미 |
|---|---|
| A | IPv4 주소 후보 |
| AAAA | IPv6 주소 후보 |
| CNAME | 다른 정규 이름으로 이어지는 별칭 |
| MX | 메일 서버와 우선순위 |
| NS | 영역의 권한 네임 서버 |
| TXT | 텍스트 기반 검증 또는 운영 정보 |
| HTTPS | 서비스 종단점, ALPN, 주소 힌트 등의 정보 |

TTL은 응답을 캐시할 수 있는 시간을 안내합니다. 애플리케이션, 운영체제, 브라우저, 중간 리졸버가 서로 다른 캐시를 가질 수 있으므로 권한 레코드를 바꾼 직후 모든 클라이언트가 동시에 새 값을 사용하지는 않습니다. NXDOMAIN 같은 부정 응답도 캐시될 수 있습니다.

전통적인 DNS는 UDP와 TCP 53번 포트를 모두 사용할 수 있습니다. 응답이 잘렸거나 전송 규칙상 필요한 경우 TCP를 사용하며, DoT와 DoH는 암호화된 다른 전송 경로를 사용합니다. "DNS는 항상 UDP를 사용합니다"라고 설명해서는 안 됩니다.

## 주소 후보 선택

A와 AAAA가 모두 있으면 클라이언트는 주소 체계, 실제 경로, 연결 진행 상황을 보고 여러 후보를 시도할 수 있습니다. DNS 응답의 첫 주소와 실제 연결에 성공한 주소가 같다고 가정해서는 안 됩니다.

다음 내용을 기록합니다.

```text
질의한 이름과 리졸버
A, AAAA, HTTPS 응답
캐시 출처와 남은 TTL
실제로 시도한 주소와 순서
각 시도의 시작 시각과 오류
최종 선택 주소와 출력 인터페이스
```

숫자 주소로는 성공하고 이름으로만 실패하면 DNS와 주소 선택을 먼저 확인합니다. 숫자 주소도 실패하면 경로와 전송 단계로 이동합니다.

## HTTP 의미와 전송 방식

HTTP는 메서드, 요청 대상, 필드, 상태 코드, 표현의 의미를 정의합니다. HTTP/1.1, HTTP/2, HTTP/3은 같은 HTTP 의미를 서로 다른 프레이밍과 전송 방식으로 전달할 수 있습니다.

```text
HTTP 의미
GET /items/42
Host 또는 :authority
Accept

전송 방식
HTTP/1.1 메시지
HTTP/2 프레임과 스트림
HTTP/3 프레임과 QUIC 스트림
```

메서드의 안전성과 멱등성은 프로토콜 의미입니다. 실제 서비스가 그 의미를 지키는지는 애플리케이션에서 검증해야 합니다.

## HTTP/1.1, HTTP/2와 HTTP/3

HTTP/1.1은 텍스트 메시지 프레이밍과 지속 연결을 사용합니다. `Content-Length`, chunked coding, 연결 종료가 메시지 경계를 정할 수 있습니다.

HTTP/2는 하나의 TCP 연결에 이진 프레임과 여러 스트림을 다중화합니다. 한 스트림의 애플리케이션 처리가 늦어도 다른 스트림의 프레임을 보낼 수 있지만, TCP 바이트 하나가 손실되면 그 뒤의 모든 스트림 바이트가 TCP의 순서 복구를 기다릴 수 있습니다.

HTTP/3는 QUIC 스트림 위에 HTTP를 매핑합니다. 한 QUIC 스트림의 손실은 다른 스트림에 이미 도착한 데이터를 TCP의 전역 바이트 순서처럼 막지 않습니다. 다만 같은 스트림 안의 순서와 QPACK 의존성은 남아 있으므로 head-of-line blocking이 모든 위치에서 사라진다고 표현해서는 안 됩니다.

## TLS

TLS는 서버 인증, 선택적인 클라이언트 인증, 기밀성, 무결성, 협상한 키를 제공합니다. 일반적인 클라이언트는 인증서 체인과 요청한 호스트 이름을 확인합니다.

인증서가 유효해도 애플리케이션 권한이 허용된다는 뜻은 아닙니다. TLS에 성공한 뒤에도 HTTP `401`, `403`이나 애플리케이션 오류가 발생할 수 있습니다.

- SNI는 클라이언트가 연결하려는 서버 이름을 핸드셰이크에 전달합니다.
- ALPN은 `h2`, `http/1.1`, `h3` 같은 애플리케이션 프로토콜을 협상합니다.

같은 IP 주소와 포트에서도 SNI와 ALPN에 따라 인증서와 애플리케이션 프로토콜이 달라질 수 있습니다.

TLS 1.3의 0-RTT 데이터는 이전 세션 정보를 사용해 지연을 줄일 수 있지만 재생될 수 있습니다. 상태를 바꾸는 요청을 0-RTT로 허용할지는 애플리케이션에서 정해야 합니다.

## QUIC

QUIC은 UDP 데이터그램 안에서 다음 기능을 구현합니다.

- TLS 1.3 기반 핸드셰이크와 암호화
- 여러 독립 스트림
- 손실 탐지와 혼잡 제어
- Connection ID를 이용한 경로 변경 처리
- 패킷 번호와 ACK
- 전송 매개변수 협상

QUIC 연결은 UDP 4-tuple만으로 식별되지 않으므로 NAT 재바인딩이나 네트워크 변경 뒤 연결 이동을 지원할 수 있습니다. 다만 새 경로 검증, 증폭 제한, 유효한 Connection ID가 필요하므로 주소가 바뀌면 항상 끊김 없이 이동한다고 단정해서는 안 됩니다.

UDP가 차단되어 있거나 NAT 매핑 제한 시간이 지나치게 짧으면 HTTP/3가 실패하고 HTTP/2로 대체될 수 있습니다. 페이지가 열렸다는 사실만으로 처음 시도한 전송 프로토콜까지 정상이라고 판단해서는 안 됩니다.

## 단계별 관찰

```text
DNS         이름, 응답 코드, A/AAAA/HTTPS, 캐시
주소 선택   실제 시도한 주소와 순서
IP          출발지, 경로, 다음 홉, MTU, ICMP
전송        TCP SYN/ACK 또는 QUIC Initial/Handshake
TLS         SNI, 인증서, 버전, ALPN
HTTP        버전, 상태 코드, redirect, 프레이밍
애플리케이션 인증, 인가, 업무 결과
```

대표적인 명령은 다음과 같습니다.

```sh
dig example.com A
dig example.com AAAA
curl -v --http2 https://example.com/
openssl s_client -connect example.com:443 -servername example.com -alpn h2
```

옵션 지원 여부는 빌드와 운영체제에 따라 다릅니다. TLS와 QUIC 페이로드는 암호화되어 있으므로 패킷 캡처만으로 애플리케이션 내용을 읽을 수 없습니다. 필요한 경우 종단점의 키 로그와 명시적인 디버그 환경을 사용합니다.

## 대체 경로 기록

대체 경로로 최종 성공했더라도 첫 시도의 실패를 지우지 않습니다.

```text
AAAA 주소 TCP 연결: 제한 시간 초과
A 주소 TCP 연결:    성공
HTTP/3 시도:         UDP 제한 시간 초과
HTTP/2 대체:         성공
최종 HTTP 상태:      200
```

이 기록은 "사용자가 페이지를 열 수 있습니다"와 "모든 주소 체계와 전송 경로가 정상입니다"를 구분합니다.
