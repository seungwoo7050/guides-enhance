# 단계별 네트워크 장애 진단

네트워크 장애 조사의 목적은 익숙한 원인을 빨리 고르는 것이 아닙니다. 같은 요청을 같은 조건에서 재현하고, 마지막으로 성공한 단계와 처음 실패한 단계 사이를 관찰 자료로 좁혀야 합니다. "DNS 같습니다", "방화벽 같습니다"와 같은 문장은 확인 전까지 가설일 뿐입니다.

## 학습 목표

- 요청 조건과 관찰 위치를 먼저 고정합니다.
- 관찰, 해석, 가설, 변경 결과를 따로 기록합니다.
- 마지막 성공 단계와 첫 실패 단계를 원본 자료로 뒷받침합니다.

## 요청 조건 고정

같은 이름과 포트라도 호스트, 컨테이너, VPN, 네임스페이스, 브라우저에 따라 리졸버와 경로가 달라질 수 있습니다. 조사 전에 다음 값을 적습니다.

```text
클라이언트 프로세스와 실행 위치
네임스페이스 또는 컨테이너
요청한 이름, 주소, 포트
전송, 암호화, 애플리케이션 프로토콜
시작 시각과 전체 제한 시간
기대한 결과
실제 오류와 발생 시각
재현 입력과 반복 횟수
```

주소 후보, 연결 재사용, 프록시, VPN, 캐시를 가능한 범위에서 고정합니다. 서로 다른 조건에서 나온 성공과 실패를 같은 실험으로 묶어서는 안 됩니다.

## 관찰과 해석 분리

조사 기록에는 다음 항목이 필요합니다.

| 항목 | 기록할 내용 |
|---|---|
| 관찰 | 실제 명령 출력, 패킷, 상태, 계수기 |
| 위치 | 프로세스, 인터페이스, 네임스페이스 또는 홉 |
| 해석 | 어떤 가설을 지지하거나 반박하는지 |
| 다음 검사 | 불확실성을 가장 많이 줄이는 읽기 전용 확인 |

예시는 다음과 같습니다.

| 시각 | 위치 | 관찰 | 해석 | 다음 검사 |
|---|---|---|---|---|
| 12:00:00.100 | 클라이언트 | A와 AAAA 응답 수신 | 이름 해석 성공 | 실제 선택 주소 확인 |
| 12:00:00.110 | 클라이언트 | 기본 경로와 게이트웨이 선택 | 로컬 경로 존재 | 이웃 상태 확인 |
| 12:00:00.120 | 클라이언트 | SYN 3회 전송, 응답 없음 | 로컬 송신 확인 | 게이트웨이 뒤쪽 캡처 |
| 12:00:03.200 | 서버 진입 지점 | SYN 미관찰 | 중간 경로 또는 필터 후보 | 홉별 계수기 확인 |

관찰 항목에는 "방화벽이 막았습니다"가 아니라 "클라이언트에서 SYN을 보냈지만 서버 진입 지점에서 보이지 않았습니다"라고 적습니다.

## 1. DNS와 주소 선택

다음을 확인합니다.

- 실제로 질의한 리졸버
- A, AAAA, HTTPS 레코드
- hosts 파일, 로컬 캐시, 부정 캐시
- NXDOMAIN, SERVFAIL, 제한 시간 초과
- 클라이언트가 실제로 시도한 주소와 순서

숫자 주소로는 성공하고 이름으로만 실패하면 DNS와 주소 선택을 먼저 봅니다. 숫자 주소도 실패하면 같은 DNS 검사를 반복하지 않고 경로 단계로 이동합니다.

## 2. 로컬 경로와 출발지 주소

다음을 확인합니다.

- 선택된 라우팅 테이블과 프리픽스
- 다음 홉과 출력 인터페이스
- 실제 출발지 주소
- 정책 기반 라우팅, VRF, VPN, 네임스페이스
- IPv4 또는 IPv6 선택

라우팅 테이블에 기본 경로가 보인다는 사실만으로 해당 목적지에 그 경로가 선택되었다고 판단해서는 안 됩니다. Linux에서는 `ip route get`, macOS에서는 `route -n get`처럼 목적지별 결과를 확인합니다.

## 3. 이웃 조회와 링크

현재 링크에서 필요한 MAC 주소는 원격 서버가 아니라 경로가 선택한 다음 홉의 주소입니다.

다음을 확인합니다.

- 출력 인터페이스 상태와 VLAN
- 다음 홉의 ARP 또는 Neighbor Discovery 상태
- 요청 송신과 응답 수신
- 인터페이스 오류와 폐기 계수기

이웃 항목이 존재해도 현재 도달 가능하다고 단정해서는 안 됩니다. 상태, 갱신 시각, 실제 프레임 송수신을 함께 봅니다.

## 4. 중간 전달과 MTU

다음을 확인합니다.

- TTL 또는 Hop Limit이 어느 홉에서 감소하는지
- 어느 위치까지 패킷과 계수기가 확인되는지
- 작은 페이로드와 큰 페이로드의 결과가 다른지
- ICMP Packet Too Big 또는 fragmentation needed가 돌아오는지
- 터널 헤더를 포함한 경로 MTU가 얼마인지

작은 요청은 성공하지만 큰 TLS 응답에서 멈추고 필요한 ICMP도 보이지 않으면 MTU 블랙홀을 후보로 둡니다. `ping` 성공만으로 모든 패킷 크기가 정상이라고 판단해서는 안 됩니다.

## 5. 전송

TCP에서는 다음 사건을 구분합니다.

```text
SYN을 보내지 못함
SYN 전송 뒤 응답 없음
RST 수신
SYN/ACK 뒤 마지막 ACK 누락
ESTABLISHED 뒤 sequence 진행 중단
zero window
반복 재전송과 RTO
FIN 또는 RST로 종료
```

UDP에서는 다음 항목을 확인합니다.

```text
데이터그램 송신과 수신
ICMP 오류
NAT 매핑과 유휴 제한 시간
응답 경로
애플리케이션 메시지 ID와 재시도
```

TCP 제한 시간 초과는 서버가 요청을 처리하지 않았다는 증거가 아닙니다. 요청이나 응답이 경로에서 사라졌거나 중간 장비의 상태가 없어졌을 수 있습니다.

## 6. TLS와 HTTP

전송에 성공한 뒤 다음 항목을 따로 확인합니다.

- SNI가 의도한 호스트 이름인지
- 인증서 체인과 호스트 이름 검증 가운데 무엇이 실패했는지
- 협상한 TLS 버전과 ALPN
- HTTP 버전, 상태 코드, redirect
- 인증 실패와 인가 실패

TCP 핸드셰이크 성공은 TLS 성공을 보장하지 않습니다. TLS 성공은 HTTP 성공을 보장하지 않으며, HTTP 200도 업무 결과가 올바르다는 뜻은 아닙니다.

## 마지막 성공과 첫 실패

충분한 자료를 모으면 다음 형식으로 결론을 적습니다.

```text
마지막 성공: route
성공 근거: 목적지 192.0.2.10에 eth0, 다음 홉 192.0.2.1 선택
첫 실패: neighbor
실패 근거: ARP Request 3회 송신, Reply 없음, 항목 상태 FAILED
미확인 항목: 스위치 VLAN, 게이트웨이 인터페이스 상태
다음 읽기 전용 검사: 같은 시각의 게이트웨이 포트 캡처
```

자료가 부족하면 `UNKNOWN`으로 남깁니다. 불확실한 상태에서 특정 제품이나 팀을 원인으로 확정해서는 안 됩니다.

## 변경 전 준비

1. 바꾸려는 값과 예상 효과를 적습니다.
2. 현재 출력과 캡처를 보존합니다.
3. 영향을 받는 인터페이스, 네임스페이스, 규칙, 사용자를 확인합니다.
4. 되돌리기 명령과 성공 확인 방법을 준비합니다.
5. 한 번에 한 변수만 바꿉니다.
6. 변경 뒤 원래 증상과 인접 경로의 회귀를 함께 확인합니다.

패킷 캡처와 방화벽 변경은 권한과 개인정보 범위를 확인한 격리 환경에서 수행합니다.

## 경로 진단 프로젝트

[path-diagnosis](../../exercises/path-diagnosis/README.md)은 DNS부터 HTTP까지의 관찰값을 JSON으로 읽고 다음 결과를 반환합니다.

- 정상 경로
- NXDOMAIN
- 경로 누락
- 이웃 조회 실패
- MTU 블랙홀
- 전송 제한 시간 초과
- TLS 이름 불일치
- HTTP 접근 거부

입력 단계의 순서와 상태 조합이 모순되면 진단 결과를 만들지 않고 입력 오류로 거부합니다. 자동 결과는 고정 입력 파일에 기록된 사실만 사용합니다. ECMP, 비대칭 라우팅, 프록시, anycast, 연결 재사용, 캡처 누락은 별도 관찰이 필요합니다.

## 완료 기준

- 재현 입력, 실행 위치, 시각을 포함한 요청 조건을 작성합니다.
- 마지막 성공과 첫 실패를 원본 출력이나 패킷으로 뒷받침합니다.
- 변경 전에 반증 조건과 되돌리기 확인 방법을 적습니다.
- 자동 분류가 입력 자료보다 더 많은 사실을 확정하지 않도록 제한합니다.
