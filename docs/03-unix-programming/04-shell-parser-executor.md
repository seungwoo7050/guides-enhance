# 명령 문자열 파싱과 실행

명령 문자열을 실행하려면 먼저 문자열을 **토큰과 명령 구조로 완전히 파싱하고 문법이 유효한지 확인한 뒤** 그 결과를 사용해 자식 프로세스를 만들어야 합니다.

파싱 도중 바로 `fork`하거나 `exec`하면 뒤쪽 입력에서 문법 오류가 발견되어도 앞에서 실행한 외부 프로그램의 부수효과를 되돌릴 수 없습니다.

예를 들어 다음 입력이 문법 오류라고 가정합니다.

```text
touch marker |
```

`touch marker`를 먼저 실행한 뒤 마지막의 빈 파이프 오른쪽을 오류로 발견하면 `marker` 파일은 이미 만들어졌습니다. 따라서 이 문서의 실행기는 다음 원칙을 사용합니다.

```text
파싱 성공 전에는 외부 프로그램을 하나도 실행하지 않음
```

이 문서는 완전한 POSIX 셸을 구현하는 것이 아니라, **명시적으로 제한된 문법을 가진 작은 명령 실행기**를 다룹니다.

## 처리 순서

전체 처리는 다음 두 단계로 나눕니다.

```text
파싱 단계
  문자 단위로 읽기
  → 단어와 제어 토큰 구분
  → 전체 문법 검사
  → 각 명령의 argv 구성

실행 단계
  모든 파싱이 성공한 뒤 fork/exec
  → 자식 회수
  → 실행 결과 변환
  → argv 메모리 해제
```

핵심은 파싱과 실행 사이에 명확한 경계를 두는 것입니다.

```text
parse(input) 실패
    → 아무 자식도 만들지 않음

parse(input) 성공
    → 완성된 명령 구조만 execute에 전달
```

## 입력 문자열과 토큰

입력 문자열은 문자 단위로 읽지만 실행 단계에서는 보통 다음 두 종류의 토큰만 필요합니다.

```text
WORD      명령 이름이나 인자
PIPE      인용되지 않은 |
```

예를 들어 다음 입력은

```text
echo "hello world" | wc -c
```

개념적으로 다음 토큰이 됩니다.

```text
WORD("echo")
WORD("hello world")
PIPE
WORD("wc")
WORD("-c")
```

이후 문법 검사를 통해 두 명령으로 나눕니다.

```text
왼쪽 command.argv  = {"echo", "hello world", NULL}
오른쪽 command.argv = {"wc", "-c", NULL}
```

## 단어 버퍼

한 단어의 길이를 미리 알 수 없으므로 동적 버퍼를 사용할 수 있습니다.

```c
struct builder {
    char *data;
    size_t length;
    size_t capacity;
};
```

여기서 의미를 명확히 구분합니다.

```text
data      현재 문자 저장 공간
length    실제 문자 수, 마지막 NUL은 포함하지 않음
capacity  data가 저장할 수 있는 전체 바이트 수
```

문자 하나를 추가한 뒤에도 C 문자열로 사용할 수 있도록 하려면 다음 공간이 필요합니다.

```text
length개의 기존 문자
+ 새 문자 1개
+ 마지막 '\0' 1개
```

따라서 필요한 크기는 개념적으로 `length + 2`입니다.

### 크기 계산의 overflow

`size_t` 덧셈이 overflow되지 않는지도 먼저 확인해야 합니다.

```c
if (builder->length > SIZE_MAX - 2) {
    errno = ENOMEM;
    return -1;
}

size_t needed = builder->length + 2;
```

실제 구현에서는 `SIZE_MAX`를 사용하려면 적절한 헤더를 포함해야 합니다.

### `realloc` 결과는 임시 포인터로 받기

다음 코드는 위험합니다.

```c
builder->data = realloc(builder->data, new_capacity);
if (builder->data == NULL) {
    /* 기존 포인터도 잃어버림 */
}
```

`realloc`이 실패하면 기존 메모리는 그대로 유효하지만 반환값은 `NULL`입니다. 기존 포인터에 바로 대입하면 그 메모리를 잃어버릴 수 있습니다.

따라서 임시 포인터를 사용합니다.

```c
char *new_data = realloc(builder->data, new_capacity);

if (new_data == NULL) {
    return -1;
}

builder->data = new_data;
builder->capacity = new_capacity;
```

`data`와 `capacity`는 할당이 성공한 뒤에만 갱신합니다.

### 버퍼 증가 정책

문자 하나를 추가할 때마다 정확히 1바이트씩 `realloc`하면 긴 입력에서 비효율적입니다. 보통 capacity를 기하급수적으로 증가시킵니다.

```text
0 → 16 → 32 → 64 → 128 → ...
```

다만 두 배 계산도 overflow될 수 있으므로 최대값을 넘지 않는지 확인합니다.

## 파서 상태

따옴표와 escape를 처리하려면 현재 어떤 문맥에 있는지 상태로 표현하는 것이 명확합니다.

예를 들어 다음 상태를 둘 수 있습니다.

```c
enum quote_state {
    QUOTE_NONE,
    QUOTE_SINGLE,
    QUOTE_DOUBLE
};
```

추가로 다음 상태가 필요할 수 있습니다.

```text
escape_next   다음 문자를 특별한 의미 없이 단어에 추가할지
word_started  길이가 0이어도 현재 단어가 존재하는지
```

`word_started`는 특히 빈 인자를 보존하기 위해 중요합니다.

## 따옴표와 escape 처리

먼저 이 작은 실행기가 지원할 규칙을 명시해야 합니다. 다음은 **완전한 POSIX 셸 문법이 아니라 이 문서에서 정의한 단순화된 규칙**입니다.

```text
인용되지 않은 공백
    현재 단어를 끝냄

작은따옴표 '
    다음 작은따옴표까지 모든 문자를 그대로 단어에 포함
    작은따옴표 자체는 argv에 포함하지 않음

큰따옴표 "
    다음 큰따옴표까지 문자를 같은 단어에 포함
    큰따옴표 자체는 argv에 포함하지 않음

역슬래시 \
    작은따옴표 밖에서는 다음 문자 하나의 특별한 의미를 제거하고
    그 문자를 현재 단어에 포함

붙어 있는 인용 조각
    공백 없이 이어지면 같은 단어로 연결

'' 또는 ""
    길이 0인 인자 하나를 생성
```

작은따옴표 안에서는 역슬래시도 일반 문자로 취급한다고 정하면 규칙이 단순해집니다.

```text
'a\b'
```

결과:

```text
a\b
```

큰따옴표 안의 역슬래시 규칙 역시 이 실행기의 계약으로 명시해야 합니다. 위 규칙에서는 다음 문자 하나를 그대로 포함하도록 단순화합니다.

이 동작은 실제 POSIX 셸의 모든 세부 규칙과 같지 않습니다. 환경 변수 확장, 명령 치환 등까지 구현하지 않는 실행기라면 **지원하는 문법만 일관되게 정의하는 것**이 중요합니다.

## 따옴표와 escape 예시

입력:

```text
one 'two three' "" ab"cd" escaped\ space
```

결과 인자는 다음과 같습니다.

```text
argv[0] = "one"
argv[1] = "two three"
argv[2] = ""
argv[3] = "abcd"
argv[4] = "escaped space"
argv[5] = NULL
```

붙어 있는 여러 조각은 하나의 단어입니다.

```text
ab'cd'"ef"
```

결과:

```text
abcdef
```

escape된 공백도 단어를 끝내지 않습니다.

```text
hello\ world
```

결과:

```text
hello world
```

## 빈 인자를 보존하기

빈 문자열은 "단어가 없음"과 다릅니다.

다음 입력을 비교합니다.

```text
echo
```

```text
echo ""
```

첫 번째는 인자가 없습니다.

```text
argc = 1
argv = {"echo", NULL}
```

두 번째는 길이가 0인 인자가 하나 있습니다.

```text
argc = 2
argv = {"echo", "", NULL}
```

따라서 단어 버퍼의 `length == 0`만 보고 단어의 존재 여부를 결정하면 안 됩니다.

다음과 같은 별도 상태가 필요합니다.

```c
int word_started;
```

예를 들어 `""`를 읽으면 문자는 하나도 추가되지 않지만 따옴표를 여는 순간 현재 단어가 존재한다고 표시할 수 있습니다.

```text
" 발견
→ word_started = 1
→ 닫는 " 발견
→ length는 여전히 0
→ 공백 또는 입력 끝에서 빈 WORD 하나 확정
```

## 끝나지 않은 따옴표와 escape

입력 끝에 도달했을 때 파서 상태도 확인합니다.

다음은 문법 오류입니다.

```text
echo 'abc
echo "abc
echo abc\
```

이유는 각각 다음과 같습니다.

```text
작은따옴표가 닫히지 않음
큰따옴표가 닫히지 않음
역슬래시가 escape할 다음 문자가 없음
```

이 경우 지금까지 만든 모든 임시 명령 데이터를 해제하고, 실행 단계로 넘어가지 않습니다.

## 제어 토큰

파이프 하나만 지원한다면 **인용되지 않았고 escape되지 않은 `|`** 만 제어 토큰으로 처리합니다.

```text
명령 | 명령
```

반면 다음 `|`는 단어의 일부입니다.

```text
'a|b'
"a|b"
a\|b
```

예를 들어:

```text
echo 'a|b'
```

결과:

```text
argv[0] = "echo"
argv[1] = "a|b"
```

파이프라인으로 해석하지 않습니다.

## 지원하지 않는 제어 문자

이 실행기가 `<`, `>`, `;`, `&`를 지원하지 않는다면 인용되지 않은 상태에서 발견했을 때 조용히 일반 문자로 넘기지 않습니다.

예를 들어:

```text
echo hello > out.txt
```

를 단순히 다음 argv로 바꾸면

```text
{"echo", "hello", ">", "out.txt", NULL}
```

사용자는 셸처럼 redirection이 수행될 것으로 오해할 수 있습니다.

따라서 지원하지 않는 문법은 명시적으로 오류로 처리합니다.

```text
인용되지 않은 <  → 문법 오류
인용되지 않은 >  → 문법 오류
인용되지 않은 ;  → 문법 오류
인용되지 않은 &  → 문법 오류
```

하지만 인용되거나 escape된 문자는 일반 데이터로 사용할 수 있습니다.

```text
echo '>'
echo \&
```

## 파이프 문법 검사

파이프 하나만 지원한다면 문법은 개념적으로 다음 둘 중 하나입니다.

```text
command
```

또는

```text
command | command
```

따라서 다음은 모두 오류입니다.

```text
|
| echo hi
echo hi |
echo || wc
echo | | wc
echo | wc | cat
```

이유는 다음과 같습니다.

```text
파이프 왼쪽 명령이 비어 있음
파이프 오른쪽 명령이 비어 있음
파이프가 두 개 이상 있음
```

명령은 최소한 하나의 인자, 즉 `argv[0]`을 가져야 합니다.

```text
command.argc >= 1
command.argv[0] != NULL
command.argv[0][0] != '\0'
```

빈 문자열 `""` 자체를 명령 이름으로 허용할지 여부도 API 계약으로 정해야 합니다. 작은 실행기에서는 실행할 프로그램 이름이 없으므로 빈 `argv[0]`을 문법 또는 사용법 오류로 거부하는 편이 명확합니다.

## 공백만 있는 입력

다음처럼 공백만 있는 입력은 명령이 없습니다.

```text
"     "
```

이 경우 외부 프로그램을 실행하지 않습니다.

어떤 상태를 반환할지는 API 계약으로 정합니다.

예를 들어:

```text
빈 입력 → 상태 0
```

또는

```text
빈 입력 → 사용법 오류 2
```

둘 다 가능하지만 호출자가 예측할 수 있도록 반드시 명시해야 합니다.

## 명령 데이터의 메모리 소유권

각 명령은 실행에 필요한 `argv`를 소유하도록 만들 수 있습니다.

```c
struct command {
    char **argv;
    size_t argc;
    size_t capacity;
};
```

각 단어를 별도로 할당하면 다음과 같은 소유 관계가 됩니다.

```text
command
  │
  ├─ argv 배열
  │    ├─ argv[0] → 할당된 문자열
  │    ├─ argv[1] → 할당된 문자열
  │    └─ ...
  │
  └─ argc
```

`execvp`에 그대로 전달하려면 항상 다음 불변식을 유지합니다.

```c
command->argv[command->argc] == NULL;
```

예를 들어 인자 두 개를 가진 명령은 다음 형태입니다.

```text
argv[0] = "echo"
argv[1] = "hello"
argv[2] = NULL
argc = 2
```

## `argv` 배열 확장

새 인자를 추가할 때는 문자열 포인터 하나뿐 아니라 마지막 `NULL` 자리까지 필요합니다.

즉 새 인자를 추가한 뒤 필요한 포인터 수는 다음과 같습니다.

```text
새 argc + 1
```

capacity 계산에도 overflow를 고려합니다.

그리고 `realloc`은 단어 버퍼와 마찬가지로 임시 포인터로 받습니다.

```c
char **new_argv = realloc(command->argv,
                          new_capacity * sizeof *new_argv);

if (new_argv == NULL) {
    return -1;
}

command->argv = new_argv;
command->capacity = new_capacity;
```

곱셈 `new_capacity * sizeof *new_argv`도 `SIZE_MAX`를 넘지 않는지 확인해야 합니다.

## 정리 함수

명령 객체가 각 단어와 `argv` 배열을 소유한다면 정리 함수가 그 모든 메모리를 해제합니다.

```c
static void command_destroy(struct command *command) {
    size_t i;

    for (i = 0; i < command->argc; ++i) {
        free(command->argv[i]);
    }

    free(command->argv);

    command->argv = NULL;
    command->argc = 0;
    command->capacity = 0;
}
```

초기화되지 않은 임의의 구조체에 이 함수를 호출하면 안 됩니다. 다음처럼 처음부터 0 상태로 초기화하면 오류 경로 정리가 단순해집니다.

```c
struct command command = {0};
```

## 파싱 실패 시 부분 결과 정리

파싱 중에는 여러 단계에서 실패할 수 있습니다.

```text
단어 버퍼 확장 실패
단어 문자열 할당 실패
argv 배열 확장 실패
닫히지 않은 따옴표
끝의 역슬래시
잘못된 파이프 위치
지원하지 않는 연산자
```

어느 지점에서 실패해도 지금까지 만든 메모리를 모두 정리해야 합니다.

예를 들어 왼쪽과 오른쪽 명령을 임시로 만들었다면:

```c
struct command left = {0};
struct command right = {0};

/* parsing ... */

if (failed) {
    command_destroy(&left);
    command_destroy(&right);
    return -1;
}
```

이렇게 하면 호출자는 부분적으로 만들어진 객체의 상태를 알 필요가 없습니다.

## 전체 파싱 후 반영하기

파서가 호출자의 출력 구조체를 직접 조금씩 채우다가 실패하면 호출자가 어느 필드까지 유효한지 판단하기 어려워집니다.

따라서 임시 결과를 만든 뒤 전체 파싱이 성공했을 때만 호출자에게 넘기는 방식이 안전합니다.

예를 들어:

```c
int parse_pipeline(const char *input, struct pipeline *out) {
    struct pipeline temporary = {0};

    if (parse_into(input, &temporary) == -1) {
        pipeline_destroy(&temporary);
        return -1;
    }

    *out = temporary;
    return 0;
}
```

이 패턴에서는 실패 시 `out`을 변경하지 않는 계약을 둘 수 있습니다.

```text
성공:
    out에 완성된 결과 전달

실패:
    out은 호출 전 상태 그대로
    임시 메모리는 파서가 전부 정리
```

단, 단순 구조체 대입으로 소유권을 넘기는 경우 이후 `temporary`를 다시 `destroy`하면 이중 해제가 되므로 **성공한 순간 소유권이 `out`으로 이동했다는 규칙**을 명확히 해야 합니다.

## 파싱과 실행의 원자적 경계

실행기의 중요한 보장은 다음과 같습니다.

```text
문법 오류가 있으면 외부 명령의 부수효과가 전혀 발생하지 않음
```

이를 테스트할 수 있습니다.

예를 들어 문법 오류가 뒤에 있는 입력을 만듭니다.

```text
touch marker |
```

실행 결과:

```text
문법 오류 반환
marker 파일이 존재하지 않음
```

이 검사가 통과하려면 `touch marker`를 파싱 도중 실행해서는 안 됩니다.

## 단일 명령 실행

파싱 결과가 명령 하나라면 기본 실행 순서는 다음과 같습니다.

```text
fork
→ 자식: execvp
→ 부모: waitpid
→ wait 상태를 공개 종료 상태로 변환
```

자식에서는 `execvp`가 성공하면 돌아오지 않습니다.

```c
execvp(command->argv[0], command->argv);

/* 여기까지 왔다면 exec 실패 */
```

`exec` 실패 뒤 자식이 부모의 일반 실행 흐름으로 돌아가면 안 됩니다. 보통 오류 상태를 정한 뒤 `_exit`합니다.

```c
int saved_errno = errno;
_exit(saved_errno == ENOENT ? 127 : 126);
```

### `126`과 `127`

셸과 비슷한 규칙을 사용한다면 흔히 다음 상태를 사용합니다.

```text
127  실행할 명령을 찾지 못함
126  명령은 찾았지만 실행할 수 없음
```

다만 `execvp`에는 경로 검색과 일부 오류 처리 규칙이 포함되어 있으므로 단순히 모든 `errno`를 POSIX 셸과 완전히 같은 의미로 분류한다고 가정하면 안 됩니다.

이 작은 실행기의 계약을 단순하게 만들려면 다음처럼 정의할 수 있습니다.

```text
execvp가 최종적으로 ENOENT로 실패 → 127
그 밖의 execvp 실패             → 126
```

이것은 실행기의 **공개 상태 변환 정책**입니다.

## `waitpid`와 종료 상태

부모는 자식을 반드시 회수해야 합니다.

```c
int status;
pid_t result;

do {
    result = waitpid(pid, &status, 0);
} while (result == -1 && errno == EINTR);
```

`waitpid`가 성공한 뒤 상태를 해석합니다.

```c
if (WIFEXITED(status)) {
    return WEXITSTATUS(status);
}

if (WIFSIGNALED(status)) {
    return 128 + WTERMSIG(status);
}
```

`128 + signal`은 셸에서 흔히 쓰는 표현이지만 모든 프로그램에 강제되는 POSIX 규칙은 아닙니다. 이 실행기가 그 정책을 사용한다고 명시하는 것입니다.

## 파이프 실행

파싱 결과가 다음 형태라면

```text
left | right
```

개념적인 데이터 흐름은 다음과 같습니다.

```text
left stdout
    │
    ▼
  pipe
    │
    ▼
right stdin
```

기본 순서는 다음과 같습니다.

```text
pipe 생성
→ 왼쪽 자식 fork
→ 오른쪽 자식 fork
→ 각 자식에서 dup2와 불필요한 FD close
→ 부모에서 파이프 양 끝 close
→ 두 자식 모두 waitpid
```

왼쪽 자식을 기다린 뒤 오른쪽 자식을 생성하면 큰 출력에서 파이프가 가득 차 교착 상태가 생길 수 있으므로 **두 자식을 모두 시작한 뒤 기다립니다**.

파일 디스크립터의 구체적인 닫기 규칙과 `dup2`에서 FD 0·1이 재사용되는 경우는 별도의 프로세스·파이프 규칙을 그대로 적용해야 합니다.

## 파이프라인의 공개 종료 상태

두 자식은 서로 다른 종료 상태를 가질 수 있습니다.

예를 들어:

```text
left exits 1
right exits 0
```

파이프라인 전체 결과를 무엇으로 할지는 실행기의 정책입니다.

단순한 셸과 비슷하게 **마지막 명령의 상태**를 공개 결과로 사용한다고 정할 수 있습니다.

```text
left | right
       └──── pipeline status는 right의 상태
```

이 정책에서는 왼쪽 명령이 실패해도 오른쪽 명령이 0으로 끝나면 전체 결과는 0일 수 있습니다.

따라서 다음 두 사항을 분리합니다.

```text
모든 자식은 반드시 waitpid로 회수
공개 반환값은 마지막 명령의 상태
```

왼쪽 자식의 상태를 버린다는 뜻은 아니며, 프로세스 자원은 반드시 회수해야 합니다.

## `fork` 또는 `pipe` 실패

실행 단계에서도 오류가 발생할 수 있습니다.

```text
pipe 실패
첫 번째 fork 실패
두 번째 fork 실패
waitpid 실패
```

이들은 외부 명령 자체의 종료 상태와 다른 **실행기 내부 오류**입니다.

예를 들어 상태 `125`를 예약할 수 있습니다.

```text
125  실행기 내부의 pipe/fork/wait 오류
```

다만 이 값 역시 프로그램의 정책이며 POSIX가 일반 프로그램에 강제하는 값은 아닙니다.

두 번째 `fork`가 실패했다면 이미 만들어진 첫 번째 자식을 그대로 남겨 두면 안 됩니다.

```text
부모의 파이프 FD 정리
→ 이미 생성한 첫 자식 종료 정책 수행
→ waitpid로 회수
→ 내부 실행 오류 반환
```

## 오류 종류 나누기

작은 실행기에서 다음처럼 오류 영역을 구분할 수 있습니다.

```text
사용법 오류
    예: 함수 인자 자체가 잘못됨
    → 상태 2

문법 오류
    예: 닫히지 않은 따옴표, 빈 파이프 한쪽
    → 상태 2
    → 외부 명령 실행 안 함

실행기 내부 오류
    예: pipe/fork/wait 실패
    → 상태 125

exec 대상 없음
    → 자식 상태 127

그 밖의 exec 실패
    → 자식 상태 126

일반 명령 종료
    → 해당 자식의 종료 상태

시그널 종료
    → 128 + signal
```

프로그램이 다른 값을 선택할 수도 있습니다. 중요한 점은 **문법 오류, 실행기 자체 오류, 실행한 명령의 결과를 서로 구분할 수 있는 계약**을 만드는 것입니다.

메모리 할당 실패를 상태 125와 같은 내부 오류로 처리할지 별도의 API 오류로 전달할지도 미리 정합니다.

## 오류 반환과 `errno`

함수가 `-1`과 `errno`를 사용해 내부 오류를 보고한다면 정리 작업이 원래 `errno`를 덮어쓰지 않게 해야 합니다.

```c
if (pipe(pipefd) == -1) {
    int saved_errno = errno;

    /* 필요한 정리 */

    errno = saved_errno;
    return -1;
}
```

상태 코드만 반환하는 API라면 `errno`가 공개 계약의 일부인지 아닌지도 명확히 정하는 편이 좋습니다.

## 긴 파이프와 FD 재사용

파이프 구현은 작은 출력에서만 검사하면 부족합니다.

왼쪽 프로그램이 파이프 용량보다 많은 데이터를 쓰도록 테스트해야 합니다.

```text
큰 출력 생성
→ pipe
→ 오른쪽 프로그램이 전체 입력 소비
```

두 자식을 모두 생성하기 전에 왼쪽을 기다리는 구현은 이 테스트에서 멈출 수 있습니다.

또한 stdin이나 stdout이 미리 닫힌 상태도 테스트합니다. `pipe`는 사용 가능한 가장 작은 FD 번호를 재사용할 수 있으므로 다음과 같은 상황이 가능합니다.

```text
STDIN_FILENO(0)가 닫힘
→ pipe가 read_end = 0 반환
```

또는

```text
STDOUT_FILENO(1)가 닫힘
→ pipe가 write_end = 1 반환
```

이때 `dup2(source, destination)`의 `source == destination` 상황을 고려하지 않고 복제 뒤 source를 무조건 닫으면 실제 표준 스트림을 닫을 수 있습니다.

## 실행 후 메모리 수명

`fork` 이후 부모와 자식은 각자의 주소 공간을 가지므로 부모가 가진 `argv` 메모리는 부모가 자식을 기다리는 동안 그대로 유지할 수 있습니다.

자식은 `execvp` 호출에 필요한 동안만 해당 메모리를 사용합니다.

부모는 필요한 자식들을 생성한 뒤 적절한 시점에 파싱 결과를 해제합니다. 보통 구현을 단순하게 하기 위해 모든 자식을 회수한 뒤 파이프라인 구조 전체를 해제할 수 있습니다.

```text
parse 성공
→ execute
→ wait 완료
→ pipeline_destroy
```

오류 경로에서도 동일한 소유권 규칙을 유지해야 합니다.

## 범위 제한하기

작은 명령 실행기는 다음 기능을 의도적으로 제외할 수 있습니다.

- 환경 변수 확장
- 명령 치환
- glob 패턴 확장
- 입출력 재지정
- 논리 연산자
- 여러 개의 파이프
- 작업 제어
- 대화형 프롬프트

이 기능들을 구현하지 않는다면 실제 셸처럼 어설프게 일부만 해석하지 않습니다.

예를 들어 환경 변수 확장을 지원하지 않는다면:

```text
echo "$HOME"
```

을 실제 셸처럼 홈 디렉터리로 바꾸지 않고, 이 실행기가 정의한 따옴표 규칙에 따라 문자 `$HOME` 자체를 인자로 전달할 수 있습니다.

반면 `<`, `>`, `;`, `&`처럼 사용자가 제어 연산자로 오해하기 쉬운 문자는 지원하지 않는 문법으로 명시적으로 거부할 수 있습니다.

중요한 것은 **지원 범위를 작게 유지하더라도 입력 하나가 어떤 의미인지 항상 결정적으로 알 수 있게 하는 것**입니다.

## 테스트할 내용

- 일반 공백으로 여러 인자를 나누는 경우
- 작은따옴표와 큰따옴표
- escape된 공백
- 따옴표로 만든 빈 인자 `''`, `""`
- 붙어 있는 인용 구간 `ab"cd"'ef'`
- 인용된 `|`
- escape된 `|`
- 열린 작은따옴표
- 열린 큰따옴표
- 입력 끝의 역슬래시
- 공백만 있는 입력의 정책
- 파이프 왼쪽이 빈 경우
- 파이프 오른쪽이 빈 경우
- 파이프가 둘 이상 있는 경우
- 지원하지 않는 `<`, `>`, `;`, `&`
- 지원하지 않는 문자를 인용했을 때 일반 인자로 전달되는지
- 긴 단어에서 builder가 안전하게 확장되는지
- 많은 인자에서 `argv` 배열이 안전하게 확장되는지
- 메모리 할당 실패 후 부분 결과가 모두 정리되는지
- 파싱 실패 시 호출자의 출력 구조가 부분 변경되지 않는지
- 문법 오류 입력 앞에 부수효과 명령을 두어도 실제 실행되지 않는지
- 일반 종료 상태
- 없는 명령의 127
- 그 밖의 `execvp` 실패의 126
- 시그널 종료의 `128 + signal`
- 왼쪽 명령 실패, 오른쪽 명령 성공 시 마지막 명령 상태를 반환하는지
- 파이프 용량보다 큰 데이터
- 표준 FD 0·1 재사용
- `dup2`의 source와 destination이 같은 경우
- 두 번째 `fork` 실패 뒤 첫 번째 자식을 회수하는지
- 반복 실행 뒤 FD와 메모리가 누수되지 않는지

## 완료 기준

1. 파싱과 실행을 분리하고 전체 문법이 성공하기 전에는 자식을 만들지 않습니다.
2. 단어 버퍼와 `argv` 확장 시 크기 overflow와 `realloc` 실패를 안전하게 처리합니다.
3. 따옴표, escape, 공백의 의미를 상태 기반으로 명확히 구분합니다.
4. 길이가 0이어도 존재하는 단어 상태를 별도로 기록하여 빈 인자를 보존합니다.
5. 붙어 있는 인용 조각을 하나의 인자로 연결합니다.
6. 인용되거나 escape된 `|`는 일반 문자로 전달합니다.
7. 파이프 왼쪽·오른쪽의 빈 명령과 두 개 이상의 파이프를 문법 오류로 거부합니다.
8. 지원하지 않는 제어 문법을 조용히 다른 의미로 처리하지 않습니다.
9. 각 명령의 `argv[argc] == NULL`을 유지하여 `execvp`에 직접 전달할 수 있게 합니다.
10. 명령 객체가 각 문자열과 `argv` 배열의 소유권을 가지며 오류·정상 경로 모두에서 해제합니다.
11. 전체 파싱 성공 전에는 호출자의 최종 출력 구조에 부분 결과를 넘기지 않습니다.
12. 단일 명령과 파이프 모두에서 모든 자식을 `waitpid`로 회수합니다.
13. 파이프에서는 두 자식을 모두 생성한 뒤 기다려 큰 출력에서도 교착 상태를 피합니다.
14. 파이프라인 전체 상태를 어느 자식의 상태로 정할지 명시합니다.
15. 문법 오류, 실행기 내부 오류, `exec` 실패, 일반 종료, 시그널 종료를 서로 구분합니다.
16. stdin/stdout의 FD 번호가 파이프에 재사용되어도 최종 표준 스트림을 잘못 닫지 않습니다.
17. 이 실행기가 완전한 POSIX 셸이 아니며 지원하지 않는 기능의 의미를 명확히 제한합니다.
