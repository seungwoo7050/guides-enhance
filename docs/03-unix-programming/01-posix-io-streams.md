# POSIX 입출력과 스트림 상태

이 문서에서 다루는 입출력은 ISO C의 `FILE *` 기반 표준 입출력(`fread`, `fprintf` 등)이 아니라, **POSIX 파일 디스크립터(file descriptor)** 를 사용하는 `read`와 `write`입니다.

`read`와 `write`는 호출할 때 요청한 바이트 수를 항상 한 번에 처리하지 않습니다. 파일, 파이프, 터미널, 소켓은 각각 다른 이유로 일부 바이트만 처리할 수 있고, 시그널 때문에 호출이 중단될 수도 있습니다. 따라서 다음 두 가지를 분리해서 생각해야 합니다.

- 시스템 호출 한 번이 실제로 몇 바이트를 처리했는가
- 애플리케이션이 필요로 하는 논리적인 데이터 단위가 완성되었는가

예를 들어 newline으로 끝나는 한 줄을 읽고 싶더라도 `read` 한 번이 정확히 한 줄을 반환한다는 보장은 없습니다. 한 줄이 여러 `read`에 나뉠 수도 있고, 한 번의 `read`에 여러 줄이 함께 들어올 수도 있습니다.

## 파일 디스크립터

파일 디스크립터(file descriptor, FD)는 프로세스가 열린 입출력 자원을 참조할 때 사용하는 **0 이상의 작은 정수 핸들**입니다. 파일뿐 아니라 파이프, 터미널, 소켓 등도 파일 디스크립터를 통해 다룰 수 있습니다.

관례적으로 프로세스가 시작될 때 다음 번호가 표준 스트림에 연결되어 있습니다.

```text
0  표준 입력(stdin)
1  표준 출력(stdout)
2  표준 오류(stderr)
```

다만 이 파일 디스크립터들은 닫히거나 다른 자원으로 다시 연결될 수 있으므로, 숫자 자체가 항상 특정 장치나 터미널을 의미하는 것은 아닙니다.

`open`, `pipe`, `dup` 계열 함수 등으로 얻은 파일 디스크립터는 누가 소유하는지 명확히 정해야 하며, 소유자는 더 이상 필요하지 않을 때 `close`해야 합니다.

## `read`

기본 형태는 다음과 같습니다.

```c
ssize_t count = read(fd, buffer, capacity);
```

`capacity > 0`이라고 할 때 반환값은 다음과 같이 해석합니다.

```text
count > 0   실제로 읽은 바이트 수
count == 0  더 읽을 바이트가 없음, 즉 EOF 상태
count == -1 오류, errno 확인
```

`read`의 세 번째 인수인 `capacity`는 "최대 몇 바이트까지 읽어도 되는가"를 뜻합니다. 성공했다고 해서 반드시 그만큼 읽는 것은 아닙니다.

예를 들어 다음 호출에서:

```c
char buffer[4096];
ssize_t count = read(fd, buffer, sizeof buffer);
```

`count == 600`이 반환되어도 오류가 아니며, 그것만으로 EOF라고 판단할 수도 없습니다. 이번 호출에서 600바이트만 얻었다는 뜻입니다. 다음 `read`에서 데이터가 더 나올 수 있습니다.

따라서 **짧은 읽기(short read)** 와 EOF는 구분해야 합니다.

```text
0 < count < capacity   짧은 읽기. 읽은 데이터는 정상적으로 처리한다.
count == 0             EOF. 더 읽을 데이터가 없다.
```

특히 스트림이나 파이프, 터미널, 소켓에서는 현재 이용 가능한 데이터가 요청량보다 적다는 이유만으로 짧은 읽기가 발생할 수 있습니다.

> 주의: `capacity == 0`인 `read(fd, buffer, 0)`은 실제 데이터를 요구하지 않으므로 `0`을 반환할 수 있습니다. 따라서 단순히 "반환값 0은 항상 EOF"라고 외우기보다는, 일반적인 `capacity > 0` 읽기에서 `0`을 EOF로 해석한다고 이해하는 편이 정확합니다.

## `write`

`write`도 요청한 바이트 수를 모두 기록했다고 보장하지 않습니다.

```c
ssize_t count = write(fd, data, length);
```

`count > 0`이면 그 수만큼의 바이트는 기록되었습니다. 하지만 `count < length`일 수 있으므로, 호출자가 남은 바이트를 이어서 써야 합니다.

예를 들어 100바이트를 요청했는데 `write`가 40을 반환했다면:

```text
처리 완료: 앞의 40바이트
남은 데이터: 뒤의 60바이트
```

다음 `write`는 처음부터 다시 쓰는 것이 아니라 **아직 쓰지 못한 60바이트부터** 시작해야 합니다.

```c
int write_all(int fd, const void *data, size_t length) {
    const unsigned char *cursor = data;

    while (length > 0) {
        ssize_t count = write(fd, cursor, length);

        if (count > 0) {
            cursor += (size_t)count;
            length -= (size_t)count;
            continue;
        }

        if (count == -1 && errno == EINTR) {
            continue;
        }

        /* count == 0이거나 재시도하지 않을 오류 */
        return -1;
    }

    return 0;
}
```

이 함수에서 `cursor`는 아직 쓰지 않은 데이터의 시작 위치를 가리키고, `length`는 아직 남은 바이트 수를 뜻합니다. 따라서 부분 쓰기가 발생할 때마다 두 값을 함께 갱신합니다.

`write`가 양수를 반환했다면 그 바이트들은 이미 처리된 것입니다. 이후 오류가 발생하더라도 이미 기록된 바이트까지 다시 처음부터 보내면 데이터가 중복될 수 있습니다.

## `EINTR`

`read`나 `write` 같은 시스템 호출이 기다리는 도중 시그널에 의해 중단되면 호출이 `-1`을 반환하고 `errno == EINTR`이 될 수 있습니다.

예를 들어 `read`를 `EINTR`일 때만 다시 시도하려면 다음처럼 작성할 수 있습니다.

```c
ssize_t count;

do {
    count = read(fd, buffer, sizeof buffer);
} while (count == -1 && errno == EINTR);
```

핵심은 **모든 오류를 무조건 재시도하지 않는 것**입니다.

```text
EINTR       시그널에 의해 중단됨 → 이 코드에서는 재시도
다른 오류  원인을 호출자에게 전달하거나 별도 처리
```

또한 `errno`는 시스템 호출이 오류를 나타내는 값을 반환했을 때 확인해야 합니다. `read`나 `write`가 성공해서 `0` 이상의 값을 반환했다면 이전 호출에서 남아 있던 `errno` 값으로 성공 여부를 다시 판단하면 안 됩니다.

시스템 호출이 일부 바이트를 이미 처리한 뒤 중단된 경우에는 `-1` 대신 실제 처리한 바이트 수를 반환할 수 있습니다. 이때는 그 양수 반환값을 정상적인 부분 읽기 또는 부분 쓰기로 처리하면 됩니다.

## 바이트 수와 문자열 길이 구분하기

`read`가 반환하는 데이터는 **바이트 배열**이지, 자동으로 완성된 C 문자열이 아닙니다.

```c
char buffer[128];
ssize_t count = read(fd, buffer, sizeof buffer);
```

`count > 0`이어도 다음 보장은 없습니다.

- `buffer[count]` 위치에 `\0`이 들어 있다.
- 읽은 데이터 내부에 NUL(`\0`) 바이트가 없다.
- `strlen(buffer)`가 `count`와 같다.

따라서 바이트 데이터는 항상 `read`의 반환 길이를 기준으로 처리해야 합니다.

```c
process_bytes(buffer, (size_t)count);
```

문자열로 사용할 데이터라면 마지막 NUL 문자를 직접 넣을 공간을 남겨야 합니다.

```c
char buffer[129];
ssize_t count = read(fd, buffer, sizeof buffer - 1);

if (count > 0) {
    buffer[count] = '\0';
}
```

그러나 이렇게 NUL을 덧붙였더라도 원래 데이터 중간에 NUL 바이트가 있을 수 있다면 `strlen`, `strcpy`, `strchr`처럼 NUL을 문자열 끝으로 해석하는 함수만으로 데이터를 처리하면 안 됩니다. 이 문서의 레코드 읽기처럼 **임의의 바이트를 허용하는 인터페이스에서는 포인터와 길이를 함께 유지하는 방식**이 안전합니다.

예를 들어 newline을 찾을 때도 NUL이 포함될 수 있는 버퍼라면 `strchr`보다 길이를 받는 `memchr`를 사용해야 합니다.

```c
void *newline = memchr(buffer, '\n', length);
```

## 레코드와 `read` 호출은 일치하지 않습니다

여기서는 예시를 구체화하기 위해 다음과 같은 레코드 규칙을 사용합니다.

```text
구분자: newline('\n')
반환 레코드: newline 자체는 제외
연속 newline: 길이 0인 빈 레코드를 생성
EOF 직전의 마지막 조각: 비어 있지 않으면 마지막 레코드로 반환
입력이 newline으로 끝남: 마지막 newline 뒤에 추가 빈 레코드는 만들지 않음
```

입력 전체가 다음과 같다고 가정합니다.

```text
alpha\nbeta\ngamma
```

실제 `read` 결과는 다음처럼 나뉠 수 있습니다.

```text
첫 read:   "alpha\nbe"
둘째 read: "ta\ngamma"
셋째 read: EOF
```

이 경우 논리적인 처리 과정은 다음과 같습니다.

```text
첫 read 후 pending = "alpha\nbe"
→ "alpha" 반환
→ pending = "be"

다음 호출에서 delimiter 없음
→ 둘째 read를 이어 붙임
→ pending = "beta\ngamma"
→ "beta" 반환
→ pending = "gamma"

다음 호출에서 delimiter 없음
→ 셋째 read가 0을 반환하여 EOF 확인
→ pending의 "gamma"를 마지막 레코드로 반환
→ pending 비움

그 다음 호출
→ EOF이고 pending도 비어 있음
→ 0 반환
```

즉, 다음 두 상황을 모두 처리해야 합니다.

1. 한 레코드가 여러 `read`에 걸쳐 나뉜다.
2. 한 번의 `read`에 여러 레코드가 들어온다.

따라서 `read`에서 받은 청크를 곧바로 "레코드 하나"라고 간주할 수 없습니다. 현재 호출에서 사용하지 않은 바이트는 다음 호출을 위해 보관해야 합니다.

## 상태를 보관하는 읽기 객체

호출 사이에 남은 바이트와 EOF 여부를 유지하려면 읽기 상태를 객체에 보관할 수 있습니다.

```c
struct record_reader {
    int fd;
    char *pending;       /* 아직 레코드로 반환하지 않은 바이트 */
    size_t length;       /* pending에 들어 있는 유효 바이트 수 */
    size_t capacity;     /* pending이 현재 담을 수 있는 바이트 수 */
    int eof;             /* read가 0을 반환했는지 */
    int failed;          /* 복구하지 않는 오류가 발생했는지 */
};
```

각 필드의 의미를 구분해야 합니다.

- `length == 0`은 단지 현재 남은 바이트가 없다는 뜻입니다. 아직 EOF가 아닐 수 있습니다.
- `eof == 1`은 더 이상 커널에서 읽을 바이트가 없다는 뜻입니다. 그래도 `pending`에 마지막 레코드 조각이 남아 있을 수 있습니다.
- `failed == 1`은 이 구현에서 더 이상 정상적인 읽기를 계속하지 않기로 했다는 뜻입니다.

특히 `eof == 1`과 "모든 레코드를 이미 반환했다"는 같은 상태가 아닙니다. EOF를 발견한 순간 `pending`에 newline 없는 마지막 조각이 남아 있다면 그 조각을 먼저 한 번 반환해야 합니다.

## 상태를 보관하는 읽기 객체의 처리 순서

blocking FD를 대상으로 한 단순한 `record_reader_next`는 다음 순서로 생각할 수 있습니다.

```text
1. failed이면 -1 반환
2. pending에서 delimiter 검색
3. delimiter가 있으면 그 앞부분을 레코드로 반환
4. delimiter가 없고 eof이면:
   - pending이 비어 있지 않으면 마지막 레코드로 반환
   - pending도 비어 있으면 0 반환
5. 아직 eof가 아니면 read 수행
6. read > 0이면 받은 바이트를 pending에 추가하고 2번으로 돌아감
7. read == 0이면 eof를 기록하고 2번으로 돌아감
8. read == -1 && errno == EINTR이면 read 재시도
9. 그 밖의 오류면 failed를 기록하고 -1 반환
```

이 구조에서 중요한 점은 **레코드를 찾기 전에 무조건 새 `read`를 하지 않는 것**입니다. 이미 `pending` 안에 완성된 레코드가 있다면 추가 입출력 없이 먼저 반환할 수 있습니다.

또한 한 번의 `read`에 레코드 여러 개가 들어왔다면 첫 번째 레코드만 반환하고 나머지는 `pending`에 남겨 다음 `record_reader_next` 호출에서 사용합니다.

전역 정적 버퍼 하나를 여러 파일 디스크립터가 공유하면 서로 다른 입력의 남은 데이터가 섞일 수 있습니다. 따라서 동시에 여러 입력을 읽을 가능성이 있다면 각 읽기 객체마다 독립적인 `pending`, `length`, `eof` 등의 상태를 둡니다.

## 빈 레코드와 마지막 조각

입력이 실제 바이트 기준으로 다음과 같다고 가정합니다.

```text
alpha\n\nbeta
```

이 문서의 레코드 규칙에서는 다음 세 레코드를 반환합니다.

```text
"alpha"
""
"beta"
```

두 newline이 연속으로 나오면 그 사이에 바이트가 없으므로 길이 0인 빈 레코드가 하나 존재합니다.

반면 다음 입력을 비교해 봅니다.

```text
alpha\n
```

이 문서에서는 `"alpha"`를 반환한 뒤 EOF를 반환하며, 마지막 newline 뒤에 별도의 빈 레코드를 추가로 만들지 않습니다.

빈 입력도 마찬가지입니다.

```text
입력 바이트 수: 0
반환 레코드 수: 0
첫 next 호출: 0
이후 next 호출: 계속 0
```

이 규칙이 유일한 정답이라는 뜻은 아닙니다. 다른 API는 newline 포함 여부나 마지막 빈 레코드 처리 방식을 다르게 정할 수 있습니다. 중요한 것은 **인터페이스가 어떤 규칙을 사용하는지 명시하고 구현과 테스트가 그 규칙을 일관되게 따르는 것**입니다.

## 출력 메모리 소유권

읽기 객체가 레코드를 새 메모리에 복사해 반환하는 인터페이스라면, 누가 그 메모리를 해제하는지 계약에 포함해야 합니다.

예를 들어 다음과 같은 반환 규칙을 사용할 수 있습니다.

```text
1   레코드 하나 반환 성공
0   EOF이며 더 반환할 레코드 없음
-1  오류
```

그리고 성공한 경우에만 `record`와 `length`를 설정한다고 정합니다.

```c
char *record;
size_t length;
int result = record_reader_next(&reader, &record, &length);

if (result == 1) {
    consume(record, length);
    free(record);
} else if (result == 0) {
    /* 정상적인 EOF */
} else {
    /* 오류 */
}
```

이 계약에서는:

```text
result == 1
  record가 새로 할당된 레코드를 가리킴
  length가 레코드의 바이트 수
  호출자가 record를 free해야 함

result == 0 또는 -1
  record와 length는 출력값으로 사용하지 않음
```

`0`이나 `-1`일 때 출력 매개변수를 변경하지 않는 규칙을 사용하면 호출자가 성공한 경우에만 값을 소비하면 되므로 상태 구분이 단순해집니다.

반환 레코드가 임의의 바이트를 포함할 수 있다면 `length`가 실제 데이터 길이의 기준입니다. 구현이 편의를 위해 끝에 `\0`을 한 바이트 더 붙여 주더라도, embedded NUL이 허용되는 한 `strlen(record)`를 실제 레코드 길이로 간주해서는 안 됩니다.

## 실패 후 상태

읽기 객체는 이미 커널에서 가져온 바이트를 내부 `pending`에 보관합니다. 따라서 내부 버퍼 확장 같은 작업이 실패한 뒤 상태를 어떻게 다룰지 명확히 정해야 합니다.

예를 들어 새로 읽은 바이트를 보관하기 위한 메모리 할당에 실패했다고 가정합니다. 그 바이트가 이미 `read`를 통해 커널 버퍼에서 소비되었다면 단순히 다음 호출에서 처음부터 다시 읽어서 복구할 수 없습니다.

이런 이유로 단순한 구현에서는 **복구하지 않는 실패**로 고정하는 방식이 명확합니다.

```text
오류 발생
→ failed = 1
→ 현재 호출은 -1
→ 이후 next 호출도 -1
```

이 규칙을 사용하면 불완전하게 보존된 입력을 정상적인 레코드처럼 계속 노출하는 일을 피할 수 있습니다.

정리 함수는 오류 상태와 관계없이 내부 자원을 해제해야 합니다.

```text
pending이 할당되어 있으면 free
내부 길이/용량 상태 정리
FD를 소유한 객체라면 close
빌린 FD라면 close하지 않음
```

## 파일 디스크립터 소유자

읽기 객체가 파일 디스크립터를 사용하는 것과 **소유하는 것**은 별개의 개념입니다.

두 가지 대표적인 계약은 다음과 같습니다.

```text
빌린 FD(borrowed FD):
  호출자가 FD를 열거나 보유함
  읽기 객체는 그 FD를 사용만 함
  record_reader_destroy는 FD를 닫지 않음
  최종 close 책임은 호출자에게 있음

소유한 FD(owned FD):
  읽기 객체가 직접 열었거나 소유권을 명시적으로 넘겨받음
  record_reader_destroy가 FD를 close함
  소유권을 넘긴 뒤 호출자는 별도로 close하지 않음
```

이 계약이 불분명하면 두 종류의 버그가 생길 수 있습니다.

```text
양쪽이 모두 close함       → 이중 close
아무도 close하지 않음     → 파일 디스크립터 누수
```

따라서 생성 함수 이름, 문서, 타입 규칙 중 적어도 한 곳에서는 FD 소유권을 명확히 드러내야 합니다.

## Blocking과 non-blocking

### Blocking FD

blocking 파일 디스크립터에서 `read`할 데이터가 아직 없으면 호출이 데이터가 도착하거나 EOF 또는 오류가 발생할 때까지 기다릴 수 있습니다.

따라서 blocking 전용 `record_reader_next`는 "완성된 레코드 하나가 나오거나 EOF/오류가 결정될 때까지 내부에서 계속 읽는다"는 비교적 단순한 계약을 사용할 수 있습니다.

### Non-blocking FD

non-blocking 파일 디스크립터에서는 현재 당장 읽을 데이터가 없을 때 `read`가 `-1`을 반환하고 `errno`가 `EAGAIN` 또는 `EWOULDBLOCK`일 수 있습니다.

이 상태는 EOF와 다릅니다.

```text
read == 0
  더 읽을 데이터가 없음 → EOF

read == -1 && (errno == EAGAIN || errno == EWOULDBLOCK)
  지금 당장은 읽을 데이터가 없음
  나중에는 데이터가 도착할 수 있음
```

따라서 non-blocking 읽기 객체를 blocking 전용 API와 똑같은 `1 / 0 / -1` 의미로 처리하면 "지금 데이터 없음"과 "영구적인 EOF" 또는 "실제 오류"를 구분하기 어려울 수 있습니다.

non-blocking API는 필요에 따라 다음과 같은 상태를 별도로 표현해야 합니다.

```text
레코드 준비됨
EOF
지금은 더 읽을 수 없음(WOULD_BLOCK)
실제 오류
```

또한 언제 다시 호출할지, `poll`/`select`/`epoll` 같은 입출력 가능 알림과 어떻게 연결할지, delimiter가 오지 않는 매우 긴 입력을 `pending`에 얼마나 보관할지 같은 정책도 필요합니다.

따라서 단순한 blocking 레코드 리더와 non-blocking 이벤트 기반 리더는 오류 처리와 상태 계약을 별도로 설계하는 편이 명확합니다.

## 전체 상태 예시

newline 레코드 리더가 다음 입력을 처리한다고 가정합니다.

```text
A\n\nBC
```

시스템 호출 결과가 우연히 다음처럼 나뉘었다고 해도:

```text
read #1 → "A\n"
read #2 → "\nB"
read #3 → "C"
read #4 → 0
```

호출자가 보는 논리적인 결과는 시스템 호출 경계와 무관해야 합니다.

```text
next #1 → 1, "A",  length 1
next #2 → 1, "",   length 0
next #3 → 1, "BC", length 2
next #4 → 0
next #5 → 0
```

이 예제가 보여 주는 핵심은 다음과 같습니다.

- `read` 청크와 레코드 경계는 서로 독립적입니다.
- 빈 레코드도 정상적인 레코드입니다.
- EOF를 확인한 뒤에도 `pending`의 마지막 조각을 한 번 반환할 수 있습니다.
- 최종 레코드까지 반환한 뒤에는 반복 호출해도 계속 EOF를 반환할 수 있습니다.

## 테스트할 내용

최소한 다음 경우를 테스트합니다.

- 한 번의 `read` 버퍼보다 긴 레코드
- 한 청크에 여러 레코드가 들어오는 경우
- 한 레코드가 여러 청크에 걸쳐 나뉘는 경우
- 연속 newline으로 생기는 빈 레코드
- newline 없는 마지막 레코드
- newline으로 끝나는 입력에서 불필요한 추가 빈 레코드가 생기지 않는지
- 빈 입력과 반복 EOF 호출
- 데이터 중간의 embedded NUL
- 두 읽기 객체를 번갈아 호출했을 때 상태가 섞이지 않는지
- `read`가 `EINTR`로 중단된 뒤 올바르게 재시도하는지
- `write`가 일부 바이트만 기록했을 때 남은 부분만 이어 쓰는지
- 내부 버퍼 할당 실패 뒤 `failed` 상태가 유지되는지
- destroy 뒤 빌린 FD는 여전히 열려 있는지
- 소유한 FD라면 destroy가 해당 FD를 닫는지
- non-blocking을 지원한다면 `EAGAIN`/`EWOULDBLOCK`과 EOF를 구분하는지

## 완료 기준

1. `read`의 짧은 반환과 EOF를 구분합니다.
2. `read`와 `write`의 반환값이 실제 처리한 바이트 수라는 점을 설명할 수 있습니다.
3. `write`가 요청보다 적게 기록하면 포인터와 남은 길이를 갱신해 반복해서 씁니다.
4. `EINTR`처럼 명시적으로 재시도하기로 한 오류만 재시도합니다.
5. `errno`는 시스템 호출이 오류를 반환했을 때만 의미 있게 확인합니다.
6. 논리적인 레코드 경계와 시스템 호출 한 번의 경계를 구분합니다.
7. 다음 호출에 필요한 바이트를 읽기 객체의 `pending` 상태에 보관합니다.
8. EOF를 발견한 것과 `pending`의 마지막 레코드까지 모두 반환한 것을 구분합니다.
9. 바이트 데이터의 길이는 `strlen`이 아니라 명시적인 길이 값으로 관리합니다.
10. 빈 레코드, 마지막 조각, 마지막 newline의 처리 규칙을 명시합니다.
11. 파일 디스크립터와 반환 레코드 각각의 소유자와 해제 책임을 설명합니다.
12. blocking의 EOF와 non-blocking의 `EAGAIN`/`EWOULDBLOCK`을 구분합니다.
