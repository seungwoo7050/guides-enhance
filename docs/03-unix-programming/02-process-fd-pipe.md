# 프로세스·파일 디스크립터·파이프

`fork`, `exec`, `pipe`, `dup2`를 함께 사용할 때는 **각 프로세스가 어떤 파일 디스크립터(FD)를 보유하고, 어떤 FD를 실제 입출력에 사용하며, 언제 닫는지**를 먼저 정해야 합니다. 출력 내용만 확인하면 작은 입력에서는 우연히 동작하다가 큰 입력, EOF, 오류 경로에서 멈추거나 파일 디스크립터가 누수될 수 있습니다.

특히 파이프에서는 **어느 프로세스든 쓰기 끝을 하나라도 열어 두고 있으면 EOF 조건에 영향을 준다**는 점이 중요합니다.

## `fork`

```c
pid_t pid = fork();
```

반환값은 호출한 프로세스에 따라 다릅니다.

```text
pid > 0   부모 프로세스, 값은 새로 생성된 자식의 PID
pid == 0  자식 프로세스
pid == -1 실패, 자식은 생성되지 않음
```

`fork`가 성공하면 부모와 자식은 서로 독립된 주소 공간을 갖습니다. 논리적으로는 부모의 메모리 상태가 자식에게 복사되어 시작하며, 실제 구현에서는 보통 copy-on-write를 사용합니다.

파일 디스크립터 표도 자식에게 복제됩니다. 그러나 부모의 FD와 자식의 대응하는 FD는 단순히 같은 번호만 가진 별개의 파일을 가리키는 것이 아니라, 커널의 **같은 열린 파일 상태(open file description)** 를 참조합니다.

예를 들어 일반 파일이라면 다음과 같은 상태를 공유할 수 있습니다.

```text
부모 fd 3 ─┐
           ├─ 같은 open file description ─ 파일
자식 fd 3 ─┘
```

따라서 같은 열린 파일 상태에 연결된 FD들은 파일 오프셋과 일부 파일 상태 플래그를 공유합니다. 반면 각 프로세스의 **FD 자체는 별도 항목**이므로 한 프로세스에서 `close(fd)`해도 다른 프로세스의 같은 번호 FD가 자동으로 닫히지는 않습니다.

커널 객체는 이를 참조하는 FD가 모두 닫힐 때까지 유지됩니다. 이 특성이 파이프의 EOF 판정에서 특히 중요합니다.

## `exec`

```c
execvp(argv[0], argv);
```

`exec` 계열 함수는 새 프로세스를 만드는 함수가 아닙니다. 성공하면 **현재 프로세스가 실행하던 프로그램 이미지를 새 프로그램으로 교체**합니다. 따라서 성공한 `execvp`는 호출 지점으로 돌아오지 않습니다.

반환했다면 실패입니다.

```c
execvp(argv[0], argv);

int saved_errno = errno;
_exit(saved_errno == ENOENT ? 127 : 126);
```

자식 프로세스에서 `exec`가 실패했을 때는 보통 `exit`보다 `_exit`를 사용합니다.

`fork` 직전 부모의 `stdio` 출력 버퍼에 아직 출력되지 않은 데이터가 있었다면 그 버퍼 상태도 자식에게 복사됩니다. 자식이 `exit`를 호출하면 `stdio` 버퍼를 flush하거나 `atexit` 처리기를 실행하면서 부모가 나중에 처리할 데이터를 중복 출력할 수 있습니다. `_exit`는 이러한 사용자 공간 정리 절차를 수행하지 않고 즉시 프로세스를 종료합니다.

필요하다면 `exec` 실패 진단은 `_exit` 전에 `write`, `dprintf` 등으로 직접 출력합니다.

### `exec`와 열린 FD

`exec`에 성공해도 모든 파일 디스크립터가 자동으로 닫히는 것은 아닙니다. `FD_CLOEXEC` 플래그가 설정되지 않은 FD는 새 프로그램에서도 열린 상태로 남습니다.

따라서 파이프를 구성하는 자식은 `exec` 전에 사용하지 않는 파이프 끝을 반드시 닫아야 합니다. 그렇지 않으면 새 프로그램이 의도하지 않은 쓰기 끝을 계속 보유하여 다른 프로세스의 EOF를 막을 수 있습니다.

필요한 FD에 `FD_CLOEXEC`를 설정할 때는 POSIX의 `fcntl`을 사용할 수 있습니다.

```c
int flags = fcntl(fd, F_GETFD);
if (flags != -1) {
    fcntl(fd, F_SETFD, flags | FD_CLOEXEC);
}
```

단, 표준 입력이나 표준 출력으로 연결하기 위해 `dup2`한 FD는 새 프로그램에서도 사용해야 하므로 해당 최종 표준 FD가 `exec` 뒤 살아 있어야 합니다.

### `argv` 계약

`execvp`에 넘길 인자 배열은 일반적으로 다음 형태를 사용합니다.

```text
argv[0]  실행할 명령 이름
argv[1]  첫 번째 인자
...
argv[n]  NULL
```

호출하는 함수의 계약에서 최소한 다음을 확인하는 것이 안전합니다.

```text
argv != NULL
argv[0] != NULL
argv[0][0] != '\0'
```

`NULL`인 `argv`나 빈 `argv[0]`의 동작에 기대는 코드는 이식성이 떨어지고, 실행할 명령 자체가 없다는 의미가 될 수 있으므로 파이프 실행 함수가 미리 거부하는 편이 명확합니다.

### `126`과 `127`

셸과 비슷한 공개 종료 상태를 사용한다면 흔히 다음 의미를 부여합니다.

```text
127  실행할 명령을 찾지 못함
126  명령은 지정되었지만 실행할 수 없음
```

다만 이것은 모든 일반 프로그램에 POSIX가 강제하는 내부 오류 표현 규칙이 아닙니다. 또한 단순히 `errno == ENOENT`를 모두 "명령 자체가 없음"으로 해석하면 완전히 정확하지 않을 수 있습니다. 예를 들어 실행 파일은 존재해도 스크립트가 요구하는 인터프리터를 찾지 못해 `ENOENT`가 발생할 수 있습니다.

따라서 자신의 API가 `exec` 실패를 어떤 종료 상태로 변환할지 명시해야 합니다.

## `waitpid`

부모는 종료한 자식을 `wait` 계열 함수로 **회수(reap)** 해야 합니다. 회수하지 않은 종료 자식은 부모가 상태를 읽을 때까지 좀비 상태로 남을 수 있습니다.

```c
int status;
pid_t result;

do {
    result = waitpid(pid, &status, 0);
} while (result == -1 && errno == EINTR);
```

`status`는 `waitpid`가 대상 자식을 성공적으로 회수한 경우에만 해석합니다.

```c
if (result == -1) {
    /* errno에 따른 오류 처리 */
}

if (WIFEXITED(status)) {
    int code = WEXITSTATUS(status);
}

if (WIFSIGNALED(status)) {
    int signal_number = WTERMSIG(status);
}
```

상태를 공개 정수 하나로 바꾸는 API에서는 다음처럼 정의할 수 있습니다.

```c
if (WIFEXITED(status)) {
    return WEXITSTATUS(status);
}
if (WIFSIGNALED(status)) {
    return 128 + WTERMSIG(status);
}
```

`128 + signal`은 셸에서 흔히 사용하는 표현이지만 모든 프로그램이 따라야 하는 POSIX 규칙은 아닙니다. 프로그램이 어떤 값을 외부에 반환할지 직접 계약으로 정합니다.

파이프라인에 자식이 둘 이상 있으면 **모든 자식을 회수**해야 합니다. 파이프라인 전체의 결과로 어느 자식의 종료 상태를 사용할지도 별도로 정합니다. 단순한 셸과 비슷한 인터페이스라면 마지막 명령의 상태를 결과로 사용하는 경우가 많지만, 이것 역시 프로그램의 정책입니다.

## `pipe`

```c
int ends[2];

if (pipe(ends) == -1) {
    return -1;
}
```

성공하면 서로 다른 두 FD가 만들어집니다.

```text
ends[0]  읽기 끝
ends[1]  쓰기 끝
```

파이프는 **바이트 스트림**입니다. `write` 한 번이 반대편의 `read` 한 번과 일치한다는 보장은 없으며, 파이프 자체가 줄이나 레코드 경계를 보존해 주지도 않습니다.

### 파이프의 EOF 조건

읽는 쪽의 `read`가 EOF, 즉 `0`을 반환하려면 다음 두 조건이 충족되어야 합니다.

```text
1. 파이프 내부에 더 읽을 데이터가 없음
2. 파이프 쓰기 끝을 참조하는 FD가 모든 프로세스에서 닫힘
```

따라서 왼쪽 자식이 자신의 쓰기 끝을 닫았더라도 부모나 오른쪽 자식이 같은 쓰기 끝을 계속 열어 두고 있으면 오른쪽 명령은 EOF를 받지 못할 수 있습니다.

```text
부모 write_end 열림
        │
        └── 아직 writer가 존재한다고 판단
                    │
오른쪽 자식 read ──┴── EOF가 오지 않아 대기 가능
```

반대로 파이프의 읽기 끝을 가진 프로세스가 하나도 없는데 쓰려고 하면 `write`가 `EPIPE`로 실패할 수 있고, 기본 동작에서는 프로세스가 `SIGPIPE`를 받을 수 있습니다.

## `dup2`

```c
if (dup2(ends[1], STDOUT_FILENO) == -1) {
    /* 오류 처리 */
}
```

`dup2(source, destination)`는 `destination`이 이미 열려 있다면 필요한 닫기와 복제를 하나의 연산으로 처리하여, 성공 후 `destination`이 `source`와 같은 열린 파일 상태를 참조하게 만듭니다.

따라서 왼쪽 명령의 stdout을 파이프 쓰기 끝으로 연결할 수 있습니다.

```text
write_end ──dup2──> STDOUT_FILENO
```

오른쪽 명령은 파이프 읽기 끝을 stdin으로 연결합니다.

```text
read_end ──dup2──> STDIN_FILENO
```

### `source == destination`

`source == destination`이면 `dup2`는 유효한 FD에 대해 성공하며 실제 복제를 할 필요가 없습니다.

문제는 다음과 같이 복제 후 원본이라고 생각한 FD를 무조건 닫는 코드입니다.

```c
dup2(source, destination);
close(source);              /* source == destination이면 잘못됨 */
```

이 경우 `source`와 `destination`이 같은 번호라면 방금 사용할 표준 스트림을 직접 닫아 버립니다.

이 상황은 stdin 또는 stdout이 미리 닫혀 있어서 `pipe`가 FD `0`이나 `1`을 파이프 끝으로 재사용할 때 실제로 발생할 수 있습니다.

안전한 기본 형태는 다음과 같습니다.

```c
if (source != destination) {
    if (dup2(source, destination) == -1) {
        /* 오류 처리 */
    }
}
```

복제 후 파이프 원본 FD를 닫을 때도 **현재 최종 표준 FD와 같은 번호인지 확인**해야 합니다.

## 두 명령 연결

다음과 같은 파이프라인을 생각합니다.

```text
left_command | right_command
```

목표 FD 연결은 다음과 같습니다.

```text
부모
├── 왼쪽 자식
│   stdin  → 기존 stdin
│   stdout → 파이프 쓰기 끝
└── 오른쪽 자식
    stdin  → 파이프 읽기 끝
    stdout → 기존 stdout
```

각 프로세스는 자신에게 필요하지 않은 파이프 끝을 닫아야 합니다.

### 왼쪽 자식

왼쪽 자식은 파이프의 쓰기 끝만 stdout으로 사용합니다.

```c
if (write_end != STDOUT_FILENO) {
    if (dup2(write_end, STDOUT_FILENO) == -1) {
        /* exec하지 말고 오류 처리 후 _exit */
    }
}

/*
 * dup2가 STDOUT_FILENO를 교체했을 수도 있으므로
 * 번호가 최종 stdout과 같은 FD는 다시 닫지 않는다.
 */
if (read_end != STDOUT_FILENO) {
    close(read_end);
}

if (write_end != STDOUT_FILENO) {
    close(write_end);
}

execvp(argv[0], argv);
/* 실패 처리 후 _exit */
```

보통 stdin은 부모에게서 상속받은 기존 stdin을 그대로 사용합니다.

### 오른쪽 자식

오른쪽 자식은 파이프의 읽기 끝만 stdin으로 사용합니다.

```c
if (read_end != STDIN_FILENO) {
    if (dup2(read_end, STDIN_FILENO) == -1) {
        /* exec하지 말고 오류 처리 후 _exit */
    }
}

if (read_end != STDIN_FILENO) {
    close(read_end);
}

if (write_end != STDIN_FILENO) {
    close(write_end);
}

execvp(argv[0], argv);
/* 실패 처리 후 _exit */
```

보통 stdout은 부모에게서 상속받은 기존 stdout을 그대로 사용합니다.

### 부모

두 자식을 성공적으로 만든 뒤 부모는 파이프 자체를 읽거나 쓰지 않으므로 양쪽 끝을 모두 닫습니다.

```c
close(read_end);
close(write_end);
```

그 후 두 자식을 모두 `waitpid`로 회수합니다.

```text
두 자식 생성
→ 부모의 read_end 닫기
→ 부모의 write_end 닫기
→ 두 자식 waitpid
```

부모가 특히 `write_end`를 계속 열어 두면 왼쪽 명령이 종료한 뒤에도 오른쪽 자식이 EOF를 받지 못할 수 있습니다.

## 두 자식을 시작한 뒤 기다리기

왼쪽 자식이 파이프 용량보다 많은 데이터를 쓰는데, 부모가 오른쪽 자식을 만들기 전에 왼쪽 자식부터 기다리면 교착 상태가 생길 수 있습니다.

```text
왼쪽 자식
    │
    ├─ 파이프에 계속 write
    ▼
파이프가 가득 참
    │
    └─ write에서 대기

부모
    │
    └─ 왼쪽 자식이 종료하기를 waitpid에서 대기

오른쪽 자식
    └─ 아직 생성되지 않아 파이프를 읽을 수 없음
```

결과적으로 세 조건이 서로를 기다립니다.

```text
왼쪽 자식은 공간이 생기기를 기다림
부모는 왼쪽 자식이 끝나기를 기다림
파이프를 비울 오른쪽 자식은 아직 없음
```

따라서 기본 순서는 다음과 같습니다.

```text
pipe 생성
→ 왼쪽 자식 fork
→ 오른쪽 자식 fork
→ 부모의 파이프 양 끝 닫기
→ 두 자식 waitpid
```

두 자식이 모두 실행 중이라면 부모가 어느 자식을 먼저 `waitpid`하는지는 데이터 흐름 자체를 막지 않습니다. 중요한 점은 **파이프를 소비할 자식을 만들기 전에 생산자 자식의 종료를 기다리지 않는 것**입니다.

## 부분 `fork` 실패

첫 번째 `fork`는 성공했지만 두 번째 `fork`가 실패할 수 있습니다.

```text
pipe 생성 성공
→ 왼쪽 자식 생성 성공
→ 오른쪽 fork 실패
```

이 시점에는 이미 실제 자식 프로세스가 존재하므로 단순히 오류를 반환하면 안 됩니다. 부모가 먼저 파이프 끝을 닫고, 이미 만든 자식을 정리한 뒤 회수해야 합니다.

```text
부모의 read_end 닫기
→ 부모의 write_end 닫기
→ 이미 생성한 자식 종료 정책 수행
→ waitpid로 자식 회수
→ 원래 fork 오류 반환
```

부모의 파이프 끝을 먼저 닫는 이유는 자식이 파이프 입출력에서 불필요하게 계속 대기하는 상황을 줄이기 위해서입니다.

자식을 어떻게 종료할지는 함수의 계약으로 정합니다.

```text
SIGTERM  정상적인 종료 기회를 주고 싶을 때
SIGKILL  즉시 중단이 필요한 단순한 실패 정리 정책
```

`kill` 시점에 자식이 이미 종료했을 수도 있으므로 해당 오류와 관계없이 가능한 한 `waitpid`로 회수를 시도해야 합니다. `waitpid`가 `EINTR`로 중단되면 다시 호출합니다.

원래 두 번째 `fork`의 `errno`를 호출자에게 전달해야 한다면 정리 작업 전에 저장해야 합니다.

```c
pid_t right_pid = fork();

if (right_pid == -1) {
    int saved_errno = errno;

    close(read_end);
    close(write_end);

    kill(left_pid, SIGTERM);

    while (waitpid(left_pid, NULL, 0) == -1 && errno == EINTR) {
    }

    errno = saved_errno;
    return -1;
}
```

이 코드는 종료 정책의 한 예입니다. 실제 API에서는 자식이 `SIGTERM`을 무시하는 경우까지 기다릴 것인지, 강제 종료할 것인지도 정해야 합니다.

## 오류 경로에서도 FD를 닫기

정상 경로에서만 `close`를 잘해도 충분하지 않습니다. 다음 중 어느 단계에서 실패해도 이미 열린 FD를 정리해야 합니다.

```text
pipe 실패
첫 번째 fork 실패
두 번째 fork 실패
자식의 dup2 실패
자식의 exec 실패
부모의 waitpid 실패
```

예를 들어 첫 번째 `fork` 자체가 실패했다면 아직 자식은 없으므로 부모가 파이프 양 끝만 닫으면 됩니다.

```c
pid_t left_pid = fork();

if (left_pid == -1) {
    int saved_errno = errno;
    close(read_end);
    close(write_end);
    errno = saved_errno;
    return -1;
}
```

오류 처리 중 `close`, `kill`, `waitpid` 등이 `errno`를 바꿀 수 있으므로 호출자에게 보고할 원래 오류가 있다면 먼저 저장합니다.

## 파일 디스크립터 누수 확인

같은 파이프 실행 함수를 반복 호출했을 때 열린 파일 디스크립터 수가 계속 증가하지 않아야 합니다.

Linux에서는 `/proc/<pid>/fd`를 확인할 수 있고, 작은 테스트에서는 `fcntl`로 열려 있는 FD를 조사하거나 leak 검사 도구를 사용할 수 있습니다.

예를 들어 테스트 전후 열린 FD 수를 비교할 수 있습니다.

```text
호출 전 열린 FD 수 = N
파이프 함수 반복 실행
호출 후 열린 FD 수 = N
```

다만 이 검사는 테스트 중 다른 스레드나 라이브러리가 동시에 FD를 열거나 닫지 않는다는 전제가 필요합니다. 그렇지 않으면 개수 차이가 곧 해당 함수의 누수를 의미하지는 않습니다.

FD 개수뿐 아니라 **의도하지 않은 FD가 `exec`된 자식에게 상속되었는지**도 확인해야 합니다. 불필요한 파이프 쓰기 끝 하나가 남는 것만으로도 EOF 관련 정지가 발생할 수 있습니다.

## 프로세스 그룹

여러 자식에게 하나의 시그널을 전달해야 한다면 프로세스 그룹을 사용할 수 있습니다.

```text
pipeline process group
├── left child
└── right child
```

이렇게 묶으면 파이프라인 전체에 시그널을 전달하는 구조를 만들 수 있습니다.

프로세스 그룹 설정에는 `setpgid`를 사용하며, `fork`와 `exec` 사이에 어느 프로세스가 언제 그룹을 설정할지 정해야 합니다. 부모만 너무 늦게 설정하거나 자식만 설정하도록 두면 스케줄링 시점에 따라 경쟁이 생길 수 있으므로, 작업 제어를 구현하는 프로그램에서는 부모와 자식 양쪽의 `setpgid` 호출 정책을 명확히 설계합니다.

단순한 두 명령 파이프를 실행하고 기다리는 정도라면 프로세스 그룹은 필수가 아닙니다. 그러나 대화형 프로그램, 터미널 제어, 파이프라인 전체에 대한 `SIGINT` 전달 같은 **작업 제어(job control)** 를 구현할 때 중요해집니다.

## 테스트할 내용

- 파이프 용량보다 큰 데이터
- 빈 출력
- 왼쪽 명령 실패, 오른쪽 명령 성공
- 오른쪽 명령 실패
- 오른쪽 명령이 먼저 종료하여 왼쪽 writer가 `SIGPIPE` 또는 `EPIPE`를 만나는 경우
- 일반 종료 상태
- 시그널에 의한 종료
- 없는 명령
- 실행 권한 없는 파일
- `exec`가 다른 이유로 실패하는 경우
- stdin 또는 stdout이 닫혀 FD `0`·`1`이 파이프 끝으로 재사용되는 경우
- `dup2`에서 source와 destination이 같은 경우
- 부모가 파이프 쓰기 끝을 닫지 않았을 때 EOF 대기가 발생하는지
- 두 번째 `fork` 실패 뒤 첫 번째 자식이 회수되는지
- `waitpid`가 `EINTR`로 중단되는 경우
- 반복 실행 뒤 파일 디스크립터 수가 증가하지 않는지
- `exec`된 프로그램에 불필요한 파이프 FD가 남지 않는지
- `NULL` argv와 빈 `argv[0]`을 API가 명확히 거부하는지

## 완료 기준

1. `fork`의 세 반환 경우를 구분하고 실패 시 이미 확보한 자원을 정리합니다.
2. `fork` 후 부모와 자식의 FD가 같은 열린 파일 상태를 참조할 수 있음을 설명합니다.
3. 자식의 `exec` 실패는 정상 실행으로 돌아가지 않고 `_exit`로 끝냅니다.
4. `exec` 뒤에도 `FD_CLOEXEC`가 없는 FD는 남을 수 있음을 고려합니다.
5. 부모와 두 자식이 사용하지 않는 파이프 끝을 모두 닫습니다.
6. 파이프 EOF는 버퍼가 비고 모든 쓰기 끝이 닫힌 뒤에만 관찰됨을 설명합니다.
7. `dup2`의 source와 destination이 같은 경우에도 최종 stdin/stdout을 닫지 않습니다.
8. stdin 또는 stdout이 미리 닫혀 FD `0`·`1`이 재사용되는 경우를 처리합니다.
9. 두 자식을 모두 시작한 뒤 기다리는 이유를 교착 상태와 연결해 설명합니다.
10. 모든 자식을 `waitpid`로 회수하고 일반 종료와 시그널 종료를 구분합니다.
11. 파이프라인 전체의 공개 종료 상태를 어떤 자식에서 가져올지 명시합니다.
12. 두 번째 `fork` 실패 시 첫 번째 자식을 정리하고 회수합니다.
13. 오류 처리 중에도 호출자에게 반환할 원래 `errno`를 보존합니다.
14. 반복 실행과 `exec` 경로에서 파일 디스크립터가 누수되지 않음을 테스트합니다.
15. `argv`의 최소 입력 계약을 명확히 정의합니다.
