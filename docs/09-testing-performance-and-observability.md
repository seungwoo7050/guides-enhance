# 테스트, 성능과 관찰 정보

시뮬레이터에서 정상 동작을 한 번 확인한 것만으로 모바일 앱의 품질을 판단할 수 없습니다. 프로세스가 종료되고 권한이 바뀌며 네트워크가 끊기고 화면 크기와 글자 크기가 달라져도 같은 업무 결과를 얻는지 확인해야 합니다.

검사는 가능한 한 낮고 결정적인 위치에서 시작하고, 운영체제와 실제 바이너리가 필요한 항목만 실제 기기로 올립니다. 모든 경우를 E2E 테스트 하나에 넣지 않습니다.

## 이 문서에서 확인할 내용

- 상태 계산, 저장소, 네이티브 어댑터, 화면, 앱 통합, 실제 기기 검사의 역할을 나눕니다.
- 시간, ID, 네트워크, 저장소, 권한, 앱 상태를 테스트에서 통제합니다.
- 프로세스 재시작과 스키마 마이그레이션을 실제 초기 상태로 만듭니다.
- TalkBack, VoiceOver, 큰 글자와 키보드로 핵심 작업을 확인합니다.
- 릴리스에 가까운 빌드에서 시작 절차, 프레임, 메모리, 이미지, 네트워크와 배터리 사용을 측정합니다.
- 오류 기록에 앱, 빌드와 런타임과 동기화 상태를 남기되 민감정보는 제외합니다.

## 업무 결과에 맞춰 검사 위치를 고릅니다

### 1. 상태 계산 검사

대상:

- 기록 검증
- 화면 이동 입력 파싱
- 권한 결과 정규화
- 재시도 여부와 재시도 간격 결정
- 동기화 상태 전이
- 충돌 해결

장점:

- 빠르고 결정적입니다.
- Android와 iOS 런타임 없이 사건 순서를 직접 만들 수 있습니다.
- 잘못된 ID, 오래된 결과, 버전 회귀를 작은 입력으로 확인할 수 있습니다.

### 2. 저장소와 어댑터 검사

대상:

- SQLite 트랜잭션과 마이그레이션
- 기록 변경과 outbox 추가
- 명령 선점과 lease
- 파일 임시 저장, 소유된 경로, 미참조 정리
- HTTP 응답 파싱
- 네이티브 권한 결과 연결

테스트용 구현과 실제 어댑터가 호출자에게 같은 결과를 반환하는지 확인합니다. 단, 메모리 기반 테스트용 구현이 실제 SQLite 트랜잭션과 파일 실패를 지나치게 단순화하지 않게 별도 실제 어댑터 테스트를 둡니다.

### 3. 컴포넌트와 화면 검사

대상:

- 로딩, 빈 상태, 오프라인, 충돌 화면
- 입력 화면 검증과 초안 보존
- 라벨, 역할, 상태
- 경로 매개변수에 따른 화면 결과
- 저장 성공과 실패 뒤 사용자 동작

내부 hook 호출 순서보다 사용자가 누른 동작과 화면·접근성 결과를 확인합니다.

### 4. 앱 통합 검사

대상:

- 시작 절차 + 데이터베이스 + 최초 링크
- 로컬 저장 + outbox + 동기화 결과
- 선택기 결과 + 파일 복사 + 첨부 파일 행
- 알림 응답, 현재 저장 상태 조회와 화면 이동
- 앱 활성화 + 대기 중인 outbox

여러 어댑터를 연결했을 때 실제 순서와 실패 처리가 맞는지 봅니다.

### 5. 실제 기기 검사

대상:

- 설치, 콜드 실행, 업그레이드
- 시스템 권한 대화 상자
- 카메라, 사진 선택기, 위치
- 백그라운드, 프로세스 강제 종료, 알림
- TalkBack과 VoiceOver
- 릴리스-유사 성능
- 서명과 딥 링크와 유니버설 링크

이 검사는 시뮬레이터와 모의 구현이 대신할 수 없는 운영체제 동작을 확인합니다.

## 통제할 수 없는 값을 호출 형식으로 만듭니다

```ts
interface Clock {
  now(): string;
}

interface IdGenerator {
  commandId(): string;
}

interface SyncTransport {
  send(command: RecordCommand, signal: AbortSignal): Promise<WireResponse>;
}

interface LocationPort {
  current(): Promise<LocationMeasurementResult>;
}
```

테스트에서는 다음 사건을 직접 만듭니다.

- 시간 진행
- 중복 ID
- 마감 시각과 시간 초과
- 응답 순서 역전
- 권한 철회
- 파일 복사 실패
- 처리 결과 저장 실패
- 프로세스 재시작을 나타내는 새 저장소 인스턴스

운영 어댑터만 실제 시계, 무작위 ID, Expo API와 파일 시스템을 사용합니다.

## 대기 시간으로 실행 순서 경쟁을 추측하지 않습니다

다음 검사는 불안정합니다.

```text
요청 시작
→ 500ms 기다림
→ 끝났을 것이라고 가정
```

제어된 비동기 작업과 명시적인 사건 순서를 사용합니다.

```text
명령 A 전송 시작
→ 같은 기록의 명령 B 저장
→ B 관련 작업 준비
→ A 성공 응답 완료
→ 현재 로컬 리비전과 대기 중인 명령 확인
```

백그라운드 스케줄러 테스트도 두 종류로 나눕니다.

- 작업자 테스트: 조절 가능한 마감 시각, 저장소와 전송 구현으로 즉시 확인합니다.
- 기기 테스트: 실제 작업 등록과 콜백 수신 여부를 기록합니다.

작업자 테스트가 통과했다고 운영체제가 콜백을 준다는 뜻은 아닙니다.

## 프로세스 재시작을 실제로 만듭니다

빠른 갱신이나 화면 다시 불러오기만으로는 메모리 수명 문제를 찾을 수 없습니다.

검사 예:

- 기록과 outbox 커밋 뒤 프로세스 종료
- 명령을 선점한 상태에서 프로세스 종료
- 선택기 실행 중 `Activity`와 프로세스 재생성
- 이전 스키마의 앱을 설치한 뒤 새 버전으로 업그레이드
- 알림 콜드 스타트
- 파일은 있지만 메타데이터 행이 없음
- 메타데이터 행은 있지만 파일이 없음

자동 검사에서는 메모리 객체를 새 인스턴스로 바꾸고 저장된 스냅숏을 다시 읽습니다. 실제 기기에서는 앱 프로세스를 종료한 뒤 다시 실행합니다.

시험 데이터에는 다음 정보를 둡니다.

- 스키마 버전
- 앱, 빌드와 런타임 버전
- 초기 기록, outbox, 파일과 권한 상태
- 어떤 사건 뒤 저장한 스냅숏인지

## 마이그레이션 시험 데이터를 유지합니다

마이그레이션 코드만 호출하는 테스트로 끝내지 않습니다. 실제 이전 스키마와 데이터를 준비해 새 코드가 열게 합니다.

확인할 내용:

- 이전 기록이 보존됩니다.
- Outbox 데이터와 최초 시도 사본이 손상되지 않습니다.
- 새 필수 필드의 기본값이 업무 의미를 바꾸지 않습니다.
- 마이그레이션 실패 시 기존 DB를 삭제하지 않습니다.
- 업그레이드 뒤 앱이 콜드 스타트합니다.

릴리스 전에 지원하는 최소 버전에 가까운 DB 시험 데이터를 사용합니다.

## 실제 기기 검사표를 위험에 따라 정합니다

모든 기기와 OS를 보유할 수는 없습니다. 서로 다른 위험을 대표하는 조합을 선택합니다.

| 항목 | 최소 확인 대상 |
|---|---|
| 플랫폼 | Android, iOS |
| OS | 지원 최소에 가까운 버전, 현재 주력 버전 |
| 성능 | 느린 기기 가능 시, 일반 기기 |
| 화면 | 작은 휴대전화, 큰 휴대전화 또는 태블릿 또는 분할 화면 |
| 입력 | 터치, 화상 키보드, 스크린 리더 |
| 네트워크 | 오프라인, 느린 연결 또는 손실, Wi-Fi↔이동통신망 전환 |
| 수명 | 활성화, 백그라운드, 프로세스 강제 종료, 가능하면 재부팅 |
| 권한 | `not-determined`, `granted`, 거절, 제한, 철회 |
| 빌드 | 개발, 미리보기 또는 운영 환경에 가까운 |

한 플랫폼에서 확인한 결과를 다른 플랫폼 통과로 추정하지 않습니다.

## 접근성을 마지막 단계로 미루지 않습니다

컴포넌트를 만들 때 역할, 라벨과 상태를 확인하고 최종 단계에서 실제 보조기술로 전체 작업을 수행합니다.

필수 작업 예:

```text
앱 시작
→ 기록 목록 탐색
→ 새 기록 입력
→ 검증 오류 확인과 수정
→ 권한 거절 상태에서 저장
→ 오프라인과 동기화 상태 확인
→ 충돌 선택
→ 뒤로 가기와 모달 닫기
```

확인할 항목:

- 포커스 순서와 화면 제목
- 라벨, 역할, 상태, 값
- 동적 상태 음성 알림
- 큰 글자와 굵은 글씨 텍스트
- 색 이외의 상태 표현
- 제스처를 대체하는 동작
- 키보드와 전환 제어 가능성

자동 접근성 검사만으로 실제 읽기 순서와 포커스 경험을 증명하지 않습니다.

## 성능은 릴리스에 가까운 빌드에서 측정합니다

개발 모드의 경고, 디버거와 로그 기록 비용은 릴리스와 다릅니다. 성능 주장은 운영과 가까운 빌드와 실제 기기에서 측정합니다.

### 시작 절차

다음 구간을 나눕니다.

```text
프로세스 실행
→ 네이티브 런타임 준비
→ JavaScript 실행
→ SQLite 열기와 마이그레이션
→ 첫 의미 있는 화면
→ 사용자 입력 가능
```

시작 화면을 오래 보여 주면서 시작 절차 완료 시점을 숨기지 않습니다. 콜드 스타트와 웜 스타트를 구분합니다.

### 프레임과 반응성

가능한 원인:

- 렌더링마다 큰 쿼리 또는 JSON 변환
- 전역 상태 하나 때문에 모든 목록 행이 다시 렌더링됨
- 원본 이미지를 화면 크기보다 크게 디코딩함
- 네이티브 메인 스레드에서 파일과 해시 계산을 수행함
- 애니메이션과 JavaScript 작업이 같은 시점에 몰림
- 과도한 로그 기록

느려 보인다는 이유만으로 결과 저장을 추가하지 않습니다. 프로파일러에서 어느 컴포넌트와 스레드가 시간을 사용하는지 확인합니다.

### 목록과 이미지

- 가상화 목록의 창과 안정적인 키를 확인합니다.
- 행이 필요한 상태만 구독하게 합니다.
- 목록에서는 원본 이미지 대신 적절한 썸네일을 사용합니다.
- 캐시 상한과 메모리 경고 뒤 정리 방법을 둡니다.
- 화면을 떠난 뒤 리스너와 이미지 리소스를 정리합니다.

### 네트워크와 배터리

- 포그라운드 복귀마다 모든 데이터를 다시 받지 않습니다.
- 짧은 주기 조회와 재시도 폭주를 만들지 않습니다.
- 백그라운드 작업을 합치고 운영체제 스케줄러를 사용합니다.
- 위치와 카메라가 화면 종료 뒤 계속 실행되지 않게 합니다.
- 대용량 업로드의 압축과 분할, 네트워크 조건을 제품 요구에 맞춥니다.

### 저장소

- 자주 쓰는 SQLite 쿼리와 인덱스를 확인합니다.
- 마이그레이션 시간과 임시 저장 공간 사용량을 측정합니다.
- 파일 캐시 상한을 둡니다.
- 정리 작업이 UI 스레드와 시작 절차를 지나치게 막지 않게 합니다.

## 작업 단위로 성능 예산을 기록합니다

절대 수치는 제품과 기기에 따라 달라집니다. 다음 사용자 작업마다 측정 환경, 목표와 실제 값을 기록합니다.

- 콜드 스타트에서 기록 목록이 보일 때까지
- 로컬 기록 1,000개 목록 스크롤
- 상세 화면 열기
- 편집 저장
- 썸네일 여러 개가 보이는 목록
- outbox 100개 처리 중 UI 상호작용
- 백그라운드와 포그라운드 전환

목표를 넘으면 프로파일러 측정 결과, 원인과 선택한 절충점을 남깁니다. 측정 범위를 바꿔 수치를 좋아 보이게 만들지 않습니다.

## 관찰 정보에 릴리스 식별 정보를 포함합니다

오류와 추적 정보를 특정 바이너리와 연결할 수 있어야 합니다.

```text
플랫폼과 OS
앱 버전
Android versionCode 또는 iOS buildNumber
runtimeVersion
소스 리비전과 빌드 프로필
현재 경로 종류
세션 상태 종류
SQLite 스키마 버전
동기화 명령 ID와 시도 ID
네트워크 참고 정보
권한 결과 종류
```

이 정보가 있어야 특정 iOS 빌드나 런타임에서만 발생하는 문제를 좁힐 수 있습니다.

## 오류 종류를 구분합니다

- 네이티브 비정상 종료
- JavaScript 치명적 오류
- 처리되지 않은 Promise 거부
- 처리한 애플리케이션 오류
- 예상한 취소
- 권한 거절과 오프라인 같은 정상 입력

모든 오프라인 상태와 권한 거절을 오류 추적 도구에 보내면 실제 오류가 묻힙니다. 예상한 결과는 발생 횟수와 사용자가 겪은 결과로 기록합니다.

## 개인정보를 먼저 제한합니다

기본적으로 기록하지 않을 값:

- 기록 제목과 메모
- 정확한 위치
- 이미지 바이트와 로컬 파일 URI
- 액세스 토큰과 갱신 토큰
- 인가 헤더
- 알림 데이터 전체
- 서명된 업로드 URL 전체

연관 분석에는 무작위 명령 ID와 시도 ID와 민감정보가 없는 분류를 사용합니다.

## 회귀 테스트를 가장 낮은 위치에 둡니다

```text
늦은 동기화 성공이 더 최신 편집을 덮음
→ 동기화 저장소와 모델 테스트

마이그레이션에서 인덱스 누락
→ SQLite 마이그레이션 시험 데이터

권한 거절 뒤 포커스 손실
→ 컴포넌트 테스트 + 실제 기기 접근성 확인

특정 바이너리에서 네이티브 메서드 없음
→ 런타임 호환성 기본 검사
```

모든 버그를 느린 E2E 테스트 하나로만 고정하지 않습니다. 원인을 가장 직접적으로 재현하는 테스트를 우선합니다.

## 검증 시나리오

- 같은 입력에서 항상 같은 화면 이동 결과
- 응답 순서 역전
- 명령 응답 유실과 처리 결과 저장 실패
- 유효한 lease와 lease 만료
- 이전 스키마 업그레이드
- 프로세스 강제 종료 뒤 outbox 복원
- 선택기 중 프로세스 재생성
- 권한 철회 뒤 앱 활성화
- 알림의 콜드 스타트와 웜 상태 응답
- 큰 글자, 키보드, TalkBack과 VoiceOver
- 개발과 릴리스-유사 시작 절차 차이
- 1,000개 기록과 여러 썸네일
- 로그에서 기록 내용, 토큰, 위치가 제외됨

## 완료 기준

- 상태 계산, 어댑터, 화면, 앱 통합, 실제 기기 검사를 구분합니다.
- 시간, ID, 네트워크, 저장소와 권한 실패를 테스트에서 통제합니다.
- 대기 시간 없이 실행 순서 경쟁과 순서 역전을 만듭니다.
- 실제 이전 DB 시험 데이터로 마이그레이션을 확인합니다.
- 프로세스 종료 뒤 새 인스턴스에서 저장된 상태를 복원합니다.
- Android와 iOS 실제 기기에서 권한, 알림과 백그라운드 제한을 확인합니다.
- TalkBack, VoiceOver와 큰 글자에서 핵심 작업을 수행합니다.
- 릴리스에 가까운 빌드에서 시작 절차, 목록, 이미지와 동기화 성능을 측정합니다.
- 오류 정보에 앱, 빌드, 런타임과 스키마가 있고 민감정보가 없습니다.
- 대표 버그가 가장 낮은 적절한 위치의 회귀 테스트로 남아 있습니다.
