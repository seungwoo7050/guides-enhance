# 운영 중 장애를 확인하고 복구하기

앞 장까지는 Nginx, PHP-FPM, MariaDB를 연결하고 반복 실행 가능한 시작 절차를 만들었습니다. 이제 새 기능을 추가하지 않고 정상 구성을 한 가지씩 깨뜨려 원인을 찾는 방법을 다룹니다.

장애 대응의 목적은 오류 메시지를 보고 즉시 설정을 바꾸는 것이 아니라, **요청이 어디까지 정상적으로 도달했는지 증거로 확인해 실패 지점을 좁히는 것**입니다. 여러 설정을 동시에 바꾸면 어떤 변경이 문제를 해결했는지 알 수 없고, 원인이 남은 채 증상만 달라질 수도 있습니다.

```text
증상 기록
→ 마지막으로 성공한 단계 확인
→ 바로 다음 단계 검사
→ 한 가지 가설 검증
→ 한 가지 원인 수정
→ 동일한 검사로 복구 확인
```

예를 들어 브라우저에서 `502 Bad Gateway`를 받았다는 사실만으로 Nginx 설정이 원인이라고 단정할 수 없습니다. 애플리케이션이 DB 인증 실패로 시작하지 못했고, 그 결과 Nginx가 PHP-FPM에 연결할 수 없어 502가 발생했을 수도 있습니다.

## 1. “실행 중”과 “정상”은 다릅니다

서비스 상태는 한 가지 값이 아니라 여러 계층으로 나누어 확인해야 합니다.

### 컨테이너

- 컨테이너가 생성됐습니까?
- 컨테이너 상태가 `running`, `exited`, `restarting` 중 무엇입니까?
- PID 1이 계속 실행 중입니까?
- 종료와 재시작을 반복하고 있습니까?

컨테이너가 `running`이라는 사실은 **PID 1이 살아 있다는 뜻**일 뿐, 애플리케이션이 요청을 처리할 준비가 됐다는 뜻은 아닙니다.

### 프로세스

- 기대한 서버가 PID 1입니까?
- 필요한 워커가 만들어졌습니까?
- 올바른 사용자와 그룹으로 실행됩니까?
- 프로세스가 시작 직후 죽거나 계속 다시 만들어지지 않습니까?

### 네트워크

- 서비스 이름이 IP 주소로 해석됩니까?
- 두 서비스가 같은 Compose 네트워크에 연결되어 있습니까?
- 대상 프로세스가 예상 주소와 포트에서 연결을 기다립니까?
- 다른 컨테이너에서 해당 TCP 포트까지 연결할 수 있습니까?

### 프로토콜

TCP 연결 성공 뒤에는 실제 서비스 프로토콜을 확인합니다.

- TLS 핸드셰이크가 성공합니까?
- Nginx가 올바른 HTTP 응답을 반환합니까?
- PHP-FPM이 FastCGI ping 요청에 응답합니까?
- MariaDB가 애플리케이션 계정의 인증과 읽기 쿼리를 처리합니까?

TCP 연결이 됐다는 사실만으로 해당 포트에서 기대한 프로토콜이 정상 동작한다는 것은 아닙니다.

### 사용자 기능과 데이터

- 실제 API가 기대한 상태 코드와 본문을 반환합니까?
- 필요한 테이블과 데이터가 있습니까?
- 컨테이너를 재생성해도 데이터가 남습니까?
- 백업을 별도의 빈 DB에 복원할 수 있습니까?

하위 단계가 실패한 상태에서 상위 기능부터 반복해서 검사하면 원인보다 2차 증상만 보게 됩니다.

## 2. 생존 검사, 준비 검사, 사용자 기능 검사를 구분합니다

상태 검사는 목적에 따라 확인 범위가 달라집니다.

### 생존 검사

생존 검사(liveness check)는 **프로세스가 살아 있고 계속 실행할 수 있는지** 확인합니다.

예를 들어 PHP-FPM 프로세스 자체가 멈춘 상태라면 재시작이 도움이 될 수 있습니다. 반대로 생존 검사에 DB나 외부 API까지 포함하면 외부 의존성의 일시적인 장애 때문에 정상 애플리케이션을 반복해서 재시작하는 문제가 생길 수 있습니다.

### 준비 검사

준비 검사(readiness check)는 **현재 새 요청을 받을 수 있는지** 확인합니다.

다음과 같은 상태에서는 프로세스가 살아 있어도 준비되지 않은 상태일 수 있습니다.

```text
프로세스 시작
→ 설정 읽기 완료
→ DB 연결 대기
→ 초기화 수행
→ 워커 준비 완료
→ 요청 수신 가능
```

초기화가 끝나지 않았거나 필수 의존 서비스에 접근할 수 없다면 트래픽을 받아서는 안 될 수 있습니다.

### 사용자 기능 검사

사용자 기능 검사는 외부에서 실제 요청을 보내 중요한 요청 경로 전체를 확인합니다.

```text
HTTPS 요청
→ Nginx
→ FastCGI
→ PHP-FPM
→ 애플리케이션 코드
→ MariaDB 읽기
→ 응답
```

이 검사는 실제 기능을 확인한다는 장점이 있지만 실패 가능한 지점이 많습니다. 실패했을 때는 내부 계층별 검사로 원인을 다시 좁혀야 합니다.

Docker Compose의 `healthcheck`는 컨테이너에 `starting`, `healthy`, `unhealthy` 상태를 부여하는 하나의 검사 메커니즘입니다. Kubernetes처럼 별도의 liveness/readiness probe 종류를 자동으로 제공하는 것은 아닙니다. 따라서 **해당 healthcheck가 생존, 준비, 전체 기능 중 무엇을 의미하는지 구성과 문서에서 명확히 정해야 합니다.**

또한 `depends_on`에서 `condition: service_healthy`를 사용하면 Compose는 의존 서비스의 healthcheck가 성공한 뒤 종속 서비스를 시작할 수 있습니다. 하지만 이것은 이후 발생하는 모든 런타임 장애를 대신 처리하지 않습니다. 애플리케이션 자체에도 적절한 연결 오류 처리와 제한된 재시도가 필요합니다.

## 3. 서비스가 사용하는 프로토콜로 검사합니다

포트가 열렸는지만 확인하지 말고 실제 서비스가 사용하는 프로토콜로 검사합니다.

### Nginx

개발 환경에서 자체 서명 인증서를 사용한다면 다음과 같이 TLS와 HTTP 응답을 함께 확인할 수 있습니다.

```sh
curl -kfsS https://127.0.0.1:19443/healthz >/dev/null
```

이 검사가 성공하면 적어도 다음 경로가 동작합니다.

```text
호스트 TCP 연결
→ TLS 핸드셰이크
→ Nginx HTTP 처리
→ /healthz 응답
```

단, `-k` 또는 `--insecure`는 서버 인증서 검증을 끕니다. 따라서 인증서 신뢰 체인이나 호스트 이름 검증이 올바른지는 확인하지 못합니다.

### PHP-FPM

FPM 풀에 다음 설정이 있다고 가정합니다.

```ini
ping.path = /ping
ping.response = pong
```

FastCGI 클라이언트인 `cgi-fcgi`가 설치되어 있다면 app 컨테이너 내부에서 다음처럼 검사할 수 있습니다.

```sh
REQUEST_METHOD=GET \
SCRIPT_NAME=/ping \
SCRIPT_FILENAME=/ping \
cgi-fcgi -bind -connect 127.0.0.1:9000 | grep -q pong
```

PHP-FPM은 HTTP 서버가 아니라 FastCGI 서버이므로 다음 검사는 적절하지 않습니다.

```sh
curl http://127.0.0.1:9000
```

`curl`이 실패하는 것은 PHP-FPM 장애의 증거가 아니라 **프로토콜이 맞지 않는 검사**일 수 있습니다.

### MariaDB

DB 컨테이너 안에서 서버 생존 여부만 확인하려면 Unix 소켓을 사용할 수 있습니다.

```sh
mariadb-admin \
  --protocol=socket \
  --socket=/run/mysqld/mysqld.sock \
  ping --silent
```

`mariadb-admin ping`은 MariaDB 서버가 살아 있는지 확인하는 명령입니다. 중요한 점은 **서버가 실행 중이면 인증 오류가 발생해도 종료 상태 0을 반환할 수 있다는 것**입니다. 따라서 이 명령의 성공을 “애플리케이션 사용자 인증까지 성공했다”는 의미로 해석하면 안 됩니다.

애플리케이션이 실제로 사용할 수 있는지 확인하려면 애플리케이션 컨테이너에서 실제 사용자로 TCP 연결과 읽기 쿼리를 실행합니다.

```text
서비스 이름 해석
→ db:3306 TCP 연결
→ 사용자 인증
→ 데이터베이스 선택
→ SELECT 실행
```

### 전체 애플리케이션

```sh
curl -kfsS https://127.0.0.1:19443/api/notes >/dev/null
```

이 검사는 게이트웨이, 애플리케이션, 데이터베이스의 읽기 경로를 한 번에 확인합니다. 성공하면 강한 증거가 되지만, 실패만으로 어느 계층이 원인인지는 알 수 없습니다.

## 4. 좋은 상태 검사의 조건

상태 검사는 다음 성질을 갖는 것이 좋습니다.

- 짧게 끝납니다.
- 한 번의 실행에 제한 시간이 있습니다.
- 정상 상태에서 적은 CPU, 메모리와 I/O만 사용합니다.
- 읽기 전용입니다.
- 반복 실행해도 서비스 상태를 바꾸지 않습니다.
- 서비스가 실제로 사용하는 프로토콜을 확인합니다.
- 정상으로 판단하는 조건이 명확합니다.
- 실패했을 때 어느 범위를 검사했는지 알 수 있습니다.

예를 들어 다음 작업은 주기적인 상태 검사에 적합하지 않습니다.

- 대형 통계 쿼리
- 외부 인터넷 서비스 호출
- 테이블 생성이나 마이그레이션
- 데이터 자동 수정
- 전체 백업 생성

상태 검사가 너무 깊으면 의존 서비스의 장애가 연쇄적인 `unhealthy` 상태를 만들 수 있습니다. 반대로 단순히 “프로세스 이름이 존재하는지”만 확인하면 실제 서비스가 응답하지 않는 장애를 놓칠 수 있습니다. 검사 목적에 맞는 깊이를 선택해야 합니다.

## 5. 기본 진단 순서

다음 순서를 출발점으로 사용합니다.

```text
1. Compose가 기대한 서비스를 만들었는가?
2. 컨테이너의 PID 1이 실행 중인가?
3. 가장 먼저 나타난 오류 로그는 무엇인가?
4. 기대한 프로세스와 워커가 존재하는가?
5. 대상 프로세스가 예상 주소와 포트에서 기다리는가?
6. 서비스 이름이 올바른 IP로 해석되는가?
7. 다른 컨테이너에서 TCP 연결이 되는가?
8. 실제 프로토콜 요청에 응답하는가?
9. 설정과 비밀값 파일이 올바른가?
10. 파일 경로와 권한이 올바른가?
11. 기대한 볼륨과 데이터가 연결됐는가?
12. 사용자 기능이 정상인가?
```

모든 장애에 이 순서를 기계적으로 끝까지 적용할 필요는 없습니다. 이미 확보한 증거를 기준으로 다음 검사를 선택합니다.

핵심은 **마지막으로 성공한 계층 바로 다음을 검사하는 것**입니다.

예를 들어 다음 사실을 이미 확인했다고 가정합니다.

```text
getent hosts app   성공
nc -z app 9000     실패
```

이 경우 DNS를 더 조사하기보다 PHP-FPM 프로세스, `listen` 설정과 컨테이너 네트워크를 확인하는 편이 타당합니다.

## 6. Compose 상태와 실제 설정을 확인합니다

먼저 Compose가 현재 어떤 구성을 보고 있는지 확인합니다.

```sh
docker compose ps -a
docker compose config --services
docker compose config
```

확인할 내용은 다음과 같습니다.

- 기대한 서비스가 존재하는지
- 컨테이너 상태와 종료 코드
- health 상태
- 호스트에 게시된 포트
- 환경변수 보간 결과
- 연결된 네트워크와 볼륨
- `depends_on`, `healthcheck`, `restart` 설정

`docker compose config`는 여러 Compose 파일, 환경변수와 보간을 적용한 결과를 확인할 때 유용합니다. 원본 YAML이 맞아 보여도 실제 해석 결과가 예상과 다를 수 있습니다.

다만 출력에는 환경에 따라 민감한 값이 포함될 수 있습니다. 외부에 로그나 명령 결과를 공유하기 전에 비밀번호, 토큰과 인증 정보를 확인합니다.

특정 컨테이너의 더 자세한 상태는 `docker inspect`로 확인할 수 있습니다.

```sh
docker inspect container-name \
  --format 'status={{.State.Status}} exit={{.State.ExitCode}} error={{.State.Error}}'
```

## 7. 로그에서는 최초 오류를 찾습니다

```sh
docker compose logs --timestamps
docker compose logs --tail=100 app
docker compose logs -f gateway app db
```

로그를 볼 때는 마지막 오류 한 줄보다 **시간순으로 가장 먼저 발생한 의미 있는 실패**를 찾습니다.

예를 들어 다음과 같이 문제가 전파될 수 있습니다.

```text
DB 인증 실패
→ 애플리케이션 초기화 실패
→ app 컨테이너 종료
→ Nginx가 PHP-FPM에 연결하지 못함
→ 사용자 요청 502
```

사용자가 보는 502는 가장 마지막 증상입니다. 원인은 DB 인증 실패일 수 있습니다.

재시작 정책이 활성화되어 있으면 같은 오류가 반복되면서 첫 실패가 로그 위쪽으로 밀릴 수 있습니다. 가능하면 타임스탬프와 함께 확인하고, 장애 조사를 시작하기 전에 로그를 보존합니다.

로그에는 다음 정보를 남기지 않습니다.

- 비밀번호
- 비밀값 파일의 내용
- 전체 인증 토큰
- `Authorization` 헤더
- 민감한 쿼리 파라미터

비밀값을 읽는 시작 스크립트에서 `set -x`를 사용하면 명령 확장 결과에 비밀값이 포함될 수 있으므로 주의합니다.

## 8. 프로세스와 PID 1을 확인합니다

실행 중인 서비스의 프로세스 관계는 다음과 같이 확인할 수 있습니다.

```sh
docker compose top
```

컨테이너에 `ps`가 설치되어 있다면 내부에서도 확인할 수 있습니다.

```sh
docker compose exec app ps -ef
```

이미지에 따라 BusyBox `ps`, procps `ps` 등 구현과 지원 옵션이 다르므로 특정 옵션이 실패했다는 사실을 서비스 장애로 해석하지 않습니다.

확인할 항목:

- PID 1이 기대한 서버인지 시작 셸인지
- PHP-FPM master와 worker가 존재하는지
- 실행 사용자와 그룹이 올바른지
- 프로세스가 계속 새 PID로 바뀌는지
- 종료된 자식 프로세스가 누적되는지

컨테이너가 이미 종료됐다면 `docker compose exec`이나 `docker exec`으로 내부에 들어갈 수 없습니다. 이 경우 먼저 다음 정보를 확인합니다.

```sh
docker compose ps -a
docker compose logs app
docker inspect container-name \
  --format 'exit={{.State.ExitCode}} oom={{.State.OOMKilled}} error={{.State.Error}}'
```

그 뒤 필요하면 동일한 이미지로 **별도의 조사용 컨테이너**를 실행하거나, 시작 명령을 임시로 바꿔 셸을 유지한 상태에서 파일과 설정을 검사합니다. 원래 실패한 컨테이너를 바로 삭제하면 증거를 잃을 수 있습니다.

## 9. 이름 해석과 TCP 연결을 따로 검사합니다

Compose 네트워크에서 서비스 이름은 DNS 이름처럼 사용됩니다. 먼저 이름 해석을 확인합니다.

```sh
docker compose exec gateway getent hosts app
docker compose exec app getent hosts db
```

다음으로 TCP 연결을 따로 확인합니다.

```sh
docker compose exec gateway sh -c 'nc -z -w 3 app 9000'
docker compose exec app sh -c 'nc -z -w 3 db 3306'
```

`getent` 또는 `nc`는 최소 이미지에 설치되어 있지 않을 수 있습니다. **진단 도구가 없다는 것과 네트워크가 고장 났다는 것은 다른 상태**입니다. 필요한 경우 이미지에 이미 있는 런타임(PHP 등)으로 연결을 시험하거나 별도의 진단용 컨테이너를 같은 네트워크에 연결합니다.

검사 결과는 다음처럼 해석합니다.

```text
DNS 실패
→ 서비스 이름 또는 네트워크부터 확인

DNS 성공 + TCP 실패
→ 대상 프로세스, listen 주소/포트, 네트워크 경로 확인

DNS 성공 + TCP 성공 + 프로토콜 실패
→ 프로토콜 설정, 인증, 요청 내용 확인
```

확인할 항목:

- Compose 서비스 이름 오타
- 두 서비스가 공통 네트워크에 연결됐는지
- 다른 Compose 프로젝트의 자원을 보고 있지 않은지
- 대상 프로세스가 실제 포트에서 `listen` 중인지
- `127.0.0.1`에만 바인드되어 다른 컨테이너에서 접근할 수 없는지

컨테이너 IP를 설정에 직접 고정하지 않습니다. 컨테이너 재생성 뒤 IP가 달라질 수 있으므로 Compose 서비스 이름을 사용합니다.

## 10. HTTP와 TLS를 분리해서 확인합니다

개발용 자체 서명 인증서를 사용한다면 다음 명령으로 연결 과정을 자세히 볼 수 있습니다.

```sh
curl -vk https://127.0.0.1:19443/healthz
```

verbose 출력에서 다음 단계를 구분합니다.

- 어느 IP와 포트에 연결했는지
- TLS 핸드셰이크가 진행됐는지
- 서버가 어떤 인증서를 보냈는지
- 보낸 HTTP 요청의 메서드, 경로와 `Host` 헤더
- 받은 HTTP 상태 코드와 헤더

`-k`는 인증서 검증을 생략하므로 “TLS로 암호화된 연결이 만들어졌다”는 것은 확인할 수 있지만, “올바른 서버 인증서를 신뢰 가능하게 검증했다”는 증거는 아닙니다.

로컬 CA 또는 직접 신뢰하려는 인증서 파일이 있다면 검증을 켜고 확인합니다.

```sh
curl --cacert development.crt \
  https://localhost:19443/healthz
```

여기서 URL의 호스트 이름은 인증서의 SAN(Subject Alternative Name)과 일치해야 합니다.

더 자세한 TLS 정보를 확인하려면 다음과 같이 SNI 서버 이름을 명시합니다.

```sh
openssl s_client \
  -connect 127.0.0.1:19443 \
  -servername localhost \
  -showcerts </dev/null
```

확인할 항목:

- 인증서의 SAN
- 유효기간
- 서버가 보낸 인증서 체인
- 선택된 TLS 버전과 암호 스위트
- SNI에 따라 올바른 `server` 블록이 선택되는지

## 11. FastCGI 문제를 단계별로 확인합니다

Nginx가 502를 반환하면 먼저 PHP-FPM 자체가 살아 있는지 app 컨테이너 안에서 검사합니다.

```sh
docker compose exec app sh -c '
  REQUEST_METHOD=GET \
  SCRIPT_NAME=/ping \
  SCRIPT_FILENAME=/ping \
  cgi-fcgi -bind -connect 127.0.0.1:9000
'
```

이 검사는 **app 컨테이너 내부의 `127.0.0.1:9000`**에 연결합니다. gateway 컨테이너에서 같은 주소를 사용하면 gateway 자신을 가리키므로 의미가 달라집니다.

그 다음 Nginx가 실제로 사용하는 경로를 따로 확인합니다.

```text
app 내부 127.0.0.1:9000 FastCGI ping 성공
→ PHP-FPM 자체는 응답 가능

하지만 gateway → app:9000 실패
→ Compose DNS, 네트워크, FPM listen 주소 확인

app:9000 연결 성공 + Nginx 502
→ fastcgi_pass, FastCGI 파라미터, 응답 로그 확인

FastCGI 연결 성공 + PHP 파일 실행 실패
→ SCRIPT_FILENAME, 실제 파일 위치, 권한 확인
```

`SCRIPT_FILENAME`은 Nginx 컨테이너에서 보이는 경로가 아니라 **PHP-FPM 컨테이너에서 실제 PHP 파일이 존재하는 경로**여야 합니다.

예를 들어 Nginx가 다음 값을 보낸다면

```text
SCRIPT_FILENAME=/var/www/html/index.php
```

app 컨테이너에도 해당 경로의 파일이 실제로 존재해야 합니다.

```sh
docker compose exec app ls -l /var/www/html/index.php
```

PHP 코드가 실제로 실행된 뒤 500을 반환한다면 FastCGI 연결보다 애플리케이션 코드, DB 연결과 PHP-FPM 로그를 우선 확인합니다.

## 12. 데이터베이스를 단계별로 확인합니다

DB 문제도 “서버가 살아 있음”과 “애플리케이션이 사용할 수 있음”을 나눠 확인합니다.

### 1단계: DB 프로세스 생존

DB 컨테이너 안에서 Unix 소켓으로 확인합니다.

```sh
docker compose exec db mariadb-admin \
  --protocol=socket \
  --socket=/run/mysqld/mysqld.sock \
  ping --silent
```

이 검사는 서버가 살아 있는지 확인하는 용도입니다. 앞서 설명했듯 `mariadb-admin ping`은 인증 실패가 있어도 서버가 실행 중이면 성공 상태를 반환할 수 있으므로 사용자 인증 검사로 사용하지 않습니다.

### 2단계: app에서 TCP, 인증과 쿼리 확인

애플리케이션 컨테이너에서 실제 애플리케이션 계정으로 연결합니다.

```sh
docker compose exec app php -r '
$path = getenv("DB_PASSWORD_FILE");
if ($path === false || !is_readable($path)) {
    fwrite(STDERR, "DB password file is not readable\n");
    exit(1);
}

$password = rtrim(file_get_contents($path), "\r\n");
$pdo = new PDO(
    "mysql:host=db;port=3306;dbname=appdb;charset=utf8mb4",
    "appuser",
    $password,
    [
        PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
        PDO::ATTR_TIMEOUT => 3,
    ]
);

echo $pdo->query("SELECT 1")->fetchColumn(), PHP_EOL;
'
```

이 검사가 성공하면 다음 범위를 확인한 것입니다.

```text
app 컨테이너
→ db 이름 해석
→ TCP 3306 연결
→ MariaDB handshake
→ appuser 인증
→ appdb 선택
→ SELECT 실행
```

비밀번호를 명령행 인자로 직접 넣으면 프로세스 목록이나 셸 기록 등에서 노출될 수 있습니다. 위 예제는 기존 비밀값 파일을 읽습니다.

### 오류를 계층별로 해석하기

| 오류 | 의미 | 먼저 확인할 내용 |
|---|---|---|
| 이름 해석 실패 | `db`를 IP로 찾지 못함 | 서비스 이름, Compose 네트워크 |
| `Connection refused` | 주소까지 도달했지만 포트를 받는 프로세스가 없음 | DB 프로세스, 포트, `bind-address` |
| 연결 제한 시간 초과 | 연결 경로가 응답하지 않음 | 네트워크 경로, 과부하, 방화벽 |
| `Access denied` | MariaDB까지 도달했지만 인증/호스트 권한 실패 | 사용자, 비밀번호, `'user'@'host'` 권한 |
| `Unknown database` | 서버와 인증은 통과했지만 DB가 없음 | 최초 초기화, DB 이름 |
| 테이블 없음 | DB 선택까지 됐지만 스키마가 없음 | 애플리케이션 초기화, 마이그레이션 |
| 쿼리 제한 시간/지연 | 연결 후 SQL 처리 문제 | 잠금, 실행 계획, 부하 |

이렇게 해석하면 “DB 연결 실패”라는 하나의 표현을 여러 단계로 분해할 수 있습니다.

## 13. 설정과 비밀값 출처를 확인합니다

프로세스와 네트워크가 정상이어도 설정 값이 틀리면 요청은 실패합니다.

환경변수 이름을 확인할 때 비밀값 자체는 출력하지 않습니다.

예를 들어 비밀값 파일은 값 대신 메타데이터를 확인합니다.

```sh
docker compose exec app sh -c '
  test -n "$DB_PASSWORD_FILE" || exit 1
  test -r "$DB_PASSWORD_FILE" || exit 1
  ls -l "$DB_PASSWORD_FILE"
'
```

확인할 항목:

- 환경변수가 존재하는지
- 파일 경로가 기대한 값인지
- 파일이 실제로 마운트됐는지
- 실행 사용자가 읽을 수 있는지
- 빈 파일이 아닌지
- 비밀값 교체 뒤 DB 계정 값과 애플리케이션 값이 서로 일치하는지

“파일이 존재한다”와 “내용이 올바르다”는 별개의 조건입니다. 다만 실제 비밀값을 로그에 출력해 비교하지 않습니다.

## 14. 파일 경로와 권한을 확인합니다

Linux에서는 파일 자체의 권한뿐 아니라 **파일에 도달하기 위한 모든 상위 디렉터리를 통과할 수 있어야** 합니다.

```sh
id
ls -ld /var /var/www /var/www/html
ls -l /var/www/html/index.php
namei -l /var/www/html/index.php
```

`namei` 역시 이미지에 없을 수 있으므로 사용할 수 없다면 `ls -ld`로 상위 경로를 단계별로 확인합니다.

디렉터리의 실행(`x`) 권한은 해당 디렉터리를 통과하고 내부 이름을 접근하는 데 필요합니다. 따라서 파일에 읽기 권한이 있어도 상위 디렉터리를 통과하지 못하면 접근에 실패할 수 있습니다.

확인할 항목:

- 실제 실행 UID/GID
- 파일 소유자와 그룹
- 파일의 읽기·쓰기 권한
- 디렉터리의 통과(`x`) 권한
- bind mount가 이미지 안의 파일을 가렸는지
- 읽기 전용 마운트에 쓰려고 하는지
- SELinux가 활성화된 호스트에서 적절한 label이 필요한지

문제를 임시로 숨기기 위해 다음과 같이 전체 권한을 열지 않습니다.

```sh
chmod -R 777 /var/www/html
```

이렇게 하면 원래 어떤 사용자와 경로의 권한이 틀렸는지 알기 어려워지고 불필요한 쓰기 권한까지 생깁니다. 필요한 주체에게 필요한 권한만 부여합니다.

## 15. 볼륨과 데이터 위치를 확인합니다

데이터가 사라진 것처럼 보이면 먼저 **기존 데이터가 실제로 삭제됐는지, 아니면 다른 빈 볼륨을 보고 있는지** 구분합니다.

```sh
docker volume ls
docker volume inspect PROJECT_db-data
docker inspect container-name --format '{{json .Mounts}}'
```

확인할 항목:

- Compose 프로젝트 이름이 달라져 새 볼륨이 만들어졌는지
- 기대한 볼륨 이름인지
- DB 컨테이너의 `/var/lib/mysql`에 연결됐는지
- bind mount가 원래 이미지나 볼륨의 내용을 가렸는지
- `docker compose down -v` 또는 명시적 volume 삭제를 실행했는지

예를 들어 다음 두 상황은 겉으로는 모두 “DB가 비어 있음”으로 보일 수 있습니다.

```text
상황 A
기존 데이터 볼륨 삭제
→ 데이터 실제 손실

상황 B
Compose 프로젝트 이름 변경
→ 새로운 빈 볼륨 생성
→ 기존 볼륨은 호스트에 그대로 남아 있음
```

상황 B에서 새 빈 볼륨을 삭제하거나 초기화를 반복하기 전에 기존 볼륨 목록과 마운트를 확인해야 합니다.

데이터 사고가 의심될 때는 기존 볼륨에 쓰기 작업을 최소화하고, 가능하면 복사본이나 스냅샷을 만든 뒤 조사합니다.

## 16. 재시작 반복을 멈추고 원인을 확인합니다

재시작 정책은 일시적인 프로세스 종료에서 서비스를 다시 띄우는 데 도움을 줄 수 있지만, 잘못된 설정 자체를 고치지는 않습니다.

```text
시작
→ 설정 오류
→ 종료
→ 자동 재시작
→ 같은 오류
→ 다시 종료
```

상태와 로그를 먼저 확인합니다.

```sh
docker compose ps -a
docker compose logs --tail=200 app
docker inspect container-name \
  --format 'restart={{.RestartCount}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}}'
```

조사 중에는 자동 재시작 때문에 로그와 상태가 계속 변하지 않도록 재시작 반복을 제어할 필요가 있습니다. 단, 운영 서비스에서는 재시작 정책을 즉시 바꾸기 전에 영향 범위를 먼저 판단합니다.

재시작하거나 컨테이너를 삭제하기 전에 최소한 다음 증거를 남깁니다.

- 최초 오류가 포함된 로그
- 종료 코드
- OOMKilled 여부
- 적용된 이미지와 설정
- 네트워크 연결
- 볼륨 마운트
- healthcheck 상태

## 17. SIGTERM과 정상 종료를 확인합니다

일반적인 Docker 종료 경로를 검사할 때는 `kill`보다 `stop`이 더 적합합니다.

```sh
docker compose stop -t 10 app
```

일반적으로 Docker는 컨테이너의 주 프로세스에 설정된 종료 시그널을 보내고 지정된 유예 시간 동안 기다립니다. 별도 설정이 없다면 기본 시그널은 SIGTERM입니다. 프로세스가 제한 시간 안에 종료하지 않으면 SIGKILL로 강제 종료할 수 있습니다.

기대하는 흐름은 다음과 같습니다.

```text
Docker가 PID 1에 종료 시그널 전달
→ 서버가 새 작업 수락 중단
→ 진행 중 작업과 자원 정리
→ 프로세스 종료
→ 컨테이너 종료 상태 기록
```

특정 시그널에 대한 반응만 직접 시험하려면 다음처럼 보낼 수도 있습니다.

```sh
docker compose kill -s TERM app
```

이 명령은 지정한 시그널을 직접 보내는 것이며 `docker compose stop`의 유예 시간 후 SIGKILL 절차와 목적이 다릅니다.

시작 스크립트가 다음처럼 서버를 단순 자식으로 실행하면 셸이 PID 1로 남습니다.

```sh
php-fpm -F
```

셸 구현과 실행 형태에 따라 시그널 전달이나 종료 상태 처리가 원하는 대로 되지 않을 수 있습니다. 시작 스크립트 마지막을 다음처럼 작성하면 셸 프로세스를 최종 서버로 교체합니다.

```sh
exec "$@"
```

Dockerfile의 exec form도 같은 이유로 중요합니다.

```dockerfile
CMD ["php-fpm", "-F"]
```

## 18. 한 가지 오류만 주입해 검사합니다

장애 훈련(fault test)은 정상 구성에 **한 가지 변경만 추가**한 뒤 예상 증상과 진단 경로가 실제로 맞는지 확인하는 방식으로 진행합니다.

여러 장애를 동시에 넣으면 어떤 증상이 어느 원인에서 나왔는지 학습하기 어렵습니다.

### 잘못된 DB 호스트

예상 경로:

```text
DB 자체 정상
→ app의 DB 이름 해석 실패
→ 애플리케이션 초기화 실패
→ app 종료 또는 준비 실패
→ 동적 요청 실패
```

확인 순서:

```text
app 로그
→ getent hosts <잘못된 이름>
→ Compose 서비스 이름과 네트워크
```

Nginx 설정은 먼저 바꾸지 않습니다.

### 잘못된 DB 비밀번호

예상 경로:

```text
db 이름 해석 성공
→ TCP 3306 연결 성공
→ MariaDB 인증 실패
→ Access denied
```

이 장애는 “DB에 연결할 수 없음”과 “DB에 도달했지만 인증할 수 없음”을 구분하는 연습에 적합합니다.

### 존재하지 않는 비밀값 파일

애플리케이션 시작 스크립트가 파일 존재와 읽기 권한을 먼저 검사한다면 DB 연결을 시도하기 전에 실패해야 합니다.

로그에는 다음 정도만 남깁니다.

```text
DB password file is not readable: /run/secrets/...
```

실제 비밀번호 값은 남기지 않습니다.

### 잘못된 FastCGI 포트

예상 경로:

```text
Nginx 프로세스 정상
→ /healthz 정상
→ 정적 파일 정상
→ PHP 요청에서 app:잘못된포트 연결 실패
→ 502
```

이 사례는 “Nginx가 살아 있음”과 “Nginx가 upstream에 연결할 수 있음”이 다른 상태임을 보여 줍니다.

### 고장 난 healthcheck

예를 들어 healthcheck에서 존재하지 않는 실행 파일을 사용하면 실제 서비스는 정상인데 컨테이너만 `unhealthy`가 될 수 있습니다.

```text
외부 사용자 요청 성공
healthcheck 실패
```

이때 먼저 상태 검사 명령을 컨테이너 안에서 직접 실행해 봅니다. 서비스 장애와 검사 도구 장애를 구분해야 합니다.

### DB 볼륨 삭제

```text
컨테이너 재생성 + 기존 볼륨 유지
→ 데이터 유지

볼륨 삭제 + 새 볼륨 생성
→ 빈 DB 초기화
```

빈 DB가 정상적으로 다시 초기화됐다고 해서 삭제된 사용자 데이터가 복구된 것은 아닙니다. 복구하려면 검증된 백업이나 별도의 데이터 복구 수단이 필요합니다.

## 19. 백업은 복원으로 검증합니다

백업 명령의 종료 상태가 0이고 파일이 만들어졌다는 사실만으로 실제 복구 가능성이 증명되지는 않습니다.

검증 절차는 최소한 다음 범위를 포함합니다.

```text
백업 파일 준비
→ 운영 DB와 분리된 빈 DB 준비
→ 백업 복원
→ 필요한 테이블 확인
→ 대표 데이터와 행 수 확인
→ 제약 조건/인덱스 확인
→ 애플리케이션 연결
→ 핵심 사용자 기능 검사
```

복원 테스트에서는 다음 정보도 기록합니다.

- 사용한 백업 파일과 생성 시점
- MariaDB 버전
- 스키마 버전
- 복원 명령과 실행 순서
- 필요한 비밀값과 권한
- 복원에 걸린 시간
- 검증한 기능

복구 시간도 운영 요구사항의 일부입니다. 수 시간 안에 복구해야 하는 서비스라면 실제 복원 시간이 그 목표를 만족하는지 훈련 과정에서 측정해야 합니다.

> 복원해 보지 않은 백업은 “파일이 존재한다”는 사실만 확인된 것이지, 복구 수단으로 검증된 것은 아닙니다.

## 20. 증상별 출발점

다음 표는 원인을 확정하는 표가 아니라 **첫 검사를 고르는 출발점**입니다.

| 증상 | 먼저 확인 | 다음 확인 |
|---|---|---|
| 호스트 이름 해석 실패 | 서비스 이름, 네트워크 | 컨테이너 상태, Compose 프로젝트 |
| `Connection refused` | 대상 프로세스, listen 포트 | bind 주소, 네트워크 |
| 연결 시간 초과 | 대상 상태, 네트워크 경로 | 과부하, 방화벽, 연결 제한 시간 |
| TLS 인증서 오류 | SAN, 신뢰 CA, 유효기간 | SNI/server name, 인증서 체인 |
| HTTP 404 | Nginx `location`, `root`, `try_files` | 파일 경로, 애플리케이션 라우트 |
| HTTP 403 | 파일과 디렉터리 권한 | 실행 사용자, 마운트, SELinux |
| HTTP 500 | 애플리케이션/PHP-FPM 로그 | DB, 코드, 설정 |
| HTTP 502 | PHP-FPM 실행, FastCGI 포트 | DNS, 네트워크, `SCRIPT_FILENAME` |
| DB `Access denied` | 사용자, 비밀번호, 호스트 권한 | 비밀값 출처, 초기 사용자 SQL |
| DB 없음 | 최초 DB 초기화 | DB 이름, 볼륨 |
| 테이블 없음 | 스키마 초기화/마이그레이션 | 대상 DB, 적용 이력 |
| 데이터가 초기화된 것처럼 보임 | 볼륨 이름과 마운트 | 프로젝트 이름, `down -v` 이력 |
| 재시작 반복 | 최초 종료 로그와 종료 코드 | 설정, OOM, restart 정책 |
| `unhealthy`인데 요청 성공 | healthcheck 명령 | 검사 도구, 경로, 권한, 검사 범위 |

서로 다른 계층의 오류가 같은 사용자 증상을 만들 수 있다는 점을 기억해야 합니다. 예를 들어 502는 잘못된 FastCGI 포트, PHP-FPM 미실행, 네트워크 단절 등 여러 원인으로 발생할 수 있습니다.

## 21. 장애 대응 기록을 남깁니다

장애를 해결한 뒤 “무엇을 바꿨는지”만 기록하면 같은 장애가 다시 발생했을 때 진단 과정을 재사용하기 어렵습니다. 다음 항목을 함께 기록합니다.

```text
증상
→ 관찰 시각
→ 마지막 정상 상태
→ 확인한 증거
→ 배제한 가설
→ 실제 원인
→ 수정 내용
→ 복구 확인 방법
```

예:

```text
증상: /api/notes 요청 502

증거:
- /healthz 200
- gateway에서 app 이름 해석 성공
- gateway → app:9000 연결 실패
- app 로그에 DB 인증 실패 후 종료 기록

원인:
- app의 DB 비밀번호 비밀값과 MariaDB 계정 비밀번호 불일치

수정:
- MariaDB 계정 비밀번호와 주입 비밀값을 같은 값으로 회전

복구 확인:
- app에서 SELECT 1 성공
- FPM ping 성공
- /api/notes 200
```

이 기록은 증상과 원인을 연결하고, 다음 장애에서 불필요한 검사를 줄이는 데 도움이 됩니다.

## 22. 피해야 할 습관

### “재시작하면 해결될 것입니다”

일시적인 오류라면 재시작으로 사라질 수 있지만 잘못된 설정, 잘못된 비밀값과 데이터 손상은 그대로입니다. 재시작 전에 가능한 범위에서 로그, 종료 코드와 현재 상태를 보존합니다.

### “로그 마지막 줄이 원인입니다”

마지막 줄은 앞선 실패 때문에 발생한 2차 오류일 수 있습니다. 타임스탬프를 따라 가장 먼저 발생한 의미 있는 오류를 찾습니다.

### “healthcheck가 실패했으니 서비스도 고장 났습니다”

검사 명령, 도구, 경로, 인증 정보 자체가 틀릴 수 있습니다. 같은 검사를 컨테이너 안에서 직접 실행하고 실제 사용자 요청과 비교합니다.

### “관리자 권한과 777로 바꾸면 원인을 찾기 쉽습니다”

권한을 무조건 넓히면 증상만 사라지고 원인이 가려질 수 있습니다. 실제 실행 UID/GID와 필요한 경로별 권한을 확인합니다.

### “포트가 열렸으니 서비스가 정상입니다”

TCP 연결 성공은 해당 프로토콜과 애플리케이션 기능의 성공을 보장하지 않습니다. TCP 다음에 TLS, HTTP, FastCGI, DB 인증 등 실제 프로토콜을 확인합니다.

### “`mariadb-admin ping`이 성공했으니 DB 로그인도 정상입니다”

`ping`은 서버 생존 확인입니다. 애플리케이션 인증과 쿼리는 실제 애플리케이션 계정으로 별도 확인합니다.

### “`curl -k`가 성공했으니 인증서도 정상입니다”

`-k`는 인증서 검증을 끕니다. 운영 TLS 검증에서는 신뢰 CA, SAN, 유효기간과 서버 이름을 실제로 검증해야 합니다.

### “백업 파일이 있으니 복구할 수 있습니다”

별도의 빈 환경에 복원하고 데이터와 사용자 기능까지 검사해야 합니다.

## 23. 확인 질문

1. 컨테이너가 `running`인데도 서비스가 준비되지 않을 수 있는 이유는 무엇입니까?
2. 사용자에게 502가 보일 때 Nginx만 수정하지 않고 실패 계층을 어떻게 좁히겠습니까?
3. DNS 성공, TCP 연결 성공, 애플리케이션 프로토콜 성공은 각각 무엇을 증명합니까?
4. PHP-FPM의 9000번 포트를 `curl`로 검사하면 안 되는 이유는 무엇입니까?
5. `mariadb-admin ping` 성공만으로 애플리케이션 DB 인증 성공을 판단할 수 없는 이유는 무엇입니까?
6. 외부 요청은 성공하지만 컨테이너가 `unhealthy`일 때 무엇부터 확인해야 합니까?
7. 데이터가 사라진 것처럼 보일 때 기존 볼륨을 먼저 삭제하면 안 되는 이유는 무엇입니까?
8. `docker compose stop`과 `docker compose kill -s TERM`은 종료 동작을 시험할 때 어떤 차이가 있습니까?
9. 재시작이나 컨테이너 삭제 전에 어떤 증거를 보존해야 합니까?
10. 백업이 실제 복구 수단임을 어떻게 검증할 수 있습니까?

## 정리

- 컨테이너 실행 상태와 서비스 정상 상태는 다릅니다.
- 컨테이너, 프로세스, 네트워크, 프로토콜, 사용자 기능, 데이터 상태를 계층별로 확인합니다.
- 생존 검사, 준비 검사와 사용자 기능 검사의 목적과 범위를 구분합니다.
- 마지막으로 성공한 단계 바로 다음을 검사해 실패 지점을 좁힙니다.
- DNS 성공, TCP 성공과 실제 프로토콜 성공은 서로 다른 증거입니다.
- PHP-FPM은 FastCGI, MariaDB는 DB 프로토콜처럼 서비스가 실제 사용하는 프로토콜로 검사합니다.
- `mariadb-admin ping`은 서버 생존 검사이며 애플리케이션 사용자 인증 검사가 아닙니다.
- 가장 먼저 발생한 오류와 뒤따른 2차 오류를 구분합니다.
- 한 번에 한 가지 원인만 수정하고 동일한 검사로 복구를 확인합니다.
- restart 정책은 잘못된 설정을 수정하지 않습니다.
- 일반적인 정상 종료 경로는 `docker compose stop`으로 확인하고 PID 1과 `exec`의 역할을 이해합니다.
- 데이터가 사라진 것처럼 보여도 기존 볼륨을 삭제하기 전에 실제 마운트와 프로젝트 이름을 확인합니다.
- 백업은 별도의 빈 환경에 복원해 검증합니다.
- 장애 해결 과정에서 증상, 증거, 원인, 수정과 복구 검사를 함께 기록합니다.
