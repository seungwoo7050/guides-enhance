# 반복 실행해도 안전한 애플리케이션 초기화

컨테이너 프로세스가 시작되었다고 해서 애플리케이션이 곧바로 요청을 처리할 준비가 된 것은 아닙니다. 애플리케이션은 먼저 필수 설정과 비밀값을 확인하고, 데이터베이스에 연결할 수 있는지 검사하고, 필요한 스키마와 최초 데이터를 준비한 뒤 최종 서버 프로세스를 실행해야 할 수 있습니다.

이 장에서는 이 시작 절차를 여러 번 실행하거나 두 인스턴스가 동시에 실행해도 결과가 중복되거나 깨지지 않도록 설계하는 방법을 다룹니다. 같은 입력 상태에 같은 초기화를 여러 번 적용해도 목표 상태가 더 이상 변하지 않는 성질을 **멱등성(idempotency)** 이라고 합니다.

```text
초기 상태 S
초기화(S) = 목표 상태 D
초기화(D) = D
```

여기서 중요한 점은 "스크립트를 한 번만 실행한다"가 아니라 **스크립트가 다시 실행되어도 안전하다**는 것입니다. 컨테이너 재시작, 재생성, 배포 중 실패, 여러 인스턴스의 동시 시작은 모두 실제로 발생할 수 있습니다.

## 1. 코드, 설정, 비밀값, 실행 중 데이터를 나눕니다

웹 애플리케이션이 사용하는 항목은 수명이 서로 다르므로 보관 위치도 구분합니다.

| 종류 | 예 | 일반적인 보관 위치 | 기대 수명 |
|---|---|---|---|
| 코드 | PHP 파일, 정적 파일, 의존성 | 이미지 | 이미지 버전과 함께 변경 |
| 설정 | DB 호스트, 공개 URL, 로그 수준 | 환경변수 또는 설정 파일 | 배포 환경별로 변경 |
| 비밀값 | DB 비밀번호, 서명 키 | 실행 시 주입하는 비밀값 파일 | 코드와 독립적으로 교체 |
| 실행 중 데이터 | 테이블, 업로드, 세션 | 볼륨 또는 외부 저장소 | 컨테이너보다 오래 유지 |

코드를 컨테이너 시작 때마다 외부에서 다시 내려받으면 같은 이미지라도 실행 시점에 따라 내용이 달라질 수 있습니다. 그러면 어떤 버전이 실행 중인지 이미지 태그만으로 확인하기 어렵습니다.

반대로 환경마다 달라지는 비밀번호를 이미지에 넣으면 이미지 레이어와 빌드 기록에 비밀값이 남을 수 있고, 비밀번호를 바꿀 때마다 이미지를 다시 만들어야 합니다.

따라서 기준은 다음과 같습니다.

- **빌드 시점에 확정할 수 있고 배포 결과의 일부인 것**은 이미지에 넣습니다.
- **실행 환경마다 달라지는 것**은 시작 시 주입합니다.
- **컨테이너가 교체되어도 남아야 하는 것**은 컨테이너의 쓰기 계층 밖에 둡니다.

## 2. 빌드할 때 할 일과 시작할 때 할 일

### 빌드할 때

- 의존성을 설치합니다.
- 소스와 기본 설정을 복사합니다.
- 실행 사용자를 준비합니다.
- 변경되지 않는 파일의 소유권과 권한을 정합니다.
- 가능하면 애플리케이션 코드를 읽기 전용으로 사용할 수 있게 만듭니다.

### 컨테이너를 시작할 때

- 필수 환경변수를 검사합니다.
- 비밀값 파일의 존재 여부와 권한을 확인합니다.
- 의존 서비스가 준비될 때까지 제한된 범위에서 재시도합니다.
- 현재 데이터베이스 상태를 확인하고 필요한 변경만 적용합니다.
- 최초 데이터가 아직 적용되지 않았다면 한 번만 적용합니다.
- 모든 준비가 끝난 뒤 최종 서버를 `exec`로 실행합니다.

시작 스크립트는 컨테이너가 시작될 때마다 실행됩니다. "최초 설치 때 한 번만 실행된다"고 가정하면 재시작이나 컨테이너 교체 뒤에 중복 데이터, 권한 오류 또는 시작 실패가 발생할 수 있습니다.

## 3. 시작 절차를 단계별로 나눕니다

이 가이드의 애플리케이션은 다음 순서로 시작한다고 가정합니다.

```text
필수 설정 검사
    ↓
비밀값 파일 검사와 읽기
    ↓
DB 연결 재시도
    ↓
기본 테이블 준비
    ↓
최초 데이터 처리
    ↓
PHP-FPM으로 exec
```

각 단계에는 명확한 성공 조건이 있어야 합니다. 어떤 단계가 실패했다면 다음 단계로 넘어가지 않고 비정상 종료해야 합니다.

예를 들어 DB 연결에 실패했는데도 PHP-FPM을 실행하면 컨테이너 프로세스 자체는 살아 있을 수 있습니다. 하지만 실제 요청은 계속 실패하므로 "프로세스가 실행 중"이라는 상태와 "서비스가 준비됨"이라는 상태가 어긋납니다.

초기화 단계에서는 **빠르게 실패(fail fast)** 하고, 실패 원인을 로그에 남기되 비밀값 자체는 출력하지 않는 것이 좋습니다.

## 4. POSIX 셸로 시작 스크립트 작성하기

컨테이너의 `/bin/sh`가 Bash라고 가정하면 안 됩니다. Debian 계열에서는 `dash`, Alpine에서는 BusyBox `ash`가 `/bin/sh`로 사용될 수 있습니다. 셰뱅이 `/bin/sh`라면 POSIX 셸 문법 안에서 작성하는 것이 이식성이 좋습니다.

```sh
#!/bin/sh
set -eu
```

- `set -e`: 처리되지 않은 명령 실패가 스크립트 종료로 이어지게 합니다.
- `set -u`: 설정되지 않은 변수를 참조하면 오류로 처리합니다.

`set -e`는 모든 문맥에서 단순히 "0이 아니면 즉시 종료"하는 기능은 아닙니다. `if`, `while`, `&&`, `||` 등 명령의 성공 여부를 검사하는 문맥에서는 동작이 달라질 수 있습니다. 따라서 초기화의 핵심 단계는 종료 상태를 명시적으로 검사하는 편이 읽기 쉽고 안전합니다.

변수 확장은 특별한 이유가 없으면 큰따옴표로 감쌉니다.

```sh
cat "$file_path"
exec "$@"
```

`"$@"`는 전달받은 각 인자를 원래의 인자 경계대로 유지합니다. 반면 `"$*"`는 모든 위치 인자를 하나의 문자열로 합치므로 최종 명령 전달에는 적합하지 않습니다.

## 5. 필수 설정을 시작 직후 검사합니다

필수 환경변수는 실제 작업을 시작하기 전에 확인합니다.

```sh
: "${DB_HOST:?DB_HOST가 필요합니다.}"
: "${DB_NAME:?DB_NAME이 필요합니다.}"
: "${DB_USER:?DB_USER가 필요합니다.}"
: "${DB_PASSWORD_FILE:?DB_PASSWORD_FILE이 필요합니다.}"
: "${APP_PORT:?APP_PORT가 필요합니다.}"
```

`${VAR:?message}`는 변수가 설정되지 않았거나 빈 문자열이면 오류를 발생시킵니다.

환경변수 값은 모두 문자열이므로 "값이 존재한다"는 검사만으로는 충분하지 않습니다. 실제 사용 방식에 맞는 형식과 범위를 함께 확인합니다.

예를 들어 TCP 포트는 숫자인지 확인한 뒤 `1..65535` 범위인지 확인할 수 있습니다.

```sh
case "$APP_PORT" in
    ''|*[!0-9]*)
        echo "APP_PORT는 1~65535의 정수여야 합니다." >&2
        exit 1
        ;;
esac

if [ "$APP_PORT" -lt 1 ] || [ "$APP_PORT" -gt 65535 ]; then
    echo "APP_PORT는 1~65535 범위여야 합니다." >&2
    exit 1
fi
```

SQL 식별자로 직접 사용할 데이터베이스 이름처럼 별도의 문법이 있는 값은 허용 문자 집합을 좁히는 것이 안전합니다.

```sh
case "$DB_NAME" in
    ''|*[!A-Za-z0-9_]*)
        echo "DB_NAME에는 영문자, 숫자와 밑줄만 사용할 수 있습니다." >&2
        exit 1
        ;;
esac
```

입력 검사는 공격 방지뿐 아니라 오타와 잘못된 배포 설정을 실행 초기에 발견하는 수단입니다.

## 6. 비밀값 파일을 읽습니다

비밀번호를 Dockerfile, 소스 코드 또는 Compose 파일의 평문 값으로 고정하지 않고 실행 시 파일로 주입할 수 있습니다.

```yaml
services:
  app:
    secrets:
      - db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

시작 스크립트는 경로가 실제 일반 파일이고 읽을 수 있는지 확인한 뒤 값을 읽습니다.

```sh
if [ ! -f "$DB_PASSWORD_FILE" ] || [ ! -r "$DB_PASSWORD_FILE" ]; then
    echo "DB 비밀번호 파일을 읽을 수 없습니다." >&2
    exit 1
fi

DB_PASSWORD=$(cat "$DB_PASSWORD_FILE")

if [ -z "$DB_PASSWORD" ]; then
    echo "DB 비밀번호가 비어 있습니다." >&2
    exit 1
fi
```

셸의 명령 치환 `$(...)`은 결과 끝의 개행 문자를 제거합니다. 이 예시는 **비밀번호를 한 줄 텍스트로 관리한다는 규칙**을 전제로 합니다. 임의의 바이너리 값이나 개행을 포함할 수 있는 비밀값이라면 셸 변수 대신 애플리케이션이 파일을 직접 읽게 하는 편이 낫습니다.

비밀값을 읽었다고 해서 다음과 같이 로그에 출력해서는 안 됩니다.

```sh
# 하지 않습니다.
echo "DB_PASSWORD=$DB_PASSWORD"
```

PHP-FPM 워커가 원본 비밀 파일을 읽을 권한이 없고 애플리케이션 코드가 실행 중에 파일을 읽어야 한다면, 시작 단계에서 `/run` 같은 휘발성 경로에 제한된 권한으로 복사할 수 있습니다.

```text
소유자 root
그룹 www-data
권한 0440
```

이때 복사본도 비밀값이므로 로그, 백업 또는 이미지 레이어에 포함되지 않게 해야 합니다.

## 7. 데이터베이스 연결은 제한된 범위에서 재시도합니다

Compose의 `depends_on`은 의존 서비스의 시작 순서를 지정할 수 있습니다. 짧은 문법은 DB 컨테이너가 시작되었다는 것만 보장하며, `condition: service_healthy`를 사용하면 시작 시점에 DB의 healthcheck가 성공할 때까지 기다릴 수 있습니다.

```yaml
services:
  app:
    depends_on:
      db:
        condition: service_healthy
```

하지만 이것만으로 애플리케이션의 재시도가 불필요해지는 것은 아닙니다. 애플리케이션이 실행되는 동안 DB가 재시작되거나 네트워크 연결이 일시적으로 실패할 수 있고, healthcheck가 검사하는 조건과 실제 애플리케이션 인증 조건도 다를 수 있습니다.

시작 단계에서는 다음과 같이 제한된 횟수만 연결을 시도할 수 있습니다.

```php
<?php

$pdo = null;
$lastError = null;

for ($attempt = 1; $attempt <= $maxAttempts; $attempt++) {
    try {
        $pdo = new PDO(
            $dsn,
            $user,
            $password,
            [
                PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
                PDO::ATTR_TIMEOUT => 3,
            ]
        );
        break;
    } catch (PDOException $error) {
        $lastError = $error;

        if ($attempt < $maxAttempts) {
            usleep($delayMs * 1000);
        }
    }
}

if (!$pdo instanceof PDO) {
    throw new RuntimeException(
        '데이터베이스 연결 제한 횟수를 초과했습니다.',
        0,
        $lastError
    );
}
```

재시도 정책에는 최소한 다음 요소가 있어야 합니다.

- 한 번의 연결 시도에 적용할 제한 시간
- 최대 시도 횟수 또는 전체 제한 시간
- 시도 사이의 대기 시간
- 최종 실패를 식별할 수 있는 오류 기록

`PDO::ATTR_TIMEOUT`의 세부 동작은 PDO 드라이버에 영향을 받을 수 있으므로 실제 사용하는 드라이버에서 의미를 확인합니다.

무한 재시도는 잘못된 DB 호스트, 잘못된 비밀번호, 존재하지 않는 데이터베이스처럼 기다려도 해결되지 않는 설정 오류를 숨깁니다. 운영 코드에서는 가능하면 **일시적인 연결 실패**와 **인증·설정 실패**를 구분하여 재시도 여부를 결정합니다.

## 8. 테이블 생성과 최초 데이터 입력은 별개의 문제입니다

다음 SQL은 테이블이 이미 존재할 때 `CREATE TABLE` 자체가 실패하지 않게 합니다.

```sql
CREATE TABLE IF NOT EXISTS notes (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    body VARCHAR(500) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
```

하지만 `IF NOT EXISTS`는 **기존 테이블의 구조가 원하는 구조와 같은지 검증하지 않습니다.** 예를 들어 기존 `notes` 테이블에 `created_at` 컬럼이 없어도 위 문장은 "이미 테이블이 있다"는 이유로 구조를 수정하지 않습니다.

따라서 이 방식은 최초 스키마를 만드는 작은 예제에는 사용할 수 있지만, 이미 배포된 스키마를 발전시키는 문제는 마이그레이션 도구가 해결해야 합니다.

테이블을 재생성하지 않는 것과 최초 데이터를 중복 삽입하지 않는 것도 별개의 문제입니다.

```sql
INSERT INTO notes (body) VALUES ('seed note');
```

이 명령을 시작할 때마다 실행하면 같은 행이 계속 추가됩니다. 최초 데이터는 별도의 고유한 완료 마커나 데이터 자체의 고유 키를 이용해 한 번만 적용되게 해야 합니다.

## 9. 완료 마커 테이블을 명확히 정의합니다

최초 데이터의 적용 여부를 기록할 작은 테이블을 사용할 수 있습니다.

```sql
CREATE TABLE IF NOT EXISTS app_meta (
    meta_key VARCHAR(100) NOT NULL PRIMARY KEY,
    meta_value VARCHAR(255) NOT NULL,
    applied_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB;
```

`meta_key`가 기본키이므로 같은 마커를 두 번 삽입할 수 없습니다.

```text
seed_v1  → 최초 데이터 버전 1이 적용됨
seed_v2  → 이후 추가된 최초 데이터 세트가 적용됨
```

마커 이름에는 무엇이 완료되었는지 구분할 수 있는 버전을 포함하는 편이 좋습니다. 단순히 `seed_done` 하나만 두면 나중에 새로운 초기 데이터가 추가되었을 때 기존 환경과 새 환경을 구분하기 어렵습니다.

## 10. 마커와 최초 데이터는 같은 트랜잭션에서 처리합니다

목표는 다음 두 결과 중 하나만 남게 하는 것입니다.

```text
마커 없음 + 데이터 없음
또는
마커 있음 + 데이터 있음
```

`마커 있음 + 데이터 없음` 상태가 남으면 다음 시작에서 이미 작업이 끝난 것으로 잘못 판단할 수 있습니다.

따라서 마커 획득과 최초 데이터 입력을 같은 트랜잭션에서 처리합니다. 또한 단순히 `INSERT IGNORE`로 모든 오류를 무시하기보다 **중복 키 오류만 "이미 다른 실행이 처리했다"고 판단하고 다른 오류는 그대로 실패**시키는 것이 안전합니다.

```php
<?php

$pdo->beginTransaction();

try {
    $shouldSeed = false;

    try {
        $marker = $pdo->prepare(
            "INSERT INTO app_meta (meta_key, meta_value)
             VALUES ('seed_v1', 'done')"
        );
        $marker->execute();
        $shouldSeed = true;
    } catch (PDOException $error) {
        $driverCode = $error->errorInfo[1] ?? null;

        // MariaDB/MySQL의 duplicate key 오류 번호는 1062입니다.
        if ($error->getCode() === '23000' && (int) $driverCode === 1062) {
            $shouldSeed = false;
        } else {
            throw $error;
        }
    }

    if ($shouldSeed) {
        $seed = $pdo->prepare(
            'INSERT INTO notes (body) VALUES (:body)'
        );
        $seed->execute(['body' => 'seed note']);
    }

    $pdo->commit();
} catch (Throwable $error) {
    if ($pdo->inTransaction()) {
        $pdo->rollBack();
    }
    throw $error;
}
```

첫 번째 인스턴스가 `seed_v1` 마커를 삽입하면 같은 기본키를 삽입하려는 두 번째 인스턴스는 InnoDB의 동시성 제어에 따라 첫 번째 트랜잭션의 결과를 기다리게 될 수 있습니다.

- 첫 번째 트랜잭션이 커밋되면 두 번째 삽입은 중복 키가 됩니다.
- 첫 번째 트랜잭션이 롤백되면 마커도 사라지므로 다른 실행이 다시 시도할 수 있습니다.

중요한 것은 **"먼저 SELECT하고 없으면 INSERT"** 하는 두 단계 검사만으로 작업 주체를 정하지 않는 것입니다.

```text
인스턴스 A: SELECT → 없음
인스턴스 B: SELECT → 없음
인스턴스 A: INSERT
인스턴스 B: INSERT
```

고유 제약이 없다면 두 인스턴스가 모두 작업할 수 있습니다. 고유 키와 원자적인 INSERT 결과를 이용하면 데이터베이스가 경쟁을 조정하게 할 수 있습니다.

> 이 예제는 MariaDB/MySQL의 중복 키 오류 번호를 사용합니다. 다른 DBMS로 옮기면 오류 코드와 동시성 동작을 해당 DBMS에 맞게 확인해야 합니다.

## 11. DDL과 최초 데이터 트랜잭션을 구분합니다

MariaDB에서는 `CREATE TABLE`, `ALTER TABLE` 같은 많은 DDL 문장이 현재 트랜잭션을 암시적으로 커밋할 수 있습니다. 따라서 다음처럼 "테이블 생성부터 seed까지 하나의 트랜잭션으로 완전히 되돌릴 수 있다"고 가정하면 안 됩니다.

```text
테이블 준비(DDL)
    ↓
seed 트랜잭션 시작
    ↓
마커 획득
    ↓
최초 데이터 INSERT
    ↓
COMMIT
```

테이블 준비는 자체적으로 재실행 가능해야 하고, 최초 데이터와 완료 마커처럼 원자성이 필요한 DML 작업은 별도의 트랜잭션에서 처리합니다.

또한 트랜잭션으로 보호하려는 테이블은 실제로 트랜잭션을 지원하는 저장 엔진을 사용해야 합니다. 이 장의 예제에서는 `ENGINE=InnoDB`를 명시합니다.

## 12. 부분 실패 뒤 다시 실행할 수 있어야 합니다

다음 상황을 생각해 봅니다.

```text
notes 테이블 생성 성공
→ app_meta 테이블 생성 성공
→ seed 트랜잭션 시작
→ 마커 삽입 성공
→ 최초 데이터 입력 실패
→ ROLLBACK
→ 컨테이너 종료
→ 다시 시작
```

마커와 최초 데이터가 같은 트랜잭션에 있다면 입력 실패 시 둘 다 롤백됩니다. 다음 시작에서는 `seed_v1` 마커가 없으므로 다시 시도할 수 있습니다.

반대로 마커를 먼저 별도로 커밋했다면 다음과 같은 잘못된 상태가 남을 수 있습니다.

```text
seed_v1 마커 있음
seed note 없음
```

부분 실패를 검토할 때는 다음 질문을 순서대로 확인합니다.

- 어느 변경이 트랜잭션 안에 있는가?
- 완료를 나타내는 값은 언제 커밋되는가?
- 실패 뒤 남아도 되는 파일이나 행은 무엇인가?
- 두 인스턴스가 동시에 시작하면 누가 작업 주체가 되는가?
- 외부 API 호출처럼 DB 트랜잭션으로 롤백할 수 없는 작업이 있는가?

마지막 항목이 중요합니다. 이메일 발송, 결제 요청, 외부 API 호출 같은 작업은 DB 트랜잭션을 롤백한다고 취소되지 않습니다. 이런 작업까지 포함하는 초기화에는 별도의 멱등 키, 작업 큐 또는 보상 전략이 필요하며 이는 이 장의 DB 초기화 범위를 넘어섭니다.

## 13. 파일 권한은 필요한 경로에만 줍니다

코드와 기본 설정은 가능한 한 읽기 전용으로 유지하고, 워커가 실제로 쓰는 디렉터리만 쓰기 가능하게 합니다.

```text
/var/www/html     읽기 전용 코드와 정적 파일
/opt/app          관리 스크립트
/run/app-secrets  컨테이너가 살아 있는 동안만 쓰는 비밀값 복사본
/app/var          애플리케이션이 실제로 쓰는 데이터
```

시작할 때마다 전체 코드 디렉터리에 다음과 같은 명령을 실행하는 것은 피합니다.

```sh
chown -R www-data:www-data /var/www/html
```

파일 수가 많으면 시작 시간이 길어지고, 원래 불변이어야 할 코드까지 런타임 프로세스가 수정할 수 있게 만들 수 있습니다. 빌드 시 정할 수 있는 소유권은 빌드 때 정하고, 시작 시에는 `/run`이나 쓰기 볼륨처럼 실제로 준비가 필요한 경로만 처리합니다.

## 14. 마지막에는 최종 서버를 `exec`합니다

초기화 스크립트는 준비 작업이 모두 성공한 뒤에만 최종 서버를 실행합니다.

```sh
php /opt/app/bootstrap.php
exec "$@"
```

Dockerfile은 최종 실행 명령을 제공합니다.

```dockerfile
ENTRYPOINT ["/usr/local/bin/app-entrypoint.sh"]
CMD ["php-fpm", "-F"]
```

`exec "$@"`는 새 자식 프로세스를 하나 더 만드는 것이 아니라 현재 셸 프로세스를 PHP-FPM으로 교체합니다.

```text
exec 전
PID 1  app-entrypoint.sh

exec 후
PID 1  php-fpm -F
```

이렇게 하면 PHP-FPM이 Docker가 보내는 종료 신호를 직접 받고, PHP-FPM의 종료 상태가 컨테이너 종료 상태가 됩니다.

초기화가 실패했다면 `exec`까지 도달하지 않아야 합니다. 준비되지 않은 애플리케이션을 단순히 "실행 중"인 상태로 남기는 것보다 컨테이너를 실패시키고 원인을 관찰 가능하게 만드는 편이 낫습니다.

## 15. 상태 검사는 상태를 바꾸지 않습니다

초기화와 상태 검사는 목적이 다릅니다.

### 초기화

- 테이블을 준비합니다.
- 최초 데이터를 넣습니다.
- 런타임 디렉터리를 만듭니다.
- 필요한 비밀값 복사본을 준비합니다.

### 상태 검사

- PHP-FPM이 응답하는지 확인합니다.
- 작은 읽기 요청을 보냅니다.
- 데이터베이스에서 `SELECT 1` 같은 읽기 전용 쿼리를 실행합니다.

상태 검사는 짧은 주기로 반복될 수 있습니다. 여기에서 `CREATE TABLE`, `INSERT`, 데이터 수정 같은 작업을 수행하면 다음 문제가 생깁니다.

- 장애를 검사하는 과정이 오히려 상태를 변경합니다.
- 검사 주기에 비례해 쓰기 부하가 발생합니다.
- 실패한 초기화를 healthcheck가 우연히 보완해 장애 원인을 숨길 수 있습니다.
- 여러 상태 검사 실행이 서로 경쟁할 수 있습니다.

따라서 **초기화는 상태를 목표 상태로 바꾸는 작업**, **상태 검사는 현재 상태를 관찰하는 작업**으로 분리합니다.

## 16. 실제 스키마 변경 도구가 추가로 해결해야 하는 문제

이 장의 `CREATE TABLE IF NOT EXISTS` 예제는 작은 애플리케이션의 최초 부트스트랩을 설명하기 위한 것입니다. 서비스가 발전해 이미 데이터가 들어 있는 스키마를 변경해야 한다면 별도의 마이그레이션 체계가 필요합니다.

마이그레이션 도구는 최소한 다음 문제를 다뤄야 합니다.

- 각 변경의 고유 버전 또는 식별자
- 변경 파일의 적용 순서
- 동시에 여러 인스턴스가 마이그레이션하지 않도록 하는 잠금
- 어떤 변경이 적용되었는지 기록하는 이력 테이블
- 각 DDL/DML이 트랜잭션 가능한지 여부
- 오래 걸리는 인덱스 생성이나 컬럼 변경의 서비스 영향
- 실패 시 롤백할지 수정된 새 마이그레이션으로 전진할지에 대한 정책

예를 들어 다음 문장은 테이블이 없을 때 만드는 데는 유용하지만 기존 스키마의 진화를 표현하지 못합니다.

```sql
CREATE TABLE IF NOT EXISTS notes (...);
```

이미 `notes`가 존재한다면 컬럼 추가, 타입 변경, 인덱스 변경 또는 데이터 변환은 별도의 명시적인 변경 단계가 필요합니다.

## 17. 자주 생기는 오해

### "멱등성이면 명령을 여러 번 실행해도 아무 일도 일어나지 않습니다"

멱등성은 두 번째 실행이 반드시 아무 작업도 하지 않는다는 뜻이 아닙니다. 필요한 검사를 다시 수행할 수 있지만 **관찰 가능한 최종 상태가 목표 상태를 벗어나지 않아야 한다**는 뜻입니다.

### "시작 스크립트는 최초 설치 때만 실행됩니다"

아닙니다. 컨테이너가 시작될 때마다 실행됩니다. 기존 데이터와 기존 런타임 상태가 있는 경우에도 안전해야 합니다.

### "`depends_on`이 있으니 애플리케이션 재시도는 필요 없습니다"

짧은 `depends_on`은 시작 순서를 제공할 뿐 준비 완료를 의미하지 않습니다. `condition: service_healthy`를 사용해도 시작 시점의 준비 상태를 돕는 기능이며, 실행 중 발생하는 DB 재시작이나 일시적 연결 실패를 애플리케이션 대신 처리하지 않습니다.

### "`IF NOT EXISTS`를 붙이면 스키마도 원하는 상태가 됩니다"

아닙니다. 이미 객체가 존재하면 생성 오류를 피할 뿐 기존 객체의 컬럼, 인덱스 또는 제약 조건이 원하는 정의와 같은지 보장하지 않습니다.

### "`IF NOT EXISTS`를 붙이면 최초 데이터도 중복되지 않습니다"

테이블 생성과 행 삽입은 별개의 작업입니다. 최초 데이터는 고유 키, 완료 마커 또는 자연스러운 유일성을 이용해 별도로 중복을 방지해야 합니다.

### "먼저 SELECT해서 없으면 INSERT하면 동시 실행에도 안전합니다"

검사와 삽입 사이에 다른 인스턴스가 같은 판단을 할 수 있습니다. DB의 UNIQUE/PRIMARY KEY 같은 제약과 원자적인 쓰기 결과를 이용해야 합니다.

### "`INSERT IGNORE`는 중복 키만 무시합니다"

아닙니다. MariaDB의 `IGNORE`는 중복 키 외의 여러 오류를 경고로 낮출 수 있습니다. 특정 중복 상황만 정상 흐름으로 취급하려면 그 오류를 구체적으로 식별하고 나머지는 실패시키는 편이 안전합니다.

### "관리자 권한으로 실행해도 컨테이너 안이므로 괜찮습니다"

컨테이너가 관리자 권한의 위험을 없애지는 않습니다. root 권한이 필요한 준비 작업이 있다면 필요한 범위에서만 사용하고, 최종 서비스 프로세스는 가능한 한 비특권 사용자로 실행합니다.

### "비밀값 파일이면 값이 어디에도 노출되지 않습니다"

애플리케이션이 사용하려면 파일이나 프로세스 메모리 어딘가에는 값이 존재합니다. 파일 권한, 로그, 예외 메시지, 진단 출력, 코어 덤프와 백업 범위를 함께 관리해야 합니다.

## 18. 확인 질문

1. 이미지에 넣을 파일과 시작할 때 주입할 값을 어떤 수명 기준으로 구분할 수 있습니까?
2. DB 연결 재시도가 무한하면 어떤 종류의 설정 오류가 숨겨질 수 있습니까?
3. `CREATE TABLE IF NOT EXISTS`가 기존 테이블을 원하는 스키마로 변경해 주지 않는 이유는 무엇입니까?
4. 완료 마커와 최초 데이터 입력을 같은 트랜잭션에 둬야 하는 이유는 무엇입니까?
5. 두 애플리케이션 인스턴스가 동시에 시작해도 최초 데이터가 한 번만 들어가게 하려면 DB에 어떤 제약이 필요합니까?
6. `SELECT → 없으면 INSERT`만으로 동시 실행을 제어하기 어려운 이유는 무엇입니까?
7. 초기화가 실패했을 때 PHP-FPM을 시작하지 않아야 하는 이유는 무엇입니까?
8. 상태 검사에서 데이터 변경 작업을 하면 어떤 문제가 생깁니까?
9. `exec "$@"`를 생략하고 셸이 부모 프로세스로 남으면 시그널과 종료 상태 전달 구조가 어떻게 달라집니까?
10. `CREATE TABLE IF NOT EXISTS` 수준의 부트스트랩에서 버전 기반 마이그레이션으로 넘어가야 하는 시점은 언제입니까?

## 정리

- 코드, 설정, 비밀값, 실행 중 데이터는 서로 다른 수명으로 관리합니다.
- 시작 직후 필수 설정과 비밀값 파일을 검사하고 잘못된 설정은 빠르게 실패시킵니다.
- 의존 서비스 연결은 제한 시간과 최대 횟수를 둔 재시도로 처리합니다.
- `depends_on`과 healthcheck는 애플리케이션의 연결 오류 처리 자체를 대신하지 않습니다.
- `CREATE TABLE IF NOT EXISTS`는 최초 생성에는 유용하지만 기존 스키마의 동일성을 보장하지 않습니다.
- 테이블 생성과 최초 데이터 중복 방지는 서로 다른 문제로 다룹니다.
- 동시 시작은 SELECT 선검사보다 DB의 고유 제약과 원자적인 쓰기 결과로 조정합니다.
- 완료 마커와 최초 데이터는 함께 커밋되거나 함께 롤백되어야 합니다.
- DDL과 트랜잭션으로 보호할 DML의 경계를 구분합니다.
- 실패 뒤 다시 실행할 수 있는 상태만 남깁니다.
- 초기화가 끝난 뒤 `exec`로 최종 서버를 PID 1로 실행합니다.
- 상태 검사는 읽기 전용으로 유지합니다.
- 서비스가 발전하면 명시적인 버전, 잠금과 이력을 갖는 마이그레이션 체계를 사용합니다.
