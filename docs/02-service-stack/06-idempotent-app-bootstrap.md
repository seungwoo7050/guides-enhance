# 반복 실행해도 안전한 애플리케이션 초기화

컨테이너를 시작했다고 해서 애플리케이션이 바로 요청을 처리할 수 있는 것은 아닙니다. 데이터베이스 연결을 확인하고, 필요한 테이블을 만들고, 최초 데이터가 없다면 추가한 뒤에야 최종 서버 프로세스를 실행할 수 있습니다.

이 장에서는 같은 초기화 코드를 여러 번 실행해도 결과가 중복되거나 깨지지 않게 만드는 방법을 다룹니다. 이를 **멱등성(idempotency)** 이라고 합니다.

```text
초기 상태 S
초기화(S) = 목표 상태 D
초기화(D) = D
```

## 1. 코드, 설정, 비밀값, 실행 중 데이터를 나눕니다

웹 애플리케이션이 사용하는 항목은 성격에 따라 보관 위치가 달라집니다.

| 종류 | 예 | 일반적인 보관 위치 |
|---|---|---|
| 코드 | PHP 파일, 정적 파일, 의존성 | 이미지 |
| 설정 | DB 호스트, 공개 URL, 로그 수준 | 환경변수 또는 설정 파일 |
| 비밀값 | DB 비밀번호, 서명 키 | 실행 시 주입하는 비밀값 파일 |
| 실행 중 데이터 | 테이블, 업로드, 세션 | 볼륨 또는 외부 저장소 |

코드를 시작할 때마다 외부에서 다시 내려받으면 어느 버전이 실행되는지 확인하기 어렵습니다. 반대로 환경마다 달라지는 비밀번호를 이미지에 넣으면 이미지 기록에 값이 남습니다. 빌드할 때 확정할 수 있는 항목과 시작할 때만 알 수 있는 항목을 구분해야 합니다.

## 2. 빌드할 때 할 일과 시작할 때 할 일

### 빌드할 때

- 의존성을 설치합니다.
- 소스와 기본 설정을 복사합니다.
- 실행 사용자를 준비합니다.
- 변경되지 않는 파일의 권한을 정합니다.

### 컨테이너를 시작할 때

- 필수 환경변수를 검사합니다.
- 비밀값 파일을 읽을 수 있는지 확인합니다.
- 의존 서비스가 준비될 때까지 제한된 횟수로 재시도합니다.
- 현재 데이터베이스 상태를 확인하고 필요한 변경만 적용합니다.
- 모든 준비가 끝난 뒤 최종 서버를 `exec`로 실행합니다.

시작 스크립트는 컨테이너가 시작될 때마다 실행됩니다. 최초 설치만 가정하면 재시작이나 컨테이너 교체에서 문제가 생깁니다.

## 3. 시작 절차

이 가이드의 애플리케이션은 다음 순서로 시작합니다.

```text
필수 설정 검사
    ↓
비밀값 파일 검사와 읽기
    ↓
DB 연결 재시도
    ↓
테이블 준비
    ↓
최초 데이터 처리
    ↓
PHP-FPM으로 exec
```

각 단계는 성공과 실패를 종료 상태로 구분해야 합니다. 실패했는데도 다음 단계로 넘어가면 컨테이너는 실행 중처럼 보이지만 실제 요청은 처리하지 못할 수 있습니다.

## 4. POSIX 셸로 시작 스크립트 작성하기

컨테이너의 `/bin/sh`는 Bash가 아닐 수 있습니다. Debian은 보통 `dash`, Alpine은 BusyBox `ash`를 사용합니다. 셰뱅이 `/bin/sh`라면 Bash 전용 문법을 피합니다.

```sh
#!/bin/sh
set -eu
```

- `set -e`는 처리하지 않은 명령 실패에서 스크립트를 종료합니다.
- `set -u`는 설정되지 않은 변수를 참조하면 종료합니다.

중요한 실패는 `set -e`에만 맡기지 말고 직접 검사합니다. 조건문이나 파이프 안에서는 동작이 예상과 다를 수 있습니다.

변수는 특별한 이유가 없으면 큰따옴표로 감쌉니다.

```sh
cat "$file_path"
exec "$@"
```

`"$@"`는 전달받은 인자를 각각 유지합니다. `"$*"`는 모든 인자를 하나의 문자열로 합치므로 용도가 다릅니다.

## 5. 필수 설정을 시작 직후 검사합니다

```sh
: "${DB_HOST:?DB_HOST가 필요합니다.}"
: "${DB_NAME:?DB_NAME이 필요합니다.}"
: "${DB_USER:?DB_USER가 필요합니다.}"
: "${DB_PASSWORD_FILE:?DB_PASSWORD_FILE이 필요합니다.}"
```

환경변수는 모두 문자열이며 오타나 잘못된 값이 들어올 수 있습니다. 값이 있다는 사실만 확인하지 말고 실제 사용 방식에 맞게 검사합니다.

예를 들어 포트는 숫자 형식과 범위를 함께 확인하고, SQL 식별자로 사용할 DB 이름은 허용 문자를 제한합니다.

```sh
case "$APP_PORT" in
    ''|*[!0-9]*)
        echo "APP_PORT는 숫자여야 합니다." >&2
        exit 1
        ;;
esac
```

입력 검사는 공격 방지뿐 아니라 설정 오류를 실행 초기에 발견하는 수단입니다.

## 6. 비밀값 파일을 읽습니다

비밀번호를 Dockerfile, 소스 코드, Compose의 평문 환경변수에 직접 쓰지 않습니다. Compose가 마운트한 파일 경로를 애플리케이션에 전달합니다.

```yaml
services:
  app:
    secrets:
      - db_password
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password
```

시작 스크립트는 파일이 존재하고 읽을 수 있는지 확인합니다. 파일 내용은 비어 있지 않은 한 줄이어야 하며 오류 메시지에 실제 값을 포함하지 않습니다.

주입된 파일을 PHP-FPM 워커가 직접 읽지 못할 수도 있습니다. 이 경우 시작 시 `/run` 아래의 tmpfs에 다음 권한으로 복사할 수 있습니다.

```text
소유자 root
그룹 www-data
권한 0440
```

워커는 읽을 수 있지만 수정할 수 없습니다. 복사본은 컨테이너가 사라지면 함께 사라집니다.

## 7. 데이터베이스 연결은 제한된 횟수만 재시도합니다

Compose가 데이터베이스의 상태 검사를 기다리더라도 애플리케이션은 연결 시점의 일시적인 실패를 처리해야 합니다.

```php
$pdo = null;
for ($attempt = 1; $attempt <= $maxAttempts; $attempt++) {
    try {
        $pdo = new PDO($dsn, $user, $password, $options);
        break;
    } catch (PDOException $error) {
        if ($attempt < $maxAttempts) {
            usleep($delayMs * 1000);
        }
    }
}

if (!$pdo instanceof PDO) {
    throw new RuntimeException('데이터베이스 연결 제한 횟수를 초과했습니다.');
}
```

재시도에는 다음 값이 필요합니다.

- 한 번의 연결 제한 시간
- 최대 시도 횟수 또는 전체 제한 시간
- 시도 사이의 대기 시간
- 최종 실패 메시지

무한 재시도는 설정 오류를 숨깁니다. 잘못된 비밀번호는 기다린다고 해결되지 않으므로 실제 운영 코드에서는 인증 실패와 일시적인 연결 실패를 구분하는 편이 좋습니다.

## 8. 테이블 생성과 최초 데이터 입력은 별개입니다

다음 SQL은 테이블 중복 생성을 막습니다.

```sql
CREATE TABLE IF NOT EXISTS notes (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    body VARCHAR(500) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

하지만 이것만으로 최초 데이터의 중복 입력까지 막지는 못합니다.

```sql
INSERT INTO notes (body) VALUES ('seed note');
```

위 명령을 시작할 때마다 실행하면 같은 행이 계속 추가됩니다. 최초 데이터에는 고유한 마커를 두고, 마커를 실제로 만든 실행만 데이터를 추가하게 해야 합니다.

## 9. 마커와 최초 데이터는 같은 트랜잭션에서 처리합니다

```php
$pdo->beginTransaction();
try {
    $marker = $pdo->prepare(
        "INSERT IGNORE INTO app_meta (meta_key, meta_value)
         VALUES ('seed_v1', 'done')"
    );
    $marker->execute();

    if ($marker->rowCount() === 1) {
        $seed = $pdo->prepare('INSERT INTO notes (body) VALUES (:body)');
        $seed->execute(['body' => 'seed note']);
    }

    $pdo->commit();
} catch (Throwable $error) {
    if ($pdo->inTransaction()) {
        $pdo->rollBack();
    }
    throw $error;
}
```

마커와 데이터 입력을 한 트랜잭션에 두면 데이터 입력이 실패했을 때 마커도 남지 않습니다. 다음 시작에서 다시 시도할 수 있습니다.

먼저 `SELECT`로 마커가 없는지 확인하고 나중에 `INSERT`하는 방식은 두 인스턴스가 동시에 시작할 때 경쟁 상태가 생길 수 있습니다. `app_meta.meta_key`의 기본키와 원자적인 `INSERT IGNORE` 결과를 이용해 실제 작업 주체를 정합니다.

MariaDB의 DDL은 암시적으로 커밋될 수 있으므로 테이블 준비와 최초 데이터 트랜잭션을 구분합니다.

## 10. 부분 실패 뒤 다시 실행할 수 있어야 합니다

다음 상황을 생각해 봅니다.

```text
notes 테이블 생성 성공
→ 최초 데이터 입력 실패
→ 컨테이너 종료
→ 다시 시작
```

테이블 생성이 재실행 가능하고 완료 마커가 데이터보다 먼저 남지 않았다면 다음 시작에서 안전하게 이어갈 수 있습니다.

부분 실패를 검토할 때는 다음을 확인합니다.

- 어느 변경이 트랜잭션 안에 있는가?
- 완료를 나타내는 값은 언제 기록하는가?
- 실패 뒤 남아도 되는 파일이나 행은 무엇인가?
- 동시에 두 인스턴스가 시작하면 누가 작업하는가?
- 재실행할 수 없는 외부 작업이 있는가?

## 11. 파일 권한은 필요한 경로에만 줍니다

코드와 기본 설정은 읽기 전용으로 유지하고, 워커가 실제로 쓰는 디렉터리만 쓰기 가능하게 합니다.

```text
/var/www/html     읽기 전용 코드와 정적 파일
/opt/app          관리 스크립트
/run/app-secrets  컨테이너가 살아 있는 동안만 쓰는 비밀값 복사본
/app/var          애플리케이션이 쓰는 데이터
```

시작할 때마다 전체 코드 디렉터리에 `chown -R`을 수행하면 시작이 느려지고 불변 코드까지 수정 가능해질 수 있습니다. 필요한 디렉터리만 준비합니다.

## 12. 마지막에는 최종 서버를 `exec`합니다

```sh
php /opt/app/bootstrap.php
exec "$@"
```

Dockerfile은 최종 실행 명령을 제공합니다.

```dockerfile
ENTRYPOINT ["/usr/local/bin/app-entrypoint.sh"]
CMD ["php-fpm", "-F"]
```

`exec`는 시작 셸을 PHP-FPM으로 교체합니다. PHP-FPM이 PID 1이 되어 Docker의 SIGTERM을 직접 받고 종료 상태도 그대로 전달합니다.

초기화가 실패하면 `exec`까지 도달하지 않아야 합니다. 준비되지 않은 애플리케이션을 실행 중인 것처럼 남기지 않습니다.

## 13. 상태 검사는 상태를 바꾸지 않습니다

초기화와 상태 검사의 목적은 다릅니다.

### 초기화

- 테이블을 만듭니다.
- 최초 데이터를 넣습니다.
- 런타임 디렉터리를 만듭니다.
- 비밀값 복사본을 준비합니다.

### 상태 검사

- PHP-FPM ping을 확인합니다.
- 작은 읽기 요청을 보냅니다.
- 데이터베이스에서 `SELECT 1`을 실행합니다.

상태 검사는 짧은 주기로 반복됩니다. 스키마를 바꾸거나 데이터를 추가하면 장애를 숨기고 쓰기 부하를 만들 수 있습니다.

## 14. 실제 스키마 변경 도구가 추가로 해결해야 하는 문제

이 장의 예제는 최초 스키마를 만드는 데 집중합니다. 서비스가 발전하면 다음 기능이 필요합니다.

- 변경 파일의 버전과 적용 순서
- 한 번만 실행되도록 하는 잠금
- 적용 이력 기록
- 트랜잭션 가능 여부
- 오래 걸리는 변경의 서비스 영향
- 실패했을 때 이전 상태로 되돌릴지 다음 수정으로 전진할지 결정

`CREATE TABLE IF NOT EXISTS`만으로 컬럼 변경이나 데이터 변환까지 안전해지는 것은 아닙니다.

## 15. 자주 생기는 오해

### “시작 스크립트는 최초 설치 때만 실행됩니다”

아닙니다. 컨테이너를 시작할 때마다 실행됩니다. 기존 상태에서도 안전해야 합니다.

### “`depends_on`이 있으니 애플리케이션 재시도는 필요 없습니다”

`depends_on`은 시작 시점의 순서를 도울 뿐 실행 중 DB 재시작이나 일시적인 연결 실패까지 처리하지 않습니다.

### “`IF NOT EXISTS`를 붙이면 초기 데이터도 중복되지 않습니다”

테이블 생성과 행 삽입은 별개의 작업입니다. 최초 데이터는 고유 마커나 자연스러운 고유 키로 중복을 막아야 합니다.

### “관리자 권한으로 실행해도 컨테이너 안이므로 괜찮습니다”

컨테이너가 관리자 권한의 위험을 없애지는 않습니다. 필요한 준비를 마친 뒤 최종 서비스는 비특권 사용자로 실행합니다.

### “비밀값 파일이면 값이 어디에도 노출되지 않습니다”

애플리케이션이 사용하려면 메모리에 값이 존재합니다. 로그, 진단 출력, 프로세스 환경과 파일 권한을 함께 관리해야 합니다.

## 16. 확인 질문

1. 이미지에 넣을 파일과 시작할 때 주입할 값을 어떤 기준으로 나누시겠습니까?
2. DB 연결 재시도가 무한하면 어떤 오류가 숨겨집니까?
3. 마커와 최초 데이터 입력을 같은 트랜잭션에 둬야 하는 이유는 무엇입니까?
4. 두 애플리케이션 인스턴스가 동시에 시작해도 최초 데이터가 한 번만 들어가게 하려면 무엇이 필요합니까?
5. 초기화가 실패했을 때 PHP-FPM을 시작하지 않아야 하는 이유는 무엇입니까?
6. 상태 검사에서 데이터 변경 작업을 하면 어떤 문제가 생깁니까?
7. `exec "$@"`를 생략하면 시그널과 종료 상태 전달이 어떻게 달라집니까?

## 정리

- 코드, 설정, 비밀값, 실행 중 데이터는 서로 다른 수명으로 관리합니다.
- 시작 직후 필수 설정과 비밀값 파일을 검사합니다.
- 의존 서비스 연결은 제한된 횟수만 재시도합니다.
- 테이블 생성과 최초 데이터 중복 방지는 따로 설계합니다.
- 완료 마커와 최초 데이터는 함께 커밋되거나 함께 롤백되어야 합니다.
- 실패 뒤 다시 실행할 수 있는 상태만 남깁니다.
- 초기화가 끝난 뒤 `exec`로 최종 서버를 PID 1로 실행합니다.
- 상태 검사는 읽기 전용이어야 합니다.
