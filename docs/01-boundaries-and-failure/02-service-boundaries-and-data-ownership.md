# 서비스 경계와 데이터 소유권

## 목표

서비스 이름이나 저장소 수를 정하기 전에 데이터마다 정본과 유일한 변경 주체를 정합니다. 다른 서비스는 소유 서비스의 명령을 호출하거나 이벤트를 구독하되, 같은 데이터를 직접 수정하지 않습니다.

## 실행 파일만 나눈다고 서비스가 분리되지는 않습니다

두 서비스가 같은 테이블을 직접 수정하면 배포 단위만 나뉘었을 뿐 상태 변경 규칙은 공유된 상태입니다.

```text
reservation-service ─┐
                     ├─ shared.reservations UPDATE
admin-service ───────┘
```

이 경우 다음 질문에 일관되게 답하기 어렵습니다.

- 어느 서비스의 입력 검사가 최종 규칙입니까?
- 두 서비스의 배포 버전이 다르면 어느 schema를 사용합니까?
- 한 서비스의 transaction이 잡은 lock을 다른 서비스가 얼마나 기다립니까?
- 장애 뒤 잘못된 값을 어느 서비스가 복구합니까?

서비스를 나눌 때는 “이 상태 변경을 최종 승인하고 저장하는 곳은 어디인가”부터 정합니다.

## 데이터마다 정본과 writer를 기록합니다

각 데이터 집합에 다음 정보를 적습니다.

| 항목 | 확인할 내용 |
| --- | --- |
| 정본 | 최종 업무 상태를 저장하는 위치 |
| writer | 상태 전이를 검증하고 기록하는 서비스 |
| reader | API나 복제본으로 값을 읽는 서비스 |
| 허용 지연 | 복제본이 원본보다 늦어도 되는 시간 |
| 복구 주체 | 불일치를 찾아 원본과 맞추는 작업 |

읽기 편의를 위해 복제본을 만들 수는 있지만, 복제본은 쓰기 판단의 정본이 아닙니다. 다른 서비스가 값을 바꾸려면 owner의 명령 API를 호출하거나 owner가 처리할 메시지를 보냅니다.

## 같은 transaction에서 지켜야 할 조건을 함께 둡니다

항상 함께 지켜야 하는 상태를 서로 다른 서비스로 나누면 네트워크를 건너는 조정이 필요합니다.

예를 들어 “가용 수량은 음수가 될 수 없다”는 조건을 Inventory Service가 검사한다면 Reservation Service가 재고 테이블을 직접 줄이면 안 됩니다. Reservation Service는 수량 예약을 요청하고, Inventory Service가 현재 재고를 확인해 수락 또는 거절합니다.

나누기 전에 다음을 확인합니다.

- 같은 transaction에서 함께 바뀌어야 하는 값이 무엇인지
- 같은 검증 규칙으로 보호해야 하는 값이 무엇인지
- 독립 배포와 확장이 실제로 필요한지
- 네트워크 지연과 부분 실패를 감수할 이유가 있는지

모듈로 충분한 기능을 무조건 별도 서비스로 만들 필요는 없습니다.

## 전체 진행과 개별 상태 변경을 구분합니다

여러 서비스를 순서대로 호출하는 작업에서는 전체 진행을 기록하는 조정자와 각자 상태를 바꾸는 참여자를 구분합니다.

```text
Reservation Service: 전체 예약 진행 상태와 다음 작업
Inventory Service: 재고 확인, 예약과 해제
Payment Service: 결제 승인과 취소
Notification Service: 알림 전달 결과
```

조정자가 참여자의 데이터베이스를 직접 수정하면 어느 서비스의 검증 규칙을 따라야 하는지 불분명해집니다. 참여자가 다른 참여자의 내부 테이블을 조회해 결정해도 숨은 의존이 생깁니다.

## 공개 형식은 서비스 구현을 참조하지 않습니다

공유 event type이나 API schema는 특정 서비스의 entity나 repository를 가져오지 않습니다.

```text
service implementation → published contract
published contract      -X→ service implementation
```

공유 모듈에 내부 업무 코드를 계속 넣으면 서비스 하나를 배포할 때 다른 서비스까지 같은 버전으로 맞춰야 합니다. 공유 파일에는 외부에 공개한 필드와 의미만 둡니다.

## 흔한 잘못

- 두 서비스가 같은 테이블에 씁니다.
- 조회용 복제본을 최신 정본처럼 사용해 쓰기 여부를 결정합니다.
- 전체 진행을 관리하는 서비스가 다른 서비스의 DB를 직접 고칩니다.
- 공개 event type이 내부 entity를 그대로 사용합니다.
- 독립 배포가 필요하지 않은 코드까지 네트워크로 분리합니다.
- 복제 데이터의 지연 시간과 재구축 방법을 정하지 않습니다.

## 검증 방법

구성도보다 명령과 상태 변경 표를 먼저 작성합니다.

```text
명령: ReserveInventory
정본: Inventory Service
입력: operation_id, item_id, units
결과: ACCEPTED / REJECTED / PENDING / UNKNOWN
거절 시 유지할 값: reserved_units
복구: operation_id로 결과 조회
```

각 상태 변경에 writer를 하나만 지정할 수 없다면 분리가 끝난 것이 아닙니다.

## 관련 프로젝트

[`service-boundary`](../../exercises/service-boundary/)는 DataSet별 owner와 writer를 검사하고, 등록되지 않은 이름과 동기 의존 순환을 보고합니다.

## 완료 기준

- 데이터마다 정본과 writer를 하나씩 지정할 수 있습니다.
- 복제본의 허용 지연과 재구축 담당을 정할 수 있습니다.
- 전체 진행을 관리하는 코드와 실제 상태를 바꾸는 서비스를 구분할 수 있습니다.
- 모듈로 둘 기능과 별도 서비스로 나눌 기능을 설명할 수 있습니다.
