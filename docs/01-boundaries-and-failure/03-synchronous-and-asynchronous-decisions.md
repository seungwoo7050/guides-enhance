# 동기·비동기 명령 결정

## 목표

서비스 전체에 한 가지 통신 방식을 적용하지 않고, 명령마다 언제 결과를 확정해야 하는지에 따라 동기 판정과 비동기 처리를 선택합니다.

## 통신 방식보다 반환해야 할 결과가 먼저입니다

“비동기가 확장에 유리하다”거나 “동기가 단순하다”는 이유만으로 방식을 정하면 사용자에게 돌려준 결과와 실제 처리 상태가 달라질 수 있습니다.

동기 호출은 응답 시점에 수락·거절을 알려 줄 수 있지만 하위 서비스의 지연과 장애가 호출자까지 전달됩니다. 비동기 처리는 호출을 빨리 끝낼 수 있지만 `PENDING`, 중복 전달, 순서 변경과 결과 조회가 필요합니다.

먼저 다음 질문에 답합니다.

> 이 명령을 받은 시점에 어떤 결과까지 확정해야 합니까?

## 즉시 판정이 필요한 경우

다음 조건에서는 동기 호출이 자연스럽습니다.

- 사용자가 다음 작업을 하기 전에 수락 또는 거절을 알아야 합니다.
- 오래된 복제본으로 판단하면 안 됩니다.
- 거절한 요청은 어떤 상태도 바꾸면 안 됩니다.
- 한 서비스가 짧은 시간 안에 결과를 결정할 수 있습니다.

동기 호출은 전체 deadline을 먼저 정하고 하위 서비스에는 남은 시간을 전달합니다. 하위 서비스가 응답하지 못했을 때 `REJECTED`, `PENDING`, `UNKNOWN` 중 무엇을 반환할지도 미리 정합니다.

## 처리를 나중에 끝내도 되는 경우

다음 조건에서는 비동기 처리를 사용할 수 있습니다.

- 통계나 알림처럼 핵심 판정 이후 실행해도 됩니다.
- 호출자가 `PENDING`과 결과 조회를 받아들일 수 있습니다.
- 같은 메시지가 다시 오거나 순서가 바뀌어도 처리할 수 있습니다.
- 대기열 크기와 최대 대기 시간을 제한할 수 있습니다.

API가 `202 Accepted`를 반환한다면 “작업이 끝났다”가 아니라 “시스템이 이 작업을 보관하고 후속 처리를 맡았다”는 뜻이어야 합니다. operation ID와 조회 경로를 함께 반환해야 합니다.

## 한 요청 안에서도 방식을 나눌 수 있습니다

```text
재고 수량 판정: 동기 호출
예약 상태와 Outbox 저장: local transaction
통계와 알림: 비동기 event
조회 모델 갱신: 비동기 projection
```

“이 서비스는 비동기 서비스다”처럼 서비스 단위로 정하면 명령별 실패 상태가 사라집니다. 각 명령에는 다음을 기록합니다.

- 응답 전에 확정해야 할 결과
- 허용할 수 있는 최대 지연
- 하위 서비스가 응답하지 않을 때의 상태
- 결과 조회 방법
- 재시도와 취소 방법
- 실패했을 때 바뀌면 안 되는 값

## 원격 호출을 기다리며 DB transaction을 유지하지 않습니다

DB lock을 잡은 상태에서 원격 서비스 응답을 기다리면 네트워크 지연이 lock 유지 시간으로 바뀝니다. 보통 다음처럼 나눕니다.

```text
짧은 transaction으로 PENDING 저장
→ transaction 종료
→ 원격 명령 실행
→ 결과에 따라 짧은 transaction으로 상태 변경
```

중간 상태가 생기지만 저장되어 있으므로 재시작 뒤 다시 확인할 수 있습니다.

## 흔한 잘못

- `202`를 반환하면서 operation ID와 조회 API를 제공하지 않습니다.
- 원격 판정 전에 로컬 수량을 먼저 변경합니다.
- 비동기 대기열의 크기와 최대 지연을 정하지 않습니다.
- 하위 timeout의 합이 전체 deadline보다 깁니다.
- 원격 호출 동안 DB transaction과 lock을 유지합니다.
- 메시지를 Broker에 보냈다는 사실을 최종 업무 성공으로 반환합니다.

## 검증 방법

동기 실패 테스트는 바뀌면 안 되는 값을 함께 확인합니다.

```text
Policy Service 응답 없음
→ 요청은 REJECTED 또는 PENDING
→ reserved_units는 증가하지 않음
```

비동기 접수 테스트는 시스템이 후속 처리를 실제로 보관하는지 확인합니다.

```text
202 + operation_id
→ 조회 결과 PENDING
→ 처리 뒤 ACCEPTED 또는 REJECTED
→ 최대 처리 시간을 넘기면 재조정 대상
```

## 관련 프로젝트

[`request-decision`](../../exercises/request-decision/)은 같은 입력을 동기와 비동기 방식으로 처리합니다. Policy가 `ALLOW`를 반환하기 전에는 예약 수량을 바꾸지 않습니다.

## 완료 기준

- 명령마다 동기 또는 비동기를 선택한 이유를 설명할 수 있습니다.
- `202 Accepted`가 완료가 아니라 접수를 뜻한다는 점을 설명할 수 있습니다.
- 하위 서비스 장애에서 바뀌면 안 되는 값을 테스트합니다.
- DB transaction과 원격 호출의 실행 시간을 분리합니다.
