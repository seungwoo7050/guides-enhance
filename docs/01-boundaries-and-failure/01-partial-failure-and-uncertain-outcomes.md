# 부분 실패와 확정할 수 없는 결과

## 목표

원격 호출에서 응답을 받지 못한 사실과 서버의 업무 처리 결과를 구분합니다. 결과를 확정할 수 없을 때는 `UNKNOWN`을 사용하고, 처음 사용한 operation ID로 결과를 다시 확인합니다.

## 응답이 없다고 실패한 것은 아닙니다

로컬 함수가 예외를 던지면 일반적으로 그 함수가 결과를 만들지 못했다고 판단할 수 있습니다. 원격 호출은 다릅니다.

```text
클라이언트가 요청을 보냅니다.
→ 서버가 상태를 저장합니다.
→ 서버가 성공 응답을 보냅니다.
→ 네트워크에서 응답이 사라집니다.
```

클라이언트는 timeout을 받지만 서버 상태는 이미 바뀌었습니다. 이때 새 ID로 같은 요청을 보내면 상태가 두 번 바뀔 수 있습니다. 반대로 timeout을 최종 실패로 기록하면 실제로 성공한 처리를 실패라고 보여 주게 됩니다.

따라서 다음 두 결과를 따로 기록해야 합니다.

```text
호출 결과: 응답 수신 / 연결 실패 / timeout
업무 결과: ACCEPTED / REJECTED / PENDING / UNKNOWN
```

`UNKNOWN`은 단순한 오류 문구가 아닙니다. 처리가 끝났을 수도 있고 시작되지 않았을 수도 있으므로 정본을 다시 확인해야 하는 상태입니다.

## 같은 업무에는 같은 operation ID를 사용합니다

operation ID는 사용자가 시작한 업무 한 건을 식별합니다. 같은 업무를 여러 번 전송하더라도 이 값은 바꾸지 않습니다.

```text
operation_id = 업무 의도 한 건의 식별자
attempt_id   = 같은 업무를 전달하려고 시도한 개별 호출
```

서버는 operation ID와 입력 지문을 함께 저장합니다.

- 같은 ID와 같은 입력이 다시 오면 이전 결과를 반환합니다.
- 같은 ID와 다른 입력이 오면 충돌로 거절합니다.
- 아직 처리 중이면 `PENDING`을 반환합니다.
- 처리 결과를 알 수 없다면 `UNKNOWN`과 후속 확인 방법을 반환합니다.

ID만 비교하고 입력을 비교하지 않으면 과거 결과를 다른 요청에 잘못 돌려줄 수 있습니다.

## 명령과 결과 조회를 분리합니다

응답을 잃은 호출자는 무조건 새 명령을 보내기보다 기존 결과를 조회할 수 있어야 합니다.

```text
POST /reservations
Idempotency-Key: op-123

GET /operations/op-123
```

조회 결과는 다음과 같이 해석합니다.

- `PENDING`: 시스템이 요청을 보관했고 계속 처리합니다.
- `ACCEPTED`: 상태 변경이 적용되었습니다.
- `REJECTED`: 상태를 바꾸지 않았으며 거절 이유가 확정되었습니다.
- `UNKNOWN`: 처리 주체도 결과를 확인하지 못해 재조정이 필요합니다.

`UNKNOWN`을 영구 상태로 남기면 안 됩니다. 누가 언제 어떤 정본을 확인할지 정해야 합니다.

## timeout과 취소는 다릅니다

클라이언트가 기다리기를 멈췄다고 서버 작업이 자동으로 취소되지는 않습니다. timeout은 호출자가 응답을 기다리는 시간이고, 서버 작업의 deadline과 cancellation은 별도로 정의해야 합니다.

취소를 지원한다면 다음을 정합니다.

- 어느 상태에서 취소할 수 있는지
- 이미 적용된 변경을 되돌릴지
- 완료와 취소가 동시에 발생하면 어느 결과를 우선할지
- 취소 요청에 어떤 멱등성 키를 사용할지
- 최종 결과를 어디에서 조회할지

## 흔한 잘못

- timeout을 즉시 업무 실패로 저장합니다.
- 재시도마다 새 operation ID를 만듭니다.
- 같은 ID에 다른 입력을 허용합니다.
- 응답을 잃은 뒤 결과를 조회하지 않고 다시 상태를 변경합니다.
- 클라이언트 timeout을 서버 작업 취소로 간주합니다.
- `UNKNOWN`을 남기고 다시 확인할 작업을 두지 않습니다.

## 검증 방법

응답 코드만 보지 말고 실제 상태 변경 횟수를 확인합니다.

```text
서버가 상태를 저장한 뒤 응답을 잃습니다.
→ 같은 operation ID로 결과를 조회합니다.
→ ACCEPTED를 확인합니다.
→ 같은 명령을 다시 보내도 상태 변경 횟수는 1입니다.
```

같은 ID에 다른 입력을 보내면 이전 결과를 반환하지 않고 상태 변경 없이 거절해야 합니다.

## 관련 프로젝트

- [`uncertain-outcome`](../../exercises/uncertain-outcome/)은 응답 유실과 결과 조회만 작게 재현합니다.
- 필수 최종 프로젝트인 [`reservation-flow`](../../exercises/reservation-flow/)도 같은 operation ID로 결과를 조회하고 `UNKNOWN`을 재조정합니다.

## 완료 기준

- 전송 실패와 업무 실패를 구분할 수 있습니다.
- `PENDING`, `UNKNOWN`, `ACCEPTED`, `REJECTED`의 의미를 설명할 수 있습니다.
- 재시도와 조회에 같은 operation ID를 사용합니다.
- 응답 유실 뒤에도 업무 효과가 한 번만 남는 테스트를 작성할 수 있습니다.
