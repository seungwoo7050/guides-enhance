# 점근 분석

## 학습 목표

이 문서를 읽고 나면 다음을 할 수 있어야 합니다.

- 입력 크기를 나타내는 변수를 문제에 맞게 정의합니다.
- 어떤 연산을 비용의 기본 단위로 셀지 먼저 정합니다.
- `O`, `Ω`, `Θ`의 의미를 구분합니다.
- 최악·평균·기대·상각 비용이 서로 다른 주장임을 설명합니다.
- 반복문뿐 아니라 자료구조 연산, 복사, 재귀 stack, 출력 크기까지 포함해 시간과 공간 비용을 계산합니다.
- 여러 입력 변수를 임의로 하나로 합치지 않고 각 변수의 영향을 유지합니다.
- 그래프의 희소·밀집 표현에 따라 같은 작업의 비용이 달라지는 이유를 설명합니다.

## 선행지식

[문제 조건과 반례](01-problem-contracts-and-counterexamples.md)에서 입력 크기를 정의하는 방법과 기본적인 합·곱·로그 표기를 먼저 이해해야 합니다.

특히 다음 표현을 읽을 수 있어야 합니다.

```text
1 + 2 + ... + n
log n
n log n
n²
2^n
```

## 핵심 관점

점근 분석(asymptotic analysis)은 특정 컴퓨터에서 실행 시간이 몇 초인지 정확히 예측하는 작업이 아닙니다.

목적은 **입력 크기가 증가할 때 필요한 시간이나 메모리가 어떤 증가율로 커지는지 설명하는 것**입니다.

기본 순서는 다음과 같습니다.

```text
입력 크기를 정의합니다.
→ 세려는 기본 연산을 정합니다.
→ 그 연산이 몇 번 수행되는지 계산합니다.
→ 충분히 큰 입력에서 지배적인 증가율을 정리합니다.
→ 추가로 사용하는 메모리도 계산합니다.
```

예를 들어 배열 전체를 한 번 순회하는 코드가 있다면 단순히 "`O(n)`이다"라고 쓰기 전에 다음을 명확히 해야 합니다.

```text
n = 배열의 원소 수
기본 연산 = 각 원소를 한 번 검사하는 작업
```

`n`의 의미가 불분명하면 복잡도 표현도 불분명합니다.

## 1. `n`의 의미부터 정합니다

문제마다 입력 크기를 나타내는 변수가 다릅니다.

대표적인 예는 다음과 같습니다.

- 배열: 원소 수 `n`
- 문자열 검색: 본문 길이 `n`, pattern 길이 `m`
- 그래프: 정점 수 `V`, 간선 수 `E`
- 행렬: 행 수 `R`, 열 수 `C`
- 큰 정수: 정수값 자체가 아니라 표현에 필요한 bit 수 `b`
- 모든 결과를 열거하는 문제: 입력 크기와 출력 개수 `k`

### 값의 크기와 입력 크기를 구분합니다

정수 `1,000,000,000` 하나를 입력받는 문제에서 입력 크기를 무조건 `n = 1,000,000,000`이라고 볼 수는 없습니다.

정수가 이진수로 저장된다면 필요한 bit 수는 대략 다음과 같습니다.

```text
log₂ n
```

따라서 큰 정수 연산에서는 "정수의 값"과 "정수를 표현하는 데 필요한 bit 수"를 구분해야 합니다.

작은 고정 폭 정수형의 덧셈은 보통 상수 시간으로 취급하지만, 임의 정밀도 정수처럼 숫자의 자릿수가 계속 증가할 수 있다면 덧셈·곱셈 비용도 입력 크기에 따라 증가할 수 있습니다.

### 그래프에서는 `V`와 `E`를 함께 유지합니다

그래프 전체를 탐색하면서 모든 정점과 모든 간선을 확인해야 한다면 비용을 `O(V)`라고만 쓸 수 없습니다.

인접 list를 사용한 그래프 전체 순회는 보통 다음과 같습니다.

```text
Θ(V + E)
```

왜냐하면 다음 두 작업이 모두 필요하기 때문입니다.

```text
각 정점을 확인: Θ(V)
각 간선을 확인: Θ(E)
```

희소 그래프에서는 `E`가 `V`와 비슷한 크기일 수 있지만, 밀집 그래프에서는 `E`가 `Θ(V²)`까지 커질 수 있습니다.

따라서 `V`와 `E`를 하나의 변수로 섣불리 합치면 그래프 구조에 따른 비용 차이를 잃게 됩니다.

## 2. 점근 표기의 의미

점근 표기는 충분히 큰 입력에서 함수의 증가율을 비교합니다.

### Big-O: 상한

```text
f(n) = O(g(n))
```

는 충분히 큰 `n`에 대해 어떤 양의 상수 `c`가 존재하여

```text
f(n) <= c · g(n)
```

이 성립한다는 뜻입니다.

즉 `f(n)`이 상수배의 `g(n)`보다 더 빠르게 증가하지 않는다는 **점근적 상한**입니다.

### Big-Omega: 하한

```text
f(n) = Ω(g(n))
```

는 충분히 큰 `n`에 대해 어떤 양의 상수 `c`가 존재하여

```text
f(n) >= c · g(n)
```

이 성립한다는 뜻입니다.

즉 `f(n)`이 상수배의 `g(n)`보다 더 느리게 증가하지 않는다는 **점근적 하한**입니다.

### Big-Theta: 정확한 증가율 범위

```text
f(n) = Θ(g(n))
```

는

```text
f(n) = O(g(n))
f(n) = Ω(g(n))
```

을 동시에 만족한다는 뜻입니다.

즉 충분히 큰 입력에서 두 함수가 상수배 차이 안에서 같은 증가율을 가집니다.

### 예: 낮은 차수 항과 상수 계수는 제거합니다

다음 함수가 있다고 합시다.

```text
f(n) = 3n² + 10n + 7
```

충분히 큰 `n`에서는 `n²` 항이 증가율을 지배하므로

```text
f(n) = Θ(n²)
```

입니다.

`O(n³)`라고 써도 상한이라는 의미에서는 참이지만, 실제 증가율보다 지나치게 느슨한 설명입니다.

가능하다면 알고 있는 가장 유용하고 타이트한 경계를 사용합니다.

### `O`가 항상 "최악 시간"을 뜻하지는 않습니다

`O`는 단지 **상한을 나타내는 표기**입니다.

예를 들어 다음은 모두 의미가 다른 문장입니다.

```text
최악 시간은 O(n²)입니다.
평균 시간은 O(n log n)입니다.
추가 공간은 O(n)입니다.
```

`O` 자체가 최악·평균·공간 중 무엇을 분석하는지 말해 주지는 않습니다. 분석 대상을 문장으로 함께 밝혀야 합니다.

## 3. 최악·평균·기대·상각 비용을 구분합니다

같은 알고리즘도 어떤 관점으로 분석하느냐에 따라 다른 비용을 가질 수 있습니다.

### 최악 비용

**같은 입력 크기를 가진 모든 허용 입력 중 가장 큰 비용**입니다.

예를 들어 선형 검색에서 배열 끝에 답이 있거나 답이 없다면 최대 `n`개의 원소를 확인할 수 있습니다.

```text
최악 시간: Θ(n)
```

### 평균 비용

**입력에 대한 확률 분포를 정하고 그 분포에서 평균한 비용**입니다.

평균 비용을 말하려면 어떤 입력이 얼마나 자주 등장하는지에 대한 분포가 필요합니다.

예를 들어 "검색 대상이 각 위치에 같은 확률로 존재한다"라는 가정을 둘 수 있습니다.

분포를 명시하지 않고 단순히 "평균적으로 `O(n)`"이라고 하면 어떤 평균인지 불분명합니다.

### 기대 비용

**알고리즘 내부의 무작위 선택에 대한 기댓값**입니다.

같은 입력을 넣어도 알고리즘이 난수에 따라 다른 실행 경로를 선택할 수 있다면, 그 무작위성에 대해 평균을 계산할 수 있습니다.

예를 들어 randomized quicksort는 pivot 선택에 무작위성을 사용할 수 있습니다.

```text
고정된 입력
+
무작위 pivot 선택
→ 기대 실행 시간 분석
```

### 상각 비용

상각 분석(amortized analysis)은 특정 연산 한 번의 평균이 아니라, **여러 연산을 연속으로 수행했을 때의 총비용을 전체 연산 수에 나누어 각 연산의 장기적인 비용 상한을 분석**합니다.

대표적인 예가 동적 배열의 `append`입니다.

대부분의 `append`는 빈 공간에 값을 하나 기록하므로 `O(1)`이지만, 용량이 가득 차면 더 큰 배열을 만들고 기존 원소를 복사해야 할 수 있습니다.

```text
일반 append: O(1)
재할당이 발생하는 append 한 번: O(n)
여러 append를 연속 수행한 상각 비용: O(1) per append
```

여기서 중요한 점은 `O(1)` 상각 비용이 "`append`가 매번 `O(1)`"이라는 뜻이 아니라는 것입니다.

### 서로 다른 주장을 한 문장으로 합치지 않습니다

예를 들어 다음 두 문장은 근거가 다릅니다.

```text
hash 조회의 기대 시간: O(1)
동적 배열 append의 상각 시간: O(1)
```

첫 번째는 hash 함수나 충돌 분포에 관한 기대값이고, 두 번째는 여러 연산의 총비용에 대한 상각 분석입니다.

둘을 단순히 "`평균적으로 O(1)`"이라고 표현하면 분석의 의미를 잃습니다.

## 4. 반복문은 들여쓰기가 아니라 상태 변화 횟수로 계산합니다

반복문의 시간 복잡도를 계산할 때는 반복문이 몇 겹인지보다 **실제 작업이 몇 번 수행되는지**를 세는 것이 중요합니다.

### 독립적인 중첩 반복

다음 코드에서는 바깥 반복이 `n`번, 안쪽 반복도 매번 `n`번 수행됩니다.

```text
for i = 1 .. n:
    for j = 1 .. n:
        work()
```

따라서 작업 수는

```text
n · n = n²
```

이고 전체 시간은

```text
Θ(n²)
```

입니다.

### 반복 범위가 바뀌면 합을 세웁니다

다음 코드는 안쪽 반복 횟수가 `i`에 따라 달라집니다.

```text
for i = 1 .. n:
    for j = 1 .. i:
        work()
```

전체 작업 수는 다음과 같습니다.

```text
1 + 2 + ... + n
```

합 공식에 따라

```text
n(n + 1) / 2
```

이므로

```text
Θ(n²)
```

입니다.

### 중첩된 `while`이 항상 곱은 아닙니다

다음처럼 두 pointer가 각각 한 방향으로만 움직이는 알고리즘을 생각해 봅시다.

```text
left = 0
right = 0

while right < n:
    while condition:
        left += 1
    right += 1
```

겉으로는 `while`이 중첩되어 있지만,

```text
right는 최대 n번 증가
left도 전체 실행 동안 최대 n번 증가
```

라면 총 pointer 이동 횟수는 `O(n)`입니다.

따라서 전체 시간이 `O(n²)`이라고 단정할 수 없습니다.

이러한 패턴은 two-pointer, sliding window 알고리즘에서 자주 나타납니다.

핵심 질문은 다음과 같습니다.

```text
각 상태 또는 index가 전체 실행 동안 몇 번 변합니까?
```

## 5. 반복문 안의 숨은 비용을 포함합니다

코드에 반복문이 하나뿐이라고 해서 전체 비용이 `O(n)`인 것은 아닙니다.

반복문 내부에서 수행하는 연산도 함께 계산해야 합니다.

### 복사

길이 `k`인 배열이나 문자열을 복사하면 보통

```text
Θ(k)
```

의 시간이 필요합니다.

예를 들어

```python
for i in range(n):
    copy = values[:]
```

에서 `values[:]`가 길이 `n` 전체를 복사한다면

```text
n번 반복 × Θ(n) 복사
= Θ(n²)
```

입니다.

### 문자열 slice

언어와 구현에 따라 다르지만, 새로운 문자열을 만드는 slice는 보통 slice 길이에 비례하는 비용이 듭니다.

예를 들어 길이 `k`인 substring을 새로 만든다면 대략

```text
Θ(k)
```

로 볼 수 있습니다.

반복문 내부에서 큰 slice를 계속 만들면 예상보다 높은 비용이 발생할 수 있습니다.

### 문자열 연결

불변 문자열(immutable string)을 반복해서 이어 붙이면 매번 이전 문자열을 복사해야 하는 언어가 있습니다.

예를 들어

```python
s = ""
for part in parts:
    s = s + part
```

의 비용은 각 `part`의 길이와 문자열 구현에 따라 단순 `O(n)`보다 커질 수 있습니다.

이런 경우 문자열 builder나 `join`처럼 전체 크기를 효율적으로 구성하는 방법이 필요할 수 있습니다.

### 정렬

비교 정렬은 보통 다음 정도의 비교 횟수를 사용합니다.

```text
O(n log n)
```

하지만 원소 비교 자체가 상수 시간이 아닐 수도 있습니다.

비교 한 번의 비용이 `C`라면 전체 정렬 비용은 대략

```text
O(n log n · C)
```

로 표현할 수 있습니다.

예를 들어 긴 문자열을 사전순으로 비교한다면 비교 한 번이 공통 prefix 길이에 비례할 수 있습니다.

## 6. 자료구조 연산 비용을 포함합니다

자료구조 연산은 이름만 보고 상수 시간이라고 가정하면 안 됩니다.

대표적인 비용은 다음과 같습니다.

| 연산 | 일반적인 비용 |
| --- | --- |
| 배열 index 접근 | `O(1)` |
| 동적 배열 끝 append | 상각 `O(1)` |
| 동적 배열 중간 삽입·삭제 | `O(n)` |
| binary heap 삽입 | `O(log n)` |
| binary heap 최솟값/최댓값 확인 | 보통 `O(1)` |
| binary heap root 삭제 | `O(log n)` |
| 균형 binary search tree 탐색 | `O(log n)` |
| hash table 조회 | 기대 `O(1)`, 최악 `O(n)` 가능 |
| linked list의 알고 있는 노드 삭제 | `O(1)` |
| linked list에서 특정 값 탐색 | `O(n)` |

실제 표준 library는 언어와 구현에 따라 세부 비용이 다를 수 있으므로, 중요한 분석에서는 사용하는 자료구조의 계약을 확인해야 합니다.

### 동적 배열 앞쪽 삭제

동적 배열에서 첫 원소를 삭제하면 뒤 원소를 한 칸씩 앞으로 이동시켜야 할 수 있습니다.

```text
길이 n 배열의 앞쪽 삭제: O(n)
```

이를 `n`번 반복하면 전체 비용은 `O(n²)`가 될 수 있습니다.

queue가 필요하다면 앞쪽 삭제가 상수 시간인 deque 같은 구조를 사용하는 이유가 여기에 있습니다.

### hash table의 `O(1)`은 보통 기대 비용입니다

hash table은 적절한 hash 분산과 load factor가 유지되는 상황에서 조회·삽입이 기대 `O(1)`인 경우가 많습니다.

하지만 충돌이 심하거나 adversarial input이 들어오면 최악의 경우 더 느려질 수 있습니다.

따라서 다음처럼 표현하는 것이 더 정확합니다.

```text
hash 조회: 기대 O(1), 최악 O(n) 가능
```

구체적인 최악 비용은 실제 구현 방식에 따라 달라질 수 있습니다.

---

## 7. 출력 크기는 시간 하한이 됩니다

알고리즘이 모든 결과를 실제로 반환하거나 출력해야 한다면, 결과를 쓰는 데 필요한 시간보다 빨리 끝날 수 없습니다.

이를 **출력 민감도(output sensitivity)** 관점에서 생각할 수 있습니다.

### 그래프의 모든 간선 반환

간선이 `E`개이고 모든 간선을 출력해야 한다면 최소한 각 간선을 한 번은 기록해야 합니다.

```text
시간 하한: Ω(E)
```

### 모든 부분집합 반환

원소가 `n`개라면 부분집합의 수는

```text
2^n
```

개입니다.

부분집합 하나를 상수 크기로 표현할 수 있다고 가정하더라도 모든 결과를 반환하는 데 최소

```text
Ω(2^n)
```

의 시간이 필요합니다.

실제로 각 부분집합의 원소까지 모두 출력한다면 총 출력 크기는 더 클 수 있습니다.

### 문자열의 모든 일치 위치 반환

본문 검색 결과가 `k`개라면 결과 index를 모두 반환하는 데 최소

```text
Ω(k)
```

가 필요합니다.

따라서 검색 알고리즘을 다음처럼 표현할 수 있습니다.

```text
O(n + k)
```

여기서

```text
n = 검색에 필요한 입력 크기
k = 실제로 반환하는 결과 개수
```

입니다.

입력 처리 시간만 보고 출력 비용을 무시하면 실제 실행 비용을 과소평가하게 됩니다.

---

## 8. 추가 공간과 전체 보관 공간을 구분합니다

공간 복잡도를 설명할 때는 **입력 자체를 저장하는 공간**과 **알고리즘이 추가로 요구하는 공간(auxiliary space)** 을 구분하는 것이 좋습니다.

예를 들어 인접 list 그래프에 BFS를 수행한다고 합시다.

```text
입력 그래프 저장: Θ(V + E)
방문 배열: Θ(V)
BFS queue: 최악 Θ(V)
```

알고리즘이 입력 그래프 외에 추가로 사용하는 공간은

```text
Θ(V)
```

입니다.

입력까지 포함한 전체 보관 공간은

```text
Θ(V + E)
```

입니다.

### 같은 표현이라도 무엇을 포함했는지 밝혀야 합니다

다음 두 문장은 서로 다른 의미일 수 있습니다.

```text
BFS 공간 복잡도는 O(V)입니다.
BFS가 사용하는 전체 메모리는 O(V + E)입니다.
```

첫 번째는 추가 공간만 말하고, 두 번째는 입력 그래프 저장까지 포함한 표현일 수 있습니다.

따라서 분석 문서에서는 다음처럼 명시하는 편이 좋습니다.

```text
추가 공간: O(V)
입력 포함 전체 공간: O(V + E)
```

---

## 9. 재귀 stack도 공간 비용입니다

재귀 함수는 각 호출의 지역 상태와 반환 위치 등을 call stack에 저장합니다.

따라서 재귀 깊이가 공간 복잡도에 영향을 줍니다.

### 선형 깊이 재귀

다음 형태의 재귀를 생각해 봅시다.

```text
f(n):
    if n == 0:
        return
    f(n - 1)
```

호출이 종료되기 전에 `n`개 수준이 stack에 쌓일 수 있으므로 추가 공간은

```text
Θ(n)
```

입니다.

### 분할 정복

병합 정렬은 재귀 깊이가 대략

```text
Θ(log n)
```

입니다.

재귀 stack만 계산하면 `Θ(log n)`이지만, 병합에 사용하는 임시 배열이 있다면 추가 공간은 보통 `Θ(n)`이 됩니다.

따라서 공간 복잡도는 stack만 보지 말고 모든 보조 저장 공간을 함께 계산해야 합니다.

---

## 10. 여러 입력 변수를 한 변수로 뭉개지 않습니다

문제에 독립적인 크기 변수가 여러 개 있다면 가능하면 그대로 유지합니다.

### 문자열 검색

본문 길이를 `n`, pattern 길이를 `m`이라고 합시다.

단순한 위치별 비교는 각 시작 위치에서 최대 `m`글자를 비교할 수 있으므로 보통

```text
O(nm)
```

으로 표현할 수 있습니다.

KMP는 pattern 전처리와 본문 탐색을 합쳐

```text
O(n + m)
```

입니다.

이를 모두 `O(n²)`로 표현하면 `n`과 `m`이 크게 다른 경우의 정보를 잃습니다.

예를 들어

```text
본문 길이 n = 1,000,000
pattern 길이 m = 10
```

이라면 `O(nm)`과 `O(n²)`는 문제의 실제 구조를 매우 다르게 설명합니다.

### 행렬

`R x C` 행렬을 모두 순회하면

```text
Θ(RC)
```

입니다.

정사각 행렬이라는 조건이 없다면 무조건 `Θ(n²)`라고 쓰는 것보다 `R`, `C`를 유지하는 편이 정확합니다.

---

## 11. 그래프 표현에 따라 비용이 달라집니다

같은 그래프라도 어떤 자료구조로 표현하느냐에 따라 연산 비용이 달라집니다.

### 인접 list

저장 공간:

```text
Θ(V + E)
```

전체 순회:

```text
Θ(V + E)
```

특정 정점의 모든 이웃을 확인하는 비용은 그 정점의 degree에 비례합니다.

### 인접 matrix

저장 공간:

```text
Θ(V²)
```

두 정점 `u`, `v` 사이의 간선 존재 여부 확인:

```text
O(1)
```

하지만 한 정점의 모든 이웃을 찾으려면 해당 행의 `V`개 항목을 확인해야 하므로

```text
Θ(V)
```

가 필요합니다.

### edge list

간선을 `(u, v, w)` 형태의 목록으로 저장하면 공간은

```text
Θ(E)
```

입니다.

Kruskal 알고리즘처럼 모든 간선을 정렬한다면 정렬 비용은

```text
O(E log E)
```

입니다.

### 희소 그래프와 밀집 그래프

희소 그래프(sparse graph)는 보통 `E`가 `V²`보다 훨씬 작은 그래프를 말합니다.

밀집 그래프(dense graph)는 `E`가 `Θ(V²)`에 가까울 수 있습니다.

따라서

```text
O(V + E)
```

는 희소 그래프에서는 `V`에 가까운 비용일 수 있지만, 밀집 그래프에서는 `O(V²)`와 같은 크기가 될 수 있습니다.

두 표현은 항상 서로 대체 가능한 것이 아닙니다.

## 12. 점화식과 실제 비용을 연결합니다

재귀 알고리즘은 다음 세 요소를 분리해서 봅니다.

```text
하위 문제의 개수
하위 문제의 크기
현재 호출에서 수행하는 추가 작업
```

이를 점화식(recurrence)으로 표현할 수 있습니다.

```text
T(n) = 하위 문제 비용 + 현재 호출의 작업
```

### 병합 정렬

병합 정렬은 입력을 대략 절반 크기의 두 하위 문제로 나누고, 두 결과를 병합하는 데 선형 시간이 필요합니다.

```text
T(n) = 2T(n/2) + Θ(n)
```

재귀 tree의 깊이는 `Θ(log n)`이고 각 level에서 총 `Θ(n)`의 병합 작업을 하므로

```text
T(n) = Θ(n log n)
```

입니다.

### quicksort의 나쁜 분할

pivot이 계속 가장 작거나 가장 큰 값이 되어 한쪽 하위 문제에 거의 모든 원소가 몰리면 다음과 같은 형태가 됩니다.

```text
T(n) = T(n - 1) + Θ(n)
```

이를 펼치면

```text
n + (n - 1) + ... + 1
```

이므로

```text
Θ(n²)
```

입니다.

### 점화식에서 현재 호출의 비용을 빼먹지 않습니다

다음처럼 재귀 호출 수만 보고

```text
T(n) = 2T(n/2)
```

라고 쓰면 병합 과정 같은 실제 작업이 빠질 수 있습니다.

항상 현재 호출에서 다음을 확인합니다.

- 배열 분할이나 복사
- 결과 병합
- pivot partition
- 문자열 결합
- 하위 결과를 순회하는 작업

## 13. 상수 시간 가정이 적절한지 확인합니다

알고리즘 분석에서는 흔히 다음 연산을 `O(1)`로 취급합니다.

```text
고정 폭 정수 덧셈
고정 폭 정수 비교
배열 index 접근
pointer 이동
```

이는 일반적인 RAM model에서 유용한 단순화입니다.

하지만 입력의 숫자가 매우 커질 수 있는 문제에서는 이러한 가정이 맞지 않을 수 있습니다.

예를 들어 `b` bit 정수 두 개의 덧셈은 모든 bit를 처리해야 할 수 있으므로 대략

```text
O(b)
```

가 필요할 수 있습니다.

따라서 다음 문제에서는 bit complexity를 고려해야 할 수 있습니다.

- 임의 정밀도 정수
- 매우 큰 팩토리얼
- 큰 정수 곱셈
- 암호 알고리즘
- 숫자의 자릿수가 입력과 함께 증가하는 문제

반면 일반적인 고정 폭 정수 범위의 알고리즘 문제에서는 산술 연산을 상수 시간으로 보는 모델이 흔히 사용됩니다.

## 14. benchmark와 점근 분석은 다른 도구입니다

benchmark는 실제 컴퓨터에서 구현의 실행 시간을 측정합니다.

점근 분석은 입력 크기가 커질 때 비용이 어떻게 증가하는지 수학적으로 설명합니다.

두 도구는 서로 대체하지 않습니다.

### benchmark가 알려 줄 수 있는 것

- 상수 계수 차이
- cache 효과
- compiler 최적화 영향
- library 구현 차이
- 실제 입력 분포에서의 성능

### 점근 분석이 알려 주는 것

- 입력 크기가 매우 커질 때 증가율
- 알고리즘 구조 자체의 확장성
- 입력 변수 간 비용 관계
- 최악·상각·기대 비용의 이론적 경계

예를 들어 작은 입력에서는 `O(n²)` 구현이 `O(n log n)` 구현보다 더 빠를 수 있습니다.

이는 점근 분석이 틀렸다는 뜻이 아닙니다. 작은 입력에서는 상수 계수와 구현 오버헤드가 더 큰 영향을 줄 수 있기 때문입니다.

따라서 benchmark 한 번으로 "`O(n²)`이 더 좋은 알고리즘"이라고 일반화해서는 안 됩니다.

점근 분석을 작성한 뒤 다음을 확인합니다.

- 각 입력 변수의 의미를 정의했습니까?
- 세려는 기본 연산을 정했습니까?
- `O`, `Ω`, `Θ` 중 어떤 경계를 주장하는지 적절합니까?
- 최악·평균·기대·상각 중 무엇을 분석했는지 밝혔습니까?
- 평균 비용을 말한다면 입력 분포를 설명했습니까?
- library 호출, 복사, 정렬, 문자열 slice 비용을 포함했습니까?
- 자료구조 연산의 실제 비용을 확인했습니까?
- 재귀 stack을 추가 공간에 포함했습니까?
- 출력 개수가 시간 하한이 되는지 확인했습니까?
- 여러 입력 변수를 임의로 하나로 합치지 않았습니까?
- 정수 연산을 상수 시간으로 보는 전제가 적절합니까?
- 추가 공간과 입력 저장 공간을 구분했습니까?
- benchmark 결과를 점근 복잡도와 혼동하지 않았습니까?

## 연결 구현

[`verified-algorithms`](../../exercises/verified-algorithms/)에서 다음 비용을 직접 설명합니다.

### `prefix_sums`

길이 `n`의 배열을 한 번 순회해 누적 합 배열을 만듭니다.

```text
전처리 시간: O(n)
질의 시간: O(1)
추가 공간: O(n)
```

질의를 많이 수행할 때 초기 `O(n)` 비용을 지불하고 각 질의를 상수 시간으로 줄이는 구조입니다.

### `lower_bound`

정렬된 길이 `n` 배열에서 탐색 범위를 절반씩 줄입니다.

```text
시간: O(log n)
추가 공간: O(1)
```

반복문 구현을 기준으로 한 추가 공간입니다. 재귀 구현이라면 재귀 stack 비용을 별도로 계산해야 합니다.

### `dijkstra`

인접 list와 binary heap을 사용하는 일반적인 구현은 다음과 같이 표현할 수 있습니다.

```text
O((V + E) log V)
```

정점과 간선을 처리하고 heap 연산에 `log V` 비용이 발생하기 때문입니다.

구현과 분석 방식에 따라 `O(E log V)`로 단순화되는 경우도 있지만, 어떤 항을 포함했는지 명확히 해야 합니다.

### `bellman_ford`

최악의 경우 모든 간선에 대한 relaxation을 최대 `V-1`번 수행하므로

```text
O(VE)
```

입니다.

음수 cycle 검사를 위한 추가 순회가 있어도 같은 점근 차수 안에 포함됩니다.

### `kmp_find`

pattern 전처리에 `O(m)`, 본문 검색에 `O(n)`이 필요하므로

```text
O(n + m)
```

입니다.

여기서

```text
n = 본문 길이
m = pattern 길이
```

입니다.

## 실패 신호

다음 중 하나라도 해당하면 분석을 다시 확인해야 합니다.

- `O(n)`이라고 쓰면서 `n`이 무엇인지 정의하지 않습니다.
- `O`를 무조건 최악 시간의 의미로 사용합니다.
- 평균 비용과 기대 비용을 같은 뜻으로 사용합니다.
- 평균 비용과 상각 비용을 같은 뜻으로 사용합니다.
- 중첩 반복문이라는 이유만으로 항상 비용을 곱합니다.
- 반복문 내부의 정렬, 복사, slice 비용을 무시합니다.
- hash table 연산을 조건 없이 항상 최악 `O(1)`이라고 단정합니다.
- 그래프 비용을 항상 `O(V²)` 또는 항상 `O(V+E)`라고 단정합니다.
- 재귀 stack이나 반환 결과 저장 공간을 무시합니다.
- 출력해야 할 결과가 매우 많은데 출력 비용을 제외합니다.
- 서로 독립적인 입력 변수를 하나의 `n`으로 합쳐 중요한 정보를 잃습니다.
- benchmark 한 번을 점근 분석의 근거로 사용합니다.
