# 입력 오류와 디버깅

프로그램에 문제가 생겼을 때 가장 먼저 해야 할 일은 **실패의 종류를 구분하는 것**입니다. 사용자가 잘못된 값을 입력한 경우와 프로그램이 배열 범위를 벗어나 메모리를 읽은 경우는 겉으로는 모두 "프로그램이 실패했다"는 결과를 만들 수 있지만, 원인과 해결 방법은 완전히 다릅니다.

입력 오류는 프로그램이 **예상하고 처리해야 하는 상황**입니다. 반면 배열 범위 밖 접근, 해제한 메모리 사용, 잘못된 포인터 역참조 같은 문제는 프로그램 구현의 결함입니다. 코드 결함을 단순한 입력 오류처럼 처리해서는 안 됩니다.

디버깅의 기본 흐름은 다음과 같습니다.

```text
실패 종류 구분
→ 같은 문제를 재현
→ 관찰 가능한 증거 수집
→ 원인에 대한 가설 설정
→ 디버거·sanitizer 등으로 확인
→ 코드 수정
→ 같은 입력으로 재검증
→ 경계·실패 사례까지 다시 테스트
```

## 실패 종류

| 종류 | 예 | 처리 방법 |
| --- | --- | --- |
| 입력 형식 오류 | 인자 누락, 숫자가 아닌 문자열 | 진단 메시지를 출력하고 정해진 실패 종료 상태를 반환합니다. |
| 값 범위 오류 | 음수 금지, 허용 범위 초과 | 입력을 거부하고, 가능하면 기존 상태와 출력 매개변수를 유지합니다. |
| 자원 확보 실패 | `malloc`, `open`, `fork` 실패 | 이미 확보한 자원을 필요한 순서로 정리하고 오류를 호출자에게 전달합니다. |
| 코드 결함 | 범위 밖 접근, 해제 후 사용, 잘못된 포인터 역참조 | 재현 조건을 만든 뒤 디버거와 sanitizer 등의 도구로 원인을 찾아 코드를 수정합니다. |

이 구분은 오류 처리 코드를 설계할 때 중요합니다.

예를 들어 사용자가 숫자 대신 `"abc"`를 입력한 것은 충분히 예상 가능한 입력 오류입니다.

```text
./program abc
```

프로그램은 이를 검사하여 진단 메시지와 실패 종료 상태를 반환하면 됩니다.

반면 다음과 같은 코드는:

```c
int values[10];
printf("%d\n", values[20]);
```

입력의 문제가 아니라 프로그램 자체가 잘못된 메모리에 접근하는 코드 결함입니다. 이런 문제를 다음처럼 단순히 "입력이 잘못되었습니다"라고 처리하는 것은 원인을 숨길 뿐입니다.

## 입력 검증의 기본 원칙

입력 문자열을 정수로 바꾸는 함수는 단순히 "숫자로 바뀌었는가"만 확인해서는 부족합니다. 다음 조건을 함께 정해야 합니다.

```text
빈 문자열을 허용하는가?
앞뒤 공백을 허용하는가?
+ 또는 - 부호를 허용하는가?
문자열 일부만 숫자여도 되는가?
표현 가능한 범위를 벗어난 값은 어떻게 처리하는가?
실패했을 때 출력 매개변수는 유지되는가?
```

예를 들어 다음 입력들은 서로 다른 정책이 필요할 수 있습니다.

```text
"123"
"-123"
"+123"
" 123"
"123 "
"123abc"
""
```

따라서 변환 함수의 구현 전에 **어떤 문자열 형식을 유효한 입력으로 인정할지** 먼저 정해야 합니다.

## `atoi`보다 `strtol`을 사용하는 이유

`atoi`는 간단하지만 입력 검증이 필요한 코드에는 적합하지 않습니다.

예를 들어:

```c
int value = atoi("abc");
```

는 `0`을 반환할 수 있습니다.

하지만 정상적인 입력 `"0"`도:

```c
int value = atoi("0");
```

결과가 `0`입니다.

따라서 반환값만 보고는 다음 두 상황을 구분하기 어렵습니다.

```text
정상적으로 숫자 0을 읽음
숫자로 변환할 수 없음
```

또한 `atoi`는 변환 결과가 `int` 범위를 벗어나는 입력을 신뢰성 있게 검사하는 인터페이스를 제공하지 않습니다.

입력을 검증해야 한다면 `strtol`처럼 다음 정보를 확인할 수 있는 함수를 사용하는 편이 좋습니다.

- 실제 변환 결과
- 어디까지 변환했는지 나타내는 끝 포인터
- 표현 범위를 벗어났는지 나타내는 `errno`

## `strtol`로 정수 문자열 전체 검사하기

다음 함수는 다음 정책을 가진다고 가정합니다.

```text
입력은 비어 있으면 안 된다.
앞 공백은 허용하지 않는다.
10진수만 허용한다.
문자열 전체가 하나의 정수여야 한다.
long 범위를 벗어나면 실패한다.
실패하면 *out_value를 변경하지 않는다.
```

```c
#include <ctype.h>
#include <errno.h>
#include <stdlib.h>

int parse_long(const char *text, long *out_value) {
    char *end;
    long value;

    if (text == NULL || out_value == NULL || text[0] == '\0' ||
        isspace((unsigned char)text[0])) {
        return -1;
    }

    errno = 0;
    value = strtol(text, &end, 10);

    if (errno == ERANGE || end == text || *end != '\0') {
        return -1;
    }

    *out_value = value;
    return 0;
}
```

이 구현의 각 검사는 서로 다른 문제를 확인합니다.

### 1. 포인터 검사

```c
if (text == NULL || out_value == NULL) {
    return -1;
}
```

`text`가 `NULL`이면 문자열을 읽을 수 없고, `out_value`가 `NULL`이면 성공 결과를 기록할 위치가 없습니다.

### 2. 빈 문자열 검사

```c
text[0] == '\0'
```

첫 문자가 바로 NUL 문자라면 문자열의 길이는 0입니다.

```text
""
```

이 함수의 정책에서는 빈 문자열을 정수로 인정하지 않으므로 실패합니다.

### 3. 앞 공백 검사

```c
isspace((unsigned char)text[0])
```

`strtol` 자체는 앞쪽 공백을 건너뛸 수 있습니다.

따라서:

```text
"   123"
```

도 별도 검사가 없다면 `123`으로 변환될 수 있습니다.

현재 함수는 **앞 공백을 입력 오류로 처리한다는 정책**을 가지고 있으므로 `strtol`을 호출하기 전에 첫 문자를 검사합니다.

여기서:

```c
(unsigned char)text[0]
```

로 변환하는 이유는 `isspace`에 `EOF` 또는 `unsigned char`로 표현 가능한 값만 전달해야 하기 때문입니다.

### 4. `errno` 초기화

```c
errno = 0;
```

`errno`는 이전 함수 호출에서 설정된 값이 남아 있을 수 있습니다.

따라서 `strtol` 호출이 새로 `ERANGE`를 설정했는지 확인하려면 호출 전에 값을 초기화합니다.

```c
errno = 0;
value = strtol(text, &end, 10);
```

`strtol`이 성공할 때 반드시 `errno`를 0으로 되돌려 준다고 가정해서는 안 됩니다.

### 5. 아무 문자도 변환하지 못했는지 검사

```c
end == text
```

`end`는 변환이 멈춘 위치를 가리킵니다.

만약 `end == text`라면 입력의 첫 위치에서 바로 변환이 중단되었다는 뜻이므로 숫자로 변환한 문자가 하나도 없습니다.

예:

```text
"abc"
```

### 6. 문자열 전체를 변환했는지 검사

```c
*end != '\0'
```

이 조건은 변환이 끝난 뒤 아직 문자가 남아 있는지 확인합니다.

예를 들어:

```text
"123abc"
```

라면 숫자 부분 `"123"`은 변환할 수 있지만, `end`는 `"abc"`의 시작을 가리킵니다.

따라서:

```c
*end != '\0'
```

가 참이 되어 전체 문자열 검증에는 실패합니다.

반대로:

```text
"123"
```

은 변환이 끝난 위치가 문자열의 마지막 NUL 문자이므로:

```c
*end == '\0'
```

입니다.

현재 정책에서는 뒤쪽 공백도 허용하지 않습니다.

```text
"123 "
```

의 경우 숫자 `123` 뒤에서 변환이 멈추므로 `*end != '\0'`가 되어 실패합니다.

뒤 공백을 허용하고 싶다면 `end` 이후의 공백을 별도로 건너뛴 뒤 NUL인지 검사하는 다른 계약을 구현해야 합니다.

### 7. 범위 오류 검사

```c
errno == ERANGE
```

입력 숫자가 `long`으로 표현할 수 있는 범위를 벗어나면 `strtol`은 `ERANGE`를 설정합니다.

예를 들어 매우 큰 숫자 문자열을 입력했을 때:

```text
"999999999999999999999999999999999"
```

단순히 반환된 값만 사용해서는 안 되고 `errno`를 함께 검사해야 합니다.

`strtol`은 범위를 벗어났을 때 `LONG_MIN` 또는 `LONG_MAX`와 같은 경계값을 반환할 수 있으므로, 경계값 자체만 보고 오류 여부를 판단해서는 안 됩니다. 정상 입력이 실제로 `LONG_MIN`이나 `LONG_MAX`일 수도 있기 때문입니다.

### 8. 모든 검사 후 출력 값 변경

```c
*out_value = value;
```

이 대입은 모든 검사를 통과한 뒤에만 수행됩니다.

따라서 다음과 같이 호출할 수 있습니다.

```c
long value = 42;

if (parse_long("abc", &value) != 0) {
    /* value는 여전히 42입니다. */
}
```

실패 시 출력 매개변수를 유지한다는 규칙은 함수 호출자가 실패한 부분 결과를 해석하지 않아도 되게 만듭니다.

## `strtol` 검사 순서 정리

위 함수의 논리를 순서대로 정리하면 다음과 같습니다.

```text
1. text와 out_value가 NULL인지 확인
2. 빈 문자열인지 확인
3. 정책상 금지된 앞 공백인지 확인
4. errno를 0으로 초기화
5. strtol 호출
6. end == text인지 확인
7. *end == '\0'인지 확인
8. errno == ERANGE인지 확인
9. 모든 검사를 통과한 뒤 *out_value 갱신
```

실제 코드에서는 6~8번 검사를 하나의 `if`로 묶어도 됩니다.

```c
if (errno == ERANGE || end == text || *end != '\0') {
    return -1;
}
```

중요한 것은 **무엇을 검사하는지 이해하는 것**이지 조건문의 물리적인 순서 자체가 아닙니다.

## 오류 메시지와 종료 상태

입력 오류를 발견했다면 사용자가 문제를 수정할 수 있도록 충분한 정보를 제공해야 합니다.

예:

```c
fprintf(stderr, "오류: 정수가 아닙니다: %s\n", argv[index]);
return 2;
```

오류 메시지는 일반적으로 다음 정보를 제공하면 도움이 됩니다.

- 어떤 입력 또는 작업에서 실패했는가?
- 어떤 형식이나 범위가 필요했는가?
- 필요하다면 사용법이나 올바른 예가 무엇인가?

예를 들어:

```c
fprintf(
    stderr,
    "오류: 정수가 필요합니다: %s\n",
    argv[index]
);
```

범위까지 알려 줄 수 있다면:

```c
fprintf(
    stderr,
    "오류: 값은 1부터 100 사이여야 합니다: %s\n",
    argv[index]
);
```

처럼 작성할 수 있습니다.

### 종료 상태는 메시지와 별개의 인터페이스다

오류 메시지와 종료 상태는 서로 다른 역할을 합니다.

```text
stderr 메시지 → 사람이 읽는 진단 정보
종료 상태     → 셸, 스크립트, 테스트 프로그램이 성공·실패를 판단하는 값
```

예를 들어:

```c
fprintf(stderr, "오류: 정수가 필요합니다.\n");
return 2;
```

프로그램은 메시지를 출력하면서 동시에 종료 상태 `2`를 반환할 수 있습니다.

오류 메시지 안에 종료 상태를 반드시 문장으로 적어야 하는 것은 아닙니다. 중요한 것은 프로그램의 인터페이스에서 어떤 실패가 어떤 종료 상태를 사용하는지 일관되게 정하는 것입니다.

## 오류 메시지와 자동 테스트

자동 테스트가 오류 메시지 전체 문장에 지나치게 의존하면 문구를 조금 수정하는 것만으로 테스트가 깨질 수 있습니다.

예를 들어 다음 문장을 정확히 일치시키는 테스트는:

```text
오류: 입력값은 유효한 정수여야 합니다.
```

문장을 다음처럼 개선하는 것만으로 실패할 수 있습니다.

```text
오류: 정수가 필요합니다.
```

따라서 메시지 형식을 외부 인터페이스로 보장해야 하는 요구사항이 없다면 다음과 같은 요소만 검사할 수 있습니다.

```text
stderr가 비어 있지 않은가?
"오류:" 같은 고정 접두어가 있는가?
문제가 된 입력값이 포함되는가?
종료 상태가 기대한 값인가?
```

반대로 과제 명세, 프로토콜, 외부 프로그램과의 호환성 때문에 정확한 메시지 형식이 계약의 일부라면 그 형식을 그대로 테스트해야 합니다.

## 상태를 변경하기 전에 입력 검증하기

잘못된 입력이 들어왔을 때 기존 상태를 유지해야 한다면 먼저 모든 검사를 끝낸 뒤 상태를 갱신합니다.

다음 코드는 좋지 않은 예입니다.

```c
stats->count++;

if (value < 0) {
    return -1;
}
```

입력이 잘못되어 실패했지만 `count`는 이미 증가했습니다.

더 안전한 순서는 다음과 같습니다.

```c
if (value < 0) {
    return -1;
}

stats->count++;
```

여러 필드를 함께 변경해야 하는 경우에는 지역 변수나 임시 구조체에서 결과를 먼저 계산한 뒤 성공 시 한 번에 반영하는 방법을 사용할 수 있습니다.

핵심 규칙은 다음과 같습니다.

```text
검증
→ 필요한 계산
→ 성공 확정
→ 외부에서 관찰 가능한 상태 변경
```

## 자원 확보 실패

`malloc`, `open`, `fork` 같은 함수는 자원 확보에 실패할 수 있습니다.

예를 들어:

```c
char *buffer = malloc(size);

if (buffer == NULL) {
    return -1;
}
```

이미 다른 자원을 확보한 상태에서 이후 작업이 실패한다면 이전에 확보한 자원을 정리해야 합니다.

예:

```c
FILE *file = fopen(path, "r");
if (file == NULL) {
    return -1;
}

char *buffer = malloc(size);
if (buffer == NULL) {
    fclose(file);
    return -1;
}
```

실패 경로마다 어떤 자원을 이미 확보했는지 확인해야 합니다.

자원 정리의 기본 원칙은 다음과 같습니다.

```text
성공한 자원 확보만 정리한다.
한 자원을 두 번 해제하지 않는다.
실패한 뒤 사용할 수 없는 자원을 다시 사용하지 않는다.
소유권을 넘긴 자원을 이전 소유자가 다시 정리하지 않는다.
```

## 최소 재현 사례 만들기

오류를 고치기 전에 **같은 문제를 반복해서 재현할 수 있어야 합니다**.

재현에 필요한 정보를 기록합니다.

```text
실행 명령
명령행 인자
입력 파일 또는 표준 입력
컴파일 명령과 옵션
stdout
stderr
종료 상태
운영체제
컴파일러 종류와 버전
필요한 환경 변수나 작업 디렉터리
```

예를 들어 다음처럼 기록할 수 있습니다.

```text
빌드:
cc -std=c11 -Wall -Wextra -Wpedantic -g source.c -o program

실행:
./program 10 bad 30

stdout:
없음

stderr:
오류 메시지 ...

종료 상태:
2
```

재현 조건을 기록한 뒤에는 문제를 유지하면서 관련 없는 요소를 하나씩 제거합니다.

예를 들어:

```text
입력 파일 1000줄
→ 100줄
→ 10줄
→ 2줄
→ 한 줄
```

또는:

```text
여러 함수가 연결된 프로그램
→ 의심되는 함수 호출만 남김
→ 필요한 데이터만 남김
```

같은 문제가 발생하는 가장 작은 사례를 **최소 재현 사례(minimal reproducible example)**라고 합니다.

최소화할수록 다음 장점이 있습니다.

- 관련 없는 코드가 줄어듭니다.
- 실패를 더 빠르게 반복할 수 있습니다.
- 원인 후보가 줄어듭니다.
- 수정 전후 결과를 비교하기 쉬워집니다.
- 다른 사람에게 문제를 설명하기 쉬워집니다.

## 재현되지 않는 문제를 다룰 때

문제가 한 번 발생했는데 다시 나타나지 않는다면 즉시 코드를 추측해서 바꾸기보다 당시 조건을 최대한 복원합니다.

확인할 항목은 다음과 같습니다.

```text
입력이 정확히 같았는가?
같은 실행 파일인가?
같은 컴파일 옵션인가?
최적화 수준이 같은가?
환경 변수가 같은가?
작업 디렉터리가 같은가?
같은 운영체제와 라이브러리 환경인가?
파일 내용이나 외부 상태가 달라지지 않았는가?
```

특히 정의되지 않은 동작이 있는 프로그램은 빌드 옵션이나 주변 메모리 상태가 달라졌을 때 증상이 사라지거나 다른 형태로 나타날 수 있습니다. "재현되지 않는다"는 사실만으로 문제가 해결되었다고 판단해서는 안 됩니다.

## 디버그 빌드

초기 조사에서는 디버거가 소스 코드와 실행 상태를 연결하기 쉬운 빌드를 사용하는 것이 좋습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -g -O0 source.c -o program
```

### `-g`

```text
-g
```

디버거가 함수 이름, 소스 파일, 줄 번호, 변수 정보 등을 표시하는 데 사용할 디버그 정보를 생성합니다.

디버그 정보가 있다고 해서 프로그램 동작이 자동으로 안전해지는 것은 아닙니다. 단지 디버깅에 필요한 정보를 추가하는 옵션입니다.

### `-O0`

```text
-O0
```

컴파일러 최적화를 최소화합니다.

최적화된 빌드에서는 다음과 같은 일이 생길 수 있습니다.

- 변수가 레지스터로 이동하거나 제거됩니다.
- 여러 소스 문장이 합쳐질 수 있습니다.
- 실행 순서가 소스 코드와 단순하게 대응하지 않을 수 있습니다.
- 디버거가 일부 변수 값을 표시하기 어려울 수 있습니다.

따라서 처음 조사할 때는 `-O0`이 소스 코드와 실제 실행 흐름을 대응시키기 쉬운 경우가 많습니다.

하지만 실제 프로그램을 최적화 옵션으로 빌드한다면 수정 후에는 **실제 사용할 최적화 수준에서도 다시 테스트해야 합니다**.

예를 들어:

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -O2 source.c -o program
```

에서도 같은 테스트를 수행합니다.

`-O0`에서 정상적으로 보인다는 이유만으로 코드 결함이 사라졌다고 판단해서는 안 됩니다. 정의되지 않은 동작이 있는 코드는 최적화 수준에 따라 증상이 달라질 수 있습니다.

## 디버거를 사용할 때의 기본 생각

디버거는 프로그램을 처음부터 끝까지 무작정 한 줄씩 실행하는 도구가 아닙니다.

먼저 다음과 같은 가설을 세우는 편이 효율적입니다.

```text
index가 10이 되는 순간 배열 범위를 벗어날 것이다.
parse 함수가 실패한 뒤에도 count가 증가하는 것 같다.
이 포인터가 free 이후에도 사용되는 것 같다.
이 함수에 들어올 때 length 값이 예상보다 크다.
```

그다음 중단점과 변수 값을 사용해 가설을 확인합니다.

```text
어디에서 잘못된 값이 처음 생기는가?
그 직전 값은 무엇이었는가?
어떤 함수 호출을 거쳐 이 상태가 되었는가?
```

## GDB 기본 사용

예:

```sh
gdb ./program
```

`main`에 중단점을 설정합니다.

```text
(gdb) break main
```

인자를 주어 실행합니다.

```text
(gdb) run 10 bad 30
```

다음 소스 줄로 진행합니다.

```text
(gdb) next
```

현재 줄에서 호출하는 함수 안으로 들어갑니다.

```text
(gdb) step
```

변수 값을 확인합니다.

```text
(gdb) print index
```

현재 호출 스택을 확인합니다.

```text
(gdb) backtrace
```

`next`와 `step`의 차이는 중요합니다.

```text
next → 함수 호출을 한 단계로 실행하고 현재 함수의 다음 줄에서 멈춤
step → 호출되는 함수 안으로 들어가서 멈춤
```

오류가 발생한 함수 내부를 조사하려면 `step`을 사용할 수 있고, 이미 신뢰하는 함수의 내부를 볼 필요가 없다면 `next`가 더 편리합니다.

## LLDB 기본 사용

LLDB에서도 같은 개념을 사용합니다.

```sh
lldb ./program
```

중단점:

```text
(lldb) breakpoint set --name main
```

실행:

```text
(lldb) run 10 bad 30
```

다음 줄:

```text
(lldb) next
```

함수 안으로 진입:

```text
(lldb) step
```

변수 확인:

```text
(lldb) frame variable index
```

호출 스택:

```text
(lldb) bt
```

명령 이름은 다르지만 디버깅 사고방식은 같습니다.

```text
중단할 위치를 정함
→ 재현 입력으로 실행
→ 예상 값과 실제 값 비교
→ 잘못된 값이 처음 만들어지는 지점까지 범위를 좁힘
```

## 중단점을 어디에 둘 것인가

중단점은 단순히 `main`에만 둘 필요가 없습니다.

다음과 같은 위치가 유용합니다.

- 오류가 발생하기 직전의 함수
- 상태를 변경하는 함수
- 배열 인덱스를 계산하는 함수
- 메모리를 할당하거나 해제하는 함수
- 실패 반환값이 처음 만들어지는 함수

예를 들어 `parse_long`이 잘못된 결과를 만드는 것으로 의심된다면:

```text
(gdb) break parse_long
```

처럼 함수 자체에 중단점을 설정할 수 있습니다.

잘못된 값이 어느 시점에 생기는지 알면 문제 범위를 크게 줄일 수 있습니다.

## 호출 스택 읽기

프로그램이 여러 함수 호출을 거쳐 실패하면 현재 함수만 봐서는 왜 그 값이 전달되었는지 알기 어려울 수 있습니다.

호출 스택은 현재 함수에 도달한 호출 경로를 보여 줍니다.

예:

```text
main
→ process_file
→ parse_line
→ parse_value
```

`backtrace` 또는 `bt`를 사용하면 이런 흐름을 역순으로 확인할 수 있습니다.

이를 통해 다음 질문에 답할 수 있습니다.

```text
어떤 함수가 현재 함수를 호출했는가?
문제가 된 인자는 어디서 만들어졌는가?
잘못된 상태가 상위 호출자에서 이미 존재했는가?
```

## AddressSanitizer와 UndefinedBehaviorSanitizer

컴파일러가 지원한다면 다음처럼 sanitizer를 활성화할 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -g \
    -fsanitize=address,undefined -fno-omit-frame-pointer \
    source.c -o program
```

sanitizer는 실행 중 특정 종류의 오류를 감지하기 위해 프로그램에 검사 코드를 추가합니다.

### AddressSanitizer

AddressSanitizer(ASan)는 다음과 같은 메모리 오류를 찾는 데 도움이 됩니다.

- 배열이나 힙 영역의 범위를 벗어난 메모리 접근
- 이미 해제한 메모리 사용(use-after-free)
- 중복 해제(double free)
- 일부 잘못된 스택 메모리 접근

예를 들어:

```c
int values[4];
values[10] = 1;
```

같은 코드가 실제로 실행되면 ASan이 문제 위치와 호출 스택을 보고할 수 있습니다.

### UndefinedBehaviorSanitizer

UndefinedBehaviorSanitizer(UBSan)는 여러 종류의 정의되지 않은 동작을 실행 중 검사하는 데 도움이 됩니다.

대표적으로 다음과 같은 문제를 탐지할 수 있습니다.

- 일부 부호 있는 정수 overflow
- 0으로 정수 나누기
- 잘못된 시프트 연산
- 일부 정렬 요구사항 위반
- 일부 잘못된 타입·포인터 사용

정확한 검사 종류는 컴파일러와 활성화된 sanitizer 옵션에 따라 달라질 수 있습니다.

## sanitizer의 한계

sanitizer를 켰다고 해서 프로그램 전체가 안전하다는 뜻은 아닙니다.

가장 중요한 이유는 **실제로 실행된 코드 경로만 검사할 수 있기 때문**입니다.

예를 들어 프로그램에 다음 두 경로가 있다고 가정합니다.

```text
입력 A → 안전한 코드 경로
입력 B → 배열 범위 오류가 있는 코드 경로
```

sanitizer를 켜고 입력 A만 실행했다면 입력 B의 문제는 발견하지 못합니다.

따라서:

```text
sanitizer 활성화
+
다양한 테스트 입력
```

이 함께 필요합니다.

또한 모든 종류의 버그를 sanitizer가 찾는 것은 아닙니다.

예를 들어 다음 문제는 sanitizer만으로 충분하지 않을 수 있습니다.

- 잘못된 비즈니스 로직
- 요구사항과 다른 계산 결과
- 누락된 입력 검증
- 특정 동시성 문제
- 테스트하지 않은 실행 경로
- 도구가 계측하지 않는 종류의 오류

sanitizer는 테스트와 코드 검토를 대신하는 것이 아니라 **추가적인 오류 탐지 도구**입니다.

## sanitizer 보고서를 읽는 순서

sanitizer가 긴 메시지를 출력해도 먼저 핵심 정보를 찾습니다.

```text
어떤 종류의 오류인가?
어느 소스 파일의 몇 번째 줄인가?
어떤 함수 호출 경로에서 발생했는가?
접근한 주소나 인덱스가 왜 잘못되었는가?
```

예를 들어 ASan이 heap-use-after-free를 보고한다면 다음 세 위치를 찾는 것이 중요합니다.

```text
메모리를 처음 할당한 위치
메모리를 해제한 위치
해제 후 다시 사용한 위치
```

단순히 오류가 보고된 마지막 줄만 수정하기보다 **객체의 수명과 소유권이 어디서 잘못 관리되었는지** 확인해야 합니다.

## 경고를 오류로 다루기

다음 옵션을 사용하면 경고가 하나라도 발생했을 때 빌드를 실패하게 만들 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic -Werror source.c -o program
```

`-Werror`는 경고를 실제 코드 오류로 바꾸는 것이 아니라 **컴파일러의 경고를 빌드 실패 조건으로 취급하도록 만드는 옵션**입니다.

이 방식은 프로젝트에서 경고 없는 빌드를 유지하는 데 도움이 됩니다.

그러나 경고를 없애기 위해 원인을 이해하지 않은 채 캐스트나 경고 억제 옵션을 추가해서는 안 됩니다.

다음 항목을 먼저 확인합니다.

- 타입을 잘못 선택하지 않았습니까?
- signed와 unsigned 값을 섞지 않았습니까?
- `printf` 계열의 형식 지정자와 실제 인자 타입이 일치합니까?
- 확인해야 할 함수 반환값을 무시하지 않았습니까?
- 암시적 변환으로 값이 잘리거나 의미가 바뀌지 않습니까?
- 변환할 값이 대상 타입 범위 안에 있습니까?
- 사용하지 않는 변수나 매개변수가 실제 설계 문제를 나타내지는 않습니까?

예를 들어 다음과 같은 경고가 있다고 가정합니다.

```c
int index = -1;
size_t length = 10;

if (index < length) {
    /* ... */
}
```

단순히:

```c
if ((size_t)index < length) {
    /* ... */
}
```

로 바꾸면 경고는 줄어들 수 있지만 `index == -1`이라는 근본 문제는 해결되지 않습니다.

먼저:

```c
if (index >= 0 && (size_t)index < length) {
    /* ... */
}
```

처럼 값의 의미와 범위를 확인해야 합니다.

## 디버깅용 빌드와 배포용 빌드의 차이

디버깅할 때는 다음과 같은 옵션을 사용할 수 있습니다.

```sh
-g
-O0
-fsanitize=address,undefined
```

하지만 실제 배포 빌드는 다른 최적화와 설정을 사용할 수 있습니다.

따라서 수정이 끝났다면 적어도 다음 두 종류를 모두 확인하는 것이 좋습니다.

```text
디버깅 빌드:
문제 위치를 찾기 쉬운 옵션으로 테스트

실제 사용 빌드:
실제 배포·제출에 사용할 옵션으로 다시 테스트
```

특히 정의되지 않은 동작이 남아 있으면 최적화 수준이 달라질 때 증상이 달라질 수 있습니다.

## 테스트할 입력 나누기

테스트 입력은 한 종류만 준비하지 않습니다.

### 정상 사례

프로그램이 지원한다고 명시한 일반적인 입력입니다.

예:

```text
"0"
"10"
"-5"      /* 음수를 지원한다면 */
```

정상 사례에서는 다음을 확인합니다.

```text
예상한 결과가 stdout에 출력되는가?
stderr가 불필요하게 출력되지 않는가?
종료 상태가 성공 값인가?
내부 상태가 올바르게 갱신되는가?
```

### 경계 사례

허용 범위나 데이터 구조의 경계에 있는 입력입니다.

예:

- 빈 문자열
- 한 글자 문자열
- 허용되는 최솟값
- 허용되는 최댓값
- 배열의 첫 번째 원소
- 배열의 마지막 원소
- 길이가 0인 입력
- 버퍼에 정확히 맞는 데이터

경계 오류는 흔히 다음 형태로 나타납니다.

```text
< 대신 <= 사용
length 대신 length - 1 잘못 사용
마지막 NUL 바이트 공간 누락
최솟값·최댓값 바로 바깥 값 미검사
```

### 실패 사례

프로그램이 명시적으로 거부하거나, 외부 자원 실패로 처리해야 하는 상황입니다.

예:

- 숫자가 아닌 문자
- 숫자 뒤의 불필요한 문자
- 허용 범위 초과
- 필요한 인자 누락
- 파일 열기 실패
- 메모리 할당 실패
- 시스템 호출 실패

실패 사례에서는 단순히 "실패했다"는 것만 확인하지 않습니다.

다음도 함께 검사합니다.

```text
정해진 실패 종료 상태를 반환하는가?
진단 메시지가 stderr로 가는가?
stdout에 잘못된 부분 결과가 남지 않는가?
출력 매개변수가 유지되는가?
기존 상태가 부분적으로 변경되지 않는가?
이미 확보한 자원이 정리되는가?
```

## 경계 바로 바깥도 테스트하기

경계값 하나만 테스트하면 비교 연산의 실수를 놓칠 수 있습니다.

예를 들어 허용 범위가:

```text
1 <= value <= 100
```

이라면 다음 값을 함께 테스트합니다.

```text
0
1
2
99
100
101
```

특히 중요한 값은:

```text
최솟값 바로 아래
최솟값
최댓값
최댓값 바로 위
```

입니다.

이 방식은 `<`, `<=`, `>`, `>=`를 잘못 사용한 오류를 찾는 데 효과적입니다.

## 실패 시 상태 유지 테스트

함수의 계약이 "실패 시 출력 값을 변경하지 않는다"라면 이를 직접 테스트해야 합니다.

예:

```c
long value = 1234;

int result = parse_long("abc", &value);

if (result == 0) {
    /* 테스트 실패: 잘못된 입력인데 성공함 */
}

if (value != 1234) {
    /* 테스트 실패: 실패했는데 출력 값이 변경됨 */
}
```

구조체 상태도 같은 방식으로 검사할 수 있습니다.

```text
함수 호출 전 상태 저장
→ 실패 입력으로 함수 호출
→ 함수가 실패했는지 확인
→ 호출 후 상태가 이전 상태와 같은지 비교
```

성공 결과만 검사하면 실패 경로의 부분 갱신이나 자원 정리 오류를 놓칠 수 있습니다.

## 디버깅할 때 피해야 할 습관

### 무작정 출력문 추가하기

`printf` 디버깅 자체가 잘못된 것은 아니지만, 무엇을 확인하려는지 없이 많은 출력문을 넣으면 정보가 오히려 복잡해집니다.

다음처럼 가설을 세운 뒤 필요한 값만 출력하는 편이 좋습니다.

```text
가설: index가 length보다 커진다.
확인: 반복 직전의 index와 length를 출력한다.
```

### 오류가 난 줄만 보기

배열 범위 오류나 잘못된 포인터 접근은 그 줄에서 잘못된 값이 **사용된 것**일 뿐, 값이 잘못 만들어진 지점은 훨씬 앞일 수 있습니다.

따라서:

```text
잘못된 값이 사용된 위치
→ 그 값을 누가 전달했는가?
→ 그 값은 어디서 처음 잘못되었는가?
```

순서로 거슬러 올라가야 합니다.

### 증상만 없애기

예를 들어 범위 밖 접근이 발생했다고 해서 인덱스를 강제로 잘라내는 것은 근본 원인을 숨길 수 있습니다.

```c
index %= length;
```

이 코드가 경고나 충돌을 없앨 수는 있어도, 원래 `index`가 왜 범위를 벗어났는지 설명하지 못한다면 올바른 수정이라고 볼 수 없습니다.

디버깅의 목표는 **현재 증상을 숨기는 것**이 아니라 **잘못된 상태가 처음 만들어지는 원인을 제거하는 것**입니다.

## 완료 기준

다음을 직접 설명하고 수행할 수 있어야 합니다.

1. 입력 형식 오류, 값 범위 오류, 자원 확보 실패와 코드 결함을 구분합니다.
2. 입력 검증 함수에서 허용할 문자열 형식을 먼저 정해야 하는 이유를 설명합니다.
3. `atoi`보다 `strtol`이 입력 검증에 적합한 이유를 설명합니다.
4. `strtol` 호출 전 `errno`를 0으로 초기화하는 이유를 설명합니다.
5. `end == text`가 아무 문자도 변환하지 못했다는 뜻임을 설명합니다.
6. `*end == '\0'` 검사가 문자열 전체가 변환되었는지 확인한다는 점을 설명합니다.
7. `errno == ERANGE`를 사용하여 `long` 표현 범위 초과를 검사합니다.
8. 모든 검사가 끝난 뒤 출력 매개변수를 변경하여 실패 시 기존 값을 유지합니다.
9. stderr의 진단 메시지와 프로세스 종료 상태가 서로 다른 역할을 한다는 점을 설명합니다.
10. 상태를 변경하기 전에 입력 검증을 완료합니다.
11. 자원 확보가 중간에 실패했을 때 이미 확보한 자원을 정리합니다.
12. 실행 명령, 입력, 빌드 옵션, 출력, 종료 상태와 환경 정보를 기록하여 실패를 재현합니다.
13. 문제를 유지하면서 입력과 코드를 줄여 최소 재현 사례를 만듭니다.
14. `-g`와 `-O0`이 초기 디버깅에서 어떤 도움을 주는지 설명합니다.
15. 디버거에서 중단점, 변수 값과 호출 스택을 사용하여 가설을 확인합니다.
16. `next`와 `step`의 차이를 설명합니다.
17. AddressSanitizer와 UndefinedBehaviorSanitizer가 찾는 대표적인 오류를 설명합니다.
18. sanitizer는 실제로 실행된 경로만 검사하며 모든 버그를 찾는 도구가 아니라는 점을 설명합니다.
19. `-Werror`가 경고를 빌드 실패로 취급하게 한다는 점을 설명합니다.
20. 정상 사례, 경계 사례와 실패 사례를 나누어 테스트합니다.
21. 경계값뿐 아니라 경계 바로 안쪽과 바깥쪽 값도 테스트합니다.
22. 실패 시 출력 매개변수, 기존 상태와 확보한 자원이 올바르게 처리되는지 검사합니다.
