# Docker 이미지와 컨테이너

이 장에서는 애플리케이션을 이미지로 만들고 컨테이너로 실행할 때 무엇이 빌드 시점에 고정되고 무엇이 실행 시점에 새로 생기는지 구분합니다. Docker 명령을 많이 외우는 것보다 이미지, 컨테이너, 프로세스와 파일의 수명(lifecycle)을 정확히 이해하는 것이 먼저입니다.

이 장은 Linux 컨테이너와 Docker Engine을 기준으로 설명합니다. Windows 컨테이너나 다른 컨테이너 런타임(containerd, Podman 등)은 세부 명령이 다를 수 있지만, 이미지·컨테이너·계층을 구분하는 개념은 대체로 같습니다.

---

## 1. Docker가 정리해 주는 것

애플리케이션을 실행했을 때 나오는 결과는 소스 코드만으로 결정되지 않습니다. 다음 항목도 함께 결과에 영향을 줍니다.

- 운영체제와 CPU 아키텍처
- 언어 런타임과 시스템 라이브러리
- 설치한 패키지와 그 버전
- 설정 파일과 환경변수
- 실행 사용자와 파일 권한
- 컨테이너 시작 명령

Dockerfile은 이 항목들을 어떻게 갖추어 실행 가능한 상태로 만들지, 그 절차를 순서대로 기록한 빌드 스크립트입니다.

```text
소스 + Dockerfile + 빌드 입력
              ↓ docker build
            이미지
              ↓ docker run
           컨테이너
```

여기서 “빌드 입력”은 Dockerfile 안의 `COPY`나 `ADD`로 이미지에 들어가는 파일들, 즉 **빌드 컨텍스트(build context)** 를 뜻합니다. 빌드 컨텍스트는 5절에서 더 자세히 다룹니다.

Docker를 사용한다고 해서 “같은 Dockerfile → 항상 같은 이미지”가 자동으로 보장되지는 않습니다. 다음과 같은 요인이 재현성을 깨뜨릴 수 있습니다.

- **가변 태그**: `python:3.12`처럼 버전만 적힌 태그는 시간이 지나면 다른 실제 이미지(다이제스트)를 가리킬 수 있습니다.
- **빌드 중 외부 다운로드**: `RUN curl ...`이나 패키지 설치처럼 빌드 시점에 외부 네트워크에서 내려받는 내용은 그 시점의 최신 버전이 반영됩니다.
- **고정하지 않은 패키지 저장소**: 패키지 관리자가 참조하는 저장소의 최신 버전을 그대로 설치하면, 나중에 같은 Dockerfile로 빌드해도 다른 버전이 설치될 수 있습니다.

즉 재현성은 “Docker를 쓰는지”가 아니라 **입력을 얼마나 명확히 고정했는지**에 달려 있습니다. 완전히 고정하려면 태그 대신 다이제스트를 쓰거나 패키지 버전을 명시하는 방법을 함께 검토합니다(4절 `FROM` 참고).

## 2. 컨테이너는 작은 가상 머신이 아닙니다

가상 머신은 일반적으로 하드웨어를 에뮬레이션하는 하이퍼바이저 위에서 자신만의 게스트 커널을 포함한 완전한 운영체제를 실행합니다. Linux 컨테이너는 이와 달리 **호스트 커널을 그대로 공유**하면서, 커널이 제공하는 격리 기능을 이용해 하나의 프로세스(또는 프로세스 그룹)가 마치 독립된 시스템처럼 보이게 만든 것입니다.

```text
가상 머신                         컨테이너
┌──────────────┐                 ┌──────────────┐
│ 애플리케이션  │                 │ 애플리케이션  │
│ 라이브러리    │                 │ 라이브러리    │
│ 게스트 OS     │                 │ 이미지 파일   │
│ 게스트 커널   │                 ├──────────────┤
├──────────────┤                 │ 호스트 커널   │
│ 하이퍼바이저  │                 └──────────────┘
└──────────────┘
```

Linux 커널은 이 격리를 주로 두 가지 기능으로 구현합니다.

- **네임스페이스(namespace)**: 프로세스가 볼 수 있는 범위를 나눕니다. PID 네임스페이스는 프로세스 목록을, 네트워크 네임스페이스는 네트워크 인터페이스와 라우팅 테이블을, 마운트 네임스페이스는 파일시스템 마운트 지점을, 사용자 네임스페이스는 UID/GID 매핑을 컨테이너별로 독립시킵니다. 1장에서 다룬 “컨테이너 안의 `127.0.0.1`은 그 컨테이너 자신을 가리킨다”는 설명이 바로 네트워크 네임스페이스가 분리되어 있기 때문입니다.
- **cgroups(control groups)**: CPU, 메모리 같은 자원의 사용량을 프로세스 그룹 단위로 제한하고 계측합니다.

즉 컨테이너 안에서 실행되는 프로그램도 결국은 **호스트 커널 위에서 실행되는 일반 프로세스**이며, 다만 커널이 그 프로세스가 볼 수 있는 범위와 쓸 수 있는 자원을 제한하고 있을 뿐입니다. 이 사실은 PID 1, 시그널, 파일 권한과 네트워크를 이해할 때 계속 중요하게 쓰입니다.

컨테이너 격리가 가상 머신만큼 강한 보안 경계를 자동으로 제공하지는 않는다는 점도 함께 기억해 둘 필요가 있습니다. 커널을 공유하기 때문에, 커널 자체의 취약점이나 잘못된 설정(예: 불필요하게 넓은 권한 부여)은 컨테이너 경계를 넘는 문제로 이어질 수 있습니다.

## 3. 이미지와 컨테이너

### 이미지

이미지는 **읽기 전용 파일 계층들의 묶음과 실행 설정**입니다. 여기에는 다음이 포함됩니다.

- 기본 명령과 entrypoint
- 작업 디렉터리
- 환경변수 기본값
- 실행 사용자
- 애플리케이션 파일과 라이브러리

이미지 자체는 실행 중인 프로세스가 아니라, 실행에 필요한 파일과 설정을 담아 둔 **정적인 산출물**입니다. 디스크나 레지스트리에 저장되어 있을 뿐이며, 그 자체로는 아무 것도 실행하지 않습니다.

### 컨테이너

컨테이너는 이미지를 바탕으로 만든 **실행 인스턴스**입니다. `docker run`을 실행하면 Docker는 이미지의 읽기 전용 계층들 위에 그 컨테이너만을 위한 **쓰기 가능한 계층**을 하나 추가하고, 그 안에서 프로세스를 시작합니다.

```text
컨테이너 전용 쓰기 계층   ← 이 컨테이너만의 변경 사항
──────────────────────
애플리케이션 계층
런타임 계층
기본 이미지 계층         ← 이미지에 포함된, 여러 컨테이너가 공유
```

이 구조는 대개 **OverlayFS 같은 유니온 파일시스템(union filesystem)** 이나 **카피-온-라이트(copy-on-write)** 방식으로 구현됩니다. 컨테이너가 기존 파일을 수정하면 원본 이미지 계층은 그대로 두고, 변경된 내용만 쓰기 계층에 복사해서 저장합니다. 그래서 같은 이미지로 여러 컨테이너를 만들어도 이미지 계층(디스크 상의 실제 파일)은 공유하면서, 프로세스와 쓰기 계층은 컨테이너마다 독립적으로 유지됩니다.

### 컨테이너를 중지·삭제할 때

여기서 “중지”와 “삭제”를 구분하는 것이 중요합니다.

- `docker stop`으로 컨테이너를 **중지**하면 프로세스는 멈추지만, 그 컨테이너의 쓰기 계층은 디스크에 그대로 남아 있습니다. 같은 컨테이너를 `docker start`로 다시 시작하면 중지 전 상태가 유지됩니다.
- `docker rm`으로 컨테이너를 **삭제**하면(또는 `docker run --rm`으로 실행해 종료 시 자동 삭제되면) 그 쓰기 계층도 함께 사라집니다. 볼륨이나 바인드 마운트로 컨테이너 밖에 연결해 두지 않은 경로에 저장한 파일은 새 컨테이너에 남지 않습니다.

이 구분에 따라 데이터를 어디에 둘지 정합니다.

- 애플리케이션 코드와 기본 설정: 이미지에 둡니다.
- 잃어도 되는 임시 데이터: 컨테이너 쓰기 계층이나 tmpfs에 둘 수 있습니다.
- 컨테이너를 교체(삭제 후 재생성)해도 남아야 하는 데이터: 볼륨이나 외부 저장소(데이터베이스, 오브젝트 스토리지 등)에 둡니다.
- 로그: 보통 표준 출력과 표준 오류로 보내고, 컨테이너 런타임이나 별도 로그 수집기가 이를 모으도록 합니다.

## 4. Dockerfile의 기본 구성

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.12-slim-bookworm
WORKDIR /app
COPY server.py /app/server.py
ENV APP_HOST=0.0.0.0 APP_PORT=8080
USER 65532:65532
EXPOSE 8080
ENTRYPOINT ["python", "/app/server.py"]
```

### `FROM`

기본 이미지와 그 이미지가 제공하는 런타임을 선택합니다. 앞서 1절에서 다룬 것처럼 태그는 시간이 지나면 다른 이미지 다이제스트를 가리킬 수 있습니다.

```dockerfile
FROM python:3.12-slim-bookworm
```

같은 바이트를 항상 다시 받아야 한다면 태그 대신 다이제스트로 고정하는 방법을 검토합니다.

```dockerfile
FROM python:3.12-slim-bookworm@sha256:<다이제스트값>
```

다만 다이제스트로 고정하면 보안 패치가 반영된 새 이미지로 자동으로 갱신되지 않으므로, 정기적으로 다이제스트를 갱신하는 별도 절차(예: 의존성 자동 업데이트 도구)를 함께 마련해야 합니다.

### `RUN`

**빌드 중**에 명령을 실행하고, 그 결과로 바뀐 파일 상태를 새 이미지 계층으로 남깁니다.

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

`RUN`은 **이미지를 만드는 시점**에 한 번 실행되는 명령이라는 점에서, 컨테이너가 **시작될 때마다** 실행되는 `ENTRYPOINT`/`CMD`와 구분해야 합니다. 예를 들어 `RUN`으로 패키지를 설치해 두면 그 결과가 이미지에 저장되지만, `ENTRYPOINT`로 지정한 서버 프로세스는 `docker run`으로 컨테이너를 새로 만들 때마다 매번 새로 시작됩니다.

### `COPY`

빌드 컨텍스트(5절 참고)에 포함된 파일을 이미지 안으로 복사합니다.

```dockerfile
COPY app/ /app/
```

### `WORKDIR`

이후 이어지는 `RUN`, `COPY`, `ENTRYPOINT` 등의 명령이 기준으로 삼는 기본 작업 디렉터리를 지정합니다. 지정한 디렉터리가 없으면 자동으로 생성됩니다.

### `ENV`

컨테이너가 실행될 때 프로세스에 전달할 환경변수의 기본값을 지정합니다. 여기서 지정한 값은 이미지에 그대로 저장되므로, 비밀번호나 토큰처럼 노출되면 안 되는 값은 `ENV`에 넣지 않습니다. 이미지를 `docker history`나 `docker inspect`로 조사하면 이 값을 그대로 확인할 수 있기 때문입니다.

### `USER`

서비스가 관리자 권한(루트)을 필요로 하지 않는다면 비특권 사용자로 실행하도록 지정합니다.

```dockerfile
USER 65532:65532
```

여기서 65532는 특정 UID를 예로 든 것으로, 그 값 자체에 특별한 의미가 있지는 않습니다. 다만 이 UID/GID가 컨테이너에 마운트하는 볼륨이나 바인드 마운트 파일의 소유권과 맞아야, 해당 사용자가 그 파일을 읽고 쓸 수 있습니다(10절 참고).

### `EXPOSE`

이 이미지로 만든 컨테이너가 어느 포트에서 서비스를 제공할 예정인지 알려 주는 **문서화용 메타데이터**입니다. `EXPOSE`만으로는 호스트에서 그 포트로 실제 접근할 수 있게 되지 않습니다(9절 참고).

### `ENTRYPOINT`와 `CMD`

컨테이너가 시작될 때 실행할 기본 실행 파일과 기본 인자를 정합니다.

```dockerfile
ENTRYPOINT ["python", "/app/server.py"]
CMD ["--verbose"]
```

`ENTRYPOINT`와 `CMD`를 함께 지정하면 실제 실행되는 명령은 두 배열을 이어 붙인 것과 같습니다.

```text
python /app/server.py --verbose
```

`docker run` 시 이미지 이름 뒤에 인자를 추가로 전달하면, 그 인자는 일반적으로 `CMD`를 교체합니다(`ENTRYPOINT`는 그대로 유지됩니다).

```sh
docker run image --debug
# 실행되는 명령: python /app/server.py --debug
```

## 5. 빌드 입력과 `.dockerignore`

다음 명령에서 마지막 인자인 `.`은 **빌드 컨텍스트(build context)**, 즉 Docker 빌더가 읽을 수 있는 디렉터리 범위를 지정합니다.

```sh
docker build -t example .
```

Docker 빌더는 이 디렉터리 전체를 빌드를 실행하는 데몬(또는 빌드 프로세스)에 전송한 뒤, Dockerfile 안의 `COPY`와 `ADD`로 그 범위 안의 파일만 이미지에 넣을 수 있습니다. 빌드 컨텍스트 **밖**에 있는 파일은 `COPY`/`ADD`로 참조할 수 없습니다.

`.dockerignore`는 이 빌드 컨텍스트에 포함되지 않도록, 즉 애초에 빌더에 전달하지 않을 파일을 정합니다.

```text
.git
.env
*.log
__pycache__
backups
```

효과는 다음과 같습니다.

- 빌더에 전송할 파일 크기와 개수를 줄여 빌드를 더 빠르게 합니다.
- 코드와 무관한 파일(로그, 캐시 등) 변경 때문에 빌드 캐시가 불필요하게 깨지는 일을 줄입니다.
- 비밀 파일(`.env` 등)이나 로컬 산출물이 실수로 이미지에 들어갈 가능성을 낮춥니다.

다만 `.dockerignore`는 어디까지나 “빌드 컨텍스트에 무엇을 포함할지”를 정하는 설정일 뿐, 비밀 정보를 보호하는 보안 장치는 아닙니다. 민감한 파일은 가능하면 애초에 빌드 컨텍스트 디렉터리 안에 두지 않거나, Docker의 빌드 시크릿(build secret) 기능처럼 이미지 계층에 값을 남기지 않는 방법을 사용하는 편이 안전합니다.

## 6. 이미지 계층과 캐시

Dockerfile에서 파일 시스템을 바꾸는 단계(`RUN`, `COPY`, `ADD` 등)는 대체로 각각 새로운 이미지 계층을 만듭니다. 이 계층들은 이전 절에서 설명한 것처럼 유니온 파일시스템으로 겹쳐져 하나의 파일시스템처럼 보입니다.

여기서 중요한 성질이 하나 있습니다. **한 계층에서 만든 파일을 다음 계층에서 지워도, 이전 계층에 이미 기록된 파일 자체는 이미지 안에 그대로 남아 있다**는 점입니다. 유니온 파일시스템은 “삭제되었다”는 표시만 새 계층에 남기고 실제로 그 바이트를 지우지는 않기 때문입니다. 그래서 다음처럼 설치와 삭제를 서로 다른 `RUN`으로 나누면, 최종 이미지에서 파일이 안 보이더라도 이미지 전체 크기는 줄어들지 않습니다.

```dockerfile
RUN apt-get install -y build-essential
RUN apt-get remove -y build-essential
```

`build-essential`이 차지했던 용량은 첫 번째 `RUN`이 만든 계층에 이미 저장되어 있고, 두 번째 `RUN`은 “이 파일들이 삭제되었다”는 정보만 담은 새 계층을 추가할 뿐입니다. 두 계층 모두 최종 이미지 크기에 포함됩니다.

임시 파일은 **만든 단계와 같은 `RUN` 안에서** 함께 지워야 그 계층 자체에 남지 않습니다.

```dockerfile
RUN apt-get install -y build-essential \
    && make \
    && apt-get remove -y build-essential
```

빌드에 쓰는 도구(컴파일러 등)와 실행에만 필요한 결과물을 완전히 분리하려면 **다중 단계 빌드(multi-stage build)** 를 사용합니다.

```dockerfile
FROM golang:1.24-bookworm AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/app ./cmd/app

FROM scratch
COPY --from=build /out/app /app
ENTRYPOINT ["/app"]
```

`AS build`는 첫 번째 `FROM` 단계에 `build`라는 이름을 붙입니다. 두 번째 `FROM scratch`는 아무 파일도 없는 빈 이미지에서 새로 시작하고, `COPY --from=build`로 앞 단계의 결과물(컴파일된 바이너리)만 가져옵니다. 이렇게 하면 최종 이미지에는 Go 컴파일러나 소스 코드가 전혀 남지 않고, 실행에 필요한 바이너리만 포함됩니다.

캐시를 잘 활용하려면 **자주 바뀌지 않는 파일을 먼저 복사**합니다. Docker는 각 명령을 순서대로 실행하면서, 이전 빌드와 같은 명령·같은 입력이면 그 계층을 다시 만들지 않고 캐시에 있는 계층을 재사용합니다.

```dockerfile
COPY requirements.txt /app/
RUN pip install --no-cache-dir -r /app/requirements.txt
COPY . /app/
```

의존성 목록(`requirements.txt`)이 바뀌지 않았다면, 소스 코드만 바뀌어도 `pip install` 계층은 캐시에서 그대로 재사용되어 빌드 시간이 줄어듭니다. 반대로 `COPY . /app/`을 `pip install`보다 앞에 두면, 소스 코드가 한 글자만 바뀌어도 그 이후 모든 계층(패키지 설치 포함)이 캐시 무효화되어 다시 실행됩니다.

## 7. Debian 패키지 설치

Debian 계열 이미지(예: `python:3.12-slim-bookworm`)에서는 패키지 인덱스 업데이트, 설치, 인덱스 파일 제거를 **하나의 `RUN`** 에 묶어서 실행합니다.

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        ca-certificates \
        curl \
    && rm -rf /var/lib/apt/lists/*
```

`apt-get update`는 사용 가능한 패키지 목록(인덱스)을 저장소에서 내려받아 로컬에 저장하는 명령이며, 이미 설치된 프로그램을 최신 버전으로 올려 주는 명령이 아닙니다(그 역할은 `apt-get upgrade`가 합니다).

`apt-get update`와 `apt-get install`을 서로 다른 `RUN`으로 나누면 문제가 생길 수 있습니다.

```dockerfile
# 권장하지 않는 방식
RUN apt-get update
RUN apt-get install -y curl
```

`RUN apt-get update`로 만든 계층은 이후 Dockerfile 내용이 바뀌지 않는 한 캐시로 재사용됩니다. 그런데 실제 패키지 저장소의 내용은 시간이 지나며 계속 바뀌므로, 나중에 `apt-get install`만 있는 두 번째 `RUN`이 캐시가 깨져 다시 실행될 때 오래된(로컬에 캐시된) 인덱스를 기준으로 설치를 시도하게 되어, 이미 저장소에서 삭제된 패키지 버전을 찾다가 설치가 실패할 수 있습니다. `update`와 `install`을 한 `RUN`에 묶으면 항상 최신 인덱스를 받은 직후에 설치하므로 이 문제를 피할 수 있습니다.

`--no-install-recommends`는 Debian 패키지가 “권장(recommends)”으로 표시한 부가 패키지를 자동으로 함께 설치하지 않도록 합니다. 실제로 필요한 패키지는 명시적으로 목록에 추가합니다.

## 8. 배열 형식과 PID 1

다음 **배열(exec) 형식**은 셸을 거치지 않고 지정한 프로그램을 곧바로 실행합니다.

```dockerfile
ENTRYPOINT ["python", "/app/server.py"]
```

반면 다음 **셸 형식**은 내부적으로 `/bin/sh -c`가 먼저 실행되고, 그 셸이 다시 지정한 명령을 실행합니다.

```dockerfile
ENTRYPOINT python /app/server.py
```

```text
PID 1: /bin/sh -c "python /app/server.py"
└─ 실제 서버 프로세스 (PID 1이 아님)
```

이 경우 컨테이너의 PID 1은 파이썬 서버가 아니라 셸입니다. `docker stop`이 보내는 SIGTERM은 기본적으로 컨테이너의 PID 1 프로세스로 전달되는데, 셸이 이 시그널을 자식 프로세스(서버)로 전달하지 않으면 서버는 SIGTERM을 받지 못한 채 남아 있다가, 유예 시간이 지난 뒤 결국 SIGKILL로 강제 종료될 수 있습니다. 그래서 정상 종료 절차(1장 7절 참고)를 기대한다면 이 차이가 실제로 문제가 됩니다.

특별한 이유가 없다면 `ENTRYPOINT`와 `CMD`는 배열 형식을 사용해, 서버 프로세스 자신이 PID 1이 되도록 합니다.

시작 전에 준비 작업(설정 파일 생성, 마이그레이션 등)이 필요해 셸 스크립트를 거쳐야 한다면, 그 스크립트의 마지막에서 `exec`로 서버를 실행합니다.

```sh
#!/bin/sh
set -eu

# 시작 준비 작업
exec "$@"
```

`exec`는 새 프로세스를 만들지 않고, **현재 셸 프로세스를 지정한 프로그램으로 그대로 교체**합니다. 그 결과 스크립트를 실행하던 셸의 PID가 그대로 서버의 PID가 되어, 서버가 PID 1로서 종료 신호와 종료 상태를 직접 받게 됩니다.

다음처럼 주 서버를 백그라운드로 보내고 스크립트가 먼저 끝나 버리면 문제가 생깁니다.

```sh
# 잘못된 예
python /app/server.py &
exit 0
```

이 경우 스크립트(PID 1)가 `exit 0`으로 즉시 종료되므로, 그 자식으로 남아 있던 서버 프로세스가 아직 실행 중이더라도 컨테이너 자체는 종료된 것으로 처리됩니다. 컨테이너의 수명은 PID 1 프로세스의 수명과 묶여 있기 때문입니다.

## 9. 포트 게시

컨테이너 안에서 서버가 `0.0.0.0:8080`에 바인드해도(1장 3절 참고), 그 사실만으로 호스트에서 그 포트에 접근할 수 있게 되지는 않습니다. 컨테이너는 자신만의 네트워크 네임스페이스를 가지고 있어서, 명시적으로 연결해 주지 않으면 호스트의 네트워크와 분리되어 있기 때문입니다.

```sh
docker run -p 127.0.0.1:18080:8080 image
```

이 옵션은 `호스트주소:호스트포트:컨테이너포트` 형식으로, 호스트의 `127.0.0.1:18080`으로 들어온 연결을 컨테이너의 `8080` 포트로 전달하라는 뜻입니다.

```text
호스트 127.0.0.1:18080 → 컨테이너 8080
```

호스트 주소를 생략하면(`-p 18080:8080`) 기본적으로 호스트의 모든 인터페이스(`0.0.0.0`)에서 들어오는 연결을 전달합니다. `-p`를 아예 지정하지 않으면 컨테이너 밖에서는 해당 포트로 접근할 수 없습니다.

앞서 4절에서 다룬 `EXPOSE 8080`은 이미지에 “이 컨테이너는 8080 포트를 쓸 예정”이라는 정보만 기록할 뿐, 실제로 호스트 포트를 여는 것은 `docker run -p`나 Docker Compose의 `ports` 설정입니다.

## 10. 비특권 실행과 파일 권한

서비스가 80번이나 443번처럼 1024 미만의 낮은 포트를 컨테이너 안에서 직접 열 필요가 없다면(리눅스에서 1024 미만 포트를 여는 데는 보통 관리자 권한이 필요합니다), 비특권 사용자로 실행하기 쉽습니다. 예를 들어 애플리케이션이 내부적으로 8080 같은 높은 포트를 쓰고, 앞단의 리버스 프록시나 로드밸런서가 80/443 포트와 8080 포트 사이의 변환을 맡는 구성을 쓸 수 있습니다.

이미지를 비특권 사용자로 실행할 때는 다음을 확인합니다.

- 그 사용자가 애플리케이션 코드와 설정 파일을 읽을 수 있습니다.
- 그 사용자가 실제로 쓰기가 필요한 디렉터리에만 쓸 수 있고, 나머지는 읽기 전용으로 남아 있습니다.
- 컨테이너에 마운트한 볼륨의 UID/GID가 컨테이너 안에서 실행되는 사용자의 UID/GID와 맞습니다. 맞지 않으면 파일이 존재해도 “Permission denied” 오류가 날 수 있습니다. 예를 들어 이미지가 `USER 65532:65532`로 실행되는데 마운트한 볼륨 디렉터리의 소유자가 `root(0:0)`이고 다른 사용자의 쓰기를 막아 두었다면, 컨테이너 안 프로세스는 그 볼륨에 쓸 수 없습니다.
- 시작 시 관리자 권한으로 준비 작업(예: 낮은 포트 바인드)을 한 뒤 권한을 낮추는 방식을 쓴다면, 최종적으로 서버 프로세스 자체는 관리자 권한으로 남아 있지 않아야 합니다.

전체 디렉터리에 무조건 `chmod -R 777`을 사용해 권한 문제를 우회하지 않습니다. 이는 모든 사용자에게 읽기·쓰기·실행 권한을 열어 주는 것과 같아서 불필요한 보안 위험을 만듭니다. 실제로 쓰기가 필요한 경로와 그 경로를 써야 하는 사용자를 확인해 필요한 만큼만 권한을 부여합니다.

## 11. 기본 진단 명령

```sh
docker image ls
docker image inspect image-name
docker image history image-name

docker ps -a
docker inspect container-name
docker logs container-name
docker exec container-name ps -ef
```

이 명령들은 대략 다음을 확인하는 데 씁니다.

- `docker image ls`: 로컬에 있는 이미지 목록과 크기를 봅니다.
- `docker image inspect`: 이미지의 상세 설정(ENTRYPOINT, ENV, 계층 정보 등)을 JSON으로 봅니다.
- `docker image history`: 어떤 Dockerfile 명령이 어떤 계층을 만들었는지, 각 계층의 크기를 봅니다. 6절에서 다룬 “계층이 지워지지 않고 남는” 문제를 확인할 때 유용합니다.
- `docker ps -a`: 실행 중이거나 중지된 컨테이너 목록을 봅니다(`-a` 없이는 실행 중인 것만 보입니다).
- `docker inspect`: 컨테이너의 네트워크, 마운트, 환경변수 같은 상세 상태를 봅니다.
- `docker logs`: 컨테이너의 표준 출력·표준 오류를 봅니다(1장 8절 참고).
- `docker exec ... ps -ef`: 실행 중인 컨테이너 **안에서** 새 명령을 실행해, 그 안의 프로세스 목록을 봅니다.

`docker exec`으로 컨테이너 안에 들어가 무언가를 설치하거나 수정해도, 그 변경은 3절에서 설명한 **그 컨테이너의 쓰기 계층에만** 남습니다. 컨테이너를 삭제하거나 이미지를 다시 빌드해서 만든 새 컨테이너에는 반영되지 않으므로, 영구적으로 필요한 변경은 반드시 Dockerfile과 빌드 입력에 반영해야 합니다.

```sh
docker stop container-name
docker kill container-name
```

`docker stop`은 컨테이너의 PID 1 프로세스에 SIGTERM을 보낸 뒤, 정해진 유예 시간(기본 10초, `-t` 옵션으로 조절 가능) 안에 프로세스가 종료되지 않으면 SIGKILL을 보내 강제 종료합니다. `docker kill`은 기본적으로 곧바로 SIGKILL을 보내 유예 시간 없이 즉시 종료시킵니다.

## 12. 자주 생기는 오해

### “이미지를 실행하면 이미지가 바뀝니다”

아닙니다.

컨테이너 실행 중에 파일을 바꾸면 그 변경은 3절에서 설명한 **그 컨테이너 전용 쓰기 계층**에만 기록됩니다. 이미지를 구성하는 읽기 전용 계층들은 바뀌지 않으며, 같은 이미지로 만든 다른 컨테이너에는 영향을 주지 않습니다.

### “`EXPOSE`가 방화벽을 열어 줍니다”

아닙니다.

`EXPOSE`는 이미지에 “이 포트를 쓸 예정”이라는 정보를 남기는 설명용 메타데이터일 뿐입니다. 실제로 호스트에서 그 포트에 접근할 수 있게 하려면 `docker run -p`나 Docker Compose의 `ports` 설정이 필요합니다(9절 참고).

### “컨테이너 안에서 패키지를 설치하면 수정이 완료됩니다”

아닙니다.

`docker exec`으로 컨테이너 안에서 설치한 패키지는 그 컨테이너의 쓰기 계층에만 남습니다(11절 참고). 컨테이너를 삭제하거나 새로 만들면 그 변경은 사라집니다. 여러 환경에서 반복적으로 필요한 변경이라면 Dockerfile을 고쳐서 이미지 자체에 반영해야 합니다.

### “`latest`는 항상 최신 안전 버전을 뜻합니다”

아닙니다.

`latest`는 Docker가 특별히 관리하는 예약어가 아니라, 태그를 생략했을 때 기본으로 쓰이는 **평범한 태그 이름**입니다. 이미지를 배포하는 쪽이 `latest` 태그를 어떤 이미지에 붙일지는 전적으로 그쪽의 관례에 달려 있으며, 시간이 지나면 다른(때로는 더 이전 버전의) 이미지를 가리키도록 다시 지정될 수도 있습니다. 재현 가능한 빌드나 배포가 필요하다면 구체적인 버전 태그나 다이제스트를 사용하는 편이 안전합니다.

## 확인 문제

1. 이미지와 컨테이너는 각각 어떤 상태(정적 파일 묶음 vs 실행 중인 프로세스)를 가지며, 하나의 이미지로 여러 컨테이너를 만들면 이미지 계층과 쓰기 계층은 각각 공유됩니까, 독립적입니까?
2. 컨테이너를 `docker stop`으로 중지했을 때와 `docker rm`으로 삭제했을 때 쓰기 계층은 각각 어떻게 됩니까?
3. 시작 스크립트 마지막에 `exec "$@"`를 쓰는 이유는 무엇이며, 이를 생략하고 서버를 `&`로 백그라운드 실행한 뒤 스크립트를 종료하면 어떤 문제가 생깁니까?
4. `EXPOSE 8080`과 `-p 127.0.0.1:18080:8080`은 각각 무엇을 하며, 왜 `EXPOSE`만으로는 호스트에서 접근할 수 없습니까?
5. Dockerfile에서 `requirements.txt`(또는 의존성 파일)를 소스 코드보다 먼저 `COPY`하면 어떤 캐시 효과가 있으며, 반대로 소스 코드를 먼저 복사하면 무엇이 달라집니까?
6. 비특권 사용자로 컨테이너를 실행할 때, 마운트한 볼륨의 소유자 UID/GID가 컨테이너 안 실행 사용자와 다르면 어떤 문제가 생길 수 있습니까?
7. `RUN apt-get install -y build-essential`과 `RUN apt-get remove -y build-essential`을 서로 다른 `RUN`으로 나누어도 이미지 크기가 줄어들지 않는 이유를 유니온 파일시스템 관점에서 설명해 보세요.
8. 컨테이너가 가상 머신과 달리 호스트 커널을 공유한다는 사실은, 컨테이너의 격리를 보안 경계로 여길 때 어떤 한계로 이어집니까?
