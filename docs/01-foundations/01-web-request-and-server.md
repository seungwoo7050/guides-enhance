# 웹 요청과 서버

이 장에서는 서버를 단순히 “요청을 받는 프로그램”이라고만 설명하지 않습니다. 클라이언트가 어떤 주소와 포트로 연결하는지, 운영체제가 어떤 프로세스의 소켓으로 연결을 전달하는지, 그리고 DNS·TCP·TLS·HTTP·애플리케이션 오류가 어느 단계에서 서로 갈리는지 순서대로 확인합니다.

이 장의 TCP 설명은 주로 **HTTP/1.1과 HTTP/2**를 기준으로 합니다. HTTP/3은 TCP 대신 QUIC(UDP 기반 전송 프로토콜)을 사용하므로 연결 과정이 다릅니다. 다만 “이름 해석 → 연결 수립 → 보안 협상 → HTTP 요청/응답 → 애플리케이션 처리”처럼 계층별로 문제를 나누어 진단하는 원칙은 같습니다.

완료 후에는 다음 내용을 자신의 말로 설명할 수 있어야 합니다.

> 서버는 보통 특정 주소와 포트에 바인드한 소켓에서 연결이나 요청을 기다리는 프로세스이고, HTTP는 클라이언트와 서버가 교환하는 요청과 응답의 의미와 형식을 정하는 애플리케이션 계층 프로토콜입니다.

## 1. URL을 나누어 보기

다음 URL을 예로 듭니다.

```text
https://example.test:443/articles?id=10
```

| 부분 | 값 | 의미 |
|---|---|---|
| 스킴 | `https` | HTTPS를 사용한다는 뜻입니다. HTTP/1.1·HTTP/2에서는 보통 TCP 연결 위에 TLS를 수립한 뒤 HTTP를 교환합니다. |
| 호스트 | `example.test` | 연결할 대상을 식별하는 이름입니다. 일반적으로 DNS 또는 로컬 이름 해석을 통해 IP 주소를 얻습니다. |
| 포트 | `443` | 대상 호스트에서 어떤 서비스의 통신 끝점(endpoint)에 연결할지 지정합니다. |
| 경로 | `/articles` | HTTP 요청에서 서버가 처리할 자원 또는 라우트를 나타냅니다. |
| 쿼리 | `id=10` | 경로와 함께 서버에 전달하는 추가 매개변수입니다. |

`https`의 기본 포트는 443이므로 실제 URL에서는 `:443`을 생략할 수 있습니다.

```text
https://example.test/articles?id=10
```

HTTP/1.1 또는 HTTP/2를 TCP 위에서 사용하는 경우, 브라우저나 `curl`의 통신 과정을 단순화하면 다음과 같습니다.

```text
호스트 이름을 IP 주소로 해석
→ 대상 IP와 포트로 TCP 연결
→ TLS 핸드셰이크
→ HTTP 요청 전송
→ HTTP 응답 수신
```

각 단계는 서로 다른 종류의 실패를 만들 수 있습니다.

- **이름 해석 실패**: 호스트 이름에 대응하는 IP 주소를 얻지 못했습니다.
- **연결 거부(connection refused)**: 대상 호스트까지는 도달했고 운영체제도 즉시 응답했지만, 해당 주소·포트에서 TCP 연결을 받는 소켓이 없거나 방화벽이 명시적으로 거부했습니다.
- **연결 시간 초과(timeout)**: 연결 시도에 대해 정해진 시간 안에 성공이나 명시적 거부를 받지 못했습니다. 패킷이 중간에서 버려지거나 방화벽이 응답하지 않는 경우 등이 원인이 될 수 있습니다.
- **TLS 오류**: TCP 연결은 만들어졌지만 인증서 검증, 지원 암호군, TLS 버전, 서버 이름 검증 등의 과정에서 실패했습니다.
- **HTTP 404**: 연결과 HTTP 통신은 성립했고, 서버가 요청한 자원이나 라우트를 찾지 못했다고 응답했습니다.
- **HTTP 500**: 서버가 HTTP 요청을 받았지만 요청 처리 중 내부 오류가 발생했다고 응답했습니다.

따라서 **404와 500은 네트워크 연결 실패가 아닙니다.** HTTP 서버와 통신하여 유효한 HTTP 응답까지 받은 상태입니다.

## 2. 클라이언트와 서버

클라이언트와 서버는 프로그램의 고정된 종류라기보다 **통신에서 맡는 역할**을 나타냅니다.

- 클라이언트는 연결이나 요청을 시작합니다.
- 서버는 미리 정한 통신 끝점에서 연결이나 요청을 기다리고 응답합니다.

TCP 서버의 기본 흐름을 단순화하면 다음과 같습니다.

```text
클라이언트                              서버
   │                                     │
   │                                     │ socket
   │                                     │ bind
   │                                     │ listen
   │ TCP connect                         │
   ├────────────────────────────────────▶│ accept
   │                                     │
   │ HTTP request                        │ read
   ├────────────────────────────────────▶│
   │                                     │ 요청 처리
   │ HTTP response                       │ write
   │◀────────────────────────────────────┤
```

서버 쪽 용어를 구분하면 다음과 같습니다.

- `socket`: 통신에 사용할 소켓을 만듭니다.
- `bind`: 소켓을 로컬 주소와 포트에 연결합니다.
- `listen`: 해당 소켓을 들어오는 TCP 연결을 기다리는 상태로 만듭니다.
- `accept`: 대기 중인 연결 하나를 받아 실제 통신에 사용할 새 연결 소켓을 얻습니다.

웹 브라우저와 `curl`은 HTTP 클라이언트가 될 수 있습니다. Nginx는 HTTP 서버로 동작할 수 있습니다. MariaDB도 서버 프로세스이지만 HTTP가 아니라 MariaDB/MySQL 프로토콜을 사용합니다. PHP-FPM은 일반적으로 FastCGI 요청을 받습니다.

즉, **“서버가 살아 있다”**라는 말만으로는 상태를 충분히 설명할 수 없습니다. 최소한 다음을 구분해야 합니다.

```text
어떤 프로세스가 실행 중인가?
→ 어떤 주소와 포트에서 기다리는가?
→ 어떤 프로토콜을 받는가?
→ 실제 요청에 기대한 응답을 하는가?
```

예를 들어 MariaDB가 정상 실행 중이어도 `http://localhost:3306/`이 정상적인 웹 서비스가 되는 것은 아닙니다. 같은 포트에 연결할 수 있더라도 서로 기대하는 프로토콜이 다르기 때문입니다.

## 3. 주소와 포트

서버가 연결을 받으려면 운영체제에 **어느 로컬 주소와 포트에서 받을 것인지** 알려 주어야 합니다. 이를 보통 “바인드한다(bind)”라고 표현합니다.

### `127.0.0.1`

`127.0.0.1`은 IPv4 루프백 주소입니다. 네트워크 패킷을 외부 인터페이스로 보내지 않고 현재 네트워크 환경 내부에서 자기 자신과 통신할 때 사용합니다.

특히 컨테이너나 네트워크 네임스페이스를 사용할 때는 “자기 자신”의 범위가 중요합니다.

```text
호스트의 127.0.0.1      → 호스트 자신
컨테이너 A의 127.0.0.1 → 컨테이너 A 자신
컨테이너 B의 127.0.0.1 → 컨테이너 B 자신
```

따라서 컨테이너 A에서 `127.0.0.1:3306`으로 연결하면 호스트나 다른 컨테이너가 아니라 **컨테이너 A 내부의 3306 포트**를 찾습니다.

### `localhost`

`localhost`는 IP 주소 자체가 아니라 **이름**입니다. 보통 시스템 설정에 따라 루프백 주소로 해석됩니다.

예를 들어 다음 중 하나 또는 둘 다로 해석될 수 있습니다.

```text
127.0.0.1
::1
```

`::1`은 IPv6 루프백 주소입니다.

따라서 다음 두 개념은 구분해야 합니다.

```text
localhost   이름
127.0.0.1   IPv4 주소
::1         IPv6 주소
```

환경에 따라 `localhost`가 먼저 `::1`로 해석될 수 있으므로, 서버가 IPv4에만 바인드되어 있으면 `localhost` 접속과 `127.0.0.1` 접속의 결과가 다르게 보일 수도 있습니다.

### `0.0.0.0`

서버의 **바인드 주소**로 사용되는 `0.0.0.0`은 “이 호스트가 가진 모든 IPv4 인터페이스에서 들어오는 연결을 받겠다”는 뜻입니다.

예를 들어 서버가 다음처럼 바인드되었다고 가정합니다.

```text
0.0.0.0:8080
```

이는 대략 다음 인터페이스로 들어오는 연결을 모두 받을 수 있다는 의미입니다.

```text
127.0.0.1:8080
192.168.0.20:8080
기타 로컬 IPv4 인터페이스의 :8080
```

단, 실제 외부 접근 가능 여부는 방화벽, 라우팅, 컨테이너 포트 게시 설정 등에도 영향을 받습니다.

`0.0.0.0`은 보통 **서버가 어디에서 받을지를 지정하는 와일드카드 주소**이지, 클라이언트가 특정 원격 호스트를 식별하는 주소가 아닙니다.

따라서 클라이언트는 보통 다음처럼 실제 접속 대상을 사용합니다.

```text
127.0.0.1
192.168.0.20
example.test
service-name
```

### 포트

IP 주소가 호스트의 네트워크 인터페이스를 식별한다면, 포트는 그 호스트 안에서 어떤 통신 끝점으로 전달할지를 구분하는 숫자입니다.

예를 들어 한 호스트에서 다음 서비스가 동시에 실행될 수 있습니다.

```text
127.0.0.1:8080  HTTP 서버
127.0.0.1:3306  MariaDB
127.0.0.1:9000  PHP-FPM
```

다만 **포트 번호 자체가 프로토콜을 강제하지는 않습니다.**

예를 들어 8080 포트에서 HTTP를 사용하는 것은 흔하지만 필수 규칙은 아닙니다. 프로그램이 원한다면 다른 프로토콜을 사용할 수도 있습니다.

중요한 것은 다음 세 가지가 서로 맞아야 한다는 점입니다.

```text
클라이언트가 연결하는 주소
클라이언트가 연결하는 포트
양쪽이 기대하는 프로토콜
```

## 4. TCP와 HTTP

TCP는 두 프로세스 사이에 **신뢰성 있고 순서가 보장되는 바이트 스트림**을 제공합니다.

TCP가 직접 이해하는 개념은 다음과 같은 HTTP 개념과 다릅니다.

```text
TCP가 모르는 것
- URL
- GET / POST
- HTTP 헤더
- JSON
- HTTP 상태 코드
```

TCP 입장에서는 애플리케이션이 보내는 데이터는 바이트의 연속일 뿐입니다.

HTTP는 그 바이트를 다음처럼 **요청과 응답의 구조와 의미**로 해석하는 규칙을 정합니다.

```http
GET /healthz HTTP/1.1
Host: 127.0.0.1:8080
Accept: */*

```

서버는 다음과 같이 응답할 수 있습니다.

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 3

ok
```

여기서 빈 줄 하나가 헤더 영역과 본문을 구분합니다.

따라서 다음 두 질문은 서로 다릅니다.

```text
TCP 연결이 가능한가?
HTTP 요청에 올바르게 응답하는가?
```

TCP 연결이 성공해도 애플리케이션이 정상이라고 결론 내릴 수 없는 이유는 다음과 같습니다.

- 해당 포트가 HTTP가 아닌 다른 프로토콜을 사용할 수 있습니다.
- HTTP 서버가 `500 Internal Server Error`를 반환할 수 있습니다.
- HTTP 상태는 200이지만 본문 데이터가 잘못될 수 있습니다.
- 특정 경로만 고장 났을 수 있습니다.
- 인증이나 데이터베이스 같은 뒤쪽 의존성이 실패할 수 있습니다.

따라서 헬스 체크나 진단에서는 **검사하려는 기능 수준에 맞는 검증**을 해야 합니다.

```text
프로세스 존재 확인
< 포트 수신 확인
< TCP 연결 확인
< HTTP 상태 확인
< HTTP 본문 또는 기능 확인
```

오른쪽으로 갈수록 실제 애플리케이션 동작을 더 많이 검증합니다.

## 5. HTTP 요청과 응답

HTTP 통신의 핵심은 클라이언트가 **요청(request)** 을 보내고 서버가 **응답(response)** 을 돌려주는 것입니다.

### 요청 메서드

대표적인 HTTP 메서드는 다음과 같습니다.

- `GET`: 자원을 조회할 때 주로 사용합니다.
- `POST`: 데이터를 제출하거나 서버에 어떤 처리를 요청할 때 주로 사용합니다.
- `PUT`: 일반적으로 특정 자원의 전체 표현을 생성하거나 교체하는 의미로 사용합니다.
- `PATCH`: 자원의 일부 변경을 요청할 때 사용합니다.
- `DELETE`: 자원의 삭제를 요청합니다.

다만 메서드 이름만 보고 실제 서버 동작을 완전히 알 수는 없습니다. 서버 구현이 메서드의 의미를 어기도록 작성될 수도 있기 때문입니다.

예를 들어 다음과 같은 구현은 기술적으로 가능하지만 좋지 않은 설계입니다.

```text
GET /delete-user?id=10
```

`GET`은 HTTP 의미상 서버 상태를 변경하지 않는 **안전한(safe) 메서드**로 취급되어야 하므로 삭제 동작에 사용해서는 안 됩니다.

즉, 메서드에는 프로토콜 수준의 의미가 있지만 **실제 코드가 그 의미를 지켜야 합니다.**

### 헤더와 본문

HTTP 헤더는 요청이나 응답의 부가 정보를 전달합니다.

예를 들어 JSON 요청은 다음처럼 보일 수 있습니다.

```http
POST /users HTTP/1.1
Host: example.test
Content-Type: application/json
Content-Length: 16

{"name":"Alice"}
```

주요 헤더의 의미는 다음과 같습니다.

- `Content-Type`: 본문 데이터의 미디어 타입을 설명합니다.
- `Content-Length`: 전송되는 본문의 바이트 길이를 나타냅니다.
- `Authorization`: 인증 자격 증명이나 토큰을 전달할 수 있습니다.
- `Accept`: 클라이언트가 어떤 응답 형식을 받을 수 있는지 나타냅니다.

`Content-Type: application/json`이라고 적혀 있다고 해서 본문이 자동으로 올바른 JSON이 되는 것은 아닙니다.

예를 들어 다음 요청은 선언과 실제 본문이 일치하지 않습니다.

```http
Content-Type: application/json

not-json
```

서버는 보통 다음을 별도로 검증해야 합니다.

```text
Content-Type이 허용되는가?
→ 본문을 해당 형식으로 파싱할 수 있는가?
→ 파싱된 값의 구조가 요구사항에 맞는가?
```

문법적으로 잘못된 JSON이나 필수 필드가 빠진 요청처럼 **클라이언트 요청 자체가 유효하지 않은 경우**에는 보통 4xx 응답을 사용합니다.

`Authorization`, 세션 쿠키, API 키 같은 민감 정보는 로그에 그대로 남기지 않아야 합니다.

### 상태 코드

HTTP 상태 코드는 서버가 요청을 어떻게 처리했는지 요약합니다.

| 범위 | 의미 | 대표 예 |
|---|---|---|
| 1xx | 처리 진행 관련 정보 | 100 |
| 2xx | 요청을 성공적으로 처리 | 200, 201, 204 |
| 3xx | 리디렉션 또는 조건부·캐시 관련 응답 | 301, 302, 304 |
| 4xx | 요청을 그대로 처리할 수 없음 | 400, 401, 403, 404 |
| 5xx | 서버 측에서 정상 처리를 완료하지 못함 | 500, 502, 503, 504 |

몇 가지 코드를 구분하면 다음과 같습니다.

- `200 OK`: 요청이 정상적으로 처리되었습니다.
- `201 Created`: 요청 처리 결과 새 자원이 만들어졌습니다.
- `204 No Content`: 요청은 성공했지만 응답 본문이 없습니다.
- `400 Bad Request`: 요청 문법이나 입력이 잘못되었습니다.
- `401 Unauthorized`: 이름과 달리 보통 “인증이 필요하거나 인증에 실패했다”는 의미로 사용합니다.
- `403 Forbidden`: 서버가 요청자를 식별했더라도 해당 동작을 허용하지 않습니다.
- `404 Not Found`: 요청 대상 자원이나 라우트를 찾지 못했습니다.
- `500 Internal Server Error`: 서버 내부 처리 중 오류가 발생했습니다.
- `502 Bad Gateway`: 게이트웨이 또는 프록시가 뒤쪽 서버(upstream)에서 유효한 응답을 얻지 못했습니다.
- `503 Service Unavailable`: 서버가 일시적으로 요청을 처리할 수 없습니다.
- `504 Gateway Timeout`: 게이트웨이 또는 프록시가 뒤쪽 서버의 응답을 제한 시간 안에 받지 못했습니다.

특히 `502`는 “Nginx 자체가 죽었다”는 뜻이 아닙니다. 오히려 Nginx 같은 게이트웨이가 클라이언트에게 HTTP 응답을 보낼 만큼은 동작하고 있지만, 뒤쪽 서버와의 통신에 실패했다는 뜻일 수 있습니다.

예를 들어 다음과 같은 원인이 가능합니다.

```text
upstream 프로세스가 실행되지 않음
upstream 주소나 포트가 잘못됨
이름 해석 실패
프로토콜 불일치
upstream이 연결 직후 비정상 종료
잘못된 응답 형식 수신
```

## 6. HTTPS가 추가하는 검사

HTTPS는 HTTP 통신에 TLS를 사용하여 전송 내용을 보호합니다.

HTTP/1.1과 HTTP/2에서는 보통 다음 순서가 됩니다.

```text
TCP 연결
→ TLS 핸드셰이크
→ 암호화된 연결 위에서 HTTP 통신
```

TLS는 대표적으로 다음 기능을 제공합니다.

- 전송 중인 내용을 암호화합니다.
- 데이터가 통신 중 임의로 변경되었는지 검증합니다.
- 인증서를 사용해 클라이언트가 서버의 신원을 검증할 수 있게 합니다.

서버는 일반적으로 **개인키(private key)** 와 **인증서(certificate)** 를 사용합니다.

### 개인키

개인키는 서버가 비밀로 보관해야 합니다. 외부에 공개되면 안 됩니다.

### 인증서

인증서에는 대표적으로 다음 정보가 포함됩니다.

- 서버의 공개키
- 인증서가 유효한 호스트 이름
- 유효 기간
- 발급자 정보
- 디지털 서명

실제 인증서 필드는 인증서 형식과 발급 방식에 따라 더 많을 수 있습니다.

클라이언트는 일반적으로 다음을 검사합니다.

```text
인증서의 신뢰 체인이 유효한가?
접속한 호스트 이름과 인증서 이름이 일치하는가?
인증서 유효 기간 안에 있는가?
서명이 올바른가?
```

### 자체 서명 인증서

자체 서명 인증서(self-signed certificate)도 암호화된 TLS 연결 자체는 만들 수 있습니다.

하지만 클라이언트가 해당 인증서를 별도로 신뢰하도록 설정하지 않았다면, **그 서버가 신뢰할 수 있는 주체라는 보장까지 자동으로 생기지는 않습니다.**

개발 환경에서 다음과 같이 검증을 끌 수 있습니다.

```sh
curl -k https://localhost:8443/
```

또는 같은 의미의 긴 옵션을 사용할 수 있습니다.

```sh
curl --insecure https://localhost:8443/
```

중요한 점은 `-k`가 인증서를 “신뢰 목록에 추가”하는 것이 아니라 **인증서 검증을 생략하는 옵션**이라는 것입니다.

따라서 운영 환경에서 인증서 문제를 해결하는 방법으로 사용해서는 안 됩니다.

## 7. 서버는 실행 중인 프로세스입니다

디스크에 저장된 프로그램 파일과 현재 실행 중인 프로세스는 구분해야 합니다.

```text
프로그램
  디스크에 저장된 실행 코드

프로세스
  프로그램이 실제로 실행 중인 인스턴스
```

프로세스는 실행 중 다음과 같은 상태를 가집니다.

- PID
- 메모리
- 열린 파일과 소켓
- 환경변수
- 현재 작업 디렉터리
- 사용자와 권한
- 표준 입력·출력·오류 스트림

프로세스 상태는 예를 들어 다음처럼 확인할 수 있습니다.

```sh
ps -o pid,ppid,user,stat,command -p "$pid"
```

### 포그라운드와 백그라운드

일반적인 대화형 셸에서 포그라운드 프로세스는 현재 터미널의 전면 작업으로 실행됩니다. 셸은 보통 그 작업이 종료되거나 정지될 때까지 다음 명령을 실행하지 않습니다.

```sh
python3 server.py
```

명령 뒤에 `&`를 붙이면 셸은 작업을 백그라운드에서 실행하고 프롬프트를 다시 표시합니다.

```sh
python3 server.py &
pid=$!
```

`$!`에는 가장 최근에 백그라운드로 시작한 작업의 PID가 들어갑니다.

컨테이너에서는 보통 주 서버 프로세스를 데몬으로 분리하지 않고 **컨테이너의 주 프로세스로 포그라운드 실행**합니다.

그 이유는 컨테이너의 생명주기가 주 프로세스와 연결되어 있기 때문입니다. 일반적으로 컨테이너의 PID 1 프로세스가 종료되면 컨테이너도 종료 상태가 됩니다.

### 시그널

운영체제는 시그널을 사용해 프로세스에 비동기적인 사건이나 제어 요청을 전달할 수 있습니다.

대표적인 시그널은 다음과 같습니다.

- `SIGTERM`: 정상 종료할 기회를 주면서 종료를 요청합니다.
- `SIGINT`: 대화형 터미널에서 보통 Ctrl-C에 의해 전달됩니다.
- `SIGKILL`: 프로세스가 잡거나 무시하거나 처리할 수 없는 강제 종료입니다.

정상 종료를 요청하려면 다음처럼 사용할 수 있습니다.

```sh
kill -TERM "$pid"
wait "$pid"
```

`wait`는 해당 자식 프로세스가 실제로 종료될 때까지 기다리고 종료 상태를 얻을 수 있게 합니다.

가능하면 처음부터 `SIGKILL`을 사용하지 않는 것이 좋습니다. `SIGTERM`을 처리하는 프로그램은 다음과 같은 정리 작업을 수행할 수 있기 때문입니다.

```text
새 요청 받기 중단
진행 중인 요청 마무리
버퍼 flush
파일과 소켓 정리
임시 상태 저장
```

`SIGKILL`은 이런 정리 기회를 주지 않습니다.

### 종료 상태

프로세스는 종료할 때 정수 형태의 종료 상태(exit status)를 남깁니다.

관례적으로 다음처럼 해석합니다.

```text
0       성공
0 이외  어떤 종류의 실패 또는 특별한 상태
```

직전 명령의 종료 상태는 셸에서 `$?`로 확인할 수 있습니다.

```sh
command
printf 'exit=%s\n' "$?"
```

자동화에서는 사람이 읽는 출력 문자열보다 **종료 상태처럼 프로그램이 기계적으로 판정할 수 있는 신호**를 우선 사용하는 것이 일반적입니다.

다만 종료 코드의 정확한 의미는 프로그램마다 다르므로 해당 명령의 문서를 확인해야 합니다.

## 8. 환경변수, 파일과 표준 스트림

### 환경변수

환경변수는 프로세스가 가진 문자열 형태의 이름-값 설정입니다. 새 프로세스는 일반적으로 부모 프로세스로부터 환경변수를 상속받습니다.

예를 들어 다음 명령은 `python3 server.py` 프로세스에만 `APP_PORT=8080`을 전달합니다.

```sh
APP_PORT=8080 python3 server.py
```

프로그램은 이를 읽어 설정값으로 사용할 수 있습니다.

환경변수는 편리하지만 **그 자체가 비밀 저장소는 아닙니다.**

비밀번호, API 키, 토큰 같은 민감 정보를 환경변수로 사용할 경우 실행 환경, 진단 도구, 오류 보고, 프로세스 덤프, 잘못된 로그 출력 등을 통해 노출될 가능성을 고려해야 합니다.

따라서 다음을 구분하는 습관이 중요합니다.

```text
일반 설정
비밀값(secret)
```

실제 비밀값 관리 방법은 실행 환경과 배포 시스템의 보안 기능에 맞게 선택해야 합니다.

### 표준 스트림

유닉스 계열 프로세스는 일반적으로 시작할 때 다음 세 개의 표준 파일 디스크립터를 가집니다.

| 파일 디스크립터 | 이름 | 일반적 용도 |
|---|---|---|
| 0 | 표준 입력(stdin) | 입력 |
| 1 | 표준 출력(stdout) | 정상 출력 |
| 2 | 표준 오류(stderr) | 오류·진단 출력 |

예를 들어 다음은 표준 출력과 표준 오류를 구분합니다.

```sh
printf 'normal output\n'
printf 'error output\n' >&2
```

컨테이너에서 실행하는 서비스는 로그를 파일 안에만 저장하는 대신 표준 출력과 표준 오류로 보내면 컨테이너 런타임이 이를 수집하기 쉽습니다.

Docker에서는 다음 명령으로 확인할 수 있습니다.

```sh
docker logs <container>
docker compose logs
```

## 9. 기본 진단 순서

문제가 생겼을 때 애플리케이션 내부 코드부터 바로 확인하면 원인을 찾는 데 시간이 오래 걸릴 수 있습니다.

대신 통신 경로를 바깥 단계부터 하나씩 확인합니다.

```text
이름 해석
→ 주소와 포트 설정
→ TCP 연결
→ TLS
→ HTTP 상태와 본문
→ 애플리케이션 처리
→ 뒤쪽 의존성
```

예를 들어 `https://service.example/healthz`가 동작하지 않는다면 다음처럼 질문을 나눌 수 있습니다.

```text
1. service.example 이름을 IP 주소로 해석할 수 있는가?
2. 그 IP의 대상 포트까지 TCP 연결할 수 있는가?
3. TLS 핸드셰이크와 인증서 검증이 성공하는가?
4. HTTP 응답 자체를 받을 수 있는가?
5. 상태 코드는 기대한 값인가?
6. 응답 본문은 기대한 내용인가?
7. 애플리케이션이 DB 같은 의존성과 정상 통신하는가?
```

이 순서의 장점은 **실패 지점을 좁힐 수 있다는 것**입니다.

예를 들어 DNS부터 실패한다면 아직 HTTP 라우팅 코드를 조사할 필요가 없습니다.

### 이름 해석 확인

```sh
getent hosts service-name
```

`getent`는 Linux에서 시스템 이름 해석 설정을 통해 결과를 조회할 때 유용합니다.

### 수신 TCP 포트 확인

```sh
ss -ltnp
```

옵션의 의미는 다음과 같습니다.

```text
-l  listening 소켓만 표시
-t  TCP 소켓 표시
-n  이름 대신 숫자로 표시
-p  가능하면 소켓을 사용하는 프로세스 표시
```

프로세스 정보 조회에는 권한이 필요할 수 있습니다.

특정 포트를 좁혀 볼 수도 있습니다.

```sh
ss -ltnp | grep ':8080'
```

### HTTP 응답 확인

```sh
curl -i http://127.0.0.1:8080/healthz
```

`-i`는 응답 헤더를 본문과 함께 출력합니다.

더 자세한 연결 과정을 보고 싶다면 다음처럼 사용합니다.

```sh
curl -v http://127.0.0.1:8080/healthz
```

HTTPS의 TLS 과정까지 확인하려면 다음을 사용할 수 있습니다.

```sh
curl -v https://localhost:8443/healthz
```

### `curl`의 HTTP 오류 판정

중요한 점은 기본 `curl`이 HTTP 404나 500을 받았다는 이유만으로 항상 실패 종료 상태를 반환하는 것은 아니라는 것입니다.

예를 들어 서버와 통신 자체가 성공해 500 응답을 받으면 기본 설정에서는 `curl` 프로세스의 종료 코드가 0일 수 있습니다.

자동화에서 HTTP 4xx·5xx도 실패로 처리하고 싶다면 다음 옵션을 사용할 수 있습니다.

```sh
curl --fail http://127.0.0.1:8080/healthz
```

또는 에러 본문도 출력하고 싶다면 비교적 최근 curl에서 다음을 사용할 수 있습니다.

```sh
curl --fail-with-body http://127.0.0.1:8080/healthz
```

즉, 다음 두 값은 서로 다른 층의 상태입니다.

```text
curl 프로세스의 종료 상태
HTTP 응답의 상태 코드
```

자동화에서는 어떤 실패를 잡고 싶은지에 따라 둘을 의도적으로 처리해야 합니다.

### TLS 직접 확인

TLS 핸드셰이크와 인증서를 더 직접 확인하려면 다음을 사용할 수 있습니다.

```sh
openssl s_client \
  -connect localhost:8443 \
  -servername localhost \
  </dev/null
```

`-servername`은 TLS의 SNI(Server Name Indication)에 사용할 서버 이름을 지정합니다. 하나의 IP에서 여러 HTTPS 사이트를 서비스하는 환경에서는 특히 중요합니다.

### macOS에서 수신 포트 확인

macOS에서는 `ss` 대신 `lsof`를 사용하는 경우가 많습니다.

```sh
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

## 10. 자주 생기는 오해

### “포트가 열리면 애플리케이션이 정상입니다”

아닙니다.

포트가 열려 있다는 것은 보통 해당 주소·포트에서 어떤 프로세스가 연결을 받을 준비가 되어 있다는 뜻에 가깝습니다.

그 이후에도 다음은 실패할 수 있습니다.

```text
HTTP 프로토콜 처리
라우팅
인증
비즈니스 로직
데이터베이스 접근
응답 데이터 생성
```

실제 기능 상태를 확인하려면 적절한 HTTP 요청과 응답 내용까지 확인해야 합니다.

### “404는 네트워크 오류입니다”

아닙니다.

HTTP 404를 받았다는 것은 일반적으로 다음 단계가 이미 성공했다는 뜻입니다.

```text
이름 해석
연결
필요한 경우 TLS
HTTP 요청 전송
HTTP 응답 수신
```

따라서 404 문제에서는 네트워크 연결보다 요청 경로, 라우팅 규칙, 정적 파일 위치, 프록시 경로 변환 등을 먼저 확인하는 편이 적절합니다.

### “`localhost`는 항상 물리 호스트입니다”

아닙니다.

`localhost`는 **명령을 실행한 네트워크 환경의 자기 자신**을 가리키는 이름으로 이해하는 편이 정확합니다.

컨테이너 안에서 실행한 명령의 `localhost`는 그 컨테이너를 가리킵니다.

예를 들어 다음 구조에서:

```text
호스트
├─ 컨테이너 A: 웹 서버
└─ 컨테이너 B: 데이터베이스
```

컨테이너 A가 데이터베이스에 연결할 때 다음 주소는 보통 잘못된 대상입니다.

```text
localhost:3306
```

이는 컨테이너 A 자신의 3306 포트를 찾기 때문입니다.

컨테이너 네트워크에서 데이터베이스 서비스 이름이 `db`라면 보통 다음처럼 연결합니다.

```text
db:3306
```

### “`0.0.0.0`은 외부에서 접속할 때 쓰는 서버 주소입니다”

보통 그렇게 이해하면 안 됩니다.

`0.0.0.0`은 서버가 **모든 로컬 IPv4 인터페이스에서 연결을 받도록 바인드할 때** 사용하는 와일드카드 주소입니다.

클라이언트는 실제 대상의 IP 주소나 호스트 이름을 사용합니다.

### “강제 종료가 가장 확실합니다”

`SIGKILL`은 프로세스를 즉시 종료시키는 데는 강력하지만, 정상적인 종료 과정은 거치지 않습니다.

따라서 일반적인 종료 순서는 다음과 같이 생각할 수 있습니다.

```text
SIGTERM으로 정상 종료 요청
→ 일정 시간 동안 종료 대기
→ 필요할 때만 SIGKILL
```

이렇게 해야 진행 중인 요청, 버퍼, 임시 파일, 연결 상태 등을 정리할 기회를 줄 수 있습니다.

### “HTTP 상태 코드와 명령의 종료 코드는 같습니다”

다릅니다.

예를 들어 서버가 HTTP 500을 반환해도 `curl` 자체는 서버와 정상적으로 통신했다고 판단하여 기본 설정에서 종료 코드 0을 반환할 수 있습니다.

```text
HTTP 상태 코드
  서버가 HTTP 요청 처리 결과를 표현

프로세스 종료 코드
  curl 같은 로컬 프로그램이 자신의 실행 결과를 표현
```

자동화에서는 두 값을 혼동하지 않아야 합니다.
