# 웹 요청과 서버

이 장에서는 서버를 “요청을 받는 어떤 프로그램” 정도로 뭉뚱그리지 않습니다. 클라이언트가 어느 주소와 포트로 연결하고, 운영체제가 어떤 프로세스에 연결을 넘기며, HTTP 오류와 연결 실패가 어디에서 갈리는지 확인합니다.

완료 후에는 다음 문장을 자신의 말로 설명할 수 있어야 합니다.

> 서버는 특정 주소와 포트에서 연결을 기다리는 프로세스이며, HTTP는 그 연결 위에서 요청과 응답의 형식을 정합니다.

## 1. URL을 나누어 보기

다음 URL을 예로 듭니다.

```text
https://example.test:443/articles?id=10
```

| 부분 | 값 | 의미 |
|---|---|---|
| 스킴 | `https` | HTTP를 TLS 연결 위에서 사용합니다. |
| 호스트 | `example.test` | 연결할 서버의 주소를 찾기 위한 이름입니다. |
| 포트 | `443` | 서버가 연결을 받는 지점입니다. |
| 경로 | `/articles` | 서버에 요청할 자원이나 라우트입니다. |
| 쿼리 | `id=10` | 경로와 함께 전달하는 추가 입력입니다. |

브라우저나 `curl`은 대략 다음 순서로 요청을 보냅니다.

```text
호스트 이름을 IP 주소로 해석
→ TCP 연결
→ TLS 핸드셰이크
→ HTTP 요청 전송
→ HTTP 응답 수신
```

각 단계의 실패는 서로 다릅니다.

- DNS 실패: IP 주소를 얻지 못했습니다.
- 연결 거부: 대상 주소에는 도달했지만 포트에서 연결을 받는 프로세스가 없습니다.
- 연결 시간 초과: 네트워크나 방화벽이 응답하지 않거나 서버가 제때 처리하지 못했습니다.
- TLS 오류: TCP 연결 뒤 인증서나 암호화 협상에서 실패했습니다.
- HTTP 404: 앞 단계는 성공했고, 서버가 해당 경로를 찾지 못했다고 응답했습니다.
- HTTP 500: 서버가 요청을 받았지만 처리 중 오류가 발생했습니다.

404와 500은 네트워크 연결 실패가 아닙니다. 유효한 HTTP 응답을 받은 상태입니다.

## 2. 클라이언트와 서버

클라이언트는 연결을 시작하고 요청을 보냅니다. 서버는 연결을 기다렸다가 요청을 읽고 응답합니다.

```text
클라이언트                          서버
   │                                 │
   │ TCP connect                     │ bind + listen
   ├────────────────────────────────▶│
   │ HTTP request                    │ accept + read
   ├────────────────────────────────▶│
   │                                 │ 요청 처리
   │ HTTP response                   │
   │◀────────────────────────────────┤
```

웹 브라우저와 `curl`은 HTTP 클라이언트입니다. Nginx는 HTTP 서버입니다. MariaDB도 서버 프로세스지만 HTTP가 아니라 MariaDB/MySQL 프로토콜을 사용합니다. PHP-FPM은 FastCGI 요청을 받습니다.

따라서 “서버가 살아 있다”는 말만으로는 부족합니다. 어떤 프로세스가 어떤 프로토콜에 응답하는지 지정해야 합니다.

## 3. 주소와 포트

### `127.0.0.1`

IPv4 루프백 주소입니다. 같은 네트워크 네임스페이스 안에서만 접근할 수 있습니다. 컨테이너 안의 `127.0.0.1`은 호스트가 아니라 그 컨테이너 자신을 가리킵니다.

### `localhost`

일반적으로 루프백 주소로 해석되는 이름입니다. 환경에 따라 `127.0.0.1`이나 `::1`이 될 수 있습니다. 이름과 IP 주소는 같은 개념이 아닙니다.

### `0.0.0.0`

서버의 수신 설정에서 모든 IPv4 인터페이스를 뜻합니다. 컨테이너 밖에서 전달된 연결을 받아야 하는 서버는 보통 컨테이너 안에서 `0.0.0.0`에 바인드합니다.

클라이언트가 연결할 주소로 `0.0.0.0`을 사용한다는 뜻은 아닙니다. 클라이언트는 `127.0.0.1`, 실제 IP 주소나 서비스 이름을 사용합니다.

### 포트

포트는 한 주소 안에서 연결을 받을 프로세스를 구분합니다.

```text
127.0.0.1:8080  HTTP 서버
127.0.0.1:3306  MariaDB
127.0.0.1:9000  PHP-FPM
```

포트 번호가 프로토콜을 강제하지는 않습니다. 관례적인 기본값일 뿐입니다. 클라이언트와 서버가 같은 주소와 포트를 사용하도록 설정되어 있어야 합니다.

## 4. TCP와 HTTP

TCP는 순서가 보장된 바이트 스트림을 제공합니다. TCP 자체는 URL, JSON, 상태 코드를 모릅니다. HTTP가 그 바이트를 요청과 응답으로 해석하는 규칙을 정합니다.

```http
GET /healthz HTTP/1.1
Host: 127.0.0.1:8080
Accept: */*

```

```http
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 3

ok
```

포트에 연결할 수 있다는 사실만으로 HTTP가 정상이라고 판단할 수 없습니다.

- 다른 프로토콜이 같은 포트를 사용할 수 있습니다.
- HTTP 서버가 500을 반환할 수 있습니다.
- 상태 코드는 200이지만 본문이 잘못될 수 있습니다.

검사하려는 기능에 맞는 프로토콜과 응답 내용을 확인해야 합니다.

## 5. HTTP 요청과 응답

### 요청 메서드

- `GET`: 자원을 조회합니다.
- `POST`: 데이터를 제출하거나 처리를 요청합니다.
- `PUT`: 일반적으로 자원 전체를 교체합니다.
- `PATCH`: 자원의 일부를 변경합니다.
- `DELETE`: 자원 삭제를 요청합니다.

메서드 이름만으로 안전한 동작이 보장되지는 않습니다. 실제 처리는 서버 코드가 결정합니다.

### 헤더와 본문

`Content-Type`은 본문의 형식을 알려 줍니다. `Content-Length`는 본문 길이를 나타냅니다. `Authorization`에는 인증 정보가 들어갈 수 있으므로 로그에 그대로 남기지 않습니다.

서버는 `Content-Type`과 본문을 함께 검증해야 합니다. JSON이라고 선언했지만 파싱할 수 없는 본문을 보냈다면 400 계열 응답이 적절합니다.

### 상태 코드

| 범위 | 의미 | 예 |
|---|---|---|
| 2xx | 요청 처리 성공 | 200, 201, 204 |
| 3xx | 리디렉션 또는 캐시 관련 응답 | 301, 302, 304 |
| 4xx | 요청을 처리할 수 없음 | 400, 401, 403, 404 |
| 5xx | 서버 처리 실패 | 500, 502, 503, 504 |

502는 게이트웨이가 뒤쪽 서버에서 유효한 응답을 얻지 못했다는 뜻입니다. 원인은 프로세스 종료, 이름 해석 실패, 포트 불일치, 프로토콜 불일치 등 여러 가지일 수 있습니다.

## 6. HTTPS가 추가하는 검사

HTTPS는 HTTP를 TLS 연결 위에서 전달합니다. TLS는 전송 내용을 암호화하고, 클라이언트가 연결한 서버의 인증서를 검증할 수 있게 합니다.

서버는 개인키와 인증서를 사용합니다.

- 개인키는 외부에 공개하면 안 됩니다.
- 인증서에는 공개키, 도메인 이름, 유효기간과 발급자 정보가 들어갑니다.
- 클라이언트는 인증서 체인, 이름과 유효기간을 확인합니다.

자체 서명 인증서도 암호화 연결을 만들 수 있지만, 클라이언트가 별도로 신뢰하도록 설정하지 않았다면 서버 신원을 확인해 주지 않습니다.

```sh
curl -k https://localhost:8443/
```

`-k`는 인증서를 신뢰하게 만드는 옵션이 아니라 검증을 끄는 옵션입니다. 로컬 개발에서만 제한적으로 사용합니다.

## 7. 서버는 실행 중인 프로세스입니다

프로그램은 디스크에 저장된 코드입니다. 프로세스는 그 프로그램이 실행되어 PID, 메모리, 열린 파일, 환경변수와 표준 스트림을 가진 상태입니다.

```sh
ps -o pid,ppid,user,stat,command -p "$pid"
```

### 포그라운드와 백그라운드

현재 셸이 직접 기다리는 프로세스는 포그라운드에서 실행됩니다. `&`를 붙이면 셸은 프로세스를 백그라운드로 보내고 다음 명령을 받습니다.

```sh
python3 server.py &
pid=$!
```

컨테이너에서는 주 서버 프로세스를 포그라운드에 두는 것이 중요합니다. 주 프로세스가 끝나면 컨테이너도 끝납니다.

### 시그널

- `SIGTERM`: 정상 종료를 요청합니다.
- `SIGINT`: 보통 Ctrl-C로 전달됩니다.
- `SIGKILL`: 프로세스가 처리할 수 없는 강제 종료입니다.

```sh
kill -TERM "$pid"
wait "$pid"
```

가능하면 SIGTERM으로 종료해 진행 중인 작업과 파일 버퍼를 정리할 시간을 줍니다.

### 종료 상태

프로세스는 종료할 때 정수 상태를 반환합니다. 보통 0은 성공, 0이 아닌 값은 실패입니다.

```sh
command
printf 'exit=%s\n' "$?"
```

자동화에서는 출력 문자열보다 종료 상태를 우선 사용합니다.

## 8. 환경변수, 파일과 표준 스트림

환경변수는 부모 프로세스가 자식 프로세스에 전달하는 문자열 설정입니다.

```sh
APP_PORT=8080 python3 server.py
```

비밀번호를 환경변수로 전달하면 프로세스 정보나 진단 출력에 노출될 수 있습니다. 일반 설정과 비밀값은 따로 관리합니다.

프로세스는 기본적으로 다음 스트림을 가집니다.

- 표준 입력: 파일 디스크립터 0
- 표준 출력: 파일 디스크립터 1
- 표준 오류: 파일 디스크립터 2

컨테이너 서비스는 로그를 표준 출력과 표준 오류로 보내면 `docker logs`와 `docker compose logs`로 확인하기 쉽습니다.

## 9. 기본 진단 순서

문제가 생기면 깊은 기능부터 확인하지 않습니다.

```text
이름 해석
→ 주소와 포트
→ TCP 연결
→ TLS
→ HTTP 상태와 본문
→ 애플리케이션 처리
```

자주 쓰는 명령은 다음과 같습니다.

```sh
getent hosts service-name
ss -ltnp
curl -i http://127.0.0.1:8080/healthz
curl -v https://localhost:8443/healthz
openssl s_client -connect localhost:8443 -servername localhost </dev/null
```

macOS에서는 수신 포트를 다음처럼 확인할 수 있습니다.

```sh
lsof -nP -iTCP:8080 -sTCP:LISTEN
```

## 10. 자주 생기는 오해

### 포트가 열리면 애플리케이션이 정상입니다

TCP 연결만 가능한 상태일 수 있습니다. 실제 요청 경로와 응답 내용을 확인해야 합니다.

### 404는 네트워크 오류입니다

404를 받았다면 연결과 HTTP 교환은 성공했습니다. 요청 경로와 라우팅을 확인합니다.

### `localhost`는 항상 호스트입니다

`localhost`는 명령을 실행한 네트워크 네임스페이스 자신을 가리킵니다. 컨테이너 안에서는 해당 컨테이너입니다.

### 강제 종료가 가장 확실합니다

프로세스를 즉시 없애지만 정상 종료와 데이터 정리 기회를 제거합니다. SIGTERM부터 사용합니다.
