# 문제 조건과 반례

## 학습 목표

이 문서를 읽고 나면 다음을 할 수 있어야 합니다.

- 자연어로 주어진 문제를 검증 가능한 입력·출력 조건으로 바꿉니다.
- 입력 크기와 값의 범위를 알고리즘 선택의 근거로 사용합니다.
- 후보 구현과 핵심 로직을 공유하지 않는 단순한 기준 계산(reference implementation)을 만듭니다.
- 구현이 암묵적으로 가정한 조건을 직접 깨는 최소 반례를 설계합니다.
- 무작위 검사에서 발견한 실패를 재현 가능한 회귀 테스트로 남깁니다.

## 선행지식

다음 내용을 알고 있어야 합니다.

- 함수의 매개변수와 반환값
- 조건문과 반복문
- 배열이나 리스트의 index
- 작은 입력에 대해 프로그램의 실행 상태를 손으로 추적하는 방법
- `O(n)`, `O(n²)`처럼 입력 크기에 따른 연산량 증가를 표현하는 기초적인 시간 복잡도 표기

## 핵심 관점

알고리즘 문제를 푼다는 것은 곧바로 정답 코드를 떠올리는 일이 아닙니다. 먼저 **무엇이 정답인지 명확히 정의하고**, 그 정의를 만족하는지 확인할 방법을 준비해야 합니다.

구현 전에 다음 네 가지를 순서대로 정합니다.

```text
조건: 어떤 입력을 받고 어떤 결과를 반환합니까?
기준: 작은 입력에서 정답을 가장 단순하고 확실하게 계산하는 방법은 무엇입니까?
비용: 입력이 커질 때 시간과 메모리가 얼마나 필요합니까?
증거: 구현이 조건을 지켰다는 사실을 어떤 테스트와 비교로 확인합니까?
```

이 네 항목은 서로 연결됩니다.

- **조건**이 불명확하면 무엇을 테스트해야 하는지 결정할 수 없습니다.
- **기준 계산**이 없으면 복잡한 최적화 구현의 결과가 맞는지 비교하기 어렵습니다.
- **비용**을 계산하지 않으면 정답은 맞지만 제한 시간 안에 끝나지 않는 알고리즘을 선택할 수 있습니다.
- **증거**가 없으면 구현이 샘플 입력 몇 개에서만 우연히 맞는지 구분하기 어렵습니다.

## 1. 문제를 입력·출력 조건으로 정리합니다

자연어 문제에는 구현에 필요한 조건이 생략되어 있는 경우가 많습니다. 구현을 시작하기 전에 문제를 함수의 계약(contract)처럼 다시 작성합니다.

다음 항목을 확인합니다.

```text
입력으로 허용하는 값:
반환값의 의미:
정상 결과가 만족해야 하는 조건:
답이 여러 개일 때의 선택 순서:
답이 없을 때의 결과:
잘못된 입력을 처리하는 위치:
입력 크기와 값의 범위:
허용 시간과 메모리:
```

여기서 **정상 결과의 조건**은 단순히 "정답을 반환한다"가 아니라, 반환값을 검사할 수 있을 정도로 구체적이어야 합니다.

예를 들어 다음 문제를 생각해 봅시다.

> 배열에서 합이 `target`이 되는 두 원소의 index를 반환합니다.

이 문장만으로는 함수의 동작이 완전히 정해지지 않습니다.

- 같은 위치를 두 번 사용할 수 있습니까?
- 두 index의 반환 순서는 중요합니까?
- 같은 값이 여러 번 있으면 어느 index를 선택합니까?
- 답이 여러 개라면 어떤 쌍을 반환합니까?
- 답이 없으면 무엇을 반환합니까?
- 입력 배열을 수정해도 됩니까?
- 두 값을 더할 때 정수 범위를 넘을 수 있습니까?

예를 들어 다음 두 입력에는 여러 답이 존재할 수 있습니다.

```text
values = [1, 4, 2, 3]
target = 5
```

가능한 쌍은 `(0, 1)`과 `(2, 3)`입니다.

따라서 문제 조건이 다음처럼 정해져야 테스트도 결정할 수 있습니다.

```text
서로 다른 두 index를 사용합니다.
i < j인 형태로 반환합니다.
가능한 쌍 중 (i, j)가 사전순으로 가장 작은 쌍을 반환합니다.
답이 없으면 None을 반환합니다.
입력 배열은 수정하지 않습니다.
```

`(i, j)`의 **사전순(lexicographical order)** 비교란 먼저 `i`가 작은 쌍을 우선하고, `i`가 같다면 `j`가 작은 쌍을 우선한다는 뜻입니다.

예를 들어 다음 순서입니다.

```text
(0, 3) < (1, 2) < (1, 5)
```

이처럼 반환 규칙을 정확히 정해야 서로 다른 구현이 같은 문제를 풀고 있는지 비교할 수 있습니다.

### 잘못된 입력과 답이 없는 입력은 구분합니다

다음 두 상황은 의미가 다릅니다.

```text
정상 입력이지만 조건을 만족하는 답이 없음
입력 자체가 문제의 허용 범위를 위반함
```

예를 들어 입력 배열은 정상인데 두 수의 합이 `target`이 되는 쌍이 없다면 이것은 **정상적인 실패 결과**입니다.

반면 문제에서 값이 음수가 아니어야 하는데 음수가 들어왔다면 이것은 **잘못된 입력**입니다.

이 둘을 모두 `-1` 같은 하나의 값으로 표현하면 호출자는 원인을 구분하기 어렵습니다. API가 허용한다면 서로 다른 반환값이나 예외로 구분하는 편이 명확합니다.

## 2. 입력 제한을 목표 비용으로 바꿉니다

입력 제한은 단순한 부가 정보가 아니라 알고리즘 선택의 중요한 근거입니다.

다음 표는 절대적인 규칙이 아니라 첫 후보를 고르기 위한 대략적인 신호입니다. 실제 허용 시간, 언어, 상수 비용, 입력 형태에 따라 결과는 달라질 수 있습니다.

| 입력 크기 | 먼저 검토할 비용 |
| ---: | --- |
| `n <= 20` | 부분집합, 순열, 백트래킹 |
| `n <= 2,000` | `O(n²)` |
| `n <= 200,000` | `O(n log n)` 또는 `O(n)` |
| 큰 희소 그래프 | `O(V+E)` 또는 `O((V+E) log V)` |

여기서 `V`는 정점 수, `E`는 간선 수입니다.

예를 들어 모든 원소 쌍을 검사하는 알고리즘은 대략 다음 수의 쌍을 확인합니다.

```text
n(n - 1) / 2
```

`n = 2,000`이면 약 200만 쌍이지만, `n = 200,000`이면 약 200억 쌍입니다.

따라서 같은 `O(n²)` 알고리즘이라도 입력 크기에 따라 현실적으로 사용할 수 있는지가 크게 달라집니다.

### 반복문 개수만 세지 않습니다

시간 복잡도를 판단할 때 겉으로 보이는 반복문만 세면 실제 비용을 놓칠 수 있습니다.

예를 들어 다음 코드는 반복문 하나처럼 보입니다.

```python
for i in range(n):
    sorted_values = sorted(values)
```

하지만 `sorted(values)`가 매번 `O(n log n)`이므로 전체 비용은 대략 다음과 같습니다.

```text
O(n² log n)
```

다음 연산도 반복문 내부에 있으면 전체 비용에 포함해야 합니다.

- 정렬
- 배열이나 문자열 전체 복사
- 문자열 slice
- 동적 배열 앞쪽 원소 삭제
- 연결 리스트가 아닌 배열에서의 중간 삽입·삭제
- 비교 함수 자체의 비용
- hash key 계산 비용
- 재귀 호출 깊이
- 결과를 출력하거나 저장하는 비용

### 메모리 비용도 함께 계산합니다

시간만 줄이고 메모리를 과도하게 사용하는 알고리즘도 제한을 위반할 수 있습니다.

예를 들어 `n x n` 테이블은 `O(n²)`개의 원소를 저장합니다.

```text
n = 10,000
원소 수 = 100,000,000
```

원소 하나가 8 byte라면 데이터만 약 800 MB가 필요합니다. 실제 프로그램에서는 컨테이너 오버헤드나 다른 데이터도 사용하므로 더 많은 메모리가 필요할 수 있습니다.

따라서 알고리즘 후보를 비교할 때는 최소한 다음을 함께 적는 습관이 좋습니다.

```text
시간 복잡도:
추가 공간 복잡도:
입력 자체를 수정하는지:
재귀 깊이:
```

## 3. 느리더라도 독립적인 기준 계산을 먼저 만듭니다

복잡한 알고리즘을 검증할 때는 작은 입력에서 정답을 확실하게 계산하는 **기준 계산(reference implementation, oracle)** 을 따로 준비하면 유용합니다.

기준 계산은 빠를 필요가 없습니다. 대신 다음 조건이 중요합니다.

1. 작은 입력에서는 결과가 명백하게 맞아야 합니다.
2. 후보 구현과 핵심 알고리즘을 공유하지 않아야 합니다.
3. 가능하면 구현 구조도 단순해야 합니다.

예를 들어 다음과 같이 서로 다른 계산 방법을 사용할 수 있습니다.

| 후보 구현 | 독립적인 기준 계산 |
| --- | --- |
| 누적 합 | 질의할 때마다 해당 구간을 직접 더합니다. |
| 이분 탐색 | 앞에서부터 선형 탐색합니다. |
| Dijkstra | 작은 그래프에서 Floyd–Warshall을 사용합니다. |
| 구간 선택 greedy | 모든 부분집합을 검사합니다. |
| KMP | 각 시작 위치에서 문자를 직접 비교합니다. |
| 최대 유량 | 작은 그래프에서 가능한 모든 source-side cut을 열거합니다. |

예를 들어 `lower_bound`를 검증한다고 가정합니다.

후보 구현이 이분 탐색이라면 기준 계산은 다음처럼 단순한 선형 탐색으로 만들 수 있습니다.

```python
def reference_lower_bound(values, target):
    for i, value in enumerate(values):
        if value >= target:
            return i
    return len(values)
```

후보 구현과 기준 계산이 같은 방식으로 작성되지 않았기 때문에, 후보 구현의 경계 조건 실수를 기준 계산까지 그대로 복제할 가능성이 줄어듭니다.

### 기준 계산이 후보와 같은 결함을 공유하지 않게 합니다

다음처럼 작성하면 두 구현이 같은 실수를 공유할 수 있습니다.

```text
후보 구현
  └─ normalize_input()
  └─ custom_compare()
  └─ 핵심 알고리즘

기준 계산
  └─ normalize_input()
  └─ custom_compare()
  └─ 다른 형태의 핵심 알고리즘
```

만약 `normalize_input()`이나 `custom_compare()`에 결함이 있다면 후보와 기준 계산이 동시에 같은 잘못된 결과를 만들 수 있습니다.

특히 다음 요소를 공유할 때 주의합니다.

- parser
- 정렬 기준
- 비교 함수
- 그래프 전처리
- 중복 제거 규칙
- index 변환
- overflow를 포함할 수 있는 산술 helper

모든 코드를 완전히 중복 작성해야 한다는 뜻은 아닙니다. 다만 **검증하려는 핵심 성질과 관련된 로직은 가능한 한 독립적으로 계산해야 합니다.**

## 4. 반례는 구현의 가정을 하나씩 깨야 합니다

반례(counterexample)는 구현이 틀렸음을 보여 주는 입력입니다.

좋은 반례를 만들려면 먼저 구현이 암묵적으로 기대하는 조건을 적어 봅니다.

```text
입력이 비어 있지 않습니다.
모든 값이 서로 다릅니다.
간선 가중치는 음수가 아닙니다.
그래프가 연결되어 있습니다.
답이 하나뿐입니다.
합이 정수 범위를 넘지 않습니다.
재귀 깊이가 충분히 작습니다.
```

이러한 문장은 문제 조건이 아니라 **구현의 가정**일 수 있습니다.

문제에서 보장하지 않은 가정을 구현이 사용한다면 그 가정을 깨는 입력이 반례 후보가 됩니다.

예를 들어 구현이 다음처럼 작성되었다고 생각해 봅시다.

```python
def first_equal(values, target):
    left = 0
    right = len(values) - 1

    while left <= right:
        mid = (left + right) // 2

        if values[mid] == target:
            return mid
        if values[mid] < target:
            left = mid + 1
        else:
            right = mid - 1

    return -1
```

이 코드는 `target`을 찾기는 하지만, 중복 값이 있을 때 **첫 번째 위치를 반환한다는 보장**은 없습니다.

문제 조건이 "`target` 이상인 첫 위치를 반환한다"라면 다음 입력이 반례가 될 수 있습니다.

```text
values = [1, 2, 2, 2]
target = 2
```

기대 결과:

```text
1
```

위 구현은 중간 원소를 즉시 반환하므로 `2`를 반환합니다. 따라서 값 자체를 찾는 데는 성공하지만, "첫 위치"라는 계약은 위반합니다.

이 차이가 중요합니다. 테스트는 "어떤 `2`를 찾았는가?"가 아니라 실제 계약인 **첫 위치를 반환했는가?**를 검사해야 합니다.

### 자주 확인할 입력 범주

다음 입력들은 많은 알고리즘에서 경계 조건과 숨은 가정을 드러냅니다.

- 빈 입력
- 최소 크기 입력
- 원소가 하나뿐인 입력
- 같은 값의 반복
- 모든 값이 같은 입력
- 이미 정렬된 입력
- 역순 입력
- 답이 첫 위치에 있는 경우
- 답이 마지막 위치에 있는 경우
- 답이 없는 경우
- 여러 최적해가 존재하는 경우
- 동점 처리 규칙이 필요한 경우
- 연결되지 않은 그래프
- 자기 loop
- 중복 간선
- 0
- 음수
- 매우 큰 값
- 긴 공통 prefix
- 반복 문자열

모든 문제에 이 목록을 기계적으로 적용할 필요는 없습니다. 문제와 구현의 가정에 관련된 항목을 선택합니다.

## 5. 반례는 한 번에 하나의 가정을 겨냥합니다

큰 입력 하나가 여러 문제를 동시에 포함하면 실패 원인을 찾기 어렵습니다.

예를 들어 다음 입력이 실패한다고 가정합니다.

```text
[1000000, -7, -7, 3, 0, 3, 999999]
```

이 입력에는 다음 요소가 동시에 있습니다.

- 큰 값
- 음수
- 중복
- 0
- 여러 위치의 같은 값

실패 원인이 "중복 값을 잘못 처리함"이라면 더 작은 입력으로 줄이는 편이 좋습니다.

```text
[2, 2]
```

또는 문제 조건에 따라 다음처럼 줄일 수 있습니다.

```text
[1, 2, 2]
```

이제 실패가 중복 처리와 직접 연결되어 있음을 쉽게 확인할 수 있습니다.

좋은 최소 반례는 다음 질문에 빠르게 답할 수 있어야 합니다.

```text
어떤 조건을 기대했습니까?
구현은 어떤 가정을 했습니까?
이 입력이 그 가정을 어떻게 깨뜨립니까?
실제 결과와 기대 결과는 무엇입니까?
```

## 6. 실패 입력을 최소화합니다

무작위 검사나 복잡한 테스트에서 실패를 발견하면, 그 입력을 그대로 분석하기보다 먼저 최소화하는 것이 좋습니다.

다음 변환을 반복하면서 **같은 종류의 실패가 계속 발생하는지** 확인합니다.

1. 원소, 정점, 간선을 줄입니다.
2. 값의 절댓값을 줄입니다.
3. 실패와 무관한 중복을 제거합니다.
4. 문자열의 앞뒤를 줄입니다.
5. 실패와 관계없는 연산을 삭제합니다.
6. 그래프라면 필요하지 않은 정점과 간선을 제거합니다.

예를 들어 다음 문자열에서 parser가 실패한다고 가정합니다.

```text
abcabcabcXabcabc
```

앞부분과 뒷부분을 계속 제거한 뒤 다음 입력에서도 같은 문제가 발생한다면,

```text
X
```

실패 원인은 반복 prefix와 관련이 없었다는 것을 알 수 있습니다.

반대로 다음처럼 줄여야만 실패가 유지된다면,

```text
abcX
```

공통 prefix나 경계 위치가 문제의 일부일 가능성이 높습니다.

이 과정을 **shrinking** 또는 **test case reduction**이라고 부르기도 합니다.

최소화의 목적은 단순히 입력 길이를 가장 작게 만드는 것이 아니라, **실패 원인을 설명하는 데 불필요한 요소를 제거하는 것**입니다.

## 7. 무작위 검사는 재현할 수 있어야 합니다

무작위 검사는 사람이 직접 떠올리지 못한 조합을 찾는 데 유용합니다.

하지만 다음과 같은 테스트는 실패 후 원인을 다시 확인하기 어렵습니다.

```python
for _ in range(10000):
    values = random_input()
    assert candidate(values) == reference(values)
```

실패한 입력을 출력하지 않고 seed도 저장하지 않았다면 다음 실행에서는 다른 입력이 만들어질 수 있습니다.

따라서 무작위 검사는 다음 규칙을 지킵니다.

- seed를 고정하거나 기록합니다.
- 작은 입력부터 시작합니다.
- 실패한 실제 입력을 출력하거나 저장합니다.
- 사용한 seed도 함께 기록합니다.
- 후보와 기준 계산에 같은 내용의 독립 복사본을 전달합니다.
- 발견한 실패 입력을 고정 회귀 테스트로 추가합니다.

예를 들면 다음과 같습니다.

```python
import random

seed = 20260829
rng = random.Random(seed)

for case_index in range(1000):
    values = [rng.randint(-5, 5) for _ in range(rng.randint(0, 8))]

    candidate_input = list(values)
    reference_input = list(values)

    actual = candidate(candidate_input)
    expected = reference(reference_input)

    if actual != expected:
        print("seed =", seed)
        print("case =", case_index)
        print("input =", values)
        print("actual =", actual)
        print("expected =", expected)
        raise AssertionError("candidate differs from reference")
```

독립 복사본을 전달하는 이유는 후보 구현이 입력을 수정했을 때 기준 계산이 변경된 입력을 받는 문제를 막기 위해서입니다.

예를 들어 후보 구현이 내부에서 정렬을 수행하면,

```python
candidate(values)
reference(values)
```

처럼 같은 객체를 전달했을 때 기준 계산은 원래 입력이 아니라 이미 정렬된 입력을 보게 될 수 있습니다.

### 무작위 검사는 증명이 아닙니다

무작위 검사에서 100만 개의 입력을 통과해도 아직 검사하지 않은 입력에서 실패할 수 있습니다.

무작위 검사의 역할은 다음과 같습니다.

```text
정확성을 증명하는 도구 X
예상하지 못한 반례를 찾는 도구 O
```

따라서 무작위 검사는 다음과 함께 사용하는 것이 좋습니다.

- 문제 조건에 직접 대응하는 예제
- 경계값 테스트
- 구현의 가정을 깨는 반례
- 작은 입력에 대한 기준 계산 비교
- 알고리즘이 맞는 이유에 대한 논리적 설명 또는 증명

## 8. 기준 계산과 무작위 검사를 함께 사용합니다

가장 실용적인 검증 방법 중 하나는 작은 입력을 많이 생성한 뒤 후보 구현과 기준 계산의 결과를 비교하는 것입니다.

구조는 다음과 같습니다.

```text
작은 입력 생성
    ↓
후보 구현 실행
    ↓
독립적인 기준 계산 실행
    ↓
결과 비교
    ↓
불일치하면 입력과 seed 저장
    ↓
실패 입력 최소화
    ↓
고정 회귀 테스트로 추가
```

예를 들어 `lower_bound` 구현을 검증한다면 입력 크기를 작게 제한하고 중복 값을 자주 생성하는 편이 좋습니다.

```python
import random

def reference_lower_bound(values, target):
    for i, value in enumerate(values):
        if value >= target:
            return i
    return len(values)

seed = 7
rng = random.Random(seed)

for _ in range(1000):
    values = sorted(
        rng.randint(-3, 3)
        for _ in range(rng.randint(0, 10))
    )
    target = rng.randint(-4, 4)

    assert lower_bound(values, target) == reference_lower_bound(values, target)
```

값의 범위를 `-3`부터 `3`처럼 좁게 잡은 이유는 중복이 자주 발생하도록 하기 위해서입니다.

무작위 검사는 단순히 "랜덤한 값을 많이 넣는 것"이 아니라, **깨뜨리고 싶은 가정이 자주 나타나도록 입력 분포를 설계하는 것**이 중요합니다.

## 9. 조건, 반례, 회귀 테스트를 연결합니다

테스트는 임의로 추가하는 것이 아니라 문제 조건에서 직접 파생시키는 것이 좋습니다.

예를 들어 계약이 다음과 같다고 가정합니다.

```text
정렬된 배열에서 target 이상인 첫 index를 반환합니다.
그런 원소가 없으면 len(values)를 반환합니다.
중복 값이 허용됩니다.
빈 배열도 허용됩니다.
```

그러면 최소한 다음 테스트가 필요합니다.

| 조건 | 대표 입력 | 기대 결과 |
| --- | --- | ---: |
| 빈 배열 | `[], 3` | `0` |
| 첫 원소가 답 | `[3, 5], 3` | `0` |
| 중간 위치가 답 | `[1, 3, 5], 2` | `1` |
| 중복에서 첫 위치 | `[1, 2, 2, 2, 3], 2` | `1` |
| 모든 값이 작음 | `[1, 2], 5` | `2` |
| 모든 값이 큼 | `[5, 6], 1` | `0` |

이렇게 하면 각 테스트가 어떤 조건을 검증하는지 분명해집니다.

버그가 발견되었다면 해당 실패 입력을 수정 후 삭제하지 말고 회귀 테스트로 남깁니다.

**회귀 테스트(regression test)** 는 이미 발견하여 수정한 결함이 나중의 코드 변경으로 다시 나타나지 않는지 확인하는 테스트입니다.

---

## 연결 구현

[`verified-algorithms`](../../exercises/verified-algorithms/)의 다음 API에서 이 과정을 확인합니다.

### `lower_bound`

중복 값에서 임의의 일치 위치가 아니라 **첫 삽입 위치**, 즉 `target` 이상인 첫 원소의 index를 반환해야 합니다.

따라서 다음과 같은 중복 입력이 중요합니다.

```text
values = [1, 2, 2, 2, 4]
target = 2
expected = 1
```

### `select_intervals`

시작 시간이 빠른 구간부터 선택하는 규칙은 일반적으로 최대 개수의 서로 겹치지 않는 구간을 보장하지 않습니다.

작은 입력에서는 모든 부분집합을 검사하는 기준 계산을 만들어 greedy 결과와 비교할 수 있습니다.

이때 기준 계산은 느리지만, 입력 크기를 작게 제한하면 정답 판별용으로 충분합니다.

### `bellman_ford`

음수 cycle이 존재한다는 사실만으로 항상 시작점의 최단 경로가 무효가 되는 것은 아닙니다.

다음을 구분해야 합니다.

```text
시작점에서 도달 가능한 음수 cycle
시작점에서 도달할 수 없는 음수 cycle
```

시작점에서 도달할 수 없는 cycle은 해당 시작점에서의 최단 경로 결과에 영향을 주지 않습니다.

따라서 음수 cycle 관련 테스트는 "cycle이 존재하는가?"뿐 아니라 "시작점에서 그 cycle에 도달 가능한가?"까지 포함해야 합니다.

## 완료 기준

다음을 모두 만족하면 구현을 시작하거나 최적화 구현을 신뢰할 준비가 된 것입니다.

- 입력과 출력의 의미를 문장으로 설명할 수 있습니다.
- 답이 여러 개일 때의 선택 규칙이 명확합니다.
- 정상 입력에서 답이 없는 경우와 잘못된 입력을 구분합니다.
- 입력 크기에서 선택한 알고리즘의 시간 복잡도가 왜 필요한지 설명할 수 있습니다.
- 후보 구현과 핵심 로직을 공유하지 않는 기준 계산을 작성합니다.
- 구현의 특정 가정 하나를 깨는 최소 반례를 남깁니다.
- 무작위 검사의 seed와 실패 입력을 다시 실행할 수 있게 보존합니다.
- 발견한 실패 입력을 고정 회귀 테스트로 추가합니다.

## 실패 신호

다음 중 하나라도 해당하면 구현 조건이나 검증 방법을 더 정리해야 합니다.

- 답이 없을 때의 결과를 설명하지 못합니다.
- 답이 여러 개일 때 어떤 결과가 맞는지 설명하지 못합니다.
- 입력 제한에서 단순 풀이가 왜 부족한지 계산하지 못합니다.
- 후보 구현과 기준 계산이 같은 핵심 알고리즘을 사용합니다.
- 후보와 기준 계산이 검증 대상과 관련된 helper를 과도하게 공유합니다.
- 샘플 외의 실패 입력을 하나도 만들지 못합니다.
- 구현이 의존하는 가정을 적어 보지 않았습니다.
- 무작위 검사에 고정 또는 기록된 seed가 없습니다.
- 실패한 실제 입력을 보존하지 않습니다.
- 수정한 버그의 입력을 회귀 테스트로 남기지 않습니다.
