# 편집·컴파일·실행

C 프로그램을 작성할 때 가장 먼저 익혀야 할 것은 문법 자체보다 **소스 파일을 실행 가능한 프로그램으로 만드는 과정**입니다.

일반적인 작업 흐름은 다음과 같습니다.

```text
소스 코드 작성·수정
→ 파일 저장
→ 컴파일 및 링크
→ 경고·오류 확인
→ 실행
→ 출력과 종료 상태 확인
```

소스 파일과 실행 파일은 서로 다른 파일입니다. 소스 코드를 수정하더라도 이미 만들어진 실행 파일의 내용이 자동으로 바뀌지는 않습니다. 따라서 수정한 코드를 실행하려면 **파일을 저장한 뒤 다시 컴파일해야 합니다**.

또한 다음 두 사실은 서로 다릅니다.

- **컴파일에 성공했다**: 컴파일러와 링커가 실행 파일을 만들 수 있었다는 뜻입니다.
- **프로그램이 올바르게 동작한다**: 실행 결과가 프로그램의 요구사항과 일치한다는 뜻입니다.

컴파일에 성공한 프로그램도 잘못된 결과를 출력하거나 실행 중 비정상 종료할 수 있습니다.

> 아래 명령 예시는 Unix/Linux/macOS와 같은 Unix 계열 환경의 셸을 기준으로 합니다.

## 가장 작은 프로그램

```c
#include <stdio.h>

int main(void) {
    puts("hello");
    return 0;
}
```

파일 이름을 `hello.c`로 저장했다면 다음과 같이 컴파일합니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic hello.c -o hello
```

컴파일에 성공하면 현재 디렉터리에 `hello`라는 실행 파일이 만들어집니다.

```sh
./hello
```

실행 결과는 다음과 같습니다.

```text
hello
```

현재 디렉터리에 있는 실행 파일은 보통 `./hello`처럼 **경로를 명시해서** 실행합니다.

여기서 `.`은 현재 디렉터리를 뜻하고, `/`는 경로 구분자이므로 `./hello`는 "현재 디렉터리에 있는 `hello` 파일"이라는 의미입니다.

셸은 명령 이름만 입력했을 때 `PATH` 환경 변수에 등록된 디렉터리에서 실행 파일을 찾습니다. 현재 디렉터리 `.`은 보통 `PATH`에 포함되어 있지 않으므로 다음 명령은 실패할 수 있습니다.

```sh
hello
```

현재 디렉터리를 `PATH`에 자동으로 포함하지 않는 것은 같은 이름의 의도하지 않은 프로그램을 실수로 실행하는 위험을 줄이는 데에도 도움이 됩니다.

## 컴파일 명령 읽기

```sh
cc -std=c11 -Wall -Wextra -Wpedantic hello.c -o hello
```

각 부분의 의미는 다음과 같습니다.

- `cc`: 시스템에서 사용할 수 있는 C 컴파일러 **드라이버**를 실행합니다. 드라이버는 필요한 전처리, 컴파일, 어셈블, 링크 단계를 순서대로 호출합니다.
- `-std=c11`: C 언어의 C11 표준을 기준으로 소스 코드를 해석하도록 지정합니다.
- `-Wall`: 자주 문제가 되는 여러 종류의 경고를 활성화합니다.
- `-Wextra`: `-Wall`에 포함되지 않은 추가 경고를 활성화합니다.
- `-Wpedantic`: 선택한 C 표준을 벗어나는 언어 확장이나 비표준 사용에 대한 진단을 더 엄격하게 출력합니다.
- `hello.c`: 컴파일할 입력 소스 파일입니다.
- `-o hello`: 최종 결과 파일의 이름을 `hello`로 지정합니다.

`-Wall`이라는 이름과 달리 **가능한 모든 경고를 활성화한다는 뜻은 아닙니다**. 실제로 어떤 경고가 포함되는지는 컴파일러에 따라 조금씩 다를 수 있습니다.

경고는 오류와 달리 실행 파일 생성을 막지 않을 수 있습니다. 그러나 경고는 타입 불일치, 잘못된 비교, 사용하지 않는 값 등 실제 버그로 이어질 수 있는 문제를 알려 줄 수 있습니다.

따라서 초보 단계에서는 경고가 나오면 단순히 숨기거나 캐스트로 없애기보다 다음 순서로 처리하는 것이 좋습니다.

```text
경고 메시지 읽기
→ 경고가 발생한 코드 확인
→ 원인 이해
→ 코드 수정
→ 다시 컴파일
```

경고가 항상 버그를 의미하는 것은 아니지만, **왜 발생했는지 설명할 수 없는 경고를 그대로 두지 않는 습관**이 중요합니다.

## 소스 파일과 실행 파일은 별개다

다음 상황을 생각해 봅시다.

처음에 `hello.c`가 다음과 같다고 가정합니다.

```c
puts("hello");
```

컴파일하면 `hello` 실행 파일에는 이 코드에 해당하는 기계어가 들어갑니다.

그 뒤 소스 코드를 다음처럼 바꿉니다.

```c
puts("goodbye");
```

하지만 다시 컴파일하지 않고 기존 실행 파일을 실행하면 다음과 같이 이전 결과가 나올 수 있습니다.

```text
hello
```

이는 컴퓨터가 수정된 `.c` 파일을 직접 실행하는 것이 아니라, **마지막으로 성공적으로 만들어진 실행 파일을 실행하고 있기 때문**입니다.

특히 주의할 점은 **재컴파일이 실패했을 때 이전 실행 파일이 남아 있을 수 있다는 것**입니다. 예를 들어:

```sh
cc -std=c11 -Wall -Wextra -Wpedantic hello.c -o hello
```

이 명령이 오류 때문에 실패했더라도 기존의 `hello` 파일이 삭제되지 않았다면 다음 명령은 이전 버전을 실행할 수 있습니다.

```sh
./hello
```

따라서 컴파일 오류가 발생한 뒤에는 기존 실행 파일의 결과를 새 코드의 결과로 착각하지 않아야 합니다.

## 종료 상태 확인하기

프로세스는 실행을 마칠 때 운영체제에 **종료 상태(exit status)**를 전달합니다. C 프로그램에서는 정상적으로 `main`에서 반환한 값이 종료 상태를 결정하는 데 사용됩니다.

예를 들어:

```c
int main(void) {
    return 7;
}
```

프로그램을 실행한 직후 셸에서 다음과 같이 종료 상태를 확인할 수 있습니다.

```sh
./program
printf '%s\n' "$?"
```

`$?`는 **바로 직전에 실행한 명령의 종료 상태**를 나타내는 셸 변수입니다.

따라서 다음처럼 다른 명령을 먼저 실행하면 더 이상 `./program`의 종료 상태를 확인하는 것이 아닙니다.

```sh
./program
echo "다른 명령"
printf '%s\n' "$?"
```

마지막 `printf`가 확인하는 값은 `./program`이 아니라 바로 앞의 `echo` 명령의 종료 상태입니다.

Unix 계열 프로그램에서는 일반적으로 다음 관례를 사용합니다.

```text
0      → 성공
0 이외 → 실패 또는 특별한 상태
```

구체적으로 어떤 실패에 어떤 값을 사용할지는 프로그램이 정합니다.

예를 들어:

```c
int main(int argc, char *argv[]) {
    if (argc != 2) {
        return 2;
    }

    return 0;
}
```

이 프로그램은 인자 개수가 기대와 다르면 `2`, 정상적으로 처리하면 `0`을 반환합니다.

## stdout과 stderr

프로그램은 기본적으로 여러 입출력 스트림을 사용할 수 있습니다. 그중 가장 자주 사용하는 두 출력 스트림은 다음과 같습니다.

- **stdout**: 표준 출력. 정상적인 프로그램 결과를 출력하는 데 사용합니다.
- **stderr**: 표준 오류. 오류, 진단 메시지, 사용법 안내 등을 출력하는 데 사용합니다.

둘 다 기본적으로 터미널에 표시될 수 있기 때문에 화면에서는 비슷하게 보일 수 있지만, **서로 독립된 출력 통로**입니다.

다음 프로그램을 봅시다.

```c
#include <stdio.h>

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "사용법: %s <이름>\n", argv[0]);
        return 2;
    }

    printf("안녕하세요, %s\n", argv[1]);
    return 0;
}
```

인자를 올바르게 전달하면 `printf`가 정상 결과를 stdout에 출력합니다.

```sh
./greet Alice
```

```text
안녕하세요, Alice
```

인자를 전달하지 않으면 `fprintf(stderr, ...)`가 오류 메시지를 stderr에 출력하고 프로그램은 종료 상태 `2`를 반환합니다.

```sh
./greet
```

```text
사용법: ./greet <이름>
```

이 프로그램을 `greet.c`로 저장했다면 먼저 다음처럼 컴파일해야 합니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic greet.c -o greet
```

### stdout과 stderr를 따로 저장하기

셸에서는 두 출력을 서로 다른 파일로 보낼 수 있습니다.

```sh
./greet Alice >out.txt 2>err.txt
```

여기서:

- `>out.txt`: stdout을 `out.txt`에 기록합니다.
- `2>err.txt`: stderr를 `err.txt`에 기록합니다.

`1`은 stdout, `2`는 stderr에 대응하는 파일 디스크립터 번호입니다. stdout의 `1`은 일반적인 `>` 문법에서는 생략할 수 있습니다.

따라서 다음 두 표현은 같은 의미입니다.

```sh
./program >out.txt
./program 1>out.txt
```

`>`와 `2>`는 기본적으로 대상 파일이 이미 존재하면 내용을 덮어씁니다.

stdout과 stderr를 구분하면 프로그램을 다른 프로그램이나 스크립트에서 사용할 때 정상 결과와 오류 메시지를 각각 다르게 처리할 수 있습니다.

## 오류가 난 뒤 부분 결과를 남기지 않기

다음과 같은 프로그램을 생각해 봅시다.

```c
printf("결과: ");
```

이 출력 이후에 입력값이 잘못되었다는 사실을 발견하고 오류로 종료하면, 호출자는 stdout에 남은 `"결과: "`가 유효한 결과인지 판단하기 어려울 수 있습니다.

따라서 가능하다면 다음 순서가 좋습니다.

```text
입력 검증
→ 필요한 처리 수행
→ 성공이 확인되면 정상 결과 출력
```

예를 들어:

```c
#include <stdio.h>

int main(int argc, char *argv[]) {
    if (argc != 2) {
        fprintf(stderr, "사용법: %s <이름>\n", argv[0]);
        return 2;
    }

    printf("안녕하세요, %s\n", argv[1]);
    return 0;
}
```

이 프로그램은 먼저 인자 개수를 검사한 뒤, 정상 입력일 때만 stdout에 결과를 출력합니다.

모든 프로그램에서 결과 출력을 완전히 마지막까지 미룰 수 있는 것은 아니지만, **실패한 실행이 정상 결과처럼 보이지 않게 출력 구조를 설계한다**는 원칙은 중요합니다.

## 셸 인자와 `argc`, `argv`

다음 명령을 실행한다고 가정합니다.

```sh
./program one "two three"
```

셸은 먼저 명령줄을 해석하고 프로그램에 전달할 인자들을 나눕니다.

프로그램은 개념적으로 다음 값을 받습니다.

```text
argc == 3

argv[0] == "./program"
argv[1] == "one"
argv[2] == "two three"
argv[3] == NULL
```

### `argc`

`argc`는 **argument count**의 약자로, 프로그램에 전달된 인자의 개수를 나타냅니다.

일반적인 환경에서는 프로그램 이름에 해당하는 `argv[0]`도 개수에 포함되므로 위 예제의 `argc`는 `3`입니다.

```text
argv[0] → "./program"
argv[1] → "one"
argv[2] → "two three"
```

### `argv`

`argv`는 프로그램에 전달된 문자열들을 가리키는 포인터 배열입니다.

```c
int main(int argc, char *argv[])
```

이 선언에서:

- `argv[0]`은 프로그램을 실행할 때 사용된 이름 또는 경로입니다.
- `argv[1]`부터 실제 명령행 인자들이 들어갑니다.
- 마지막 유효 인자 다음에는 `NULL` 포인터가 있습니다.

따라서 유효한 인자의 인덱스 범위는 일반적으로 다음과 같습니다.

```text
argv[0] ... argv[argc - 1]
```

그리고 다음 값은 항상 인자 배열의 끝을 표시합니다.

```text
argv[argc] == NULL
```

### 따옴표는 왜 사라지는가

명령에서 다음 부분은:

```sh
"two three"
```

셸에게 공백을 기준으로 두 개의 인자로 나누지 말고 하나의 인자로 취급하라는 뜻입니다.

따옴표 자체는 일반적으로 프로그램에 전달되지 않습니다. 따라서 프로그램이 받는 문자열은:

```text
two three
```

입니다.

즉, C 프로그램은 원래 입력한 명령줄 문자열 전체를 직접 나누는 것이 아니라, **셸이 이미 인자 단위로 나눈 문자열 배열을 전달받습니다**.

## 수정과 실행 사이의 확인 순서

코드를 수정한 뒤에는 다음 순서를 습관화하는 것이 좋습니다.

```text
소스 수정
→ 소스 저장
→ 컴파일
→ 컴파일 성공 여부 확인
→ 경고 확인
→ 실행
→ stdout 확인
→ stderr 확인
→ 종료 상태 확인
```

특히 **컴파일에 실패했다면 새 실행 파일이 만들어졌다고 가정해서는 안 됩니다**.

실행 결과가 예상과 다르거나 수정한 내용이 반영되지 않는다면 다음을 확인합니다.

- 수정한 소스 파일을 저장했습니까?
- 실제로 다시 컴파일했습니까?
- 컴파일이 성공했습니까?
- 컴파일 실패 뒤 남아 있던 이전 실행 파일을 실행한 것은 아닙니까?
- 다른 디렉터리에 있는 같은 이름의 실행 파일을 실행한 것은 아닙니까?
- 빌드 명령이 실제로 수정한 소스 파일을 입력으로 포함합니까?
- `-o`로 지정한 실행 파일과 실제 실행한 파일이 같은 파일입니까?

예를 들어 다음 명령은 `hello.c`를 사용해 `hello`를 만듭니다.

```sh
cc hello.c -o hello
```

그런데 다음과 같이 다른 파일을 실행하면 수정 결과를 볼 수 없습니다.

```sh
./program
```

컴파일한 파일 이름과 실행한 파일 이름을 함께 확인해야 합니다.

## 프로그램이 만들어지는 단계

`cc hello.c -o hello`처럼 한 번의 명령으로 실행 파일을 만들 수 있지만, 내부에서는 개념적으로 여러 단계가 진행됩니다.

```text
소스 파일
→ 전처리
→ 컴파일
→ 어셈블
→ 링크
→ 실행 파일
```

각 단계의 역할은 다음과 같습니다.

### 전처리

`#include`, `#define`, 조건부 컴파일 같은 **전처리 지시문**을 처리합니다.

예를 들어:

```c
#include <stdio.h>
```

는 컴파일에 필요한 선언을 헤더에서 가져오도록 전처리기에 지시합니다.

### 컴파일

전처리가 끝난 C 코드를 분석하여 문법, 타입 등의 문제를 검사하고 더 낮은 수준의 코드로 변환합니다.

### 어셈블

컴파일러가 만든 어셈블리 수준의 코드를 **오브젝트 파일(object file)**로 변환합니다.

오브젝트 파일에는 기계어가 들어 있지만, 다른 파일에 정의된 함수나 라이브러리와 아직 연결되지 않은 참조가 남아 있을 수 있습니다.

### 링크

하나 이상의 오브젝트 파일과 필요한 라이브러리를 결합하여 최종 실행 파일을 만듭니다.

여러 소스 파일로 프로그램을 작성한 경우 이 단계의 의미가 특히 중요합니다.

예를 들어:

```text
main.c
parse.c
```

두 파일이 모두 필요한 프로그램이라면 다음처럼 함께 컴파일하고 링크할 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic main.c parse.c -o program
```

`main.c`가 `parse.c`에 정의된 함수를 호출하는데 `parse.c`를 링크 명령에서 빼면 링크 오류가 발생할 수 있습니다.

## 실패 단계 구분하기

오류가 발생했을 때 **어느 단계에서 실패했는지 구분하면 무엇을 확인해야 하는지 빠르게 좁힐 수 있습니다**.

### 전처리 오류

헤더 파일을 찾지 못하거나 전처리 지시문이 잘못된 경우입니다.

예:

```text
fatal error: my_header.h: No such file or directory
```

주로 다음을 확인합니다.

- `#include`에 적은 헤더 이름이 올바른가?
- 헤더 파일이 실제로 존재하는가?
- 필요한 헤더 검색 경로가 지정되어 있는가?
- `-I` 옵션이 필요한가?

예를 들어 사용자 헤더가 `include` 디렉터리에 있다면 빌드 구조에 따라 다음과 같은 옵션이 필요할 수 있습니다.

```sh
cc -Iinclude main.c -o program
```

### 컴파일 오류

C 문법이 잘못되었거나 타입 규칙을 만족하지 못해 컴파일 단계가 진행되지 못한 경우입니다.

예를 들어 세미콜론이 빠진 코드는:

```c
int x = 10
printf("%d\n", x);
```

여러 개의 오류 메시지를 발생시킬 수 있습니다.

이때 뒤쪽 오류가 모두 독립적인 문제라고 가정하면 안 됩니다. 앞에서 발생한 하나의 문법 오류 때문에 컴파일러가 이후 코드를 잘못 해석하여 **연쇄 오류(cascading errors)**가 발생할 수 있기 때문입니다.

따라서 보통은 오류 메시지를 위에서부터 읽고 **가장 처음 나타난 근본 원인부터 수정한 뒤 다시 컴파일**합니다.

### 링크 오류

각 소스 파일 자체의 컴파일은 성공했지만, 최종 실행 파일을 만들기 위해 필요한 함수나 전역 객체의 정의를 찾지 못한 경우입니다.

대표적인 메시지는 다음과 같습니다.

```text
undefined reference to `parse_input'
```

예를 들어 `main.c`에서 다음 함수를 호출한다고 가정합니다.

```c
parse_input();
```

함수 선언은 보이더라도 실제 정의가 들어 있는 `parse.c`가 링크 명령에 포함되지 않았다면 링크에 실패할 수 있습니다.

```sh
cc main.c -o program
```

필요한 소스 파일이 `parse.c`라면 다음처럼 함께 링크해야 합니다.

```sh
cc main.c parse.c -o program
```

라이브러리 함수를 사용하는 경우에는 필요한 라이브러리 링크 옵션이 빠지지 않았는지도 확인해야 합니다.

즉, 링크 오류에서는 주로 다음을 확인합니다.

- 필요한 소스 파일 또는 오브젝트 파일이 링크 명령에 포함되었는가?
- 함수 이름과 정의가 정확히 일치하는가?
- 필요한 라이브러리가 링크되었는가?

### 실행 오류

실행 파일은 성공적으로 만들어졌지만 실행 중 문제가 발생하는 경우입니다.

실행 오류에는 크게 두 종류가 있습니다.

```text
비정상 종료
잘못된 실행 결과
```

비정상 종료의 원인에는 잘못된 포인터 사용이나 배열 범위 접근 등이 있을 수 있습니다.

잘못된 실행 결과는 프로그램이 끝까지 실행되더라도 계산식, 조건문, 입력 처리 등의 논리가 잘못되었을 때 발생할 수 있습니다.

따라서 실행 단계에서는 다음을 확인합니다.

- 입력값이 예상한 형식인가?
- 배열 인덱스가 유효한 범위 안에 있는가?
- 포인터가 유효한 객체를 가리키는가?
- 함수와 시스템 호출의 반환값을 확인했는가?
- 조건식과 계산식이 의도한 논리와 일치하는가?
- stdout과 stderr에 어떤 내용이 출력되었는가?
- 종료 상태가 무엇인가?

## 오류 메시지를 읽는 기본 순서

컴파일이나 링크에 실패했을 때 출력되는 메시지가 많더라도 처음부터 모든 줄을 같은 비중으로 볼 필요는 없습니다.

다음 순서로 확인합니다.

```text
1. 명령이 성공했는지 실패했는지 확인
2. 가장 먼저 보고된 오류를 찾음
3. 오류가 가리키는 파일과 줄 번호를 확인
4. 해당 줄뿐 아니라 바로 앞의 코드도 확인
5. 원인을 수정
6. 다시 컴파일
7. 남은 오류를 다시 확인
```

컴파일러가 표시한 줄이 항상 실제 실수 위치와 정확히 일치하는 것은 아닙니다.

예를 들어 이전 줄에서 `;`, `)`, `}` 등이 빠지면 컴파일러는 그다음 줄을 읽은 뒤에야 문법이 맞지 않는다는 사실을 발견할 수 있습니다. 따라서 오류가 표시된 줄 주변, 특히 **바로 앞부분**도 함께 확인해야 합니다.

## 기본 개발 습관

- 한 번에 큰 코드를 작성하기보다 작은 단위로 작성하고 자주 컴파일합니다.
- 소스를 수정한 뒤에는 저장 여부를 확인하고 다시 컴파일합니다.
- 컴파일에 실패한 뒤 남아 있는 이전 실행 파일을 새 결과로 착각하지 않습니다.
- 경고를 읽지 않은 채 캐스트나 경고 억제 옵션으로 덮지 않습니다.
- 경고가 발생하면 원인을 이해한 뒤 필요한 경우 코드를 수정합니다.
- 정상 입력뿐 아니라 인자 누락과 잘못된 입력도 실행해 봅니다.
- 정상 결과는 stdout, 오류와 진단 메시지는 stderr에 보내는 습관을 들입니다.
- 프로그램 출력뿐 아니라 종료 상태도 함께 확인합니다.
- 실행 파일과 다른 빌드 산출물은 소스 코드와 구분하여 관리합니다.
- 오류가 여러 개라면 가장 앞의 원인부터 수정하고 다시 컴파일합니다.

## 완료 기준

다음을 직접 수행하고 설명할 수 있어야 합니다.

1. 새 `.c` 파일을 만들고 저장한 뒤 경고 옵션을 켜서 실행 파일로 컴파일할 수 있습니다.
2. 소스 파일을 수정한 뒤 왜 다시 컴파일해야 하는지 설명할 수 있습니다.
3. `cc -std=c11 -Wall -Wextra -Wpedantic source.c -o program` 명령의 각 부분을 설명할 수 있습니다.
4. `./program`에서 `./`가 필요한 이유를 설명할 수 있습니다.
5. `argc`와 `argv`를 사용해 명령행 인자의 개수를 검사하고 각 인자에 접근할 수 있습니다.
6. 정상 결과는 stdout, 오류 메시지는 stderr로 보낼 수 있습니다.
7. 성공과 실패에 서로 다른 종료 상태를 반환하고 셸에서 `$?`로 확인할 수 있습니다.
8. 전처리, 컴파일, 링크, 실행 단계의 차이를 설명할 수 있습니다.
9. 오류 메시지를 보고 어느 단계에서 실패했는지 구분할 수 있습니다.
10. 컴파일 실패 뒤 남아 있는 이전 실행 파일을 실행하여 생기는 혼동을 피할 수 있습니다.
