# 프런트엔드 실무 점검표

이 문서는 처음부터 끝까지 읽는 본문이 아닙니다. 구현, 코드 리뷰, 장애 분석 또는 역량 검증 프로그램 실패와 관련된 항목만 골라 확인합니다.

## 프로젝트 합류

- [ ] `.nvmrc`, `engines`, `packageManager`와 잠금 파일을 확인했습니다.
- [ ] 고정 설치, 형 검사, 단위 테스트, 빌드, E2E와 smoke 명령을 찾았습니다.
- [ ] 개발 서버와 운영 서버를 각각 실행했습니다.
- [ ] URL에서 page, 데이터 읽기 함수, Client Component, 사용자 명령과 테스트까지 추적했습니다.
- [ ] 브라우저, Next.js 서버와 빌드 시점에 실행되는 코드를 구분했습니다.
- [ ] 서버 전용 환경 변수와 브라우저 공개 환경 변수를 구분했습니다.
- [ ] CI가 실제로 실행하는 명령과 환경을 확인했습니다.

## 사용자 기능

- [ ] 사용자, 조건, 행동과 결과를 한 문장으로 적었습니다.
- [ ] 입력, 출력, 실패와 요청 완료 순서를 적었습니다.
- [ ] 첫 변경을 확인 가능한 기능 하나로 제한했습니다.
- [ ] 정상 결과, 빈 결과와 실패를 구분했습니다.
- [ ] 새로 고침과 back/forward 뒤 복원할 값을 정했습니다.
- [ ] 같은 명령이 반복될 가능성을 검토했습니다.

## 값의 저장 위치

- [ ] 공유해야 하는 검색 조건은 URL과 history에 저장합니다.
- [ ] 서버 응답을 여러 클라이언트 저장소에 불필요하게 복사하지 않았습니다.
- [ ] 서버가 확정한 값과 사용자가 작성 중인 입력 초안을 분리했습니다.
- [ ] 계산할 수 있는 값은 렌더링 중 계산합니다.
- [ ] 서로 배타적인 화면 상태를 discriminated union으로 표현했습니다.
- [ ] `pending`과 `error`에서 마지막 정상 결과를 유지할지 정했습니다.
- [ ] 화면 이동, logout과 사용자 전환 때 지울 값을 정했습니다.

## Server Component와 Client Component

- [ ] 비밀값과 데이터 접근을 서버에 둘 수 있는지 확인했습니다.
- [ ] `"use client"` 범위를 실제 상호작용이 필요한 파일로 제한했습니다.
- [ ] Client Component에 넘기는 props는 직렬화할 수 있습니다.
- [ ] 서버 전용 module이 클라이언트 import graph에 포함되지 않습니다.
- [ ] 서버 코드가 같은 애플리케이션의 Route Handler를 불필요하게 HTTP로 호출하지 않습니다.
- [ ] `loading`, `error`, `not-found` 화면에 사용자의 다음 행동이 있습니다.

## 외부 입력

- [ ] URL, HTTP, storage와 message 입력을 `unknown`으로 받습니다.
- [ ] TypeScript assertion을 실행 중 검증으로 오해하지 않습니다.
- [ ] 중복 id, 음수, 지나치게 큰 값과 알 수 없는 enum을 처리합니다.
- [ ] API 응답을 컴포넌트에 넘기기 전에 필요한 필드를 검사합니다.
- [ ] 형식이 잘못된 성공 응답을 화면에 반영하지 않습니다.
- [ ] 사용자에게 보여 줄 문구와 개발자가 확인할 세부 오류를 분리했습니다.

## 요청과 Effect

- [ ] 새 요청이 이전 signal을 abort합니다.
- [ ] 응답을 반영하기 전에 최신 generation인지 확인합니다.
- [ ] 사용자 취소, 시간 초과, HTTP 실패와 응답 형식 오류를 구분합니다.
- [ ] 이전 generation의 결과는 화면을 바꾸지 않습니다.
- [ ] Effect에서 연결 대상, dependency와 정리 함수를 확인할 수 있습니다.
- [ ] 렌더링 중 계산할 값을 Effect로 다시 저장하지 않습니다.
- [ ] unmount 뒤 요청, event listener와 connection이 남지 않습니다.

## 변경 저장과 충돌

- [ ] 낙관적 갱신 전에 이전 서버 값을 보관합니다.
- [ ] 성공 응답의 보정 값과 새 `version`을 사용합니다.
- [ ] 일반 실패에서 서버 값을 되돌리고 입력 초안을 유지합니다.
- [ ] `409 Conflict`에서 최신 서버 값과 입력 초안을 함께 유지합니다.
- [ ] 저장 중 중복 제출을 어떻게 처리할지 정했습니다.
- [ ] 충돌, 권한 오류와 네트워크 오류를 다른 문구로 설명합니다.
- [ ] 사용자가 입력을 복구하거나 다시 저장할 수 있습니다.

## 접근성

- [ ] 이동에는 link, 동작에는 button을 사용합니다.
- [ ] 모든 폼 요소에 연결된 이름이 있습니다.
- [ ] icon-only button에 accessible name이 있습니다.
- [ ] heading, main, form, list와 article이 의미에 맞게 배치되어 있습니다.
- [ ] 대기, 실패와 저장 결과를 live region으로 알립니다.
- [ ] 키보드만으로 주요 기능을 완료할 수 있습니다.
- [ ] 편집기 열기, 취소, 성공, 실패와 충돌 뒤 초점 위치를 정했습니다.
- [ ] `:focus-visible` 표시가 실제 computed style에서 보입니다.
- [ ] 상태를 색 하나로만 구분하지 않습니다.

## 좁은 화면과 motion

- [ ] 320px에서 주요 작업과 문장이 잘리지 않습니다.
- [ ] 200% 확대에서 페이지 전체에 가로 넘침이 없습니다.
- [ ] 공백 없는 긴 문자열과 큰 글자에서도 article이 넘치지 않습니다.
- [ ] input, select와 flex/grid child에 필요한 `min-width: 0`이 있습니다.
- [ ] image와 font가 늦게 표시되어도 layout이 크게 움직이지 않습니다.
- [ ] motion 감소 설정을 실제 computed style로 확인했습니다.

## 테스트

- [ ] 가장 큰 사용자 위험과 이를 검출할 테스트를 먼저 적었습니다.
- [ ] parser, 상태 전이와 요청 수명 관리자는 DOM 없이 검사합니다.
- [ ] Route Handler의 입력, 상태 코드와 응답 본문을 직접 검사합니다.
- [ ] 응답 순서를 고정 sleep 없이 제어합니다.
- [ ] 예상하지 않은 애플리케이션 요청을 발견할 수 있습니다.
- [ ] 운영 빌드 뒤 운영 서버에서 브라우저 테스트를 실행합니다.
- [ ] cookie, storage, 서버 fixture와 route mock을 테스트 사이에 초기화합니다.
- [ ] 실패 trace, screenshot, 브라우저 console과 서버 출력을 보존합니다.
- [ ] 항상 재현되는 오류를 retry로 숨기지 않습니다.

## 성능

- [ ] 변경 전 예산 또는 측정값이 있습니다.
- [ ] 첫 route의 JavaScript 응답 본문 크기를 비교합니다.
- [ ] DOM element 수가 기능 크기에 비해 급증하지 않았습니다.
- [ ] 작은 상호작용 때문에 Client Component 범위가 넓어지지 않았습니다.
- [ ] 선택 기능과 큰 library가 첫 route에 불필요하게 포함되지 않습니다.
- [ ] memoization은 실제 측정한 병목이 있을 때 사용합니다.
- [ ] 배포 전후의 실제 사용자 측정값을 비교할 방법이 있습니다.

## 운영 실행

- [ ] 고정 설치, 빌드와 시작 명령을 문서화했습니다.
- [ ] health 응답은 필요한 필드만 반환하고 `no-store`를 포함합니다.
- [ ] 릴리스 식별자를 health와 오류 기록에서 찾을 수 있습니다.
- [ ] 테스트 전용 endpoint는 테스트 모드와 token 없이는 동작하지 않습니다.
- [ ] 서버 전용 canary가 HTML, health와 첫 JavaScript 응답에 없습니다.
- [ ] standalone smoke test는 매 실행에서 고유 port와 시간 제한을 사용합니다.
- [ ] smoke test 성공과 실패 뒤 하위 프로세스가 남지 않습니다.
- [ ] 애플리케이션이 제공할 실행 정보와 인프라가 제공할 환경을 구분했습니다.

## 장애 원인을 줄이는 순서

1. 같은 URL, 사용자, 입력과 release에서 다시 발생하는지 확인합니다.
2. 개발 환경과 운영 빌드 결과를 비교합니다.
3. 서버 렌더링, hydration, 사용자 event 이후 중 언제부터 값이 달라지는지 찾습니다.
4. URL, 입력 초안과 서버 응답을 각각 확인합니다.
5. HTTP method, URL, 상태 코드, 본문과 응답 순서를 확인합니다.
6. 이전 응답, 중복 명령과 `version` 충돌 가능성을 확인합니다.
7. 데이터는 맞지만 DOM, CSS 또는 초점 표현만 잘못되었는지 분리합니다.
8. request id와 release id로 브라우저와 서버 기록을 연결합니다.
9. 한 부분만 수정하고 같은 조건에서 다시 실행합니다.
10. 수정한 부분과 핵심 운영 브라우저 동작을 다시 검사합니다.
