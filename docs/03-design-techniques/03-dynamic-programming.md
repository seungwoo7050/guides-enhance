# 동적 계획법

## 학습 목표

- 이후 결과를 결정하는 데 필요한 최소한의 정보로 상태를 정의합니다.
- 상태 정의, 점화식(recurrence), 기저 조건(base case), 계산 순서를 구분합니다.
- memoization과 tabulation을 같은 상태 의존 관계를 계산하는 두 방법으로 이해합니다.
- 공간 최적화에서 갱신 순서가 점화식의 의미를 바꾸는 이유를 설명합니다.
- 필요할 때 최적값뿐 아니라 실제 선택 결과도 복원합니다.

## 선행지식

재귀적 문제 분해, [점화식](../01-foundations/03-recurrences-and-divide-and-conquer.md), 상태 불변식을 설명할 수 있어야 합니다.

## 핵심 관점

Dynamic programming(DP)은 큰 문제를 여러 **상태(state)** 로 표현된 하위 문제로 나누고, 같은 하위 문제의 결과를 한 번 계산해 재사용하는 방법입니다.

전형적으로 다음 조건을 확인합니다.

```text
같은 하위 문제가 여러 경로에서 반복됩니다.
하위 문제의 결과로 현재 결과를 계산할 수 있습니다.
같은 상태라면 어떤 경로로 도달했는지와 관계없이 이후 결과가 같습니다.
상태 의존 관계를 올바른 순서로 계산할 수 있습니다.
```

첫 번째 성질을 흔히 **overlapping subproblems**라고 합니다. 최적화 문제에서는 하위 문제의 최적해로 현재 최적해를 구성할 수 있어야 하며, 이를 **optimal substructure**라고 부릅니다.

이 문서에서는 상태 의존 관계를 cycle 없이 정렬할 수 있는 전형적인 DP를 다룹니다. cycle이 있는 의존 관계도 별도의 반복 완화나 fixed point 계산으로 처리할 수 있는 경우가 있지만, 그때는 수렴 조건과 해의 의미를 따로 정의해야 합니다.

Table부터 만들지 말고 다음 순서로 설계합니다.

```text
상태의 의미
→ 가능한 선택과 전이
→ base case
→ 상태 의존 관계
→ 계산 순서
→ 시간·공간 복잡도
```

## 1. 상태를 완전한 문장으로 정의합니다

상태는 단순한 배열 index가 아니라 **하위 문제 하나의 입력과 반환값을 요약한 것**입니다.

좋은 상태 정의에는 처리한 입력 범위, 아직 남아 있는 제약, 저장하는 값의 의미가 들어갑니다.

```text
dp[i]
= 처음 i개 원소를 처리했을 때의 최적값

dp[i][c]
= 처음 i개 물건만 사용할 수 있고
  capacity가 c일 때 얻는 최대 가치

dp[i][j]
= A[:i]와 B[:j]의 LCS 길이
```

반대로 다음 정의는 부족합니다.

```text
dp[i] = 현재까지의 최적값
```

`현재까지`가 어느 범위를 뜻하는지, `i`가 무엇인지, 어떤 제약이 남아 있는지가 없습니다. 이런 상태로는 점화식을 정확히 정하기 어렵습니다.

### 상태는 충분해야 합니다

상태에서 미래 결과에 필요한 정보가 빠지면 서로 다른 하위 문제를 같은 상태로 합쳐 잘못된 값을 재사용합니다.

예를 들어 이후 선택 가능성이 다음 세 값에 의존한다면

```text
index
remaining_capacity
used_special_item
```

memo key에서도 세 정보를 모두 구분해야 합니다.

```text
(index, remaining_capacity, used_special_item)
```

`used_special_item`을 빼면 special item을 이미 사용한 상태와 아직 사용할 수 있는 상태를 같은 문제로 취급하게 됩니다.

상태를 정한 뒤에는 다음 질문을 확인합니다.

```text
상태 값이 같다면
앞으로 가능한 선택과 그 최적 결과도 항상 같은가?
```

답이 아니라면 상태 정보가 부족합니다.

### 불필요한 정보는 빼야 합니다

반대로 미래 결과에 영향을 주지 않는 과거 정보까지 상태에 넣으면 상태 수만 커집니다.

0/1 knapsack에서 앞으로 사용할 수 있는 물건이 `i`로 결정되고 남은 제약이 capacity `c`로 결정된다면, 지금까지 물건을 어떤 순서로 골랐는지는 미래 최적값에 영향을 주지 않습니다. 전체 선택 목록을 상태에 넣을 필요가 없습니다.

## 2. 점화식과 base case

상태를 정의했다면 한 상태의 답을 더 작은 상태들의 답으로 표현합니다. 이것이 점화식입니다.

점화식은 보통 다음 순서로 만듭니다.

```text
현재 상태에서 가능한 선택을 나눕니다.
각 선택 뒤 도달하는 하위 상태를 적습니다.
그 결과를 min, max, sum 등 문제 목적에 맞게 결합합니다.
```

Base case는 더 분해하지 않아도 직접 답을 알 수 있는 상태입니다. 초기화를 편하게 하기 위한 임의의 값이 아니라 **상태 정의를 최소 입력까지 적용했을 때 나오는 실제 답**이어야 합니다.

예를 들어

```text
dp[i][c]
= 처음 i개 물건과 capacity c로 얻는 최대 가치
```

라면 물건이 하나도 없을 때 다음이 성립합니다.

```text
dp[0][c] = 0
```

모든 weight가 양수라면 capacity가 0일 때도 다음이 성립합니다.

```text
dp[i][0] = 0
```

## 3. 0/1 knapsack

각 물건 `(weight_i, value_i)`를 사용하지 않거나 한 번만 사용할 수 있다고 하겠습니다.

상태를 다음과 같이 정의합니다.

```text
dp[i][c]
= 처음 i개 물건만 고려하고
  capacity c를 넘지 않게 선택했을 때 얻는 최대 가치
```

현재 `i`번째 물건에 대해 선택은 두 가지입니다.

### 선택하지 않는 경우

사용 가능한 물건은 처음 `i-1`개이고 capacity는 그대로입니다.

```text
dp[i-1][c]
```

### 선택하는 경우

`weight_i <= c`여야 합니다. 현재 물건을 이미 한 번 사용했으므로 남은 문제는 이전 물건들만 사용해야 합니다.

```text
dp[i-1][c-weight_i] + value_i
```

따라서 점화식은 다음과 같습니다.

```text
if weight_i > c:
    dp[i][c] = dp[i-1][c]
else:
    dp[i][c] = max(
        dp[i-1][c],
        dp[i-1][c-weight_i] + value_i
    )
```

두 경우가 모두 **이전 행 `i-1`** 을 읽는 이유는 현재 물건을 최대 한 번만 사용해야 하기 때문입니다.

### 작은 예제

```text
A: weight 2, value 3
B: weight 3, value 4
capacity = 3
```

물건 `A`만 고려하면

```text
dp[1][0] = 0
dp[1][1] = 0
dp[1][2] = 3
dp[1][3] = 3
```

입니다.

물건 `B`까지 고려하는 `dp[2][3]`은 두 경우를 비교합니다.

```text
B를 고르지 않음: dp[1][3] = 3
B를 고름:       dp[1][0] + 4 = 4
```

따라서

```text
dp[2][3] = 4
```

입니다.

## 4. 0/1 knapsack을 1차원으로 줄일 때

2차원 점화식에서 현재 행은 이전 행만 참조하므로 같은 배열을 재사용할 수 있습니다.

```text
best[c]
= 지금까지 처리한 물건만 사용할 때
  capacity c에서 얻는 최대 가치
```

하지만 같은 배열에는 이전 단계 값과 현재 단계 값이 함께 존재합니다. 따라서 **갱신 순서가 점화식의 의미를 결정합니다.**

0/1 knapsack에서는 capacity를 큰 값에서 작은 값으로 순회합니다.

```text
for each item:
    for c from capacity down to item.weight:
        best[c] = max(
            best[c],
            best[c-item.weight] + item.value
        )
```

### 왜 내림차순입니까?

현재 `c`에서 읽는 `best[c-item.weight]`가 아직 **현재 물건을 처리하기 전 값**이어야 하기 때문입니다.

weight가 `2`, value가 `3`인 물건 하나만 있고 capacity가 `4`라고 하겠습니다.

초기 상태는 다음과 같습니다.

```text
best = [0, 0, 0, 0, 0]
```

오름차순으로 갱신하면 먼저

```text
best[2] = 3
```

이 됩니다.

그 뒤 `c = 4`에서 방금 갱신한 `best[2]`를 읽으면

```text
best[4] = best[2] + 3 = 6
```

이 되어 같은 물건을 두 번 사용한 결과가 됩니다.

내림차순으로 처리하면 `best[4]`를 계산하는 시점의 `best[2]`는 아직 이전 단계의 값이므로 같은 물건을 다시 사용할 수 없습니다.

공간 최적화에서는 항상 다음을 확인합니다.

```text
현재 상태가 참조해야 하는 이전 단계의 값이
현재 단계 갱신으로 덮어써지기 전에 읽히는가?
```

## 5. unbounded knapsack과 갱신 방향

Unbounded knapsack에서는 같은 물건을 여러 번 사용할 수 있습니다.

따라서 현재 물건을 선택한 뒤에도 같은 물건을 다시 사용하는 상태 전이가 허용됩니다. 1차원 배열에서는 capacity를 오름차순으로 갱신할 수 있습니다.

```text
for each item:
    for c from item.weight up to capacity:
        best[c] = max(
            best[c],
            best[c-item.weight] + item.value
        )
```

차이는 다음과 같습니다.

```text
0/1 knapsack
= 현재 물건을 다시 사용하면 안 됨
= 이전 단계 값만 읽어야 함
= capacity 내림차순

unbounded knapsack
= 현재 물건을 다시 사용해도 됨
= 현재 단계에서 갱신한 작은 capacity 값을 읽어도 됨
= capacity 오름차순 가능
```

반복 방향은 외워야 하는 규칙이 아니라 물건 재사용 조건과 상태 의존 관계에서 도출되는 결과입니다.

## 6. LCS

LCS(Longest Common Subsequence)는 두 문자열에 공통으로 나타나는 subsequence 중 가장 긴 것의 길이 또는 실제 subsequence를 구하는 문제입니다.

**Subsequence**는 원래 순서를 유지하지만 중간 문자를 건너뛸 수 있습니다.

```text
A = "abcde"
```

에서 `"ace"`는 subsequence입니다.

반면 **substring**은 문자들이 연속되어 있어야 합니다. 따라서 LCS와 longest common substring은 서로 다른 문제입니다.

상태를 다음과 같이 정의합니다.

```text
dp[i][j]
= A[:i]와 B[:j]의 LCS 길이
```

여기서 `A[:i]`, `B[:j]`는 각각 앞에서부터 `i`, `j`개의 문자로 이루어진 prefix입니다.

Base case는 다음과 같습니다.

```text
dp[0][j] = 0
dp[i][0] = 0
```

한쪽 문자열이 비어 있으면 공통 subsequence의 길이가 `0`이기 때문입니다.

마지막 문자가 같으면

```text
A[i-1] == B[j-1]
```

그 문자를 공통 subsequence의 마지막 문자로 사용할 수 있습니다.

```text
dp[i][j] = dp[i-1][j-1] + 1
```

마지막 문자가 다르면 둘을 동시에 LCS의 마지막 문자로 사용할 수 없으므로 적어도 하나를 제외해야 합니다.

```text
dp[i][j] = max(
    dp[i-1][j],
    dp[i][j-1]
)
```

따라서 전체 점화식은 다음과 같습니다.

```text
if A[i-1] == B[j-1]:
    dp[i][j] = dp[i-1][j-1] + 1
else:
    dp[i][j] = max(
        dp[i-1][j],
        dp[i][j-1]
    )
```

### 작은 예제

```text
A = "ab"
B = "acb"
```

마지막 문자 `b`가 같으므로

```text
dp[2][3] = dp[1][2] + 1
```

입니다.

`"a"`와 `"ac"`의 LCS 길이가 `1`이므로 최종 LCS 길이는 `2`이며 실제 LCS는 `"ab"`입니다.

길이만 반환한다면 동점에서 어느 방향을 선택해도 됩니다. 실제 subsequence를 반환하거나 사전순 최소 같은 추가 조건이 있다면 predecessor와 동점 규칙이 필요합니다.

## 7. 계산 순서는 의존 관계에서 정합니다

Tabulation에서는 각 상태가 참조하는 값이 먼저 계산되어 있어야 합니다.

계산 순서를 외우기보다 어떤 상태를 참조하는지 먼저 적습니다.

### prefix DP

```text
dp[i] <- dp[i-1], dp[i-2], ...
```

처럼 더 짧은 prefix만 참조한다면 작은 index에서 큰 index로 진행합니다.

### 2차원 prefix DP

LCS처럼

```text
dp[i-1][j]
dp[i][j-1]
dp[i-1][j-1]
```

을 참조한다면 행과 열을 작은 index에서 큰 index로 채웁니다.

### interval DP

`dp[l][r]`이 더 짧은 구간에 의존한다면 짧은 구간부터 긴 구간 순서로 계산합니다.

```text
length = 1
length = 2
length = 3
...
```

### DAG path DP

정점의 값이 선행 정점에 의존한다면 topological order로 계산합니다.

### 1차원 knapsack

같은 배열을 재사용할 때는 이전 단계 값과 현재 단계 값을 구분해야 합니다.

```text
0/1 knapsack:       capacity 내림차순
unbounded knapsack: capacity 오름차순 가능
```

핵심 질문은 다음과 같습니다.

```text
현재 상태를 계산할 때 필요한 모든 값이
점화식이 의도한 단계의 값으로 준비되어 있는가?
```

## 8. memoization과 tabulation

Memoization과 tabulation은 같은 상태와 점화식을 계산하는 두 대표적인 방식입니다.

### memoization

재귀 함수의 결과를 상태 key로 저장합니다.

```text
solve(state):
    if state가 base case:
        return 직접 계산한 값

    if state가 memo에 있음:
        return memo[state]

    answer = 하위 상태들로 계산
    memo[state] = answer
    return answer
```

장점은 다음과 같습니다.

- 실제로 필요한 상태만 계산하기 쉽습니다.
- 재귀적 점화식을 코드에 직접 표현하기 쉽습니다.
- 접근 가능한 상태가 전체 상태 공간보다 훨씬 적을 때 유리할 수 있습니다.

주의할 점은 다음과 같습니다.

- recursion depth와 call stack 사용량을 확인합니다.
- hash key를 사용한다면 key 생성과 조회 비용을 고려합니다.
- memo key가 미래 결과를 결정하는 모든 정보를 포함해야 합니다.

### tabulation

Base case부터 시작해 의존 순서에 맞춰 배열이나 map을 채웁니다.

장점은 다음과 같습니다.

- 재귀 호출 비용이 없습니다.
- 계산 순서와 memory layout을 직접 제어하기 쉽습니다.
- rolling array 같은 공간 최적화를 적용하기 쉽습니다.

주의할 점은 다음과 같습니다.

- 실제 답에 필요하지 않은 상태까지 계산할 수 있습니다.
- 반복 순서가 의존 관계와 맞지 않으면 잘못된 단계의 값을 읽을 수 있습니다.

두 방식이 다음을 공유한다면 계산하는 핵심 문제는 같습니다.

```text
같은 상태 정의
같은 base case
같은 recurrence
같은 유효 상태 범위
```

## 9. 공간을 줄일 때 확인할 점

현재 row가 직전 row만 참조한다면 전체 table 대신 두 row만 보관할 수 있습니다. 경우에 따라 한 row만 재사용할 수도 있습니다.

예를 들어

```text
O(rows * columns)
```

공간을

```text
O(columns)
```

추가 공간으로 줄일 수 있습니다.

하지만 먼저 다음을 확인합니다.

- 갱신 전 값과 갱신 후 값을 같은 배열에서 구분할 수 있습니까?
- 같은 단계에서 새로 계산한 값을 읽어도 되는 문제입니까?
- 실제 해를 복원하려면 이전 선택 정보가 필요하지 않습니까?
- 동점 처리에 필요한 정보가 사라지지 않습니까?
- 계산 순서를 바꾸면서 recurrence의 의미가 달라지지 않습니까?
- 공간을 줄인 코드가 오류 가능성을 지나치게 높이지 않습니까?

공간을 줄이면 최적값은 유지하면서 실제 해 복원이 어려워질 수 있습니다. 먼저 full table 구현으로 상태와 점화식을 검증한 뒤 필요할 때 공간을 줄이는 편이 안전합니다.

## 10. 실제 해 복원

최적값만이 아니라 어떤 물건을 선택했는지, 어떤 문자열이 LCS인지가 필요할 수 있습니다.

대표적인 방법은 두 가지입니다.

### table을 역으로 추적합니다

Full table이 남아 있다면 현재 값이 어느 이전 상태에서 왔는지 점화식을 역으로 검사할 수 있습니다.

0/1 knapsack에서

```text
dp[i][c] == dp[i-1][c]
```

이면 `i`번째 물건을 선택하지 않은 최적해가 존재합니다.

선택한 경우에는 보통 다음 관계를 확인합니다.

```text
dp[i][c] == dp[i-1][c-weight_i] + value_i
```

그 뒤

```text
i <- i - 1
c <- c - weight_i
```

로 이동합니다.

### predecessor를 저장합니다

상태를 계산할 때 어떤 이전 상태와 선택에서 왔는지 함께 기록할 수도 있습니다.

```text
parent[i][j] = 이전 상태
choice[i][j] = 현재 선택
```

복원은 단순해지지만 추가 공간이 필요합니다.

### 동점 규칙

최적값이 같아도 실제 해는 여러 개일 수 있습니다.

LCS에서

```text
dp[i-1][j] == dp[i][j-1]
```

이라면 길이만 반환할 때 어느 방향을 골라도 최적 길이는 같습니다.

하지만 다음 요구가 있다면 동점 규칙을 명시해야 합니다.

```text
사전순으로 가장 작은 결과
index가 작은 항목 우선
선택한 항목 수가 가장 작은 결과
같은 입력에서 항상 같은 결과
```

따라서 **최적값을 계산하는 규칙**과 **어떤 최적해를 반환할지 정하는 규칙**을 구분합니다.

복원 결과는 다음을 만족해야 합니다.

- 계산한 최적값과 실제 결과의 값이 같습니다.
- 원본 제약을 모두 지킵니다.
- 같은 항목을 허용 횟수보다 많이 사용하지 않습니다.
- 요구된 순서와 동점 규칙을 지킵니다.
- 복원 비용이 전체 시간 상한을 깨지 않습니다.

## 11. 시간과 공간 복잡도

DP의 시간 복잡도는 보통 다음처럼 계산합니다.

```text
상태 수 × 상태 하나에서 검사하는 전이 수
```

0/1 knapsack에서 상태는

```text
i = 0..n
c = 0..capacity
```

이므로 `O(n * capacity)`개입니다. 각 상태에서 선택/비선택 두 경우만 확인하므로 시간 복잡도는

```text
O(n * capacity)
```

입니다.

2차원 table을 쓰면 공간도 `O(n * capacity)`이고, 1차원으로 줄이면 추가 공간은 `O(capacity)`입니다.

LCS에서 문자열 길이가 각각 `n`, `m`이면 상태 수는 `O(nm)`이고 각 상태의 전이는 상수 개이므로 시간은 `O(nm)`입니다.

Full table 공간은 `O(nm)`입니다. 길이만 필요하고 직전 row만 유지한다면 `O(min(n, m))` 추가 공간으로 줄일 수 있습니다.

Knapsack의 `O(n * capacity)`는 capacity의 **수치 크기**에 비례합니다. capacity가 매우 크면 이 복잡도도 실용적이지 않을 수 있으므로 입력 제한을 확인해야 합니다.

## 12. DP를 사용하기 어려운 경우

다음 경우에는 상태 설계나 다른 알고리즘을 다시 검토합니다.

- 이후 결과를 정하려면 과거 전체가 필요해 상태가 지나치게 커집니다.
- 같은 key처럼 보이는 상태가 실제로는 서로 다른 이후 제약을 가집니다.
- 의존 관계에 cycle이 있고 어떤 fixed point를 구해야 하는지 정의되지 않았습니다.
- 상태 수가 입력 제한에 비해 너무 큽니다.
- 상태 하나에서 검사해야 하는 전이 수가 너무 많습니다.
- greedy 교환 논리로 더 단순하게 풀 수 있습니다.
- 하위 문제가 거의 중복되지 않아 결과 저장의 이점이 작습니다.

DP를 사용할 수 있다는 사실과 충분히 빠르다는 사실은 다릅니다.

항상 다음을 따로 계산합니다.

```text
상태 수
상태당 전이 수
상태 저장 비용
복원 비용
```

## 13. 기준 계산과 비교합니다

작은 입력에서는 가능한 선택을 모두 검사해 DP 결과와 비교합니다.

- knapsack: 모든 물건 부분집합
- LCS: 짧은 문자열의 모든 subsequence
- 작은 DAG DP: 가능한 경로 전체

기준 계산은 후보 구현과 독립적이어야 합니다.

```text
후보 구현:
    효율적인 DP

기준 구현:
    느리지만 단순한 완전탐색

테스트:
    작은 입력에서 두 결과를 비교
```

기준 계산이 후보와 같은 table 갱신 함수나 helper를 공유하면 같은 버그가 두 구현에 들어가 테스트가 통과할 수 있습니다.

실제 해를 반환하는 문제라면 최적값만 비교하지 말고 반환한 해가 원본 제약을 만족하는지도 별도로 검사합니다.

## 완료 기준

- 각 상태가 어떤 입력 범위, 남은 제약, 반환값을 뜻하는지 한 문장으로 적습니다.
- 같은 상태라면 과거 경로와 관계없이 이후 결과가 같은 이유를 설명합니다.
- recurrence의 각 항이 어떤 선택을 뜻하는지 설명합니다.
- base case가 빈 입력이나 최소 상태의 반환 조건과 일치하는지 확인합니다.
- 모든 참조 상태가 점화식이 의도한 단계의 값으로 먼저 계산되는 순서를 설명합니다.
- 1차원 knapsack의 반복 방향이 물건 재사용 조건과 어떻게 연결되는지 설명합니다.
- 상태 수와 상태당 전이 수로 시간 복잡도를 계산합니다.
- 공간 최적화 전후 결과가 같은지 독립적인 기준 계산과 비교합니다.
- 실제 해가 필요할 때 복원 정보와 동점 규칙을 설계합니다.
- 복원한 결과가 원본 제약과 계산한 최적값을 모두 만족하는지 검사합니다.

## 실패 신호

- 상태 정의에 처리한 입력 범위나 남은 제약이 없습니다.
- 서로 다른 미래 선택을 가지는 상태를 같은 memo key로 합칩니다.
- base case가 빈 입력의 함수 조건과 다릅니다.
- recurrence의 각 항이 어떤 선택인지 설명할 수 없습니다.
- 계산 순서가 아직 계산되지 않은 상태나 잘못된 단계의 값을 읽습니다.
- 0/1 knapsack을 capacity 오름차순으로 in-place 갱신해 같은 물건을 여러 번 사용합니다.
- 공간을 줄인 뒤 이전 단계 값과 현재 단계 값을 구분하지 못합니다.
- 공간을 줄인 뒤 실제 해를 복원할 수 없는데 복원 요구사항을 확인하지 않습니다.
- 상태 수와 전이 수를 계산하지 않고 table 크기만 보고 충분히 빠르다고 판단합니다.
- 최적 부분 문제를 설명하지 않고 table부터 만듭니다.
- 기준 계산이 후보 구현과 같은 recurrence나 helper를 사용합니다.
