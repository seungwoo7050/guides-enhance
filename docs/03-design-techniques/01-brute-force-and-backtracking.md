# 완전탐색과 백트래킹

## 학습 목표

- 가능한 답 전체를 어떤 **상태(state)** 와 **선택 순서**로 빠짐없이 생성할지 정합니다.
- 같은 결과가 여러 선택 경로에서 만들어질 때 중복 생성을 제거하는 기준을 설계합니다.
- pruning이 정답 후보를 제거하지 않는 이유를 상태 공간 관점에서 설명합니다.
- 서로 다른 경로가 같은 미래 문제로 합쳐질 때 memoization을 적용할 수 있는 조건을 설명합니다.
- 작은 입력의 기준 계산과 실제 제출용 구현의 역할을 구분합니다.

## 선행지식

문제의 입력·출력 조건, 재귀 함수의 종료 조건, [정확성 설명](../01-foundations/04-correctness-and-invariants.md)을 작성할 수 있어야 합니다.

## 핵심 관점

완전탐색은 단순히 "느리지만 확실한 풀이"가 아닙니다. **가능한 답의 범위를 상태 공간으로 정확히 정의하고, 그 상태 공간을 빠짐없이 방문하는 방법**입니다.

탐색을 설계할 때 먼저 다음 질문에 답합니다.

```text
상태: 지금까지 어떤 결정을 했고, 앞으로의 선택에 필요한 정보는 무엇입니까?
다음 선택: 현재 상태에서 어떤 선택들이 허용됩니까?
전이: 선택 하나를 적용하면 상태가 어떻게 바뀝니까?
종료: 언제 하나의 완성된 후보가 됩니까?
평가: 완성된 후보가 유효한지, 또는 목적 함수 값이 얼마인지 어떻게 계산합니까?
```

이 구조를 트리로 생각하면 각 노드는 하나의 부분 상태이고, 간선은 하나의 선택입니다. 완성된 후보는 보통 leaf에 대응하지만, 문제에 따라 중간 상태도 답이 될 수 있습니다.

**백트래킹(backtracking)** 은 이 상태 공간을 깊이 우선으로 탐색하면서, 현재 상태에서 시작하는 모든 완성이 정답이 될 수 없다고 증명되는 순간 그 하위 트리를 방문하지 않는 방법입니다. 이 하위 트리 생략을 **pruning(가지치기)** 이라고 합니다.

## 1. 상태 공간 크기부터 계산합니다

대표적인 완전탐색의 후보 수는 다음과 같습니다.

- `n`개 원소의 부분집합: `2^n`
- `n`개 서로 다른 원소의 순열: `n!`
- 길이 `n`의 각 위치마다 `k`개 값 중 하나를 선택: `k^n`
- 깊이 `d`, 각 상태의 최대 분기 수가 `b`인 탐색: 최악 `O(b^d)`

후보 수만 세고 끝내면 안 됩니다. 각 후보 또는 각 상태에서 수행하는 검사 비용까지 포함해야 합니다.

예를 들어 모든 부분집합 `2^n`개를 만들고, 매 부분집합마다 원소 `n`개를 다시 훑어 합을 계산한다면 단순한 상한은 다음과 같습니다.

```text
상태 수 × 상태당 검사 비용
= 2^n × O(n)
= O(n · 2^n)
```

반대로 재귀 중에 현재 합을 함께 유지하면 선택 하나를 추가하거나 제거하는 비용을 `O(1)`로 만들 수 있으므로 같은 탐색이라도 실제 비용이 달라집니다.

입력 제한을 확인하기 전에 재귀 함수부터 작성하지 않습니다. 먼저 다음을 계산합니다.

```text
최대 깊이
× 각 깊이의 최대 선택 수
→ 방문할 수 있는 상태 수의 상한
× 상태당 작업량
→ 전체 시간 복잡도 상한
```

pruning이 많은 문제에서도 **최악의 경우 pruning이 거의 일어나지 않을 수 있는지** 확인해야 합니다. pruning이 평균적으로 빠르다는 이유만으로 최악 시간 복잡도가 작아지는 것은 아닙니다.

## 2. 선택, 재귀 호출, 복구

공유하는 mutable 상태를 직접 수정하는 전형적인 백트래킹은 다음 형태입니다.

```text
search(state):
    if state가 완성되었다면:
        결과를 검사하거나 저장합니다.
        return

    for choice in 현재 상태에서 가능한 선택:
        choice를 state에 반영합니다.
        search(state)
        choice를 state에서 되돌립니다.
```

핵심 불변식은 다음과 같습니다.

```text
for문의 각 반복이 시작될 때 state는
현재 재귀 호출에 들어왔을 때의 상태와 같아야 합니다.
```

즉, 한 선택을 탐색한 뒤에는 다음 sibling branch가 시작되기 전에 그 선택이 만든 변경을 모두 복구해야 합니다.

예를 들어 현재 선택 목록을 `path`에 저장한다면 다음과 같이 대응됩니다.

```text
path.push(choice)   # 선택 반영
search(...)
path.pop()          # 선택 복구
```

`used`, 현재 합, 방문 표시, 카운터처럼 여러 상태를 동시에 바꿨다면 그 변경들도 모두 복구해야 합니다.

복구가 빠지면 다음 sibling branch가 이전 branch의 선택을 그대로 물려받으므로, 실제 상태 공간과 다른 탐색을 하게 됩니다.

### 상태를 복사하는 방식

복구 대신 각 재귀 호출에 상태 복사본을 넘길 수도 있습니다.

```text
next_state = copy(state)
choice를 next_state에 반영합니다.
search(next_state)
```

이 방식은 복구 실수를 줄이지만, 상태 크기가 `S`라면 호출마다 최대 `O(S)`의 복사 비용이 추가됩니다. 따라서 "복사하면 안전하다"와 "복사해도 충분히 빠르다"는 별개의 문제입니다.

## 3. 모든 답을 빠짐없이 한 번씩 생성합니다

완전탐색의 정확성은 보통 다음 두 가지를 따로 증명합니다.

```text
완전성(completeness): 모든 유효한 답을 적어도 한 번 생성합니다.
유일성(uniqueness): 같은 답을 불필요하게 여러 번 생성하지 않습니다.
```

유일성이 반드시 필요한 것은 아닙니다. 중복 생성이 있어도 마지막에 집합으로 제거하면 정답 자체는 맞을 수 있습니다. 하지만 탐색량이 크게 늘 수 있으므로 가능하면 생성 단계에서 중복을 제거합니다.

### 같은 값이 여러 번 있는 경우

예를 들어 입력이 다음과 같다고 합시다.

```text
[1, 1, 2]
```

두 `1`은 index는 다르지만 값으로 만든 결과만 중요하다면, 두 index를 바꾸어 선택하는 경로가 같은 결과를 만들 수 있습니다.

대표적인 중복 제거 방법은 다음과 같습니다.

- 먼저 정렬한 뒤 **같은 깊이에서** 같은 값을 한 번만 선택합니다.
- 남은 값의 개수를 `value -> count`로 관리하여 동일한 값들을 하나의 종류로 취급합니다.
- 선택 순서를 **canonical order(표준 순서)** 로 고정합니다.

canonical order란 하나의 결과를 표현하는 여러 선택 순서 중 하나만 허용하는 규칙입니다. 예를 들어 조합을 만들 때 다음 index는 항상 이전에 선택한 index보다 크게 제한하면 `{a, b}`와 `{b, a}`를 따로 만들지 않습니다.

정렬된 배열에서 조합을 생성할 때 흔히 쓰는 "같은 깊이 중복 건너뛰기"는 다음 의미입니다.

```text
현재 깊이에서 이미 값 x를 첫 번째 후보로 사용했다면
같은 깊이에서 다시 등장한 x는 건너뜁니다.
```

여기서 중요한 점은 **같은 값이라고 항상 건너뛰는 것이 아니라 같은 선택 위치에서 중복되는 경우만 건너뛰는 것**입니다. 깊이가 달라지면 같은 값을 다시 사용하는 것이 유효한 답의 일부일 수 있습니다.

중복 제거 규칙을 적용할 때는 다음을 설명할 수 있어야 합니다.

```text
제거되는 두 경로가 실제로 같은 결과를 만듭니까?
서로 다른 유효한 답까지 하나로 합쳐지지는 않습니까?
모든 동치인 경로 중 적어도 하나는 남습니까?
```

## 4. pruning은 "이 아래에는 답이 없다"는 증명입니다

pruning 조건은 단순한 성능 최적화가 아닙니다. 잘못된 pruning은 정답 branch 자체를 제거하므로 오답이 됩니다.

안전한 pruning의 공통 형태는 다음과 같습니다.

```text
현재 상태에서 가능한 모든 완성을 생각했을 때
그중 어떤 것도 필요한 조건을 만족하거나 현재 최적값을 개선할 수 없다.
```

이 명제가 참일 때만 현재 상태 아래의 하위 트리를 버릴 수 있습니다.

### 4.1 이미 제약을 위반했고 회복할 수 없는 경우

현재까지의 선택이 capacity, 합, 충돌 조건 등을 위반했고 이후 선택으로 그 위반을 되돌릴 수 없다면 더 내려가지 않습니다.

예를 들어 모든 물건의 weight가 양수인 0/1 knapsack에서

```text
current_weight > capacity
```

라면 이후 물건을 더 선택해도 무게는 감소하지 않습니다. 따라서 이 상태에서 시작하는 모든 완성은 capacity를 초과하므로 안전하게 중단할 수 있습니다.

반대로 음수 weight가 허용되는 문제라면 이후 선택으로 총 무게가 다시 줄어들 수 있으므로 같은 pruning은 안전하지 않습니다.

즉, pruning의 근거에는 종종 다음과 같은 **단조성(monotonicity)** 이 필요합니다.

```text
한 번 위반한 조건이 이후 선택으로 다시 만족될 수 없습니다.
```

### 4.2 최적값을 개선할 가능성이 없는 경우

최대화 문제에서는 현재 상태에서 앞으로 얻을 수 있는 최선의 결과에 대한 **상한(upper bound)** 을 계산할 수 있습니다.

```text
U(state) >= state에서 출발해 실제로 얻을 수 있는 모든 완성의 값
```

이미 찾은 최적값을 `best`라고 할 때

```text
U(state) <= best
```

라면 이 상태 아래에서는 `best`보다 좋은 답이 나올 수 없으므로 pruning할 수 있습니다.

예를 들어

```text
U(state) = current + optimistic_remaining
```

을 사용한다면 `optimistic_remaining`은 **실제로 추가로 얻을 수 있는 최대 이득보다 작아서는 안 됩니다.**

- 너무 큰 상한: pruning이 덜 되어 느릴 수 있지만 정답은 유지됩니다.
- 실제 가능 값보다 작은 상한: 개선 가능한 branch를 잘라낼 수 있어 오답이 됩니다.

최소화 문제는 반대 방향입니다. 현재 상태에서 달성 가능한 비용의 **하한(lower bound)** `L(state)`을 계산하여

```text
L(state) >= best
```

이면 현재 최적값보다 나아질 수 없으므로 pruning할 수 있습니다.

탐색 순서는 이 pruning의 **효율**에는 영향을 줍니다. 좋은 답을 일찍 발견해 `best`가 강해지면 더 많은 branch를 자를 수 있습니다. 그러나 탐색 순서 자체가 pruning의 정확성을 대신 증명하지는 않습니다.

### 4.3 대칭인 상태를 하나만 탐색하는 경우

서로 다른 상태가 단지 이름이나 배치 순서만 다르고, 앞으로 만들 수 있는 답들이 일대일 대응한다면 대표 하나만 탐색할 수 있습니다.

예를 들어 서로 구별할 필요가 없는 동일한 물건 여러 개를 어느 상자에 넣는 문제에서, 아직 내용이 완전히 같은 빈 상자들은 서로 이름만 다를 수 있습니다. 이런 상자 하나를 선택한 경우 다른 동일한 빈 상자를 선택하는 branch는 대칭일 수 있습니다.

대칭 pruning을 적용하려면 다음을 설명할 수 있어야 합니다.

```text
두 상태에서 가능한 이후 선택 집합이 본질적으로 같습니까?
한 상태의 모든 완성 답을 다른 상태의 완성 답과 대응시킬 수 있습니까?
대표 하나를 남겨도 서로 다른 답이 사라지지 않습니까?
```

## 5. memoization으로 합칠 수 있는 상태를 찾습니다

백트래킹에서는 서로 다른 선택 경로가 **앞으로의 문제는 완전히 같은 상태**에 도달할 수 있습니다.

예를 들어 다음 두 경로가 있다고 합시다.

```text
경로 A -> state X
경로 B -> state X
```

`state X` 이후의 가능한 선택과 결과가 경로 A와 B에서 완전히 같다면, `state X`의 결과를 한 번 계산한 뒤 저장하여 재사용할 수 있습니다. 이것이 memoization입니다.

memoization의 핵심 질문은 다음과 같습니다.

```text
memo key가 현재 상태 이후의 결과를 결정하는 모든 정보를 포함합니까?
```

예를 들어 0/1 knapsack의 재귀 상태가

```text
(index, remaining_capacity)
```

만으로 이후 최적값을 결정한다면 이 두 값을 key로 사용할 수 있습니다.

반대로 현재 경로에서 어떤 정점을 이미 방문했는지가 이후 선택 가능성을 바꾸는 문제라면 `current_vertex`만 key로 써서는 안 됩니다. 서로 다른 visited 집합이 같은 정점에 도착해도 이후 가능한 경로가 다르기 때문입니다.

안전한 memo key는 다음 성질을 가져야 합니다.

```text
key가 같은 두 상태에서는
허용되는 이후 선택과 그 선택들로부터 얻는 결과가 같아야 합니다.
```

### 백트래킹과 동적 계획법의 관계

상태가 같은 부분문제가 반복해서 등장하고, 각 상태의 답을 더 작은 상태의 답으로 정의할 수 있다면 memoization을 통해 중복 계산을 제거할 수 있습니다. 이를 상태와 점화식 관점에서 체계화하면 dynamic programming으로 정리할 수 있습니다.

단순한 top-down memoization은 보통 재귀 의존 관계가 종료 방향으로 진행되어 다시 자기 자신을 미완성 상태로 참조하지 않는 구조에서 가장 직접적으로 사용할 수 있습니다. 상태 사이에 cycle이 있다면 방문 상태 처리, 고정점 계산, 그래프 알고리즘 등 별도의 설계가 필요할 수 있습니다.

또한 dynamic programming은 최적화 문제에만 한정되지 않습니다. 다음과 같은 값도 상태별로 저장할 수 있습니다.

- 가능한지 여부
- 경우의 수
- 최댓값 또는 최솟값
- 문자열이나 경로를 구성하기 위한 선택 정보

## 6. 작은 기준 계산으로 사용하는 완전탐색

작은 입력에서는 단순한 완전탐색이 최적화 구현보다 더 좋은 **기준 계산(reference implementation, oracle)** 이 될 수 있습니다.

목적은 빠르게 푸는 것이 아니라, 작은 입력에서 신뢰할 수 있는 정답을 만들어 실제 구현과 비교하는 것입니다.

예시는 다음과 같습니다.

- 구간 선택: 모든 구간 부분집합을 검사하고 서로 겹치지 않는 집합의 최대 크기를 구합니다.
- knapsack: 모든 물건 부분집합을 검사하고 capacity 이하인 부분집합의 최대 가치를 구합니다.
- MST: 간선 중 `V-1`개를 고르는 모든 조합을 검사하고 spanning tree인 조합의 최소 가중치를 구합니다.
- 최대 유량: source는 포함하고 sink는 포함하지 않는 모든 정점 집합을 source-side cut으로 보고 최소 cut capacity를 구합니다.
- LCS: 한쪽 짧은 문자열의 모든 subsequence를 생성하고 다른 문자열의 subsequence인지 검사하여 최대 길이를 구합니다.

기준 계산은 보통 실제 알고리즘보다 훨씬 느리지만, 입력을 매우 작게 제한하면 테스트용으로 충분합니다.

### 후보 구현과 독립적으로 만듭니다

기준 계산이 후보 구현과 같은 핵심 로직을 공유하면 같은 버그가 두 구현에 동시에 들어갈 수 있습니다. 그러면 잘못된 결과끼리 일치하여 테스트가 통과할 수 있습니다.

따라서 가능하면 다음을 분리합니다.

```text
후보 구현: 실제 제약을 만족하는 효율적인 알고리즘
기준 구현: 작고 단순하며 직접적인 완전탐색
```

특히 정답을 결정하는 핵심 상태 전이, pruning 조건, 정렬 기준, 비교 로직을 그대로 공유하지 않는 것이 좋습니다. 단순 입력 파싱처럼 정답 계산과 무관한 공통 유틸리티까지 반드시 복제해야 한다는 뜻은 아닙니다.

기준 계산 자체에도 테스트가 필요합니다. 작은 손계산 예제와 경계값으로 기준 구현이 독립적으로 맞는지 먼저 확인합니다.

## 7. 예제: N-Queens

`N × N` 체스판의 각 행에 queen 하나씩을 놓는 방식으로 상태를 정의할 수 있습니다.

```text
row: 다음에 queen을 놓을 행
used_columns: 이미 queen이 놓인 열 집합
used_diag_down: 이미 사용한 \ 방향 대각선 식별자 집합
used_diag_up: 이미 사용한 / 방향 대각선 식별자 집합
```

좌표를 `(row, column)`이라고 하면 같은 대각선의 식별자는 다음처럼 일정합니다.

```text
\ 방향 대각선: row - column
/ 방향 대각선: row + column
```

`row - column`은 음수가 될 수 있으므로 배열 index로 사용한다면 `n - 1`만큼 offset을 더합니다. 집합 자료구조를 쓴다면 음수 값을 그대로 저장해도 됩니다.

재귀 호출 `search(row)`가 시작될 때 유지할 불변식은 다음과 같습니다.

```text
[0, row) 범위의 각 행에는 queen이 정확히 하나 있습니다.
놓인 queen들은 서로 같은 열에 있지 않습니다.
놓인 queen들은 서로 같은 대각선에 있지 않습니다.
```

다음 행에서는 다음 조건을 모두 만족하는 열만 선택합니다.

```text
column이 used_columns에 없습니다.
row - column이 used_diag_down에 없습니다.
row + column이 used_diag_up에 없습니다.
```

선택 후 세 집합에 값을 추가하고 다음 행으로 내려갔다가, 재귀 호출이 끝나면 세 값을 모두 제거합니다.

```text
search(row):
    if row == n:
        답 하나를 찾았습니다.
        return

    for column in [0, n):
        if 열 또는 대각선이 이미 사용 중이면:
            continue

        열과 두 대각선을 사용 중으로 표시합니다.
        search(row + 1)
        열과 두 대각선 표시를 복구합니다.
```

이 pruning이 안전한 이유는 이미 놓인 queen과 충돌하는 위치에 새 queen을 놓으면 그 충돌은 이후 다른 행에 queen을 더 놓아도 사라지지 않기 때문입니다. 따라서 충돌하는 선택 아래에는 유효한 완성 답이 없습니다.

## 8. 반복 구현을 선택할 때

재귀 깊이가 입력 크기에 비례하고 입력 상한이 커서 호출 스택 한도를 넘을 수 있다면 명시적인 stack으로 DFS를 구현할 수 있습니다.

재귀 호출 하나가 암묵적으로 기억하던 정보는 반복 구현에서 stack frame에 직접 저장해야 합니다. 예를 들면 다음과 같습니다.

```text
현재 깊이 또는 위치
다음에 시도할 choice의 index
현재 frame에 들어올 때 적용한 선택
복구에 필요한 정보
```

또 다른 방법은 stack 항목마다 상태 복사본을 저장하는 것입니다. 이 경우 명시적인 복구는 줄어들지만 상태 복사 비용과 메모리 사용량이 증가합니다.

중요한 점은 다음과 같습니다.

```text
재귀를 반복문으로 바꾸는 것
!=
상태 관리 문제가 자동으로 해결되는 것
```

재귀 구현에서 호출 스택과 "선택 후 복구"가 담당하던 역할을 반복 구현에서 어떤 데이터가 대신하는지 명확히 정해야 합니다.

## 9. 완전탐색 설계 순서

문제를 받았을 때 다음 순서로 설계하면 누락을 줄일 수 있습니다.

```text
1. 하나의 완성된 답이 무엇인지 정의합니다.
2. 답의 prefix 또는 부분 선택을 표현하는 상태를 정의합니다.
3. 현재 상태에서 가능한 다음 선택을 정의합니다.
4. 모든 답이 적어도 한 경로로 생성되는지 확인합니다.
5. 같은 답이 여러 경로로 생성되는지 확인합니다.
6. 상태 공간 크기와 상태당 비용을 계산합니다.
7. 안전성을 증명할 수 있는 pruning만 추가합니다.
8. 같은 미래를 가진 상태가 반복되면 memoization을 검토합니다.
9. mutable 상태를 쓴다면 호출 전후 복구 불변식을 확인합니다.
```

pruning이나 memoization은 상태 공간 정의가 끝난 뒤에 추가합니다. 무엇을 탐색하는지도 명확하지 않은 상태에서 최적화부터 넣으면 정답 누락과 잘못된 상태 병합을 발견하기 어렵습니다.

## 연결 구현

[`verified-algorithms`](../../exercises/verified-algorithms/)의 테스트에서 다음 기준 계산을 확인합니다.

- `brute_knapsack`: 물건의 모든 부분집합을 검사합니다.
- `brute_interval_count`: 모든 구간 부분집합을 검사합니다.
- `brute_mst_weight`: 가능한 `V-1`개 간선 조합을 검사합니다.
- `brute_min_cut`: 모든 source-side 정점 집합을 검사합니다.
- `brute_lcs_length`: 짧은 문자열의 모든 subsequence를 검사합니다.

이 함수들은 작은 입력에서만 실행되며, 실제 알고리즘과 다른 방식으로 결과를 계산합니다. 후보 구현과 결과가 다르면 먼저 두 구현 중 어느 쪽의 상태 정의나 경계 조건이 잘못되었는지 최소 반례로 줄여 확인합니다.

## 완료 기준

- 완성된 답, 부분 상태, 다음 선택, 종료 조건을 각각 정의합니다.
- 선택 수와 깊이로 상태 공간의 상한을 계산하고 상태당 비용까지 포함합니다.
- 모든 유효한 답이 적어도 한 번 생성되는 이유를 설명합니다.
- 중복 제거를 사용한다면 서로 다른 답까지 없애지 않는 이유를 설명합니다.
- 재귀 호출 전후에 mutable 상태가 정확히 복구되는지 손으로 추적합니다.
- 각 pruning 조건에 대해 현재 상태 아래의 모든 완성이 버려져도 되는 이유를 적습니다.
- bound를 사용한다면 최대화 문제의 상한 또는 최소화 문제의 하한 방향이 올바른지 확인합니다.
- memo key가 미래 선택과 결과를 결정하는 모든 정보를 포함하는지 확인합니다.
- 기준 계산과 후보 구현이 핵심 정답 계산 로직을 공유하지 않게 합니다.

## 실패 신호

- 상태 공간 크기를 계산하지 않고 재귀부터 작성합니다.
- 완성된 답과 중간 상태의 의미가 명확하지 않습니다.
- mutable 상태를 복구하지 않아 sibling branch가 서로 영향을 줍니다.
- 같은 답을 여러 경로로 만들지만 중복 비용을 인식하지 못합니다.
- 중복 제거 조건이 서로 다른 유효한 답까지 합칩니다.
- "현재는 조건을 위반했다"는 이유만으로 이후 회복 가능성을 확인하지 않고 pruning합니다.
- 최대화 문제의 optimistic upper bound가 실제 가능한 최대값보다 작습니다.
- 최소화 문제의 lower bound가 실제 가능한 최소 비용보다 큽니다.
- memo key에서 이후 선택 가능성에 영향을 주는 값을 빠뜨립니다.
- 경로 의존 상태를 무시한 채 서로 다른 상태를 같은 memo 항목으로 합칩니다.
- 기준 계산이 후보와 같은 핵심 알고리즘이나 같은 잘못된 가정을 공유합니다.
