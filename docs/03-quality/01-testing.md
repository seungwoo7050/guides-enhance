# 재현 가능한 테스트

## 학습 목표

좋은 테스트는 사례 수가 많은 테스트가 아니라 **무엇을 보장하려는지**, 그리고 **어떤 잘못된 구현이라면 실패해야 하는지** 설명할 수 있는 테스트입니다.

또한 테스트는 같은 코드와 같은 조건에서 반복 실행했을 때 같은 결과를 내야 합니다. 실행 순서, 이전 테스트가 남긴 파일, 전역 난수 상태, 현재 작업 디렉터리 같은 우연한 외부 상태에 따라 성공과 실패가 바뀐다면 테스트 자체를 신뢰하기 어렵습니다.

이 문서에서는 다음 내용을 다룹니다.

- 계산 코드와 파일·프로세스 입출력을 나눠 테스트하는 방법
- 단위·통합·종단 간 테스트의 역할
- 경곗값과 실패 경로를 선택하는 방법
- 표 기반 테스트, 작은 입력 전수 검사, 고정 시드 사용
- 기준 구현과 비교해 최적화 구현을 검사하는 방법
- 임시 디렉터리와 테스트용 입력·프로그램으로 외부 상태를 재현하는 방법
- 출력 스트림, 종료 상태, 운영체제 의존 동작을 검사하는 방법

필수 프로젝트인 [`data-report`](../../exercises/data-report/README.md)는 입력 검증부터 CLI까지 표준 라이브러리 `unittest`로 검사합니다.

## 선행 개념

- **순수한 계산**과 **부작용(side effect)**을 구분할 수 있어야 합니다.
  - 순수한 계산: 같은 입력에 같은 결과를 반환하며 파일, 네트워크, 프로세스 같은 외부 상태를 변경하지 않는 계산
  - 부작용: 파일 읽기·쓰기, 표준 출력, 프로세스 실행처럼 함수 바깥의 상태를 읽거나 변경하는 동작
- 정상 사례, 경계 사례, 실패 사례를 나누어 생각할 수 있어야 합니다.
- 함수 반환값뿐 아니라 예외, 출력 파일, `stdout`, `stderr`, 프로세스 종료 상태도 프로그램 동작의 일부라는 점을 이해해야 합니다.

## 계산 코드와 부작용 분리하기

테스트하기 쉬운 구조를 만들려면 가능한 한 **계산 규칙**과 **외부 입출력**을 분리합니다.

```python
def normalize_words(text: str) -> list[str]:
    return sorted({word.lower() for word in text.split()})
```

위 함수는 전달받은 문자열만 사용하고 파일이나 프로세스에 접근하지 않습니다. 따라서 외부 환경을 준비하지 않고 직접 테스트할 수 있습니다.

```python
import unittest


class NormalizeWordsTest(unittest.TestCase):
    def test_removes_duplicates_and_sorts(self) -> None:
        self.assertEqual(normalize_words("B a b"), ["a", "b"])
```

이런 테스트는 실패했을 때 원인을 좁히기 쉽습니다. 파일 권한이나 현재 작업 디렉터리가 아니라 `normalize_words()`의 계산 규칙을 먼저 의심할 수 있기 때문입니다.

반면 CLI처럼 실제 실행 환경까지 확인해야 하는 부분은 소수의 통합 테스트와 종단 간 테스트로 보완합니다.

`data-report`에서는 다음처럼 역할을 나눌 수 있습니다.

```text
load_records()  → 실제 임시 파일을 사용하는 통합 테스트
aggregate()     → Record와 Report만 사용하는 단위 테스트
render_text()   → 문자열 결과를 확인하는 단위 테스트
main()          → stdout, stderr, 출력 파일, 종료 상태를 확인하는 통합 테스트
설치된 명령     → 콘솔 스크립트를 실제 프로세스로 실행하는 종단 간 테스트
```

핵심은 모든 동작을 한 종류의 테스트로 검사하지 않는 것입니다. 계산 규칙은 작고 빠른 테스트로 많이 검사하고, 외부 환경과 연결되는 부분은 필요한 범위만 실제 자원으로 검사합니다.

## 테스트 수준 구분하기

테스트 수준은 파일 개수나 함수 개수로 결정되지 않습니다. **테스트가 실제로 연결하는 범위와 외부 경계**가 기준입니다.

| 수준 | 확인하는 범위 | 예시 |
|---|---|---|
| 단위 테스트 | 함수나 타입처럼 작은 계산 단위의 동작 | `Decimal` 합산, `category` 정렬 |
| 통합 테스트 | 여러 모듈 또는 코드와 실제 자원의 연결 | CSV 파일 읽기와 JSON 파일 저장 |
| 종단 간 테스트 | 사용자가 사용하는 최종 실행 경로 전체 | `python -m data_report` 또는 설치된 `data-report` |

예를 들어 `main()`을 같은 Python 프로세스 안에서 직접 호출하면서 임시 파일과 출력 스트림을 함께 검사한다면 여러 구성 요소를 연결하므로 통합 테스트에 가깝습니다. 반대로 설치된 `data-report` 명령을 별도 프로세스로 실행하면 패키징, 진입점, 인자 전달, 종료 상태까지 실제 사용자 경로를 통과하므로 종단 간 테스트입니다.

모든 테스트를 하위 프로세스로 실행하면 다음 문제가 생깁니다.

- 프로세스를 매번 시작하므로 느려집니다.
- 실패가 계산 로직, 파일 처리, CLI 파싱, 패키징 중 어디에서 생겼는지 구분하기 어렵습니다.
- 테스트 입력과 내부 상태를 직접 확인하기 어렵습니다.

반대로 단위 테스트만 작성하면 다음과 같은 실제 실행 조건이 빠질 수 있습니다.

- CLI 인자가 올바르게 전달되는지
- 현재 작업 디렉터리와 상대 경로가 올바르게 처리되는지
- `stdout`과 `stderr`를 올바르게 구분하는지
- 올바른 종료 상태를 반환하는지
- 설치된 콘솔 스크립트가 실제로 실행되는지

따라서 일반적으로 **많은 단위 테스트 + 필요한 통합 테스트 + 소수의 종단 간 테스트**로 역할을 나누는 편이 좋습니다.

## 경곗값과 분기 겨냥하기

테스트 입력은 서로 다른 숫자를 많이 넣는 것이 아니라 **서로 다른 동작이 선택되는 지점**을 겨냥해야 합니다.

일반적으로 다음 사례를 확인합니다.

- 빈 입력과 최소 입력
- 중복 값
- 첫 원소나 마지막 원소에서만 상태가 바뀌는 경우
- 정상값과 오류값이 갈리는 경계의 바로 앞·경계·바로 뒤 값
- 잘못된 타입과 허용하지 않은 필드
- 존재하지 않는 파일과 쓰기 실패
- 유한하지 않은 숫자
- 일부 작업이 성공한 뒤 발생하는 정리 실패

예를 들어 길이가 `1` 이상이어야 하는 입력을 검증한다면 `5`, `6`, `7`을 각각 검사하는 것보다 다음 세 경우가 더 의미가 있습니다.

```text
길이 0 → 거부되어야 함
길이 1 → 허용되는 최소값
길이 2 → 최소값을 넘는 정상값
```

이 세 입력은 검증 조건이 `>= 1`이어야 하는데 실수로 `> 1` 또는 `>= 0`으로 구현된 경우를 구분해서 잡아낼 수 있습니다.

예제 입력을 단순히 여러 개 복사하지 말고, 각 테스트가 어떤 분기와 잘못된 구현을 잡는지 이름에 드러냅니다.

예를 들어 다음 이름은 의도가 구체적입니다.

```text
test_validation_rejects_unknown_fields
test_validation_rejects_non_finite_amount
test_aggregation_sorts_categories_and_uses_decimal
test_cli_reports_invalid_input
```

`test_invalid_input`처럼 너무 넓은 이름은 실패했을 때 무엇이 깨졌는지 바로 알기 어렵습니다. 가능하면 **조건 + 기대 동작**이 이름에 드러나게 합니다.

## 표 기반 테스트

같은 규칙을 여러 입력에 반복해서 적용해야 한다면 표 기반 테스트가 유용합니다.

```python
cases = [
    ("", []),
    ("a", ["a"]),
    ("B a b", ["a", "b"]),
]

for input_text, expected in cases:
    with self.subTest(input_text=input_text):
        self.assertEqual(normalize_words(input_text), expected)
```

`subTest()`를 사용하면 한 입력이 실패하더라도 어떤 입력에서 실패했는지 구분할 수 있습니다. 반복문 하나 전체가 불명확한 한 건의 실패처럼 보이는 것을 피할 수 있습니다.

테스트가 실패했을 때는 최소한 다음 정보를 확인할 수 있어야 합니다.

- 어떤 입력을 사용했는지
- 무엇을 기대했는지
- 실제 결과가 무엇이었는지

표 기반 테스트는 **같은 규칙에 여러 입력을 적용할 때** 적합합니다. 서로 다른 실패 원인을 한 반복문에 억지로 묶으면 어떤 계약이 깨졌는지 알기 어려우므로 별도 테스트로 나눕니다.

예를 들어 “알 수 없는 필드 거부”와 “`NaN` 거부”는 둘 다 입력 검증 실패이지만 서로 다른 검증 규칙입니다. 한 표에 묶기보다 각각의 테스트 이름으로 분리하는 편이 실패 원인을 더 명확하게 보여 줍니다.

## 작은 입력 공간 전수 검사하기

입력 공간이 충분히 작다면 일부 예제를 고르는 대신 **가능한 모든 조합**을 검사할 수 있습니다.

```python
from itertools import product

for values in product(range(3), repeat=4):
    self.assertEqual(optimized(values), reference(values))
```

위 코드는 각 위치에 `0`, `1`, `2`가 들어갈 수 있는 길이 4 입력을 모두 검사합니다. 조합 수는 다음과 같습니다.

```text
3^4 = 81
```

81개 정도라면 일반적인 단위 테스트에서 충분히 현실적인 수입니다.

하지만 입력 종류가 10개이고 길이가 8이라면 다음과 같이 급격히 커집니다.

```text
10^8 = 100,000,000
```

따라서 전수 검사를 사용할 때는 먼저 가능한 조합 수를 계산해야 합니다. 입력 공간이 너무 크다면 경곗값 테스트나 고정 시드 무작위 테스트처럼 더 제한된 전략을 사용합니다.

전수 검사의 장점은 실행한 범위 안에서는 “우연히 중요한 입력을 빼먹었다”는 문제가 없다는 것입니다.

## 재현 가능한 무작위 테스트

입력 공간이 너무 커 전수 검사가 불가능하지만 다양한 조합을 확인하고 싶다면 무작위 입력을 사용할 수 있습니다.

```python
import random

rng = random.Random(4242)

for _ in range(500):
    values = [
        rng.randint(-100, 100)
        for _ in range(rng.randint(0, 30))
    ]
    self.assertEqual(optimized(values), reference(values))
```

여기서 중요한 점은 `random.seed()`로 전역 난수 상태를 바꾸는 대신 테스트 전용 `Random` 객체를 만든다는 것입니다.

```python
rng = random.Random(4242)
```

같은 Python 구현과 같은 난수 생성 규칙에서 같은 시드를 사용하면 같은 순서의 테스트 입력을 다시 생성할 수 있습니다. 여러 테스트가 전역 난수 상태를 공유해 실행 순서에 따라 입력이 바뀌는 문제도 피할 수 있습니다.

무작위 테스트가 실패하면 **시드만 남기는 것보다 실제 실패 입력도 함께 남기는 편이 좋습니다.** 테스트 코드가 나중에 변경되면 같은 시드가 같은 의미의 입력을 만들지 않을 수도 있기 때문입니다.

예를 들면 다음처럼 실패 메시지에 입력을 포함할 수 있습니다.

```python
for _ in range(500):
    values = [
        rng.randint(-100, 100)
        for _ in range(rng.randint(0, 30))
    ]
    self.assertEqual(
        optimized(values),
        reference(values),
        msg=f"failed input: {values!r}",
    )
```

무작위 테스트의 목적은 “실행할 때마다 새로운 입력을 뽑는 것”이 아니라 **다양한 입력을 자동으로 만들면서도 실패를 다시 재현할 수 있게 하는 것**입니다.

## 독립적인 기준 구현 사용하기

복잡하거나 최적화된 구현은 더 단순한 기준 구현(reference implementation)과 비교해 검사할 수 있습니다.

```python
self.assertEqual(optimized(values), reference(values))
```

이 방식이 유효하려면 두 구현이 **동작 규칙은 같되 구현 경로는 가능한 한 독립적**이어야 합니다.

예를 들어 최적화 구현과 기준 구현이 모두 같은 정렬 보조 함수나 같은 필터링 함수를 호출한다면, 그 보조 함수의 버그가 두 결과에 동일하게 반영될 수 있습니다. 그러면 두 결과는 서로 같지만 둘 다 잘못된 상태가 됩니다.

따라서 기준 구현은 보통 다음 성질을 가지는 편이 좋습니다.

- 성능보다 단순성과 명확성을 우선함
- 최적화 구현의 내부 자료구조를 그대로 재사용하지 않음
- 비교하려는 핵심 규칙을 독립적으로 표현함

`command-checker`에서는 프로세스 수집과 결과 비교를 분리합니다. 프로세스를 실행하는 코드가 예상값 비교까지 다시 구현하지 않고, 수집한 값을 순수 비교 함수에 전달합니다.

이 분리는 프로세스 실행 자체의 문제와 결과 비교 규칙의 문제를 서로 다른 테스트에서 확인할 수 있게 합니다.

## 실패 주입하기

정상 경로만 테스트하면 오류 처리와 자원 정리 동작을 확인할 수 없습니다. **실패 주입(failure injection)**은 원하는 실패 상황을 테스트가 의도적으로 만들어 오류 경로를 검사하는 방법입니다.

예를 들어 다음 상황을 재현할 수 있어야 합니다.

- 파일을 읽을 수 없음
- 출력 파일을 쓸 수 없음
- 잘못된 CSV 헤더
- JSON에 예상하지 않은 필드가 있음
- 숫자가 `NaN` 또는 `Infinity`임
- 프로세스가 타임아웃을 넘김
- 자식 프로세스가 파이프를 계속 열어 둠
- `stdout`을 제한 없이 출력함

중요한 것은 실패 자체를 만드는 데서 끝나지 않는다는 점입니다. 실패가 발생했을 때 프로그램이 어떤 계약을 지켜야 하는지도 검사해야 합니다.

예를 들어 입력 파일이 존재하지 않는다면 다음을 각각 확인할 수 있습니다.

```text
오류가 정상 결과로 처리되지 않는가?
stderr에 사용자가 이해할 수 있는 오류가 기록되는가?
종료 상태가 성공(0)이 아닌가?
부분적으로 생성된 출력 파일이 남지 않는가?
```

실패를 반복해서 재현할 수 있도록 임시 디렉터리, 전용 테스트 프로그램, 필요한 경우 모의 객체를 사용합니다.

파일 권한처럼 운영체제나 실행 계정에 따라 결과가 달라질 수 있는 실패는 단순히 “권한을 제거하면 실패할 것”이라고 가정하지 말고, 실제 테스트 환경에서 안정적으로 재현되는 방법인지 확인해야 합니다.

## 임시 디렉터리 사용하기

파일 테스트에서는 실제 사용자 디렉터리 대신 테스트마다 독립된 임시 디렉터리를 사용합니다.

```python
import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)
    input_path = root / "data.csv"
    output_path = root / "report.json"

    input_path.write_text(
        "category,amount\nfood,12.50\n",
        encoding="utf-8",
    )

    # input_path와 output_path를 사용하는 코드 실행
    ...
```

`TemporaryDirectory()`의 컨텍스트가 끝나면 디렉터리와 그 안의 파일은 정리됩니다.

이 방식은 다음 문제를 줄여 줍니다.

- 테스트가 실제 사용자 파일을 읽거나 덮어쓰는 문제
- 이전 테스트가 만든 파일 때문에 다음 테스트 결과가 바뀌는 문제
- 동일한 파일 이름을 사용하는 테스트끼리 충돌하는 문제
- 개발자 컴퓨터에만 존재하는 경로를 우연히 참조하는 문제

테스트마다 새 디렉터리를 사용하면 **테스트 실행 순서에 따른 상태 공유**도 크게 줄어듭니다.

가능하면 테스트가 특정 현재 작업 디렉터리를 암묵적으로 기대하지 않게 하고, 사용할 경로를 명시적으로 구성합니다.

## 출력과 종료 상태 검사하기

CLI 프로그램에서는 반환값만이 아니라 출력 스트림과 종료 상태도 공개된 동작의 일부입니다.

일반적으로 다음을 구분합니다.

```text
stdout → 정상 결과처럼 다른 프로그램이 소비할 수 있는 출력
stderr → 오류, 경고, 진단 메시지
종료 상태 0 → 성공
0이 아닌 종료 상태 → 실패
```

구체적인 비영(0이 아닌) 종료 코드의 의미는 프로그램이 정의한 계약을 따릅니다.

함수를 직접 호출할 수 있다면 `stdout`과 `stderr`를 임시 스트림으로 바꿔 검사할 수 있습니다.

```python
import contextlib
import io

stderr = io.StringIO()

with contextlib.redirect_stderr(stderr):
    status = main(["missing.txt"])

self.assertEqual(status, 2)
self.assertIn("input file", stderr.getvalue())
```

정상 출력과 오류 출력을 구분해야 한다면 두 스트림을 모두 캡처합니다.

```python
stdout = io.StringIO()
stderr = io.StringIO()

with (
    contextlib.redirect_stdout(stdout),
    contextlib.redirect_stderr(stderr),
):
    status = main(["input.csv"])

self.assertEqual(status, 0)
self.assertEqual(stderr.getvalue(), "")
self.assertIn("total", stdout.getvalue())
```

함수를 직접 호출하는 테스트는 빠르고 내부 오류를 찾기 쉽지만, 실제 Python 모듈 진입점이나 설치된 콘솔 스크립트의 연결까지 보장하지는 않습니다.

따라서 실제 모듈 진입점과 콘솔 스크립트는 하위 프로세스로 별도 확인합니다.

```python
import subprocess
import sys

completed = subprocess.run(
    [sys.executable, "-m", "data_report", "missing.txt"],
    text=True,
    capture_output=True,
    check=False,
)

self.assertNotEqual(completed.returncode, 0)
self.assertIn("input file", completed.stderr)
```

여기서 `check=False`를 사용하는 이유는 실패 종료 상태 자체를 테스트하려는 경우 `subprocess.run()`이 먼저 예외를 발생시키지 않게 하기 위해서입니다. 테스트는 `returncode`, `stdout`, `stderr`를 직접 검사합니다.

하위 프로세스 테스트에서는 필요하다면 다음 실행 조건도 명시적으로 통제합니다.

- `cwd`: 현재 작업 디렉터리
- `env`: 환경 변수
- 입력 파일의 절대 경로 또는 임시 디렉터리 기준 경로
- 타임아웃

이 조건을 암묵적으로 두면 개발자 환경에서는 성공하지만 CI에서는 실패하는 테스트가 생길 수 있습니다.

## 테스트가 서로 독립적이어야 하는 이유

테스트는 가능하면 어떤 순서로 실행해도 같은 결과가 나와야 합니다.

다음과 같은 테스트는 실행 순서에 의존할 수 있습니다.

```text
test_a가 output.json을 생성함
test_b가 기존 output.json이 있다고 가정함
```

`test_b`를 단독 실행하면 실패하므로 독립적인 테스트가 아닙니다.

각 테스트는 자신에게 필요한 상태를 직접 준비하고, 사용한 상태를 정리해야 합니다.

특히 다음 상태를 테스트끼리 공유하지 않도록 주의합니다.

- 임시 파일과 디렉터리
- 전역 변수
- 전역 난수 상태
- 환경 변수
- 현재 작업 디렉터리
- 실행 중인 자식 프로세스

테스트 독립성은 단순히 “깔끔한 코드”를 위한 규칙이 아닙니다. 실패를 한 테스트로 좁히고 병렬 실행이나 선택 실행을 가능하게 만드는 조건입니다.

## 환경에 의존하는 테스트

일부 동작은 특정 운영체제에서만 의미가 있습니다. 예를 들어 POSIX 프로세스 그룹을 직접 사용하는 기능은 Windows와 같은 비-POSIX 환경에서는 같은 방식으로 검사할 수 없습니다.

이 경우 지원 여부를 테스트 코드에 명시합니다.

```python
import os
import unittest


@unittest.skipUnless(os.name == "posix", "POSIX 프로세스 그룹이 필요합니다.")
def test_timeout_terminates_spawned_process_group(self) -> None:
    ...
```

여기서 **skip은 성공(pass)이 아닙니다.** 해당 환경에서는 테스트 조건이 충족되지 않아 실행하지 않았다는 별도 결과입니다.

따라서 다음을 지킵니다.

- 실행할 수 없는 테스트를 성공한 것으로 보고하지 않습니다.
- 왜 건너뛰는지 구체적인 이유를 남깁니다.
- 특정 환경에서 반드시 보장해야 하는 동작이라면 그 환경을 포함한 CI에서 실제로 실행되게 합니다.

환경 의존 테스트를 무조건 제거하는 것이 목표가 아니라, **어느 환경에서 무엇을 검증했는지 명확하게 만드는 것**이 목표입니다.

## 프로젝트에 적용하기

### 필수: `data-report`

`data-report`의 테스트는 적어도 다음과 같은 잘못된 구현을 잡아낼 수 있어야 합니다.

- CSV와 JSON이 서로 다른 `Report`를 만드는 구현
- 예상하지 않은 필드를 조용히 무시하는 구현
- `NaN`이나 `Infinity`처럼 유한하지 않은 값을 합계에 포함하는 구현
- 금액 계산에 `float`를 사용해 이진 부동소수점 오차가 합계에 남는 구현
- `category` 출력 순서가 입력 순서에 따라 달라지는 구현
- `--output`이 지정되어도 파일이 아니라 `stdout`에만 쓰는 구현
- 입력 오류를 종료 상태 0으로 처리하는 구현

예를 들어 CSV와 JSON이 같은 의미의 데이터를 나타낸다면 두 입력 형식의 최종 `Report`가 같아야 한다는 계약을 테스트할 수 있습니다.

```text
CSV 입력 ─┐
          ├─> 같은 Report
JSON 입력 ─┘
```

이 테스트는 두 파서가 각각 “실행된다”는 것만 확인하는 것이 아니라, 서로 다른 입력 형식이 같은 도메인 의미로 수렴하는지를 확인합니다.

또한 정렬 테스트에서는 한 가지 이미 정렬된 입력만 사용해서는 부족합니다. 입력 순서를 바꾸어도 결과 순서가 안정적으로 동일한지 검사해야 입력 순서를 그대로 보존하는 잘못된 구현을 잡을 수 있습니다.

### 선택: `command-checker`

`command-checker`의 테스트는 적어도 다음 오류를 구분해서 잡아낼 수 있어야 합니다.

- 타임아웃과 출력 상한 초과를 같은 실패로 처리하는 구현
- 병렬 완료 순서를 그대로 결과 순서로 사용하는 구현
- XML 1.0에서 허용하지 않는 문자를 보고서에 그대로 쓰는 구현
- 타임아웃 뒤 자식 프로세스를 남기는 구현

프로세스 관련 테스트에서는 실제 외부 명령에 우연히 의존하기보다 테스트 전용 작은 프로그램을 만드는 편이 재현성이 좋습니다.

예를 들어 다음 동작을 각각 하는 테스트 프로그램을 준비할 수 있습니다.

```text
즉시 성공하고 정해진 stdout을 출력
정해진 stderr를 출력하고 비정상 종료
일정 시간보다 오래 대기
stdout을 계속 출력
자식 프로세스를 만든 뒤 대기
```

이렇게 하면 운영체제에 설치된 특정 명령의 버전이나 동작 차이보다 `command-checker`가 처리해야 하는 조건 자체를 직접 통제할 수 있습니다.

## 완료 기준

- 각 테스트 이름이 확인하려는 조건과 기대 동작을 설명합니다.
- 단위·통합·종단 간 테스트가 실제 확인 범위에 따라 나뉘어 있습니다.
- 계산 규칙은 가능한 한 외부 입출력과 분리되어 직접 검사할 수 있습니다.
- 경곗값과 실패 경로를 반복해서 재현할 수 있습니다.
- 표 기반 테스트는 같은 규칙을 공유하는 사례에 사용합니다.
- 작은 입력 공간은 조합 수를 계산한 뒤 현실적인 범위에서 전수 검사합니다.
- 무작위 테스트는 고정 시드를 사용하고 실패 입력을 확인할 수 있게 합니다.
- 최적화 구현과 비교하는 기준 구현은 가능한 한 독립적으로 작성합니다.
- 임시 디렉터리를 사용해 테스트 간 파일 상태를 공유하지 않습니다.
- 각 테스트가 다른 테스트의 실행 결과나 순서에 의존하지 않습니다.
- CLI 테스트는 필요한 경우 `stdout`, `stderr`, 종료 상태, 출력 파일을 각각 검사합니다.
- 지원하지 않는 환경의 테스트는 구체적인 이유와 함께 건너뜁니다.
