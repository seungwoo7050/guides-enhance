# CLI 검사기 설계

> 선택 심화 문서입니다. 외부 CLI 프로그램의 실제 실행 결과를 반복해서 검사해야 할 때 사용합니다.

## 학습 목표

이 문서를 마치면 다음 내용을 설명하고 구현할 수 있어야 합니다.

- CLI 프로그램을 검사할 때 확인해야 하는 외부 동작
- 입력 명세 오류와 실행 결과 불일치의 구분
- 프로세스 실행, 결과 비교, 보고서 생성을 별도 모듈로 나누는 방법
- 타임아웃과 출력 상한을 포함한 프로세스 정리 절차
- `stdout`과 `stderr`를 동시에 수집해야 하는 이유
- 병렬 실행 중에도 입력 순서를 유지하는 결과 수집 방식
- JSON/JUnit 보고서를 같은 실행 결과에서 만드는 방법
- 소스 트리와 설치된 콘솔 스크립트를 모두 확인하는 방법

연결 프로젝트는 [`command-checker`](../../exercises/command-checker/README.md)입니다.

## 선행 개념

- 파일과 JSON 입력 검증
- `subprocess`를 사용한 외부 프로세스 실행
- 제한된 동시 실행과 자원 정리
- 단위·통합·종단 간 테스트의 역할
- 예상한 실패와 구현 오류의 구분

이 문서에서 검사 대상은 **현재 Python 프로세스 안에서 직접 호출하는 함수**가 아니라 **별도 운영체제 프로세스로 실행되는 CLI 프로그램**입니다. 따라서 함수 반환값뿐 아니라 프로세스가 외부에 드러내는 모든 동작을 검사해야 합니다.

## 검사할 외부 동작

함수를 직접 호출하는 단위 테스트만으로는 CLI 프로그램이 실제로 제공하는 동작을 모두 확인할 수 없습니다.

```text
명령줄 인자
현재 작업 디렉터리
환경 변수
stdin
stdout
stderr
종료 상태
타임아웃
자식 프로세스 수명
보고서 저장
```

각 항목은 다음처럼 서로 다른 실패를 만들 수 있습니다.

- 인자가 잘못 전달되면 대상 프로그램이 다른 작업을 수행할 수 있습니다.
- `cwd`가 달라지면 상대 경로 해석 결과가 달라질 수 있습니다.
- 환경 변수가 누락되면 설정 기반 동작을 재현할 수 없습니다.
- `stdin` 전달이 막히면 프로그램이 입력을 기다리며 종료하지 않을 수 있습니다.
- `stdout`과 `stderr`를 잘못 합치면 정상 출력과 오류 출력을 구분할 수 없습니다.
- 종료 상태를 무시하면 실패한 프로그램을 성공으로 오인할 수 있습니다.
- 타임아웃 뒤 자식 프로세스가 남으면 테스트가 끝난 뒤에도 외부 상태가 유지됩니다.
- 보고서 파일을 부분적으로 쓰면 소비자가 불완전한 결과를 읽을 수 있습니다.

`command-checker`는 이런 조건을 JSON 사례에 기록하고 실제 프로세스 실행 결과와 비교합니다.

## 실행 방법

```text
command-checker --cases CASES [--jobs N]
                [--json-report PATH]
                [--junit-report PATH]
                -- COMMAND [ARG ...]
```

`--` 뒤에는 검사할 실제 명령과 기본 인자를 전달합니다.

예를 들어 다음 명령은 `sorter` 프로그램을 사례 파일에 따라 검사한다고 가정할 수 있습니다.

```sh
command-checker --cases cases.json -- sorter
```

사례 파일은 JSON 배열입니다.

```json
[
  {
    "name": "ascending",
    "args": [],
    "stdin": "3 1 2\n",
    "stdout": "1\n2\n3\n",
    "stderr": "",
    "returncode": 0,
    "timeout": 2.0,
    "output_limit": 1048576
  }
]
```

각 사례는 하나의 독립적인 프로세스 실행을 설명합니다.

```text
기본 COMMAND + 사례별 args
+ 사례별 stdin
+ 사례별 cwd와 환경
→ 프로세스 실행
→ stdout / stderr / returncode 수집
→ 예상값과 비교
→ Result 생성
```

## 실패 유형 구분하기

검사기의 오류를 모두 같은 “실패”로 처리하면 사용자가 무엇을 고쳐야 하는지 알기 어렵습니다.

`command-checker`는 다음 세 상태를 구분합니다.

```text
검사기 자체를 정상적으로 실행할 수 없음 → 종료 상태 2
검사는 실행했지만 대상 결과가 예상과 다름 → 종료 상태 1
모든 사례가 예상과 일치함 → 종료 상태 0
```

### 입력 또는 실행 환경 오류

다음 문제는 대상 프로그램의 결과 불일치가 아니라 검사를 시작하거나 정상적으로 마무리할 수 없는 오류입니다.

- JSON 문법 오류
- 필드 타입 오류
- 중복된 사례 이름
- 존재하지 않는 작업 디렉터리
- 잘못된 환경 변수 이름이나 값
- 실행 파일을 찾을 수 없거나 실행할 수 없음
- 프로세스를 시작하거나 정리할 수 없음
- 보고서 파일을 저장할 수 없음

이 경우 종료 상태 2를 반환합니다.

예를 들어 사례 파일의 `"timeout": "two"`는 대상 프로그램이 틀린 것이 아니라 사례 명세 자체가 잘못된 것입니다.

```text
잘못된 사례 명세
→ 대상 프로그램을 정상적으로 검사할 수 없음
→ command-checker 종료 상태 2
```

### 실행 결과 불일치

대상 프로그램을 실제로 실행하고 결과를 받았지만 예상과 다른 경우입니다.

- `returncode` 불일치
- `stdout` 불일치
- `stderr` 불일치
- 타임아웃
- 출력 상한 초과

각 사례를 `Result(passed=False, ...)`로 기록하고 전체 종료 상태 1을 반환합니다.

타임아웃과 출력 상한 초과는 모두 프로세스를 중단시킬 수 있지만 **같은 실패가 아닙니다.**

```text
timeout
→ 제한 시간 안에 종료하지 못함

output_limit
→ 허용한 출력 크기를 넘김
```

사용자가 원인을 구분할 수 있도록 `Result`에도 서로 다른 실패 원인을 기록해야 합니다.

### 성공

모든 사례가 예상값과 일치하면 종료 상태 0을 반환합니다.

이 구분이 유지되어야 사용자가 다음 중 무엇을 고쳐야 하는지 판단할 수 있습니다.

```text
사례 파일 또는 검사 실행 환경
대상 CLI 프로그램
아무것도 고칠 필요 없음
```

## 핵심 데이터 흐름

구현을 시작하기 전에 전체 흐름을 먼저 고정합니다.

```text
cases.json
   │
   ▼
specification.py
   │  검증된 Case
   ▼
runner.py
   │
   ├── process.py ── 실제 프로세스 실행
   │                   │
   │                   ▼
   │                관측값
   │                   │
   └── comparison.py ◀─┘
           │
           ▼
         Result
           │
           ├── 터미널 출력
           ├── JSON 보고서
           └── JUnit 보고서
```

중요한 점은 프로세스 실행 코드가 “통과/실패”까지 직접 결정하지 않는다는 것입니다. `process.py`는 관측한 실행 결과를 수집하고, `comparison.py`가 예상값과 비교해 의미를 부여합니다.

## 모듈별 작업

| 모듈 | 수행하는 작업 |
|---|---|
| `model.py` | 검증된 `Case`, 실행 결과 `Result`, 입력·실행 예외 정의 |
| `comparison.py` | `returncode`, `stdout`, `stderr`, 타임아웃, 출력 상한 비교 |
| `specification.py` | JSON을 읽고 필드별로 검사해 `Case`로 변환 |
| `process.py` | 프로세스 시작, 파이프 수집, 마감 시각 확인, 신호 전송, 정리 |
| `runner.py` | 실행 파일 선택, 순차·병렬 실행, 결과 출력, 종료 상태 계산 |
| `reports.py` | JSON/JUnit 문자열 생성과 파일 교체 |
| `cli.py` | 인자 파싱, 오류 메시지, 전체 함수 호출 |
| `_command_checker_build.py` | wheel 메타데이터와 파일 목록 생성 |

의존 방향은 다음과 같습니다.

```text
model ← comparison
model ← specification
model ← process
model ← reports

runner → process, comparison
cli → specification, runner, reports
```

여기서 `model`은 다른 상위 모듈을 알지 않는 가장 안쪽 계층입니다.

예를 들어 다음 구조는 피합니다.

```text
process.py → reports.py
reports.py → runner.py
runner.py  → process.py
```

이렇게 되면 프로세스 실행, 결과 수집, 보고서 저장이 서로 순환하며 독립적으로 테스트하기 어려워집니다.

`process.py`가 터미널 문구를 정하거나 `reports.py`가 명령을 실행하면 서로 다른 작업이 다시 섞인 것입니다.

## 구현 순서

### 1. 패키지와 진입점

- `pyproject.toml`에서 패키지 메타데이터와 콘솔 스크립트를 선언합니다.
- `__main__.py`와 설치된 명령이 같은 `cli.main`을 호출합니다.

예를 들어 두 실행 방법이 모두 같은 코드 경로를 지나야 합니다.

```sh
python -m command_checker ...
command-checker ...
```

진입점별로 인자 파싱이나 종료 상태 계산을 따로 구현하면 두 실행 방법의 동작이 달라질 수 있습니다.

### 2. `Case`, `Result`, 예외

검증을 통과한 입력은 `Case`로 저장합니다.

개념적으로 `Case`에는 다음 정보가 들어갑니다.

```text
name
args
stdin
expected stdout
expected stderr
expected returncode
cwd
environment
timeout
output_limit
```

프로세스 실행 뒤에는 `Result`를 만듭니다.

`Result`에는 최소한 다음 정보를 구분해서 보존할 수 있어야 합니다.

```text
어떤 Case의 결과인지
통과 여부
실제 returncode
실제 stdout
실제 stderr
실패 원인
타임아웃 여부
출력 상한 초과 여부
```

명세 오류와 프로세스 관리 오류도 같은 예외 하나로 뭉치지 않습니다.

예를 들어 다음처럼 의미를 나눌 수 있습니다.

```text
SpecificationError
→ 사례 파일이 잘못됨

ProcessError
→ 프로세스를 시작하거나 정리할 수 없음

ReportError
→ 보고서를 저장할 수 없음
```

정확한 클래스 이름보다 **오류 범주가 호출자에게 구분되어 전달되는 것**이 중요합니다.

### 3. 결과 비교

`returncode`, `stdout`, `stderr`를 공백과 줄바꿈까지 정확히 비교합니다.

예를 들어 다음 두 문자열은 서로 다릅니다.

```text
"ok\n"
"ok"
```

CLI 출력 계약에서 마지막 줄바꿈도 의미가 있을 수 있기 때문입니다.

비교 함수는 프로세스 실행 없이 직접 테스트할 수 있게 작성합니다.

개념적으로 다음과 같은 입력만 받으면 됩니다.

```text
Case의 기대값
+
프로세스에서 실제로 관측한 값
→ Result
```

이렇게 하면 실행 코드의 복잡성과 비교 규칙의 복잡성을 분리할 수 있습니다.

### 4. JSON 사례 검증

외부 JSON은 신뢰하지 않습니다. `json.loads()`가 성공했다고 해서 올바른 사례라는 뜻은 아닙니다.

다음 순서로 검사합니다.

```text
JSON 문법
→ 최상위 배열 여부
→ 각 원소가 객체인지
→ 필수 필드 존재 여부
→ 각 필드 타입
→ 필드별 값 범위
→ 사례 간 제약
→ Case 생성
```

다음 조건을 명시적으로 검사합니다.

- 최상위 값은 배열이어야 합니다.
- 각 사례는 객체여야 합니다.
- 사례 이름은 중복될 수 없습니다.
- 타임아웃은 유한한 양수여야 합니다.
- 출력 상한은 양의 정수여야 합니다.
- `cwd`는 사례 파일 기준 상대 경로로 해석합니다.
- 환경 변수 키와 값에 사용할 수 없는 문자를 거부합니다.
- 알려지지 않은 필드를 허용하지 않는다면 명시적으로 거부합니다.

특히 숫자형 필드에서는 `NaN`과 `Infinity` 같은 비유한 값이 예상치 않게 들어오지 않도록 검사합니다.

### 5. 실행 파일 선택

사용자가 `-- COMMAND ...`로 지정한 실행 파일은 **사례마다 다시 찾지 않고 한 번 결정**합니다.

예를 들어 `COMMAND`가 `tool`이고 각 사례가 서로 다른 `PATH`를 전달한다고 가정합니다.

사례마다 다시 `PATH`를 탐색하면 다음처럼 서로 다른 실행 파일이 선택될 수 있습니다.

```text
case A PATH → /a/bin/tool
case B PATH → /b/bin/tool
```

그러면 같은 명령을 검사한다고 생각했지만 실제로는 다른 프로그램을 실행하게 됩니다.

따라서 호출 환경에서 실행 파일을 한 번 선택하고 절대 경로로 고정합니다.

```text
"tool"
→ /usr/local/bin/tool
→ 모든 사례에서 같은 경로 사용
```

사례별 환경 변수는 대상 프로세스의 실행 환경을 바꾸는 용도이지, 검사할 실행 파일 자체를 바꾸는 용도가 아닙니다.

### 6. 사례 한 건 실행

하나의 `Case`를 실행할 때는 다음 값을 명시적으로 전달합니다.

```text
실행 파일
기본 인자
사례별 args
stdin
cwd
environment
timeout
output_limit
```

그 뒤 다음 값을 수집합니다.

```text
stdout
stderr
returncode
timeout 발생 여부
output_limit 초과 여부
```

`process.py`는 이 관측값을 얻는 데 집중하고, 예상값과의 비교는 `comparison.py`에 맡깁니다.

### 7. `stdout`과 `stderr`를 동시에 읽기

프로세스의 `stdout`과 `stderr`는 별도의 파이프입니다.

한쪽을 끝까지 읽은 뒤 다른 쪽을 읽는 방식은 교착을 만들 수 있습니다.

예를 들어 대상 프로세스가 다음처럼 동작한다고 가정합니다.

```text
stderr를 매우 많이 씀
→ stderr 파이프 버퍼가 가득 참
→ 대상 프로세스가 stderr 쓰기에서 멈춤
→ 검사기는 stdout이 EOF가 되기를 기다림
→ 대상은 종료하지 못함
```

따라서 두 출력 스트림을 **동시에 진전시켜야 합니다.**

POSIX 환경에서는 파이프를 논블로킹 모드로 두고 준비된 스트림만 읽는 방식으로 구현할 수 있습니다.

개념적인 루프는 다음과 같습니다.

```text
while 프로세스 또는 열려 있는 파이프가 남아 있음:
    현재 시각 확인
    timeout 여부 확인
    읽을 수 있는 stdout/stderr 확인
    준비된 스트림에서 일부 바이트 읽기
    누적 출력 크기 확인
    프로세스 종료 여부 확인
```

핵심은 어느 한 파이프의 EOF를 기다리느라 다른 파이프를 방치하지 않는 것입니다.

### 8. 바이트 기준 출력 상한

출력 상한은 **디코딩된 문자 수가 아니라 실제 읽은 바이트 수**를 기준으로 적용하는 편이 명확합니다.

UTF-8에서는 문자 하나가 여러 바이트일 수 있기 때문입니다.

예를 들어 다음 두 문자열은 문자 수가 같더라도 UTF-8 바이트 수가 다를 수 있습니다.

```text
"abc"
"가나다"
```

따라서 프로세스에서 읽는 단계에서 바이트 수를 누적하고 제한을 검사합니다.

또한 상한을 넘긴 뒤에도 계속 모든 출력을 메모리에 저장해서는 안 됩니다.

```text
출력 제한 초과 감지
→ 실패 원인 기록
→ 프로세스 그룹 종료 시작
→ 남은 자원 정리
```

출력 상한은 메모리 사용량을 제한하는 안전장치이므로, 초과 후 무한히 수집하면 제한의 의미가 없어집니다.

### 9. 프로세스 수명 제한

타임아웃과 출력 상한을 안전하게 처리하려면 프로세스 하나만이 아니라 그 프로세스가 만든 자식까지 고려해야 합니다.

대상을 새 POSIX 세션에서 시작하면 대상 프로세스를 루트로 하는 별도 프로세스 그룹을 관리할 수 있습니다.

```text
command-checker
   │
   └── 새 세션 / 프로세스 그룹
         └── target
               └── child
```

제한을 넘겼을 때 부모인 `target`만 종료하면 `child`가 계속 살아남을 수 있습니다.

따라서 프로세스 그룹 전체를 종료 대상으로 삼습니다.

개념적인 정리 순서는 다음과 같습니다.

```text
1. 제한 초과 또는 오류 감지
2. 프로세스 그룹에 SIGTERM 전송
3. 짧은 종료 유예 기간 동안 상태 확인
4. 여전히 살아 있으면 SIGKILL 전송
5. 프로세스 종료 상태 회수
6. stdout/stderr 파이프 닫기
```

`SIGTERM`은 정상적인 정리 기회를 주는 신호이고, `SIGKILL`은 응답하지 않는 프로세스를 강제로 종료하기 위한 마지막 수단입니다.

### 10. 어떤 예외가 발생해도 정리하기

프로세스를 시작한 뒤에는 정상 경로뿐 아니라 모든 예외 경로에서 정리가 필요합니다.

예를 들어 다음 순간에도 예외가 발생할 수 있습니다.

- 파이프 모드 설정
- 출력 읽기
- 디코딩
- 시간 확인 또는 선택 시스템 호출
- 결과 객체 생성
- 상위 코드가 취소됨

따라서 “정상적으로 제한을 넘겼을 때만” 정리하는 구조로는 부족합니다.

프로세스를 시작한 함수는 자신이 만든 프로세스 그룹과 파이프의 소유권을 가졌다고 보고, 함수가 끝나기 전에 정리를 책임져야 합니다.

```text
process.py가 프로세스를 시작함
→ process.py가 종료와 wait까지 책임짐
```

상위 모듈이 “아마 process.py에서 정리했을 것”이라고 추측하게 만들지 않습니다.

### 11. 순차 실행과 결과 표시

처음에는 병렬 실행보다 순차 실행을 먼저 완성합니다.

```text
case 0 실행 → Result 0
case 1 실행 → Result 1
case 2 실행 → Result 2
```

사례 하나가 실패해도 다음 사례를 계속 실행합니다. 사용자는 한 번의 실행으로 가능한 많은 불일치를 확인할 수 있어야 합니다.

결과는 입력 순서대로 반환합니다.

터미널 출력도 성격에 따라 구분합니다.

```text
정상적인 통과 요약 → stdout
실패 세부 내용     → stderr
```

모든 결과를 확인한 뒤 전체 종료 상태를 계산합니다.

```text
하나라도 Result.passed == False
→ 종료 상태 1

모두 통과
→ 종료 상태 0
```

검사 과정 자체에서 명세 오류나 실행 환경 오류가 발생하면 앞서 정의한 종료 상태 2를 사용합니다.

### 12. JSON/JUnit 보고서

두 보고서는 같은 실행 결과를 서로 다른 형식으로 표현해야 합니다.

다음 구조를 유지합니다.

```text
모든 사례 실행
→ Result 목록 확정
→ JSON 생성
→ JUnit 생성
```

JSON과 JUnit을 만들기 위해 대상 프로그램을 다시 실행해서는 안 됩니다.

그렇게 하면 두 실행 사이에 외부 상태가 바뀌어 보고서가 서로 다른 사실을 기록할 수 있습니다.

### 13. XML 1.0 문자 처리

JUnit은 XML이므로 JSON과 달리 모든 Unicode 코드 포인트를 그대로 넣을 수 있는 것은 아닙니다.

동적 XML 텍스트에는 다음 값이 포함될 수 있습니다.

- 사례 이름
- 실패 메시지
- `stdout`
- `stderr`

대상 프로그램이 XML 1.0에서 허용하지 않는 문자를 출력했다면 보고서를 생성하기 전에 안전한 대체 문자로 바꿉니다.

중요한 점은 **CLI 출력 비교 자체를 바꾸는 것이 아니라 JUnit 직렬화 단계에서만 정리하는 것**입니다.

```text
실제 stdout
→ 비교에는 원래 내용 사용
→ JUnit에 쓸 때 XML 허용 문자로 정리
```

### 14. 보고서 파일을 완성한 뒤 교체하기

보고서를 최종 경로에 직접 쓰다가 중간에 실패하면 부분 파일이 남을 수 있습니다.

```text
report.json에 직접 쓰기
→ 중간 오류
→ 절반만 기록된 report.json이 남음
```

이를 피하려면 같은 파일 시스템의 임시 경로에 전체 내용을 먼저 완성한 뒤 `os.replace()`로 최종 경로를 교체합니다.

```text
report.json.tmp에 전체 내용 작성
→ flush/close
→ os.replace(temp, final)
```

`os.replace()`가 지원되는 같은 파일 시스템 안에서는 최종 이름이 기존 완성 파일 또는 새 완성 파일을 가리키도록 만들 수 있어, 소비자가 부분 내용을 보는 위험을 줄일 수 있습니다.

여러 보고서 파일을 동시에 하나의 트랜잭션으로 교체하는 것은 이 문서의 범위 밖입니다.

### 15. 제한된 병렬 실행

순차 실행이 완성된 뒤에 병렬화를 추가합니다.

```python
ThreadPoolExecutor(max_workers=jobs)
```

`max_workers=jobs`는 동시에 실행되는 사례 수를 제한합니다.

중요한 점은 **완료 순서와 사용자에게 보여 줄 결과 순서가 다를 수 있다는 것**입니다.

예를 들어 입력 순서가 다음과 같다고 가정합니다.

```text
0: slow
1: fast
2: medium
```

실제 완료 순서는 다음과 같을 수 있습니다.

```text
1 → 2 → 0
```

그렇더라도 최종 결과는 원래 입력 순서로 정렬해야 합니다.

```text
Result[0]
Result[1]
Result[2]
```

가장 단순한 방법은 제출 시 입력 인덱스를 함께 보존하는 것입니다.

```text
(index, future)
```

또는 결과 배열을 미리 만들고 완료된 작업의 원래 인덱스 위치에 결과를 저장할 수 있습니다.

병렬 실행 여부가 사용자에게 보이는 사례 순서를 바꾸지 않게 하는 것이 핵심입니다.

### 16. 작업자와 보고서 저장 분리

병렬 작업자는 사례 한 건을 실행하고 `Result`를 반환하는 데 집중합니다.

작업자가 직접 JSON/JUnit 보고서 파일을 수정하게 하면 여러 작업자가 같은 파일에 동시에 접근할 수 있습니다.

```text
worker A ─┐
          ├─ report.json 동시 수정 → 경쟁 조건
worker B ─┘
```

대신 다음 구조를 사용합니다.

```text
worker → Result
worker → Result
worker → Result
        ↓
runner가 전체 Result 수집
        ↓
reports.py가 한 번에 파일 생성
```

이렇게 하면 결과 순서, 직렬화, 파일 교체를 한 위치에서 통제할 수 있습니다.

### 17. CLI와 패키지 완성

CLI 계층은 내부 예외를 사용자에게 보이는 메시지와 종료 상태로 바꿉니다.

예를 들어:

```text
SpecificationError → stderr + 종료 상태 2
ProcessError       → stderr + 종료 상태 2
ReportError        → stderr + 종료 상태 2
불일치 Result 존재 → 종료 상태 1
모두 통과          → 종료 상태 0
```

라이브러리 내부 함수가 직접 `sys.exit()`를 호출하게 만들기보다 최상위 `main()`이 정수 상태를 반환하고 진입점에서 `SystemExit`로 바꾸는 편이 테스트하기 쉽습니다.

```python
raise SystemExit(main())
```

### 18. 설치된 패키지 검증

소스 트리에서 실행되는 것만 확인해서는 패키징 오류를 잡을 수 없습니다.

다음 순서로 확인합니다.

```text
wheel 생성
→ 새 가상 환경 생성
→ wheel 설치
→ 저장소 밖으로 이동
→ 설치된 command-checker 실행
```

이 검사는 다음과 같은 오류를 찾습니다.

- 패키지 파일이 wheel에 빠짐
- 콘솔 스크립트가 잘못된 함수로 연결됨
- 소스 루트가 `PYTHONPATH`에 있을 때만 import됨
- 빌드 메타데이터와 실제 패키지 내용이 다름

## 전체 구현 순서 요약

실제 구현은 다음 순서로 진행하면 의존성을 한 단계씩 검증하기 쉽습니다.

```text
1. 패키지와 진입점
2. Case / Result / 예외
3. 결과 비교
4. JSON 사례 검증
5. 실행 파일 선택
6. 사례 한 건 실행
7. stdout/stderr 동시 수집
8. timeout / output_limit / 프로세스 그룹 정리
9. 순차 runner
10. JSON / JUnit 보고서
11. 제한된 병렬 실행
12. CLI 오류 처리
13. wheel 생성과 설치된 콘솔 스크립트 검증
```

복잡한 프로세스 관리와 병렬화를 먼저 구현하지 않고, 순수한 데이터 모델과 비교 함수부터 고정하는 것이 중요합니다.

## 보고서 생성 원칙

JSON과 JUnit을 각자 다른 결과에서 만들면 두 보고서가 서로 달라질 수 있습니다.

다음 흐름을 유지합니다.

```text
모든 사례의 `Result`를 확정합니다.
→ 같은 `Result` 시퀀스로 JSON을 만듭니다.
→ 같은 `Result` 시퀀스로 JUnit을 만듭니다.
→ 각 파일을 임시 경로에 완성합니다.
→ 최종 경로로 교체합니다.
```

여기서 보고서 형식은 다르지만 입력 데이터는 동일합니다.

```text
Result
 ├─ JSON 표현
 └─ JUnit XML 표현
```

보고서 생성 함수는 가능하면 문자열 또는 바이트 생성과 파일 저장을 분리합니다.

예를 들어 다음 두 단계로 나누면 직렬화 자체를 파일 시스템 없이 단위 테스트할 수 있습니다.

```text
render_json(results)  → str
render_junit(results) → str

write_atomic(path, text)
```

## 테스트에서 잡아야 할 잘못된 구현

### 실행 파일 선택 오류

- 사례별 `PATH`에서 실행 파일을 다시 찾아 다른 파일을 실행합니다.

이를 잡으려면 서로 다른 `PATH`를 가진 사례를 준비하되 실제 검사 대상 실행 파일은 처음 선택한 절대 경로로 유지되는지 확인합니다.

### 프로세스 정리 오류

- 타임아웃 뒤 부모 프로세스만 종료하고 자식 프로세스를 남깁니다.
- `SIGTERM`만 보내고 종료 여부를 확인하지 않습니다.
- 예외 경로에서 `wait()` 또는 파이프 정리를 건너뜁니다.

테스트용 프로그램이 자식 프로세스를 만든 뒤 오래 대기하게 하면 이런 오류를 재현할 수 있습니다.

### 파이프 처리 오류

- `stdout`과 `stderr`를 차례로 읽다가 파이프 교착이 발생합니다.
- 한 스트림만 계속 읽고 다른 스트림을 방치합니다.
- 프로세스는 종료했지만 남은 파이프를 닫지 않습니다.

양쪽 스트림에 충분한 양의 데이터를 동시에 쓰는 테스트 프로그램으로 확인할 수 있습니다.

### 출력 상한 오류

- 출력 상한을 넘긴 뒤에도 계속 메모리에 저장합니다.
- 문자 수와 바이트 수를 혼동합니다.
- 출력 상한 초과를 타임아웃으로 기록합니다.

### 병렬 실행 오류

- 병렬 작업의 완료 순서를 그대로 최종 결과 순서로 사용합니다.
- 작업자가 같은 보고서 파일을 동시에 수정합니다.
- 한 작업자의 예외가 다른 실행 중 프로세스 정리를 방해합니다.

### 보고서 오류

- JSON과 JUnit이 서로 다른 결과 목록을 사용합니다.
- XML 1.0에서 허용하지 않는 문자를 그대로 씁니다.
- 최종 보고서 파일에 직접 쓰다가 부분 파일을 남깁니다.

### 패키징 오류

- 소스 루트에 있을 때만 패키지 `import`가 성공합니다.
- 설치된 콘솔 스크립트가 `python -m command_checker`와 다른 코드를 호출합니다.

## 테스트용 대상 프로그램 만들기

프로세스 테스트에서 시스템에 설치된 임의의 명령을 사용하면 운영체제와 버전에 따라 동작이 달라질 수 있습니다.

대신 원하는 동작만 수행하는 작은 테스트용 프로그램을 준비합니다.

예를 들어 다음 동작을 각각 만들 수 있습니다.

```text
정해진 stdout을 출력하고 성공 종료
정해진 stderr를 출력하고 실패 종료
stdin을 그대로 stdout에 복사
환경 변수와 cwd를 출력
timeout보다 오래 대기
stdout을 계속 출력
stdout과 stderr를 동시에 많이 출력
자식 프로세스를 만든 뒤 대기
XML에 넣기 어려운 제어 문자를 출력
```

이런 프로그램은 검사기의 특정 분기만 정확히 재현하므로 실패 원인을 좁히기 쉽습니다.

## 한계

- Windows 네이티브 프로세스 트리 종료는 지원하지 않습니다.
- 셸 파이프라인 문법을 해석하지 않습니다. 명령과 인자는 이미 분리된 목록으로 받습니다.
- 바이너리 프로토콜이 아니라 UTF-8 텍스트 CLI를 검사합니다.
- 디코딩할 수 없는 바이트는 대체 문자로 바꿉니다.
- 원격 실행, 컨테이너 오케스트레이션, 분산 테스트 스케줄링은 다루지 않습니다.
- 여러 보고서 파일을 하나의 트랜잭션으로 묶지는 않습니다.

“셸 파이프라인 문법을 해석하지 않는다”는 것은 다음과 같은 문자열을 셸에 다시 해석시키지 않는다는 뜻입니다.

```text
"producer | consumer"
```

대신 실행 파일과 인자를 분리된 목록으로 전달합니다. 이렇게 하면 셸 인용 규칙과 명령 주입 문제를 검사기 자체의 범위에서 제외할 수 있습니다.

## 완료 기준

- 입력·실행 환경 오류와 실행 결과 불일치를 구분합니다.
- 전체 종료 상태 0, 1, 2의 의미를 설명할 수 있습니다.
- 프로세스 실행과 결과 비교를 독립적으로 테스트합니다.
- 사례 파일을 검증한 뒤에만 `Case`를 만듭니다.
- 실행 파일은 사례별 환경 변수와 무관하게 한 번 선택해 고정합니다.
- `stdout`과 `stderr`를 동시에 수집해야 하는 이유를 설명할 수 있습니다.
- 출력 상한을 바이트 기준으로 적용하고 초과 뒤 무제한으로 저장하지 않습니다.
- 프로세스와 모든 파이프를 어느 함수가 정리하는지 설명할 수 있습니다.
- 타임아웃이나 출력 상한을 넘겨도 자식 프로세스가 남지 않습니다.
- 병렬 실행이 사용자에게 보여 주는 결과 순서를 바꾸지 않습니다.
- 작업자가 보고서 파일을 직접 수정하지 않습니다.
- JSON과 JUnit은 같은 `Result` 시퀀스에서 생성됩니다.
- XML 1.0에서 허용하지 않는 문자를 JUnit 직렬화 단계에서 처리합니다.
- 보고서 파일은 전체 내용이 완성된 뒤에만 최종 경로로 교체됩니다.
- 설치된 `command-checker`를 저장소 밖에서 실행할 수 있습니다.
