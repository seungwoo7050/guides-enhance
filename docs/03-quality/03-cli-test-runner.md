# CLI 검사기 설계

> 선택 심화 문서입니다. 외부 CLI 프로그램의 실제 실행 결과를 반복해서 검사해야 할 때 사용합니다.

## 학습 목표

이 문서를 마치면 다음 내용을 설명하고 구현할 수 있어야 합니다.

- CLI 프로그램을 검사할 때 확인해야 하는 외부 동작
- 입력 명세 오류와 실행 결과 불일치의 구분
- 프로세스 실행, 결과 비교, 보고서 생성을 별도 모듈로 나누는 방법
- 타임아웃과 출력 상한을 포함한 프로세스 정리 절차
- 병렬 실행 중에도 입력 순서를 유지하는 결과 수집 방식
- 소스 트리와 설치된 콘솔 스크립트를 모두 확인하는 방법

연결 프로젝트는 [`command-checker`](../../exercises/command-checker/README.md)입니다.

## 선행 개념

- 파일과 JSON 입력 검증
- `subprocess`를 사용한 외부 프로세스 실행
- 제한된 동시 실행과 자원 정리
- 단위·통합·종단 간 테스트의 역할
- 예상한 실패와 구현 오류의 구분

## 검사할 외부 동작

함수를 직접 호출하는 단위 테스트만으로는 CLI 프로그램이 실제로 제공하는 동작을 모두 확인할 수 없습니다.

```text
명령줄 인자
현재 작업 디렉터리
환경 변수
stdin
stdout
stderr
종료 상태
타임아웃
자식 프로세스 수명
보고서 저장
```

`command-checker`는 이 항목을 JSON 사례에 기록하고 실제 프로세스 실행 결과와 비교합니다.

## 실행 방법

```text
command-checker --cases CASES [--jobs N]
                [--json-report PATH]
                [--junit-report PATH]
                -- COMMAND [ARG ...]
```

사례 파일은 JSON 배열입니다.

```json
[
  {
    "name": "ascending",
    "args": [],
    "stdin": "3 1 2\n",
    "stdout": "1\n2\n3\n",
    "stderr": "",
    "returncode": 0,
    "timeout": 2.0,
    "output_limit": 1048576
  }
]
```

## 실패 유형 구분하기

### 입력 또는 실행 환경 오류

다음 문제는 대상 프로그램의 결과 불일치가 아니라 검사를 시작하거나 마무리할 수 없는 오류입니다.

- JSON 문법 오류
- 필드 타입 오류
- 중복된 사례 이름
- 존재하지 않는 작업 디렉터리
- 잘못된 환경 변수 이름이나 값
- 실행 파일을 찾을 수 없거나 실행할 수 없음
- 프로세스를 시작하거나 정리할 수 없음
- 보고서 파일을 저장할 수 없음

이 경우 종료 상태 2를 반환합니다.

### 실행 결과 불일치

대상 프로그램을 실행하고 결과를 받았지만 예상과 다른 경우입니다.

- `returncode` 불일치
- `stdout` 불일치
- `stderr` 불일치
- 타임아웃
- 출력 상한 초과

각 사례를 `Result(passed=False, ...)`로 기록하고 전체 종료 상태 1을 반환합니다.

### 성공

모든 사례가 예상값과 일치하면 종료 상태 0을 반환합니다.

이 구분이 유지되어야 사용자가 사례 파일이나 실행 환경을 고쳐야 하는지, 대상 프로그램을 고쳐야 하는지 판단할 수 있습니다.

## 모듈별 작업

| 모듈 | 수행하는 작업 |
|---|---|
| `model.py` | 검증된 `Case`, 실행 결과 `Result`, 입력·실행 예외 정의 |
| `comparison.py` | `returncode`, `stdout`, `stderr`, 타임아웃, 출력 상한 비교 |
| `specification.py` | JSON을 읽고 필드별로 검사해 `Case`로 변환 |
| `process.py` | 프로세스 시작, 파이프 수집, 마감 시각 확인, 신호 전송, 정리 |
| `runner.py` | 실행 파일 선택, 순차·병렬 실행, 결과 출력, 종료 상태 계산 |
| `reports.py` | JSON/JUnit 문자열 생성과 파일 교체 |
| `cli.py` | 인자 파싱, 오류 메시지, 전체 함수 호출 |
| `_command_checker_build.py` | wheel 메타데이터와 파일 목록 생성 |

의존 방향은 다음과 같습니다.

```text
model ← comparison
model ← specification
model ← process
model ← reports
runner → process
cli → specification, runner, reports
```

`process.py`가 터미널 문구를 정하거나 `reports.py`가 명령을 실행하면 서로 다른 작업이 다시 섞인 것입니다.

## 구현 순서

### 1. 패키지와 진입점

- `pyproject.toml`에서 패키지 메타데이터와 콘솔 스크립트를 선언합니다.
- `__main__.py`와 설치된 명령이 같은 `cli.main`을 호출합니다.

### 2. `Case`, `Result`, 예외

- 검증된 입력은 `Case`로 저장합니다.
- 실행 결과와 실패 설명은 `Result`로 저장합니다.
- 명세 오류와 프로세스 관리 오류를 다른 예외로 구분합니다.

### 3. 결과 비교

`returncode`, `stdout`, `stderr`를 공백과 줄바꿈까지 정확히 비교합니다. 프로세스 실행 없이 직접 테스트할 수 있는 함수로 작성합니다.

### 4. JSON 사례 검증

- 최상위 배열과 필드를 검사합니다.
- 타임아웃은 유한한 양수인지 확인합니다.
- 출력 상한은 양의 정수인지 확인합니다.
- `cwd`는 사례 파일 기준 상대 경로로 해석합니다.
- 환경 변수 키와 값에 사용할 수 없는 문자를 거부합니다.

### 5. 실행 파일 선택과 사례 한 건 실행

- 호출 환경에서 실행 파일을 한 번 선택해 절대 경로로 고정합니다.
- 사례의 인자, `stdin`, `cwd`, 환경 변수를 전달합니다.
- `stdout`, `stderr`, `returncode`를 수집합니다.

### 6. 순차 실행과 결과 표시

- 사례 하나가 불일치해도 다음 사례를 실행합니다.
- 결과를 입력 순서로 반환합니다.
- 통과 결과는 `stdout`, 실패 세부 내용은 `stderr`에 출력합니다.
- 모든 결과를 확인한 뒤 종료 상태를 계산합니다.

### 7. 프로세스 수명 제한

- 대상을 새 POSIX 세션에서 시작합니다.
- 세 파이프를 논블로킹 모드로 처리합니다.
- 마감 시각과 스트림별 바이트 상한을 확인합니다.
- 제한을 넘으면 프로세스 그룹에 `SIGTERM`, 필요하면 `SIGKILL`을 보냅니다.
- 어떤 예외가 발생해도 자신이 시작한 프로세스 그룹을 정리합니다.

### 8. JSON/JUnit 보고서

- 같은 `Result` 목록으로 두 형식을 만듭니다.
- XML 1.0에서 허용하지 않는 문자를 바꿉니다.
- 임시 파일을 완성한 뒤 `os.replace()`로 최종 경로를 교체합니다.

### 9. 제한된 병렬 실행

- `ThreadPoolExecutor(max_workers=jobs)`로 작업자 수를 제한합니다.
- 완료 순서와 관계없이 입력 순서대로 결과를 반환합니다.
- 작업자는 보고서 파일을 직접 쓰지 않습니다.

### 10. CLI와 패키지 완성

- 인자 오류를 종료 상태 2로 처리합니다.
- 명세, 실행, 보고서 오류를 사용자 메시지로 바꿉니다.
- wheel을 만들고 새 가상 환경에 설치합니다.
- 저장소 밖에서 콘솔 스크립트를 실행합니다.

### 11. 전체 동작 검증

- JSON 필드와 상대 `cwd` 검증
- 인자, 환경 변수, 세 출력 값 보존
- 타임아웃과 출력 상한 구분
- 병렬 실행 중 입력 순서 보존
- JSON/JUnit 결과 일치
- 모듈 CLI 종단 간 실행
- POSIX 프로세스 그룹 정리

## 보고서 생성 원칙

JSON과 JUnit을 각자 다른 결과에서 만들면 두 보고서가 서로 달라질 수 있습니다.

```text
모든 사례의 `Result`를 확정합니다.
→ 같은 `Result` 튜플로 JSON을 만듭니다.
→ 같은 `Result` 튜플로 JUnit을 만듭니다.
→ 각 파일을 임시 경로에 완성합니다.
→ 최종 경로로 교체합니다.
```

동적 XML 텍스트에는 사례 이름, 실패 메시지, stdout, stderr가 포함됩니다. XML 1.0에서 허용하지 않는 코드 포인트는 대체 문자로 바꿉니다.

## 테스트에서 잡아야 할 잘못된 구현

- 사례별 `PATH`에서 실행 파일을 다시 찾아 다른 파일을 실행합니다.
- 타임아웃 뒤 부모 프로세스만 종료하고 자식 프로세스를 남깁니다.
- `stdout`과 `stderr`를 차례로 읽다가 파이프 교착이 발생합니다.
- 출력 상한을 넘긴 뒤에도 계속 메모리에 저장합니다.
- 병렬 작업의 완료 순서를 그대로 최종 결과 순서로 사용합니다.
- 작업자가 같은 보고서 파일을 동시에 수정합니다.
- JSON과 JUnit이 서로 다른 결과 목록을 사용합니다.
- 소스 루트에 있을 때만 패키지 `import`가 성공합니다.

## 한계

- Windows 네이티브 프로세스 트리 종료는 지원하지 않습니다.
- 셸 파이프라인 문법을 해석하지 않습니다. 명령과 인자는 이미 분리된 목록으로 받습니다.
- 바이너리 프로토콜이 아니라 UTF-8 텍스트 CLI를 검사합니다. 디코딩할 수 없는 바이트는 대체 문자로 바꿉니다.
- 원격 실행, 컨테이너 오케스트레이션, 분산 테스트 스케줄링은 다루지 않습니다.
- 여러 보고서 파일을 하나의 트랜잭션으로 묶지는 않습니다.

## 완료 기준

- 입력·실행 환경 오류와 실행 결과 불일치를 구분합니다.
- 프로세스 실행과 결과 비교를 독립적으로 테스트합니다.
- 프로세스와 모든 파이프를 어느 함수가 정리하는지 설명합니다.
- 타임아웃이나 출력 상한을 넘겨도 자식 프로세스가 남지 않습니다.
- 병렬 실행이 사용자에게 보여 주는 결과 순서를 바꾸지 않습니다.
- 보고서 파일은 전체 내용이 완성된 뒤에만 최종 경로로 교체됩니다.
- 설치된 `command-checker`를 저장소 밖에서 실행할 수 있습니다.
