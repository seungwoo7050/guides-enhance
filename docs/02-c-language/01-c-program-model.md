# C 프로그램의 구성과 전처리

C 프로그램은 `.c` 소스 파일에서 곧바로 실행 파일이 만들어지는 방식이 아닙니다. 일반적인 구현에서는 각 `.c` 파일이 자신이 `#include`한 헤더의 내용과 함께 전처리되어 **번역 단위(translation unit)** 를 이루고, 번역 단위마다 독립적으로 컴파일·어셈블되어 오브젝트 파일이 됩니다.

그 뒤 여러 오브젝트 파일과 필요한 라이브러리를 **링커(linker)** 가 결합하여 실행 파일이나 공유 라이브러리를 만듭니다. 정적 라이브러리(`.a`)는 보통 링크 결과가 아니라 여러 오브젝트 파일을 `ar` 같은 도구로 묶은 **아카이브(archive)** 입니다.

## 빌드 단계

일반적인 실행 파일 빌드는 다음과 같이 이해할 수 있습니다.

```text
.c 파일 + #include로 포함된 헤더
  ↓ 전처리
번역 단위
  ↓ 컴파일
어셈블리 코드
  ↓ 어셈블
오브젝트 파일(.o)
  ↓ 링크
실행 파일 또는 공유 라이브러리
```

정적 라이브러리는 보통 다음 경로로 만듭니다.

```text
오브젝트 파일(.o)
  ↓ 아카이브
정적 라이브러리(.a)
```

실제 컴파일러는 컴파일과 어셈블을 내부적으로 한 번에 처리할 수도 있습니다. 위 단계는 각 단계가 담당하는 역할을 구분하기 위한 개념적 모델입니다.

`cc`는 전처리기, 컴파일러, 어셈블러, 링커 등을 필요한 순서로 실행하는 **컴파일러 드라이버(compiler driver)** 로 사용할 수 있습니다. 시스템에 따라 실제 구현은 GCC나 Clang일 수 있습니다.

```sh
cc -std=c11 -Wall -Wextra -Wpedantic main.c text.c -o textstat
```

이 한 명령을 실행해도 내부적으로는 각 `.c` 파일이 따로 번역된 뒤 최종 링크가 수행됩니다.

문제가 생겼을 때는 실패가 다음 중 어느 단계에서 발생했는지 구분해야 합니다.

- **전처리 오류**: 헤더를 찾지 못함, 잘못된 전처리 지시문 등
- **컴파일 오류**: 문법 오류, 타입 불일치, 선언 누락 등
- **링크 오류**: 필요한 정의를 찾지 못함, 정의가 중복됨 등
- **실행 중 오류**: 빌드는 성공했지만 프로그램 동작 중 문제가 발생함

## 각 단계의 결과 확인하기

```sh
cc -std=c11 -E main.c -o main.i
cc -std=c11 -S main.c -o main.s
cc -std=c11 -c main.c -o main.o
cc main.o text.o -o textstat
```

- `-E`: 전처리까지만 수행하여 전처리 결과를 만듭니다.
- `-S`: 컴파일까지만 수행하여 어셈블리 소스를 만듭니다.
- `-c`: 오브젝트 파일까지만 만들고 링크는 수행하지 않습니다.
- 마지막 명령: 이미 만들어진 오브젝트 파일을 링크하여 실행 파일을 만듭니다.

예를 들어 `#include`와 매크로가 실제로 어떻게 확장되었는지 확인하려면 `-E` 결과가 유용합니다.

## 전처리기는 전처리 토큰을 처리합니다

전처리기는 C 표현식의 타입을 검사하거나 함수를 실행하는 단계가 아닙니다. `#include`, `#define`, 조건부 컴파일 지시문 등을 처리하여 이후 컴파일 단계가 읽을 소스 형태를 만듭니다.

전처리 단계에서 주로 다루는 단위는 **전처리 토큰(preprocessing token)** 입니다. 따라서 매크로 치환은 함수 호출이 아니라 토큰 수준의 변환입니다.

### 객체형 매크로

```c
#define BUFFER_SIZE 4096
#define DEBUG_ENABLED 1
```

`BUFFER_SIZE` 같은 매크로 이름이 사용되면 전처리 과정에서 매크로의 **치환 목록(replacement list)** 으로 바뀝니다.

```c
char buffer[BUFFER_SIZE];
```

전처리 후에는 개념적으로 다음과 같은 코드가 됩니다.

```c
char buffer[4096];
```

매크로 자체에는 C 타입이 없습니다. 다만 치환 결과인 `4096`은 이후 컴파일 단계에서 정수 상수로 해석됩니다.

타입이 있는 값을 표현하고 싶다면 `const` 객체가 더 적절할 수 있습니다.

```c
static const size_t buffer_size = 4096;
```

반면 C에서 `const` 객체는 모든 문맥에서 **정수 상수식(integer constant expression)** 으로 취급되는 것은 아닙니다. 컴파일 타임 정수 상수가 반드시 필요한 문맥에서는 `enum` 상수가 적합할 수 있습니다.

```c
enum { BUFFER_SIZE = 4096 };
```

즉, 매크로·`const` 객체·`enum` 상수는 서로 완전히 같은 기능이 아니며 필요한 성질에 따라 선택해야 합니다.

### 함수형 매크로

```c
#define MIN(a, b) ((a) < (b) ? (a) : (b))
```

이 문법은 함수 호출처럼 보이지만 실제 함수가 아닙니다. 인자는 함수 매개변수에 값으로 전달되는 것이 아니라 매크로 본문의 해당 위치에 토큰으로 치환됩니다.

```c
MIN(index++, limit)
```

개념적으로 다음과 같이 확장됩니다.

```c
((index++) < (limit) ? (index++) : (limit))
```

따라서 `index++`은 조건 비교에서 한 번 평가되고, 비교 결과가 참이면 두 번째로 한 번 더 평가됩니다. 즉, 이 호출에서 `index++`은 **한 번 또는 두 번 평가될 수 있습니다**.

이처럼 값 변경, 입출력, 함수 호출 등의 **부수 효과(side effect)** 가 있는 표현식을 함수형 매크로 인자로 전달하면 예상하기 어려운 결과가 생길 수 있습니다.

```c
MIN(index++, limit)   /* 피하는 편이 좋음 */
```

함수라면 각 인자는 함수 호출 전에 한 번 평가되지만, 함수형 매크로에는 그러한 보장이 없습니다.

괄호도 중요합니다.

```c
#define SQUARE_BAD(x) x * x
#define SQUARE(x) ((x) * (x))
```

다음 호출을 비교해 봅니다.

```c
SQUARE_BAD(1 + 2)
```

확장 결과는 다음과 같습니다.

```c
1 + 2 * 1 + 2
```

곱셈이 덧셈보다 우선하므로 결과는 `9`가 아니라 `5`가 됩니다.

반면 다음 매크로는

```c
#define SQUARE(x) ((x) * (x))
```

다음처럼 확장됩니다.

```c
((1 + 2) * (1 + 2))
```

따라서 인자를 사용하는 각 위치와 전체 결과를 괄호로 감싸는 것이 일반적인 안전 수칙입니다.

그러나 괄호는 **연산자 우선순위 문제만 줄일 뿐 중복 평가 문제를 해결하지는 않습니다.**

```c
SQUARE(i++)
```

는 여전히 `i++`을 두 번 평가할 수 있으므로 안전하지 않습니다.

### 여러 줄 매크로

긴 치환 목록을 여러 물리적 줄에 작성하려면 줄을 계속 이어야 하는 위치에서 `\` 바로 뒤에 줄바꿈을 둡니다.

```c
#define CHECK(expression)                                      \
    do {                                                       \
        if (!(expression)) {                                   \
            fprintf(stderr, "%s:%d: 실패: %s\n",               \
                    __FILE__, __LINE__, #expression);          \
            return 1;                                          \
        }                                                      \
    } while (0)
```

`\` 뒤에 불필요한 문자가 들어가면 줄 연결이 깨질 수 있으므로 일반적으로 `\`를 줄의 마지막 문자로 둡니다. 마지막 줄에는 줄 연결이 필요하지 않습니다.

`do { ... } while (0)`은 여러 문장을 가진 매크로를 호출 위치에서 **하나의 문장(statement)** 처럼 사용하기 위한 관용구입니다.

```c
if (ready)
    CHECK(value != 0);
else
    recover();
```

호출부에서는 일반 함수 호출처럼 세미콜론을 붙일 수 있고, `if`/`else`와도 자연스럽게 결합합니다.

단순히 블록만 치환하는 매크로나 여러 문장을 그대로 늘어놓는 매크로는 호출 위치의 문법 구조와 예상하지 못하게 결합할 수 있습니다.

### 문자열화 연산자 `#`

함수형 매크로의 치환 목록에서 `#parameter`는 해당 매크로 인자로 전달된 토큰을 문자열 리터럴 형태로 만듭니다. 이를 **문자열화(stringification)** 라고 합니다.

```c
#define STRINGIFY(value) #value

STRINGIFY(buffer_size)
/* "buffer_size" */
```

따라서 테스트나 진단 매크로에서 실제로 전달된 표현식의 철자를 출력할 때 유용합니다.

```c
#define CHECK(expression)                                      \
    do {                                                       \
        if (!(expression)) {                                   \
            fprintf(stderr, "실패: %s\n", #expression);        \
        }                                                      \
    } while (0)
```

```c
CHECK(count > 0);
```

실패하면 `"count > 0"`과 같은 문자열을 출력할 수 있습니다.

주의할 점은 `#`가 적용된 매개변수는 일반적인 매크로 인자 확장과 조금 다르게 처리된다는 것입니다. 예를 들어 다음 코드는

```c
#define VALUE 100
#define STRINGIFY(x) #x

STRINGIFY(VALUE)
```

`"100"`이 아니라 `"VALUE"`가 됩니다. 매크로를 먼저 확장한 뒤 문자열화하려면 보통 한 단계의 간접 매크로를 추가합니다.

```c
#define STRINGIFY_INNER(x) #x
#define STRINGIFY(x) STRINGIFY_INNER(x)

STRINGIFY(VALUE)
/* "100" */
```

### 미리 정의된 매크로

C 구현은 소스 위치 등을 나타내는 미리 정의된 매크로를 제공합니다. 대표적으로 다음이 있습니다.

```c
__FILE__
__LINE__
```

- `__FILE__`: 현재 소스 파일 이름을 나타내는 문자열 리터럴로 확장됩니다.
- `__LINE__`: 현재 소스 줄 번호를 나타내는 정수 상수로 확장됩니다.

```c
fprintf(stderr, "%s:%d: 잘못된 상태\n", __FILE__, __LINE__);
```

이런 매크로는 오류 메시지나 디버깅용 로그에 소스 위치를 포함할 때 유용합니다.

### 가변 인자 매크로

C99부터 함수형 매크로도 가변 개수의 인자를 받을 수 있습니다.

```c
#define LOG(format, ...) \
    fprintf(stderr, format, __VA_ARGS__)
```

예를 들어

```c
LOG("count = %d\n", count);
```

는 개념적으로 다음처럼 확장됩니다.

```c
fprintf(stderr, "count = %d\n", count);
```

여기에서

- `...`는 이름이 정해지지 않은 추가 매크로 인자들을 받는 문법이고,
- `__VA_ARGS__`는 그 추가 인자들이 들어가는 위치입니다.

매크로의 가변 인자와 `<stdarg.h>`를 사용하는 **가변 인자 함수(variadic function)** 는 서로 다른 기능입니다.

- 가변 인자 매크로: 전처리 단계에서 토큰을 확장합니다.
- `va_list`, `va_start`, `va_arg` 등: 실제 함수 호출 시 전달된 가변 인자 값을 함수 안에서 읽습니다.

위의 C11 형태에서는 다음 호출을 주의해야 합니다.

```c
LOG("started\n");
```

추가 인자가 없으면 구현과 확장 방식에 따라 `fprintf(stderr, "started\n", );`처럼 유효하지 않은 형태가 될 수 있습니다. C11에서 이 경우를 이식성 있게 처리하려면 추가 인자를 항상 하나 이상 요구하거나, 인자가 없는 경우를 위한 별도 매크로를 두는 방법이 단순합니다.

```c
#define LOG0(message) \
    fprintf(stderr, "%s", (message))

#define LOG(format, ...) \
    fprintf(stderr, format, __VA_ARGS__)
```

컴파일러별 확장 기능이나 더 새로운 C 표준에서는 다른 방법을 제공할 수 있으므로 사용하는 표준과 컴파일러의 지원 범위를 확인해야 합니다.

### 조건부 컴파일

전처리기는 특정 매크로가 정의되어 있는지 또는 전처리 시 계산 가능한 정수 조건이 참인지에 따라 일부 코드를 포함하거나 제외할 수 있습니다.

```c
#ifdef DEBUG
fprintf(stderr, "debug mode\n");
#endif
```

`#ifdef DEBUG`는 `DEBUG`의 **값**을 검사하는 것이 아니라 `DEBUG`라는 매크로가 **정의되어 있는지**를 검사합니다.

따라서 다음처럼 `DEBUG`를 `0`으로 정의해도

```sh
cc -DDEBUG=0 source.c -o program
```

`#ifdef DEBUG`의 조건은 참입니다.

같은 정의 여부 검사는 `defined` 연산자를 사용해 쓸 수도 있습니다.

```c
#if defined(DEBUG)
fprintf(stderr, "debug mode\n");
#endif
```

반대로 `DEBUG`를 숫자 플래그로 사용해 `0`과 `1`을 구분하고 싶다면 다음처럼 작성할 수 있습니다.

```c
#if DEBUG
fprintf(stderr, "debug mode\n");
#endif
```

이때는 보통 빌드에서 값을 명시적으로 정의합니다.

```sh
cc -DDEBUG=1 source.c -o program
```

여러 조건을 조합할 때는 `defined`가 특히 유용합니다.

```c
#if defined(DEBUG) && defined(TRACE)
    /* DEBUG와 TRACE가 모두 정의된 경우 */
#endif
```

플랫폼이나 선택 기능에 따라 다른 코드를 포함할 수도 있습니다.

```c
#if defined(__linux__)
    /* Linux에서 사용할 코드 */
#elif defined(__APPLE__)
    /* macOS에서 사용할 코드 */
#else
    /* 다른 환경에서 사용할 공통 구현 */
#endif
```

`__linux__`, `__APPLE__` 같은 이름은 ISO C가 모든 구현에 요구하는 표준 매크로가 아니라 특정 컴파일러·플랫폼 환경이 제공하는 매크로입니다. 따라서 실제 지원 여부는 사용하는 툴체인에서 확인해야 합니다.

컴파일 명령의 `-D` 옵션은 전처리 매크로를 명령행에서 정의합니다.

```sh
cc -DDEBUG source.c -o program
```

이 명령은 일반적으로 `DEBUG`를 값 `1`로 정의한 것처럼 사용할 수 있습니다.

명시적인 값을 줄 수도 있습니다.

```sh
cc -DBUFFER_SIZE=8192 source.c -o program
```

Makefile에서는 전처리 관련 옵션을 관례적으로 `CPPFLAGS`에 둡니다.

```make
CPPFLAGS += -DDEBUG
```

### Include guard

헤더는 여러 다른 헤더를 통해 같은 번역 단위에 반복해서 포함될 수 있습니다.

예를 들어

```text
main.c
 ├─ a.h
 │   └─ common.h
 └─ b.h
     └─ common.h
```

와 같은 구조라면 `common.h`가 같은 번역 단위에서 두 번 포함될 수 있습니다.

이를 막기 위해 **include guard**를 사용합니다.

```c
#ifndef OWNED_STRING_H
#define OWNED_STRING_H

/* declarations */

#endif
```

처음 포함할 때는 `OWNED_STRING_H`가 정의되어 있지 않으므로 본문을 처리하고 그 과정에서 `OWNED_STRING_H`를 정의합니다.

같은 번역 단위에서 다시 포함되면 이미 매크로가 정의되어 있으므로 `#ifndef` 내부가 제외됩니다.

중요한 점은 include guard가 헤더를 **프로그램 전체에서 한 번만** 처리하게 만드는 것이 아니라, **각 번역 단위 안에서 중복 처리를 막는 것**이라는 점입니다. 다른 `.c` 파일의 번역 단위에서는 같은 헤더가 다시 처리됩니다.

### 토큰 결합 연산자 `##`

`##`는 매크로 치환 과정에서 두 전처리 토큰을 이어 하나의 새 전처리 토큰을 만드는 **토큰 결합(token pasting)** 연산자입니다.

```c
#define MAKE_NAME(prefix, name) prefix##name

MAKE_NAME(test_, append)
/* test_append */
```

예를 들어 반복되는 함수 이름이나 변수 이름을 규칙적으로 만들 때 사용할 수 있습니다.

```c
#define DECLARE_TEST(name) \
    void test_##name(void)

DECLARE_TEST(append);
/* void test_append(void); */
```

결합 결과는 유효한 전처리 토큰이 되어야 합니다. `##` 역시 일반 함수 기능이 아니라 전처리 단계의 토큰 조작 기능입니다.

일반 프로그램에서 자주 필요하지는 않지만 테스트 도구, 코드 생성형 매크로, 반복 선언을 읽을 때 의미를 알아둘 필요가 있습니다.

## 번역 단위

**번역 단위(translation unit)** 는 하나의 `.c` 파일을 출발점으로 하여 그 파일이 포함한 헤더의 내용과 전처리 결과를 합친, 독립적으로 컴파일되는 단위입니다.

개념적으로 다음과 같습니다.

```text
main.c + main.c가 포함한 헤더들 → 전처리 → 번역 단위 A
text.c + text.c가 포함한 헤더들 → 전처리 → 번역 단위 B
```

번역 단위 A를 컴파일할 때 컴파일러가 번역 단위 B의 함수 본문을 자동으로 보는 것은 아닙니다.

예를 들어 다음 구조를 생각해 봅니다.

`text.h`:

```c
#ifndef TEXT_H
#define TEXT_H

#include <stddef.h>

size_t text_length(const char *text);

#endif
```

`text.c`:

```c
#include "text.h"

size_t text_length(const char *text) {
    size_t length = 0;

    while (text[length] != '\0') {
        ++length;
    }

    return length;
}
```

`main.c`:

```c
#include "text.h"

int main(void) {
    return text_length("abc") == 3 ? 0 : 1;
}
```

`main.c`를 컴파일하는 시점에는 `text_length`의 함수 본문이 보이지 않아도 됩니다. `text.h`의 **선언**을 통해 함수 이름과 타입을 알 수 있기 때문입니다.

그 뒤 링크 단계에서 `text.c`를 컴파일해 만든 오브젝트 파일 안의 `text_length` **정의**를 찾아 연결합니다.

즉, 다른 번역 단위의 함수를 사용할 때는 보통 다음 두 조건이 필요합니다.

1. 컴파일 시점: 호출하는 번역 단위에서 올바른 선언을 볼 수 있어야 합니다.
2. 링크 시점: 최종 링크 입력 어딘가에 실제 정의가 있어야 합니다.

## 선언과 정의

**선언(declaration)** 은 식별자의 이름과 타입 등의 정보를 컴파일러에 알려 줍니다.

```c
size_t text_length(const char *text);
extern unsigned long processed_count;
```

첫 번째 줄은 함수 선언이고, 두 번째 줄은 다른 곳에 정의된 외부 객체를 가리키는 선언입니다.

**정의(definition)** 는 선언의 한 종류이면서, 함수라면 본문을 제공하고 객체라면 실제 객체를 정의합니다.

```c
size_t text_length(const char *text) {
    /* ... */
}

unsigned long processed_count = 0;
```

함수 정의는 함수 본문을 포함합니다.

객체 정의는 해당 객체가 프로그램 안에서 실제로 존재하도록 합니다.

일반적인 헤더와 구현 파일 분리는 다음과 같습니다.

`counter.h`:

```c
#ifndef COUNTER_H
#define COUNTER_H

extern unsigned long processed_count;

#endif
```

`counter.c`:

```c
#include "counter.h"

unsigned long processed_count = 0;
```

헤더에는 선언을 두고 실제 정의는 하나의 `.c` 파일에 둡니다.

선언만 있고 최종 링크에 필요한 정의가 없으면 도구에 따라 다음과 같은 링크 오류가 발생할 수 있습니다.

```text
undefined reference to `text_length'
```

반대로 외부 링키지를 가진 동일한 함수나 객체를 여러 번 정의하면 다음과 같은 링크 오류가 발생할 수 있습니다.

```text
multiple definition of `processed_count'
```

정확한 메시지는 컴파일러와 링커에 따라 다르지만, 핵심은 **선언을 보았는가**와 **정의가 링크에 존재하는가**가 서로 다른 문제라는 것입니다.

## 헤더 작성

공개 헤더에는 다른 번역 단위가 해당 모듈을 올바르게 사용하기 위해 필요한 선언을 둡니다.

```c
#ifndef TEXT_H
#define TEXT_H

#include <stddef.h>

size_t text_length(const char *text);
size_t text_word_count(const char *text);

#endif
```

이 헤더는 `size_t`를 사용하므로 `size_t`를 선언하는 `<stddef.h>`를 직접 포함합니다.

헤더 작성 시 다음 원칙을 지키면 의존 관계를 명확하게 유지할 수 있습니다.

- 헤더에서 사용하는 타입이나 매크로에 필요한 헤더를 직접 포함합니다.
- 같은 번역 단위에서 중복 포함되는 것을 막기 위해 include guard를 둡니다.
- 호출자가 알아야 하는 공개 선언만 둡니다.
- 일반적인 외부 함수 정의를 헤더에 넣지 않습니다.
- 변경 가능한 외부 전역 객체의 정의를 헤더에 넣지 않고 `extern` 선언만 둡니다.
- 구현 파일은 자신의 공개 헤더를 먼저 포함해, 헤더가 필요한 의존성을 스스로 포함하는지와 선언·정의의 타입이 일치하는지를 컴파일러가 확인하게 합니다.

예를 들어 `text.c`는 다음처럼 시작하는 것이 좋습니다.

```c
#include "text.h"

#include <ctype.h>
#include <string.h>
```

이렇게 하면 `text.h`가 우연히 다른 헤더가 먼저 포함되어야만 컴파일되는 문제를 더 빨리 발견할 수 있습니다.

## 내부 링키지

**링키지(linkage)** 는 서로 다른 위치의 선언에서 사용된 같은 이름이 동일한 함수나 객체를 가리키는지를 결정하는 성질입니다.

파일 범위의 함수에 `static`을 붙이면 그 함수 이름은 **내부 링키지(internal linkage)** 를 가져 현재 번역 단위 안에서만 같은 함수로 연결될 수 있습니다.

```c
static int is_separator(char value) {
    return value == ' ' || value == '\t' || value == '\n';
}
```

이 함수는 다른 `.c` 파일에서 같은 이름으로 선언해 호출할 공개 함수가 아닙니다.

파일 범위 객체에도 `static`을 사용할 수 있습니다.

```c
static unsigned long local_count;
```

`local_count` 역시 현재 번역 단위의 구현 세부사항으로 제한됩니다.

`static`은 사용 위치에 따라 의미가 다르다는 점에 주의해야 합니다.

블록 내부의 `static` 객체는 다음과 같습니다.

```c
void record_call(void) {
    static unsigned long call_count = 0;
    ++call_count;
}
```

여기에서

- 이름 `call_count`는 해당 블록 안에서만 사용할 수 있고,
- 객체 자체는 함수 호출이 끝나도 사라지지 않으며,
- 프로그램 실행 동안 값을 유지합니다.

즉, **이름을 어디에서 사용할 수 있는가**와 **객체가 얼마나 오래 존재하는가**는 다른 개념입니다.

## 스코프·링키지·저장 기간

이 세 개념은 서로 관련되어 보이지만 각각 다른 질문에 답합니다.

| 개념 | 의미 | 확인할 질문 |
| --- | --- | --- |
| 스코프(scope) | 소스 코드에서 이름을 사용할 수 있는 범위 | 이 이름을 소스의 어디에서 사용할 수 있는가? |
| 링키지(linkage) | 여러 선언의 같은 이름이 같은 개체를 가리키는지 여부 | 이 선언과 저 선언은 같은 함수나 객체를 뜻하는가? |
| 저장 기간(storage duration) | 객체의 저장 공간이 존재하는 기간 | 이 객체는 언제 생성되어 언제까지 존재하는가? |

예를 들어 자동 지역 변수는 보통 블록 스코프와 자동 저장 기간을 가집니다.

```c
void function(void) {
    int value = 10;
}
```

`value`라는 이름은 블록 안에서만 사용할 수 있고, 해당 블록 실행이 끝나면 그 호출에 대응하는 객체의 수명도 끝납니다.

반면 블록 내부 `static` 객체는 블록 스코프이지만 정적 저장 기간을 가집니다.

```c
void function(void) {
    static int value = 10;
}
```

이름을 사용할 수 있는 범위는 좁지만 객체의 저장 공간은 프로그램 실행 동안 유지됩니다.

파일 범위 `static` 객체는 파일 스코프, 내부 링키지, 정적 저장 기간을 가집니다.

```c
static int value;
```

따라서 `static`이라는 키워드 하나만 보고 스코프·링키지·저장 기간을 같은 개념으로 생각하면 안 됩니다.

## 오브젝트 파일과 심볼 확인

Unix 계열 개발 환경에서는 `nm`과 `ar`를 사용해 오브젝트 파일이나 정적 라이브러리의 심볼과 멤버를 확인할 수 있습니다.

```sh
nm main.o
nm text.o
ar t libtext.a
nm libtext.a
```

`nm`으로는 다음과 같은 사실을 확인할 수 있습니다.

- 현재 오브젝트 파일이 정의한 심볼
- 현재 오브젝트 파일에는 정의가 없어서 다른 링크 입력이 제공해야 하는 심볼
- 정적 라이브러리의 각 오브젝트 멤버가 정의하거나 참조하는 심볼

많은 `nm` 구현에서 정의되지 않은 외부 심볼은 `U`처럼 표시됩니다.

예를 들어 `main.o`가 `text_length`를 호출하지만 정의하지 않는다면 다음과 비슷하게 보일 수 있습니다.

```text
                 U text_length
```

반대로 `text.o`가 함수를 정의한다면 구현에 따라 다음처럼 표시될 수 있습니다.

```text
0000000000000000 T text_length
```

정확한 문자와 출력 형식은 오브젝트 형식과 `nm` 구현에 따라 달라질 수 있습니다.

`ar t`는 정적 라이브러리 아카이브 안에 어떤 오브젝트 파일 멤버가 들어 있는지 보여 줍니다.

```sh
ar t libtext.a
```

예상 출력:

```text
text.o
token.o
```

헤더에 선언이 있다는 사실만으로 그 정의가 최종 링크에 포함되어 있다고 볼 수 없습니다. 헤더는 컴파일러에게 인터페이스를 알려 줄 뿐이며, 실제 정의는 오브젝트 파일이나 라이브러리 형태로 링크 입력에 제공되어야 합니다.

## 매크로를 읽을 때 확인할 사항

- 확장된 식의 연산자 우선순위가 의도한 대로 유지됩니까?
- 매크로 인자가 치환 목록에서 여러 번 사용됩니까?
- 부수 효과가 있는 표현식을 인자로 전달하면 여러 번 평가될 수 있습니까?
- 여러 문장으로 확장되는 매크로가 호출 위치에서 하나의 문장처럼 동작합니까?
- `#ifdef`가 값이 아니라 정의 여부를 검사한다는 점을 고려했습니까?
- 어떤 `-D` 옵션과 조건부 컴파일 지시문이 연결됩니까?
- `#` 문자열화와 `##` 토큰 결합이 인자 확장에 미치는 영향을 이해하고 있습니까?
- 실제 함수, `const` 객체, `enum` 상수보다 매크로가 적합한 이유가 있습니까?

## 완료 기준

1. 전처리, 컴파일, 어셈블, 링크의 역할을 구분합니다.
2. 정적 라이브러리와 링크 결과의 차이를 설명합니다.
3. 번역 단위마다 독립적으로 컴파일되는 이유를 설명합니다.
4. 다른 번역 단위의 함수를 호출할 때 선언과 정의가 각각 언제 필요한지 설명합니다.
5. 선언과 정의를 헤더와 `.c` 파일에 적절히 나눕니다.
6. 함수형 매크로의 중복 평가 위험을 실제 확장 결과로 설명합니다.
7. 매크로에서 괄호가 해결하는 문제와 해결하지 못하는 문제를 구분합니다.
8. `#`, `##`, `__FILE__`, `__LINE__`, `__VA_ARGS__`의 용도를 구분합니다.
9. `#ifdef`, `#if`, `defined`, `-D`의 차이와 관계를 설명합니다.
10. include guard가 같은 번역 단위 안에서 중복 포함을 막는 원리를 설명합니다.
11. 스코프, 링키지, 저장 기간을 서로 다른 개념으로 설명합니다.
12. `nm`과 `ar`를 사용해 선언이 아닌 실제 링크 대상과 심볼을 확인할 수 있습니다.
