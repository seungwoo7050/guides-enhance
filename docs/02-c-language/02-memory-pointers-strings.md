# 메모리·포인터·문자열

C에서 포인터는 단순히 “숫자로 된 메모리 주소”라고 이해하면 부족합니다. 포인터를 안전하게 사용하려면 최소한 다음을 함께 확인해야 합니다.

- 어떤 타입의 객체를 가리키는가
- 그 객체의 수명이 아직 끝나지 않았는가
- 접근하려는 위치가 해당 객체나 배열의 유효한 범위 안인가
- 읽기와 쓰기 중 어떤 접근이 허용되는가
- 동적 메모리라면 누가 소유하고 누가 해제하는가

포인터 값이 `NULL`이 아니라는 사실은 이 조건들을 보장하지 않습니다.

## 객체와 주소

```c
int value = 42;
int *pointer = &value;

*pointer = 7;
```

`&value`는 객체 `value`의 주소를 구하고, `pointer`는 그 주소를 저장하여 `value`를 가리킵니다.

```c
*pointer
```

처럼 포인터 앞에 `*`를 붙이는 것은 포인터가 가리키는 객체에 접근하는 **역참조(dereference)** 입니다.

따라서

```c
*pointer = 7;
```

은 `pointer`가 가리키는 `value`에 `7`을 저장하며, 실행 후 `value`의 값도 `7`입니다.

포인터의 타입도 중요합니다.

```c
int *pointer;
```

는 `pointer`가 `int` 객체를 가리키는 포인터임을 나타냅니다. `*pointer`로 접근할 때 컴파일러는 `int` 객체에 접근하는 것으로 해석합니다.

그러나 타입이 맞는 포인터 값이라고 해서 언제나 역참조할 수 있는 것은 아닙니다. 객체의 수명이 끝났거나 배열 범위를 벗어난 위치를 가리키면 접근할 수 없습니다.

## NULL 포인터

`NULL` 포인터는 어떤 객체도 가리키지 않는다는 것을 나타내는 데 사용합니다.

```c
int read_value(const int *pointer, int *out_value) {
    if (pointer == NULL || out_value == NULL) {
        return -1;
    }

    *out_value = *pointer;
    return 0;
}
```

이 함수는 두 포인터가 `NULL`이면 역참조하지 않고 실패를 반환합니다.

하지만 다음 두 조건은 서로 다릅니다.

```text
pointer != NULL
```

```text
pointer가 현재 접근 가능한 유효한 객체를 가리킨다
```

`NULL`이 아닌 포인터도 다음과 같은 이유로 사용할 수 없을 수 있습니다.

- 이미 수명이 끝난 지역 객체를 가리킴
- 이미 `free`된 할당을 가리킴
- 배열의 유효한 범위를 벗어난 위치를 가리킴
- 쓰기가 허용되지 않는 객체를 쓰려고 함
- 필요한 객체 타입과 맞지 않는 방식으로 접근하려 함

따라서 `NULL` 검사는 필요한 경우가 많지만 포인터 유효성 전체를 검사하는 방법은 아닙니다.

## 저장 기간과 객체 수명

**저장 기간(storage duration)** 은 객체의 저장 공간이 얼마나 오래 존재하는지를 나타냅니다. 포인터를 사용하려면 가리키는 객체의 수명이 아직 유지되고 있어야 합니다.

### 자동 저장 기간

일반적인 지역 변수는 자동 저장 기간을 가집니다.

```c
int *wrong(void) {
    int value = 42;
    return &value;
}
```

`value`는 `wrong`의 블록 실행이 끝날 때 수명이 끝납니다.

따라서 반환된 포인터는 함수가 끝난 뒤 더 이상 `value`에 접근하는 데 사용할 수 없습니다.

```c
int *pointer = wrong();

/* 잘못된 접근 */
printf("%d\n", *pointer);
```

포인터에 어떤 주소 비트가 남아 있는 것처럼 보여도 그 위치의 `value` 객체는 이미 존재하지 않습니다. 이런 포인터를 흔히 **댕글링 포인터(dangling pointer)** 라고 부릅니다.

지역 객체의 값을 호출자에게 전달하려면 다음과 같은 방법을 사용합니다.

값 자체를 반환:

```c
int read_value(void) {
    int value = 42;
    return value;
}
```

또는 호출자가 제공한 객체에 결과를 기록:

```c
int read_value(int *out_value) {
    if (out_value == NULL) {
        return -1;
    }

    *out_value = 42;
    return 0;
}
```

### 정적 저장 기간

파일 범위 객체와 `static` 지역 객체는 정적 저장 기간을 가지며 프로그램 실행 동안 저장 공간이 유지됩니다.

```c
static int global_count;

void increment(void) {
    static int local_count;

    ++global_count;
    ++local_count;
}
```

이 객체들은 함수 호출이 끝나도 사라지지 않습니다.

하지만 “오래 존재한다”는 것과 “어디서나 자유롭게 접근하거나 변경해도 안전하다”는 것은 다른 문제입니다.

예를 들어 여러 코드가 같은 변경 가능한 객체를 공유하면 다음을 별도로 고려해야 합니다.

- 어떤 함수가 값을 변경할 수 있는가
- 동시에 접근하는 실행 흐름이 있는가
- 호출 간 상태가 유지되는 것이 API 의도와 맞는가

즉, 객체의 수명과 공유 상태 관리 문제를 구분해야 합니다.

### 할당 저장 기간

`malloc`, `calloc`, `realloc` 같은 동적 메모리 할당 함수로 얻은 객체는 **할당 저장 기간(allocated storage duration)** 을 가집니다. 흔히 “동적 저장 기간”이라고도 표현합니다.

```c
int *values = malloc(count * sizeof *values);
```

`malloc`이 성공하면 반환된 메모리는 명시적으로 해제할 때까지 사용할 수 있습니다.

```c
free(values);
```

해제한 뒤에는 그 할당을 가리키던 포인터로 객체에 접근하면 안 됩니다.

동적 메모리는 함수가 끝나도 자동으로 해제되지 않으므로 API나 자료구조마다 다음 규칙을 정해야 합니다.

```text
누가 할당하는가?
누가 소유하는가?
누가 free하는가?
언제 소유권이 이동하는가?
```

이 규칙이 불분명하면 메모리 누수, 이중 해제, 해제 후 사용 같은 오류가 발생하기 쉽습니다.

## 할당 성공 여부와 크기 계산

동적 배열을 할당할 때는 원소 개수와 원소 크기를 곱해 필요한 바이트 수를 계산합니다.

```c
int *values = malloc(count * sizeof *values);
```

하지만 `size_t` 연산은 표현 가능한 최댓값을 넘으면 모듈러 방식으로 돌아가므로, 곱셈 결과가 실제 필요한 크기보다 작은 값이 될 수 있습니다.

따라서 곱하기 전에 검사합니다.

```c
if (count > SIZE_MAX / sizeof *values) {
    return -1;
}

values = malloc(count * sizeof *values);
if (values == NULL && count != 0) {
    return -1;
}
```

예를 들어 실제로는 매우 큰 배열이 필요했는데 곱셈이 넘쳐 작은 값이 되면, 그 작은 크기만큼만 할당된 버퍼를 충분히 큰 배열이라고 착각해 이후 범위를 벗어나 쓸 수 있습니다.

`sizeof *values` 형태를 쓰면 포인터 타입이 바뀌어도 원소 크기 계산이 함께 따라갑니다.

```c
values = malloc(count * sizeof *values);
```

는 다음보다 유지보수하기 쉽습니다.

```c
values = malloc(count * sizeof(int));
```

### `malloc(0)`

크기가 `0`인 할당의 반환값은 구현에 따라 `NULL`일 수도 있고, `free`에 전달할 수 있는 `NULL`이 아닌 값일 수도 있습니다.

따라서 빈 동적 배열의 표현을 API 차원에서 하나로 정해 두면 상태 처리가 단순해집니다.

예:

```text
빈 상태:
  data == NULL
  size == 0
  capacity == 0
```

이 규칙을 사용한다면 크기가 0일 때 굳이 `malloc(0)`을 호출하지 않고 빈 상태를 그대로 유지할 수도 있습니다.

## `realloc`의 의미와 실패 처리

`realloc`은 기존 할당의 크기를 변경하는 데 사용합니다.

```c
void *resized = realloc(data, new_size);
```

크기가 커지거나 줄어들 때 같은 주소를 그대로 사용할 수도 있고, 새로운 위치로 데이터를 옮길 수도 있습니다.

중요한 규칙은 **실패했을 때 기존 할당이 그대로 유지된다는 것**입니다. 단, 여기서는 `new_size > 0`인 일반적인 경우를 전제로 합니다.

따라서 다음 코드는 위험합니다.

```c
data = realloc(data, new_size);

if (data == NULL) {
    return -1;
}
```

`realloc`이 실패하면 `NULL`이 반환되고, 원래 `data` 포인터를 덮어써 버립니다. 그러면 아직 존재하는 기존 할당을 가리키는 포인터를 잃어 메모리 누수가 발생합니다.

임시 포인터로 먼저 결과를 받습니다.

```c
void *resized = realloc(data, new_size);
if (resized == NULL) {
    return -1;
}

data = resized;
```

이렇게 하면 실패했을 때 원래 `data`가 그대로 남습니다.

### `realloc` 성공 후 기존 별칭

`data`뿐 아니라 기존 할당 내부를 가리키는 다른 포인터가 있을 수 있습니다.

```c
char *source = data + 2;
```

그 상태에서

```c
char *resized = realloc(data, new_size);
```

가 성공하면 기존 할당을 기준으로 만들어 둔 포인터를 계속 사용해서는 안 됩니다.

`realloc`이 데이터를 다른 주소로 옮길 수 있기 때문입니다.

```text
기존 data
  ├─ data + 2  ← source
  └─ ...

realloc 후 새 주소로 이동 가능

새 data
  └─ 기존 source는 새 버퍼 내부를 가리키지 않음
```

따라서 필요한 위치는 `realloc` 전에 오프셋과 같은 형태로 보존하고, 성공 후 새 기준 포인터에서 다시 계산해야 합니다.

### `realloc(pointer, 0)`

크기 `0`을 `realloc`에 전달했을 때의 세부 동작은 사용하는 C 표준과 구현에 따라 다루기가 까다롭습니다.

이식성이 중요한 코드에서는 다음처럼 크기 0을 별도로 처리하면 소유권 규칙이 명확해집니다.

```c
if (new_size == 0) {
    free(data);
    data = NULL;
    return 0;
}

void *resized = realloc(data, new_size);
if (resized == NULL) {
    return -1;
}

data = resized;
```

## 소유권

**소유권(ownership)** 은 C의 타입 시스템이 자동으로 추적하는 언어 기능이 아니라 프로그램이 정하는 규칙입니다.

동적으로 할당된 메모리의 소유자는 보통 그 메모리를 적절한 시점에 해제할 책임이 있습니다.

함수 인자로 받은 포인터는 적어도 다음 중 어떤 의미인지 정해야 합니다.

- 호출자가 계속 소유하고 함수는 읽기만 함
- 호출자가 계속 소유하고 함수는 내용을 수정함
- 함수가 새 메모리를 할당해 호출자에게 소유권을 넘김
- 함수가 전달된 포인터의 소유권을 넘겨받아 나중에 해제함

예를 들어 다음 함수가

```c
char *string_copy(const char *source);
```

새 문자열을 동적으로 할당해 반환한다면 API 문서에는 다음 사실이 필요합니다.

```text
반환값:
- 성공 시 새로 할당된 문자열
- 호출자가 free로 해제해야 함
- 실패 시 NULL
```

반대로 다음 함수가

```c
size_t text_length(const char *text);
```

`text`를 잠시 읽기만 한다면 호출자가 계속 소유하고 함수는 빌려 쓰는 **비소유 참조(borrowed pointer)** 로 이해할 수 있습니다.

중요한 것은 이런 규칙이 포인터 타입만 보고 항상 결정되지는 않는다는 점입니다. 공개 헤더의 주석이나 API 문서에 명확하게 적어야 합니다.

또한 함수가 포인터를 나중에 사용하기 위해 저장한다면, 호출이 끝난 뒤에도 가리키는 객체가 살아 있어야 한다는 수명 조건도 문서화해야 합니다.

## 얕은 복사와 이중 해제

다음 구조체가 동적 메모리의 소유권을 가진다고 가정합니다.

```c
struct string {
    char *data;
    size_t length;
};
```

구조체 대입은 각 멤버의 값을 복사합니다.

```c
struct string left = right;
```

따라서 `data` 포인터가 가리키는 문자 배열 자체를 새로 복사하는 것이 아니라 포인터 값만 복사합니다.

```text
right.data ─┐
            ├──> 같은 동적 할당
left.data  ─┘
```

이것을 **얕은 복사(shallow copy)** 라고 합니다.

두 구조체가 모두 자신이 `data`를 소유한다고 생각하고 다음과 같이 정리하면 문제가 됩니다.

```c
free(left.data);
free(right.data);
```

같은 할당을 두 번 해제하게 되므로 이중 해제가 발생합니다.

독립적으로 소유하는 복사본이 필요하면 새 메모리를 할당하고 내용을 복사하는 **깊은 복사(deep copy)** 가 필요합니다.

```c
struct string_copy {
    char *data;
    size_t length;
};
```

개념적으로는 다음 과정입니다.

```text
1. 새 버퍼를 할당
2. 원본 내용을 새 버퍼로 복사
3. 새 구조체가 새 버퍼를 소유
```

반대로 의도적으로 한 버퍼를 여러 구조체가 공유한다면 어느 객체가 실제 소유자인지, 누가 해제하는지를 별도 규칙으로 정해야 합니다.

## 배열 범위와 포인터 연산

배열의 원소는 연속된 객체로 배치되므로 포인터 연산으로 다음 원소를 가리킬 수 있습니다.

```c
int values[3] = {10, 20, 30};

int *pointer = values;

pointer++;  /* 이제 values[1]을 가리킴 */
```

포인터 `p`가 어떤 배열의 원소를 가리킨다면, 같은 배열 안의 원소 또는 배열의 마지막 원소 바로 다음 위치까지의 포인터를 계산할 수 있습니다.

```c
for (int *cursor = values;
     cursor != values + count;
     ++cursor) {
    process(*cursor);
}
```

여기에서 `values + count`는 마지막 원소 **바로 다음(one past the end)** 위치를 가리킵니다.

이 포인터는 반복 종료를 위한 비교 등에 사용할 수 있지만 역참조하면 안 됩니다.

```c
*(values + count)   /* 잘못됨 */
```

포인터 연산에서 중요한 전제는 `values`가 실제로 적어도 `count`개의 원소를 가진 같은 배열 객체를 가리킨다는 것입니다.

임의의 포인터에 숫자를 더했다고 해서 유효한 포인터가 되는 것은 아닙니다.

또한 빈 배열 상태를

```text
values == NULL
count == 0
```

으로 표현한다면 `values + count`처럼 `NULL`에 포인터 산술을 적용하는 형태에 의존하지 않는 편이 안전합니다.

예를 들어 인덱스를 사용하면 빈 상태도 자연스럽게 처리됩니다.

```c
for (size_t i = 0; i < count; ++i) {
    process(values[i]);
}
```

`count == 0`이면 루프 본문이 실행되지 않으므로 `values`를 역참조하지 않습니다.

## 포인터 차이와 오프셋

같은 배열 객체 내부의 두 포인터는 위치 차이를 계산할 수 있습니다.

```c
ptrdiff_t offset = source - data;
```

이 연산이 유효하려면 `source`와 `data`가 같은 배열 객체 안의 원소를 가리키거나 허용되는 한 칸 뒤 위치와 관련되어 있어야 합니다.

서로 관계없는 두 객체를 가리키는 포인터에 대해 단순히 뺄셈을 수행해 “주소 차이”를 구하는 용도로 사용하면 안 됩니다.

이 규칙은 이후 `realloc` 중 별칭 포인터를 오프셋으로 보존할 때도 중요합니다.

## C 문자열과 버퍼

C에서 **문자열(string)** 은 `char` 배열 안에 저장된 문자들의 연속이며 마지막에 널 문자 `'\0'`가 있어야 합니다.

```c
char text[] = "abc";
```

메모리에는 개념적으로 다음 네 바이트가 들어 있습니다.

```text
'a' 'b' 'c' '\0'
```

따라서 문자열 길이가 3이라면 저장에는 최소 4바이트가 필요합니다.

문자열의 다음 세 값을 구분하면 버퍼 코드를 이해하기 쉽습니다.

- **문자열 길이(length)**: 첫 `'\0'` 전까지의 문자 수
- **버퍼 크기/용량(capacity)**: 실제로 사용할 수 있도록 확보한 총 바이트 수
- **필요 바이트 수**: 문자열 길이 + 종료용 `'\0'` 1바이트

예:

```text
내용:      "abc"
length:    3
필요 크기: 4 bytes
capacity:  예를 들어 16 bytes
```

## `strlen`의 전제

```c
size_t length = strlen(source);
```

`strlen`은 `source`부터 시작해 첫 `'\0'`을 만날 때까지 읽습니다.

따라서 호출 전에 `source`가 실제로 종료 문자를 포함하는 유효한 C 문자열이어야 합니다.

다음처럼 종료되지 않은 단순 바이트 배열을 문자열이라고 가정하면 안 됩니다.

```c
char data[3] = {'a', 'b', 'c'};

/* data에는 '\0'가 없음 */
strlen(data);   /* 잘못된 접근으로 이어질 수 있음 */
```

`strlen`은 버퍼의 전체 용량을 알려 주는 함수도 아닙니다. 오직 종료된 문자열의 현재 길이를 계산합니다.

## 문자열 복사 크기 계산

문자열 복사본을 만들 때는 종료 문자 공간까지 포함해야 합니다.

```c
size_t length = strlen(source);

char *copy = malloc(length + 1);
if (copy == NULL) {
    return NULL;
}

memcpy(copy, source, length + 1);
```

유효한 C 문자열이 실제 객체 안에 존재한다면 그 문자열은 종료 문자까지 저장되어 있어야 하므로 실질적으로 `length + 1`도 그 객체 크기 안에 존재합니다.

그러나 일반적인 크기 산술을 작성할 때는 덧셈과 곱셈이 `SIZE_MAX`를 넘지 않는지 단계별로 검사하는 습관이 중요합니다.

특히 여러 독립적인 길이를 조합할 때는 다음처럼 계산할 수 있습니다.

```c
if (left_length > SIZE_MAX - right_length) {
    return -1;
}

size_t combined = left_length + right_length;

if (combined == SIZE_MAX) {
    return -1;
}

size_t required = combined + 1;
```

여기에서 마지막 `1`은 종료 문자 `'\0'` 공간입니다.

검사식 자체에서 unsigned 뺄셈이 먼저 언더플로하지 않도록, 복잡한 식 하나보다 단계적으로 계산하는 편이 이해하기 쉽고 안전합니다.

## 길이와 용량을 함께 관리하는 문자열

동적 문자열 구조체는 보통 길이와 용량을 구분해 저장합니다.

```c
struct string {
    char *data;
    size_t length;
    size_t capacity;
};
```

예를 들어 다음 불변식을 정할 수 있습니다.

```text
빈 상태:
  data == NULL
  length == 0
  capacity == 0

비어 있지 않은 버퍼 상태:
  data != NULL
  length < capacity
  data[length] == '\0'
```

여기서 `length < capacity`인 이유는 `data[length]` 위치에 종료 문자 한 바이트가 필요하기 때문입니다.

이런 **불변식(invariant)** 을 정해 두면 각 함수가 반환될 때 구조체가 어떤 상태여야 하는지 확인하기 쉬워집니다.

## `memcpy`와 `memmove`

두 함수 모두 바이트 단위로 메모리를 복사하지만 원본과 대상 영역이 겹치는지에 대한 규칙이 다릅니다.

- `memcpy`: 원본과 대상 영역이 겹치지 않는 경우 사용
- `memmove`: 원본과 대상 영역이 겹칠 수 있는 경우 사용

예를 들어 같은 버퍼의 내용을 오른쪽으로 한 칸 이동한다고 가정합니다.

```c
char data[8] = "abc";

memmove(data + 1, data, 4);
```

복사하는 네 바이트는 다음과 같습니다.

```text
'a' 'b' 'c' '\0'
```

원본 `[data, data + 4)`와 대상 `[data + 1, data + 5)`가 서로 겹치므로 `memmove`가 필요합니다.

같은 상황에서 `memcpy`를 사용하면 C 표준상 동작이 정의되지 않습니다.

```c
memcpy(data + 1, data, 4);   /* 영역이 겹치므로 잘못됨 */
```

`memmove`는 겹침이 있어도 원본 바이트들이 먼저 보존된 것처럼 결과가 나오도록 정의되어 있습니다.

## 별칭과 내부 포인터

서로 다른 포인터가 같은 객체나 같은 할당 내부를 가리키는 상황을 **별칭(aliasing)** 이라고 부를 수 있습니다.

예를 들어

```c
char *data = string.data;
char *source = string.data + 2;
```

라면 `data`와 `source`는 같은 할당과 관련된 포인터입니다.

`source`는 버퍼 시작이 아니라 버퍼 내부의 한 위치를 가리키므로 **내부 포인터(interior pointer)** 라고 볼 수 있습니다.

이런 내부 포인터가 존재할 때 버퍼를 재할당하면 특별히 주의해야 합니다.

## 별칭 입력과 `realloc`

현재 문자열의 일부를 다시 자기 자신에게 덧붙이는 호출을 생각해 봅니다.

```c
append(&string, string.data + 2);
```

예를 들어 `string.data`가 `"abcdef"`라면 입력 `source`는 `"cdef"`가 시작되는 현재 버퍼 내부를 가리킵니다.

```text
string.data
↓
a b c d e f \0
    ↑
    source
```

`append`가 용량을 늘리기 위해 `realloc`을 수행하면 버퍼가 새 주소로 이동할 수 있습니다.

```c
char *resized = realloc(string.data, new_capacity);
```

성공 후 기존 `source`를 그대로 사용하면 새 버퍼의 `"cdef"`를 가리킨다는 보장이 없습니다.

따라서 **입력이 현재 버퍼 내부를 가리킨다는 사실을 API의 상태나 호출 문맥상 이미 알고 있는 경우**에는 재할당 전에 시작 위치로부터의 오프셋을 저장할 수 있습니다.

```c
ptrdiff_t source_offset = source - old_data;
```

그 뒤 `realloc`이 성공하면 새 기준 포인터에서 다시 계산합니다.

```c
source = new_data + source_offset;
```

개념적으로는 다음과 같습니다.

```text
재할당 전:
old_data + 2  → source

저장:
source_offset = 2

realloc 성공

재할당 후:
source = new_data + 2
```

여기에는 중요한 전제가 있습니다.

`source - old_data`는 두 포인터가 같은 배열 객체와 관련된 경우에만 사용할 수 있습니다. 따라서 **임의의 외부 포인터에 대해 먼저 포인터 뺄셈을 해 보고 내부 포인터인지 알아내는 방식은 사용할 수 없습니다.**

또한 서로 관계없는 두 포인터에 `<`, `>`, `<=`, `>=`를 적용하여 메모리 주소 범위를 일반적으로 판정하는 방식도 이식 가능한 C 코드의 보편적인 “버퍼 내부 검사” 방법으로 취급하면 안 됩니다.

따라서 API 설계 단계에서 다음 중 하나를 명확히 정하는 편이 좋습니다.

- 입력 포인터는 현재 버퍼의 일부일 수 있다고 계약에 명시하고 그 경우를 별도로 처리
- 내부 위치를 포인터 대신 오프셋으로 전달
- 재할당 전에 필요한 입력 데이터를 별도 임시 버퍼에 복사
- 자기 자신을 입력으로 사용하는 경우를 별도 코드 경로로 처리

핵심은 `realloc` 뒤에 **기존 할당을 기준으로 만든 포인터를 그대로 신뢰하지 않는 것**입니다.

## `const`

```c
size_t text_length(const char *text);
```

`const char *text`는 `text`가 가리키는 문자를 이 포인터를 통해 수정하지 않겠다는 의미입니다.

예를 들어 함수 안에서 다음 코드는 허용되지 않습니다.

```c
text[0] = 'A';
```

하지만 `const`가 다음을 자동으로 보장하는 것은 아닙니다.

- `text`가 `NULL`이 아님
- `text`가 유효한 문자열임
- 가리키는 객체가 함수가 사용하는 동안 계속 살아 있음
- 함수가 포인터 값을 따로 저장하지 않음
- 메모리의 소유권이 누구에게 있는지

즉, `const`는 주로 **이 접근 경로를 통한 수정 가능성**에 관한 타입 규칙이지 포인터의 수명이나 소유권 규칙이 아닙니다.

또한 다음 두 선언은 의미가 다릅니다.

```c
const char *text;
char *const text = buffer;
```

첫 번째는 가리키는 문자를 이 포인터를 통해 수정하지 않는다는 뜻이고, 두 번째는 포인터 변수 `text` 자체를 다른 주소로 바꿀 수 없다는 뜻입니다.

```c
const char *const text = buffer;
```

처럼 둘을 동시에 적용할 수도 있습니다.

## 정리 함수

동적 메모리를 소유하는 구조체는 정리 함수를 두면 관리하기 쉽습니다.

```c
void buffer_destroy(struct buffer *buffer) {
    if (buffer == NULL) {
        return;
    }

    free(buffer->data);

    buffer->data = NULL;
    buffer->length = 0;
    buffer->capacity = 0;
}
```

`free(NULL)`은 아무 동작도 하지 않으므로, 정리 후 `data`를 `NULL`로 만들면 **같은 구조체 객체에 대해** `buffer_destroy`를 다시 호출하기 쉬워집니다.

하지만 이것이 모든 이중 해제 문제를 자동으로 해결하는 것은 아닙니다.

예를 들어 얕은 복사로 두 구조체가 같은 포인터를 가지고 있다면

```text
left.data  ─┐
            ├──> 같은 할당
right.data ─┘
```

`left`를 정리해 `left.data = NULL`로 만들어도 `right.data`에는 해제된 주소가 그대로 남을 수 있습니다.

또한 다른 코드가 `buffer->data` 내부를 가리키는 포인터를 보관하고 있다면 정리 후 그 포인터 역시 더 이상 사용할 수 없습니다.

따라서 안전한 정리는 다음 조건을 함께 필요로 합니다.

- 이 구조체가 실제 소유자임
- 같은 할당을 다른 소유자가 다시 해제하지 않음
- 해제 후 내부 포인터나 별칭을 사용하지 않음
- 구조체 객체 자체도 아직 살아 있음

## 메모리 코드를 읽을 때 확인할 사항

- 이 포인터가 어떤 객체나 배열을 가리키는가?
- 그 객체의 수명은 아직 유지되고 있는가?
- `NULL` 검사가 필요한가?
- 읽거나 쓰는 범위가 실제 배열 범위 안인가?
- 한 칸 뒤 포인터를 역참조하고 있지는 않은가?
- 원소 개수를 바이트 수로 바꾸는 곱셈이 넘칠 수 있는가?
- 여러 길이를 더할 때 각 단계의 덧셈이 넘치지 않는가?
- 문자열이라면 종료 문자 `'\0'` 공간을 포함했는가?
- `strlen`에 전달한 버퍼가 실제로 종료된 문자열인가?
- `realloc` 실패 시 기존 포인터를 보존하는가?
- `realloc` 성공 후 예전 할당 내부를 가리키던 포인터를 다시 사용하고 있지는 않은가?
- 복사 영역이 겹칠 가능성이 있는데 `memcpy`를 사용하고 있지는 않은가?
- 구조체 복사가 소유 포인터의 얕은 복사를 만들지는 않는가?
- 누가 메모리를 소유하고 누가 해제하는지 API에 정해져 있는가?
- `const`를 수명이나 소유권 보장으로 오해하고 있지는 않은가?

## 완료 기준

1. 포인터가 단순한 숫자 주소가 아니라 객체의 타입·수명·범위와 함께 해석되어야 하는 이유를 설명합니다.
2. `pointer != NULL`과 “유효한 객체를 가리킨다”가 서로 다른 조건인 이유를 설명합니다.
3. 자동 저장 기간을 가진 지역 객체의 주소를 함수 밖에서 사용하지 않습니다.
4. 할당한 메모리마다 소유자와 해제 책임을 정합니다.
5. 원소 개수와 원소 크기를 곱하기 전에 `size_t` overflow를 검사합니다.
6. `realloc` 실패 시 기존 포인터를 잃지 않도록 임시 포인터를 사용합니다.
7. `realloc` 성공 후 기존 할당을 기준으로 만든 내부 포인터를 그대로 사용하지 않습니다.
8. 얕은 복사가 동적 메모리 소유 구조체에서 이중 해제로 이어질 수 있는 이유를 설명합니다.
9. 배열의 한 칸 뒤 포인터는 계산할 수 있지만 역참조할 수 없음을 설명합니다.
10. 포인터 산술과 포인터 차이가 같은 배열 객체와 관련된 범위에서만 의미가 있음을 설명합니다.
11. C 문자열의 길이와 버퍼 용량, 종료 문자 공간을 구분합니다.
12. `strlen`이 유효하게 종료된 문자열을 전제로 한다는 사실을 설명합니다.
13. 겹치는 메모리 영역을 복사할 때 `memmove`를 사용합니다.
14. 별칭 입력이 있는 상태에서 `realloc`하면 오프셋을 보존해야 하는 이유와 그 전제를 설명합니다.
15. `const`가 수정 제한을 나타내지만 포인터의 유효성·수명·소유권을 보장하지는 않는다는 점을 설명합니다.
16. 정리 함수가 객체를 빈 상태로 되돌려도 다른 별칭이나 얕은 복사까지 자동으로 안전해지는 것은 아님을 설명합니다.
