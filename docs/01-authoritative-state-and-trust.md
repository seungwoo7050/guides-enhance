# 서버 권위 상태와 신뢰

## 목적

클라이언트가 보낸 값을 그대로 게임 상태에 저장하지 않고, 서버가 허용한 명령만 현재 정본 상태에 반영하는 기준을 정합니다.

## 먼저 구분할 값

| 구분 | 예시 | 생성하거나 변경하는 주체 |
|---|---|---|
| 플레이어 의도 | 이동 방향, skill 사용 요청 | 클라이언트 |
| 명령 | 세션, `sequence`, 명령 종류와 payload | 클라이언트가 생성하고 서버가 검증 |
| 정본 상태 | 위치, 체력, cooldown, 점수, 경기 단계 | 방을 실행하는 서버 |
| 화면 표현 상태 | animation, camera, effect, UI | 클라이언트 |
| 장기 저장 상태 | account, inventory, reward, rating | 별도 service 또는 DB |

클라이언트가 `position = 100`처럼 결과를 제출하게 두지 않습니다. `move_right`처럼 의도를 보내고, 서버가 현재 위치, 경기 규칙과 tick을 기준으로 다음 위치를 계산합니다.

## 정본 상태를 정하는 순서

1. 경기 규칙에 따라 바뀌는 값을 나열합니다.
2. 각 값을 변경할 수 있는 process와 방을 하나로 정합니다.
3. 클라이언트가 요청할 수 있는 명령을 정의합니다.
4. 명령마다 세션, 경기 단계, resource, cooldown과 소유 관계를 확인합니다.
5. 거절된 명령이 위치, 점수, cooldown과 `sequence`를 바꾸지 않는지 검사합니다.
6. account, inventory, reward처럼 방 밖에서 오래 유지해야 하는 값은 별도 저장 주체에 맡깁니다.

한 상태를 여러 스레드가 직접 수정하지 않습니다. network callback은 명령을 검증 가능한 형태로 큐에 넣고, 방의 tick 실행부가 정본 상태를 바꾸는 방식이 일반적입니다.

## 명령 검증 순서

다음 순서는 한 예시입니다. 실제 명령에 맞게 항목을 줄이거나 추가할 수 있지만, 앞 단계에서 실패한 요청은 뒤 단계의 값을 바꾸지 않아야 합니다.

```text
message framing과 version
→ identity와 session
→ room·match 참가 관계
→ sequence와 duplicate
→ payload type·length·range
→ 현재 경기 단계에서 허용한 명령인지
→ resource·cooldown·rate limit
→ 다음 상태 계산
→ 정본 상태 반영
→ 결과 event와 audit 기록
```

상태를 먼저 바꾼 뒤 실패하면 되돌리는 방식은 누락 위험이 큽니다. 가능하면 모든 검사를 끝낸 뒤 다음 값을 계산하고, 성공한 결과만 한 번에 반영합니다. 여러 값을 바꿔야 한다면 실패 시 원래 상태를 보존하는 검사를 반드시 둡니다.

## 지켜야 할 조건

- 한 방의 정본 상태를 변경하는 실행 주체는 하나여야 합니다.
- 거절된 명령은 위치, 점수, cooldown, inventory와 `sequence`를 바꾸지 않습니다.
- 클라이언트 시각은 지연 추정에 참고할 수 있지만 명령 순서의 유일한 기준으로 사용하지 않습니다.
- 클라이언트가 보낸 object ID는 현재 세션과 방에서 접근 가능한지 확인합니다.
- 경기 결과와 보상은 같은 요청을 여러 번 받아도 한 번만 반영되게 합니다.
- log에는 판정에 필요한 식별자와 reason code만 남기고 secret과 불필요한 개인정보를 기록하지 않습니다.

## 대표적인 잘못된 구현

### 클라이언트가 결과를 제출합니다

클라이언트가 위치, 점수나 경기 결과를 보내고 서버가 범위만 확인합니다. 허용 범위 안에서 조작한 값을 정상 결과와 구분할 수 없습니다.

### 여러 실행 경로가 같은 상태를 바꿉니다

network callback과 tick thread가 같은 플레이어 객체를 직접 수정합니다. 실행 순서가 환경에 따라 달라지고 같은 입력을 다시 실행해도 결과가 달라질 수 있습니다.

### 검증 전에 일부 값을 바꿉니다

resource를 먼저 차감한 뒤 cooldown 검사에서 실패합니다. 명령은 거절됐지만 resource는 사라집니다.

### 방이 외부 저장 상태까지 직접 소유합니다

방 process가 account나 reward를 직접 수정하면 재시작과 retry에서 중복 지급이나 누락이 생길 수 있습니다.

## 확인 질문

- 클라이언트가 보낼 수 있는 최소 명령은 무엇입니까?
- 명령이 거절될 때 바뀌면 안 되는 값은 무엇입니까?
- 한 방의 정본 상태를 바꾸는 함수는 어디입니까?
- network thread와 tick 실행부가 같은 객체를 직접 수정합니까?
- 다른 플레이어의 object ID를 보낸 요청을 어디에서 거절합니까?
- 경기 결과를 여러 번 전달해도 업무 효과가 한 번만 남는 근거는 무엇입니까?
