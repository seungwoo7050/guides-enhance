# 동시성·잠금과 실행기

여러 스레드가 같은 객체를 읽고 바꾸면 각 작업이 단독으로는 올바르더라도 전체 결과가 틀릴 수 있습니다. 동시성 오류는 실행 속도가 빨라서 우연히 생기는 문제가 아니라, 함께 실행되어야 할 연산과 공유 자원의 수명을 정하지 않았을 때 발생합니다.

## 스레드와 공유 상태

한 JVM에서 실행되는 스레드는 각자 호출 스택을 가지지만 heap의 객체를 함께 사용할 수 있습니다. 두 스레드가 같은 필드를 읽고 쓰면 실행 순서에 따라 결과가 달라질 수 있습니다.

다음 코드는 한 줄처럼 보여도 여러 단계로 실행됩니다.

```text
현재 값 읽기 → 변경 가능 여부 판단 → 새 값 기록
```

```java
if (balance >= amount) {
  balance -= amount;
}
```

두 스레드가 같은 `balance`를 읽으면 둘 다 차감 가능하다고 판단할 수 있습니다. 두 스레드가 같은 새 값을 기록하면 한 번의 변경이 사라집니다. 이를 손실 갱신이라고 합니다.

## visibility와 atomicity

`volatile`은 한 스레드가 기록한 값을 다른 스레드가 관찰할 수 있게 하고 일부 명령 재배치를 제한합니다. 그러나 여러 연산을 하나로 묶지는 않습니다.

```java
volatile int balance;

if (balance >= amount) {
  balance -= amount;
}
```

`balance`의 최신 값이 보이더라도 읽기, 비교와 쓰기 사이에 다른 스레드가 끼어들 수 있습니다.

`AtomicLong.addAndGet`처럼 하나의 값에 대한 단순 연산은 atomic type으로 처리할 수 있습니다. 하지만 다음처럼 여러 조건과 값이 함께 바뀌어야 한다면 atomic variable 하나만으로 충분하지 않습니다.

```text
잔액이 충분한지 확인
→ 잔액 차감
→ 적용 횟수 증가
→ 결과 기록
```

이 경우에는 잠금으로 필요한 연산 전체를 보호하거나, 바뀌지 않는 상태 객체를 한 번에 교체하는 방식을 검토합니다.

## 경쟁 상태를 반복해서 재현합니다

동시성 테스트에서 `Thread.sleep`으로 작업 순서를 추측하지 않습니다. 컴퓨터의 부하와 실행 속도가 달라지면 테스트 결과도 달라질 수 있습니다.

다음 도구로 필요한 시점을 직접 만듭니다.

- `CountDownLatch`: 여러 작업이 준비될 때까지 기다리거나 한 번의 진행 신호를 보냅니다.
- `CyclicBarrier`: 정해진 수의 작업이 같은 지점에 도착한 뒤 함께 진행합니다.
- 제어 가능한 `Clock`이나 collaborator: 작업을 특정 호출 지점에서 멈춥니다.

[Counter Race](../../exercises/counter-race/README.md)는 두 작업이 같은 값을 읽은 뒤 barrier에서 기다리게 합니다. 두 작업이 모두 도착하면 같은 초기 값으로 차감을 계속해 손실 갱신을 매번 재현합니다.

테스트는 최종 값 하나만 확인하지 않습니다.

- 성공한 작업 수
- 승인된 변경량의 합
- 최종 값
- 기록된 변경 건수
- 작업 스레드에서 발생한 예외

여러 값을 함께 확인해야 서로 모순되는 결과를 찾을 수 있습니다.

## 잠금 범위를 정합니다

한 JVM 안의 짧은 상태 변경에는 `synchronized`나 `ReentrantLock`을 사용할 수 있습니다.

```java
lock.lock();
try {
  long next = Math.subtractExact(balance, amount);
  if (next < 0) {
    throw new IllegalStateException("잔액이 부족합니다.");
  }
  balance = next;
} finally {
  lock.unlock();
}
```

잠금은 함께 지켜야 하는 검증과 변경 전체를 포함해야 합니다. 값을 읽을 때만 잠그거나 쓸 때만 잠그면 읽은 값이 여전히 유효하다는 보장이 없습니다.

잠금 안에는 필요한 계산과 메모리 상태 변경만 둡니다. 네트워크 호출, 파일 I/O와 호출 시간이 긴 콜백을 잠금 안에서 실행하면 같은 상태와 관계없는 작업도 오래 기다립니다.

여러 잠금을 사용한다면 항상 같은 순서로 획득합니다. 순서가 다르면 두 스레드가 서로 상대 잠금을 기다리는 교착 상태가 생길 수 있습니다. 가능하면 함께 바뀌는 상태를 한 객체와 한 잠금으로 관리합니다.

JVM의 잠금은 다른 프로세스나 서버의 상태를 보호하지 않습니다. 데이터베이스와 여러 서비스 사이의 동시성에는 해당 저장소와 통신 방식에 맞는 별도 처리가 필요합니다.

## 공유할 상태를 줄입니다

잠금을 추가하기 전에 상태를 공유하지 않아도 되는지 확인합니다.

- 생성 뒤 바뀌지 않는 record와 값 객체를 전달합니다.
- 가변 컬렉션 대신 복사본을 반환합니다.
- 상태를 바꿀 수 있는 객체를 하나로 제한합니다.
- 작업마다 지역 변수를 사용합니다.
- 외부 콜백에 내부 가변 객체를 그대로 전달하지 않습니다.

공유 상태가 줄어들면 잠금 범위와 경쟁 가능성도 함께 줄어듭니다.

## 제한된 실행기를 구성합니다

스레드 풀은 작업자 수만 정한다고 끝나지 않습니다. 다음 항목을 함께 결정해야 합니다.

- 작업자 수
- 대기열 종류와 크기
- 대기열이 찼을 때 처리 방법
- 작업 예외를 확인하는 방법
- 작업별 제한 시간과 취소 방법
- 인터럽트 처리
- 정상 종료를 기다릴 시간
- 제한 시간 이후 강제 종료 방법
- 작업자 스레드 이름

무제한 대기열은 새 작업을 계속 받지만 메모리 사용량과 대기 시간이 끝없이 늘어날 수 있습니다. 제한된 대기열과 `RejectedExecutionException`을 사용하면 더 받을 수 없는 상태를 호출자에게 즉시 알릴 수 있습니다.

[Bounded Task Runner](../../exercises/bounded-task-runner/README.md)는 고정된 작업자 수와 `ArrayBlockingQueue`를 사용하고, 포화 상태에서 `AbortPolicy`로 새 작업을 거절합니다.

## `Future`에서 작업 결과를 확인합니다

실행기에 작업을 제출한 뒤 `Future`를 읽지 않으면 작업 스레드에서 발생한 예외를 놓칠 수 있습니다.

```java
try {
  return future.get();
} catch (InterruptedException error) {
  Thread.currentThread().interrupt();
  throw new IllegalStateException("작업 대기가 중단되었습니다.", error);
} catch (ExecutionException error) {
  throw new IllegalStateException("작업이 실패했습니다.", error.getCause());
}
```

여러 작업을 제출했다면 일부 결과만 확인하고 끝내지 않습니다. 모든 `Future`의 성공과 실패를 회수하고 전체 대기 시간도 제한합니다.

`CompletableFuture`는 비동기 결과를 조합하기 편하지만, 기본 비동기 메서드는 공용 풀을 사용할 수 있습니다. 어느 실행기에서 실행할지, 예외를 어떻게 전달할지, 취소가 어디까지 전달되는지 명시합니다.

## 시간 초과와 취소는 다릅니다

호출자가 기다리기를 포기했다고 해서 작업이 자동으로 멈추는 것은 아닙니다.

```java
try {
  return future.get(timeout.toNanos(), TimeUnit.NANOSECONDS);
} catch (TimeoutException error) {
  future.cancel(true);
  throw error;
}
```

`cancel(true)`는 실행 중인 스레드에 인터럽트를 요청합니다. 작업이 인터럽트를 확인하지 않거나 블로킹 API가 인터럽트에 반응하지 않으면 바로 끝나지 않을 수 있습니다.

반복 작업은 중간에 인터럽트 상태를 확인하고, 일관된 상태에서 빠져나올 수 있어야 합니다.

## 인터럽트를 잃지 않습니다

`InterruptedException`은 현재 작업을 중단해 달라는 신호입니다. 다음 중 하나를 선택합니다.

- 정리한 뒤 `InterruptedException`을 그대로 상위로 전달합니다.
- 다른 예외로 바꿔야 한다면 `Thread.currentThread().interrupt()`로 상태를 복원합니다.

예외를 잡고 무시하면 상위 종료 코드가 중단 요청을 알 수 없습니다.

## 실행기를 종료합니다

일반적인 종료 순서는 다음과 같습니다.

```text
새 작업 수락 중단
→ 이미 받은 작업 완료 대기
→ 제한 시간 초과 시 실행 중인 작업에 인터럽트 요청
→ 대기 중인 작업 취소
→ 종료 여부 재확인
```

`shutdown()`만 호출하고 종료를 확인하지 않으면 JVM이 남은 스레드 때문에 끝나지 않거나 작업이 실제로 완료됐는지 알 수 없습니다. 반대로 처음부터 `shutdownNow()`를 호출하면 끝낼 수 있었던 작업까지 불필요하게 중단할 수 있습니다.

`shutdownNow()`는 시작하지 못한 `Runnable` 목록을 반환합니다. 해당 작업이 `Future`를 가지고 있다면 취소 상태로 바꿔야 호출자가 무한히 기다리지 않습니다.

종료 메서드는 여러 번 호출해도 같은 결과가 되도록 만드는 편이 안전합니다. 종료가 시작된 뒤에는 새 작업을 즉시 거절합니다.

## 동시성 테스트 점검

- `sleep`으로 순서를 맞추지 않습니다.
- latch나 barrier 대기에 제한 시간을 둡니다.
- 모든 `Future`를 읽어 작업 예외를 테스트 스레드로 전달합니다.
- 테스트가 실패해도 실행기와 차단된 작업을 정리합니다.
- 최종 값, 성공 횟수와 기록 수를 함께 확인합니다.
- 테스트가 끝난 뒤 작업자 스레드가 남지 않게 합니다.

## 성능은 정확성 뒤에 측정합니다

작업자 수를 늘린다고 처리량이 항상 늘지는 않습니다. CPU를 사용하는 작업인지 블로킹 작업인지, 대기열 지연, 잠금 경쟁과 외부 시스템 제한을 측정해야 합니다.

먼저 정확성 테스트를 통과한 뒤 JFR이나 profiler로 실제 병목을 확인합니다. 잘못된 결과를 더 빨리 만드는 변경은 최적화가 아닙니다.

## 완료 기준

- visibility와 atomicity의 차이를 설명합니다.
- `volatile`, atomic type과 잠금을 각각 언제 사용할지 구분합니다.
- latch나 barrier로 경쟁 순서를 반복해서 재현합니다.
- 읽기·판단·쓰기를 필요한 범위 전체에서 보호합니다.
- 작업자 수, 대기열, 거절과 종료 방법을 정한 실행기를 만듭니다.
- 작업 예외, 시간 초과와 취소를 호출자에게 전달합니다.
- 인터럽트를 잃지 않고 종료 뒤 스레드가 남지 않게 합니다.

이제 [Counter Race](../../exercises/counter-race/README.md)와 [Bounded Task Runner](../../exercises/bounded-task-runner/README.md)를 확인한 뒤 [Concurrent Job Ledger](../../exercises/concurrent-job-ledger/README.md)를 완성합니다.
