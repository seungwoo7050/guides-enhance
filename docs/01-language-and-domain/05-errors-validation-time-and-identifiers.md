# 오류·검증·시간과 식별자

실패를 모두 같은 예외나 `false`로 반환하면 호출자는 입력을 고쳐야 하는지, 현재 상태를 확인해야 하는지, 잠시 뒤 다시 시도해야 하는지 판단하기 어렵습니다. 실패 종류는 예외 클래스의 수보다 실패 뒤 가능한 행동을 기준으로 나눕니다.

## 실패 종류를 구분합니다

| 실패 종류 | 예 | 호출자가 할 수 있는 일 |
| --- | --- | --- |
| 입력 조건 위반 | 빈 식별자, 0 이하 금액 | 입력을 수정합니다. |
| 현재 상태에서의 거절 | 잔액 부족, 종료한 실행기 | 상태를 확인하거나 다른 요청을 선택합니다. |
| 실행 환경 실패 | 파일 읽기 실패, 시간 초과 | 원인을 기록하고 제한된 재시도나 복구를 검토합니다. |
| 프로그램 내부의 잘못된 상태 | 도달할 수 없어야 하는 분기 | 결함으로 보고 코드를 수정합니다. |

잔액 부족처럼 정상적으로 예상할 수 있는 거절을 일시 장애로 분류하면 같은 요청을 의미 없이 반복할 수 있습니다. 반대로 시간 초과를 입력 오류로 숨기면 재시도나 취소 여부를 판단할 근거가 사라집니다.

## checked exception과 unchecked exception

checked exception은 호출하는 코드가 처리하거나 다시 선언해야 합니다. 파일과 네트워크 API에서 자주 만납니다. unchecked exception은 메서드 선언에 강제되지 않지만 문서와 테스트에서 실패 의미를 정해야 합니다.

기계적으로 “복구할 수 있으면 checked exception”이라고 정하지 않습니다.

- 현재 메서드가 실제로 처리할 수 있으면 처리합니다.
- 호출자가 결정해야 하면 원인을 보존해 전달합니다.
- 저수준 예외를 공개 API 전체에 그대로 노출하지 않도록 의미 있는 위치에서 바꿉니다.
- 입력과 상태 거절은 가능한 한 구체적인 예외 타입과 메시지를 사용합니다.

```java
try {
  return Files.readString(path);
} catch (IOException error) {
  throw new ConfigurationLoadException("설정을 읽지 못했습니다: " + path, error);
}
```

원인 예외를 버리거나, 오류를 기록한 뒤 성공값을 반환하지 않습니다. 같은 예외를 여러 메서드에서 반복해 기록하면 하나의 실패가 여러 사건처럼 보일 수 있으므로 실제 처리 지점에서 한 번 기록합니다.

## 검증할 위치를 정합니다

같은 값도 위치에 따라 다른 내용을 검사합니다.

- 명령행이나 HTTP 입력을 읽는 코드는 문자열 형식과 필수 항목을 검사합니다.
- 값 객체 생성자는 항상 참이어야 하는 조건을 검사합니다.
- 현재 상태를 가진 서비스는 잔액, 중복 요청과 종료 여부를 판단합니다.
- 데이터베이스 제약은 동시에 들어오는 요청 사이에서도 마지막 무결성을 지킵니다.

값 객체가 사용자 권한이나 데이터베이스 조회까지 수행하게 하지 않습니다. 반대로 “금액은 0보다 큽니다.”처럼 항상 참이어야 하는 조건을 모든 서비스에서 반복하지 않습니다.

## 실패 전에 새 상태를 계산합니다

상태를 바꾸는 작업은 실패 뒤 무엇이 남는지까지 정해야 합니다.

```text
입력 검증 실패       → 기존 상태 유지
정수 연산 실패       → 기존 상태 유지
외부 저장 실패       → 메모리와 저장 결과의 관계를 명시
취소 또는 인터럽트   → 완료된 작업과 남은 작업을 명시
```

다음처럼 필요한 검증과 새 값을 먼저 계산한 뒤 상태를 바꿉니다.

```java
long nextBalance = Math.subtractExact(balance, amount);
if (nextBalance < 0) {
  throw new IllegalStateException("잔액이 부족합니다.");
}
balance = nextBalance;
```

상태를 먼저 바꾸고 뒤에서 예외가 발생하면 호출자가 다시 시도할 때 같은 변경이 두 번 적용될 수 있습니다.

[Concurrent Job Ledger](../../exercises/concurrent-job-ledger/README.md)는 다음 잔액과 적용 횟수를 모두 계산한 뒤 두 필드를 함께 반영합니다.

## 닫아야 하는 자원의 수명

파일, stream, socket과 실행기는 사용이 끝나면 닫아야 합니다. 일반적으로 자원을 만든 코드가 닫을 의무도 가집니다.

```java
try (BufferedReader reader = Files.newBufferedReader(path)) {
  return reader.lines().toList();
}
```

자원을 반환해 호출자에게 수명을 넘긴다면 누가 언제 닫아야 하는지 API에 드러냅니다. 정상 종료뿐 아니라 예외와 조기 반환에서도 정리 코드가 실행되어야 합니다.

실행기는 다음 순서로 종료할 수 있습니다.

```text
새 작업 수락 중단
→ 이미 받은 작업 완료 대기
→ 제한 시간 초과 시 남은 작업 취소
→ 종료 여부 재확인
```

종료 대기가 인터럽트되면 정리한 뒤 현재 스레드의 인터럽트 상태를 복원합니다.

## 시간을 직접 읽지 않습니다

저장하거나 다른 시스템으로 전달할 시각은 보통 `Instant`로 표현하고 UTC로 보존합니다. 사용자의 지역 시간은 입력과 표시 시점에 `ZoneId`와 함께 변환합니다.

테스트할 코드에서 `Instant.now()`를 직접 호출하지 않고 `Clock`을 주입합니다.

```java
public final class ExpiryPolicy {
  private final Clock clock;

  public ExpiryPolicy(Clock clock) {
    this.clock = Objects.requireNonNull(clock, "clock");
  }

  public boolean expired(Instant deadline) {
    return !clock.instant().isBefore(deadline);
  }
}
```

테스트에서는 `Clock.fixed`로 같은 시각을 반복해서 사용할 수 있습니다.

```java
Clock clock = Clock.fixed(
    Instant.parse("2026-01-02T03:04:05Z"),
    ZoneOffset.UTC);
```

마감 시각과 정확히 같은 순간을 포함하는지, 사용자 지역 날짜를 어떤 시간대로 해석하는지도 테스트 이름에 드러냅니다.

## 식별자가 나타내는 대상을 정합니다

UUID를 사용한다는 사실만으로 식별자 설계가 끝나지는 않습니다. 다음을 정해야 합니다.

- 누가 식별자를 만듭니까?
- 저장 전과 저장 후 중 언제 만듭니까?
- 같은 요청을 다시 보낼 때 같은 식별자를 사용합니까?
- 같은 식별자로 다른 내용이 들어오면 어떻게 처리합니까?
- 업무 대상 ID, 요청 추적 ID와 작업 ID를 구분합니까?
- 내부 ID를 외부에 그대로 노출해도 됩니까?

문자열을 그대로 전달하기보다 값 타입으로 감싸면 빈 값과 서로 다른 종류의 식별자를 섞는 실수를 줄일 수 있습니다.

```java
public record JobId(String value) {
  public JobId {
    Objects.requireNonNull(value, "작업 식별자가 필요합니다.");
    if (value.isBlank()) {
      throw new IllegalArgumentException("작업 식별자는 비어 있을 수 없습니다.");
    }
  }
}
```

같은 작업 ID와 같은 내용이 다시 들어오면 이전 완료 결과를 재사용할 수 있습니다. 같은 ID에 다른 내용이 들어오면 충돌로 거절해야 합니다.

## 민감한 정보와 오류 메시지

예외 메시지와 로그에 비밀번호, 토큰, 세션 ID와 개인정보를 넣지 않습니다. 예상하지 못한 예외에는 스택 추적과 안전한 추적 ID를 남기고, 예상 가능한 거절은 필요한 정보만 기록합니다.

사용자에게 보여 줄 메시지와 운영자가 원인을 찾을 진단 정보는 목적이 다릅니다. 내부 클래스 이름, 파일 경로와 SQL을 외부 응답에 그대로 노출하지 않습니다.

## 완료 기준

- 입력 조건 위반, 현재 상태의 거절, 실행 환경 실패와 내부 결함을 구분합니다.
- 예외를 다른 타입으로 바꿀 때 원인을 보존합니다.
- 검증과 새 값 계산이 끝난 뒤 상태를 반영합니다.
- 닫아야 하는 자원을 누가 관리하는지 정하고 모든 종료 경로에서 정리합니다.
- `Clock`으로 시간에 의존하는 테스트를 반복할 수 있게 만듭니다.
- 식별자의 생성, 재사용과 충돌 의미를 설명합니다.
