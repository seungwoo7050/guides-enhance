# 파이프라인의 위험과 분기 처리

파이프라인은 명령 하나를 여러 단계로 나누고 서로 다른 명령의 단계를 겹쳐 처리량을 높입니다. 그러나 레지스터 의존성, 같은 하드웨어 사용과 분기 결과 때문에 일부 단계를 멈추거나 이미 가져온 명령을 버려야 할 수 있습니다.

## 학습 목표

- 구조적 위험, 데이터 위험과 제어 위험을 구분합니다.
- 값 전달, 정지와 잘못 가져온 명령 제거를 적용할 위치를 찾습니다.
- 적재 직후 사용 의존성과 분기 예측 실패 비용을 계산합니다.
- 파이프라인 깊이, CPI와 클록 주기를 함께 비교합니다.

## 5단계 순차 파이프라인

교육용 RISC 파이프라인은 다음 다섯 단계를 자주 사용합니다.

| 단계 | 수행하는 일 |
| --- | --- |
| IF | PC가 가리키는 명령을 가져옵니다. |
| ID | 연산 코드를 해석하고 소스 레지스터를 읽습니다. |
| EX | ALU 결과, 주소 또는 분기 조건을 계산합니다. |
| MEM | 데이터 메모리를 읽거나 씁니다. |
| WB | 결과를 목적지 레지스터에 기록합니다. |

```text
cycle: 1  2  3  4  5  6  7
I0:    IF ID EX MEM WB
I1:       IF ID EX MEM WB
I2:          IF ID EX MEM WB
```

파이프라인이 채워진 뒤에는 이상적인 단일 발행 파이프라인이 사이클마다 한 명령을 완료할 수 있습니다. 명령 하나의 지연 시간은 여전히 여러 사이클입니다.

## 단계 사이 레지스터

각 단계의 결과는 다음 클록 에지에서 단계 레지스터에 저장됩니다.

```text
IF/ID → ID/EX → EX/MEM → MEM/WB
```

명령 비트뿐 아니라 피연산자, 목적지 레지스터, 제어 신호와 예외 정보도 함께 이동해야 합니다. 목적지 번호를 잃으면 WB 단계에서 어느 레지스터에 쓸지 알 수 없습니다.

단계 레지스터도 지연, 면적과 전력을 사용합니다. 단계를 계속 잘게 나눈다고 주파수가 끝없이 높아지는 것은 아닙니다.

## 구조적 위험

서로 다른 단계가 같은 자원을 동시에 요구할 때 발생합니다.

```text
I0: MEM 단계에서 data memory 읽기
I3: IF 단계에서 instruction 읽기
```

단일 포트 메모리 하나만 있다면 둘을 동시에 처리할 수 없습니다. 해결 방법은 다음과 같습니다.

- 한 명령을 정지시킵니다.
- 명령 메모리와 데이터 메모리 또는 캐시를 나눕니다.
- 여러 포트를 제공하는 자원을 사용합니다.
- 단계 구성을 바꿉니다.

자원을 늘리면 면적, 전력과 타이밍 비용이 생깁니다.

## 데이터 위험

다음 명령은 첫 명령의 결과가 필요합니다.

```asm
add r1, r2, r3
sub r4, r1, r5
```

### RAW: 쓰기 이후 읽기

뒤 명령이 앞 명령의 결과를 읽습니다. 실제 값 의존성이므로 결과가 준비되기 전에 실행할 수 없습니다.

### WAR: 읽기 이후 쓰기

뒤 명령이 앞 명령이 아직 읽지 않은 레지스터 이름에 먼저 씁니다.

### WAW: 쓰기 이후 쓰기

같은 목적지에 대한 쓰기 순서가 바뀔 수 있습니다.

단순한 순차 발행·순차 완료 파이프라인에서는 WAR와 WAW가 나타나지 않을 수 있습니다. 비순차 실행에서는 레지스터 이름 변경으로 이름 때문에 생긴 WAR와 WAW를 제거합니다.

## 값 전달

ALU 결과는 EX 단계 끝에 준비되지만 레지스터 파일에는 WB에서 기록됩니다. 앞 명령의 EX/MEM 또는 MEM/WB 값을 다음 명령의 EX 입력으로 직접 선택하면 기다리는 사이클을 줄일 수 있습니다. 이를 `forwarding`이라고 합니다.

```text
앞 명령의 ALU 결과
        └────────→ 다음 명령의 EX operand
```

전달 장치는 다음을 확인합니다.

- 앞 명령이 레지스터에 쓰는 명령입니까?
- 목적지 레지스터가 현재 명령의 소스 레지스터와 같습니까?
- 목적지가 0 레지스터가 아닙니까?
- 여러 앞 명령이 같은 레지스터에 쓴다면 가장 최근 값을 선택했습니까?

## 적재 직후 사용 위험

```asm
lw  r1, 0(r2)
add r3, r1, r4
```

적재한 값은 MEM 단계가 끝나야 준비됩니다. 바로 뒤 명령은 EX 시작 시점에 값이 필요하므로 일반 ALU 전달만으로 해결할 수 없습니다. 한 사이클의 빈 단계를 넣어야 합니다.

```text
cycle: 1  2  3  4  5  6  7  8
lw:     IF ID EX MEM WB
add:       IF ID ST EX MEM WB
```

```sh
cd exercises/processor-model
python3 processor-model.py pipeline \
  fixtures/traces/pipeline-load-use.trace --forwarding full
```

`data_stalls=1`을 확인한 뒤 `--forwarding none`의 결과와 비교합니다.

## 정지를 적용하는 위치

적재 직후 사용 위험을 처리할 때는 다음 상태를 조정할 수 있습니다.

```text
PC write 비활성화
IF/ID write 비활성화
ID/EX에 no-op control 삽입
```

값을 소비하는 명령은 ID에 머물고 적재 명령은 앞으로 진행하며 EX에는 빈 단계가 들어갑니다. “파이프라인 전체를 멈춥니다”라고만 설명하면 어느 단계가 진행하는지 알 수 없습니다.

## 제어 위험

분기 결과가 EX에서 확정된다면 그동안 IF와 ID에는 순차 주소의 명령이 들어와 있습니다. 실제로 분기가 실행되면 이 명령들을 아키텍처 상태에 반영하면 안 됩니다.

대응 방법은 다음과 같습니다.

- 분기 결과가 나올 때까지 명령 인출을 멈춥니다.
- 항상 실행됨 또는 실행되지 않음으로 정적으로 예측합니다.
- 이전 결과를 이용해 동적으로 예측합니다.
- 분기 목적지를 더 이른 단계에서 계산합니다.
- ISA가 분기 지연 슬롯을 정의할 수 있습니다.

잘못 가져온 명령은 버리고 올바른 목적지부터 다시 가져옵니다. 이 동작을 `flush`라고 부릅니다.

```sh
python3 processor-model.py pipeline \
  fixtures/traces/pipeline-branch.trace --branch-penalty 2
```

추적 입력의 `@taken`은 분기가 실행됐다는 뜻입니다. 분기가 EX에 있을 때 ID와 IF의 더 젊은 명령을 버리고 목적지 인덱스부터 다시 가져옵니다. 출력의 `ID*`, `IF*`는 폐기된 단계를 나타냅니다.

## 2비트 분기 예측기

1비트 예측기는 직전 결과만 저장합니다. 반복문의 마지막 미실행 결과 때문에 상태가 바뀌면 다음 반복문의 첫 실행 분기에서도 틀릴 수 있습니다.

2비트 포화 계수기는 한 번 반대 결과가 나왔다고 즉시 큰 방향을 바꾸지 않습니다.

```text
0: strongly not-taken
1: weakly not-taken
2: weakly taken
3: strongly taken
```

실제 예측기는 전역·지역 이력, 분기 목적지 버퍼와 반환 주소 스택을 함께 사용할 수 있습니다. 기본적으로 다음 질문은 같습니다.

- 어떤 PC 또는 이력으로 표를 조회합니까?
- 어느 상태를 실행 분기로 해석합니까?
- 언제 계수기를 갱신합니까?
- 잘못 추측한 갱신을 어떻게 복구합니까?

## 분기 비용과 CPI

분기 비율을 `b`, 예측 실패율을 `m`, 한 번 틀렸을 때 잃는 사이클을 `p`라고 하면 추가 CPI를 다음처럼 근사할 수 있습니다.

```text
branch penalty CPI ≈ b × m × p
```

분기가 20%, 예측 실패율이 5%, 실패 비용이 15사이클이면 약 `0.15 CPI`가 추가됩니다. 정확도뿐 아니라 예측기 조회 지연, 저장 공간과 목적지 준비 시점도 고려해야 합니다.

## 정밀한 예외

여러 명령이 파이프라인에 있을 때 더 젊은 명령이 먼저 폴트를 발견할 수 있습니다. 정밀한 예외를 제공하려면 소프트웨어에 다음 상태가 보여야 합니다.

- 폴트보다 오래된 명령은 모두 반영되어 있습니다.
- 폴트가 난 명령과 더 젊은 명령은 반영되지 않습니다.
- 폴트가 난 PC와 원인을 확인할 수 있습니다.

순차 파이프라인에서는 더 젊은 명령의 쓰기 신호를 끄고 단계를 비우는 방식으로 처리할 수 있습니다. 비순차 코어에서는 재정렬 버퍼가 프로그램 순서대로 결과를 반영합니다.

## 파이프라인 성능 비교

파이프라인을 깊게 하면 한 단계의 논리를 줄여 클록 주기를 낮출 수 있습니다. 동시에 다음 비용이 늘어날 수 있습니다.

- 단계 레지스터 지연과 전력
- 분기 예측 실패 비용
- 전달 경로와 멀티플렉서
- 제어 복잡성

```text
old time = IC × old CPI × old clock period
new time = IC × new CPI × new clock period
```

단계 수만 비교해서 더 빠르다고 결론 내리면 안 됩니다.

## 추적표를 그리는 순서

1. RAW 의존성을 표시합니다.
2. 결과를 만드는 명령의 값이 어느 단계 끝에 준비되는지 적습니다.
3. 값을 사용하는 명령이 어느 단계 시작에 값을 요구하는지 적습니다.
4. 전달 경로가 있는지 확인합니다.
5. 해결되지 않으면 유지할 단계 레지스터와 넣을 빈 단계를 표시합니다.
6. 실행된 분기 뒤에 잘못 가져온 명령을 표시하고 버립니다.
7. 총 사이클, 반영한 명령 수와 CPI를 계산합니다.

## 직접 확인할 문제

1. `add r1,...` 뒤에 독립 명령 하나가 있고 그다음 `sub ...,r1,...`가 있을 때 값 전달 유무에 따른 정지를 그려 보세요.
2. 저장 명령의 주소 소스와 데이터 소스가 각각 어느 단계까지 필요할 수 있는지 설명해 보세요.
3. 분기를 ID에서 확정할 때와 EX에서 확정할 때의 타이밍과 버릴 명령 수를 비교해 보세요.
4. `T T T N` 패턴을 두 번 반복할 때 1비트와 2비트 예측기의 실패 횟수를 계산해 보세요.
5. 주파수가 20% 늘고 CPI가 15% 늘었다면 전체 속도 향상률을 계산해 보세요.
