# 테스트와 품질

모든 기능을 하나의 브라우저 시나리오로 검사하면 느리고 실패 원인을 찾기 어렵습니다. 반대로 순수 함수 테스트만 있으면 실제 HTTP 라우트, 데이터베이스, WebSocket과 브라우저가 깨져도 발견하지 못합니다. 문제가 처음 드러나는 가장 짧은 실행 범위에서 검사하고, 소수의 종단 간 테스트로 전체 조립 상태를 확인합니다.

## 목표

- 단위·스키마·컴포넌트·API·데이터베이스·WebSocket·브라우저 테스트를 구분합니다.
- 정상·실패·최댓값·경쟁 조건을 반복해서 재현합니다.
- 가짜 구현과 실제 인프라 테스트가 각각 놓치는 문제를 설명합니다.
- 타입 검사, 테스트와 프로덕션 빌드를 따로 실행합니다.
- 테스트가 잘못된 구현을 실제로 거부하는지 확인합니다.

## 위험에 맞는 검사

| 위험 | 먼저 둘 테스트 |
|---|---|
| 좌표 제한과 상태 전이 | 순수 함수 단위 테스트 |
| Zod가 잘못된 값 거부 | 스키마 테스트 |
| 레이블·버튼·오류 안내 | 컴포넌트 또는 브라우저 테스트 |
| Fastify 훅·상태 코드·JSON 변환 | `app.inject` API 테스트 |
| 고유·외래 키·롤백 | 실제 PostgreSQL 테스트 |
| 방별 전송·재연결 | 실제 WebSocket 연결 두 개 |
| 라우팅·키보드·히스토리 | 실제 브라우저 테스트 |
| 서버/브라우저 import 오류 | Next.js 프로덕션 빌드 |

테스트 이름은 내부 함수보다 사용자가 관찰할 결과를 적습니다.

```text
viewer는 메모 내용을 수정할 수 없다
같은 좌석을 예약하는 두 요청 중 하나만 성공한다
뒤로 가면 이전 검색어와 결과가 복원된다
```

## 단위 테스트

외부 자원을 사용하지 않는 계산은 많은 입력을 빠르게 검사할 수 있습니다.

```ts
it("보드 밖 좌표를 허용 범위로 줄입니다", () => {
  expect(clampPoint({ x: -10, y: 900 }, { width: 800, height: 600 }))
    .toEqual({ x: 0, y: 600 });
});
```

현재 시각과 ID가 필요하면 `Clock`, `IdGenerator`를 입력으로 전달해 고정합니다. 비공개 함수만 직접 검사하려고 코드를 억지로 공개하지 않습니다.

## 스키마 테스트

다음 값을 포함합니다.

- 필수 필드 누락
- 잘못된 타입
- 빈 문자열과 최대 길이
- 알 수 없는 메시지 종류
- `NaN`, `Infinity`
- 추가 필드 처리
- 이전·새 메시지 버전 호환

응답도 검사해 비밀번호 해시와 내부 필드가 포함되지 않았는지 확인합니다.

## 컴포넌트 테스트

역할과 접근 가능한 이름으로 요소를 찾습니다.

```ts
await user.type(screen.getByLabelText("제목"), "회의 기록");
await user.click(screen.getByRole("button", { name: "저장" }));
expect(await screen.findByRole("status")).toHaveTextContent("저장됨");
```

CSS 클래스와 내부 상태를 직접 검사하지 않습니다. 대기, 빈 결과, 성공과 오류를 각각 만들어 봅니다. 실제 시간을 기다리지 않고 완료 시점을 제어하는 가짜 API를 사용합니다.

## API 테스트

Fastify의 `app.inject`는 포트를 열지 않고도 플러그인, 훅, 라우트와 직렬화를 실행합니다.

- 정상 요청의 상태와 본문
- 입력 오류 400
- 인증 없음 401
- 권한 부족 403 또는 404
- 리소스 없음 404
- 버전·고유성 충돌 409
- 내부 오류 500과 내부 정보 비노출
- 쿠키와 요청 ID

각 테스트가 만든 애플리케이션을 반드시 닫습니다.

## 실제 데이터베이스 테스트

다음은 메모리 저장소로 대신할 수 없습니다.

- PostgreSQL 마이그레이션 문법
- 고유·외래 키·검사 제약
- 트랜잭션 롤백
- 잠금과 동시 수정
- 타임스탬프·JSON·큰 정수 표현

빈 데이터베이스에 마이그레이션을 적용하고 테스트마다 고유한 데이터를 사용합니다. 종료 전에 풀을 닫습니다.

## WebSocket 테스트

실제 서버와 두 연결을 사용합니다.

```text
A와 B 연결
→ 같은 방 참가
→ 둘 다 스냅샷 수신
→ A가 최종 변경 전송
→ A와 B가 같은 시퀀스의 패치 수신
→ B 재연결
→ B가 최신 스냅샷 수신
```

첫 번째 메시지가 원하는 종류라고 가정하지 않습니다. 특정 `type`과 `sequence`를 기다리는 함수를 사용하고, 성공·실패 양쪽에서 리스너와 타임아웃을 제거합니다.

## 브라우저 테스트

실제 브라우저에서만 확인할 수 있는 항목이 있습니다.

- 키보드 포커스와 폼 기본 동작
- URL과 방문 기록
- CSS 넘침과 뷰포트
- 동적 경로 직접 접근
- hydration과 브라우저 이벤트
- 쿠키와 CORS
- Canvas 포인터 좌표

Playwright에서는 역할, 레이블과 보이는 문장을 우선합니다. 고정된 `waitForTimeout` 대신 실제 결과가 나타날 때까지 기다립니다.

## 응답 순서 역전

테스트가 두 요청의 완료 시점을 직접 결정합니다.

```text
query=a     → 늦게 완료
query=beta  → 먼저 완료
```

최종 화면에는 `beta` 결과가 남아야 합니다. 소스에 `AbortController`라는 문자열이 있는지 찾는 대신 화면 결과를 검사합니다.

## 타입 검사와 빌드

```text
타입 검사 → 정적 타입과 import 오류
테스트    → 실행 중 동작과 실패 상태
빌드      → 프레임워크 컴파일과 서버/브라우저 분리
E2E       → 실제 프로세스와 브라우저 연결
```

하나가 통과했다고 다른 항목까지 증명되지는 않습니다.

## 잘못된 구현을 넣어 봅니다

테스트가 실제로 문제를 찾는지 확인하려면 다음 변경을 잠시 적용합니다.

- 레이블 제거
- `popstate` 처리 제거
- 버전 조건 제거
- 로그아웃에서 서버 세션 삭제 제거
- `viewer` 쓰기 허용
- WebSocket 정리 코드 제거

각 변경은 관련 테스트를 실패시켜야 합니다.

## 간헐적 실패 줄이기

- 고정 대기 대신 관찰 가능한 결과를 기다립니다.
- 시각, 난수와 네트워크 완료 순서를 제어합니다.
- 고정 포트를 공유하지 않습니다.
- 테스트마다 고유 데이터를 사용합니다.
- 서버, 타이머, 소켓, 풀과 브라우저를 `finally`에서 닫습니다.
- 실패 메시지에 기대값과 실제값을 포함합니다.

## 흔한 실수

- 모든 기능을 하나의 E2E 테스트에 넣습니다.
- CSS 선택자와 내부 클래스에 테스트를 결합합니다.
- 실제 PostgreSQL과 WebSocket을 모두 모킹합니다.
- 고정된 시간만 기다립니다.
- 타입 검사를 런타임 검증으로 간주합니다.
- 테스트 뒤 열린 자원을 남깁니다.
- 잘못된 구현도 통과하는지 확인하지 않습니다.

## 완료 기준

- 각 위험이 처음 드러나는 가장 짧은 테스트를 선택합니다.
- 정상·실패·최댓값·경쟁 조건을 반복해서 재현합니다.
- 실제 데이터베이스, WebSocket과 브라우저가 필요한 이유를 설명합니다.
- 타입 검사, 테스트, 빌드와 E2E를 따로 실행합니다.
- 테스트가 의도적인 잘못된 구현을 거부합니다.
