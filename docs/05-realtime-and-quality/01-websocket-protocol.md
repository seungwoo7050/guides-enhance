# WebSocket 프로토콜

HTTP 요청은 한 번의 요청과 응답으로 끝나지만 WebSocket 연결은 오래 유지됩니다. 연결이 열렸다는 사실만으로 사용자가 어느 방에 참가했는지, 마지막으로 받은 변경이 무엇인지, 현재 쓰기 권한이 있는지는 알 수 없습니다. 연결마다 사용자, 참가 상태, 마지막 활동 시각과 정리할 자원을 관리해야 합니다.

## 목표

- HTTP 업그레이드, WebSocket 연결과 방 참가를 구분합니다.
- 클라이언트와 서버 메시지를 실행 중에 검증합니다.
- 연결별 사용자와 참가한 방을 관리합니다.
- 메시지 크기, 전송 빈도, 송신 버퍼와 하트비트를 제한합니다.
- 종료와 재연결 뒤 상태 복구 방법을 설명합니다.

## 연결 시작

브라우저는 HTTP 요청으로 업그레이드를 요청합니다.

```text
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Origin: https://app.example.com
Cookie: app_session=...
```

서버는 연결을 열기 전에 다음을 확인합니다.

- 허용한 `Origin`
- 세션 만료 여부
- 사용자 계정 상태
- 사용자별 최대 연결 수
- 서버가 새 연결을 받을 준비가 되었는지

연결 뒤에도 특정 보드의 구성원이라고 가정하지 않습니다. `board.join` 메시지를 받은 뒤 현재 멤버십을 확인하고 방에 등록합니다.

## 메시지 스키마

```ts
const ClientMessageSchema = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("board.join"),
    boardId: z.string().uuid()
  }),
  z.object({
    type: z.literal("cursor.move"),
    boardId: z.string().uuid(),
    x: z.number().finite(),
    y: z.number().finite()
  }),
  z.object({
    type: z.literal("item.move"),
    boardId: z.string().uuid(),
    itemId: z.string().uuid(),
    baseVersion: z.number().int().nonnegative(),
    x: z.number().finite(),
    y: z.number().finite(),
    final: z.boolean()
  })
]);
```

수신 문자열을 JSON으로 바꾸는 단계와 스키마로 검사하는 단계를 나눕니다. 잘못된 메시지 하나가 다른 연결이나 서버 프로세스를 종료하게 해서는 안 됩니다.

## 식별자 구분

프로토콜이 커지면 여러 식별자가 생깁니다.

- `messageId`: 한 번 보낸 메시지를 추적
- `operationId`: 사용자의 한 변경 시도를 추적
- `itemId`: 리소스 식별자
- `sequence`: 서버가 확정한 방 전체 변경 순서
- `version`: 한 항목의 현재 버전

모든 메시지에 이 값을 전부 넣을 필요는 없습니다. 중복 제거, 복구와 추적에 실제로 사용하는 값만 보냅니다.

## 연결별 상태

```ts
interface ConnectionContext {
  socket: WebSocket;
  actorId: string;
  joinedBoardIds: Set<string>;
  alive: boolean;
  queuedBytes: number;
}
```

소켓이 닫히면 모든 방의 연결 목록에서도 제거합니다. 전체 연결 목록에는 없지만 방에는 남아 있거나, 그 반대인 상태가 생기지 않게 공통 참가·퇴장 함수를 사용합니다.

## 참가와 첫 상태

```text
연결 열림
→ client: board.join
→ server: 세션·멤버십 확인
→ server: board.snapshot
→ 이후 board.patch 수신
```

스냅샷을 받기 전에 패치를 적용하면 기준 상태가 없습니다. 스냅샷에는 해당 시점까지의 `sequence`를 포함하고 클라이언트는 그 다음 번호부터 적용합니다.

## 메시지 크기와 빈도

오래 유지되는 연결에서는 한 사용자가 큰 JSON이나 너무 많은 메시지를 보내 서버 자원을 계속 사용할 수 있습니다.

- 원시 메시지 최대 크기
- 초당 메시지 수
- 사용자·방별 연결 수
- 좌표와 문자열 길이
- 압축에 사용할 CPU와 메모리

`cursor.move`처럼 마지막 값만 중요한 메시지는 중간 값을 합치거나 버릴 수 있습니다.

## 느린 수신자와 송신 버퍼

소켓의 송신 버퍼가 계속 커지면 느린 클라이언트 하나가 서버 메모리를 점유합니다.

```text
버퍼가 작음        → 전송
일시적으로 큼      → 커서 같은 임시 메시지 생략
계속 큼            → 연결 종료 후 스냅샷으로 재동기화
```

확정된 패치를 조용히 버리지 않습니다. 연결을 닫고 재접속 뒤 최신 스냅샷을 보내는 편이 명확합니다.

## 하트비트

네트워크가 끊겨도 TCP 연결이 즉시 닫히지 않을 수 있습니다.

```text
주기 시작
→ 모든 연결 alive=false
→ ping 전송
→ pong 수신 시 alive=true
→ 다음 주기에도 false면 연결 종료
```

하트비트 타이머는 서버 종료와 테스트 종료 때 반드시 해제합니다.

## 오류 응답과 연결 종료

오래된 버전처럼 복구할 수 있는 실패는 메시지로 알릴 수 있습니다.

```ts
{
  type: "operation.rejected",
  operationId: "...",
  code: "stale_item",
  message: "최신 상태를 다시 불러와 주세요."
}
```

인증 만료, 반복되는 형식 위반, 메시지 크기 초과는 연결 종료 사유가 될 수 있습니다. 종료 코드와 다시 연결해도 되는지 문서화합니다.

## 서버 종료

1. 새 업그레이드 요청을 받지 않습니다.
2. 진행 중인 확정 작업을 제한된 시간 안에 마칩니다.
3. 필요하면 재연결 안내를 보냅니다.
4. 소켓을 닫습니다.
5. 방 목록과 하트비트 타이머를 정리합니다.
6. 데이터베이스와 HTTP 서버를 닫습니다.

전체 종료 시간을 제한하고 무한히 기다리지 않습니다.

## 재연결

네트워크 오류에는 상한이 있는 지수 백오프와 무작위 지연을 사용할 수 있습니다.

```text
0.5초 → 1초 → 2초 → 4초 → 최대 간격
```

인증 실패와 명시적인 접근 거부는 무한히 재시도하지 않습니다. 재연결 뒤 메모리에 남은 이전 상태를 그대로 사용하지 않고 다시 참가해 스냅샷을 받습니다.

## 흔한 실수

- 연결 성공과 방 참가 완료를 같은 상태로 봅니다.
- JSON 파싱 실패를 서버 전체 예외로 만듭니다.
- 소켓이 닫힌 뒤 방 목록에서 제거하지 않습니다.
- 메시지 크기·빈도와 송신 버퍼에 제한이 없습니다.
- 하트비트 타이머를 정리하지 않습니다.
- 재연결 뒤 이전 상태에 패치만 이어 붙입니다.
- 인증 실패도 계속 재연결합니다.

## 완료 기준

- 업그레이드, 연결, 방 참가를 구분합니다.
- 메시지를 실행 중에 검사합니다.
- 연결을 닫을 때 방 목록과 타이머를 함께 정리합니다.
- 메시지 제한, 하트비트와 느린 수신자 처리 방식을 설명합니다.
- 재연결 뒤 스냅샷으로 복구합니다.
