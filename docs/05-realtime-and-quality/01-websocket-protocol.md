# WebSocket 프로토콜

HTTP 요청은 일반적으로 하나의 요청에 하나의 응답을 돌려주고 끝나지만, WebSocket은 한 번 연결한 뒤 같은 연결에서 클라이언트와 서버가 여러 메시지를 양방향으로 주고받습니다. 따라서 **WebSocket 연결이 열려 있다는 사실**과 **애플리케이션 상태에 참가했다는 사실**을 구분해야 합니다.

예를 들어 소켓이 연결되어 있어도 다음 사실은 별도로 관리해야 합니다.

- 이 연결이 어느 사용자에게 속하는지
- 사용자가 어느 보드에 참가했는지
- 각 보드에서 어느 `sequence`까지 동기화했는지
- 현재도 해당 보드를 읽거나 수정할 권한이 있는지
- 마지막으로 연결이 정상임을 확인한 시각
- 연결 종료 시 제거해야 할 방 등록, 타이머와 송신 대기 데이터

WebSocket 서버는 단순히 소켓을 열어 두는 코드가 아니라 **연결 상태, 애플리케이션 참가 상태, 권한, 메시지 순서와 자원 제한을 함께 관리하는 프로토콜 구현**으로 보는 편이 정확합니다.

## 목표

- HTTP 업그레이드, WebSocket 연결과 방 참가를 서로 다른 상태로 구분합니다.
- 클라이언트와 서버 메시지를 실행 중에 검증합니다.
- 연결별 사용자와 참가한 방을 일관되게 관리합니다.
- 스냅샷과 이후 패치 사이에서 변경이 누락되지 않도록 순서를 관리합니다.
- 메시지 크기, 전송 빈도, 송신 버퍼와 하트비트를 제한합니다.
- 연결 종료와 재연결 뒤 상태를 안전하게 복구합니다.

## 연결 시작

브라우저는 먼저 HTTP 요청으로 WebSocket 프로토콜 전환을 요청합니다. 이를 **WebSocket handshake** 또는 **HTTP Upgrade**라고 합니다.

```text
GET /ws HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Origin: https://app.example.com
Cookie: app_session=...
```

실제 요청에는 `Sec-WebSocket-Key`, `Sec-WebSocket-Version` 같은 WebSocket handshake 헤더도 포함됩니다. 애플리케이션 코드는 보통 사용하는 WebSocket 라이브러리가 이 세부 절차를 처리하게 하고, 서버는 업그레이드를 허용할지 판단하는 데 집중합니다.

서버는 연결을 받아들이기 전에 다음을 확인할 수 있습니다.

- 요청의 `Origin`이 허용한 웹 애플리케이션 출처인지
- 세션이나 토큰이 유효하고 만료되지 않았는지
- 사용자 계정이 비활성화되거나 차단되지 않았는지
- 사용자별 최대 WebSocket 연결 수를 넘지 않았는지
- 서버가 종료 중이거나 과부하 상태가 아닌지

`Origin` 검사는 브라우저에서 예상하지 않은 다른 웹사이트가 사용자의 쿠키를 이용해 WebSocket을 여는 위험을 줄이는 데 사용합니다. 그러나 `Origin` 자체가 사용자 인증 수단은 아닙니다. 사용자의 신원은 세션 쿠키나 토큰 등 별도의 인증 정보로 확인해야 합니다.

인터넷을 통해 인증 정보나 사용자 데이터를 전송한다면 일반적으로 TLS가 적용된 `wss://` 연결을 사용합니다.

연결이 성공했다고 해서 사용자가 특정 보드의 구성원이라고 가정해서는 안 됩니다.

```text
HTTP Upgrade 성공
        ↓
WebSocket 연결됨
        ↓
아직 어떤 보드에도 참가하지 않음
        ↓
client: board.join
        ↓
server: 현재 멤버십 확인
        ↓
참가 성공 후에만 해당 보드 메시지 송수신
```

즉 다음 세 상태는 서로 다릅니다.

```text
업그레이드 허용
WebSocket 연결됨
특정 보드 참가 완료
```

## 메시지 스키마

네트워크에서 받은 데이터는 신뢰할 수 없는 입력입니다. TypeScript 타입은 컴파일 시점에만 존재하므로, 네트워크 메시지는 실행 중에 별도로 검사해야 합니다.

예를 들어 Zod를 사용하면 메시지의 `type`에 따라 필요한 필드를 구분할 수 있습니다.

```ts
const ClientMessageSchema = z.discriminatedUnion("type", [
  z.object({
    type: z.literal("board.join"),
    boardId: z.string().uuid()
  }),
  z.object({
    type: z.literal("cursor.move"),
    boardId: z.string().uuid(),
    x: z.number().finite(),
    y: z.number().finite()
  }),
  z.object({
    type: z.literal("item.move"),
    boardId: z.string().uuid(),
    itemId: z.string().uuid(),
    baseVersion: z.number().int().nonnegative(),
    x: z.number().finite(),
    y: z.number().finite(),
    final: z.boolean()
  })
]);
```

수신 처리는 최소한 다음 단계로 나누는 편이 좋습니다.

```text
WebSocket frame 수신
→ 허용한 메시지 종류인지 확인
→ 최대 크기 확인
→ 문자열을 JSON으로 파싱
→ 스키마 검사
→ 현재 연결 상태와 권한 검사
→ 실제 작업 실행
```

예를 들어 다음 두 실패는 종류가 다릅니다.

```text
{"type":                 ← JSON 문법 오류
{"type":"item.move"}     ← JSON은 맞지만 필수 필드 누락
```

첫 번째는 JSON 파싱 단계에서 실패하고, 두 번째는 스키마 검사 단계에서 실패합니다.

```ts
function parseClientMessage(raw: string) {
  let value: unknown;

  try {
    value = JSON.parse(raw);
  } catch {
    return { ok: false as const, code: "invalid_json" };
  }

  const result = ClientMessageSchema.safeParse(value);

  if (!result.success) {
    return { ok: false as const, code: "invalid_message" };
  }

  return {
    ok: true as const,
    message: result.data
  };
}
```

잘못된 메시지 하나가 다른 연결이나 서버 프로세스를 종료하게 해서는 안 됩니다. 개별 연결의 입력 오류를 해당 연결의 오류로 처리하고, 서버 전체의 예외 경계까지 전파되지 않게 합니다.

스키마 검사가 성공했다고 해서 요청이 허용된 것은 아닙니다. 예를 들어 다음 메시지는 형식상 유효하지만 사용자가 해당 보드에 참가하지 않았다면 거부해야 합니다.

```json
{
  "type": "item.move",
  "boardId": "0c57344e-2f72-4cf6-8e7d-ea94462e464d",
  "itemId": "3d650020-b68e-4b08-8aef-6f94a4ca5c0c",
  "baseVersion": 7,
  "x": 120,
  "y": 80,
  "final": true
}
```

따라서 검사는 보통 다음 세 층으로 생각할 수 있습니다.

```text
문법 검증       JSON인가?
구조 검증       필요한 필드와 타입이 맞는가?
상태·권한 검증  이 연결이 지금 이 작업을 해도 되는가?
```

## 식별자 구분

프로토콜이 커지면 서로 목적이 다른 여러 식별자가 생깁니다. 이름이 비슷해도 의미를 섞지 않는 것이 중요합니다.

- `messageId`: 한 번 전송한 메시지를 추적하기 위한 식별자
- `operationId`: 사용자의 한 논리적 변경 시도를 추적하기 위한 식별자
- `itemId`: 보드 안의 항목 같은 리소스의 식별자
- `sequence`: 서버가 확정한 **보드 전체 변경의 순서**
- `version`: 특정 항목의 현재 버전

예를 들어 서버가 다음 순서로 변경을 확정했다고 가정합니다.

```text
sequence=40  item A version 3
sequence=41  item B version 8
sequence=42  item A version 4
```

`sequence`는 보드 전체에서 변경이 적용된 순서를 나타내고, `version`은 한 항목이 몇 번째 상태인지 나타냅니다. 따라서 둘은 같은 값일 필요가 없습니다.

`operationId`는 네트워크 재시도와 특히 관련이 있습니다. 클라이언트가 작업을 전송한 뒤 응답을 받기 전에 연결이 끊기면 다음 두 경우를 구분하기 어렵습니다.

```text
서버가 작업을 받지 못함
서버는 작업을 적용했지만 응답만 클라이언트에 도착하지 못함
```

동일한 `operationId`로 작업을 다시 보낼 수 있게 설계하고 서버가 이미 처리한 작업을 식별하면, 같은 사용자 작업을 두 번 적용하는 문제를 줄일 수 있습니다. 다만 모든 종류의 메시지에 이런 중복 제거가 필요한 것은 아닙니다.

모든 메시지에 모든 식별자를 넣을 필요는 없습니다. 중복 제거, 동기화, 복구와 추적에 실제로 필요한 값만 사용합니다.

## 연결별 상태

연결마다 애플리케이션 상태를 명시적으로 관리합니다.

```ts
interface ConnectionContext {
  socket: WebSocket;
  actorId: string;
  joinedBoardIds: Set<string>;
  alive: boolean;
  queuedBytes: number;
}
```

각 필드의 의미는 다음과 같습니다.

- `socket`: 실제 WebSocket 연결
- `actorId`: 인증된 사용자 또는 행위자의 식별자
- `joinedBoardIds`: 이 연결이 참가를 완료한 보드 목록
- `alive`: 하트비트에서 연결이 응답했는지 나타내는 상태
- `queuedBytes`: 아직 전송되지 못하고 대기 중인 데이터 크기

보통 서버에는 연결 기준 자료구조와 방 기준 자료구조가 함께 존재합니다.

```text
connections
  socket A → ConnectionContext
  socket B → ConnectionContext

boardMembers
  board 1 → { socket A, socket B }
  board 2 → { socket B }
```

문제는 한쪽만 수정했을 때 생깁니다.

```text
socket A는 이미 닫힘
하지만 board 1 목록에는 socket A가 남아 있음
```

이 상태가 남으면 존재하지 않는 소켓으로 계속 전송을 시도하거나 메모리가 해제되지 않을 수 있습니다. 따라서 참가와 퇴장을 여러 곳에서 직접 수정하기보다 공통 함수로 묶습니다.

```ts
function joinBoard(ctx: ConnectionContext, boardId: string) {
  ctx.joinedBoardIds.add(boardId);
  addSocketToBoard(boardId, ctx.socket);
}

function leaveBoard(ctx: ConnectionContext, boardId: string) {
  ctx.joinedBoardIds.delete(boardId);
  removeSocketFromBoard(boardId, ctx.socket);
}
```

실제 구현에서는 같은 참가나 퇴장 요청이 여러 번 호출되어도 상태가 깨지지 않도록 **멱등적으로** 처리하는 것이 안전합니다.

소켓이 닫히면 `joinedBoardIds`에 남은 모든 보드에서 반드시 제거합니다. 연결 종료 경로가 정상 종료, 오류, 하트비트 실패 등 여러 개라면 최종 정리 함수를 하나로 모으는 편이 좋습니다.

## 참가와 첫 상태

보드 참가의 기본 흐름은 다음과 같습니다.

```text
연결 열림
→ client: board.join
→ server: 현재 세션 확인
→ server: 현재 멤버십 확인
→ server: 방에 참가 등록
→ server: board.snapshot
→ 이후 board.patch 수신
```

여기서 **현재 세션과 멤버십**을 확인한다는 점이 중요합니다. WebSocket 연결을 열 때 권한이 있었더라도 연결이 오래 유지되는 동안 사용자가 보드에서 제거되거나 쓰기 권한이 바뀔 수 있습니다.

따라서 최소한 상태를 변경하는 작업에서는 현재 권한이 여전히 유효한지 확인해야 합니다.

```text
board.join        → 읽기 권한 확인
item.move         → 현재 쓰기 권한 확인
민감한 작업       → 필요한 세부 권한 추가 확인
```

권한 변경을 실시간으로 연결 상태에 반영하는 시스템이라면, 권한 철회 시 해당 방에서 즉시 퇴장시키는 방식도 사용할 수 있습니다.

### 스냅샷과 sequence

스냅샷은 보드의 특정 시점 전체 상태입니다.

```json
{
  "type": "board.snapshot",
  "boardId": "...",
  "sequence": 120,
  "items": []
}
```

여기서 `sequence: 120`은 다음 의미입니다.

```text
이 스냅샷에는 sequence 120까지의 확정 변경이 반영되어 있다.
```

따라서 클라이언트는 이후 `sequence=121`부터 패치를 적용해야 합니다.

```text
snapshot sequence=120
patch sequence=121
patch sequence=122
patch sequence=123
```

그런데 단순히 "스냅샷을 조회한 뒤 방에 등록"하거나 "방에 등록한 뒤 천천히 스냅샷을 조회"하면 그 사이에 발생한 패치를 잃거나 중복 적용할 수 있습니다.

예를 들어 다음 순서는 문제가 됩니다.

```text
1. 서버가 snapshot sequence=120을 조회
2. 다른 사용자의 변경으로 sequence=121 확정
3. 클라이언트를 방 전송 목록에 등록
4. snapshot 120 전송
```

이 경우 클라이언트는 `sequence=121` 패치를 받지 못할 수 있습니다.

따라서 참가 구현에는 **스냅샷과 실시간 패치 사이의 순서 경계**가 필요합니다. 구현 방법은 여러 가지가 있지만 핵심 조건은 같습니다.

```text
스냅샷의 sequence = S
클라이언트가 이후 받는 첫 패치 = S + 1 또는 그 이후
S 이후의 패치가 중간에서 사라지지 않음
```

예를 들어 서버가 참가 처리 중 발생한 패치를 잠시 버퍼링한 뒤 스냅샷 전송이 끝나면 `S+1`부터 순서대로 보내는 방식을 사용할 수 있습니다.

클라이언트도 패치 순서를 확인하는 편이 안전합니다.

```ts
if (patch.sequence !== lastSequence + 1) {
  requestResync();
  return;
}
```

예상한 다음 번호가 아니라면 중간 패치가 누락되었을 가능성이 있으므로, 계속 추측해서 적용하기보다 최신 스냅샷으로 재동기화합니다.

## 임시 이벤트와 확정 변경

모든 WebSocket 메시지가 같은 중요도를 가지지는 않습니다.

`cursor.move`는 다른 사용자의 현재 커서 위치를 보여 주기 위한 **임시 이벤트**입니다. 중간 좌표 몇 개가 사라져도 다음 좌표가 도착하면 화면을 정상적으로 갱신할 수 있습니다.

반면 `board.patch`는 보드의 확정 상태를 변경하는 메시지라면 누락되면 안 됩니다.

```text
cursor.move
10,10 → 11,10 → 12,10 → 13,10

중간 메시지 일부 누락
10,10 ───────────────→ 13,10
```

커서는 여전히 최신 위치를 표시할 수 있습니다.

그러나 다음과 같은 확정 변경은 다릅니다.

```text
sequence=41
sequence=42   ← 누락
sequence=43
```

`sequence=42`가 없는데 43을 적용하면 클라이언트 상태가 서버와 달라질 수 있습니다.

따라서 프로토콜을 설계할 때 메시지를 대략 다음처럼 구분하면 처리 정책을 정하기 쉽습니다.

```text
임시 상태
- 최신 값이 중요
- 중간 메시지를 합치거나 버릴 수 있음
- 예: cursor.move

확정 상태
- 순서와 누락 여부가 중요
- 조용히 버리면 안 됨
- 예: board.patch
```

## 메시지 크기와 빈도

오래 유지되는 연결에서는 한 사용자가 큰 메시지나 너무 많은 메시지를 계속 보내 서버 CPU와 메모리를 점유할 수 있습니다.

서버는 애플리케이션 특성에 맞게 다음 제한을 정해야 합니다.

- 한 메시지의 최대 원시 크기
- 단위 시간당 메시지 수
- 사용자별 최대 연결 수
- 방별 최대 참가 연결 수
- 문자열과 배열의 최대 길이
- 좌표 같은 숫자의 허용 범위
- 압축에 사용할 CPU와 메모리
- 한 연결이 보유할 수 있는 송신 대기 데이터

메시지 크기 제한은 가능하면 JSON 파싱이나 큰 객체 생성보다 먼저 적용합니다.

```text
수신
→ 크기 제한 확인
→ JSON 파싱
→ 스키마 검사
```

이미 지나치게 큰 데이터를 메모리에 올리고 파싱한 뒤에야 거부하면 자원 보호 효과가 줄어듭니다.

전송 빈도 제한도 메시지 종류에 따라 다를 수 있습니다. 예를 들어 `cursor.move`는 매우 자주 발생할 수 있지만 `board.join`이나 확정 쓰기 작업이 초당 수백 번 발생하는 것은 비정상일 가능성이 큽니다.

`cursor.move`처럼 마지막 값만 중요한 메시지는 서버가 중간 값을 합치거나 버릴 수 있습니다.

```text
수신: x=10
수신: x=11
수신: x=12

아직 이전 값을 보내지 못했다면
→ x=12만 남겨 전송
```

이런 방식을 **coalescing**이라고 부릅니다.

## 느린 수신자와 송신 버퍼

WebSocket의 `send()`를 호출했다고 해서 데이터가 즉시 상대방에게 도착한 것은 아닙니다. 운영체제와 런타임 내부의 송신 버퍼에 데이터가 대기할 수 있습니다.

클라이언트의 네트워크가 느리거나 읽기를 멈추면 서버가 메시지를 만드는 속도가 실제 전송 속도보다 빨라질 수 있습니다.

```text
서버 생성 속도 > 네트워크 전송 속도
              ↓
       송신 대기 데이터 증가
              ↓
          메모리 증가
```

이 현상을 제한하지 않으면 느린 클라이언트 하나가 서버 메모리를 장시간 점유할 수 있습니다. 이를 **backpressure 문제**라고 합니다.

정책은 메시지 중요도에 따라 다르게 둘 수 있습니다.

```text
버퍼가 작음
→ 정상 전송

버퍼가 일시적으로 큼
→ cursor.move 같은 임시 메시지 생략 또는 합치기

버퍼가 계속 임계값보다 큼
→ 느린 연결 종료
→ 재연결 뒤 최신 snapshot으로 복구
```

확정된 패치를 송신 버퍼가 크다는 이유로 조용히 버려서는 안 됩니다.

```text
보낸 것으로 간주
sequence=50
sequence=51  ← 실제로 버림
sequence=52
```

클라이언트는 변경 누락을 모른 채 잘못된 상태를 유지할 수 있습니다. 확정 메시지를 더 이상 신뢰성 있게 전달할 수 없다면 연결을 닫고 재동기화하는 편이 명확합니다.

## 하트비트

네트워크가 끊기거나 클라이언트가 비정상 종료되어도 서버가 즉시 연결 종료를 알지 못할 수 있습니다. TCP 연결 상태가 한동안 남아 있을 수 있기 때문입니다.

WebSocket 프로토콜에는 `ping`과 `pong` 제어 프레임이 있습니다. 서버용 WebSocket 라이브러리가 이를 지원한다면 연결 생존 여부 확인에 사용할 수 있습니다.

기본 흐름은 다음과 같습니다.

```text
주기 시작
→ 이전 주기에 응답하지 않은 연결 종료
→ 살아 있는 연결 alive=false
→ ping 전송
→ pong 수신 시 alive=true
→ 다음 주기에 다시 검사
```

예를 들어 개념적으로 다음과 같이 처리할 수 있습니다.

```ts
function heartbeat() {
  for (const ctx of connections) {
    if (!ctx.alive) {
      closeAndCleanup(ctx);
      continue;
    }

    ctx.alive = false;
    ctx.socket.ping();
  }
}

function onPong(ctx: ConnectionContext) {
  ctx.alive = true;
}
```

위 코드는 서버 라이브러리가 프로토콜 수준의 `ping()`을 제공한다고 가정한 개념 예시입니다. 브라우저의 표준 JavaScript `WebSocket` API는 애플리케이션 코드에 WebSocket `ping`/`pong` 프레임을 직접 노출하지 않습니다. 브라우저와 애플리케이션 수준에서 별도의 생존 확인이 필요하다면 일반 메시지로 `heartbeat`와 `heartbeat.ack` 같은 프로토콜을 정의할 수 있습니다.

하트비트 주기는 너무 짧으면 불필요한 트래픽이 늘고, 너무 길면 끊긴 연결을 늦게 발견합니다. 서비스의 연결 수, 네트워크 환경과 장애 감지 요구에 맞춰 정합니다.

하트비트용 interval이나 timeout은 연결 또는 서버 종료 때 반드시 해제해야 합니다. 테스트에서도 타이머가 남으면 테스트 프로세스가 끝나지 않는 원인이 될 수 있습니다.

## 오류 응답과 연결 종료

모든 오류가 WebSocket 연결 종료를 의미하지는 않습니다.

예를 들어 클라이언트가 오래된 항목 버전을 기준으로 수정하려 했다면 연결 자체는 정상이고, 해당 작업만 거부하면 됩니다.

```ts
{
  type: "operation.rejected",
  operationId: "...",
  code: "stale_item",
  message: "최신 상태를 다시 불러와 주세요."
}
```

이런 오류를 **복구 가능한 애플리케이션 오류**로 볼 수 있습니다.

반면 다음 상황은 연결 종료 사유가 될 수 있습니다.

- 인증 또는 세션이 더 이상 유효하지 않음
- 정책상 허용하지 않는 접근을 반복함
- 형식이 잘못된 메시지를 반복해서 보냄
- 최대 메시지 크기를 초과함
- 서버가 더 이상 해당 연결을 안전하게 처리할 수 없음
- 서버가 재시작 또는 종료 절차에 들어감

WebSocket close frame에는 종료 코드와 짧은 이유를 담을 수 있습니다. 애플리케이션은 어떤 종료가 재연결 가능한지 문서화하는 편이 좋습니다.

예를 들어 다음과 같이 정책을 정할 수 있습니다.

```text
정상 종료             → 자동 재연결하지 않음
일시적인 서버 재시작   → 지연 후 재연결 가능
메시지 크기 초과       → 같은 메시지를 그대로 재시도하지 않음
인증 실패              → 인증 갱신 전까지 재연결하지 않음
권한 거부              → 같은 자원에 무한 재시도하지 않음
```

표준 종료 코드를 사용할 때는 해당 코드의 의미와 라이브러리 동작을 확인해 일관되게 사용합니다. 애플리케이션 전용 종료 코드를 정의한다면 클라이언트와 서버가 같은 의미를 공유하도록 프로토콜 문서에 명시합니다.

## 연결 종료와 정리

WebSocket 연결은 여러 이유로 끝날 수 있습니다.

```text
클라이언트 정상 종료
네트워크 오류
하트비트 실패
프로토콜 위반
서버 정책에 의한 종료
서버 종료
```

종료 원인이 무엇이든 최종 정리 결과는 같아야 합니다.

```text
소켓 종료
→ 모든 참가 보드에서 제거
→ 전체 연결 목록에서 제거
→ 연결별 타이머 제거
→ 연결별 송신 대기 데이터 해제
→ 필요하면 presence 상태 갱신
```

여러 이벤트에서 같은 정리 함수를 호출할 수 있으므로 정리 함수도 여러 번 호출되어도 문제가 없도록 만드는 것이 안전합니다.

```ts
function cleanupConnection(ctx: ConnectionContext) {
  for (const boardId of [...ctx.joinedBoardIds]) {
    leaveBoard(ctx, boardId);
  }

  removeConnection(ctx);
  clearConnectionTimers(ctx);
}
```

## 서버 종료

서버 프로세스를 종료할 때 HTTP 서버만 닫고 WebSocket 연결을 그대로 두면 종료가 끝나지 않거나 진행 중인 작업이 중간에 끊길 수 있습니다.

일반적인 종료 순서는 다음과 같습니다.

1. 새 HTTP 업그레이드 요청을 더 이상 받지 않습니다.
2. 이미 받은 새 확정 작업을 제한된 시간 안에 처리합니다.
3. 필요하면 클라이언트에 서버 종료 또는 재연결 안내를 보냅니다.
4. 열린 WebSocket 연결을 닫습니다.
5. 방 목록, 연결 목록과 하트비트 타이머를 정리합니다.
6. 데이터베이스 같은 외부 자원을 닫습니다.
7. HTTP 서버를 완전히 종료합니다.

종료 절차에는 전체 제한 시간을 둡니다.

```text
정상 종료 요청
→ 정리 시도
→ 제한 시간 안에 완료
또는
→ 제한 시간을 넘기면 강제 종료
```

한 연결이 응답하지 않는다는 이유로 서버 프로세스가 무한히 종료되지 못하는 상태를 만들지 않습니다.

## 재연결

네트워크 오류는 일시적일 수 있으므로 재연결에는 보통 **상한이 있는 지수 백오프(exponential backoff)**와 **무작위 지연(jitter)**을 사용합니다.

```text
0.5초 → 1초 → 2초 → 4초 → ... → 최대 간격
```

모든 클라이언트가 정확히 같은 시점에 재연결하면 서버가 복구되는 순간 연결 요청이 한꺼번에 몰릴 수 있습니다. 각 대기 시간에 작은 무작위 지연을 추가하면 이런 동시 재시도를 분산할 수 있습니다.

재연결 가능 여부는 종료 원인에 따라 달라집니다.

```text
일시적 네트워크 오류
→ 재연결

서버 재시작
→ 백오프 후 재연결

인증 만료
→ 인증 갱신이 필요
→ 같은 자격 증명으로 무한 재시도하지 않음

명시적인 접근 거부
→ 같은 요청을 무한 재시도하지 않음
```

재연결에 성공해도 이전 연결의 참가 상태가 서버에 그대로 남아 있다고 가정해서는 안 됩니다. 새 WebSocket은 새로운 연결입니다.

```text
새 연결 성공
→ 인증 상태 확인
→ board.join 다시 전송
→ 서버가 현재 멤버십 다시 확인
→ 최신 snapshot 수신
→ snapshot의 sequence 이후 patch 적용
```

클라이언트 메모리에 이전 보드 상태가 남아 있더라도 그것만 믿고 새 패치를 이어 붙이면 안 됩니다. 연결이 끊긴 동안 어떤 변경이 발생했는지 알 수 없기 때문입니다.

### 재연결과 미확인 작업

재연결에서 한 가지 더 구분해야 할 것은 **서버 상태 복구**와 **클라이언트가 보낸 작업의 결과 확인**입니다.

예를 들어 다음 상황이 가능합니다.

```text
client → item.move(operationId=abc)
server → 작업 적용
연결 끊김
client ← 성공 응답은 받지 못함
```

클라이언트가 같은 작업을 새로운 `operationId`로 다시 보내면 서버에서 두 번 적용될 수 있습니다.

중복 실행이 문제가 되는 작업이라면 다음 중 하나가 필요합니다.

- 클라이언트가 같은 논리적 작업에 같은 `operationId`를 재사용
- 서버가 처리한 `operationId`를 일정 기간 기억해 중복 실행 방지
- 재연결 후 스냅샷이나 작업 상태 조회로 결과를 확인한 뒤 재시도

반면 `cursor.move`처럼 최신 값만 의미가 있는 임시 메시지는 끊긴 동안 보낸 값을 굳이 재전송할 필요가 없습니다.

## 상태 전이로 생각하기

WebSocket 코드는 이벤트 핸들러의 모음으로만 보면 상태 검사가 빠지기 쉽습니다. 연결 하나를 간단한 상태 전이로 생각하면 허용할 메시지가 더 분명해집니다.

```text
CONNECTING
    ↓
CONNECTED
    ↓ board.join 성공
JOINED(boardId)
    ↓ close/error/heartbeat failure
CLOSED
```

예를 들어 다음 규칙을 명시할 수 있습니다.

```text
CONNECTED
- board.join 허용
- item.move 거부

JOINED(board A)
- board A의 cursor.move 허용
- board A의 item.move는 현재 쓰기 권한 확인 후 허용
- 참가하지 않은 board B의 item.move 거부

CLOSED
- 어떤 메시지도 처리하지 않음
```

여러 보드에 동시에 참가할 수 있다면 연결 전체 상태 하나보다 `joinedBoardIds`를 이용해 각 보드 참가 여부를 검사합니다.

## 흔한 실수

- HTTP 업그레이드 성공, WebSocket 연결 성공과 방 참가 완료를 같은 상태로 봅니다.
- `Origin` 검사를 사용자 인증과 같은 것으로 취급합니다.
- TypeScript 타입만 믿고 네트워크 메시지의 실행 중 검증을 생략합니다.
- JSON 파싱 실패를 서버 전체 예외로 전파합니다.
- 스키마만 검사하고 현재 참가 상태와 권한은 검사하지 않습니다.
- 연결 때 확인한 권한이 연결이 닫힐 때까지 영원히 유효하다고 가정합니다.
- 스냅샷과 실시간 패치 사이의 `sequence` 경계를 만들지 않아 변경을 누락합니다.
- 패치의 `sequence`가 건너뛰었는데도 그대로 적용합니다.
- 소켓이 닫힌 뒤 방 목록에서 제거하지 않습니다.
- 참가 목록과 연결 목록을 서로 다른 코드 경로에서 따로 수정해 상태가 어긋납니다.
- 메시지 크기, 빈도와 송신 버퍼에 제한이 없습니다.
- 느린 수신자에게 확정 패치를 조용히 버립니다.
- 임시 메시지와 확정 메시지를 같은 전송 정책으로 처리합니다.
- 하트비트 타이머를 정리하지 않습니다.
- 브라우저 JavaScript에서도 프로토콜 수준의 `ping()`을 직접 호출할 수 있다고 가정합니다.
- 재연결 뒤 이전 상태에 패치만 이어 붙입니다.
- 응답을 받지 못한 작업을 새로운 작업으로 무조건 다시 보내 중복 적용합니다.
- 인증 실패나 권한 거부도 계속 자동 재연결합니다.
- 서버 종료 시 열린 WebSocket과 타이머를 정리하지 않습니다.

## 완료 기준

- HTTP 업그레이드, WebSocket 연결과 방 참가를 서로 다른 상태로 설명할 수 있습니다.
- 네트워크 메시지를 JSON 문법, 스키마, 현재 상태와 권한 순서로 검사합니다.
- `sequence`, `version`, `operationId`의 역할을 구분합니다.
- 스냅샷의 `sequence`와 이후 패치 사이에서 변경이 누락되지 않는 구조를 사용합니다.
- 연결을 닫을 때 방 목록, 연결 목록과 타이머를 함께 정리합니다.
- 임시 이벤트와 확정 변경에 서로 다른 송신 정책을 적용합니다.
- 메시지 크기, 빈도, 송신 버퍼와 하트비트에 상한 또는 정책이 있습니다.
- 느린 수신자 때문에 확정 패치를 잃게 하지 않습니다.
- 재연결 뒤 다시 참가하고 최신 스냅샷을 기준으로 상태를 복구합니다.
- 재연결 과정에서 미확인 작업을 중복 실행하지 않을 방법이 있습니다.
- 인증 실패와 접근 거부를 무한 재시도하지 않습니다.
