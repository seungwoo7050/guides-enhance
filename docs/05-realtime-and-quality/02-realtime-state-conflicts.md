# 실시간 상태와 충돌

두 사용자가 같은 항목을 거의 동시에 바꾸면 **메시지가 도착한 순서**와 **서버가 변경을 확정한 순서**가 같다고 가정할 수 없습니다. 네트워크 지연, 재전송, 재연결, 여러 서버 인스턴스의 병렬 처리 때문에 더 늦게 보낸 메시지가 먼저 도착할 수도 있고, 같은 메시지가 두 번 도착할 수도 있습니다.

따라서 실시간 협업에서는 다음을 분리해서 생각해야 합니다.

- 서버가 확정한 **영속 상태**
- 드래그·커서처럼 아직 저장하지 않은 **임시 상태**
- 선택·초안처럼 해당 브라우저에만 필요한 **화면 상태**
- 방 전체 변경 순서를 나타내는 `sequence`
- 개별 항목의 변경 충돌을 검사하는 `version`

핵심 원칙은 **서버의 확정 상태를 기준으로 삼고, 클라이언트는 서버가 부여한 순서와 버전을 이용해 누락·중복·오래된 쓰기를 감지하는 것**입니다.

## 목표

- 서버를 확정 상태의 기준으로 둡니다.
- 영속 상태, 임시 상태와 화면 상태를 구분합니다.
- 스냅샷, 패치, `sequence`와 항목 `version`의 역할을 구분합니다.
- 드래그 중 좌표와 최종 좌표를 서로 다른 수명과 신뢰도로 처리합니다.
- 중복·누락·순서 역전과 오래된 쓰기에서 복구합니다.
- 낙관적 변경이 실패했을 때 사용자 입력을 보존합니다.
- 여러 동시 쓰기에서도 확정 순서와 항목 버전이 원자적으로 결정되게 합니다.

## 세 종류의 상태

실시간 애플리케이션에서 모든 값을 같은 저장소와 같은 규칙으로 처리하면 불필요한 저장, 충돌과 복구 문제가 생깁니다.

```text
영속 상태 → 항목 내용·최종 좌표·항목 버전, 데이터베이스 저장
임시 상태 → 커서·드래그 중 좌표·presence, 서버 메모리 또는 짧은 수명 저장소
화면 상태 → 선택·호버·대화 상자·입력 초안, 브라우저 로컬 상태
```

각 상태의 수명은 다릅니다.

### 영속 상태

영속 상태는 서버가 **확정한 애플리케이션 상태**입니다.

예:

```text
항목 제목
항목 내용
최종 x, y 좌표
삭제 여부
현재 item version
```

서버 재시작이나 사용자의 재연결 뒤에도 유지되어야 하므로 데이터베이스 같은 영속 저장소에 기록합니다.

### 임시 상태

임시 상태는 짧은 시간 동안만 의미가 있고, 유실되더라도 다음 상태나 최신 스냅샷으로 복구할 수 있는 값입니다.

예:

```text
다른 사용자의 커서 위치
드래그 중인 중간 좌표
현재 접속 중이라는 presence
```

모든 `pointermove`를 데이터베이스에 쓰면 저장 횟수, 잠금 경쟁, 이벤트 수와 감사 기록이 지나치게 많아집니다. 따라서 이런 값은 메모리에서 전달하거나 전송 빈도를 낮춰 처리할 수 있습니다.

### 화면 상태

화면 상태는 서버의 공유 상태가 아니라 특정 브라우저 UI에만 필요한 값입니다.

예:

```text
현재 선택된 항목
hover 상태
열린 대화 상자
아직 제출하지 않은 입력 초안
드래그 시작 전의 로컬 좌표
```

화면 상태까지 서버에서 공유하려고 하면 불필요한 동기화가 발생합니다.

반대로 **최종 좌표처럼 서버 재시작 뒤에도 유지되어야 하는 값**을 임시 상태로만 두면 확정된 사용자 작업이 사라집니다.

## 서버를 확정 상태의 기준으로 둡니다

클라이언트는 사용자 경험을 위해 서버 응답 전에 화면을 먼저 바꿀 수 있습니다. 그러나 그 변경은 아직 확정된 것이 아닙니다.

```text
사용자 입력
→ 클라이언트가 낙관적으로 화면 변경
→ 서버에 작업 전송
→ 서버가 현재 상태와 권한 검사
→ 서버가 변경 확정 또는 거부
→ 클라이언트가 확정 결과에 맞게 정리
```

따라서 다음 둘을 구분해야 합니다.

```text
화면에 보임 ≠ 서버에서 확정됨
```

서버가 작업을 거부하면 클라이언트는 자신의 낙관적 변경을 수정하거나 되돌릴 수 있어야 합니다.

## 스냅샷과 패치

**스냅샷(snapshot)**은 특정 시점에 서버가 확정한 방 전체 상태입니다.

```ts
interface BoardSnapshot {
  boardId: string;
  sequence: number;
  items: BoardItem[];
}
```

여기서 `sequence`는 다음 의미입니다.

```text
이 스냅샷에는 sequence 값까지의 모든 확정 변경이 반영되어 있다.
```

예를 들어:

```text
snapshot.sequence = 120
```

이면 클라이언트는 이후 `sequence=121`부터의 패치를 적용해야 합니다.

개별 `BoardItem`은 자신의 현재 `version`을 가질 수 있습니다.

```ts
interface BoardItem {
  id: string;
  x: number;
  y: number;
  version: number;
}
```

**패치(patch)**는 스냅샷 이후 서버가 확정한 하나의 변경입니다.

```ts
interface BoardPatch {
  boardId: string;
  sequence: number;
  operationId: string;
  actorId: string;
  operation: ItemCreated | ItemUpdated | ItemMoved | ItemDeleted;
}
```

패치가 특정 항목을 변경한다면, 그 결과 항목의 새 `version`도 함께 보내는 편이 좋습니다.

예:

```ts
interface ItemMoved {
  type: "item.moved";
  itemId: string;
  x: number;
  y: number;
  version: number;
}
```

이렇게 하면 클라이언트는 패치를 적용한 뒤 해당 항목의 최신 버전을 알 수 있습니다.

## `sequence`와 `version`은 서로 다른 문제를 해결합니다

두 값은 모두 숫자지만 의미가 다릅니다.

### `sequence`

`sequence`는 **방 전체의 확정 변경 순서**입니다.

```text
sequence=40  item A version 3
sequence=41  item B version 8
sequence=42  item A version 4
```

여기서 `sequence`는 모든 항목을 합친 방 전체의 변경 순서입니다.

### `version`

`version`은 **한 항목의 현재 버전**입니다.

```text
item A version 3
item A version 4
item A version 5
```

다른 항목의 변경은 item A의 `version`을 증가시키지 않습니다.

정리하면:

```text
sequence → 방 전체 패치의 누락·중복·순서 확인
version  → 한 항목을 오래된 상태를 기준으로 수정하는지 확인
```

둘을 같은 숫자로 사용하면 여러 항목이 동시에 바뀌는 순간 의미가 섞입니다.

## 시퀀스로 누락과 중복 확인

클라이언트는 마지막으로 적용한 `sequence`를 기억합니다.

```text
lastSequence = 120
```

새 패치를 받았을 때 다음 규칙으로 처리할 수 있습니다.

```text
sequence <= lastSequence
→ 이미 적용한 패치이거나 오래된 패치
→ 일반적으로 다시 적용하지 않음

sequence == lastSequence + 1
→ 바로 다음 확정 변경
→ 정상 적용

sequence > lastSequence + 1
→ 중간 sequence 누락
→ 이후 패치 적용 중단
→ 재동기화 요청
```

예:

```text
lastSequence = 41
수신 sequence = 42  → 적용
수신 sequence = 43  → 적용
수신 sequence = 43  → 중복, 무시
수신 sequence = 46  → 44, 45 누락, 재동기화
```

`sequence`는 **네트워크 도착 순서**가 아니라 **서버가 확정한 변경 순서**입니다.

클라이언트가 `sequence=46`을 먼저 받았다고 해서 그것을 먼저 적용해서는 안 됩니다.

## 서버에서 `sequence`를 어떻게 만들 것인가

`sequence`가 방 전체 순서를 의미하려면 같은 방에서 동시에 여러 작업이 처리되어도 한 순서가 결정되어야 합니다.

개념적으로는 다음 조건이 필요합니다.

```text
같은 board의 확정 변경
→ 중복되지 않는 sequence 할당
→ 데이터 변경과 sequence 기록을 같은 확정 경계에서 처리
```

예를 들어 데이터베이스 트랜잭션 안에서 다음을 함께 처리할 수 있습니다.

```text
1. 항목의 현재 version 확인
2. 조건이 맞으면 항목 갱신
3. board sequence 증가
4. 해당 sequence로 이벤트 또는 패치 기록
5. commit
```

중요한 점은 **데이터 변경은 실패했는데 sequence만 증가했다거나, 데이터는 저장됐는데 패치 순서는 기록되지 않은 상태**를 만들지 않는 것입니다.

여러 서버 인스턴스가 같은 보드를 처리한다면 각 프로세스의 메모리 카운터를 독립적으로 사용해서는 안 됩니다. 같은 방의 확정 순서를 직렬화할 수 있는 데이터베이스 행, 원자적 카운터, 이벤트 로그 같은 공통 기준이 필요합니다.

## 버전으로 오래된 쓰기 확인

사용자가 item A의 `version=4` 상태를 보고 수정했다고 가정합니다.

클라이언트는 작업에 기준 버전을 함께 보냅니다.

```json
{
  "type": "item.move",
  "itemId": "...",
  "baseVersion": 4,
  "x": 200,
  "y": 120
}
```

서버는 "현재 버전이 아직 4일 때만 수정"하는 조건부 업데이트를 수행할 수 있습니다.

```sql
update board_items
set x = $1,
    y = $2,
    version = version + 1
where id = $3
  and version = $4
returning *;
```

`$4`가 `baseVersion`입니다.

### 성공

현재 버전이 실제로 4라면:

```text
version 4
→ UPDATE 성공
→ version 5
```

### 실패

다른 사용자가 먼저 수정해서 현재 버전이 이미 5라면:

```text
client baseVersion = 4
server currentVersion = 5
→ 조건 불일치
→ UPDATE된 행 없음
```

이 경우 "나중에 도착한 값"이라는 이유만으로 기존 값을 덮어쓰지 않습니다.

서버는 충돌을 명시적으로 반환할 수 있습니다.

```json
{
  "type": "operation.rejected",
  "operationId": "...",
  "code": "stale_item",
  "item": {
    "id": "...",
    "version": 5,
    "x": 180,
    "y": 100
  }
}
```

이 방식은 흔히 **optimistic concurrency control** 또는 **compare-and-swap에 가까운 조건부 갱신**으로 볼 수 있습니다.

## 읽고 검사한 뒤 따로 쓰면 안 됩니다

다음 구현은 경쟁 조건이 생길 수 있습니다.

```text
1. SELECT version
2. 애플리케이션에서 version 비교
3. UPDATE
```

두 요청이 동시에 같은 `version=4`를 읽으면 둘 다 "수정 가능"하다고 판단할 수 있기 때문입니다.

```text
request A → version 4 읽음
request B → version 4 읽음
request A → 수정
request B → 수정
```

따라서 버전 검사는 가능하면 UPDATE 조건 자체에 넣어 데이터베이스가 원자적으로 판단하게 합니다.

```sql
where id = $3
  and version = $4
```

반환 행 수가 `0`인지 `1`인지로 성공 여부를 판단할 수 있습니다.

## 확정 패치는 데이터베이스 확정 뒤 전송합니다

실시간 서버에서는 다음 순서가 중요합니다.

잘못된 순서:

```text
1. board.patch 전송
2. 데이터베이스 UPDATE
3. UPDATE 실패
```

이 경우 클라이언트는 실제로 저장되지 않은 상태를 확정 상태로 받아버립니다.

대신 다음처럼 처리하는 편이 안전합니다.

```text
1. 조건부 UPDATE
2. sequence와 이벤트 기록
3. transaction commit
4. commit 성공 후 board.patch 전송
```

즉 **외부에 확정 패치를 알리는 시점은 서버가 해당 변경을 확정한 뒤**여야 합니다.

전송 직후 서버가 죽어 일부 클라이언트만 패치를 받는 문제는 재연결 시 `sequence`와 스냅샷으로 복구합니다.

## 드래그 중과 완료

드래그는 같은 좌표 변경처럼 보여도 중간 값과 최종 값의 성격이 다릅니다.

```text
pointermove
→ 브라우저가 전송 빈도 제한
→ item.move(final=false)
→ 서버가 좌표 범위와 참가 상태 확인
→ 방에 임시 좌표 전송

pointerup
→ item.move(final=true, baseVersion)
→ 현재 권한 확인
→ 조건부 UPDATE
→ sequence·이벤트 기록
→ commit
→ 확정 patch 전송
```

### 드래그 중 좌표

`final=false`인 중간 좌표는 다른 사용자가 움직임을 보게 하기 위한 **미리보기**입니다.

이 값은 보통:

- 항목 `version`을 증가시키지 않음
- 데이터베이스에 저장하지 않음
- 방 전체 `sequence`를 증가시키지 않음
- 일부 메시지가 누락되어도 허용 가능

예:

```text
x=10
x=12
x=15
x=18
```

중간 `x=12`, `x=15`가 누락되어도 최신 미리보기 `x=18`을 받으면 충분할 수 있습니다.

### 최종 좌표

`final=true`인 좌표는 영속 상태를 변경하려는 요청입니다.

따라서:

- `baseVersion` 확인
- 데이터베이스 저장
- 항목 `version` 증가
- 방 `sequence` 증가
- 확정 패치 전송

이 필요합니다.

드래그 중 연결이 끊기면 임시 값을 확정 상태로 간주하지 않습니다. 임시 미리보기를 제거하고 마지막 서버 확정 좌표를 유지합니다.

## 임시 상태와 확정 상태를 화면에서도 분리합니다

클라이언트는 한 항목에 대해 다음 값을 동시에 가질 수 있습니다.

```text
confirmedPosition  → 마지막 서버 확정 좌표
previewPosition    → 현재 드래그 중 보이는 좌표
```

화면에 표시할 값은 다음처럼 선택할 수 있습니다.

```ts
const visiblePosition =
  previewPosition ?? confirmedPosition;
```

확정 패치를 받으면:

```text
confirmedPosition 갱신
previewPosition 제거
```

드래그가 취소되거나 연결이 끊기면:

```text
previewPosition 제거
confirmedPosition 유지
```

이렇게 하면 임시 값을 영속 상태로 실수로 승격시키는 문제를 줄일 수 있습니다.

## 낙관적 화면 변경

서버 응답 전에 화면을 먼저 바꾼다면 어떤 작업이 아직 확정되지 않았는지 기록해야 합니다.

```ts
interface PendingOperation {
  operationId: string;
  itemId: string;
  baseVersion: number;
  optimisticValue: unknown;
  previousValue: unknown;
}
```

예를 들어 사용자가 제목을 `"A"`에서 `"B"`로 바꿨다고 가정합니다.

```text
server confirmed = "A"
user input       = "B"
```

클라이언트는 즉시 `"B"`를 화면에 보여 줄 수 있지만, 아직 서버 확정 값은 `"A"`입니다.

```text
confirmedValue  = "A"
optimisticValue = "B"
pending         = true
```

### 같은 `operationId`의 확정 패치가 도착

```text
operationId 일치
→ 서버가 작업을 확정한 것
→ confirmedValue를 서버 값으로 갱신
→ pending 제거
```

### 작업이 거부됨

예를 들어 `stale_item`이 오면:

```text
pending 작업 거부
→ 서버 최신 값 반영
→ 사용자의 입력은 별도로 보존
→ 재적용 또는 충돌 해결 UI 제공
```

여기서 중요한 것은 **서버 최신 값으로 화면을 되돌리는 것**과 **사용자 입력을 폐기하는 것**이 같은 일이 아니라는 점입니다.

## 사용자 초안을 보존합니다

텍스트 편집처럼 사용자의 입력 자체가 중요한 경우 서버 충돌이 났다고 초안을 버리면 안 됩니다.

예:

```text
서버 최신 제목: "프로젝트 계획"
사용자 초안:    "프로젝트 계획 v2 - 검토 필요"
```

다른 사용자의 변경 때문에 현재 쓰기가 거부되어도 다음처럼 둘을 따로 보관할 수 있습니다.

```text
serverValue = 최신 서버 값
draftValue  = 사용자가 입력한 값
```

그 다음 UI에서 다음 행동을 제공할 수 있습니다.

```text
최신 값 다시 불러오기
내 초안 다시 적용
수동으로 병합
```

단순 좌표 이동은 최신 서버 좌표로 되돌리기만 해도 충분할 수 있지만, 긴 텍스트나 폼 입력은 사용자 초안 보존이 더 중요합니다.

## 같은 항목에 여러 낙관적 작업이 있을 때

한 항목에 여러 작업을 연속해서 낙관적으로 적용하면 단순히 `previousValue` 하나만 저장하는 것으로 충분하지 않을 수 있습니다.

예:

```text
confirmed = A

op1: A → B
op2: B → C
```

이때 op1이 실패했다고 무조건 `A`로 되돌리면 op2의 사용자 입력까지 사라질 수 있습니다.

따라서 복잡한 UI에서는 다음 중 하나가 필요할 수 있습니다.

- 항목별 pending operation queue
- 서버 확정 상태 위에 pending 작업을 순서대로 다시 적용
- 새 스냅샷을 받은 뒤 아직 유효한 로컬 작업을 재계산

개념적으로:

```text
visibleState =
  serverConfirmedState
  + pending operation 1
  + pending operation 2
  + ...
```

서버 상태가 바뀌면 그 위에 아직 유효한 로컬 작업을 다시 적용합니다.

## 중복 작업

네트워크 재시도와 재연결 때문에 같은 `operationId`가 서버에 다시 도착할 수 있습니다.

예를 들어:

```text
client → operationId=abc
server → 작업 적용
server → 응답 전송
네트워크 끊김
client → 결과를 받지 못함
client → operationId=abc 재전송
```

서버가 중복을 구분하지 않으면 같은 작업을 두 번 적용할 수 있습니다.

정책은 다음처럼 정할 수 있습니다.

```text
처음 받은 operationId
→ 처리
→ 결과 또는 처리 사실 기록

같은 operationId + 같은 내용
→ 새로 실행하지 않음
→ 이전 결과 재사용 또는 이미 처리됨 응답

같은 operationId + 다른 내용
→ 동일 식별자를 서로 다른 작업에 사용한 것
→ 프로토콜 위반 또는 충돌
```

예를 들어 서버는 중복 효과가 위험한 작업에 대해 다음 정보를 일정 기간 저장할 수 있습니다.

```text
actorId
operationId
request fingerprint
result
createdAt
```

`operationId`만 전역으로 비교하기보다 사용자 또는 작업 범위를 함께 두면 서로 다른 사용자가 우연히 같은 ID를 만든 경우도 구분하기 쉽습니다.

커서 이동 같은 임시 이벤트는 중복되어도 결과가 거의 같으므로 영구적인 중복 제거 기록이 필요하지 않습니다.

## 패치 중복과 작업 중복은 다릅니다

두 종류의 중복을 구분해야 합니다.

### 패치 중복

같은 서버 패치를 클라이언트가 두 번 받음:

```text
sequence=120
sequence=120
```

클라이언트의 `lastSequence`로 감지할 수 있습니다.

### 작업 중복

같은 사용자 작업을 서버가 두 번 받음:

```text
operationId=abc
operationId=abc
```

서버의 작업 중복 제거 정책으로 처리합니다.

정리하면:

```text
sequence    → 서버 → 클라이언트 패치 중복·누락 관리
operationId → 클라이언트 → 서버 작업 중복 실행 관리
```

## 순서 역전

네트워크에서는 먼저 보낸 메시지가 항상 먼저 도착한다고 가정할 수 없습니다.

예:

```text
server 확정:
sequence=101
sequence=102

client 도착:
102
101
```

클라이언트가 102를 즉시 적용하면 101을 건너뛰게 됩니다.

간단한 시스템에서는 다음 정책이 가장 명확합니다.

```text
예상 sequence가 아니면
→ 이후 패치 적용 중단
→ 최신 snapshot 요청
```

더 복잡한 시스템에서는 짧은 시간 동안 패치를 버퍼링하고 빠진 번호가 도착하는지 기다릴 수도 있지만, 버퍼 크기와 대기 시간 제한이 필요합니다.

## 재연결 복구

클라이언트가 오프라인인 동안 서버 상태가 바뀔 수 있습니다.

예:

```text
클라이언트 마지막 sequence = 120
오프라인 중 서버 확정 = 121, 122, 123
```

재연결 뒤 두 가지 복구 방식을 사용할 수 있습니다.

### 방식 1: 누락 패치 재전송

클라이언트가 마지막 `sequence`를 서버에 알립니다.

```text
client: lastSequence=120
server: 121, 122, 123 재전송
```

장점:

- 스냅샷 전체보다 데이터가 작을 수 있음

필요 조건:

- 서버가 일정 기간 패치를 보관해야 함
- 요청한 `sequence` 이후 패치가 모두 남아 있어야 함

### 방식 2: 최신 스냅샷 전송

```text
client reconnect
→ board.join
→ 최신 snapshot sequence=123
→ 이후 124부터 patch 적용
```

작은 시스템에서는 이 방식이 단순하고 안정적입니다.

### 혼합 방식

실제 시스템에서는 다음처럼 선택할 수도 있습니다.

```text
누락 패치가 적고 모두 보관 중
→ patch replay

너무 오래 끊겼거나 기록이 없음
→ full snapshot
```

즉 데이터 크기가 커질수록 다음을 함께 고려해야 합니다.

- 스냅샷 크기
- 패치 보관 기간
- 패치 수
- 재생 비용
- 복구 구현 복잡도

## 스냅샷과 실시간 패치 사이의 경계

재동기화할 때도 스냅샷과 이후 패치 사이의 변경이 빠지면 안 됩니다.

예를 들어:

```text
1. snapshot sequence=200 생성
2. sequence=201 확정
3. client를 실시간 구독에 등록
```

이면 201을 놓칠 수 있습니다.

반대로:

```text
1. client를 구독에 먼저 등록
2. sequence=201 패치 수신
3. snapshot sequence=200 수신
```

처럼 되면 클라이언트가 스냅샷과 패치를 잘못된 순서로 적용할 수 있습니다.

따라서 서버는 재동기화 시 다음 조건을 보장해야 합니다.

```text
snapshot sequence = S
S 이후 확정 패치가 누락되지 않음
클라이언트는 S 다음 sequence부터 적용
```

방법은 여러 가지입니다.

예:

- 참가 중 발생한 패치를 잠시 버퍼링
- 이벤트 로그의 sequence를 기준으로 스냅샷 이후 패치 재전송
- 데이터베이스 트랜잭션과 구독 경계를 함께 설계

중요한 것은 특정 구현 방식보다 **누락 없는 경계**를 갖는 것입니다.

## 삭제 뒤 늦은 메시지

항목 삭제 뒤 오래된 수정 메시지가 도착할 수 있습니다.

예:

```text
item A version=5
→ 다른 사용자 삭제
→ 늦게 도착한 move(baseVersion=5)
```

서버가 수정 요청만 보고 항목을 다시 만들면 삭제된 데이터가 부활할 수 있습니다.

따라서 쓰기 전에 최소한 다음을 확인합니다.

```text
항목이 현재 존재하는가?
현재 version이 baseVersion과 같은가?
현재 사용자에게 쓰기 권한이 있는가?
```

삭제를 soft delete로 표현한다면 삭제 상태 자체도 버전 변화로 취급할 수 있습니다.

예:

```text
version 5: 존재
version 6: deleted
```

이후 `baseVersion=5`인 수정은 충돌로 거부됩니다.

이벤트 재생이나 오프라인 복구가 필요하면 삭제 이벤트 또는 tombstone을 일정 기간 보관해야 할 수 있습니다. 그렇지 않으면 과거 패치만 본 클라이언트가 "항목이 왜 사라졌는지" 설명할 수 없게 됩니다.

## 타임스탬프는 전체 순서가 아닙니다

클라이언트의 `Date.now()`나 여러 서버의 시스템 시계만으로 방 전체 변경 순서를 정해서는 안 됩니다.

다음 문제가 있기 때문입니다.

```text
사용자 A의 기기 시계가 30초 빠름
사용자 B의 기기 시계가 15초 느림
서버 1과 서버 2의 시계도 완전히 같지 않을 수 있음
네트워크 지연으로 도착 순서도 달라짐
```

따라서:

```text
timestamp → 표시, 감사, 로그 분석
sequence  → 방 전체 확정 순서
version   → 한 항목의 동시 수정 검사
```

처럼 역할을 나눕니다.

타임스탬프는 "언제쯤 일어났는가"를 나타내는 데 유용하지만, "무엇이 먼저 확정되었는가"의 유일한 기준으로 사용하지 않습니다.

## 연결 중 권한 변경

사용자가 연결된 동안 역할이 바뀔 수 있습니다.

예:

```text
editor
→ viewer
```

연결 시작 때 `editor`였다는 사실만 믿고 이후 모든 쓰기를 허용하면 권한 철회 뒤에도 계속 수정할 수 있습니다.

따라서 일반적으로 다음이 필요합니다.

- 새 역할을 데이터베이스에 저장합니다.
- 연결된 클라이언트에 역할 변경 또는 새 스냅샷을 알립니다.
- 이후 쓰기마다 현재 쓰기 권한이 유효한지 확인합니다.
- 필요하면 해당 연결의 방 참가 상태를 갱신합니다.
- 이미 화면에 적용한 임시 또는 낙관적 변경은 되돌립니다.

예:

```text
사용자 드래그 중
→ 권한이 viewer로 변경
→ final=true 작업 거부
→ 서버 확정 좌표로 복구
```

권한 검사는 상태 충돌 검사와 별개입니다.

```text
baseVersion이 최신
하지만 권한 없음
→ 거부

권한 있음
하지만 baseVersion이 오래됨
→ 충돌
```

둘을 구분해서 오류 코드를 반환하는 편이 클라이언트 복구에 유리합니다.

## 충돌 정책은 작업 종류에 따라 다를 수 있습니다

모든 충돌을 같은 방식으로 처리할 필요는 없습니다.

예를 들어 좌표 이동은 보통:

```text
오래된 baseVersion
→ 최신 서버 좌표 반환
→ 사용자가 다시 드래그
```

정도로 처리할 수 있습니다.

반면 긴 텍스트 편집은 단순히 최신 값으로 덮어쓰면 사용자의 작업을 잃을 수 있습니다.

가능한 정책:

```text
좌표 이동
→ stale write 거부 + 다시 시도

짧은 속성 변경
→ 서버 최신 값 표시 + 사용자가 선택

긴 텍스트
→ 초안 보존 + 수동 병합 또는 별도 병합 전략
```

핵심은 "충돌이 발생했다"는 사실과 "어떻게 해결할 것인가"를 분리하는 것입니다.

`version`은 충돌을 **감지**하는 도구이고, 실제 충돌 **해결 정책**은 도메인에 따라 달라집니다.

## 서버 처리 흐름 예시

확정되는 `item.move` 작업을 한 번에 정리하면 다음과 같습니다.

```text
client
  item.move(
    operationId,
    itemId,
    baseVersion,
    final=true,
    x,
    y
  )
        ↓
server
  메시지 스키마 검사
        ↓
  현재 참가 상태 확인
        ↓
  현재 쓰기 권한 확인
        ↓
  operationId 중복 여부 확인
        ↓
  transaction 시작
        ↓
  version 조건부 UPDATE
        ↓
  실패
    → stale_item
    → rollback
        ↓
  성공
    → item version 증가
    → board sequence 증가
    → event/patch 기록
    → commit
        ↓
  확정 patch 전송
        ↓
client
  sequence 확인
        ↓
  patch 적용
        ↓
  같은 operationId pending 제거
```

이 흐름에서 각각의 식별자는 다른 문제를 해결합니다.

```text
operationId → 같은 사용자 작업을 두 번 실행하지 않음
version     → 오래된 항목 상태를 기준으로 덮어쓰지 않음
sequence    → 클라이언트가 확정 패치를 빠짐없이 순서대로 적용
```

## 흔한 실수

- 클라이언트 화면 값을 최종 기준으로 사용합니다.
- 영속 상태, 임시 상태와 화면 상태를 구분하지 않습니다.
- 스냅샷의 `sequence`와 항목 `version`을 같은 의미로 사용합니다.
- 방 전체 `sequence`와 항목별 `version`을 같은 숫자로 증가시킵니다.
- `SELECT`로 버전을 읽은 뒤 애플리케이션 코드에서만 비교하고 무조건 `UPDATE`합니다.
- 데이터베이스 commit 전에 확정 패치를 전송합니다.
- 여러 서버가 각자 독립적인 메모리 sequence를 사용합니다.
- 드래그 중 모든 좌표를 데이터베이스에 저장합니다.
- 임시 드래그 좌표가 항목 `version`과 방 `sequence`를 증가시킵니다.
- 패치가 누락되었는데 이후 패치를 계속 적용합니다.
- 패치가 순서 역전되어 도착했는데 도착 순서대로 적용합니다.
- 오래된 쓰기를 마지막 도착 값이라는 이유로 덮어씁니다.
- 낙관적 변경 하나가 실패했을 때 이후 사용자 입력까지 함께 되돌립니다.
- 충돌 뒤 사용자 초안을 버립니다.
- `operationId` 중복과 `sequence` 중복을 같은 문제로 취급합니다.
- 삭제된 항목에 늦게 도착한 수정으로 항목이 다시 생성됩니다.
- 타임스탬프로 전체 변경 순서를 정합니다.
- 연결 시작 때 읽은 권한을 연결이 끝날 때까지 고정합니다.
- 재연결 시 스냅샷과 실시간 패치 사이에서 변경이 누락됩니다.

## 완료 기준

- 영속·임시·화면 상태의 의미와 저장 위치를 구분합니다.
- 스냅샷, 패치, `sequence`, 항목 `version`과 `operationId`의 역할을 설명합니다.
- `sequence`로 패치 누락·중복·순서 역전을 감지합니다.
- `version`을 조건부 UPDATE에 사용해 오래된 쓰기를 원자적으로 거부합니다.
- 데이터 변경, sequence 할당과 이벤트 기록을 일관된 확정 경계에서 처리합니다.
- 확정 패치는 데이터베이스 commit 뒤에 전송합니다.
- 드래그 미리보기와 최종 저장을 나눕니다.
- 임시 이동은 영속 `version`과 `sequence`를 불필요하게 증가시키지 않습니다.
- 낙관적 변경의 승인·거부·되돌리기를 구현합니다.
- 충돌 뒤 사용자 초안을 보존할 수 있습니다.
- 중복 `operationId`가 같은 작업을 두 번 적용하지 않게 합니다.
- 삭제 뒤 늦은 수정으로 항목이 다시 생기지 않게 합니다.
- 재연결 뒤 누락 없는 스냅샷 또는 패치 복구 경계를 갖습니다.
- 연결 중 권한 변경 이후의 쓰기를 올바르게 거부합니다.
