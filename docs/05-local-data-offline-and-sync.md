# 로컬 데이터, 오프라인과 동기화

오프라인 지원은 최근 응답을 캐시하는 기능이 아닙니다. 사용자가 연결 없이 만든 변경을 기기에 저장하고, 프로세스 중단·중복 전송·순서 역전·버전 충돌 뒤에도 로컬과 서버 상태를 설명 가능한 방식으로 맞추는 작업입니다.

Field Notes는 화면에서 SQLite를 읽고, 사용자가 저장을 선택하면 `Record` 변경과 outbox 명령을 함께 저장합니다. 네트워크 요청은 그 이후 별도 실행 수명으로 처리합니다.

## 이 문서에서 확인할 내용

- 화면이 읽는 로컬 상태와 서버 상태의 역할을 구분합니다.
- SQLite, 앱이 소유한 파일, 보안 저장소, 설정 값 저장소를 용도에 맞게 사용합니다.
- 기록 변경과 outbox 명령을 한 트랜잭션에 저장합니다.
- 명령 ID와 기준 버전으로 중복, 처리 여부를 모르는 결과와 충돌을 처리합니다.
- 동기화 작업자를 짧고 중단 가능한 단계로 만듭니다.
- 로컬에 커밋한 상태, 더 최신인 편집, 원격 스냅숏과 충돌을 함께 보존합니다.
- 마이그레이션, 미참조 파일과 저장소 부족을 정상 운영 문제로 다룹니다.

## 로컬 우선 방식의 범위를 분명히 합니다

이 저장소에서 로컬 우선 방식은 다음을 뜻합니다.

```text
화면은 로컬 데이터베이스를 읽습니다.
사용자가 저장하면 로컬 트랜잭션을 먼저 완료합니다.
서버 동기화는 outbox가 별도 실행으로 처리합니다.
서버 권한과 원격 버전은 여전히 서버가 결정합니다.
```

모든 데이터의 최종 기준이 항상 로컬이라는 뜻은 아닙니다. 계정 권한, 다른 사용자의 최신 변경과 서버의 업무 처리 절차는 원격 시스템이 소유합니다.

## 값의 성격에 맞는 저장 위치를 선택합니다

| 값 | 저장 위치 | 이유 |
|---|---|---|
| `Record`, outbox, 원격 버전, 충돌 | SQLite | 트랜잭션, 쿼리, 마이그레이션, 재시작 뒤 복원 |
| 사진과 첨부 파일 바이트 | 앱이 소유한 파일 디렉터리 | 큰 바이너리와 업로드 |
| 갱신 토큰과 작은 비밀값 | 보안 저장소 | 플랫폼이 제공하는 보호 기능 |
| 테마, 마지막 필터 | 설정 값 저장소 | 작은 비민감 키-값 |
| 썸네일과 다시 받을 수 있는 파일 | 캐시 디렉터리 | 삭제돼도 재생성 가능 |
| 로딩, 누름 상태 | 메모리 | 프로세스와 함께 사라져도 됨 |

설정 값 저장소에 Bearer 토큰을 넣지 않고, 보안 저장소에 큰 기록 목록을 넣지 않습니다.

## 최소 스키마

Field Notes의 핵심 테이블은 다음과 같습니다.

```sql
CREATE TABLE records (
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,
  notes TEXT NOT NULL,
  status TEXT NOT NULL,
  observed_at TEXT NOT NULL,
  local_revision INTEGER NOT NULL,
  remote_version INTEGER,
  sync_state TEXT NOT NULL,
  deleted_at_local TEXT
);

CREATE TABLE attachments (
  id TEXT PRIMARY KEY,
  record_id TEXT NOT NULL,
  local_uri TEXT NOT NULL,
  checksum TEXT NOT NULL,
  byte_size INTEGER NOT NULL,
  mime_type TEXT NOT NULL,
  state TEXT NOT NULL,
  remote_id TEXT,
  FOREIGN KEY (record_id) REFERENCES records(id)
);

CREATE TABLE outbox (
  command_id TEXT PRIMARY KEY,
  record_id TEXT NOT NULL,
  operation TEXT NOT NULL,
  base_version INTEGER,
  local_revision INTEGER NOT NULL,
  payload_json TEXT,
  state TEXT NOT NULL,
  attempt_count INTEGER NOT NULL,
  next_attempt_at INTEGER,
  lease_token TEXT,
  lease_expires_at INTEGER,
  created_at TEXT NOT NULL
);
```

실제 구현은 충돌, 처리 결과, 알림 선점과 마이그레이션 기록을 위한 테이블도 사용합니다. 중요한 점은 기록과 전송할 명령이 별도 행으로 존재하고 각각 안정적인 ID를 가진다는 것입니다.

## 기록 변경과 outbox 생성을 함께 커밋합니다

다음 순서는 안전하지 않습니다.

```text
기록 변경 커밋
→ 프로세스 종료
→ outbox 추가 실행되지 않음
```

화면에는 저장된 기록이 보이지만 서버로 보낼 근거가 없습니다.

반대 순서도 안전하지 않습니다.

```text
outbox 추가
→ 기록 변경 실패
```

따라서 다음 작업을 하나의 SQLite 트랜잭션에 둡니다.

```text
BEGIN
→ 현재 로컬 리비전 확인
→ 기록 변경 또는 삭제 표식 작성
→ 명령 ID, 기준 버전과 데이터 사본으로 outbox 행 생성
→ 필요한 첨부 파일 참조 확인
COMMIT
```

커밋이 끝나면 UI는 `기기에 저장됨, 동기화 대기`를 표시할 수 있습니다. 원격 성공을 기다리면서 입력 화면을 잠그지 않습니다.

## 명령은 HTTP 요청보다 오래 유지됩니다

요청은 한 번의 전송 시도입니다. 명령은 사용자가 확정한 변경입니다.

```ts
type RecordCommand = {
  commandId: string;
  recordId: string;
  operation: "upsert" | "delete";
  baseVersion: number | null;
  localRevision: number;
  payload: RecordPayload | null;
  createdAt: string;
};
```

서버는 같은 `commandId`를 다시 받으면 이미 처리한 결과를 반환하거나 같은 결과를 다시 계산해야 합니다. 시간 초과 뒤 클라이언트가 새 ID를 만들면 중복 방지 기능이 작동하지 않습니다.

## 첫 전송 시도의 내용을 바꾸지 않습니다

명령을 처음 선점할 때 다음 값을 최초 시도 사본으로 고정합니다.

```text
commandId
recordId
작업
baseVersion
localRevision
데이터 또는 tombstone
createdAt
```

다음 상황에서도 이 값을 바꾸지 않습니다.

- 응답 유실
- lease 만료
- 401 뒤 재개
- 로컬 처리 결과 저장 실패
- 네트워크 예외

이미 보낸 명령의 데이터나 기준 버전을 현재 `Record`에서 다시 계산하면 같은 명령 ID가 다른 업무 의도를 가리키게 됩니다.

아직 한 번도 보내지 않은 대기 중인 명령만 명시한 규칙에 따라 합치거나 새 기준 버전으로 바꿀 수 있습니다.

## Outbox 상태를 명시합니다

```ts
type OutboxState =
  | "pending"
  | "claimed"
  | "retry-wait"
  | "blocked-auth"
  | "conflict"
  | "permanent-failure"
  | "applied"
  | "superseded";
```

`claimed` 상태를 메모리에만 두면 프로세스 종료 뒤 작업이 멈출 수 있습니다. 저장소는 소유자, lease 토큰과 만료를 저장합니다.

```text
트랜잭션 시작
→ 실행 가능한 명령 한 개 선택
→ 최초 시도 사본과 `lease` 기록
→ 커밋
→ 요청 전송
→ 결과를 새 트랜잭션에 기록
```

다른 작업자는 살아 있는 lease를 가진 명령을 가져가지 못합니다. Lease가 만료되면 새 토큰으로 같은 최초 시도 명령을 다시 선점할 수 있습니다.

Lease는 정확히 한 번 네트워크 전달을 만들지 않습니다. 로컬 선점과 서버의 명령 결과 저장이 함께 필요합니다.

## 작업자는 제한된 수의 명령만 처리합니다

백그라운드 실행 시간이 짧을 수 있으므로 대기열 전체를 한 번에 비우려 하지 않습니다.

```text
남은 실행 시간 확인
→ 명령 선점
→ 요청 전송
→ 응답 검증
→ 명령 하나의 결과를 저장
→ 다음 명령을 시작할 시간 확인
```

명령 하나가 끝날 때마다 처리 결과가 저장되므로 어느 지점에서 프로세스가 종료돼도 다시 시작할 수 있습니다.

작업자가 확인할 결과는 다음과 같습니다.

- 성공
- 충돌
- 재시도 대기
- 차단된 인증
- 영구 실패

전송 함수가 예외를 반환하거나 응답이 유실되면 성공으로 추측하지 않고 재시도 대기 상태로 저장합니다. 로컬 처리 결과 저장 자체가 실패하면 같은 실행에서 두 번째 결과를 임의로 만들지 않고 멈춥니다. Lease 만료 뒤 같은 명령을 다시 보냅니다.

## 늦은 성공이 새 편집을 덮지 않게 합니다

다음 상황을 생각합니다.

```text
로컬 리비전 3을 명령 A로 전송
→ 전송 중 사용자가 리비전 4로 저장
→ 명령 A 성공 응답(버전 8) 도착
```

응답의 데이터를 현재 기록에 그대로 덮으면 리비전 4가 사라집니다.

완료 처리는 다음처럼 나눕니다.

```text
A의 명령 ID와 응답을 확인
→ 원격 버전을 8로 갱신
→ 현재 로컬 리비전이 A와 같은지 확인
→ 같으면 서버 결과를 반영하고 `synced` 상태로 전환
→ 더 새 리비전이면 로컬 데이터 유지
→ 아직 보내지 않은 대기 중인 명령만 기준 버전 8로 새 명령으로 교체
```

이미 보낸 명령은 바꾸지 않습니다. 더 최신인 편집은 새 명령 ID로 표현합니다.

## 성공 응답도 검증합니다

성공 본문도 다음 조건을 만족해야 합니다.

- 응답 명령 ID가 선점한 명령과 같습니다.
- 기록 ID가 같습니다.
- 원격 버전이 양의 정수입니다.
- 저장된 원격 버전보다 감소하지 않습니다.
- `upsert` 결과에 필수 데이터가 모두 있는지 확인합니다.
- 삭제 결과는 `deleted=true`, `payload=null`입니다.
- 본문 필드와 HTTP 상태가 맞습니다.

검증에 실패하면 `synced`로 표시하지 않습니다. 재시도 가능 여부를 정하고 최대 시도를 초과하면 영구 실패로 남깁니다.

## 충돌에서 양쪽 상태를 보존합니다

클라이언트가 원격 버전 7을 기준으로 수정했지만 서버가 이미 버전 8이면 기존 명령을 그대로 반복하지 않습니다.

충돌에는 다음 값을 보존합니다.

```ts
type RecordConflict = {
  conflictId: string;
  commandId: string;
  recordId: string;
  attempted: RecordCommand;
  local: {
    payload: RecordPayload | null;
    localRevision: number;
  };
  remote: RemoteRecord | null;
};
```

사용자는 다음 중 하나를 선택할 수 있습니다.

- 원격 상태를 적용합니다.
- 로컬 상태를 원격 현재 버전을 기준으로 새 명령에 담습니다.
- 로컬과 원격을 합친 데이터로 새 명령을 만듭니다.
- 지금 해결하지 않고 충돌 상태를 남깁니다.

해결할 때 원래 충돌 명령을 재사용하지 않습니다. 새 명령 ID를 만들고 해결 메타데이터를 원 충돌에 기록합니다.

Field Notes는 충돌 뒤에 같은 기록으로 쌓인 아직 보내지 않은 명령을 `superseded`로 종료합니다. 사용자가 선택한 최종 상태만 새 명령으로 전송합니다.

## 클라이언트 측정 시각만으로 충돌을 해결하지 않습니다

기기 시계는 틀릴 수 있고 사용자가 바꿀 수 있습니다. `updatedAt`은 화면 표시와 진단에 유용하지만 최종 순서를 판단할 때는 서버 버전, 서버 순번 또는 충돌 토큰을 사용합니다.

## 삭제 표식(tombstone)을 남깁니다

오프라인 삭제 직후 기록 행을 완전히 제거하면 서버에 보낼 명령과 첨부 파일 정리 근거를 잃습니다.

```text
기록 삭제 표식
+ 삭제 명령
+ 첨부 파일 보존 또는 정리 상태
```

서버 삭제가 확인된 뒤 삭제 표식을 언제 제거할지 정합니다. 다른 기기의 오래된 기록이 다시 나타나는 문제도 고려합니다.

## 파일 시스템과 SQLite의 차이를 처리합니다

파일 복사와 SQLite 트랜잭션은 하나의 원자 작업이 아닙니다.

```text
선택기나 카메라가 반환한 임시 URI
→ 앱이 소유한 임시 파일로 복사
→ 체크섬과 바이트 크기 확인
→ 앱이 관리하는 영구 저장 경로로 이동
→ SQLite 트랜잭션에서 첨부 파일 메타데이터 연결
```

실패 뒤 정리 방법:

- 메타데이터가 없는 오래된 임시 저장 파일은 시작 절차에서 제거합니다.
- 메타데이터가 가리키는 파일이 없으면 `missing-local-file`로 표시합니다.
- 메타데이터 추가가 실패한 새로 만든 앱 소유 파일은 즉시 제거하거나 다음 시작 절차에서 미참조로 정리합니다.
- 업로드 성공 뒤 원격 ID 저장이 실패하면 명령 ID로 서버 결과를 다시 확인합니다.
- 기록 삭제와 파일 제거를 별도 재시도 가능한 작업으로 처리합니다.

`파일을 옮기고 DB에 저장했으므로 원자적이다`라고 설명하지 않습니다.

## 마이그레이션은 릴리스 일부입니다

새 앱은 이전 버전의 로컬 DB를 열어야 합니다.

- 스키마 버전을 저장합니다.
- 스키마 버전을 한 단계씩 올립니다.
- 가능한 마이그레이션은 트랜잭션에서 실행합니다.
- 기존 DB를 실패 즉시 삭제하지 않습니다.
- 큰 테이블을 다시 쓰는 데 필요한 시간과 저장 공간을 확인합니다.
- 이전 버전으로 되돌릴 수 있는지 명시합니다.
- 실제 이전 스키마 시험 데이터로 업그레이드를 검사합니다.
- outbox 데이터 버전과 새 코드의 호환성을 확인합니다.

새 열의 기본값이 기존 기록의 의미를 바꾸지 않는지 확인합니다.

## 저장소 부족을 분류합니다

삭제되면 안 되는 값:

- 동기화되지 않은 `Record`
- outbox와 충돌
- 필요한 인증 정보

재생성 가능한 값:

- 원격 스냅숏 일부
- 썸네일
- 내려받은 파일 캐시

제품 규칙에 따라 보존할 값:

- 이미 동기화한 원본 사진
- 감사 기록

저장소가 부족할 때 동기화되지 않은 텍스트 기록보다 썸네일을 먼저 제거합니다. 파일 정리 실패가 기록 저장 전체를 막지 않게 합니다.

## 검증 시나리오

- 기록 저장 트랜잭션 중간 실패
- 이전 스키마에서 마이그레이션
- 파일 복사는 성공했지만 메타데이터 추가는 실패함
- 메타데이터는 있지만 파일이 누락됨
- 미참조 파일과 임시 저장 파일
- 응답 유실 뒤 같은 명령 재전송
- 서버 처리는 성공했지만 로컬 결과 기록은 실패함
- 유효한 lease 중 다른 작업자 실행
- lease 만료 뒤 재시도
- 401 인증 차단과 명시적 재개
- 형식이 잘못된 성공과 버전 회귀
- 명령 전송 중 더 최신인 편집
- 충돌에서 원격 적용, 로컬 재전송과 병합 선택
- 오프라인 삭제와 삭제 표식

## 완료 기준

- 화면은 프로세스 재시작 뒤에도 남는 로컬 데이터베이스를 읽습니다.
- `Record` 변경과 outbox 명령을 하나의 트랜잭션에 저장합니다.
- 첫 선점 뒤 명령 ID, 데이터, 기준 버전을 바꾸지 않습니다.
- 살아 있는 lease를 다른 작업자가 가져가지 못합니다.
- 명령마다 저장된 처리 결과가 있습니다.
- 응답 유실과 로컬 처리 결과 저장 실패 뒤 같은 명령을 다시 보냅니다.
- 늦은 성공 응답이 더 최신인 로컬 편집을 덮지 않습니다.
- 충돌이 최초 전송 내용, 현재 로컬 내용과 원격 내용을 모두 보존합니다.
- 충돌 해결은 새 명령을 만듭니다.
- 파일 시스템과 SQLite 불일치를 시작 절차에서 조정합니다.
- 이전 DB 시험 데이터로 마이그레이션을 확인합니다.
