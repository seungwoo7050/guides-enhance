# Backpressure, Bulkhead와 Load Shedding

## 목표

처리 속도보다 요청이 빠를 때 무제한 대기열과 재시도로 문제를 숨기지 않습니다. 동시에 실행할 수 있는 수, 대기열 크기와 최대 대기 시간을 정하고 초과 요청을 명시적으로 거절합니다.

## 대기열은 처리량을 늘리지 않습니다

서비스가 초당 100건을 처리하는데 초당 500건이 계속 들어오면 대기열은 지연을 잠시 숨길 뿐입니다. 크기를 제한하지 않으면 메모리 사용량과 대기 시간이 계속 늘고, deadline이 지난 작업까지 뒤늦게 실행하게 됩니다.

의존 서비스 하나가 느린데 모든 worker와 connection을 공유하면 다른 기능도 함께 멈춥니다. 이때는 더 많이 받아 두는 것이 아니라 받을 수 있는 양을 제한해야 합니다.

## 실행 수와 대기 수를 따로 제한합니다

작업 종류마다 다음 값을 정합니다.

```text
max_running
max_queued
max_queue_time
request_deadline
```

새 요청은 다음 순서로 처리합니다.

1. deadline이 이미 지났으면 거절합니다.
2. 실행 자리가 있으면 바로 시작합니다.
3. 대기 자리가 있고 최대 대기 시간 안에 처리할 수 있으면 queue에 넣습니다.
4. 나머지는 `OVERLOADED`로 거절합니다.

비동기 API는 queue에 들어갔다는 사실만 반환하지 말고 operation ID, 예상 최대 지연과 결과 조회 방법을 알려 줘야 합니다.

## 느린 소비자의 상태를 위쪽에 전달합니다

consumer가 느린데 producer가 계속 보내면 대기열 위치만 바뀝니다. 사용하는 기술에 따라 다음 방법을 적용합니다.

- Broker 소비를 잠시 멈춥니다.
- producer의 in-flight 수를 제한합니다.
- HTTP 429 또는 503과 `Retry-After`를 반환합니다.
- 상위 서비스의 동시 호출 수를 줄입니다.
- batch 크기와 poll 수를 제한합니다.
- 중요도가 낮은 작업부터 거절합니다.

재시도 가능한 거절이라도 모든 호출자가 동시에 다시 보내지 않게 jitter와 전체 재시도 시간을 둡니다.

## 느린 기능이 전체 자원을 사용하지 못하게 합니다

Bulkhead는 기능이나 의존 서비스별로 worker, connection pool 또는 queue를 분리합니다.

```text
inventory 호출: 20개
notification 호출: 5개
admin export: 2개
```

한 기능이 포화되어도 다른 기능은 자신의 실행 자리를 사용할 수 있습니다. 단, 너무 잘게 나누면 유휴 자원이 늘고 설정이 복잡해집니다. 서로 다른 장애 영향과 중요도를 기준으로 나눕니다.

## 과부하 거절의 의미를 명확히 합니다

호출자는 거절된 요청이 실제로 시작되었는지 알아야 합니다.

- 상태를 전혀 만들지 않고 거절했는지
- 같은 operation ID로 다시 보내야 하는지
- 어느 시각 이후 다시 시도할 수 있는지
- priority나 quota를 적용했는지
- 결과 조회가 필요한지

쓰기 작업이 queue에 들어간 뒤 timeout이 발생했다면 단순 거절이 아니라 결과를 알 수 없는 상태일 수 있습니다.

## 흔한 잘못

- queue 크기와 최대 대기 시간이 없습니다.
- deadline이 지난 작업을 계속 실행합니다.
- 느린 기능이 전체 worker와 connection pool을 사용합니다.
- 과부하에서 retry가 요청 수를 더 늘립니다.
- queue 길이만 보고 가장 오래 기다린 시간은 보지 않습니다.
- 내부에서 버린 요청을 성공으로 응답합니다.
- 낮은 중요도의 대량 작업이 핵심 작업의 자리를 모두 차지합니다.

## 검증 방법

짧은 시간에 많은 요청을 넣고 다음을 확인합니다.

- 실행 중인 작업 수가 `max_running`을 넘지 않습니다.
- 대기 작업 수가 `max_queued`를 넘지 않습니다.
- 초과 요청은 상태를 만들지 않고 거절됩니다.
- 작업 하나가 끝나면 대기 작업 하나만 실행 상태로 바뀝니다.
- deadline이나 최대 대기 시간을 넘긴 작업은 실행 전에 제거됩니다.
- 한 Lane의 포화가 다른 Lane의 실행을 막지 않습니다.
- 거절 수와 가장 오래 기다린 시간을 확인할 수 있습니다.

## 관련 프로젝트

[`backpressure`](../../exercises/backpressure/)는 작업 종류별 Lane, 제한된 실행 수와 대기열, 만료와 격리를 메모리 모델로 검사합니다.

## 완료 기준

- 실행 수, 대기열 크기와 최대 대기 시간을 함께 정할 수 있습니다.
- 상위 호출자에게 어떤 과부하 응답을 보낼지 설명할 수 있습니다.
- 서로 다른 장애 영향을 가진 작업에 자원을 따로 배정할 수 있습니다.
- burst와 deadline 조건에서 대기열이 제한되는지 테스트할 수 있습니다.
