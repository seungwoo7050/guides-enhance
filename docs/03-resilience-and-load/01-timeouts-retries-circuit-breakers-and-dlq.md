# 시간 예산, 재시도, Circuit Breaker와 DLQ

## 목표

각 라이브러리에 timeout 값을 따로 넣는 대신 하나의 사용자 요청에 허용된 전체 시간을 정하고, 그 안에서 하위 호출과 재시도를 제한합니다. 실패 종류에 따라 재시도 여부를 결정하고 Circuit Breaker와 DLQ의 역할을 구분합니다.

## 재시도는 장애를 더 키울 수 있습니다

Gateway와 여러 서비스가 각각 세 번씩 재시도하면 사용자 요청 한 건이 많은 하위 호출로 늘어납니다. 의존 서비스가 느린 상황에서는 복구를 돕기보다 추가 부하를 만들 수 있습니다.

또한 timeout은 업무 결과를 알려 주지 않습니다. 호출자가 기다리기를 멈춘 뒤에도 서버는 상태를 바꿀 수 있습니다. 쓰기 명령을 다시 보내려면 같은 operation ID와 결과 조회가 필요합니다.

## 전체 deadline을 먼저 정합니다

시간 제한을 계층마다 독립적으로 정하지 않습니다.

```text
사용자 요청 전체 deadline: 800ms
Gateway 처리와 전달:        100ms
서비스 내부 처리:           100ms
하위 호출과 재시도:         최대 500ms
응답 처리 여유:             100ms
```

값은 시스템마다 다르지만 합이 전체 deadline을 넘으면 안 됩니다. 하위 호출에는 고정 timeout보다 남은 시간을 전달하는 편이 안전합니다.

다음 시간을 구분합니다.

- 연결을 맺는 데 기다릴 시간
- 개별 호출 한 번의 timeout
- queue에서 기다릴 수 있는 시간
- 업무 한 건의 전체 deadline
- 비동기 작업의 최대 완료 시간

시간이 끝난 뒤 실행 중인 작업을 실제로 취소할 수 있는지도 별도로 정합니다.

## 재시도할 실패를 제한합니다

다음 조건을 모두 만족할 때만 재시도를 고려합니다.

- 일시 장애일 가능성이 있습니다.
- 같은 operation ID로 다시 호출해도 효과가 한 번만 남습니다.
- 다음 호출과 backoff가 전체 deadline 안에 들어옵니다.
- 재시도가 의존 서비스의 복구를 방해하지 않습니다.
- 여러 계층 중 한 곳만 재시도를 수행합니다.

입력 검증 실패, 권한 부족과 업무 규칙에 따른 거절은 다시 보내도 같은 결과가 나오므로 재시도하지 않습니다. 일시 장애도 횟수만으로 제한하지 말고 최대 경과 시간을 함께 둡니다.

운영 환경의 backoff에는 jitter를 사용해 여러 인스턴스가 같은 시각에 몰리지 않게 합니다. 테스트에서는 실제 sleep과 난수 대신 가상 시계를 사용해 결과를 결정적으로 확인합니다.

## Circuit Breaker에 셀 실패를 정합니다

Circuit Breaker는 실패를 없애지 않습니다. 응답하지 않는 의존 서비스로 보내는 새 호출을 잠시 막아 추가 부하를 줄입니다.

| 결과 | 실패 횟수에 포함 |
| --- | --- |
| 연결 실패, timeout | 일반적으로 포함 |
| 기반 시설 문제로 인한 5xx | 상황에 따라 포함 |
| 업무 규칙에 따른 409, 422 | 포함하지 않음 |
| 호출자 취소 | 원인을 구분해 결정 |
| Circuit Breaker가 열려 즉시 거절 | 원래 장애와 별도 기록 |

`HALF_OPEN` probe에서 409나 422 같은 정상 업무 응답을 받았다면 의존 서비스는 응답한 것입니다. 해당 업무 결과는 호출자에게 전달하되 Circuit Breaker는 닫습니다.

쓰기 probe에는 처음 operation ID를 그대로 사용합니다. Circuit Breaker가 닫혔다고 중간 상태가 자동으로 복구되는 것은 아니므로 별도의 재조정이 필요합니다.

## DLQ에는 다시 처리할 정보가 있어야 합니다

DLQ에 payload만 넣으면 원인을 고친 뒤 어디로 어떻게 되돌릴지 알 수 없습니다. 다음 정보를 함께 저장합니다.

- 원래 channel과 위치
- event ID와 operation ID
- schema version
- 실패 종류와 마지막 오류
- 시도 횟수와 최초·최종 실패 시각
- 재처리 담당자
- 수정 뒤 실행할 처리 방법
- 보존 기간과 폐기 승인

원인을 고치지 않고 원래 channel로 계속 되돌리면 같은 poison message가 반복됩니다. 재처리할 때도 event ID를 바꾸지 않아 소비자의 중복 처리를 그대로 사용합니다.

## 흔한 잘못

- 각 계층이 독립적으로 여러 번 재시도합니다.
- 하위 timeout과 backoff 합이 전체 deadline보다 깁니다.
- 재시도마다 새 operation ID를 사용합니다.
- 업무 거절을 Circuit Breaker 실패로 셉니다.
- 열린 Circuit Breaker의 거절을 정상 응답처럼 숨깁니다.
- DLQ에 payload만 있고 원본 위치와 담당자가 없습니다.
- 실제 sleep을 사용하는 느리고 불안정한 테스트만 있습니다.

## 검증 방법

가상 시계와 미리 정한 응답 순서를 사용해 다음을 확인합니다.

- 업무 거절은 한 번만 호출됩니다.
- 일시 장애는 같은 operation ID로 다시 호출합니다.
- 다음 backoff가 deadline을 넘으면 호출하지 않습니다.
- 연속 일시 장애 뒤 Circuit Breaker가 열리고 의존 서비스를 호출하지 않습니다.
- OPEN 시간이 지난 뒤 probe 한 건만 허용합니다.
- 실패한 probe는 새 OPEN 시간을 시작합니다.
- DLQ 재처리가 실패하면 원본 메시지가 남습니다.
