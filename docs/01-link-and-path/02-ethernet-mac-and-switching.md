# Ethernet, MAC 주소와 스위칭

Ethernet은 같은 링크 안에서 프레임을 다음 인터페이스로 전달하는 형식과 규칙을 제공합니다. IP 주소가 여러 링크를 잇는 논리적 위치를 나타낸다면 MAC 주소는 현재 링크에서 프레임을 어느 방향으로 보낼지 결정할 때 사용합니다.

## 학습 목표

- Ethernet II 프레임의 주요 필드와 페이로드 시작 위치를 계산합니다.
- 스위치의 MAC 학습과 플러딩을 IP 라우팅과 구분합니다.
- VLAN이 나누는 범위와 태그가 프레임 오프셋에 미치는 영향을 설명합니다.

## Ethernet II 프레임

일반적인 캡처에서 보는 Ethernet II 프레임은 다음 순서입니다.

| 필드 | 크기 | 의미 |
|---|---:|---|
| 목적지 MAC | 6바이트 | 현재 링크의 수신 대상 |
| 출발지 MAC | 6바이트 | 현재 링크의 송신 인터페이스 |
| EtherType | 2바이트 | 페이로드 프로토콜 |
| 페이로드와 패딩 | 가변 | IPv4, IPv6, ARP 등의 데이터 |
| FCS | 4바이트 | 링크 전송 오류 검출 |

Preamble과 Start Frame Delimiter는 실제 전송에 필요하지만 일반적인 패킷 캡처에는 포함되지 않습니다. FCS도 NIC가 확인한 뒤 제거해 캡처에서 보이지 않을 수 있습니다. 캡처에 FCS가 없다는 사실만으로 링크 오류 검사가 없었다고 결론 내리지 않습니다.

## MAC 주소의 범위

48비트 MAC 주소의 첫 옥텟에는 개별·그룹 주소와 전역·로컬 관리 여부를 나타내는 비트가 있습니다. 가상 인터페이스, 컨테이너와 개인 정보 보호 기능은 로컬 관리 주소를 사용할 수 있습니다.

다음과 같이 단정하지 않습니다.

- 모든 MAC 주소가 제조 시 영구적으로 고정됩니다.
- MAC 주소가 인터넷 전체에서 라우팅됩니다.
- 출발지 MAC만 보면 물리 장비의 신원을 확정할 수 있습니다.

브로드캐스트 주소 `ff:ff:ff:ff:ff:ff`는 같은 브로드캐스트 도메인의 모든 수신자를 대상으로 합니다. 멀티캐스트 주소는 특정 그룹을, 유니캐스트 주소는 하나의 논리적 인터페이스를 가리킵니다.

## 스위치의 학습과 전달

학습형 스위치는 프레임의 **출발지 MAC과 입력 포트**를 전달 데이터베이스에 기록합니다. 목적지 MAC을 기준으로 다음처럼 처리합니다.

```text
알고 있는 유니캐스트 목적지 → 기록된 포트로 전달
알 수 없는 유니캐스트 목적지 → 입력 포트를 제외한 같은 VLAN으로 플러딩
브로드캐스트 또는 해당 멀티캐스트 → 같은 VLAN으로 플러딩
목적지가 입력 포트 쪽 → 전달하지 않음
```

스위치는 일반적인 Ethernet 프레임을 목적지 IP 프리픽스로 전달하지 않습니다. 반대로 라우터는 프레임에서 IP 패킷을 꺼낸 뒤 목적지 IP로 경로를 선택합니다. MAC 전달 테이블과 IP 라우팅 테이블은 서로 다른 입력을 사용합니다.

학습 항목은 일정 시간이 지나면 만료될 수 있습니다. 장비가 다른 포트로 이동하거나 VM이 이동하면 새 출발지 프레임을 보고 위치를 다시 학습합니다.

## VLAN 태그

802.1Q 태그는 원래 EtherType 위치에 Tag Protocol Identifier를 넣고, 그 뒤에 우선순위, Drop Eligible Indicator와 VLAN ID를 담은 Tag Control Information을 추가합니다. 실제 페이로드 EtherType은 태그 뒤로 이동합니다.

```text
Destination | Source | 0x8100 | TCI | Inner EtherType | Payload
```

같은 물리 스위치에 연결되어 있어도 VLAN이 다르면 기본적으로 같은 브로드캐스트 도메인이 아닙니다. VLAN 사이 통신에는 L3 라우팅이 필요합니다. VLAN은 통신 범위를 나누지만 인증이나 암호화를 제공하지는 않습니다.

## 프레임 크기와 MTU

일반적인 Ethernet IP MTU는 1500바이트이지만 링크와 터널 설정에 따라 달라집니다. 작은 페이로드에는 최소 프레임 크기를 맞추기 위한 패딩이 붙을 수 있습니다. 상위 프로토콜은 자신의 길이 필드를 사용해 실제 데이터와 패딩을 구분합니다.

Jumbo frame을 사용하려면 경로의 모든 관련 인터페이스와 장비가 같은 크기를 처리해야 합니다. 한 구간만 다르게 설정하면 큰 패킷이 특정 지점에서 손실되거나 분할될 수 있습니다.

## 파서가 확인해야 할 조건

[protocol-inspector](../../exercises/protocol-inspector/README.md)는 일반 Ethernet II와 802.1Q 또는 802.1ad 태그 한 개를 읽습니다.

파서는 다음 순서로 입력을 확인합니다.

1. 기본 헤더 14바이트가 실제로 존재하는지 확인합니다.
2. VLAN EtherType이면 추가 4바이트가 있는지 확인합니다.
3. Inner EtherType을 사용해 다음 파서를 선택합니다.
4. 지원하지 않는 EtherType을 IPv4로 잘못 해석하지 않습니다.

운영용 파서라면 여러 VLAN 태그, LLC/SNAP, 캡처 메타데이터와 NIC offload까지 고려해야 합니다. 이 프로젝트는 바이트 범위 검증과 다음 프로토콜 선택에 초점을 맞춥니다.

## 관찰 명령

Linux에서는 다음 명령으로 인터페이스와 bridge 전달 데이터베이스를 확인할 수 있습니다.

```sh
ip -details link show
bridge fdb show
```

macOS에서는 `ifconfig`로 로컬 인터페이스와 MAC 주소를 확인할 수 있습니다. 외부 스위치의 전달 데이터베이스는 해당 장비의 관리 기능에서 확인해야 합니다.

조사 기록에는 VLAN, 입력 포트, 학습된 MAC 위치, 플러딩 범위와 링크 상태를 따로 적습니다.

## 완료 기준

- 캡처 바이트에서 목적지·출발지 MAC, EtherType과 페이로드 시작 위치를 계산합니다.
- 알 수 없는 유니캐스트 플러딩과 브로드캐스트를 같은 현상으로 설명하지 않습니다.
- VLAN 태그가 페이로드 오프셋과 브로드캐스트 도메인에 미치는 영향을 설명합니다.
