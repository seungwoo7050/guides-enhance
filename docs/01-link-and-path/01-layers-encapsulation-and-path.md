# 계층, 캡슐화와 종단 경로

네트워크 계층화는 장비와 프로토콜을 번호표에 맞춰 분류하는 일이 아닙니다. 각 구성 요소가 어떤 입력을 받고, 어떤 값을 확인하며, 다음 구성 요소에 무엇을 넘기는지 나누는 방법입니다. 이 구분이 있으면 애플리케이션은 Ethernet 전송 방식을 몰라도 요청을 보낼 수 있고, 라우터는 HTTP 메서드를 해석하지 않아도 목적지 IP에 따라 패킷을 전달할 수 있습니다.

## 학습 목표

- 애플리케이션 데이터가 링크 프레임까지 캡슐화되는 순서를 추적합니다.
- 종단점, 라우터와 링크에서 유지되거나 바뀌는 값을 구분합니다.
- 연결 실패를 하나의 "네트워크 오류"로 묶지 않고 마지막 성공 단계를 기록합니다.

## 계층별 입력과 출력

| 범위 | 대표 입력과 출력 | 주요 식별자 | 실제로 하는 일 |
|---|---|---|---|
| 애플리케이션 | 요청, 응답, 메시지 | 이름, URI, 애플리케이션 ID | 데이터의 의미와 처리 결과를 정합니다. |
| 전송 | 바이트 스트림 또는 데이터그램 | 포트, 연결 튜플 | 프로세스에 데이터를 전달하고 필요한 경우 순서·손실·혼잡을 처리합니다. |
| 인터넷 | IP 패킷 | IP 주소, 프리픽스 | 서로 다른 링크를 지나 목적지 쪽 다음 홉으로 패킷을 보냅니다. |
| 링크 | 프레임 | MAC 주소, EtherType | 현재 링크에서 다음 인터페이스로 프레임을 보냅니다. |
| 물리 | 비트와 신호 | 채널 | 매체를 통해 비트를 전송합니다. |

이 표는 실제 구현을 다섯 개의 독립된 상자로 고정하지 않습니다. 터널, VPN, 가상 스위치와 QUIC처럼 한 구현이 여러 기능을 묶거나 다른 프로토콜 위에 다시 캡슐화할 수 있습니다. 장애를 조사할 때는 계층 번호보다 실제 헤더, 상태와 오류를 확인합니다.

## OSI 모델과 인터넷 프로토콜 모음

OSI 모델은 기능을 일곱 단계로 더 세분화합니다. 실제 인터넷 구현에서는 세션과 표현 기능이 독립된 계층으로 드러나지 않는 경우가 많습니다.

| OSI | 대표 기능 | 인터넷 환경의 예 |
|---:|---|---|
| 7 애플리케이션 | 사용자와 업무 프로토콜의 의미 | HTTP, DNS, SMTP |
| 6 표현 | 인코딩, 압축, 암호화 | JSON, CBOR, TLS 레코드 |
| 5 세션 | 대화 수립, 유지와 재개 | 애플리케이션 세션, RPC 스트림 |
| 4 전송 | 종단 전달, 순서, 손실·흐름·혼잡 제어 | TCP, UDP, QUIC의 전송 기능 |
| 3 네트워크 | 여러 링크 사이의 주소와 경로 | IPv4, IPv6, ICMP |
| 2 데이터 링크 | 한 링크 안의 프레임 전달 | Ethernet, Wi-Fi |
| 1 물리 | 비트를 신호로 바꾸어 전송 | 구리선, 광섬유, 무선 |

TLS와 QUIC처럼 여러 기능을 함께 제공하는 프로토콜을 억지로 한 칸에만 넣지 않습니다. 실제 패킷과 상태를 기준으로 설명합니다.

## 캡슐화

HTTPS 요청의 개념적인 전송 순서는 다음과 같습니다.

```text
HTTP 메시지
→ TLS 레코드
→ TCP 바이트 스트림의 일부
→ IP 패킷 페이로드
→ Ethernet 프레임 페이로드
→ 링크 신호
```

수신자는 EtherType, IP Protocol 또는 Next Header, 전송 포트와 애플리케이션 상태를 차례로 확인해 데이터를 올바른 처리기로 전달합니다. 단순히 헤더를 벗기는 것이 아니라 각 단계에서 길이, 체크섬, 상태와 허용 조건을 검증합니다.

같은 프레임이 그대로 종단까지 이동하지는 않습니다. 라우터는 입력 프레임에서 IP 패킷을 꺼내 TTL 또는 Hop Limit을 줄이고 경로를 선택한 뒤, 출력 링크에 맞는 새 프레임을 만듭니다. NAT나 터널이 없다면 출발지와 목적지 IP 및 전송 포트는 대체로 유지되지만, 링크 헤더는 홉마다 달라집니다.

## 어디에서 값이 바뀌는가

```text
애플리케이션 종단점: HTTP 의미, 애플리케이션 상태
전송 종단점:         TCP 순서 번호와 ACK, UDP 데이터그램
라우터 처리:          TTL/Hop Limit, 경로와 다음 홉
한 링크:              출발지/목적지 MAC, FCS
```

원격 서버의 MAC 주소를 첫 링크에서 알아낼 필요는 없습니다. 호스트는 경로가 선택한 **현재 링크의 다음 홉**에 사용할 MAC 주소만 찾습니다.

## 다중화와 역다중화

여러 프로토콜과 프로세스가 같은 인터페이스를 사용하려면 수신자가 입력을 올바른 처리기로 전달할 수 있어야 합니다.

```text
EtherType 0x0800 → IPv4 처리
IPv4 Protocol 6  → TCP 처리
TCP 목적지 포트 443 → 해당 수신 대기 소켓 또는 연결
TLS ALPN h2      → HTTP/2 처리
```

TCP 연결은 포트 하나만으로 식별하지 않습니다. 일반적으로 로컬·원격 IP, 로컬·원격 포트와 전송 프로토콜을 함께 사용합니다. 같은 서버 포트 443에서 많은 연결을 동시에 받을 수 있는 이유도 각 튜플이 다르기 때문입니다.

## 장애를 기록하는 순서

연결이 실패했을 때 다음 질문을 순서대로 확인합니다.

1. 이름이 어떤 주소 후보로 해석되었습니까?
2. 목적지에 어떤 경로, 다음 홉과 출력 인터페이스가 선택되었습니까?
3. 다음 홉의 링크 주소를 확인했습니까?
4. TCP 연결 또는 UDP 데이터그램 교환이 시작되었습니까?
5. TLS와 애플리케이션 프로토콜이 성공했습니까?

한 단계의 성공은 다음 단계의 성공을 보장하지 않습니다. DNS가 성공해도 경로가 없을 수 있고, TCP 핸드셰이크가 끝나도 TLS 인증이나 HTTP 권한 검사가 실패할 수 있습니다.

예시는 다음과 같습니다.

```text
DNS: A와 AAAA 응답 확인
경로: eth0, 다음 홉 192.0.2.1 선택
이웃: 다음 홉 항목 REACHABLE
전송: SYN 전송, SYN/ACK 미수신
TLS/HTTP: 아직 실행되지 않음
```

이렇게 기록하면 "네트워크가 안 됩니다"라는 표현을 실제 확인 결과로 바꿀 수 있습니다.

## 완료 기준

- 애플리케이션 메시지부터 링크 프레임까지 캡슐화 순서를 설명합니다.
- 라우터가 새로 만드는 값과 종단점에서만 해석하는 값을 구분합니다.
- 연결 실패 기록에 관찰 위치, 마지막 성공 단계와 아직 확인하지 않은 단계를 적습니다.
