# 화면 이동, 링크와 상태 복원

모바일 경로는 화면을 바꾸는 문자열에 그치지 않습니다. 실행 아이콘, 외부 링크, 알림, 운영체제의 이전 화면 복원과 사용자의 뒤로 가기 동작이 모두 같은 화면으로 들어올 수 있습니다.

각 입력이 직접 라우터를 호출하면 데이터베이스가 준비되기 전에 보호된 화면이 열리거나, 같은 알림이 여러 번 적용되고, 작성 중인 초안을 외부 링크가 덮을 수 있습니다. 먼저 입력을 검증하고 현재 저장 상태를 확인한 뒤 실제 경로를 선택해야 합니다.

## 이 문서에서 확인할 내용

- 경로 매개변수를 외부 입력으로 보고 검증합니다.
- 현재 경로, 선택한 기록, 편집 초안의 소유자를 구분합니다.
- 딥 링크와 내부 화면 이동이 같은 경로 규칙을 사용하게 합니다.
- 데이터베이스와 세션이 준비되기 전의 화면 이동 요청을 보류합니다.
- 존재하지 않거나 현재 계정에서 열 수 없는 대상에 안전한 대체 경로를 제공합니다.
- Android 뒤로 가기, iOS 제스처, 모달 닫기와 기록 변경 취소를 구분합니다.
- 콜드 스타트, 웜 전달, 복원에서 적용할 상태를 따로 정합니다.

## 입력과 결과를 분리합니다

| 값 | 누가 전달하는가 | 앱이 해야 할 일 |
|---|---|---|
| 원본 링크, 알림 응답, 복원 데이터 | 운영체제 또는 외부 앱 | 문자열 길이, `scheme`, 경로, ID와 스키마를 검증합니다. |
| 정규화한 화면 이동 요청 | 파서 | 화면 종류와 안정적인 ID만 남깁니다. |
| 현재 경로와 뒤로 가기 목록 | 라우터 | 검증된 결과만 적용합니다. |
| 기록, 계정, 초안 | 저장소와 화면 | 대상 존재 여부와 현재 작업을 확인합니다. |

화면 이동 실패가 저장된 `Record`를 되돌리거나 outbox를 지워서는 안 됩니다. 화면 이동과 업무 변경은 별도 작업입니다.

## 경로를 화면 선택의 기준으로 사용합니다

Field Notes의 주요 경로는 다음과 같습니다.

```text
/records
/records/new
/records/:recordId
/records/:recordId/edit
/sync
/settings
```

공유하거나 복원해야 하는 화면 선택은 경로에 둡니다. `selectedRecordId`를 별도 전역 상태에 복제하면 경로와 값이 어긋날 수 있습니다.

```text
경로의 기록 ID
→ ID 형식 검증
→ 저장소에서 현재 기록 조회
→ 필요한 계정과 공개 범위 확인
→ 상세, 편집, 대상 없음 또는 대체 경로 결정
```

기록 객체 전체를 경로 이동 인자로 넘겨도 콜드 스타트나 외부 링크에는 해당 객체가 없습니다. 경로에는 안정적인 식별 정보와 화면 의도만 둡니다.

## 경로 매개변수는 신뢰하지 않습니다

파일 기반 라우터가 TypeScript 타입을 제공하더라도 실제 URL은 외부에서 들어옵니다. 다음 항목을 확인합니다.

- 전체 입력 길이
- URL scheme
- 경로 조각의 개수
- 퍼센트 디코딩 실패
- 기록 ID 문법과 길이
- 허용하지 않은 쿼리 키
- 모르는 경로
- 이미 삭제된 기록
- 현재 계정과 맞지 않는 기록

잘못된 값을 단정문으로 넘기지 않습니다.

```ts
type RecordRouteResult =
  | { kind: "ready"; recordId: string }
  | { kind: "invalid-link" }
  | { kind: "not-found" }
  | { kind: "forbidden" }
  | { kind: "needs-sync"; recordId: string };
```

`not-found`와 `forbidden`을 사용자에게 어떻게 표시할지는 제품 보안 요구에 따라 달라질 수 있습니다. 다만 내부 처리에서는 실패 원인을 구분해야 반복 요청이나 잘못된 대체 처리를 피할 수 있습니다.

## 여러 진입 경로를 하나의 요청으로 바꿉니다

앱을 여는 경로는 여러 개입니다.

```text
실행 아이콘
커스텀 scheme, 유니버설 링크 또는 앱 링크
알림 응답
운영체제 복원
앱 내부 동작
```

각 소스를 바로 라우터에 연결하지 않고 공통 값으로 변환합니다.

```ts
type NavigationIntent =
  | { kind: "records"; source: NavigationIntentSource }
  | {
      kind: "open-record";
      recordId: string;
      destination: "detail" | "edit";
      source: NavigationIntentSource;
    }
  | { kind: "open-sync"; source: NavigationIntentSource }
  | { kind: "open-settings"; source: NavigationIntentSource }
  | { kind: "invalid"; reason: string; source: NavigationIntentSource };
```

그다음 현재 상태로 실제 이동을 결정합니다.

```text
원본 입력
→ 길이와 인코딩 확인
→ scheme, 경로와 ID 정규화
→ 데이터베이스 준비 대기
→ 대상 조회
→ 현재 초안과 중복 요청 확인
→ 경로 적용 또는 안전한 대체 경로
```

## 콜드, 웜, 복원을 구분합니다

### 콜드 스타트

프로세스와 JavaScript 메모리가 없습니다.

```text
최초 링크와 알림 조회
→ SQLite 열기와 마이그레이션
→ 필요한 계정 상태 읽기
→ 대상 확인
→ 최초 경로 적용
```

### 웜 전달

현재 경로와 초안이 있습니다.

```text
새 요청 도착
→ 현재 작업 확인
→ 같은 화면 요청인지 확인
→ 초안을 덮을 가능성이 있으면 보류
→ 적용하거나 사용자가 나중에 다시 선택하게 함
```

### 복원

운영체제나 라우터가 이전 경로 후보를 제공합니다.

```text
이전 경로 후보
→ 현재 앱 버전과 경로 스키마 확인
→ 계정과 기록을 다시 조회
→ 유효한 최상위 경로만 제한적으로 복원
```

로딩, 열린 모달, 실행 중 비동기 작업 같은 일시 상태는 복원하지 않습니다.

## 시작 절차 완료 순서를 고정합니다

콜드 스타트에서는 다음 작업이 동시에 시작될 수 있습니다.

- 최초 링크 조회
- 마지막 알림 응답 조회
- SQLite 마이그레이션
- 보안 세션 읽기
- 앱 설정 읽기

먼저 끝난 비동기 작업이 바로 화면을 이동하게 두면 같은 입력에서도 결과가 달라질 수 있습니다. 시작 절차 처리 코드는 필요한 준비 상태를 명시합니다.

```ts
type StartupState =
  | { kind: "booting"; pendingIntent: NavigationIntent | null }
  | { kind: "local-ready"; pendingIntent: NavigationIntent | null }
  | { kind: "private-ready"; accountId: string; pendingIntent: NavigationIntent | null }
  | { kind: "failed"; reason: string };
```

Field Notes는 데이터베이스가 준비된 뒤 기록 존재 여부를 확인합니다. 준비 전에 들어온 웜 링크는 크기가 제한된 버퍼에 보관합니다. 모르는 경로나 잘못된 ID를 준비 대기열에 넣지 않습니다.

## 최신 명시적 입력과 복원을 구분합니다

사용자가 방금 누른 링크나 알림은 이전 프로세스의 경로보다 우선할 수 있습니다. 하지만 링크와 알림이 동시에 발견됐을 때 콜백 완료 순서를 제품 의미로 사용하면 안 됩니다.

다음 값을 사용해 판단합니다.

- 소스 종류
- 안정적인 응답 또는 메시지 ID
- 앱이 기록한 수신 순서
- 이미 처리한 요청 ID
- 현재 경로와 초안

순서를 확정할 수 없다면 안전한 현재 화면을 유지하고 사용자가 선택할 수 있는 대기 중인 동작을 남깁니다. 여러 소스가 동시에 같은 경로를 요청할 때는 프로세스 안에서 한 번만 적용하도록 제한합니다.

프로세스 안의 최근 경로 키 집합은 화면 중복을 줄이는 장치입니다. 알림 메시지의 저장된 선점 기록이나 서버 명령의 멱등 처리를 대신하지 않습니다.

## 링크와 인가를 구분합니다

링크가 올바른 모양이라는 사실은 현재 사용자가 기록을 볼 수 있다는 뜻이 아닙니다.

```text
fieldnotes://records/rec-123
```

이 문자열은 화면 의도만 전달합니다. 앱은 현재 계정과 로컬·원격 상태를 다시 확인합니다.

다음 상태를 구분합니다.

- 로그인이 필요함
- 다른 계정으로 로그인됨
- 로컬에는 없고 서버 조회가 필요함
- 오프라인이라 존재 여부를 확정할 수 없음
- 기록이 삭제됨
- 현재 앱 버전이 경로를 모름

이미 승인돼 로컬에 저장된 기록은 오래된 표시와 함께 보여 줄 수 있습니다. 처음 보는 원격 기록은 오프라인 상태에서 존재한다고 단정하지 않습니다.

운영용 유니버설 링크와 앱 링크는 앱 설정 외에도 도메인 연결 파일과 실제 호스팅이 필요합니다. 커스텀 `scheme` 테스트가 통과했다고 DNS, TLS와 도메인 연결 파일 호스팅까지 확인된 것은 아닙니다.

## 알림은 화면 상태가 아닙니다

알림 제목과 본문을 최신 기록 내용으로 사용하지 않습니다. 데이터에는 업무 데이터 대신 안정적인 ID와 요청 종류만 둡니다.

```json
{
  "schemaVersion": 1,
  "messageId": "msg-123",
  "accountId": "account-1",
  "intent": {
    "kind": "record-conflict",
    "recordId": "rec-123"
  }
}
```

처리 순서는 다음과 같습니다.

```text
데이터 검증
→ 데이터베이스 준비
→ 현재 계정 조회
→ 메시지 ID 선점
→ 현재 기록과 충돌 상태 조회
→ 경로 적용
→ 메시지 처리 완료 기록
```

알림이 오래됐다면 현재 상태를 설명하거나 목록으로 이동합니다. 알림 권한이 없거나 전달되지 않아도 앱의 동기화 화면에서 같은 충돌을 찾을 수 있어야 합니다.

## 뒤로 가기는 저장 취소가 아닙니다

편집 화면에서 뒤로 가기를 눌렀을 때는 저장 상태를 기준으로 처리합니다.

- 초안이 없으면 이전 화면으로 이동합니다.
- 저장하지 않은 초안이 있으면 계속 편집하거나 버릴지 묻습니다.
- 로컬 저장이 끝났다면 화면만 이동합니다. outbox는 유지합니다.
- 저장 실패 상태라면 입력을 남기고 원인과 다음 동작을 보여 줍니다.

시스템 뒤로 가기 이벤트에서 SQLite 트랜잭션을 되돌리거나 이미 만든 outbox 명령을 지우지 않습니다.

Android 시스템 뒤로 가기, iOS 대화형 제스처, 헤더의 뒤로 가기 버튼, 모달 닫기가 같은 초안 규칙을 사용하게 합니다. 각 콜백에 별도 확인 코드를 복사하지 않습니다.

## 모달과 경로를 구분합니다

모달이 적합한 작업:

- 사진 소스 선택
- 짧은 필터
- 변경 내용 버리기 확인
- 충돌 선택의 한 단계

경로가 적합한 작업:

- 외부 링크로 열 수 있는 기록 상세
- 여러 단계 편집
- 독립된 뒤로 가기 목록이 필요한 작업
- 알림으로 직접 열어야 하는 화면

복원이 필요한 모달을 전역 불리언 하나로만 관리하지 않습니다. 필요한 경우 경로로 표현하거나 다시 시작했을 때 폐기할 일시 작업임을 명확히 합니다.

## 복원 범위를 제한합니다

이전 화면 이동 상태 전체를 그대로 되살리면 다음 문제가 생길 수 있습니다.

- 경로 스키마가 바뀌었습니다.
- 계정이 로그아웃됐습니다.
- 기록이 삭제됐습니다.
- 편집 초안은 실제로 저장되지 않았습니다.
- 이전 모달이 더는 의미가 없습니다.

안정적인 최상위 경로와 기록 ID만 복원하고 현재 데이터베이스와 계정으로 다시 확인합니다. 모르는 복원 스키마 버전은 폐기합니다. 오래된 화면을 열지 않는 것은 실패가 아니라 현재 상태로 돌아가는 정상 동작입니다.

## 관찰할 정보

화면 이동 문제를 좁힐 때 다음 정보를 남길 수 있습니다.

- 앱 버전, 빌드 번호, runtimeVersion
- 소스: 내부, 링크, 알림, 복원
- 정규화한 요청 종류
- 원본 ID가 아닌 제한된 기록 ID 표현
- 데이터베이스와 계정 준비 상태
- 적용, 보류, 중복, 잘못됨, 누락 결과
- 현재 경로와 초안 존재 여부

알림 본문, 인증 정보, 기록 내용 전체를 로그에 남기지 않습니다.

## 검증 시나리오

- 올바른 커스텀 scheme 링크
- Expo 개발 URL
- 허용하지 않은 `https` URL
- 잘못된 퍼센트 인코딩
- 너무 긴 기록 ID
- 존재하지 않는 기록
- 콜드 스타트 링크 + 마이그레이션 지연
- 웜 링크 + 저장하지 않은 초안
- 같은 링크 중복 전달
- 링크와 알림이 같은 경로를 요청함
- 이미 해결된 충돌 알림
- 프로세스 재시작 뒤 복원 대상 삭제
- 뒤로 가기 제스처와 헤더 버튼의 동일한 초안 처리

## 완료 기준

- 경로 매개변수와 외부 링크를 런타임에서 검증합니다.
- 경로와 선택한 기록 ID를 별도의 기준 값으로 중복 저장하지 않습니다.
- 콜드, 웜, 복원에서 필요한 준비 상태를 구분합니다.
- 데이터베이스가 준비되기 전에 기록 경로를 확정하지 않습니다.
- 형식이 잘못된 입력은 대기열에 넣지 않습니다.
- 중복 요청이 같은 화면을 반복해서 열지 않습니다.
- 저장하지 않은 초안이 외부 이동 요청으로 사라지지 않습니다.
- 알림은 현재 저장소 상태를 다시 읽은 뒤 처리합니다.
- 뒤로 가기 동작이 이미 커밋한 기록이나 outbox를 되돌리지 않습니다.
