# 성능식, CPI와 Amdahl의 법칙

성능 개선을 주장하려면 같은 작업을 어떤 지표로 비교했는지 먼저 정해야 합니다. 클록 주파수, 소스 줄 수 또는 한 번 측정한 실행 시간만으로는 원인을 설명할 수 없습니다. 명령 수, CPI, 클록 주기, 메모리 대기와 측정 환경을 나눠 봐야 합니다.

## 학습 목표

- 지연 시간과 처리량을 구분합니다.
- CPU 시간을 명령 수, CPI와 클록 주기로 계산합니다.
- 속도 향상률, Amdahl의 법칙과 AMAT를 올바른 입력으로 사용합니다.
- 정확성 검사와 반복 측정을 포함한 성능 근거를 남깁니다.

## 지연 시간과 처리량

### 지연 시간

작업 하나가 시작해서 끝날 때까지 걸린 시간입니다.

### 처리량

단위 시간에 완료한 작업 수입니다.

파이프라인은 여러 작업을 겹쳐 처리량을 높일 수 있지만 작업 하나의 지연 시간을 줄이지 않을 수 있습니다. 두 지표는 서로 대신할 수 없습니다.

## CPU 실행 시간

대표적인 분해식은 다음과 같습니다.

```text
CPU time
= instruction count × cycles per instruction × clock cycle time
= instruction count × CPI / clock frequency
```

세 항은 서로 영향을 줍니다.

- 복잡한 명령은 명령 수를 줄여도 CPI나 클록 주기를 늘릴 수 있습니다.
- 더 깊은 파이프라인은 주파수를 높일 수 있지만 분기 예측 실패 비용을 키울 수 있습니다.
- 벡터화는 명령 수를 줄여도 메모리 대역폭이 병목이면 전체 시간을 크게 줄이지 못할 수 있습니다.

```sh
cd exercises/processor-model
python3 processor-model.py perf cpu \
  --instructions 1000000000 --cpi 2 --ghz 2
```

위 입력은 `2×10^9 cycles / 2×10^9 cycles/s = 1s`입니다.

## 평균 CPI

명령 종류별 비율과 CPI가 주어지면 가중 평균을 계산할 수 있습니다.

```text
average CPI = Σ(instruction fraction_i × CPI_i)
```

| 종류 | 비율 | CPI |
| --- | ---: | ---: |
| ALU | 50% | 1 |
| 적재·저장 | 30% | 2 |
| 분기 | 20% | 3 |

```text
0.5×1 + 0.3×2 + 0.2×3 = 1.7
```

현대 비순차 프로세서의 CPI는 명령별 고정 비용을 단순히 더한 값보다 복잡합니다. 캐시 실패, 데이터 의존성, 분기 예측 실패와 실행 포트 경쟁이 겹칠 수 있습니다. 위 계산은 원인을 나누는 첫 모델이지 특정 CPU의 정확한 실행 시간 모델이 아닙니다.

## IPC와 CPI

같은 측정 구간에서 완료한 명령 수를 사용하면 다음 관계가 있습니다.

```text
IPC = instruction count / cycles
CPI = cycles / instruction count
```

명령 수가 0이 아니면 서로 역수입니다. 슈퍼스칼라 프로세서는 한 사이클에 여러 명령을 상태에 반영할 수 있으므로 IPC가 1보다 클 수 있습니다.

## 경과 시간과 CPU 시간

프로그램의 경과 시간에는 다음이 섞일 수 있습니다.

- CPU에서 실제로 실행한 시간
- 스케줄러에게 CPU를 받지 못한 시간
- 저장장치·네트워크 I/O 대기
- 페이지 폴트 처리
- 다른 프로세스와 자원 경쟁
- 타이머 대기

질문에 맞는 지표를 골라야 합니다.

| 질문 | 먼저 확인할 값 |
| --- | --- |
| 계산 함수의 CPU 비용 | CPU 시간, 사이클 수, 명령 수 |
| 사용자가 기다린 시간 | 단조 증가 시계로 측정한 경과 시간과 분포 |
| 서버 수용량 | 처리량, CPU 사용률, 큐 길이 |
| 메모리 영향 | 캐시·TLB 사건, 대역폭과 정지 관련 계수기 |

## 속도 향상률

```text
speedup = old time / new time
```

기존 10초, 변경 후 8초라면 속도 향상률은 `1.25x`이고 실행 시간 감소율은 20%입니다. “25% 빨라졌습니다”와 “시간이 20% 줄었습니다”를 같은 수치처럼 사용하지 않습니다.

비교할 때는 다음 조건을 고정합니다.

- 입력과 결과
- 컴파일러와 주요 옵션
- 스레드 수와 CPU 배치
- 준비 실행과 반복 방법
- 측정 구간
- 정확성 검사

결과가 달라졌다면 단순한 성능 비교가 아닙니다.

## Amdahl의 법칙

전체 시간에서 개선할 수 있는 비율을 `f`, 그 부분의 속도 향상률을 `s`라고 하면 다음과 같습니다.

```text
overall speedup = 1 / ((1 - f) + f / s)
```

전체의 40%만 8배 빨라지는 경우를 계산할 수 있습니다.

```sh
python3 processor-model.py perf amdahl --fraction 0.4 --speedup 8
```

개선할 수 있는 부분을 무한히 빠르게 만들어도 전체 속도 향상률의 상한은 `1 / (1-f)`입니다. Amdahl의 법칙은 병렬화가 무의미하다는 뜻이 아니라 실제로 시간이 걸리는 부분을 프로파일로 확인해야 한다는 뜻입니다.

## AMAT

단일 캐시 수준의 평균 접근 시간은 다음처럼 근사합니다.

```text
AMAT = hit time + miss rate × miss penalty
```

```sh
python3 processor-model.py perf amat \
  --hit-time 1 --miss-rate 0.05 --miss-penalty 80
```

다단계 캐시에서는 식을 중첩할 수 있습니다.

```text
AMAT = L1 hit time
     + L1 miss rate × (L2 hit time + L2 miss rate × memory penalty)
```

L2 실패율이 L2에 도달한 접근 중 실패한 비율인지, 전체 접근 대비 비율인지 확인해야 합니다. 분모가 다른 값을 같은 식에 넣으면 결과가 틀립니다.

비순차 코어는 여러 캐시 실패의 대기를 겹칠 수 있습니다. 따라서 AMAT가 곧 프로그램 전체 정지 시간은 아닙니다. 대역폭이 포화되면 독립적인 실패도 서로 기다릴 수 있습니다.

## 벤치마크를 만들 때 확인할 사항

### 계산 결과를 사용합니다

컴파일러가 계산 전체를 제거하지 못하도록 검사 합계 또는 외부에서 확인할 수 있는 결과를 남깁니다. 비교하는 두 구현은 같은 결과를 만들어야 합니다.

### 단조 증가 시계를 사용합니다

경과 시간에는 시스템 시각 조정의 영향을 받지 않는 시계를 사용합니다. 측정 구간이 너무 짧으면 타이머 호출 비용과 해상도가 결과를 가릴 수 있습니다.

### 여러 번 실행합니다

한 번의 결과만 남기지 않고 분포와 이상치를 확인합니다. 주파수 조절, 열 제한, CPU 이동과 다른 프로세스가 결과를 흔들 수 있습니다.

### 실행 순서를 바꿉니다

항상 A 다음 B를 실행하면 캐시 준비와 온도 상태가 한쪽에 유리할 수 있습니다. `A→B`, `B→A`를 바꾸거나 프로세스를 분리합니다.

### 작업 집합을 기록합니다

작은 입력은 상위 캐시에 들어가고 큰 입력은 메모리 대역폭을 사용할 수 있습니다. 어떤 구간을 관찰하려는지 먼저 정합니다.

## 컴파일러가 만든 명령을 확인합니다

같은 소스라도 최적화 옵션에 따라 다음이 달라집니다.

- 반복문 펼치기
- 벡터화
- 함수 인라인
- 분기 제거
- 상수 접기
- 명령 선택

[분기 벤치마크](../../examples/branch-benchmark/)는 소스의 `if`가 실제 분기로 남는지 확인하는 예제입니다. [벡터화 보고서](../../examples/vectorization-report/)는 컴파일러가 반복문 변환 성공·실패 이유를 출력하는 방법을 보여 줍니다.

“분기 예측기가 빨랐습니다”라고 결론 내리기 전에 실제 분기 명령이 남아 있는지 확인해야 합니다.

## 하드웨어 계수기

Linux에서 `perf stat` 사용 권한이 있다면 다음과 같은 사건을 요청할 수 있습니다.

```sh
perf stat -e cycles,instructions,branches,branch-misses ./program
```

사건 지원 여부와 의미는 CPU와 커널 설정에 따라 다릅니다. 다음을 확인합니다.

1. 요청한 사건을 실제로 지원합니까?
2. 계수기가 다중화되었습니까?
3. 사용자 코드, 커널, 프로세스 또는 시스템 전체 가운데 어느 범위입니까?
4. 파생 비율의 분모가 같은 측정 구간입니까?
5. 소스, 어셈블리와 입력 패턴이 일치합니까?

캐시 실패가 늘었다는 사실만으로 경과 시간 증가가 모두 그 실패 때문이라고 단정할 수 없습니다.

1. 주파수가 20% 늘고 CPI가 15% 늘었을 때 실행 시간이 실제로 줄어드는지 계산해 보세요.
