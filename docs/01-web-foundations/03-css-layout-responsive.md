# CSS 레이아웃과 반응형 화면

반응형 화면은 특정 기기 이름이나 해상도 목록에 맞춰 미디어 쿼리를 계속 추가하는 방식으로 만드는 것이 아닙니다.

핵심은 다음과 같습니다.

- 요소가 사용할 수 있는 공간에 맞춰 자연스럽게 줄어듭니다.
- 콘텐츠가 길어져도 레이아웃이 깨지지 않습니다.
- 화면이 좁아졌을 때 실제로 배치가 어려워지는 지점에서만 구조를 바꿉니다.
- 글자 크기나 브라우저 확대율이 커져도 기능을 사용할 수 있어야 합니다.

즉 "아이폰이면 이렇게, 태블릿이면 저렇게"보다 **현재 컨테이너에 실제로 얼마나 공간이 있는가**를 기준으로 설계하는 것이 중요합니다.

이 문서는 화면 배치를 구현하기 직전에 읽는 JIT 문서입니다.

## 목표

- CSS 캐스케이드와 박스 모델이 레이아웃에 어떤 영향을 주는지 설명합니다.
- 일반 문서 흐름, Flexbox, Grid를 상황에 맞게 선택합니다.
- 요소가 작은 화면에서도 줄어들 수 있도록 최소 크기를 조정합니다.
- 긴 문자열, 320px 화면, 200% 확대에서 레이아웃을 확인합니다.
- 포커스 표시와 사용자의 모션 감소 설정을 보존합니다.
- 특정 기기 이름이 아니라 실제 레이아웃이 깨지는 지점에서 브레이크포인트를 정합니다.

## 먼저 이해할 것: 캐스케이드

CSS에서는 하나의 요소에 여러 규칙이 동시에 적용될 수 있습니다.

```css
button {
  padding: .5rem 1rem;
}

.toolbar button {
  padding: .75rem 1rem;
}
```

이 경우 두 규칙이 모두 `button`에 해당하지만 최종적으로 어떤 값이 적용될지는 **캐스케이드(cascade)** 규칙이 결정합니다.

캐스케이드는 대략 다음 요소를 함께 고려합니다.

- 선언의 중요도
- 선택자의 구체성(specificity)
- 규칙이 선언된 순서
- 상속 여부

레이아웃이 예상과 다르게 보일 때는 "이 속성을 썼는가"만 보지 말고 **최종 계산된 스타일이 무엇인지** 확인해야 합니다.

브라우저 개발자 도구의 Styles 또는 Computed 패널에서 실제 적용값을 확인할 수 있습니다.

예를 들어 다음 두 규칙이 있다면

```css
.card {
  width: 100%;
}

.sidebar .card {
  width: 20rem;
}
```

`.sidebar .card`가 더 구체적이므로 사이드바 안의 카드에는 `20rem`이 적용될 수 있습니다.

반응형 CSS에서도 같은 문제가 생길 수 있습니다.

```css
.form-row {
  flex-direction: row;
}

@media (max-width: 30rem) {
  .form-row {
    flex-direction: column;
  }
}
```

미디어 쿼리 안의 규칙이 조건에 맞고 같은 수준의 구체성을 가진다면 뒤에 선언된 `column`이 적용됩니다.

따라서 반응형 문제를 디버깅할 때는 다음을 확인합니다.

```text
1. 원하는 미디어 쿼리가 실제로 활성화되었는가?
2. 해당 속성이 다른 규칙에 덮어써지지 않았는가?
3. 최종 계산값이 무엇인가?
```

## 박스 모델

HTML 요소는 단순한 하나의 직사각형 너비만 가지는 것이 아닙니다.

기본적인 박스 모델은 다음 네 부분으로 구성됩니다.

```text
margin
┌─────────────────────────────┐
│ border                      │
│ ┌─────────────────────────┐ │
│ │ padding                 │ │
│ │ ┌─────────────────────┐ │ │
│ │ │ content             │ │ │
│ │ └─────────────────────┘ │ │
│ └─────────────────────────┘ │
└─────────────────────────────┘
```

- `content`: 실제 내용 영역
- `padding`: 내용과 테두리 사이의 내부 여백
- `border`: 요소의 테두리
- `margin`: 요소 바깥쪽의 간격

기본 박스 계산 방식에서는 `width`가 콘텐츠 영역만 가리킬 수 있습니다.

예를 들어 다음 요소를 생각해 봅니다.

```css
input {
  width: 100%;
  padding: 1rem;
  border: 1px solid;
}
```

기본 `content-box`에서는 `width: 100%`에 `padding`과 `border`가 추가되므로 부모보다 실제 박스가 더 넓어질 수 있습니다.

그래서 프로젝트 전체에 다음 규칙을 두는 경우가 많습니다.

```css
*,
*::before,
*::after {
  box-sizing: border-box;
}
```

`border-box`에서는 선언한 `width`와 `height` 안에 `padding`과 `border`가 포함됩니다.

예를 들어

```css
.box {
  box-sizing: border-box;
  width: 300px;
  padding: 20px;
  border: 2px solid;
}
```

전체 바깥 너비는 여전히 `300px`입니다. 실제 콘텐츠 영역은 그 안에서 `padding`과 `border`를 제외한 만큼 줄어듭니다.

```text
content-box
width = content 너비

border-box
width = content + padding + border를 포함한 바깥 박스 너비
```

반응형 레이아웃에서는 `border-box`가 전체 크기를 예측하기 쉽기 때문에 자주 사용됩니다.

## 일반 문서 흐름부터 사용합니다

브라우저는 별도의 레이아웃 지시가 없어도 HTML을 기본적인 **일반 문서 흐름(normal flow)** 에 따라 배치합니다.

블록 요소는 보통 문서 순서대로 세로로 쌓이고, 텍스트는 사용할 수 있는 너비에 맞춰 줄바꿈됩니다.

```html
<h1>제목</h1>
<p>본문입니다.</p>
<p>다음 문단입니다.</p>
```

별도의 좌표 계산 없이도 읽을 수 있는 문서가 만들어집니다.

반응형 화면을 만들 때는 먼저 일반 흐름만으로도 콘텐츠가 읽히도록 구성하고, 정말 정렬이나 다열 배치가 필요한 부분에만 Flexbox나 Grid를 추가하는 편이 안전합니다.

### 절대 위치를 기본 레이아웃으로 사용하지 않습니다

다음처럼 모든 요소의 좌표를 직접 지정하면 초기 화면은 맞아 보일 수 있습니다.

```css
.title {
  position: absolute;
  left: 40px;
  top: 20px;
}

.actions {
  position: absolute;
  right: 40px;
  top: 20px;
}
```

하지만 다음 조건이 생기면 서로 겹치기 쉽습니다.

- 제목이 길어짐
- 번역으로 텍스트 길이가 늘어남
- 시스템 글자 크기가 커짐
- 브라우저 확대율이 올라감
- 컨테이너 너비가 작아짐

절대 위치는 일반 문서 흐름에서 요소를 빼므로 주변 요소가 해당 요소의 크기를 자연스럽게 고려하지 못합니다.

따라서 일반적인 페이지 구조는 먼저 일반 흐름, Flexbox, Grid로 만들고, 겹쳐 배치해야 하는 UI처럼 실제로 필요한 경우에만 `position: absolute`를 사용합니다.

## Flexbox와 Grid 선택하기

Flexbox와 Grid는 모두 강력한 레이아웃 도구지만 사용하는 관점이 다릅니다.

### Flexbox

Flexbox는 주로 **한 방향의 흐름**을 정렬할 때 적합합니다.

```css
.toolbar {
  display: flex;
  align-items: center;
  justify-content: space-between;
  gap: .75rem;
}
```

예를 들어 다음과 같은 UI에 잘 맞습니다.

- 툴바
- 버튼 묶음
- 아이콘과 텍스트
- 한 줄의 입력과 버튼
- 세로로 쌓인 패널

Flexbox에는 주축(main axis)과 교차축(cross axis)이 있습니다.

기본값인

```css
flex-direction: row;
```

에서는 다음과 같이 생각할 수 있습니다.

```text
주축      → → →
교차축    ↓
```

`justify-content`는 주축 방향 배치를 조절하고, `align-items`는 교차축 방향 정렬을 조절합니다.

```css
.toolbar {
  display: flex;
  justify-content: space-between;
  align-items: center;
}
```

### Grid

Grid는 **행과 열을 함께 관리해야 하는 2차원 배치**에 적합합니다.

반복되는 카드 목록을 예로 들 수 있습니다.

```css
.cards {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(min(100%, 18rem), 1fr));
  gap: 1rem;
}
```

이 규칙은 공간이 충분하면 여러 열을 만들고, 공간이 부족하면 열 수를 줄입니다.

### `repeat(auto-fit, ...)`

다음 부분은 가능한 만큼 반복 열을 만듭니다.

```css
repeat(auto-fit, ...)
```

`auto-fit`은 현재 컨테이너에 들어갈 수 있는 열 수를 브라우저가 계산하도록 합니다.

### `minmax()`

다음은 각 열의 최소·최대 크기를 지정합니다.

```css
minmax(min(100%, 18rem), 1fr)
```

최소 크기는

```css
min(100%, 18rem)
```

입니다.

컨테이너가 `18rem`보다 넓으면 최소 `18rem`을 사용하고, 컨테이너가 더 작으면 `100%`를 사용합니다.

그래서 작은 화면에서 "열의 최소 너비가 18rem이라서 컨테이너 밖으로 넘치는 문제"를 피할 수 있습니다.

최대 크기인

```css
1fr
```

은 사용 가능한 Grid 공간을 열끼리 나누어 사용한다는 뜻입니다.

### 선택 기준

대략 다음처럼 판단할 수 있습니다.

```text
한 방향 정렬이 핵심인가?
→ Flexbox

행과 열을 함께 맞춰야 하는가?
→ Grid

별도 레이아웃이 없어도 읽기 좋은가?
→ 일반 흐름 유지
```

둘 중 하나가 항상 더 좋은 것은 아닙니다. 한 컴포넌트 안에서 Grid와 Flexbox를 함께 사용할 수도 있습니다.

예를 들어 바깥 카드 목록은 Grid, 각 카드의 버튼 행은 Flexbox로 만들 수 있습니다.

## Flexbox에서 줄어들지 않는 요소

Flexbox 자식은 기본적으로 콘텐츠가 필요하다고 판단하는 최소 너비보다 작아지지 않을 수 있습니다.

예를 들어 다음 구조가 있다고 가정합니다.

```html
<div class="row">
  <div class="card-title">
    매우매우매우긴공백없는문자열...
  </div>
  <button type="button">열기</button>
</div>
```

```css
.row {
  display: flex;
}
```

긴 문자열 때문에 `.card-title`이 예상보다 작아지지 않으면 전체 행이 컨테이너 밖으로 밀려날 수 있습니다.

이때 자식이 실제로 축소될 수 있도록 다음과 같이 지정할 수 있습니다.

```css
.card-title {
  min-width: 0;
  overflow-wrap: anywhere;
}
```

### 왜 `min-width: 0`이 필요한가

Flex item의 자동 최소 크기 때문에 콘텐츠가 긴 경우 요소가 기대만큼 줄어들지 않을 수 있습니다.

`min-width: 0`은 해당 요소가 콘텐츠의 자연스러운 최소 너비보다 더 작아질 수 있도록 허용합니다.

즉 다음은 서로 다른 문제를 해결합니다.

```css
min-width: 0;
```

→ Flex item 자체가 줄어들 수 있게 합니다.

```css
overflow-wrap: anywhere;
```

→ 공백이 없는 긴 문자열도 필요하면 줄바꿈할 수 있게 합니다.

둘을 함께 쓰면 긴 URL, 해시, 사용자 입력 제목 같은 콘텐츠 때문에 레이아웃이 밀리는 문제를 줄일 수 있습니다.

## Grid에서도 최소 크기를 확인합니다

Grid item에서도 콘텐츠의 최소 너비 때문에 예상치 못한 넘침이 생길 수 있습니다.

예를 들어 다음처럼 열을 정의했다고 해도

```css
.layout {
  display: grid;
  grid-template-columns: 1fr 1fr;
}
```

자식 안에 매우 긴 콘텐츠가 있으면 열이 기대보다 줄어들지 않을 수 있습니다.

필요하다면 다음처럼 최소 크기를 명시할 수 있습니다.

```css
.panel {
  min-width: 0;
}
```

또는 열 정의 자체를 다음처럼 작성하는 경우도 있습니다.

```css
.layout {
  display: grid;
  grid-template-columns: minmax(0, 1fr) minmax(0, 1fr);
}
```

`minmax(0, 1fr)`은 각 열이 필요하면 0까지 줄어들 수 있도록 최소 크기를 명시합니다.

## 긴 콘텐츠로 테스트합니다

짧고 보기 좋은 예제만 사용하면 실제 문제를 놓치기 쉽습니다.

예를 들어 다음을 테스트 데이터로 사용합니다.

```text
https://example.com/aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
```

또는

```text
AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
```

다음과 같은 사용자 입력도 고려합니다.

```text
회의록_2026년_프로젝트_최종_최종_정말최종_검토용_문서
```

긴 콘텐츠 테스트에서 확인할 것은 다음과 같습니다.

- 카드가 컨테이너 밖으로 밀리지 않는가?
- 버튼이 화면 밖으로 사라지지 않는가?
- 텍스트가 필요한 위치에서 줄바꿈되는가?
- 전체 페이지에 가로 스크롤이 생기지 않는가?

## 유연한 너비

페이지 전체 콘텐츠에 읽기 좋은 최대 너비를 둘 수 있습니다.

```css
main {
  width: min(70rem, calc(100% - 2rem));
  margin-inline: auto;
}
```

이 규칙을 부분별로 보면 다음과 같습니다.

```css
calc(100% - 2rem)
```

은 화면 양쪽에 총 `2rem`의 여유를 남기면서 컨테이너가 현재 너비를 따라 줄어들게 합니다.

```css
min(70rem, ...)
```

은 아무리 큰 화면이라도 콘텐츠 너비가 `70rem`보다 커지지 않게 합니다.

결과적으로 다음처럼 동작합니다.

```text
작은 화면
→ 화면 크기에 맞춰 줄어듦

큰 화면
→ 최대 70rem까지만 넓어짐
```

`margin-inline: auto`는 남는 가로 공간을 양쪽으로 나눠 가운데 정렬합니다.

## 고정 너비보다 최소·최대 너비를 활용합니다

다음처럼 항상 고정 너비를 사용하면

```css
.panel {
  width: 800px;
}
```

800px보다 좁은 화면에서 넘침이 생길 수 있습니다.

대신 다음과 같이 최대 크기를 제한하고 실제 너비는 컨테이너에 맞추는 방식이 더 유연합니다.

```css
.panel {
  width: 100%;
  max-width: 50rem;
}
```

또는 한 줄로 다음처럼 작성할 수 있습니다.

```css
.panel {
  width: min(100%, 50rem);
}
```

고정 크기가 항상 나쁜 것은 아닙니다. 아이콘, 작은 썸네일처럼 실제로 일정한 크기가 필요한 요소도 있습니다.

문제는 **페이지의 주요 레이아웃 전체를 고정 픽셀 너비에 의존하는 것**입니다.

## `rem`을 사용하는 이유

`rem`은 루트 요소의 글자 크기를 기준으로 하는 단위입니다.

```css
.card {
  padding: 1rem;
}
```

기본 글자 크기가 16px인 환경에서는 `1rem`이 흔히 16px에 해당하지만, 중요한 점은 절대 숫자 자체가 아닙니다.

사용자나 브라우저가 기본 글자 크기를 변경하면 `rem` 기반 크기도 함께 변할 수 있습니다.

따라서 텍스트와 밀접한 간격, 최대 읽기 너비, 브레이크포인트 등에 `rem`을 사용하면 글자 크기 변화와 더 잘 어울리는 경우가 많습니다.

다만 모든 값을 반드시 `rem`으로 바꿔야 한다는 뜻은 아닙니다. 1px 테두리처럼 픽셀이 자연스러운 경우도 있습니다.

## 작은 화면에서 구조 바꾸기

다음 폼 행을 생각해 봅니다.

```html
<div class="form-row">
  <input type="search" />
  <button type="submit">검색</button>
</div>
```

넓은 공간에서는 한 줄 배치가 자연스럽습니다.

```css
.form-row {
  display: flex;
  gap: .5rem;
}

.form-row input {
  min-width: 0;
  flex: 1;
}
```

하지만 공간이 너무 좁아지면 입력과 버튼이 함께 들어가기 어려울 수 있습니다.

이때 실제로 배치가 깨지는 지점에서 방향을 바꿉니다.

```css
@media (max-width: 30rem) {
  .form-row {
    flex-direction: column;
  }
}
```

이 브레이크포인트의 의미는 "어떤 휴대전화 모델의 너비가 30rem이다"가 아닙니다.

다음 질문에 대한 답이어야 합니다.

```text
이 레이아웃이 어느 너비부터 한 줄로 읽기 어려워지는가?
```

실제 콘텐츠를 넣고 창 너비를 줄여 보면서 결정합니다.

## 기기 이름보다 레이아웃을 기준으로 합니다

다음과 같은 사고방식은 유지보수가 어렵습니다.

```text
아이폰 → 390px
태블릿 → 768px
노트북 → 1440px
```

실제 화면에는 더 다양한 조건이 존재합니다.

- 브라우저 창을 반만 사용
- 분할 화면
- 사이드바가 열린 상태
- 브라우저 확대 200%
- 시스템 글자 크기 증가
- 긴 번역 문자열

따라서 같은 기기라도 사용 가능한 CSS 공간은 달라질 수 있습니다.

브레이크포인트는 특정 제품 이름이 아니라 **콘텐츠와 레이아웃이 요구하는 공간**을 기준으로 정합니다.

## `100%`와 `100vw`는 다릅니다

다음 두 값은 같은 의미가 아닙니다.

```css
width: 100%;
width: 100vw;
```

`100%`는 일반적으로 부모 컨테이너의 사용 가능한 너비를 기준으로 계산됩니다.

`100vw`는 뷰포트 너비를 기준으로 합니다.

환경에 따라 `100vw`가 세로 스크롤바 영역까지 포함하여 계산될 수 있으므로 다음처럼 페이지 전체 컨테이너에 무조건 사용하면 의도하지 않은 가로 스크롤의 원인이 될 수 있습니다.

```css
.page {
  width: 100vw;
}
```

대부분의 일반적인 블록 요소는 기본적으로 사용 가능한 부모 너비를 채우므로 아예 `width`가 필요하지 않을 때도 많습니다.

```css
.page {
  /* width를 별도로 지정하지 않아도 되는지 먼저 확인합니다. */
}
```

## 가로 스크롤을 없애기 전에 원인을 찾습니다

레이아웃이 넘칠 때 다음처럼 전체 페이지를 숨겨 버리는 방식은 문제를 가릴 수 있습니다.

```css
html,
body {
  overflow-x: hidden;
}
```

이렇게 하면 실제로 화면 밖에 있는 콘텐츠나 포커스 표시가 단순히 잘릴 수 있습니다.

먼저 어떤 요소가 넘치는지 찾습니다.

흔한 원인은 다음과 같습니다.

- 고정 `width`
- 지나치게 큰 `min-width`
- 긴 공백 없는 문자열
- Flex/Grid item의 자동 최소 크기
- `100vw`
- 절대 위치 요소
- 큰 `transform`
- 이미지나 미디어의 고정 크기

원인을 수정한 뒤 정말 필요한 컴포넌트에만 `overflow`를 적용합니다.

## 이미지와 미디어도 컨테이너를 넘지 않게 합니다

큰 이미지가 원본 크기로 렌더링되면 작은 화면에서 가로 넘침을 만들 수 있습니다.

일반적인 콘텐츠 이미지에는 다음 같은 규칙을 사용할 수 있습니다.

```css
img,
video {
  max-width: 100%;
  height: auto;
}
```

이렇게 하면 원본 크기보다 반드시 커지는 것은 아니지만 부모 컨테이너보다 넓어지는 일을 줄일 수 있습니다.

모든 이미지에 동일한 규칙이 적절한지는 프로젝트 구조에 따라 확인해야 합니다.

## 화면 확대와 반응형 레이아웃

브라우저 확대는 단순히 그림을 크게 보여 주는 것과 다릅니다.

확대율이 높아지면 한 화면에 들어가는 CSS 기준 공간이 줄어들 수 있으므로 데스크톱에서도 모바일과 비슷한 레이아웃 문제가 나타날 수 있습니다.

따라서 반응형 테스트는 다음만으로 끝내면 안 됩니다.

```text
모바일 화면 너비 확인
```

다음도 확인합니다.

```text
데스크톱 창 + 브라우저 확대 200%
```

이때 확인할 것은 다음과 같습니다.

- 텍스트가 잘리지 않는가?
- 버튼이 서로 겹치지 않는가?
- 폼 입력과 버튼을 모두 사용할 수 있는가?
- 필요한 콘텐츠가 화면 밖에 고정되어 있지 않은가?
- 가로 스크롤 때문에 핵심 기능을 찾기 어렵지 않은가?

## 확인할 조건

최소한 다음 상황을 직접 확인합니다.

- CSS 픽셀 기준 너비 320px
- 브라우저 확대 200%
- 긴 제목
- 공백 없는 긴 문자열
- 빈 목록
- 매우 많은 목록 항목
- 시스템 글자 크기 증가
- 키보드 포커스 표시
- 비동기 오류 메시지처럼 예상보다 긴 텍스트
- 페이지 전체의 의도하지 않은 가로 스크롤

Canvas, 넓은 데이터 표, 코드 편집기처럼 본질적으로 가로 공간이 필요한 UI는 별도의 가로 스크롤 영역을 가질 수 있습니다.

중요한 것은 **페이지 전체가 의도치 않게 가로로 밀리지 않는 것**입니다.

## 간단한 가로 넘침 검사

개발자 도구 Console에서 다음 검사를 사용할 수 있습니다.

```js
document.documentElement.scrollWidth <=
  document.documentElement.clientWidth
```

결과가 `true`이면 문서 전체의 스크롤 가능한 너비가 현재 표시 너비보다 크지 않다는 뜻입니다.

`false`이면 문서 전체에 가로 넘침이 있을 가능성이 있습니다.

다만 이 검사는 다음을 알려 주지는 않습니다.

- 어떤 요소가 넘치는가
- 가로 스크롤이 의도된 것인가
- 디자인이 읽기 좋은가
- 버튼과 텍스트가 겹치는가

따라서 자동 검사는 출발점일 뿐이고 실제 화면도 함께 확인해야 합니다.

## 포커스 표시가 잘리지 않게 합니다

키보드 사용자는 포커스 윤곽선을 통해 현재 위치를 파악합니다.

예를 들어 다음처럼 포커스 표시를 만들 수 있습니다.

```css
:focus-visible {
  outline: 3px solid currentColor;
  outline-offset: 3px;
}
```

하지만 부모 요소에 다음과 같은 규칙이 있으면

```css
.card {
  overflow: hidden;
}
```

자식 요소의 바깥쪽 포커스 윤곽선이 잘릴 수 있습니다.

따라서 `overflow: hidden`을 단순한 레이아웃 수정 도구로 사용하지 말고, 실제로 내용 자르기가 필요한지 확인합니다.

포커스 표시를 직접 만들었다면 다음 조건에서 확인합니다.

- 카드 가장자리
- 모달 내부
- 스크롤 컨테이너
- 작은 화면
- 200% 확대

## CSS `order`와 읽기 순서

Flexbox와 Grid에서는 `order`를 사용해 화면에 보이는 순서를 바꿀 수 있습니다.

```css
.secondary {
  order: -1;
}
```

그러나 CSS로 보이는 순서를 바꿔도 DOM 순서 자체는 그대로입니다.

예를 들어 DOM이 다음과 같다면

```html
<button>첫 번째</button>
<button class="secondary">두 번째</button>
```

CSS로 두 번째 버튼을 화면 왼쪽에 먼저 보이게 만들더라도 키보드 포커스 순서나 보조 기술의 읽기 순서는 원래 DOM 구조를 따를 수 있습니다.

그 결과 사용자가 보는 순서와 키보드 이동 순서가 달라질 수 있습니다.

따라서 의미 있는 콘텐츠 순서는 가능한 한 HTML 자체에서 올바르게 구성하고, `order`는 의미를 바꾸지 않는 시각적 조정에 제한적으로 사용합니다.

## 색상과 상태

상태를 색만으로 구분하지 않습니다.

예를 들어 다음 정보가 있다고 가정합니다.

```text
초록색 → 성공
빨간색 → 실패
회색   → 권한 없음
```

색상을 구분하기 어려운 사용자는 상태를 알 수 없습니다.

텍스트를 함께 제공하는 편이 명확합니다.

```html
<p class="status success">저장했습니다.</p>
<p class="status error">저장하지 못했습니다.</p>
```

아이콘만 사용하는 경우에도 보조 기술이 의미를 알 수 있도록 접근 가능한 이름이나 주변 텍스트를 제공합니다.

색상은 상태를 **강조**할 수 있지만 상태의 유일한 전달 수단이 되어서는 안 됩니다.

## 사용자 모션 설정

일부 사용자는 애니메이션이나 큰 움직임에 불편함을 느낄 수 있습니다.

운영체제나 브라우저에서 동작 감소 설정을 사용한 경우 CSS에서 이를 감지할 수 있습니다.

```css
@media (prefers-reduced-motion: reduce) {
  .animated {
    animation: none;
    transition: none;
  }
}
```

이 규칙은 `.animated` 요소에 적용되는 애니메이션과 전환을 제거합니다.

중요한 점은 모든 애니메이션 시간을 전역에서 기계적으로 바꾸는 것이 아니라 **실제로 움직임을 만드는 요소와 기능을 확인해 적용하는 것**입니다.

예를 들어 다음처럼 모든 요소에 전역 규칙을 적용하면

```css
* {
  animation-duration: 0.001ms !important;
}
```

프로젝트에 따라 예상하지 못한 동작을 만들 수 있습니다.

대신 움직임이 있는 컴포넌트를 파악하고 그 컴포넌트에 명시적으로 대응합니다.

## 반응형 폼 예제

다음은 앞의 원칙을 함께 적용한 예입니다.

```html
<main class="page">
  <form class="search-form">
    <label for="query">검색어</label>

    <div class="search-row">
      <input
        id="query"
        name="query"
        type="search"
      />
      <button type="submit">검색</button>
    </div>
  </form>

  <section class="cards">
    <article class="card">
      <h2 class="card-title">
        매우매우매우긴공백없는제목AAAAAAAAAAAAAAAAAAAA
      </h2>
      <p>설명입니다.</p>
    </article>
  </section>
</main>
```

```css
*,
*::before,
*::after {
  box-sizing: border-box;
}

.page {
  width: min(70rem, calc(100% - 2rem));
  margin-inline: auto;
}

.search-row {
  display: flex;
  gap: .5rem;
}

.search-row input {
  min-width: 0;
  flex: 1;
}

.cards {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(min(100%, 18rem), 1fr));
  gap: 1rem;
}

.card {
  min-width: 0;
}

.card-title {
  overflow-wrap: anywhere;
}

@media (max-width: 30rem) {
  .search-row {
    flex-direction: column;
  }
}

@media (prefers-reduced-motion: reduce) {
  .animated {
    animation: none;
    transition: none;
  }
}
```

이 예제에서 중요한 점은 다음과 같습니다.

- 페이지는 최대 너비를 가지지만 작은 화면에서는 함께 줄어듭니다.
- 입력은 Flexbox 안에서 줄어들 수 있도록 `min-width: 0`을 사용합니다.
- 검색 행은 실제로 좁아지는 시점에서 세로로 바뀝니다.
- 카드 열 수는 고정 기기 목록이 아니라 사용 가능한 공간으로 결정됩니다.
- 긴 제목은 카드 바깥으로 밀려나지 않도록 줄바꿈할 수 있습니다.
- 모션 감소 설정을 별도로 처리할 수 있습니다.

## 디버깅 순서

레이아웃이 깨졌을 때 무작정 미디어 쿼리를 추가하기보다 다음 순서로 원인을 찾습니다.

```text
1. 어떤 요소가 실제로 넘치는가?
2. 그 요소의 최종 width / min-width / max-width는 무엇인가?
3. padding과 border가 너비 계산에 포함되는가?
4. Flex/Grid item이 콘텐츠 최소 너비 때문에 줄어들지 않는가?
5. 긴 문자열이나 이미지가 원인인가?
6. 100vw나 고정 px 너비가 사용되었는가?
7. overflow로 문제를 가리고 있지는 않은가?
8. 실제로 구조 변경이 필요한 지점인가?
```

그 후 정말 한 줄 배치를 유지할 수 없는 시점이라면 미디어 쿼리로 구조를 바꿉니다.

```text
넘침 발견
  ↓
원인 크기 확인
  ↓
유연한 크기로 수정 가능한가?
  ├─ 예 → min/max/flex/grid 조정
  └─ 아니오 → 실제 깨지는 지점에서 레이아웃 전환
```

이 순서를 따르면 브레이크포인트가 불필요하게 많아지는 일을 줄일 수 있습니다.

## 직접 확인하기

구현이 끝나면 브라우저 개발자 도구에서 창 너비를 천천히 줄여 봅니다.

특정 기기 프리셋만 클릭하지 말고 **레이아웃이 실제로 어느 지점에서 불편해지는지** 관찰합니다.

다음을 확인합니다.

```text
1. 텍스트가 예상대로 줄바꿈되는가?
2. 입력과 버튼이 컨테이너 밖으로 나가지 않는가?
3. 긴 문자열에서도 카드가 밀리지 않는가?
4. 페이지 전체에 의도하지 않은 가로 스크롤이 없는가?
5. 320px에서도 주요 기능을 사용할 수 있는가?
6. 200% 확대에서도 콘텐츠가 겹치지 않는가?
7. Tab으로 이동할 때 포커스 윤곽선이 잘리지 않는가?
8. reduced motion 설정에서 불필요한 애니메이션이 줄어드는가?
```

반응형 검사는 "예쁜가"만 보는 검사가 아니라 **콘텐츠와 기능이 계속 사용 가능한가**를 확인하는 과정입니다.

## 흔한 실수

- 캐스케이드 때문에 다른 규칙에 덮어써진 값을 확인하지 않고 CSS를 계속 추가합니다.
- 모든 너비를 고정 픽셀로 지정합니다.
- 주요 레이아웃을 절대 위치에 의존해 구성합니다.
- `width: 100%`에 `padding`과 `border`가 더해지는 박스 모델을 놓칩니다.
- Flex item이 줄어들지 않을 때 `min-width: 0`을 확인하지 않습니다.
- Grid item의 콘텐츠 최소 너비 때문에 열이 밀릴 수 있다는 점을 놓칩니다.
- 긴 문자열과 화면 확대를 확인하지 않습니다.
- 이미지나 비디오의 원본 크기가 컨테이너보다 커질 수 있다는 점을 놓칩니다.
- `100vw`가 환경에 따라 스크롤바 영역까지 포함할 수 있다는 점을 놓칩니다.
- 넘침의 원인을 찾지 않고 페이지 전체에 `overflow-x: hidden`을 적용합니다.
- 기기 이름을 기준으로 미디어 쿼리를 계속 추가합니다.
- CSS `order`로 보이는 순서만 바꾸고 키보드 이동 순서는 그대로 둡니다.
- `overflow: hidden`으로 포커스 윤곽선을 잘라 냅니다.
- 색만으로 성공, 실패, 권한 상태를 구분합니다.
- 모션 감소 설정을 무시하거나 모든 애니메이션에 기계적인 전역 해법을 적용합니다.

## 관련 exercise

[`browser-directory`](../../exercises/browser-directory/README.md)는 작은 화면의 검색 폼, 긴 결과 텍스트와 포커스 표시를 검사합니다.

## 완료 기준

다음 내용을 설명하고 직접 확인할 수 있으면 이 문서의 목표를 달성한 것입니다.

- 캐스케이드 때문에 같은 요소의 최종 스타일이 어떻게 결정되는지 설명할 수 있습니다.
- `content-box`와 `border-box`에서 `width`가 의미하는 범위의 차이를 설명할 수 있습니다.
- 일반 문서 흐름, Flexbox, Grid 중 하나를 선택한 이유를 설명할 수 있습니다.
- Flex item이 예상보다 줄어들지 않을 때 `min-width: 0`을 확인할 수 있습니다.
- 긴 공백 없는 문자열도 레이아웃 밖으로 밀리지 않게 처리할 수 있습니다.
- 고정 기기 이름이 아니라 실제 레이아웃이 깨지는 너비에서 브레이크포인트를 정할 수 있습니다.
- 주요 콘텐츠 컨테이너가 작은 화면에서는 줄어들고 큰 화면에서는 지나치게 넓어지지 않게 만들 수 있습니다.
- 320px 화면과 200% 확대에서도 필요한 요소를 사용할 수 있습니다.
- 페이지 전체의 의도하지 않은 가로 스크롤을 찾아 원인을 수정할 수 있습니다.
- 화면 확대와 키보드 포커스 때문에 기능이 가려지거나 잘리지 않게 확인할 수 있습니다.
- 사용자의 `prefers-reduced-motion` 설정을 필요한 애니메이션에 반영할 수 있습니다.
