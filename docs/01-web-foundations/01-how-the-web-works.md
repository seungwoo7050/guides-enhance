# 웹은 어떻게 동작하는가

브라우저 주소창에 URL을 입력하면 브라우저는 먼저 URL을 해석합니다. 그다음 호스트 이름을 실제 네트워크 주소로 찾고, 서버와 연결한 뒤 HTTP 요청을 보냅니다. HTTPS라면 HTTP 요청을 주고받기 전에 TLS 연결도 설정합니다.

서버의 응답이 HTML이면 브라우저는 HTML을 해석해 문서 구조를 만들고, 문서가 참조하는 CSS, JavaScript, 이미지 같은 리소스를 추가로 요청합니다. JavaScript가 JSON API를 호출할 때도 기본 구조는 같습니다. 클라이언트가 HTTP 요청을 보내고 서버가 HTTP 응답을 반환합니다.

처음부터 DNS, TCP, TLS, HTTP의 세부 규칙을 모두 외울 필요는 없습니다. 다만 문제가 생겼을 때 다음 흐름 중 어느 단계에서 실패했는지는 구분할 수 있어야 합니다.

```text
URL 해석
  ↓
호스트 이름 확인
  ↓
서버와 연결
  ↓
HTTPS라면 TLS 설정
  ↓
HTTP 요청
  ↓
HTTP 응답
  ↓
응답 해석과 화면 갱신
```

이 구분을 할 수 있으면 단순히 "페이지가 안 열린다"거나 "API가 실패한다"고만 보지 않고, 주소 문제인지, 연결 문제인지, 서버의 HTTP 오류인지, 응답 해석 문제인지 차례로 좁힐 수 있습니다.

## 목표

- URL의 스킴, 호스트, 포트, 경로, 쿼리, 프래그먼트를 구분합니다.
- 브라우저가 URL을 사용해 서버에 요청하기까지의 큰 흐름을 설명합니다.
- HTTP 요청과 응답의 기본 구조를 읽습니다.
- 연결 실패와 HTTP 오류 응답을 구분합니다.
- HTML, CSS, JavaScript, JSON이 각각 무엇을 전달하는지 설명합니다.
- 브라우저에서 검증한 입력도 서버에서 다시 검증해야 하는 이유를 설명합니다.
- 브라우저 개발자 도구에서 실제 요청과 응답을 확인합니다.

## URL 읽기

다음 URL을 부분별로 나누어 봅니다.

```text
https://example.com:443/boards/42?view=activity#latest
```

| 부분 | 이름 | 의미 |
|---|---|---|
| `https` | 스킴(scheme) | URL이 어떤 방식으로 리소스에 접근하는지를 나타냅니다. `https`는 HTTP 통신을 TLS로 보호한다는 뜻입니다. |
| `example.com` | 호스트(host) | 연결 대상 서버를 식별하는 호스트 이름입니다. |
| `443` | 포트(port) | 같은 호스트에서 어떤 네트워크 서비스에 연결할지를 구분하는 번호입니다. |
| `/boards/42` | 경로(path) | 서버에서 요청할 리소스나 처리 대상을 나타냅니다. |
| `view=activity` | 쿼리 문자열(query string) | 경로 뒤에 추가로 전달하는 요청 매개변수입니다. |
| `latest` | 프래그먼트(fragment) | 브라우저 등 클라이언트가 사용하는 문서 내부 위치입니다. HTTP 요청에는 포함되지 않습니다. |

구조로 표시하면 다음과 같습니다.

```text
https://example.com:443/boards/42?view=activity#latest
└─┬─┘   └────┬────┘└┬┘└───┬────┘ └────┬─────┘ └──┬───┘
 scheme      host    port   path         query       fragment
```

### 포트를 생략할 수 있습니다

HTTP와 HTTPS에는 일반적으로 사용하는 기본 포트가 있습니다.

```text
http://example.com       → 기본 포트 80
https://example.com      → 기본 포트 443
```

따라서 다음 두 HTTPS URL은 별도의 설정이 없다면 같은 포트를 가리킵니다.

```text
https://example.com/
https://example.com:443/
```

포트는 "어느 컴퓨터인가"가 아니라 "그 컴퓨터의 어느 네트워크 서비스를 사용할 것인가"를 구분합니다. 같은 컴퓨터에서도 여러 프로그램이 서로 다른 포트를 사용해 동시에 서버로 동작할 수 있습니다.

### `localhost`의 의미

`localhost`는 현재 프로그램이 실행 중인 컴퓨터 자신을 가리키는 호스트 이름입니다.

개발 환경에서는 예를 들어 다음과 같이 서로 다른 프로그램이 실행될 수 있습니다.

```text
http://localhost:3000  → 프런트엔드 개발 서버
http://localhost:4000  → API 서버
localhost:5432         → PostgreSQL의 호스트와 포트를 나타낸 표현
```

`localhost:5432`는 `host:port` 형태의 표현이지 완전한 HTTP URL은 아닙니다. 브라우저에서 HTTP 리소스를 가리키려면 보통 `http://` 또는 `https://` 같은 스킴이 필요합니다.

같은 `localhost`라도 포트가 다르면 서로 다른 연결 대상으로 구분됩니다.

## URL을 입력한 뒤 일어나는 일

다음 주소를 연다고 가정합니다.

```text
https://example.com/boards/42
```

브라우저가 수행하는 일을 큰 단계로 나누면 다음과 같습니다.

### 1. URL을 해석합니다

브라우저는 URL에서 필요한 부분을 분리합니다.

```text
scheme = https
host   = example.com
port   = 443
path   = /boards/42
```

포트가 생략되어 있다면 스킴에 따른 기본 포트를 사용합니다.

### 2. 호스트 이름을 네트워크 주소로 찾습니다

`example.com`과 같은 호스트 이름을 사용하려면 먼저 해당 이름이 가리키는 IP 주소를 찾아야 합니다. 이 과정에는 DNS가 사용됩니다.

```text
example.com
    ↓ DNS
IP 주소
```

DNS 조회에 실패하면 아직 HTTP 요청을 서버에 전달하기 전입니다. 따라서 이 경우에는 서버가 반환한 HTTP 상태 코드도 존재하지 않습니다.

### 3. 서버와 연결합니다

브라우저는 찾은 주소와 포트로 연결을 시도합니다.

HTTPS라면 이어서 TLS 연결을 설정합니다. TLS는 통신 내용을 암호화하고 서버 인증서를 확인하는 등의 역할을 합니다.

해당 주소와 포트에서 서버가 연결을 받아 주지 않으면 다음과 같은 연결 오류가 발생할 수 있습니다.

```text
ERR_CONNECTION_REFUSED
```

이때도 HTTP 응답을 받은 것이 아니므로 `404`나 `500` 같은 상태 코드는 없습니다.

### 4. HTTP 요청을 보냅니다

연결이 준비되면 브라우저가 HTTP 요청을 보냅니다.

HTTP/1.1 형식으로 단순화하면 다음과 같습니다.

```http
GET /boards/42 HTTP/1.1
Host: example.com
Accept: text/html
```

URL에 프래그먼트가 있더라도 프래그먼트는 서버에 보내는 HTTP 요청에 포함되지 않습니다.

```text
브라우저 주소
https://example.com/boards/42#latest

서버에 전달되는 경로
/boards/42
```

### 5. 서버가 HTTP 응답을 보냅니다

서버는 요청을 처리한 뒤 상태 코드, 헤더, 필요하면 본문을 포함한 응답을 보냅니다.

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<h1>게시판</h1>
```

### 6. 브라우저가 응답을 해석합니다

HTML 응답이라면 브라우저는 HTML을 해석해 문서 구조를 만들고, 문서 안에서 추가 리소스를 발견하면 다시 요청합니다.

```html
<link rel="stylesheet" href="/style.css">
<script src="/app.js"></script>
```

이 HTML을 받았다면 브라우저는 이후 다음과 같은 요청을 추가로 보낼 수 있습니다.

```text
GET /style.css
GET /app.js
```

JavaScript가 실행된 뒤 API 요청을 보낼 수도 있습니다.

```text
GET /api/boards/42
```

따라서 웹 페이지 하나를 연다고 해서 HTTP 요청이 하나만 발생하는 것은 아닙니다.

## HTTP 요청과 응답

HTTP는 클라이언트가 요청을 보내고 서버가 응답을 돌려주는 규칙입니다.

브라우저가 대표적인 HTTP 클라이언트이지만 브라우저만 HTTP를 사용할 수 있는 것은 아닙니다. `curl`, 모바일 앱, 다른 서버 프로그램도 HTTP 클라이언트가 될 수 있습니다.

### HTTP 요청

다음은 JSON 데이터를 요청하는 HTTP/1.1 요청의 예입니다.

```http
GET /boards/42 HTTP/1.1
Host: localhost:4000
Accept: application/json
```

요청에는 크게 다음 정보가 들어갑니다.

- 메서드(method): 요청으로 어떤 동작을 원하는지 나타냅니다.
- 요청 대상(request target): 보통 경로와 쿼리 문자열입니다.
- 헤더(header): 요청에 대한 부가 정보를 전달합니다.
- 본문(body): 필요한 경우 서버에 데이터를 전달합니다.

예를 들어 새 데이터를 생성하기 위한 요청은 본문을 포함할 수 있습니다.

```http
POST /boards HTTP/1.1
Host: localhost:4000
Content-Type: application/json

{"title":"학습 보드"}
```

여기서 `Content-Type: application/json`은 요청 본문이 JSON 형식이라는 뜻입니다.

### HTTP 응답

서버의 응답은 다음처럼 구성됩니다.

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"id":"42","title":"학습 보드"}
```

응답에는 크게 다음 정보가 들어갑니다.

- 상태 코드(status code): 요청 처리 결과를 숫자로 나타냅니다.
- 헤더(header): 응답에 대한 부가 정보를 제공합니다.
- 본문(body): 실제 HTML, JSON, 이미지 등의 데이터를 전달합니다.

### 상태 코드의 큰 분류

| 범위 | 의미 | 예 |
|---|---|---|
| `2xx` | 요청이 성공적으로 처리됨 | `200 OK`, `201 Created` |
| `3xx` | 다른 위치나 조건으로 이어지는 처리 | `301 Moved Permanently`, `304 Not Modified` |
| `4xx` | 요청이 서버가 요구하는 조건에 맞지 않음 | `400 Bad Request`, `404 Not Found` |
| `5xx` | 서버가 요청을 처리하는 동안 오류가 발생함 | `500 Internal Server Error` |

상태 코드만으로 정확한 원인을 모두 알 수 있는 것은 아닙니다. 실제 원인을 찾으려면 요청 값, 응답 본문, 서버 로그도 함께 확인해야 합니다.

## 연결 실패와 HTTP 오류 응답은 다릅니다

이 차이는 웹 디버깅에서 매우 중요합니다.

### HTTP 오류 응답

`404`나 `500`은 오류를 나타내는 상태 코드이지만 **HTTP 응답 자체는 정상적으로 도착한 것**입니다.

```text
브라우저
  │
  │ HTTP 요청
  ▼
서버
  │
  │ HTTP/1.1 404 Not Found
  ▼
브라우저
```

즉 다음 과정은 이미 이루어졌습니다.

- 서버의 주소를 찾음
- 서버와 연결함
- HTTP 요청을 전달함
- 서버가 HTTP 응답을 반환함

문제는 응답 결과가 성공이 아니라 오류라는 점입니다.

### 연결 실패

반면 해당 포트에서 서버가 실행되지 않는 등 연결 자체가 실패하면 HTTP 응답을 받을 수 없습니다.

```text
브라우저
  │
  │ 연결 시도
  ▼
localhost:4000
  ✕ 연결을 받아 주는 서버가 없음
```

이 경우 브라우저에는 예를 들어 다음과 같은 네트워크 오류가 나타날 수 있습니다.

```text
ERR_CONNECTION_REFUSED
```

`404`와 연결 거부를 비교하면 다음과 같습니다.

```text
404
브라우저 → 연결 성공 → HTTP 요청 → 서버 → HTTP 404 응답

연결 거부
브라우저 → 연결 시도 → 실패 → HTTP 응답 없음
```

따라서 오류를 볼 때 가장 먼저 다음 질문을 할 수 있습니다.

```text
서버로부터 HTTP 응답을 받았는가?
```

- 받았다면 상태 코드, 응답 헤더, 응답 본문을 확인합니다.
- 받지 못했다면 호스트, DNS, 포트, 서버 실행 상태, TLS 등의 연결 이전 단계를 확인합니다.

## 오류 위치를 구분하기

다음 표는 첫 조사 지점을 정하는 데 사용할 수 있습니다.

| 관찰 결과 | 의미 | 먼저 확인할 곳 |
|---|---|---|
| DNS 관련 오류 | 호스트 이름을 네트워크 주소로 찾지 못함 | 호스트 이름, DNS 설정, 네트워크 |
| `ERR_CONNECTION_REFUSED` | 대상 주소에는 도달했지만 해당 포트에서 연결을 받아 주지 않음 | 서버 프로세스, 포트, 바인딩 주소 |
| TLS/인증서 오류 | HTTPS 연결을 안전하게 설정하지 못함 | 인증서, 도메인, TLS 설정 |
| `400` | 요청 형식이나 값이 서버 요구 조건에 맞지 않음 | 요청 본문, 쿼리, 경로 변수, 헤더 |
| `401` | 인증 정보가 없거나 유효하지 않음 | 로그인 상태, 토큰, 세션 |
| `403` | 서버가 요청을 허용하지 않음 | 사용자 권한, 리소스 접근 정책 |
| `404` | 서버가 요청은 받았지만 해당 경로나 리소스를 찾지 못함 | URL 경로, 라우팅, 리소스 식별자 |
| `500` | 서버가 요청 처리 중 내부 오류를 만남 | 서버 로그, 예외, 요청 ID |
| JSON 파싱 실패 | 받은 본문을 JSON으로 해석하지 못함 | `Content-Type`, 실제 응답 본문 |
| 화면에 이전 데이터가 남음 | 응답 이후 화면 상태 갱신이 잘못되었을 수 있음 | 요청 완료 순서, 캐시, 상태 관리 코드 |

`401`과 `403`의 세부 사용은 서버 설계에 따라 달라질 수 있지만, 일반적으로는 인증 문제와 권한 문제를 구분하는 데 사용됩니다.

## HTML, CSS, JavaScript, JSON의 역할

웹 애플리케이션에서는 서로 다른 목적을 가진 여러 종류의 데이터가 함께 사용됩니다.

### HTML

HTML은 문서의 구조와 의미를 표현합니다.

```html
<h1>내 보드</h1>
<button type="button">새 보드</button>
```

브라우저는 `h1`을 제목으로, `button`을 사용자가 조작할 수 있는 버튼으로 이해합니다.

HTML은 단순히 화면의 모양을 만드는 언어가 아닙니다. 요소의 의미는 브라우저 기본 동작과 접근성에도 영향을 줍니다.

### CSS

CSS는 문서의 표현과 배치를 지정합니다.

```css
button {
  font: inherit;
}
```

글꼴, 크기, 간격, 색상, 정렬, 레이아웃 등을 CSS로 지정할 수 있습니다.

간단히 구분하면 다음과 같습니다.

```text
HTML → 무엇인가, 어떤 순서와 구조인가
CSS  → 어떻게 보이는가
```

### JavaScript

JavaScript는 사용자 입력이나 네트워크 응답 같은 사건에 반응하여 동작을 수행합니다.

```js
document.querySelector("button")?.addEventListener("click", () => {
  console.log("클릭했습니다.");
});
```

JavaScript는 예를 들어 다음과 같은 일을 할 수 있습니다.

- 버튼 클릭 처리
- 화면 요소 변경
- 폼 입력값 확인
- API 요청 전송
- 서버 응답을 화면에 반영

### JSON

JSON은 구조화된 데이터를 텍스트로 표현하는 형식입니다.

```json
{
  "id": "42",
  "title": "학습 보드"
}
```

JSON 자체가 화면 구조나 스타일, 동작을 정의하는 것은 아닙니다. 주로 클라이언트와 서버 사이에서 데이터를 전달할 때 사용합니다.

예를 들어 다음과 같은 흐름이 가능합니다.

```text
브라우저 JavaScript
      │
      │ GET /api/boards/42
      ▼
    서버
      │
      │ JSON 응답
      ▼
브라우저 JavaScript
      │
      ▼
HTML 화면 갱신
```

## 의미 있는 HTML 요소를 먼저 사용합니다

클릭할 수 있다는 이유만으로 모든 요소에 클릭 이벤트를 붙이면 안 됩니다.

다음 코드는 마우스로 클릭할 수는 있지만 원래 버튼이 제공하는 의미와 동작이 없습니다.

```html
<div id="create">새 보드</div>
```

```js
document.querySelector("#create")?.addEventListener("click", createBoard);
```

반면 실제 버튼 요소를 사용하면 브라우저가 버튼에 필요한 여러 기능을 기본으로 제공합니다.

```html
<button type="button">새 보드</button>
```

버튼은 기본적으로 다음과 같은 특성을 갖습니다.

- 키보드로 포커스를 이동할 수 있습니다.
- 키보드로 활성화할 수 있습니다.
- 보조 기술이 버튼으로 인식할 수 있습니다.
- `disabled` 상태를 사용할 수 있습니다.

따라서 브라우저가 이미 제공하는 의미와 동작이 있는 HTML 요소를 먼저 사용합니다.

## 정적 파일과 API 요청

한 화면을 열 때도 여러 요청이 발생합니다.

```text
GET /             → HTML
GET /style.css    → CSS
GET /app.js       → JavaScript
GET /api/boards   → JSON 목록
POST /api/boards  → 서버 데이터 변경 요청
```

앞의 요청들은 화면을 구성하는 파일을 받는 요청이고, 뒤의 요청들은 애플리케이션 데이터를 읽거나 변경하는 API 요청입니다.

그러나 네트워크 관점에서는 모두 HTTP 요청이라는 공통점이 있습니다.

```text
브라우저
  ├─ GET /             → HTML
  ├─ GET /style.css    → CSS
  ├─ GET /app.js       → JavaScript
  └─ GET /api/boards   → JSON
```

프런트엔드와 API가 반드시 같은 프로세스에서 실행되는 것도 아닙니다.

```text
http://localhost:3000
        │
        └─ HTML/CSS/JavaScript를 제공하는 개발 서버

http://localhost:4000
        │
        └─ JSON API를 제공하는 서버
```

포트가 다르면 브라우저 입장에서는 서로 다른 네트워크 대상입니다.

## 개발자 도구의 Network 탭 읽기

브라우저 개발자 도구의 Network 탭에서는 실제로 어떤 요청을 보냈고 어떤 응답을 받았는지 확인할 수 있습니다.

Console 오류만 보지 말고 Network 탭에서 실제 네트워크 사실을 먼저 확인하는 습관이 중요합니다.

### Request URL

실제로 요청한 URL을 확인합니다.

예를 들어 의도한 주소가 다음과 같더라도

```text
http://localhost:4000/api/boards/42
```

실제 요청이 다음으로 나갔을 수 있습니다.

```text
http://localhost:3000/api/boards/42
```

이 경우 API 구현보다 요청 대상 호스트나 포트부터 확인해야 합니다.

### Request Method

실제로 사용한 HTTP 메서드를 확인합니다.

```text
GET
POST
PUT
PATCH
DELETE
```

서버가 `POST /api/boards`만 처리하는데 클라이언트가 `GET /api/boards`를 보냈다면 경로가 같아 보여도 서로 다른 요청입니다.

### Request Headers

요청에 어떤 부가 정보가 포함되었는지 확인합니다.

JSON 본문을 보낼 때는 다음 헤더가 중요할 수 있습니다.

```http
Content-Type: application/json
```

인증이 필요한 요청이라면 인증 관련 헤더나 쿠키가 실제로 전송되었는지도 확인합니다.

### Request Body

`POST`, `PUT`, `PATCH` 요청에서는 실제로 어떤 본문을 서버에 보냈는지 확인합니다.

예를 들어 서버가 다음 형식을 기대한다고 가정합니다.

```json
{
  "title": "학습 보드"
}
```

그런데 실제 요청이 다음과 같다면 서버가 `400`을 반환할 수 있습니다.

```json
{
  "name": "학습 보드"
}
```

### Status Code

서버가 반환한 상태 코드를 확인합니다.

```text
200
201
400
404
500
```

상태 코드는 문제의 위치를 좁히는 첫 단서입니다.

### Response Headers

서버가 응답 본문을 어떤 형식이라고 선언했는지 확인합니다.

```http
Content-Type: application/json
```

이 헤더라면 서버는 본문이 JSON이라고 설명하고 있는 것입니다.

### Response Body

서버가 실제로 반환한 내용을 확인합니다.

JSON을 기대했는데 실제 응답이 HTML 오류 페이지일 수도 있습니다.

```html
<h1>Internal Server Error</h1>
```

이 상태에서 JavaScript가 응답을 JSON으로 해석하려고 하면 JSON 파싱 오류가 발생할 수 있습니다.

### Timing

요청이 시작되고 응답이 완료되기까지 어느 단계에서 시간이 걸렸는지 확인할 수 있습니다.

요청이 오랫동안 끝나지 않는다면 단순한 화면 코드 문제보다 서버 처리 지연이나 네트워크 문제를 조사해야 할 수도 있습니다.

## JSON 파싱 실패를 해석하는 방법

다음 코드를 생각해 봅니다.

```js
const response = await fetch("/api/boards/42");
const board = await response.json();
```

`response.json()`이 실패했다고 해서 곧바로 클라이언트의 JSON 코드가 잘못되었다고 결론 내리면 안 됩니다.

실제 응답 본문이 다음과 같은 HTML일 수도 있습니다.

```html
<!doctype html>
<html>
  <body>404 Not Found</body>
</html>
```

따라서 JSON 파싱 오류가 발생하면 다음 순서로 확인합니다.

```text
1. HTTP 상태 코드는 무엇인가?
2. Content-Type은 무엇인가?
3. 실제 응답 본문은 무엇인가?
4. 정말 JSON이 반환되었는가?
```

오류 메시지의 마지막 단계만 보지 말고 실제 HTTP 응답부터 확인해야 합니다.

## 브라우저의 입력은 신뢰하지 않습니다

브라우저 코드는 사용자의 기기에서 실행됩니다.

화면에서 특정 입력을 막았더라도 사용자는 개발자 도구, `curl`, 별도의 프로그램 등을 사용해 서버에 직접 요청을 보낼 수 있습니다.

예를 들어 화면에 다음 선택지만 있다고 가정합니다.

```html
<select name="role">
  <option value="viewer">viewer</option>
  <option value="editor">editor</option>
</select>
```

화면에 `admin` 선택지가 없더라도 사용자는 직접 다음과 같은 요청을 만들 수 있습니다.

```json
{
  "role": "admin"
}
```

따라서 서버는 요청을 받을 때마다 필요한 조건을 다시 확인해야 합니다.

### 형식을 검증합니다

본문, 경로, 쿼리, 헤더의 형식과 값을 확인합니다.

예를 들어 숫자 식별자를 기대한다면 실제 값이 허용되는 형식인지 확인해야 합니다.

```text
/api/boards/42
/api/boards/abc
```

### 인증 상태를 확인합니다

로그인이 필요한 요청이라면 요청자가 실제로 인증된 상태인지 확인합니다.

세션이나 토큰이 이전에 유효했다고 해서 현재도 항상 유효한 것은 아닙니다.

### 권한을 확인합니다

로그인된 사용자라고 해서 모든 리소스를 읽거나 변경할 수 있는 것은 아닙니다.

예를 들어 다음 요청을 처리하기 전에 서버는 사용자가 `42`번 보드를 수정할 권한이 있는지 확인해야 합니다.

```text
PATCH /api/boards/42
```

### 서버가 결정해야 하는 값은 서버에서 결정합니다

가격, 사용자 역할, 최종 권한처럼 서버가 책임져야 하는 값을 클라이언트가 보낸 그대로 신뢰하면 안 됩니다.

예를 들어 다음 요청이 왔다고 가정합니다.

```json
{
  "productId": "A100",
  "price": 100
}
```

서버가 최종 가격을 결정해야 하는 시스템이라면 클라이언트가 보낸 `price`를 그대로 신뢰하지 않고 `productId`를 기준으로 서버의 신뢰 가능한 데이터에서 가격을 다시 확인해야 합니다.

### 함께 성공해야 하는 변경은 함께 다룹니다

여러 데이터 변경이 하나의 논리적 작업을 구성한다면 일부만 성공하지 않도록 서버와 데이터베이스에서 적절한 원자성 보장이 필요할 수 있습니다.

예를 들어 송금은 다음 두 변경이 하나의 작업을 이룹니다.

```text
A 계좌 금액 감소
B 계좌 금액 증가
```

중간 실패로 한쪽 변경만 남으면 데이터가 일관되지 않을 수 있습니다.

브라우저 검증과 서버 검증은 목적이 다릅니다.

```text
브라우저 검증 → 사용자에게 빠른 피드백 제공
서버 검증     → 실제 데이터와 권한 보호
```

브라우저 검증은 유용하지만 서버 검증을 대신하지 못합니다.

## 직접 확인하기

작은 정적 서버를 실행하고 브라우저 개발자 도구의 Network 탭에서 실제 요청을 관찰합니다.

### 1. 정상 요청을 확인합니다

페이지를 열고 다음과 같은 요청이 발생하는지 확인합니다.

```text
GET /
GET /style.css
GET /app.js
```

각 요청에서 다음 항목을 확인합니다.

- Request URL
- Request Method
- Status Code
- Request Headers
- Response Headers
- Response Body
- Timing

### 2. 404를 확인합니다

존재하지 않는 경로를 요청합니다.

```text
http://localhost:3000/not-found
```

Network 탭에서 서버가 실제로 HTTP 응답을 반환했는지 확인합니다.

```text
Status Code: 404
```

이 경우 서버와의 연결 자체는 성공한 것입니다.

### 3. 연결 실패를 확인합니다

서버를 종료한 뒤 같은 주소를 다시 요청합니다.

이번에는 `404` 같은 HTTP 상태 코드가 아니라 연결 오류가 발생하는지 확인합니다.

```text
ERR_CONNECTION_REFUSED
```

차이를 다시 비교하면 다음과 같습니다.

```text
404
브라우저 → 서버 연결 성공 → 요청 전달 → 404 응답

연결 실패
브라우저 → 서버 연결 시도 → 실패 → HTTP 응답 없음
```

### 4. JSON 응답을 확인합니다

API 서버가 있다면 JSON 응답을 반환하는 요청을 선택합니다.

다음을 확인합니다.

```http
Content-Type: application/json
```

그리고 실제 응답 본문도 JSON인지 확인합니다.

```json
{
  "id": "42",
  "title": "학습 보드"
}
```

## 문제를 추적하는 기본 순서

웹 요청이 실패하면 다음 순서로 조사하면 문제 범위를 빠르게 좁힐 수 있습니다.

```text
1. 요청이 실제로 발생했는가?
2. 요청 URL과 메서드가 의도한 값인가?
3. 요청 헤더와 본문이 의도한 값인가?
4. 서버와 연결되었는가?
5. HTTP 상태 코드는 무엇인가?
6. 응답 Content-Type은 무엇인가?
7. 실제 응답 본문은 무엇인가?
8. 서버 로그에는 어떤 기록이 있는가?
9. 응답을 받은 뒤 브라우저 코드가 올바르게 처리했는가?
```

예를 들어 화면에 "데이터를 불러올 수 없습니다"라고 표시되더라도 곧바로 프런트엔드 상태 관리 코드부터 수정하지 않습니다.

먼저 실제 네트워크 사실을 확인합니다.

```text
화면 오류
  ↓
Network 요청 존재 여부
  ↓
요청 URL과 메서드
  ↓
상태 코드
  ↓
응답 본문
  ↓
서버 로그 또는 브라우저 코드
```

관찰할 수 있는 사실부터 확인하면 추측으로 디버깅하는 일을 줄일 수 있습니다.

## 흔한 실수

- URL 전체를 하나의 문자열로만 보고 호스트, 포트, 경로 문제를 구분하지 않습니다.
- URL의 프래그먼트까지 서버에 전송된다고 생각합니다.
- `localhost`가 항상 하나의 프로그램만 가리킨다고 생각합니다.
- 연결 실패와 HTTP 오류 응답을 같은 문제로 취급합니다.
- `404`를 네트워크 연결 실패라고 생각합니다.
- JSON 파싱 오류가 발생하면 실제 응답 본문을 확인하지 않고 JSON 코드만 수정하려고 합니다.
- Console 오류만 보고 Network 탭의 실제 요청과 응답을 확인하지 않습니다.
- TypeScript 클라이언트가 보낸 값이므로 서버에서 검사하지 않아도 된다고 생각합니다.
- 의미 있는 HTML 요소 대신 모든 UI를 `div`와 클릭 이벤트로 구현합니다.
- 프런트엔드와 API가 항상 같은 프로세스나 같은 포트에서 실행된다고 가정합니다.

## 완료 기준

다음 내용을 스스로 설명하거나 실제 브라우저에서 확인할 수 있으면 이 문서의 목표를 달성한 것입니다.

- `http://localhost:3000/boards/1?q=mine#comments`의 스킴, 호스트, 포트, 경로, 쿼리, 프래그먼트를 각각 구분할 수 있습니다.
- 프래그먼트가 HTTP 요청에 포함되지 않는다는 점을 설명할 수 있습니다.
- URL을 입력한 뒤 호스트 이름 확인, 연결, HTTP 요청, HTTP 응답이 어떤 순서로 일어나는지 큰 흐름을 설명할 수 있습니다.
- 연결 실패, `404`, `500`, JSON 파싱 실패가 각각 어느 단계에서 발생한 문제인지 구분할 수 있습니다.
- `404`나 `500`도 서버가 반환한 HTTP 응답이라는 점을 설명할 수 있습니다.
- HTML, CSS, JavaScript, JSON의 역할 차이를 설명할 수 있습니다.
- Network 탭에서 요청 URL, 메서드, 상태 코드, 요청·응답 헤더, 응답 본문을 확인할 수 있습니다.
- 브라우저에서 입력 검증을 했더라도 서버가 요청을 다시 검증해야 하는 이유를 설명할 수 있습니다.
