# Kotlin·Swift와 네이티브 코드 읽기

React Native와 Expo를 사용해도 Android와 iOS가 사라지지는 않습니다. JavaScript가 호출하는 모듈, 권한 설정, 앱 식별자, 서명, 빌드 오류와 운영체제 수명은 네이티브 프로젝트에서 결정됩니다.

이 문서는 Kotlin과 Swift 전체를 가르치지 않습니다. **현재 사용하는 네이티브 의존성 하나를 JavaScript 호출부터 Android와 iOS 구현과 실제 빌드 결과까지 따라갈 수 있는 수준**을 목표로 합니다. 커스텀 네이티브 모듈 작성은 선택 사항입니다.

## 이 문서에서 확인할 내용

- JavaScript 패키지 변경과 네이티브 바이너리 변경을 구분합니다.
- CNG로 생성된 프로젝트를 만드는 방식과 `android/`, `ios/`를 직접 관리하는 방식을 구분합니다.
- Android와 iOS 프로젝트에서 앱 식별 정보, 권한 설정과 실행 진입점을 찾습니다.
- 설정 플러그인과 네이티브 모듈이 각각 무엇을 바꾸는지 설명합니다.
- Kotlin과 Swift 메서드의 입력, 출력, 오류, 스레드와 취소 동작을 읽습니다.
- 빌드 실패를 의존성, 생성 단계, 컴파일, 링크, 서명, 설치, 런타임 단계로 나눕니다.
- 두 플랫폼이 같은 애플리케이션 결과를 반환하는지 확인합니다.

## 네이티브 프로젝트 관리 방식을 먼저 정합니다

### CNG를 사용하는 경우

```text
앱 설정
+ Expo SDK와 패키지 버전
+ 설정 플러그인
+ 로컬 네이티브 모듈
→ 네이티브 프로젝트 생성
→ 생성된 Android와 iOS 프로젝트
→ 컴파일, 서명, 설치
```

`android/`, `ios/`를 다시 만들 수 있는 결과물로 취급합니다. 생성된 파일을 직접 수정한 뒤 기준 파일로 삼지 않습니다. 변경이 필요하면 앱 설정, 설정 플러그인 또는 로컬 모듈에 작성합니다.

### 네이티브 프로젝트를 직접 관리하는 경우

```text
`android/`와 `ios/`를 버전 관리에 포함
→ Gradle과 Xcode 프로젝트를 직접 수정
→ 자동 연결과 수동 설정 관리
```

기존 네이티브 앱에 React Native를 연결하는 경우, 여러 대상처럼 생성된 프로젝트만으로 관리하기 어려운 경우에 사용합니다.

어느 방식을 선택했든 다음 질문에 답할 수 있어야 합니다.

- `android/`, `ios/`를 커밋합니까?
- 앱 식별자와 권한 설정의 기준 파일은 어디입니까?
- 초기 상태에서 다시 생성하는 작업 명령은 무엇입니까?
- 직접 수정한 네이티브 파일이 다음 생성 단계에서 사라지지 않습니까?
- 예외적으로 직접 관리하는 파일이 있다면 왜 필요합니까?

## JavaScript 변경과 바이너리 변경을 구분합니다

다음 변경은 보통 새 네이티브 빌드가 필요합니다.

- 네이티브 패키지 추가, 제거, 버전 변경
- Expo SDK 또는 React Native 변경
- 권한, 권한 안내 문구, 권한 설정 변경
- 설정 플러그인 결과 변경
- 로컬 Kotlin 또는 Swift 모듈 변경
- 앱 아이콘과 네이티브 리소스 변경
- Android 매니페스트, Gradle, iOS plist, Xcode 설정 변경

경로, 컴포넌트, 기록 검증처럼 순수 JavaScript 변경은 호환되는 런타임에 다시 배포할 수 있습니다. 실제로 호환되는지는 패키지 이름만 보고 추측하지 않고 runtimeVersion 또는 네이티브 특성값 규칙으로 확인합니다.

Metro 새로고침으로 동작했다는 사실은 새 바이너리의 설정과 서명이 맞다는 증거가 아닙니다.

## Android 프로젝트에서 찾을 값

템플릿과 SDK 버전에 따라 파일 이름은 달라질 수 있습니다. 경로를 외우기보다 빌드 결과를 만드는 값을 찾습니다.

### 애플리케이션 식별 정보

- `applicationId`는 어디서 정합니까?
- namespace와 애플리케이션 ID가 같은지 다릅니까?
- 개발, 미리보기, 운영이 다른 ID를 사용합니까?
- `versionCode`, `versionName`은 어디서 가져옵니까?

### 빌드 연결 관계

- 설정과 루트 빌드가 어떤 모듈과 플러그인을 포함합니까?
- 앱 모듈의 최소, 컴파일과 대상 SDK는 무엇입니까?
- 자동 연결로 어떤 네이티브 의존성이 들어옵니까?
- 빌드 변형과 릴리스 서명 설정은 무엇입니까?

### 런타임 진입점

- `Application`과 `Activity` 진입점은 어디입니까?
- 딥 링크와 알림 응답은 어느 `Activity`로 들어옵니까?
- New Architecture와 네이티브 로더 설정은 어디에 있습니까?

### 권한과 컴포넌트

- 최종 병합된 매니페스트에 어떤 권한, 서비스, 제공자가 있습니까?
- 라이브러리 매니페스트가 추가한 항목은 무엇입니까?
- `exported` 컴포넌트와 포그라운드 서비스가 실제로 필요합니까?

소스 매니페스트 하나만 읽지 않습니다. 해당 빌드 변형의 병합된 매니페스트를 확인합니다.

## iOS 프로젝트에서 찾을 값

### 애플리케이션 식별 정보와 서명

- 번들 식별자는 어디서 정합니까?
- 사용자에게 표시하는 버전과 빌드 번호는 무엇입니까?
- 개발팀, 인증서와 프로비저닝 프로필이 어떻게 연결됩니까?
- 대상별 기기 기능과 권한 설정이 어떻게 다릅니까?

### 빌드 연결 관계

- 작업 공간, 프로젝트와 대상은 무엇입니까?
- CocoaPods, Swift 패키지 또는 자동 연결 의존성이 어디에 연결됩니까?
- scheme과 빌드 설정이 개발, 미리보기, 운영을 어떻게 구분합니까?

### 런타임 진입점과 설정

- 애플리케이션과 `scene` 수명 콜백은 어디입니까?
- Info.plist의 권한 안내 문구와 URL scheme은 어디서 생성됩니까?
- 푸시, 백그라운드 모드, 연결된 도메인 같은 기기 기능은 어느 대상에 들어갑니까?

생성된 plist만 보지 않고 앱 설정 또는 플러그인 입력과 연결합니다.

## 설정 플러그인과 네이티브 모듈의 역할을 나눕니다

### 설정 플러그인

빌드 전에 네이티브 프로젝트 파일을 바꿉니다.

- 매니페스트와 plist 키
- 권한 설명
- Gradle/Xcode 설정
- 네이티브 리소스
- 대상 또는 권한 설정

런타임에서 JavaScript가 호출하는 기능은 아닙니다.

### 네이티브 모듈

설치된 바이너리 안에서 JavaScript와 플랫폼 API를 연결합니다.

- 기기 SDK 호출
- 플랫폼 전용 기기 기능
- 네이티브 화면
- 수명에 민감한 작업
- JavaScript보다 네이티브 구현이 필요한 연산

하나의 패키지가 둘 다 제공할 수 있습니다. 모듈 패키지를 설치했지만 플러그인이 빠지면 컴파일은 되더라도 런타임 권한이나 권한 설정이 없을 수 있습니다.

## JavaScript 호출부부터 읽습니다

네이티브 의존성을 읽을 때는 JavaScript 호출부부터 시작합니다.

```ts
type DeviceEnvironment = {
  platform: "android" | "ios";
  appBuild: string;
  runtimeVersion: string | null;
  capability: "available" | "limited" | "unavailable";
};

interface DeviceEnvironmentPort {
  getEnvironment(): Promise<DeviceEnvironment>;
}
```

다음 질문에 답합니다.

- 입력을 어디서 검증합니까?
- 결과 필드가 없거나 잘못된 형식이면 어떻게 합니까?
- 이 값이 기기 식별 정보나 바이너리 진위를 증명합니까?
- 개인정보가 될 수 있어 제외한 값은 무엇입니까?
- 어느 스레드에서 플랫폼 API를 호출합니까?
- 앱이 백그라운드로 가거나 모듈이 해제되면 작업을 취소합니까?
- 두 플랫폼이 같은 결과 종류를 반환합니까?

## 플랫폼 원본 값을 애플리케이션에 그대로 퍼뜨리지 않습니다

Kotlin 열거 값 이름이나 Swift 원본 값을 화면까지 전달하면 플랫폼별 분기가 곳곳에 생깁니다.

```text
Android 원본 결과와 iOS 원본 결과
→ 네이티브 모듈 결과
→ TypeScript 런타임 검증
→ 애플리케이션 결과 타입
```

예를 들어 권한은 `granted`, `limited`, `denied`, `restricted`, `not-required`로 맞출 수 있습니다. 단, 플랫폼 차이를 숨겨서는 안 됩니다. 한 플랫폼에 기능이 없으면 `unavailable`과 이유를 반환합니다.

숫자로 표현한 시각의 단위, `null` 허용 값, 큰 정수, 바이너리 버퍼와 URI 수명도 확인합니다. JavaScript `number`가 모든 네이티브 정수를 정확히 표현한다고 가정하지 않습니다.

## Promise와 실행 스레드는 다른 문제입니다

JavaScript에서 Promise를 반환한다고 네이티브 작업이 자동으로 백그라운드 스레드에서 실행되는 것은 아닙니다. 사용 중인 모듈 프레임워크의 현재 버전에서 콜백과 함수 본문이 어느 대기열에서 실행되는지 소스와 공식 문서로 확인합니다.

확인할 질문:

- 카메라, 권한, UI API가 메인 스레드를 요구합니까?
- 파일 해시 계산이나 이미지 처리가 UI 스레드를 막습니까?
- 콜백은 어느 스레드나 대기열에서 들어옵니까?
- 결과를 반환할 때 모듈과 JavaScript 런타임이 살아 있습니까?
- 여러 호출을 동시에 허용합니까?
- 공유하는 가변 상태를 어떤 방식으로 보호합니까?

긴 CPU 연산이나 I/O 작업은 적절한 실행기나 대기열로 옮깁니다. UI 관련 API는 메인 스레드 규칙을 지킵니다.

## 취소를 JavaScript와 네이티브 양쪽에 연결합니다

화면이 사라지거나 `AbortSignal`이 취소돼도 네이티브 SDK 작업은 계속될 수 있습니다.

가능한 형태:

```text
작업 시작 → operationId
취소(operationId)
결과와 이벤트 → operationId 포함
```

TypeScript 어댑터는 `AbortSignal` 리스너에서 네이티브 `cancel(operationId)`를 호출할 수 있습니다. `AbortSignal` 객체 자체가 Kotlin이나 Swift로 전달된다고 가정하지 않습니다.

반드시 확인할 조건:

- `cancel()`을 여러 번 호출해도 안전합니다.
- 완료와 취소가 동시에 발생해도 터미널 결과는 한 번만 전달됩니다.
- 모듈을 해제할 때 활성화 리스너와 작업을 정리합니다.
- 네이티브 API가 취소를 지원하지 않으면 애플리케이션에서 생성 단계를 확인해 늦은 결과를 버립니다.

## 오류를 고정된 오류 코드로 변환합니다

네이티브 예외 메시지는 OS와 라이브러리 버전에 따라 바뀔 수 있습니다. 애플리케이션은 안정된 코드를 사용합니다.

```ts
type NativeCapabilityError =
  | { code: "permission-denied"; canAskAgain: boolean }
  | { code: "unavailable"; reason: string }
  | { code: "cancelled" }
  | { code: "temporary"; retryable: boolean }
  | { code: "invalid-result" };
```

- 사용자에게 보여 줄 메시지와 진단 정보를 구분합니다.
- Java 또는 Kotlin 예외나 `NSError` 전체를 관찰 정보에 그대로 넣지 않습니다.
- 권한 거절처럼 예상한 결과를 비정상 종료 보고 도구 예외로 만들지 않습니다.
- 모르는 네이티브 결과를 성공으로 바꾸지 않습니다.

## 이벤트 스트림의 수명을 관리합니다

센서나 네이티브 SDK 이벤트를 노출하는 경우 다음 순서를 확인합니다.

```text
첫 리스너 등록
→ 네이티브 관찰 시작
→ 순번 또는 작업 ID가 있는 이벤트 전달
→ 리스너 제거
→ 마지막 리스너가 사라지면 네이티브 관찰 중단
```

빠른 갱신, 경로 다시 마운트, 백그라운드 전환 뒤 리스너가 중복되지 않아야 합니다. 중요한 업무 상태를 이벤트만으로 유지하지 않고 현재 스냅숏을 다시 읽는 API를 둡니다.

## Kotlin에서 읽을 최소 범위

- 클래스, 객체, 데이터 클래스
- null 허용 타입과 안전 호출
- sealed 클래스와 열거 값
- suspend 함수, 코루틴과 콜백 수명
- `Context`와 `Activity`가 필요한 API의 차이
- 메인과 백그라운드 실행 대기열
- Gradle 의존성과 매니페스트 위치
- 예외와 결과 연결

언어 문법 전체를 암기할 필요는 없습니다. JavaScript에서 호출한 메서드가 어떤 Android API를 호출하고 어떤 결과를 반환하는지 따라갈 수 있으면 됩니다.

## Swift에서 읽을 최소 범위

- 구조체, 클래스, Optional과 열거 값
- `async/await`와 완료 콜백
- `Result`, `throws`, `NSError`
- `actor`, `MainActor` 또는 실행 대기열
- 애플리케이션과 `scene`, 화면 컨트롤러가 유효한 시점
- 대상, 권한 설정과 plist 위치
- 리스너와 리소스 정리

목표는 외부 공개 호출, 수명, 스레드, 오류와 취소를 검토하는 것입니다.

## 네이티브 의존성을 선택할 때 확인합니다

- 현재 Expo SDK, React Native와 New Architecture 지원 여부
- Android와 iOS 최소 버전
- 설정 플러그인 또는 수동 등록 필요 여부
- 릴리스 주기와 문제 보고 대응 상태
- 권한과 개인정보 보호 영향
- 바이너리 크기와 시작 시간에 미치는 영향
- 메인 스레드에서 수행하는 작업
- Expo Go와 개발용 빌드 차이
- 제거했을 때 매니페스트, 권한 설정과 네이티브 코드가 깨끗이 사라지는지
- 라이선스

패키지 README만 읽지 않고 예제 앱, 소스와 초기 상태 빌드 결과를 확인합니다.

## 빌드 실패를 단계별로 나눕니다

```text
1. JavaScript 패키지·의존성 해석
2. 네이티브 프로젝트 생성
3. Kotlin/Java 또는 Swift/Objective-C 컴파일
4. 매니페스트, 리소스·plist·권한 설정 병합
5. 네이티브 링크와 패키징
6. 서명
7. 설치와 실행
8. JavaScript에서 네이티브 모듈 호출
```

각 단계에서 필요한 근거가 다릅니다.

| 단계 | 먼저 확인할 값 |
|---|---|
| 의존성 | 잠금 파일, 패키지 버전, peer dependency와 네이티브 호환성 |
| 생성 단계 | 앱 설정, 플러그인 입력, 생성된 변경 내용 |
| 컴파일 | 첫 컴파일러 오류와 관련 소스 |
| 병합 | 병합된 매니페스트, 빌드된 plist, 권한 설정 |
| 링크와 패키징 | 네이티브 심볼, 아키텍처, 패키지 형식 |
| 서명 | 인증서, 프로필과 keystore 식별 정보와 대상 |
| 설치와 실행 | 앱 ID, 버전, 기기 OS, 비정상 종료 로그 |
| 런타임 호출 | runtimeVersion, 설치된 모듈, 정규화된 오류 |

마지막 수백 줄을 그대로 복사하기보다 처음 발생한 오류와 관련 의존성을 좁힙니다.

## 네이티브 의존성 하나를 끝까지 추적합니다

완료 단계에서는 Field Notes가 실제 사용하는 모듈 하나를 고릅니다. 카메라, 위치, 알림 또는 백그라운드 작업이 적합합니다.

```text
TypeScript 외부 공개 호출과 결과 검증
→ 패키지와 자동 연결
→ 앱 설정과 설정 플러그인 입력
→ 생성된 Android 매니페스트와 Gradle 설정
→ Kotlin/Java 진입점과 OS API
→ 생성된 iOS plist와 권한 설정
→ Swift/Objective-C 진입점과 OS API
→ 스레드·수명·취소·오류 변환
→ 개발용 빌드에서 정상 호출
→ 바이너리와 런타임 불일치 실패 재현
```

각 항목에 소스 파일이나 설정, 값을 바꾸는 입력, 확인 방법과 확인하지 못하는 범위를 기록합니다.

한 플랫폼에 구현이 없으면 숨기지 않습니다. 애플리케이션이 `unavailable`을 반환하는지, 다른 기능을 사용하는지 설명합니다.

## 검증 시나리오

- 네이티브 패키지 추가 뒤 Metro 새로고침만 수행함
- 설정 플러그인 누락
- Android 병합된 매니페스트에 불필요한 권한 추가
- iOS 권한 안내 문구 누락
- 개발, 미리보기와 운영 앱 ID 충돌
- JavaScript가 설치된 바이너리에 없는 메서드 호출
- 메인 스레드에서 긴 파일 처리
- 화면 마운트 해제 뒤 콜백 도착
- 취소와 완료 처리 실행 순서 경쟁
- 리스너가 다시 마운트될 때마다 중복 등록됨
- Android와 iOS가 같은 원본 상태를 다른 의미로 반환함
- 서명 대상과 번들 또는 애플리케이션 ID 불일치

## 완료 기준

- CNG와 직접 관리하는 네이티브 프로젝트 중 어떤 방식을 사용하는지 설명할 수 있습니다.
- 네이티브 변경이 필요한 JavaScript 또는 패키지 변경을 구분할 수 있습니다.
- Android 애플리케이션 ID, 병합된 매니페스트와 런타임 진입점을 찾을 수 있습니다.
- iOS 번들 ID, 빌드된 plist, 권한 설정과 런타임 진입점을 찾을 수 있습니다.
- 설정 플러그인과 네이티브 모듈의 역할을 구분합니다.
- 네이티브 메서드의 입력, 출력, 오류, 스레드, 취소와 리스너 수명을 설명합니다.
- Android와 iOS 결과를 같은 애플리케이션 결과 타입으로 변환하거나 명시적인 대체 결과를 제공합니다.
- 네이티브 변경 뒤 새 개발용 빌드를 설치해 확인합니다.
- 빌드 실패를 생성 단계, 컴파일, 병합, 서명, 설치, 런타임 단계로 좁힐 수 있습니다.
