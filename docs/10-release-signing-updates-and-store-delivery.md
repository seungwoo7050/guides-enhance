# 릴리스, 서명, 업데이트와 스토어 전달

모바일 릴리스는 산출물을 한 번 만들고 업로드하는 작업으로 끝나지 않습니다. 애플리케이션 ID, 서명 식별 정보, 앱 버전, 빌드 번호, 네이티브 런타임, JavaScript 업데이트, 스토어 기록과 단계적 배포 대상이 서로 맞아야 합니다.

이 문서는 모바일 클라이언트가 만든 빌드와 배포 근거를 읽고 검증하는 데 집중합니다. 스토어 정책과 관리 화면 요구사항은 바뀔 수 있으므로 실제 릴리스 시점에는 공식 문서를 다시 확인해야 합니다.

## 이 문서에서 확인할 내용

- 애플리케이션 ID, 앱 버전, 빌드 번호, runtimeVersion과 소스 리비전을 구분합니다.
- 개발, 미리보기, 운영 프로필의 앱 식별 정보와 연결 대상을 분리합니다.
- 서명 인증 정보의 소유, 접근, 백업과 교체를 정합니다.
- 소스에서 설치 가능한 산출물까지 추적할 근거를 남깁니다.
- 네이티브 변경과 JavaScript 업데이트의 호환 여부를 판정합니다.
- 원격 업데이트 되돌리기와 스토어 바이너리 문제 대응을 구분합니다.
- 설치, 업그레이드, 딥 링크, 알림과 마이그레이션을 릴리스 검사 단계에 포함합니다.

## 여러 식별 정보를 구분합니다

| 값 | 실제 역할 |
|---|---|
| Android `applicationId` | 설치와 Play 관리 화면에서 앱을 식별합니다. |
| iOS 번들 식별자 | 대상, 서명과 App Store Connect에서 앱을 식별합니다. |
| Expo와 EAS 프로젝트 ID | Expo 서비스의 프로젝트를 식별합니다. |
| 앱 버전 | 사용자에게 보이는 릴리스 버전입니다. |
| Android `versionCode` | Android 스토어가 새 빌드를 비교하는 정수입니다. |
| iOS `buildNumber` | 같은 앱 버전 안에서 빌드를 구분합니다. |
| `runtimeVersion` | 설치된 네이티브 API와 JavaScript 업데이트의 호환 범위를 나타냅니다. |
| 업데이트 ID와 채널 | 배포한 JavaScript 코드·리소스와 배포 대상입니다. |
| 소스 리비전 | 빌드 입력으로 사용한 소스를 식별합니다. |
| 산출물 해시값 | 실제 빌드 결과 파일 또는 디렉터리를 식별합니다. |

앱 버전이 같아도 빌드 번호와 바이너리는 다를 수 있습니다. 소스 리비전이 같아도 프로필, 네이티브 도구 모음과 환경이 다르면 다른 산출물이 나올 수 있습니다.

## 애플리케이션 ID를 프로필별로 분리합니다

개발, 미리보기, 운영을 한 기기에 함께 설치하거나 서로 다른 백엔드를 사용하려면 ID를 분리합니다.

```text
production   dev.seungwoo7050.fieldnotes
development  dev.seungwoo7050.fieldnotes.development
preview      dev.seungwoo7050.fieldnotes.preview
```

각 프로필은 다음 값도 구분해야 합니다.

- 앱 표시 이름과 아이콘
- URL scheme 또는 연결된 도메인
- 동기화 API URL
- 푸시 프로젝트와 토큰 등록 대상
- 관찰 정보 환경
- 기능 플래그
- 원격 업데이트를 사용하는 경우 채널
- 로컬 데이터 마이그레이션 기대

미리보기가 운영 사용자 데이터에 잘못 연결되지 않게 합니다.

## 빌드 프로필의 목적을 분명히 합니다

### 개발

- 개발 클라이언트 포함
- 디버그 도구와 빠른 네이티브 반복
- 개발자 기기용
- 운영 서명과 분리

### 미리보기

- 릴리스와 가까운 최적화
- 내부 또는 제한된 테스터 배포
- 운영과 비슷하지만 안전한 테스트 환경
- 설치, 업그레이드, 권한, 알림 확인

### 운영

- 스토어 배포용 패키지
- 운영 앱 식별 정보
- 운영 서명과 관찰 정보 설정
- 승인한 runtimeVersion

프로필 이름만 나눈 채 같은 애플리케이션 ID나 백엔드를 사용하지 않습니다. 빌드가 실제로 사용한 설정을 비밀값 없이 근거로 남깁니다.

## 서명 인증 정보를 개인 파일로 취급하지 않습니다

확인할 질문:

- Android keystore와 iOS 인증서와 프로필을 누가 소유합니까?
- 개인 노트북이 아니라 조직이 복구할 수 있는 위치에 있습니까?
- 접근 권한과 감사 기록이 있습니까?
- 담당자가 바뀌어도 다음 릴리스를 만들 수 있습니까?
- 만료, 폐기, 손실과 교체 절차가 있습니까?
- CI가 인증 정보를 어떻게 가져오고 작업 뒤 제거합니까?

인증 정보를 저장소에 커밋하지 않습니다. 클라우드 서명 서비스를 사용하더라도 접근, 복구와 교체 방법을 이해해야 합니다.

## 빌드 입력을 기록합니다

릴리스 근거에는 다음 값을 포함합니다.

```text
소스 리비전과 변경되지 않음 또는 변경 있음 상태
소스 트리 해시값
잠금 파일 해시값
Node와 패키지 관리자 버전
Expo SDK와 React Native 버전
실제 적용된 앱 설정
네이티브 의존성 특성값
빌드 프로필과 환경 이름
Android와 iOS 도구 모음 정보
애플리케이션 ID와 번들 ID
앱 버전과 빌드 번호
runtimeVersion 또는 런타임 특성값
산출물 이름, 크기와 해시값
비밀값을 제외한 서명 식별 정보
```

커밋 해시 하나만으로 빌드를 재현할 수 있다고 가정하지 않습니다.

## 플랫폼별 근거를 나눕니다

`Field Notes` 릴리스 검증기에서 `ReleaseEvidence` 하나는 Android 또는 iOS 한 플랫폼만 나타냅니다. 같은 릴리스 후보는 Android 매니페스트와 iOS 매니페스트 두 개를 제출합니다.

두 매니페스트가 같아야 하는 값:

- 소스 리비전과 트리 해시값
- 잠금 파일 해시값
- 빌드 프로필
- 앱 버전
- runtimeVersion 또는 런타임 특성값

플랫폼별로 달라도 되는 값:

- 애플리케이션 ID 또는 번들 ID
- 빌드 번호
- 빌드 도구
- 생성된 설정 해시값
- 산출물 종류

Android와 iOS 산출물을 하나의 `artifacts[]`에 섞지 않습니다.

## 산출물 종류를 구분합니다

### Android

```text
AAB
- Play 배포용
- 기기에 직접 설치하는 파일이 아님

APK
- 에뮬레이터 또는 실제 기기에 직접 설치 가능

Play-생성된 분할 파일 묶음
- 특정 Play 빌드가 만든 기기 설치 결과
```

### iOS

```text
xcarchive
- Xcode 아카이브 디렉터리
- 직접 설치하는 파일이 아님

IPA
- 프로비저닝 조건을 가진 설치·배포 산출물

TestFlight 빌드
- App Store Connect가 관리하는 특정 빌드

시뮬레이터 `.app`
- 시뮬레이터 전용 디렉터리 묶음
```

AAB를 직접 설치했다고 기록하거나 xcarchive를 실제 기기 설치 산출물로 기록하지 않습니다. 시뮬레이터 `.app`을 iPhone 설치 근거로 사용하지 않습니다.

## 디렉터리 산출물의 내용을 식별합니다

`.xcarchive`와 시뮬레이터 `.app`은 디렉터리입니다. `sha256 directory`처럼 존재하지 않는 단일 파일 해시값을 적지 않습니다.

Field Notes 릴리스 검증 형식은 다음 값을 사용합니다.

- 디렉터리 이름과 확장자
- 일반 파일 수
- 일반 파일 바이트 합
- 정규화된 트리 매니페스트
- `sha256-canonical-tree-v1` 해시값

정규화된 매니페스트는 경로, 파일 모드, 파일 콘텐츠 해시와 심볼릭 링크 대상을 정해진 순서로 기록합니다. `mtime`, 사용자·그룹 ID와 확장 속성은 재현 가능한 해시값에서 제외합니다.

이 해시값은 디렉터리 내용을 식별하기 위한 값입니다. 서명, 권한 설정과 신뢰 체인을 대신 확인하지 않습니다.

## 설치 근거를 산출물에 연결합니다

설치 확인에는 다음 값이 필요합니다.

- 설치에 사용한 `artifactRef`
- 기기 종류와 비민감 식별 정보
- 실제로 관찰한 애플리케이션 ID
- 앱 버전과 빌드 번호
- runtimeVersion
- 빌드와 같은 런타임 특성값 또는 규칙 참조
- 실행 결과
- 관찰 시각
- 원본 근거 위치

매니페스트에 적힌 문자열이 서로 일치한다는 사실만으로 실제 설치가 됐다고 볼 수는 없습니다. 기기 명령, 화면 캡처, 로그 또는 테스터 기록과 연결해야 합니다.

## 서명 상태를 별도로 기록합니다

산출물마다 다음 상태 중 하나를 사용합니다.

```text
`not-run`
- 실행하지 않은 이유와 필요한 다음 근거

`claimed`
- 산출물 참조, 일부 가린 서명 식별 정보, 관찰 방법과 결과

`manually-reviewed`
- 주장 내용을 확인한 검토자, 시각과 별도 검토 근거
```

`claimed`를 자동으로 신뢰된 상태로 올리지 않습니다. `manually-reviewed`도 사람이 기록을 검토했다는 뜻이며 비공개 키 보호, 인증서 신뢰 체인과 인증 정보 소유를 암호학적으로 증명하는 값은 아닙니다.

## 스토어 상태와 전달된 바이트를 구분합니다

스토어 근거에는 다음 값을 따로 둡니다.

- 업로드한 배포용 산출물
- 관리 화면에서 바뀌지 않는 빌드 참조
- 테스트 또는 운영 배포 단계
- 검토와 단계적 배포 상태
- 스토어가 사용자에게 전달한 바이트에 대한 관찰 여부

Android 스토어는 AAB를 기기별 분할 APK로 바꾸고 재서명할 수 있습니다. iOS도 스토어 처리와 기기별 최적화을 거칩니다. 업로드 산출물 해시값이 사용자 기기 바이트와 같다고 가정하지 않습니다.

스토어 빌드 참조와 설치 관찰 결과를 연결하되 실제로 전달된 바이트를 확인하지 않았다면 `declared` 또는 `not-run`으로 남깁니다.

## 네이티브 런타임과 JavaScript 업데이트를 연결합니다

다음 변경은 새 네이티브 바이너리가 필요합니다.

- Expo SDK나 React Native 변경
- 네이티브 패키지 추가, 제거, 업그레이드
- 로컬 Kotlin 또는 Swift 모듈 변경
- 설정 플러그인 결과가 네이티브 API 또는 기기 기능을 바꿈
- 권한 설정, 권한, 네이티브 리소스 변경

이 중 JavaScript가 사용할 수 있는 네이티브 API 집합이 달라지는 변경은 새 runtimeVersion이 필요합니다.

문제 예:

```text
설치된 바이너리는 런타임 R1
→ 새 JavaScript도 R1로 배포
→ 새 코드가 R1에 없는 카메라 메서드 호출
→ 런타임 오류
```

원격 업데이트를 사용한다면 runtimeVersion 또는 특성값 규칙을 명시하고 같은 런타임의 미리보기 빌드에서 먼저 확인합니다. 원격 업데이트를 사용하지 않는 프로젝트는 업데이트 기능을 명시적으로 끄고 채널이나 전달을 성공했다고 기록하지 않습니다.

## 원격 업데이트와 스토어 바이너리 대응을 구분합니다

### 원격 업데이트 문제

- 같은 호환되는 런타임 안에서 이전 업데이트를 다시 배포하거나 수정 업데이트를 냅니다.
- 단계적 배포를 멈출 수 있습니다.
- 이미 실행한 로컬 마이그레이션과 서버에 반영된 변경은 자동으로 되돌아가지 않습니다.

### 스토어 바이너리 문제

- 새 바이너리를 만들어야 할 수 있습니다.
- 검토와 단계적 배포 시간이 필요합니다.
- 사용자 기기를 강제로 이전 바이너리로 돌리기 어렵습니다.
- 마이그레이션과 백엔드 호환성을 새 버전에서 고치는 방식으로 설계해야 합니다.

파괴적인 로컬 마이그레이션을 JavaScript 업데이트 하나로 무계획하게 실행하지 않습니다.

## 여러 앱 버전이 동시에 사용됩니다

스토어 단계적 배포는 백엔드 배포보다 느릴 수 있습니다. 다음 조합이 동시에 존재할 수 있습니다.

- 이전 클라이언트 + 새 서버
- 새 클라이언트 + 이전 서버 동작
- 새 바이너리 + 이전 호환되는 JavaScript
- 이전 바이너리 + 새 호환되는 JavaScript

API와 스키마 변경에는 호환성 기간을 둡니다.

```text
서버가 새 필드를 선택 사항으로 먼저 지원
→ 새 앱이 해당 필드 사용
→ 충분한 사용 비율 확인
→ 이전 클라이언트 지원 종료 뒤 필수로 변경
```

로컬 DB 마이그레이션도 이전 바이너리와 새 바이너리가 공유할 수 있는지, 이전 버전으로 되돌리기를 지원하지 않는다면 어떤 상태로 막을지 정합니다.

## 릴리스 실패 위치를 나눕니다

| 위치 | 예 | 처리 |
|---|---|---|
| 소스 검사 단계 | 타입 검사, 테스트, 마이그레이션 시험 데이터 실패 | 산출물을 만들지 않고 소스 수정 후 다시 검사합니다. |
| 네이티브 빌드 | 의존성, 매니페스트, 권한 설정, 서명 실패 | 네이티브 입력과 인증 정보 문제를 나눠 새 빌드를 만듭니다. |
| 설치와 실행 | 특정 OS에서 설치 또는 콜드 스타트 실패 | 해당 단계적 배포를 멈추고 기기 정보와 비정상 종료 근거를 보존합니다. |
| 런타임 업데이트 | 잘못된 번들, 네이티브 API 불일치 | 호환되는 업데이트로 되돌리거나 전달을 중단합니다. |
| 스토어 심사 | 메타데이터, 개인정보 보호, 권한 설명 불일치 | 실제 바이너리 동작과 스토어 기록을 맞춥니다. |
| 단계적 배포 | 비정상 종료, 마이그레이션, 동기화 지표 악화 | 정한 중단 기준에 따라 단계적 배포를 멈춥니다. |

문제 발생 뒤 어떤 사용자가 어떤 바이너리, 런타임과 스키마를 받았는지 추적할 수 있어야 합니다.

## 릴리스 검사 단계

### 소스와 자동 검사

- 초기 상태로 `checkout`
- 잠금 파일 기반 설치
- 타입 검사와 테스트
- 마이그레이션 시험 데이터
- 동기화 실패와 충돌 테스트
- 의존성, 라이선스와 보안 확인

### 네이티브 빌드와 설치

- Android와 iOS 운영 환경에 가까운 빌드
- 배포용 산출물과 설치 가능한 산출물 구분
- 애플리케이션 ID, 버전, runtimeVersion 확인
- 콜드 스타트와 업그레이드
- 딥 링크, 커스텀 scheme과 유니버설 링크
- 알림 등록과 탭
- 오프라인 저장, 재시작과 동기화
- 비정상 종료 보고 도구 환경

### 사용자 품질

- TalkBack과 VoiceOver
- 큰 글자와 작은 화면
- 권한 거절, 제한됨, 철회
- 개인정보 보호 데이터 목록
- 스토어 설명과 실제 기능 일치

### 운영 준비

- 단계적 배포와 중단 기준
- 오류와 성능 대시보드
- 지원과 장애 대응 담당자
- 원격 업데이트 되돌리기 또는 중지 절차
- 서명 인증 정보 복구 절차

## 스토어 업로드와 공개 릴리스는 다릅니다

바이너리 업로드 뒤에도 테스트 배포 단계, 검토, 단계적 배포 단계가 남습니다.

확인할 항목:

- 스토어 기록과 애플리케이션 ID 또는 번들 ID 일치
- 올바른 배포 단계와 테스터 대상
- 앱 버전과 빌드 번호
- 개인정보 보호와 권한 사용 이유
- 검토자가 기능을 확인할 수 있는 절차와 테스트 계정
- 메타데이터, 화면 캡처와 실제 화면 일치
- 단계적 배포 시작과 중단 상태

정책 세부 사항은 릴리스 시점에 공식 관리 화면에서 확인합니다.

## Field Notes 릴리스 검증기가 확인하는 것

`packages/release-contract`는 다음 항목의 형식과 상호 일관성을 검사합니다.

- 개발, 미리보기, 운영 EAS 프로필 역할
- 프로필별 앱 식별 정보와 환경 값
- Android와 iOS 매니페스트가 같은 소스 후보를 가리키는지
- 산출물 종류와 설치 기기 조합
- 버전, runtimeVersion과 특성값 일치
- 서명, 설치, 스토어 근거가 올바른 산출물 참조를 가리키는지

검증기 성공이 의미하지 않는 것:

- 네이티브 빌드가 실제로 실행됨
- 산출물 해시값을 실제 파일에서 다시 계산함
- 서명 신뢰 체인 확인
- 기기 설치와 실행 수행
- 스토어 업로드, 검토와 전달 성공
- 원격 업데이트 전달

실행하지 않은 항목은 스키마 오류로 만들기보다 `not-run`으로 명시하고 완료 여부 판단에서 제외합니다.

## 검증 시나리오

- 개발, 미리보기와 운영 앱 ID가 같음
- 미리보기가 운영 동기화 URL을 사용함
- 운영 Android 산출물을 APK로 잘못 선언함
- AAB를 직접 설치 근거에 연결함
- xcarchive를 iPhone 설치 산출물로 연결함
- Android와 iOS 매니페스트의 소스 또는 runtimeVersion 불일치
- 설치 관찰 결과의 앱 버전이 빌드와 다름
- 서명 주장이 다른 산출물을 가리킴
- 스토어 빌드 참조와 배포용 산출물 불일치
- 네이티브 패키지 변경 뒤 runtimeVersion 유지
- 이전 DB에서 업그레이드 실패
- 미리보기에서는 성공하지만 운영 설정이 다름
- 실행하지 않은 스토어 항목을 검증 완료로 표시함

## 완료 기준

- 애플리케이션 ID, 앱 버전, 빌드 번호, runtimeVersion과 소스 리비전을 구분합니다.
- 개발, 미리보기, 운영의 앱 식별 정보와 연결 대상을 분리합니다.
- 서명 인증 정보의 조직 소유와 복구 절차를 설명할 수 있습니다.
- 빌드 입력과 산출물 해시값을 기록합니다.
- Android 배포용 산출물과 설치 가능한 산출물을 구분합니다.
- iOS 아카이브, IPA와 TestFlight와 시뮬레이터 산출물을 구분합니다.
- 설치 근거를 정확한 산출물 참조에 연결합니다.
- 네이티브 API가 바뀔 때 새 바이너리와 runtimeVersion이 필요한지 판정합니다.
- 원격 업데이트 문제와 스토어 바이너리 문제의 대응을 구분합니다.
- Android와 iOS 운영 환경에 가까운 산출물을 설치하고 업그레이드를 확인합니다.
- 실행하지 않은 서명, 스토어, 전달 항목을 `not-run`으로 남깁니다.
