# 학습 로드맵

이 가이드는 문서를 모두 읽은 뒤 구현을 시작하는 순서로 진행하지 않습니다. 프로젝트에 필요한 모든 도메인 지식을 미리 공부하면 진입이 늦어지고, 아직 사용하지 않은 정보는 쉽게 잊힙니다.

따라서 다음 순서를 사용합니다.

```text
기초 문서 3개 정독
→ 실제 프로젝트 시작
→ 구현 중 필요한 문서만 정독
→ 프로젝트 완료 및 검증
→ 장애 진단 문서로 경험 정리
→ notes-stack 재구현
→ 부족한 부분만 복습
```

## 1. 프로젝트 진입 전에 읽을 문서

다음 세 문서는 특정 제품이나 프로젝트에 종속되지 않는 기초입니다.

1. [`웹 요청과 서버`](01-foundations/01-web-request-and-server.md)
2. [`Docker 이미지와 컨테이너`](01-foundations/02-docker-image-and-container.md)
3. [`Compose, 네트워크와 저장소`](01-foundations/03-compose-network-and-storage.md)

### 이 단계의 목표

다음을 설명할 수 있으면 프로젝트를 시작합니다.

- 클라이언트가 주소와 포트로 연결한 뒤 HTTP 요청을 보냅니다.
- HTTP 오류와 연결 실패는 서로 다른 단계에서 발생합니다.
- 컨테이너는 이미지에서 시작한 격리된 프로세스이며, PID 1이 끝나면 컨테이너도 끝납니다.
- Compose 서비스는 같은 네트워크에서 서비스 이름으로 서로를 찾습니다.
- 호스트에 공개하는 포트와 컨테이너끼리 사용하는 포트는 다릅니다.
- 이름 있는 볼륨은 컨테이너를 다시 만들어도 유지됩니다.

세부 옵션을 암기할 필요는 없습니다. 구현을 시작할 수 있을 만큼 실행 모델을 이해하는 것이 목표입니다.

## 2. 실제 프로젝트에 바로 진입

기초 문서를 읽은 뒤에는 실습를 먼저 구현하지 않습니다. 실제 요구사항을 가진 프로젝트를 시작합니다.

처음부터 완벽한 설계를 만들려고 하지 않습니다. 다음 항목부터 확인합니다.

1. 실행해야 하는 프로세스는 무엇인가?
2. 각 프로세스는 어느 주소와 포트에서 연결을 기다리는가?
3. 외부에 공개할 서비스는 무엇인가?
4. 컨테이너를 교체해도 남아야 하는 데이터는 무엇인가?
5. 시작할 때 필요한 설정과 비밀값은 무엇인가?
6. 정상 동작을 어떤 명령으로 확인할 것인가?

구현하면서 모르는 기술이 나타나면 해당 문서를 그때 읽습니다.

## 3. 필요할 때 읽을 문서

### Nginx, TLS와 PHP-FPM이 필요할 때

[`Nginx, TLS와 PHP-FPM`](02-service-stack/04-nginx-tls-and-php-fpm.md)을 읽습니다.

다음 문제를 해결할 때 사용합니다.

- HTTPS를 어느 프로세스가 처리할지 정합니다.
- 정적 파일과 PHP 요청을 나눕니다.
- Nginx가 PHP-FPM을 어떤 이름과 포트로 찾을지 정합니다.
- `SCRIPT_FILENAME`이 PHP-FPM 컨테이너 안의 실제 파일을 가리키게 합니다.
- 게이트웨이 자체 상태와 전체 애플리케이션 상태를 구분합니다.

### MariaDB 컨테이너를 만들 때

[`데이터베이스 생명주기`](02-service-stack/05-database-lifecycle.md)를 읽습니다.

다음 문제를 해결할 때 사용합니다.

- 빈 데이터 디렉터리와 기존 데이터를 구분합니다.
- `mariadb-install-db`와 초기 설정용 임시 서버를 사용합니다.
- 초기 설정이 끝나기 전에 TCP 연결을 받지 않게 합니다.
- 최종 `mariadbd`를 PID 1로 실행합니다.
- 볼륨, 백업과 복원의 차이를 구분합니다.

### 애플리케이션 시작 작업이 필요할 때

[`반복 가능한 애플리케이션 초기화`](02-service-stack/06-idempotent-app-bootstrap.md)를 읽습니다.

다음 문제를 해결할 때 사용합니다.

- 필수 환경변수와 비밀값 파일을 시작 초기에 검증합니다.
- 데이터베이스 연결을 무한히 기다리지 않습니다.
- 스키마와 초기 데이터를 여러 번 실행해도 중복하지 않습니다.
- 부분 실패 뒤 다시 실행할 수 있게 합니다.
- 초기화가 성공한 뒤 최종 서버 프로세스를 `exec`합니다.

## 4. 프로젝트 완료 기준

“컨테이너가 실행 중”인 상태만으로 완료하지 않습니다. 최소한 다음을 확인합니다.

- 깨끗한 환경에서 이미지를 다시 빌드할 수 있습니다.
- 외부에는 의도한 포트만 공개됩니다.
- 내부 서비스는 고정 IP가 아니라 서비스 이름으로 연결됩니다.
- 애플리케이션과 데이터베이스를 다시 만들어도 영속 데이터가 남습니다.
- 빈 볼륨에서만 초기화가 실행됩니다.
- 필수 설정이나 비밀값이 없으면 명확한 오류와 실패 종료 상태를 반환합니다.
- 정상 종료 시 주 프로세스가 SIGTERM을 받습니다.
- 실제 사용자 경로를 요청해 결과를 확인합니다.

프로젝트에서 제공하는 검증 절차를 모두 통과한 뒤 다음 단계로 이동합니다.

## 5. 완료 후 장애 진단 정리

프로젝트를 완료했거나 충분한 장애를 경험한 뒤 [`운영, 장애 진단과 복구`](02-service-stack/07-operations-debugging-and-recovery.md)를 읽습니다.

다음 순서를 자신의 경험과 연결합니다.

```text
Compose 설정
→ 컨테이너 상태
→ PID 1과 작업 프로세스
→ 수신 포트
→ 서비스 이름 해석
→ TCP 연결
→ TLS, HTTP, FastCGI 또는 DB 프로토콜
→ 설정과 비밀값
→ 파일 권한과 볼륨
→ 사용자 기능
```

이 문서는 문제를 만나기 전에 외우는 목록이 아니라, 이미 겪은 실패를 재사용 가능한 진단 순서로 정리하는 단계입니다.

## 6. 개발 능력 재확인

마지막에는 [`notes-stack`](../exercises/notes-stack/README.md)을 구현합니다.

이 실습는 튜토리얼이 아닙니다. README에 적힌 동작과 완료 조건만 보고 다음 시스템을 다시 구성합니다.

```text
HTTPS 요청
→ Nginx
→ PHP-FPM
→ MariaDB
→ 이름 있는 볼륨
```

### 수행 조건

- 이 가이드의 본문을 다시 읽지 않습니다.
- 이전 프로젝트나 이전 실습의 소스를 복사하지 않습니다.
- 완성 구현을 보지 않습니다.
- 공식 문서, 명령 도움말, 오류 메시지는 사용할 수 있습니다.
- 설계와 구현 순서는 직접 정합니다.

암기력을 시험하는 것이 아니라, 문제를 나누고 필요한 정보를 찾아 다시 구현할 수 있는지 확인하는 과정입니다.

### 판정

- 정상 시작과 API 요청이 성공합니다.
- 애플리케이션 재시작 뒤 초기 데이터가 중복되지 않습니다.
- 무상태 컨테이너 재생성 뒤 사용자 데이터가 유지됩니다.
- 백업으로 삭제한 테이블을 복원할 수 있습니다.
- 잘못된 호스트, 비밀번호, 비밀값 경로, FastCGI 포트와 상태 검사를 각각 재현하고 원인을 설명할 수 있습니다.

## 7. 복습 기준

실습에서 실패했다고 전체 가이드를 다시 읽지 않습니다.

| 실패 유형 | 다시 볼 문서 |
|---|---|
| 주소, 포트, HTTP 오류 구분 실패 | 01 |
| PID 1, 이미지, 컨테이너 수명 실패 | 02 |
| 서비스 이름, 공개 포트, 볼륨 실패 | 03 |
| TLS, Nginx, FastCGI, PHP-FPM 실패 | 04 |
| MariaDB 최초 초기화와 데이터 보존 실패 | 05 |
| 재시도, 멱등성, 비밀값, `exec` 실패 | 06 |
| 원인을 좁히지 못하고 여러 설정을 동시에 변경함 | 07 |

실패한 범위만 확인한 뒤 같은 조건을 처음부터 다시 검증합니다.

## 최종 완료 기준

다음 질문에 코드 없이 답할 수 있어야 합니다.

1. Nginx, PHP-FPM, MariaDB는 각각 어떤 프로토콜을 받습니까?
2. 각 프로세스는 어느 컨테이너의 PID 1 또는 작업 프로세스로 실행됩니까?
3. 외부 공개 포트와 내부 전용 포트는 무엇입니까?
4. 데이터베이스 볼륨을 유지한 컨테이너 재생성과 `down -v`는 결과가 어떻게 다릅니까?
5. MariaDB 최초 초기화 중 TCP를 끄는 이유는 무엇입니까?
6. 초기 데이터 마커와 데이터 삽입을 같은 트랜잭션에 두는 이유는 무엇입니까?
7. 게이트웨이 상태 검사가 성공해도 사용자 요청이 502가 될 수 있는 이유는 무엇입니까?
8. 백업 파일이 존재하는 것과 복구 가능성이 검증된 것은 어떻게 다릅니까?

이 질문에 답하고 `notes-stack`의 모든 검사를 통과하면 가이드의 목표를 달성한 것으로 봅니다.
