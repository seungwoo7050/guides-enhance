# 선형 자료구조, 구간과 해시

## 학습 목표

- 배열, 연결 구조, stack, queue, deque를 이름이 아니라 필요한 연산을 기준으로 구분합니다.
- 반열린 구간 `[left, right)`와 누적 합을 사용해 구간 길이와 index 경계를 일관되게 다룹니다.
- two pointers, sliding window, monotonic stack·deque를 적용할 수 있는 조건과 적용할 수 없는 조건을 구분합니다.
- hash table의 기대 시간 복잡도, 충돌, key의 동등성·불변성 조건을 설명합니다.

## 선행지식

다음 내용을 먼저 이해하면 이 문서를 읽기 쉽습니다.

- 배열과 list의 index
- [점근 분석](../01-foundations/02-asymptotic-analysis.md)
- 입력 크기와 입력 조건을 명시하는 방법
- `O(1)`, `O(n)`, 상각 분석(amortized analysis)의 기본 의미

이 문서에서 `n`은 일반적으로 입력 원소의 개수를 뜻합니다.

## 핵심 관점

자료구조는 익숙한 이름이나 구현 편의가 아니라 **필요한 연산과 그 빈도**를 기준으로 고릅니다.

먼저 다음 질문을 적습니다.

```text
어떤 값을 자주 읽습니까?
어디에 삽입하고 어디에서 삭제합니까?
입력 순서를 보존해야 합니까?
최솟값, 최댓값, 가장 최근 값 중 무엇이 필요합니까?
key로 찾습니까, 위치(index)로 찾습니까?
중간 삽입·삭제가 실제로 자주 일어납니까?
```

같은 데이터를 저장하더라도 필요한 연산이 다르면 적합한 자료구조도 달라집니다.

## 1. 선형 자료구조의 연산

선형 자료구조는 원소가 논리적으로 한 줄의 순서를 이루는 자료구조입니다. 다만 각 자료구조가 그 순서를 저장하고 접근하는 방식은 다릅니다.

| 자료구조 | 잘 지원하는 연산 | 주의할 연산 |
| --- | --- | --- |
| 동적 배열 | index를 이용한 임의 위치 읽기, 뒤쪽 `append` | 중간 삽입·삭제, 재할당 시 원소 이동 |
| 연결 구조 | 대상 node를 이미 알고 있을 때 그 주변 삽입·삭제 | 임의 위치 접근, 낮은 cache locality |
| stack | 가장 최근 원소의 `push`·`pop` | 중간 원소 접근 |
| queue | 먼저 들어온 원소를 먼저 처리하는 삽입·삭제 | 뒤쪽 원소 제거, 임의 위치 접근 |
| deque | 양끝 삽입·삭제 | 일반적인 중간 삽입·삭제 |

### 동적 배열

동적 배열은 연속된 메모리 영역에 원소를 저장하므로 index로 임의 위치에 접근하는 비용이 보통 `O(1)`입니다.

그러나 중간에 원소를 삽입하거나 삭제하면 뒤쪽 원소들을 이동해야 할 수 있으므로 보통 `O(n)`입니다.

```text
[10, 20, 30, 40]
        ↑
        여기에 25를 삽입

[10, 20, 25, 30, 40]
```

`30`, `40`을 뒤로 이동해야 하므로 단순한 `O(1)` 연산이 아닙니다.

### `append`와 상각 비용

동적 배열의 뒤쪽 `append`는 매 호출의 최악 비용이 항상 `O(1)`인 것은 아닙니다.

내부 공간이 부족하면 보통 다음 작업이 필요합니다.

```text
더 큰 메모리 공간 할당
기존 원소를 새 공간으로 이동 또는 복사
새 원소 추가
기존 공간 해제
```

이 한 번의 확장 작업은 `O(n)`이 될 수 있습니다. 그러나 배열이 일정 비율로 용량을 늘리는 구현에서는 여러 번의 `append` 비용을 전체적으로 나누어 보면 원소 하나당 평균 비용이 상수에 가까워집니다.

따라서 일반적으로 다음과 같이 표현합니다.

```text
append의 상각 시간 복잡도: O(1)
한 번의 append의 최악 시간 복잡도: O(n)
```

여기서 **상각 분석**은 확률적 평균을 뜻하는 것이 아니라, 여러 연산의 전체 비용을 연산 횟수에 나누어 보는 분석입니다.

### 연결 구조

연결 list 같은 구조는 각 node가 다음 node 또는 이전·다음 node의 위치를 저장합니다.

대상 node를 이미 알고 있다면 그 주변의 연결만 수정하여 삽입·삭제할 수 있습니다.

```text
A <-> B <-> C

B와 C 사이에 X 삽입

A <-> B <-> X <-> C
```

그러나 "100번째 원소"처럼 위치만 알고 있다면 첫 node부터 연결을 따라가야 하므로 접근 자체가 `O(n)`일 수 있습니다.

따라서 다음 두 문장은 구분해야 합니다.

```text
node를 알고 있을 때 삽입·삭제: O(1)일 수 있음
index만 알고 있을 때 해당 node를 찾는 비용: O(n)
```

또한 연결 구조는 node가 메모리에 흩어져 있을 수 있어 연속 배열보다 cache locality가 나쁠 수 있습니다.

### stack, queue, deque

이들은 저장 방식보다 **허용하는 접근 규칙**이 핵심입니다.

```text
stack: 마지막에 들어온 원소가 먼저 나옴
queue: 먼저 들어온 원소가 먼저 나옴
deque: 앞과 뒤 모두에서 삽입·삭제 가능
```

문제의 요구가 이 규칙과 맞으면 불필요한 임의 접근을 막고 구현을 단순하게 만들 수 있습니다.

## 2. 반열린 구간

배열 구간을 표현할 때 `[left, right)`처럼 **왼쪽 경계는 포함하고 오른쪽 경계는 제외하는 구간**을 반열린 구간이라고 합니다.

```text
[left, right)

포함되는 index:
left, left + 1, ..., right - 1
```

예를 들어 다음 배열이 있다고 하겠습니다.

```text
index:  0   1   2   3   4
value: 10  20  30  40  50
```

`[1, 4)`는 index `1`, `2`, `3`을 포함합니다.

```text
[20, 30, 40]
```

### 반열린 구간의 핵심 성질

`[left, right)`는 다음 성질을 가집니다.

- 길이는 `right - left`입니다.
- `left == right`이면 길이가 `0`인 빈 구간입니다.
- `[a, b)`와 `[b, c)`는 경계 `b`를 공유하지만 원소는 겹치지 않습니다.
- 길이 `n`인 배열 전체는 `[0, n)`입니다.
- 마지막으로 포함되는 index는 `right - 1`입니다. 단, 빈 구간에서는 포함되는 index가 없습니다.

예:

```text
[2, 5)의 길이 = 5 - 2 = 3
포함 index = 2, 3, 4

[3, 3)의 길이 = 0
포함 index = 없음

길이 5 배열 전체 = [0, 5)
```

반열린 구간을 쓰면 "끝 index"와 "길이"를 따로 보정하기 위한 `+1`, `-1`이 줄어듭니다.

## 3. 누적 합

배열 `A`의 여러 구간 합을 반복해서 구해야 한다면 누적 합(prefix sum)을 사용할 수 있습니다.

다음과 같이 정의합니다.

```text
prefix[0] = 0
prefix[i + 1] = prefix[i] + A[i]
```

즉 `prefix[i]`는 배열의 첫 원소부터 `i - 1`번째 원소까지의 합입니다.

```text
prefix[i] == sum(A[0:i])
```

예를 들어 다음 배열이 있다고 하겠습니다.

```text
A = [3, 5, 2, 7]
```

누적 합은 다음과 같습니다.

```text
prefix = [0, 3, 8, 10, 17]
```

각 값의 의미는 다음과 같습니다.

```text
prefix[0] = 0
prefix[1] = 3
prefix[2] = 3 + 5 = 8
prefix[3] = 3 + 5 + 2 = 10
prefix[4] = 3 + 5 + 2 + 7 = 17
```

구간 `[left, right)`의 합은 다음 두 누적 합의 차이입니다.

```text
sum(left, right) = prefix[right] - prefix[left]
```

예를 들어 `[1, 3)`의 합은 `5 + 2 = 7`입니다.

```text
prefix[3] - prefix[1]
= 10 - 3
= 7
```

빈 구간도 별도 예외 처리 없이 계산됩니다.

```text
sum(2, 2)
= prefix[2] - prefix[2]
= 0
```

배열 전체도 같은 식을 사용합니다.

```text
sum(0, n)
= prefix[n] - prefix[0]
= prefix[n]
```

### 시간과 공간 복잡도

```text
누적 합 생성: O(n)
한 번의 구간 합 질의: O(1)
추가 공간: O(n)
```

### 유지해야 할 불변식

누적 합 구현에서는 다음 조건을 유지해야 합니다.

```text
len(prefix) == n + 1
0 <= left <= right <= n
prefix[i] == sum(A[0:i])
```

이 세 조건이 유지되면 빈 구간, 배열 전체, 일반 구간을 모두 같은 공식으로 처리할 수 있습니다.

## 4. 차분 배열

여러 구간에 같은 값을 더한 뒤 **모든 갱신이 끝난 최종 배열만 필요하다면** 차분 배열(difference array)을 사용할 수 있습니다.

구간 `[left, right)`에 `value`를 더하고 싶다고 하겠습니다.

```text
A[left:right]에 value를 더함
```

차분 배열에서는 다음 두 위치만 수정합니다.

```text
diff[left] += value
diff[right] -= value
```

`right == n`인 경우까지 같은 규칙을 사용하려면 보통 `diff`의 길이를 `n + 1`로 두면 편리합니다.

### 왜 두 곳만 수정하는가

누적 합으로 `diff`를 복원한다고 가정하겠습니다.

```text
current += diff[i]
A[i] += current
```

`left`에서 `value`를 더하면 그 뒤의 모든 위치에 영향이 이어집니다. `right`에서 다시 `value`를 빼면 그 영향이 `[left, right)`에서만 유지됩니다.

예:

```text
길이 5 배열의 [1, 4)에 +3
```

차분 배열 변경:

```text
diff[1] += 3
diff[4] -= 3
```

누적하면 적용되는 값은 다음과 같습니다.

```text
index:       0  1  2  3  4
추가되는 값: 0  3  3  3  0
```

### 적합한 경우와 부적합한 경우

차분 배열은 다음 상황에 적합합니다.

```text
구간 갱신을 많이 수행
중간 결과는 거의 필요 없음
모든 갱신 뒤 최종 배열을 한 번 복원
```

반대로 갱신 도중에 다음 질의를 반복해야 한다면 단순 차분 배열만으로는 충분하지 않습니다.

```text
현재 A[i]는 얼마인가?
현재 [left, right)의 합은 얼마인가?
갱신과 질의가 번갈아 발생한다.
```

이 경우에는 문제에 따라 Fenwick tree나 segment tree처럼 갱신과 질의를 함께 지원하는 자료구조가 필요할 수 있습니다.

## 5. two pointers와 sliding window

### 공통 핵심

two pointers는 두 개의 index를 움직이며 탐색 범위를 관리하는 기법입니다.

sliding window는 그중에서도 보통 현재 구간 `[left, right)`의 상태를 유지하면서 한쪽 경계를 확장하고 다른 쪽 경계를 축소하는 형태를 말합니다.

중요한 것은 pointer의 개수가 아니라 다음 조건입니다.

> 한 번 버린 후보가 나중에 다시 정답 후보가 될 필요가 없는가?

이 조건을 보장하는 문제의 **단조성** 또는 구조가 있어야 pointer를 한 방향으로만 움직일 수 있습니다.

### 전형적인 형태

```text
현재 구간: [left, right)
저장값: 정확히 이 구간에 대한 합, 빈도, 조건 만족 여부 등

right를 오른쪽으로 이동하며 새 원소를 추가
조건을 위반하는 동안 left를 오른쪽으로 이동하며 원소를 제거
```

각 pointer가 최대 `n`번 움직이면 전체 시간 복잡도는 보통 `O(n)`입니다.

### 예: 모든 값이 음수가 아닌 경우

배열의 모든 값이 `0` 이상이고, 구간 합이 어떤 상한 `limit` 이하인 구간을 유지한다고 하겠습니다.

오른쪽에 원소를 추가하면 합은 감소하지 않습니다.

```text
sum(new window) >= sum(old window)
```

합이 `limit`을 초과했다면 왼쪽 원소를 제거하면 합이 감소하거나 그대로이므로 조건을 회복하는 방향이 명확합니다.

이러한 단조성 때문에 다음 전략이 안전합니다.

```text
right를 늘린다.
합이 너무 크면 left를 늘린다.
한 번 제거한 왼쪽 원소를 다시 포함할 필요가 없다.
```

### 음수가 섞일 때 실패하는 이유

음수가 있으면 오른쪽을 늘렸을 때 합이 증가할 수도 있고 감소할 수도 있습니다.

예:

```text
A = [5, -10, 8]
```

`5`만 보았을 때 어떤 합 조건을 위반했다고 해서 왼쪽의 `5`를 바로 버리면, 뒤에 `-10`이 들어왔을 때 다시 유효해질 수 있는 구간을 잃을 수 있습니다.

즉 다음 가정이 깨집니다.

```text
오른쪽을 늘리면 합이 한 방향으로만 변한다.
```

따라서 "구간 합 문제이므로 sliding window를 사용한다"가 아니라, **경계를 한 방향으로 이동해도 정답 후보를 잃지 않는지** 먼저 확인해야 합니다.

### two pointers가 항상 sliding window는 아니다

정렬된 배열에서 두 수의 합을 찾는 다음 방식도 two pointers입니다.

```text
left = 0
right = n - 1

합이 작으면 left 증가
합이 크면 right 감소
```

이 방식은 `[left, right)`의 상태를 유지하는 sliding window와는 다르지만, 정렬로 인해 어느 방향의 후보를 버려도 되는지가 보장된다는 점은 같습니다.

## 6. monotonic stack과 monotonic deque

monotonic stack 또는 monotonic deque는 **앞으로 절대 정답이 될 수 없는 후보를 미리 제거**하면서 후보를 단조 순서로 유지하는 기법입니다.

대표적인 문제는 다음과 같습니다.

- 다음 큰 원소
- 이전 작은 원소
- 고정 길이 창의 최댓값·최솟값

### 후보를 제거할 수 있는 이유

창의 최댓값을 구한다고 하겠습니다.

현재 후보 뒤쪽에 더 큰 새 값이 들어왔다면, 기존의 더 작은 값은 다음 두 조건에서 새 값보다 불리합니다.

```text
기존 값보다 새 값이 더 큼
새 값이 더 나중에 들어왔으므로 더 늦게 만료됨
```

따라서 기존의 더 작은 값은 이후 어떤 창에서도 새 값보다 최댓값 후보로 유리할 수 없습니다.

이런 후보를 deque의 뒤쪽에서 제거합니다.

### sliding window maximum의 전형적인 규칙

deque에는 **값이 아니라 index**를 저장한다고 하겠습니다.

새 index `i`를 처리할 때:

```text
1. 창을 벗어난 index를 앞쪽에서 제거
2. A[i] 이상으로 인해 앞으로 필요 없는 뒤쪽 후보를 제거
3. i를 뒤쪽에 추가
4. deque의 앞쪽 index가 현재 창의 최댓값
```

예를 들어 큰 값이 앞에 오도록 deque를 유지하면 다음 관계를 만족합니다.

```text
A[dq[0]] >= A[dq[1]] >= A[dq[2]] >= ...
```

구현에 따라 같은 값을 유지할지 제거할지는 달라질 수 있지만, 만료 처리와 중복 값 처리를 일관되게 해야 합니다.

### 왜 index를 저장하는가

창 크기가 `k`이면 index `i`에서 현재 창은 보통 다음 범위입니다.

```text
[i - k + 1, i]
```

또는 반열린 구간으로:

```text
[i - k + 1, i + 1)
```

deque 앞의 후보가 이 범위보다 왼쪽에 있으면 만료된 원소입니다.

값만 저장하면 같은 값이 여러 번 존재할 때 어느 값이 오래된 값인지 알 수 없습니다.

예:

```text
A = [5, 5, 1]
```

deque가 값 `5, 5`만 저장한다면 첫 번째 `5`와 두 번째 `5`의 만료 시점을 구분하기 어렵습니다.

index를 저장하면 다음처럼 명확합니다.

```text
deque = [0, 1]

index 0의 5와 index 1의 5를 구분 가능
```

### 전체가 `O(n)`인 이유

내부에 `while` 반복문이 있어도 각 원소는 보통 다음 횟수만큼만 처리됩니다.

```text
deque에 최대 한 번 들어감
deque에서 최대 한 번 나옴
```

따라서 전체 삽입·삭제 횟수는 `O(n)`이고 전체 시간 복잡도도 `O(n)`입니다.

## 7. hash table

hash table은 key를 hash 값으로 변환하고, 그 결과를 사용해 저장 위치인 bucket을 찾는 자료구조입니다.

개념적으로는 다음 단계가 있습니다.

```text
key
 -> hash 계산
 -> bucket 결정
 -> 같은 bucket의 후보 중 실제 key 비교
```

서로 다른 key가 같은 bucket으로 가는 현상을 **충돌(collision)**이라고 합니다.

충돌은 hash table에서 정상적으로 발생할 수 있으며, 구현은 chaining, open addressing 등의 방식으로 이를 처리합니다.

### key가 만족해야 할 조건

hash 기반 자료구조의 key는 최소한 다음 조건을 만족해야 합니다.

#### 1. 동등한 key는 같은 hash를 가져야 합니다

두 key가 동등성 비교에서 같다면 hash 값도 같아야 합니다.

개념적으로:

```text
a == b  이면  hash(a) == hash(b)
```

반대는 필요하지 않습니다.

```text
hash(a) == hash(b)
```

라고 해서 반드시 `a == b`인 것은 아닙니다. 이것이 충돌입니다.

#### 2. 동등성 비교와 hash 계산은 같은 기준을 사용해야 합니다

예를 들어 사용자 객체를 이름만으로 같다고 판단하면서 hash는 이름과 나이를 모두 사용하면 모순이 생길 수 있습니다.

```text
equality 기준: name
hash 기준: name + age
```

같다고 판단되는 두 객체의 hash가 달라질 수 있으므로 올바른 key 동작을 보장할 수 없습니다.

#### 3. 저장 중 hash에 영향을 주는 값이 바뀌면 안 됩니다

key를 삽입한 뒤 그 key의 hash 값이나 동등성 결과가 바뀌면, 자료구조가 처음 저장한 bucket과 나중에 조회할 bucket이 달라질 수 있습니다.

개념적으로:

```text
삽입 시:
key -> hash 10 -> bucket 10

key 내부 값 변경

조회 시:
key -> hash 27 -> bucket 27
```

원소는 bucket 10에 있는데 조회는 bucket 27을 확인하게 되어 찾지 못할 수 있습니다.

따라서 **hash와 동등성에 참여하는 값은 key가 저장된 동안 변하지 않아야 합니다.**

언어에 따라 mutable object 자체를 key로 금지하기도 하고, mutable object라도 hash에 참여하는 상태가 변하지 않도록 개발자가 책임져야 하는 경우도 있습니다.

### 기대 비용과 최악 비용

hash table의 조회·삽입·삭제는 일반적으로 다음과 같이 설명합니다.

```text
기대 또는 평균적 비용: O(1)
최악 비용: O(n)까지 증가할 수 있음
```

최악 비용이 커질 수 있는 이유는 여러 key가 같은 bucket에 몰리거나, table 상태가 좋지 않거나, 구현의 충돌 처리 방식에 따라 많은 후보를 검사해야 할 수 있기 때문입니다.

따라서 다음 표현은 피해야 합니다.

```text
hash 조회는 항상 O(1)이다.
```

더 정확한 표현은 다음과 같습니다.

```text
적절한 hash 분포와 load 상태를 가정하면 조회는 보통 기대 O(1)이다.
```

### hash 계산 비용도 포함해야 한다

`O(1)`이라는 표현은 key 자체가 상수 크기라고 가정할 때 단순해집니다.

예를 들어 길이 `m`인 문자열 key의 hash를 매번 처음부터 계산해야 한다면 hash 계산 자체가 `O(m)`일 수 있습니다.

```text
긴 문자열 key
긴 tuple key
큰 immutable composite key
```

따라서 실제 비용을 분석할 때는 bucket 접근뿐 아니라 key의 hash 계산과 동등성 비교 비용도 고려해야 합니다.

### 자주 저장하는 정보

문제에서 hash table에는 보통 다음과 같은 정보를 저장합니다.

```text
등장 여부:
set

빈도:
key -> count

마지막 위치:
key -> latest index

최초 위치:
key -> earliest index

누적값의 최초 위치:
prefix value -> earliest index
```

무엇을 저장할지는 "나중에 어떤 정보를 다시 알아야 하는가"를 기준으로 결정합니다.

## 8. 예제: 합이 `k`인 가장 긴 부분 배열

배열에 음수가 허용되면 단순한 sliding window는 일반적으로 사용할 수 없습니다.

대신 누적 합과 hash table을 결합할 수 있습니다.

### 누적 합 관계

`S[i]`를 앞에서부터 특정 위치까지의 누적 합이라고 하겠습니다.

반열린 구간 정의를 사용하면 다음처럼 둘 수 있습니다.

```text
S[0] = 0
S[i] = A[0] + A[1] + ... + A[i - 1]
```

그러면 구간 `[j, i)`의 합은 다음과 같습니다.

```text
S[i] - S[j]
```

이 값이 `k`이려면:

```text
S[i] - S[j] = k
```

따라서:

```text
S[j] = S[i] - k
```

현재 누적 합이 `S[i]`라면 과거에 `S[i] - k`가 등장했는지 찾으면 됩니다.

### 왜 최초 위치를 저장하는가

가장 긴 구간을 원한다면 같은 누적값이 여러 번 나왔을 때 **가장 이른 위치**를 저장해야 합니다.

현재 위치 `i`가 고정되어 있을 때 구간 길이는 다음과 같습니다.

```text
i - j
```

`j`가 작을수록 구간이 더 깁니다.

따라서 같은 누적값이 다시 등장해도 기존 최초 위치를 덮어쓰지 않습니다.

### 실패 예제

다음 배열에서 합이 `3`인 가장 긴 부분 배열을 찾는다고 하겠습니다.

```text
A = [1, -1, 1, 1, 1]
k = 3
```

누적 합은 다음과 같습니다.

```text
index i:  0  1  2  3  4  5
S[i]:     0  1  0  1  2  3
```

`S = 0`은 index `0`과 `2`에서 나타납니다.

마지막 `i = 5`에서:

```text
S[i] - k
= 3 - 3
= 0
```

`0`의 최초 위치 `j = 0`을 사용하면:

```text
구간 [0, 5)
길이 5
합 3
```

그러나 `S = 0`이 index `2`에서 다시 나타났을 때 위치를 덮어썼다면:

```text
j = 2
구간 [2, 5)
길이 3
```

만 찾게 되어 더 긴 정답을 잃습니다.

따라서 가장 긴 구간을 구할 때는 다음 규칙을 유지합니다.

```text
누적값이 처음 등장했을 때만 위치를 저장한다.
```

## 9. 자료구조를 바꿀 때 확인할 비용

자료구조를 바꾸면 한 연산이 빨라지는 대신 다른 연산이 느려질 수 있습니다. 자료구조 이름만 보고 "더 효율적"이라고 판단하지 않습니다.

### 배열을 연결 list로 바꾸는 경우

연결 list는 node를 알고 있을 때 삽입·삭제가 유리할 수 있지만, 임의 index 접근은 느려집니다.

```text
배열:
A[1000] 접근 -> 보통 O(1)

연결 list:
1000번째 node 찾기 -> 보통 O(n)
```

### queue를 Python `list.pop(0)`로 구현하는 경우

Python list는 동적 배열이므로 맨 앞 원소를 제거하면 뒤 원소들을 앞으로 이동해야 합니다.

```text
list.pop(0) -> O(n)
```

queue가 필요하다면 양끝 삽입·삭제를 효율적으로 지원하는 deque 계열 구조가 더 적합합니다.

### 전체 정렬과 heap을 혼동하는 경우

모든 원소의 완전한 정렬 순서가 필요하지 않고 "가장 작은 값 몇 개" 또는 "현재 최솟값 하나"만 반복해서 필요하다면 전체 배열을 매번 정렬하는 것은 불필요한 비용이 될 수 있습니다.

다만 heap이 항상 정렬보다 낫다는 뜻은 아닙니다. 필요한 연산이 무엇인지 먼저 확인해야 합니다.

### 긴 hash key를 사용하는 경우

hash table의 bucket 접근만 보면 기대 `O(1)`이지만, key가 긴 문자열이나 큰 tuple이면 hash 계산과 비교 비용이 커질 수 있습니다.

예를 들어 key 길이를 `m`이라고 하면 실제 분석에서 다음 비용이 중요할 수 있습니다.

```text
hash 계산: O(m)
동등성 비교: 최악 O(m)
```

## 10. 선택 절차

문제를 볼 때 다음 순서로 판단하면 자료구조를 이름부터 고르는 실수를 줄일 수 있습니다.

```text
1. 필요한 연산을 적는다.
2. 각 연산이 몇 번 발생하는지 본다.
3. 입력 조건에서 버려도 되는 후보가 무엇인지 확인한다.
4. 필요한 불변식을 적는다.
5. 후보 자료구조의 시간·공간 비용을 비교한다.
6. 최악 비용과 기대·상각 비용을 구분한다.
```

예:

```text
필요:
- 오른쪽에서 원소 추가
- 왼쪽에서 오래된 원소 제거
- 현재 최대값 조회

추가 조건:
- 고정 길이 창
- 오래된 index는 다시 필요 없음
- 더 작고 더 오래된 값은 앞으로 최대값이 될 수 없음

선택:
monotonic deque
```

자료구조 선택의 근거가 연산과 불변식으로 설명되어야 합니다.

## 연결 구현

[`verified-algorithms`](../../exercises/verified-algorithms/)의 `[Implementation 1]`에서 다음을 확인합니다.

- `prefix_sums`가 첫 값으로 `0`을 넣습니다.
- `range_sum`이 `[start, stop)`을 사용합니다.
- 빈 구간과 배열 전체를 같은 식으로 계산합니다.
- 잘못된 index 범위를 `ValueError`로 거부합니다.

exercise에는 sliding window와 monotonic deque가 포함되어 있지 않으므로, 창의 최댓값을 직접 구현하고 단순 검증 구현과 결과를 비교합니다.

단순 검증 구현은 각 창을 직접 순회해 최댓값을 계산하면 됩니다.

```text
창 개수: O(n)
창 하나의 최대값 계산: O(k)

전체: O(nk)
```

monotonic deque 구현은 각 index가 최대 한 번 들어가고 한 번 나오므로 전체 `O(n)`을 목표로 합니다.

두 구현의 출력이 모든 테스트 입력에서 같아야 합니다.

## 완료 기준

다음을 직접 설명하거나 구현할 수 있으면 이 문서의 핵심을 이해한 것입니다.

- `[start, stop)`의 길이가 `stop - start`인 이유를 설명합니다.
- 빈 구간 `[i, i)`와 배열 전체 `[0, n)`를 같은 규칙으로 처리합니다.
- 누적 합에서 `prefix`의 길이가 왜 `n + 1`인지 설명합니다.
- sliding window가 성립하려면 어떤 후보를 안전하게 버릴 수 있어야 하는지 설명합니다.
- 음수가 포함된 구간 합 문제에서 단순 sliding window가 실패할 수 있는 반례를 제시합니다.
- monotonic deque에서 더 약한 후보를 제거해도 되는 이유를 설명합니다.
- monotonic deque에 값이 아니라 index를 저장해야 하는 이유를 중복 값 예제로 설명합니다.
- hash table의 기대 `O(1)`과 최악 `O(n)`을 구분합니다.
- 동등성 비교와 hash 계산이 같은 기준을 사용해야 하는 이유를 설명합니다.
- 합이 `k`인 가장 긴 부분 배열 문제에서 누적값의 최초 위치를 덮어쓰면 실패하는 입력을 만듭니다.

## 실패 신호

다음과 같은 구현이나 설명이 보이면 개념을 다시 확인합니다.

- 구간 길이와 마지막 index를 같은 값처럼 사용합니다.
- `[left, right)`를 사용하면서 `right`번째 원소까지 포함한다고 설명합니다.
- 누적 합 배열을 길이 `n`으로 만들고 경계마다 별도 예외 처리를 추가합니다.
- sliding window의 단조 조건이나 후보 제거 근거를 확인하지 않습니다.
- 음수가 있는 구간 합 문제에 단순 sliding window를 기계적으로 적용합니다.
- monotonic deque에 값만 저장해 만료된 원소를 구분하지 못합니다.
- 내부 `while`문이 있다는 이유만으로 monotonic deque 알고리즘을 `O(n^2)`라고 판단합니다.
- hash 조회를 무조건 최악 `O(1)`이라고 표현합니다.
- hash 충돌이 발생하면 hash table이 잘못 구현된 것이라고 생각합니다.
- hash와 동등성에 참여하는 mutable 상태를 key 저장 중 변경합니다.
- 동등성 비교와 hash 계산 기준이 다릅니다.
- 가장 긴 부분 배열 문제에서 같은 누적값의 최초 위치를 더 최근 위치로 덮어씁니다.
