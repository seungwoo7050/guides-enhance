# SIMD, 벡터화와 데이터 배치

SIMD는 한 명령으로 여러 데이터 원소에 같은 종류의 연산을 적용합니다. 슈퍼스칼라가 여러 명령을 같은 사이클에 처리하는 명령 수준 병렬성이라면, SIMD는 한 명령 안의 여러 레인으로 데이터 수준 병렬성을 표현합니다. 여러 스레드를 여러 코어에서 실행하는 것과도 다른 방식입니다.

이 문서는 필수 경로를 마친 뒤 실제 벡터화 문제를 다룰 때 사용하는 선택 자료입니다.

## 학습 목표

- SIMD, 슈퍼스칼라와 다중 스레딩을 구분합니다.
- 반복 간 의존성과 포인터 별칭이 벡터화를 막는 이유를 설명합니다.
- 정렬, 남은 원소 처리, 마스크와 데이터 배치의 영향을 확인합니다.
- 검사 합계, 컴파일러 보고서와 어셈블리를 함께 사용해 벡터화 주장을 검증합니다.

## 스칼라와 벡터 연산

스칼라 덧셈은 원소를 하나씩 계산합니다.

```text
c0 = a0 + b0
c1 = a1 + b1
c2 = a2 + b2
c3 = a3 + b3
```

4레인 벡터 덧셈은 같은 연산을 한 명령 의미로 묶습니다.

```text
[c0 c1 c2 c3] = [a0 a1 a2 a3] + [b0 b1 b2 b3]
```

ISA가 여러 레인의 의미를 정하더라도 실제 하드웨어가 모든 레인을 한 사이클에 처리하는지는 마이크로아키텍처에 따라 다릅니다.

## SIMD와 슈퍼스칼라

```text
superscalar: instruction A와 instruction B를 함께 issue
SIMD:        instruction V가 element 0..N-1에 같은 연산 적용
```

두 방식을 함께 사용할 수 있습니다. 독립적인 벡터 명령 여러 개를 비순차 코어가 겹쳐 실행할 수도 있습니다.

## 벡터 폭

x86 SSE·AVX와 Arm NEON은 명령별 고정 폭 벡터를 제공합니다. RISC-V V는 구현의 벡터 길이에 맞춰 한 번에 처리할 원소 수를 정할 수 있습니다.

소스에서 특정 폭을 고정하면 다음 문제가 생길 수 있습니다.

- 더 넓거나 좁은 하드웨어에 맞추기 어렵습니다.
- 남은 원소를 처리하는 코드가 늘어납니다.
- 다른 ISA로 옮기기 어렵습니다.

자동 벡터화 또는 이식 가능한 라이브러리를 먼저 검토하고, 내장 함수는 실제 병목과 대상 ISA가 명확할 때 사용합니다.

## 반복문 독립성

다음 반복문은 각 인덱스가 다른 출력 원소를 씁니다.

```c
for (i = 0; i < n; ++i)
    output[i] = left[i] * scale + right[i];
```

입력과 출력 범위가 겹치지 않으면 여러 반복을 함께 계산할 수 있습니다.

다음 점화식은 이전 결과가 필요합니다.

```c
for (i = 0; i < n; ++i)
    value = value * factor + input[i];
```

`i+1`번째 반복이 `i`번째 반복의 `value`를 읽으므로 같은 방식으로 레인에 나누기 어렵습니다. 알고리즘을 스캔이나 트리 형태로 바꿀 수 있는지 별도로 검토해야 합니다.

## 포인터 별칭과 `restrict`

```c
void transform(
    float *output,
    const float *left,
    const float *right,
    size_t n
);
```

세 포인터의 접근 범위가 겹칠 수 있다면 출력 쓰기가 이후 입력 읽기를 바꿀 수 있습니다. 컴파일러는 실행 시점 별칭 검사를 만들거나 벡터화를 포기할 수 있습니다.

C의 `restrict`는 해당 포인터를 통해 접근하는 객체가 서로 겹치지 않는다는 강한 규칙입니다.

```c
void transform(
    float *restrict output,
    const float *restrict left,
    const float *restrict right,
    size_t n
);
```

호출자가 이 규칙을 어기면 동작이 정의되지 않습니다. 단순한 성능 힌트로 추가하면 안 됩니다.

## 정렬

벡터 적재가 특정 정렬을 요구하는 ISA도 있고, 정렬되지 않은 적재를 허용하지만 캐시 라인이나 페이지를 넘을 때 비용이 달라지는 구현도 있습니다.

컴파일러는 다음 방법을 사용할 수 있습니다.

- 정렬되지 않은 벡터 적재·저장
- 정렬된 지점까지 처리하는 스칼라 앞부분
- 실행 시점 정렬 검사 후 두 코드 경로 생성
- 마스크를 사용한 적재·저장

과도한 정렬은 메모리 사용량을 늘릴 수 있습니다. 할당과 해제 API도 맞아야 합니다.

## 남은 원소 처리

`n`이 레인 수의 배수가 아니면 마지막 원소가 남습니다.

- 스칼라 나머지 반복문
- 마스크 벡터 연산
- 패딩한 입력
- 벡터 길이를 남은 원소 수로 조정

패딩을 사용하더라도 실제 할당 범위 밖을 읽으면 안 됩니다.

## 마스크와 분기

레인마다 조건이 다르면 마스크를 만들 수 있습니다.

```text
mask = values > threshold
result = select(mask, transformed, original)
```

분기를 없애도 양쪽 계산을 모두 수행하거나 마스크 처리 비용이 들 수 있습니다. 조건 분포와 계산 비용을 측정해야 합니다.

## AoS와 SoA

구조체 배열(AoS):

```text
x0 y0 z0 x1 y1 z1 x2 y2 z2 ...
```

`x`만 처리하면 큰 보폭 접근 또는 gather가 필요할 수 있습니다.

배열 구조체(SoA):

```text
x0 x1 x2 x3 ...
y0 y1 y2 y3 ...
z0 z1 z2 z3 ...
```

연속한 `x`를 벡터로 적재하기 쉽습니다. 반대로 객체 하나의 모든 필드를 자주 사용하면 여러 메모리 구간을 읽어야 합니다.

배치 변경은 SIMD뿐 아니라 캐시 라인 사용, 직렬화 형식과 공개 API도 바꿉니다.

## gather와 scatter

인덱스 배열을 사용해 여러 주소의 원소를 모으거나 흩어 쓸 수 있습니다.

```text
values = gather(base, indices)
scatter(base, indices, results)
```

연속 적재보다 주소 계산과 캐시 실패가 많을 수 있고, 같은 목적지 인덱스가 중복될 때의 의미도 확인해야 합니다. 해당 명령이 있다고 무작위 접근이 연속 접근과 같은 비용이 되는 것은 아닙니다.

## 축약 연산과 부동소수점

합계 축약은 레인별 부분 합을 마지막에 합칩니다.

```text
partial sums
→ tree reduction
→ scalar result
```

부동소수점은 연산 순서가 바뀌면 마지막 비트가 달라질 수 있습니다. 정확도 요구에 따라 다음을 검토합니다.

- 쌍별 합산
- Kahan 합산
- 더 넓은 누산기
- 고정된 축약 순서
- 허용 오차 기반 검사

빠른 벡터 축약과 비트 단위로 같은 결과를 동시에 보장하기 어려울 수 있습니다.

## 컴파일러 보고서

다음 질문을 확인합니다.

1. 어느 반복문이 벡터화됐습니까?
2. 의존 관계 또는 별칭 때문에 실패한 반복문은 무엇입니까?
3. 실행 시점 분기 경로가 추가됐습니까?
4. 벡터 폭과 원소 자료형은 무엇입니까?
5. 남은 원소와 마스크를 어떻게 처리합니까?
6. 부동소수점 의미를 완화하는 옵션이 필요합니까?

`vectorized`라는 문장이 있어도 실제 병목 반복문이 아닐 수 있습니다. 어셈블리와 프로파일을 함께 봐야 합니다.

## 내장 함수 사용 조건

내장 함수는 특정 ISA 연산을 직접 지정합니다. 명령 선택을 세밀하게 제어할 수 있지만 다음 비용이 있습니다.

- ISA와 벡터 폭에 종속됩니다.
- CPU 기능 탐지와 대체 경로가 필요합니다.
- 컴파일러의 레지스터 할당과 명령 배치를 방해할 수 있습니다.
- 코드 검토와 정확성 검사가 어려워집니다.

먼저 스칼라 기준 구현과 고정 시드 검사를 만들고, 대상 기능이 없는 CPU에서는 해당 경로를 실행하지 않게 해야 합니다.

## SIMD가 효과를 내지 못하는 경우

- 반복 간 의존성이 있습니다.
- 메모리 대역폭이 이미 포화됐습니다.
- 원소 수가 너무 작습니다.
- 마스크 때문에 대부분의 레인이 비활성입니다.
- gather/scatter가 캐시 실패를 만듭니다.
- 데이터 변환 비용이 계산보다 큽니다.
- 컴파일러가 이미 같은 최적화를 수행합니다.

이 경우 알고리즘, 데이터 배치, 묶음 처리 또는 스레드 병렬화가 더 중요할 수 있습니다.
