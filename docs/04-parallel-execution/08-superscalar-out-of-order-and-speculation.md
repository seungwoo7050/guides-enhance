# 슈퍼스칼라, 비순차 실행과 추측

단일 발행 파이프라인은 여러 명령의 단계를 겹치지만 보통 사이클마다 새 명령 하나를 처리합니다. 고성능 코어는 여러 명령을 가져오고 해석하며, 피연산자와 실행 장치가 준비된 명령을 프로그램 순서와 다르게 실행할 수 있습니다. 내부 계산 순서가 달라도 소프트웨어에는 ISA가 허용한 레지스터·메모리 결과와 정밀한 예외를 보여야 합니다.

이 문서는 레지스터 이름 변경, 발행 큐, 재정렬 버퍼, 적재·저장 큐, 저장 버퍼와 ISA 메모리 순서를 다룹니다. C/C++ 원자적 연산, Java `volatile`과 언어별 happens-before 규칙은 별도 주제입니다.

## 학습 목표

- 파이프라인 병렬성, 슈퍼스칼라 폭과 비순차 실행을 구분합니다.
- RAW와 이름 재사용 때문에 생기는 WAR·WAW를 구분합니다.
- 이름 변경, 발행, 실행, 완료와 프로그램 순서 반영을 설명합니다.
- 추측 실패와 정밀한 예외가 레지스터와 메모리에 미치는 영향을 설명합니다.
- 캐시 일관성과 메모리 일관성이 서로 다른 질문이라는 점을 이해합니다.

## 세 가지 실행 방식

### 파이프라인 병렬성

서로 다른 명령이 서로 다른 단계에 있습니다.

### 슈퍼스칼라 폭

한 사이클에 여러 명령 또는 마이크로 연산을 인출, 해독, 발행, 실행하거나 상태에 반영할 수 있습니다. 각 단계의 폭은 서로 다를 수 있습니다.

### 비순차 실행

프로그램 순서에서 뒤에 있는 연산도 피연산자와 실행 장치가 준비되면 먼저 실행할 수 있습니다.

세 속성은 독립적입니다. 여러 명령을 함께 발행하더라도 프로그램 순서를 지키는 코어가 있을 수 있고, 넓은 비순차 코어도 있습니다.

## 의존성 그래프

```text
A: r1 = r2 + r3
B: r4 = r5 + r6
C: r7 = r1 + r8
```

A와 B는 독립이므로 함께 실행할 수 있습니다. C는 A의 결과가 필요합니다.

```text
A → C
B는 독립
```

실행 장치가 많아도 긴 RAW 의존 사슬은 사라지지 않습니다. 성능을 분석할 때는 명령 수와 함께 다음을 확인합니다.

- 의존성 그래프의 임계 경로
- 실행 장치의 지연 시간과 처리량
- 사용할 수 있는 실행 포트
- 명령 공급부가 제공하는 명령 수
- 캐시와 TLB 실패

한 ISA 명령이 여러 마이크로 연산으로 나뉘거나 여러 명령이 내부에서 결합될 수도 있습니다. 소스 줄 수와 내부 연산 수를 같다고 가정하면 안 됩니다.

## 레지스터 이름 변경

아키텍처 레지스터 수가 제한되어 있으면 서로 무관한 값이 같은 이름을 다시 사용할 수 있습니다.

```text
I0: r1 = ...
I1: ... = r1
I2: r1 = ...
```

I2의 쓰기가 I1의 읽기보다 먼저 보이면 WAR 문제가 생기고, 두 쓰기의 순서가 바뀌면 WAW 문제가 생깁니다. 이름 변경 단계에서 새로운 물리 레지스터를 배정하면 값의 버전을 나눌 수 있습니다.

```text
architectural r1 version 0 → physical p12
I2가 만드는 r1 version 1  → physical p37
```

이름 변경은 이름 재사용 때문에 생긴 WAR와 WAW를 제거할 수 있지만, I1이 I0의 실제 값이 필요한 RAW는 제거하지 못합니다.

이름 변경표, 빈 물리 레지스터 목록과 이전 물리 레지스터를 언제 반환할지도 복구 과정과 연결됩니다.

## 발행 큐

이름 변경이 끝난 연산은 다음 정보를 가질 수 있습니다.

- 소스 물리 레지스터 태그
- 각 소스의 준비 여부 또는 값
- 목적지 물리 레지스터
- 필요한 실행 장치
- 프로그램 순서를 나타내는 나이
- 예외와 추측 정보

소스가 준비되고 필요한 장치가 비어 있으면 발행할 수 있습니다. 준비된 연산 중 무엇을 먼저 고를지는 스케줄러가 정합니다. 먼저 발행했다고 먼저 완료하거나 상태에 반영된다는 보장은 없습니다.

### 지연 시간과 처리량

- 지연 시간은 한 연산의 결과가 준비될 때까지 걸리는 시간입니다.
- 처리량은 같은 장치가 새 연산을 받을 수 있는 빈도입니다.

독립 연산의 처리량과 의존 사슬의 지연을 구분해야 합니다.

## 재정렬 버퍼

연산이 완료되는 즉시 아키텍처 레지스터나 메모리에 반영하면 앞선 명령의 예외를 정확히 처리하기 어렵습니다. Reorder Buffer(ROB)는 프로그램 순서로 항목을 저장하고, 목적지, 결과 준비 여부와 폴트를 기록합니다.

```text
out-of-order execute
→ result complete
→ ROB head부터 in-order retire
→ architectural state 반영
```

다음 상태를 구분합니다.

```text
issued    실행을 기다립니다.
executed  계산이 끝났습니다.
complete  결과와 fault 정보가 준비되었습니다.
retired   program 순서대로 software에 보이는 상태에 반영되었습니다.
```

“먼저 계산됐습니다”와 “소프트웨어에 먼저 보였습니다”는 같은 뜻이 아닙니다.

## 정밀한 예외

ROB 맨 앞의 명령이 폴트를 일으키면 그보다 오래된 명령은 이미 반영되어 있어야 하고, 폴트가 난 명령과 더 젊은 명령은 반영되지 않아야 합니다.

```text
older instructions → retire 완료
faulting instruction → exception 보고
younger instructions → 미반영 결과 폐기
```

`processor-model`의 ROB는 뒤 항목이 먼저 완료되어도 맨 앞 항목이 준비되지 않으면 레지스터에 쓰지 않습니다. 폴트 항목을 반영할 차례가 되면 그 항목과 더 젊은 대기 항목을 제거합니다.

```sh
cd exercises/processor-model
python3 -m unittest \
  tests.test_processor_model.ReorderBufferTests -v
```

## 분기 추측

분기 예측기는 다음 PC를 추측합니다. 맞으면 분기 결과를 기다리지 않고 명령을 계속 공급할 수 있습니다. 틀리면 잘못된 경로에서 만든 연산을 버리고 올바른 목적지부터 다시 시작합니다.

```text
prediction
→ speculative fetch / execute
→ branch resolve
   ├─ correct: 계속 진행
   └─ wrong: younger work 폐기와 rename 상태 복구
```

아키텍처 상태를 복구해도 캐시, TLB와 예측기 같은 프로세서 내부 상태에는 흔적이 남을 수 있습니다.

```text
speculative 결과가 retire되지 않았습니다.
≠ speculative 실행이 관찰 가능한 흔적을 전혀 남기지 않았습니다.
```

구체적인 부채널 공격과 완화는 이 저장소의 필수 범위가 아닙니다.

## 2비트 예측기

2비트 포화 계수기는 `0`과 `1`을 분기하지 않음, `2`와 `3`을 분기함으로 해석합니다. 한 번 반대 결과가 나와도 강한 상태에서 즉시 방향을 바꾸지 않습니다.

```sh
python3 -m unittest \
  tests.test_processor_model.BranchPredictorTests -v
```

작은 표에서는 서로 다른 PC가 같은 항목을 사용할 수 있습니다. 이를 별칭이라고 하며, 표 크기와 인덱스 계산으로 어느 분기가 충돌하는지 확인할 수 있습니다.

## 적재·저장 큐

두 메모리 연산이 같은 주소인지 주소 계산 전에는 알 수 없을 수 있습니다.

```text
store [r1 + offsetA] = value
load  result = [r2 + offsetB]
```

비순차 코어는 다음을 처리해야 합니다.

- 적재가 앞선 저장과 같은 주소인지 확인합니다.
- 같은 주소이고 저장할 값이 준비되면 바로 전달합니다.
- 주소를 아직 모르는 저장을 적재가 추월할지 추측할 수 있습니다.
- 추측이 틀리면 적재와 그 결과에 의존한 연산을 다시 실행합니다.
- 저장이 프로그램 순서에 따라 반영되기 전에 외부 메모리 상태를 잘못 바꾸지 않도록 보류합니다.

포인터 별칭은 컴파일러뿐 아니라 하드웨어 스케줄러에도 영향을 줍니다.

## 저장 버퍼

프로그램 순서에 따라 반영된 저장이 캐시 계층에 완전히 적용될 때까지 명령 공급부를 멈추면 처리량이 줄어듭니다. 저장 버퍼는 주소와 데이터를 보관하고 뒤에서 캐시와 일관성 처리를 진행합니다.

같은 코어의 뒤 적재가 같은 주소를 읽으면 저장 버퍼의 값을 바로 전달해야 할 수 있습니다. 다른 코어가 쓰기를 언제 관찰하는지는 캐시 일관성과 ISA 메모리 순서를 함께 봐야 합니다.

## 캐시 일관성과 메모리 일관성

### 캐시 일관성

한 메모리 위치의 쓰기가 여러 캐시 복사본에 어떻게 전달되고 오래된 복사본이 어떻게 제거되는지 다룹니다.

### 메모리 일관성 모델

여러 주소에 대한 적재와 저장이 다른 코어에서 어떤 순서로 관찰될 수 있는지 다룹니다.

```text
core 0: data = 42; ready = 1
core 1: if (ready == 1) use(data)
```

각 캐시 라인의 일관성이 맞더라도 `ready`를 본 뒤 반드시 `data == 42`가 보인다고 모든 ISA가 자동으로 보장하는 것은 아닙니다.

## 메모리 순서 명령

ISA의 fence 명령은 특정 메모리 연산이 다른 연산보다 먼저 관찰되도록 허용되는 순서를 제한합니다. 모든 접근 사이에 강한 fence를 넣으면 저장 버퍼와 비순차 실행이 제공하는 겹침을 잃습니다.

응용 코드에서는 먼저 언어의 원자적 연산과 잠금으로 동기화를 표현해야 합니다. ISA fence만 직접 넣으면 컴파일러 재배치를 막지 못하거나 다른 ISA로 옮기기 어려울 수 있습니다.

낮은 수준의 메모리 순서를 분석할 때는 다음 순서를 사용합니다.

1. 공유 상태가 만족해야 할 조건을 적습니다.
2. 어느 쓰기가 어느 읽기보다 먼저 보여야 하는지 표시합니다.
3. 언어의 원자적 연산 또는 잠금으로 그 순서를 표현합니다.
4. 컴파일러가 어떤 명령과 fence를 생성했는지 확인합니다.
5. 필요한 경우 아키텍처 문서와 동시성 검사로 확인합니다.

## 비순차 실행 병목 분류

IPC 하나만으로 원인을 정할 수 없습니다. 다음 후보를 나눠 봅니다.

- RAW 의존 사슬이 길어 준비된 연산이 부족합니다.
- 특정 실행 포트가 포화됩니다.
- 명령 공급부가 연산을 충분히 공급하지 못합니다.
- ROB, 물리 레지스터 또는 발행 큐가 가득 찹니다.
- 적재·저장 큐가 가득 찹니다.
- 캐시 또는 TLB 실패를 기다립니다.
- 분기 예측 실패로 수행한 작업을 버립니다.
- 메모리 대역폭이 포화됩니다.
