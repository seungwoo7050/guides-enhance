# 멀티코어, 캐시 일관성과 거짓 공유

여러 코어가 같은 물리 메모리를 사용해도 각 코어의 전용 캐시에는 같은 라인의 복사본이 있을 수 있습니다. 한 코어가 값을 쓰면 다른 코어가 오래된 복사본을 계속 사용하지 않도록 일관성 프로토콜이 소유권과 무효화를 처리합니다. 관리 단위가 변수보다 큰 캐시 라인이므로 서로 다른 값을 쓰는 스레드도 같은 라인 때문에 경쟁할 수 있습니다.

## 학습 목표

- 안정 MESI 상태의 읽기·쓰기 전이를 추적합니다.
- 실제 공유와 거짓 공유를 구분합니다.
- 캐시 일관성, 메모리 일관성과 언어 메모리 모델을 구분합니다.
- 원자적 연산의 정확성과 캐시 라인 경합 성능을 따로 판단합니다.

## 공유 메모리를 보는 순서

다중 스레드 프로그램은 다음 단계를 거칩니다.

```text
language memory model
→ compiler 변환
→ ISA atomic / fence 의미
→ cache coherence와 interconnect
→ cache / memory controller
```

C/C++에서 데이터 경쟁이 있는 프로그램은 하드웨어 일관성이 있어도 올바르지 않습니다. 반대로 언어의 원자적 연산을 사용해 결과가 맞더라도 캐시 라인이 코어 사이를 계속 이동하면 느릴 수 있습니다.

## 캐시 일관성이 해결하는 문제

코어 0과 코어 1이 같은 라인을 읽으면 둘 다 복사본을 가질 수 있습니다. 코어 0이 쓰려면 다른 복사본을 무효화하거나 새 값으로 갱신해야 합니다.

대표적인 구현 방식은 다음과 같습니다.

- 스누핑 방식은 공유 연결망의 트랜잭션을 각 캐시가 관찰합니다.
- 디렉터리 방식은 라인의 공유자와 소유자를 기록하고 필요한 노드에 메시지를 보냅니다.

코어 수가 많아질수록 모든 요청을 전체에 전파하기 어려워 디렉터리와 계층형 연결망이 중요해질 수 있습니다.

## MESI 상태

### Modified(M)

해당 캐시만 최신 복사본을 가지며 메모리보다 새 값일 수 있습니다. 교체하거나 다른 코어가 읽을 때 데이터 전달 또는 `write-back`이 필요할 수 있습니다.

### Exclusive(E)

해당 캐시만 수정되지 않은 복사본을 가집니다. 다른 공유자가 없으므로 로컬 쓰기에서 버스 트랜잭션 없이 M으로 바뀔 수 있습니다.

### Shared(S)

여러 캐시가 수정되지 않은 복사본을 가질 수 있습니다. 쓰려면 다른 S 복사본을 무효화해야 합니다.

### Invalid(I)

사용할 수 없는 항목입니다.

실제 프로세서는 MESIF, MOESI와 여러 일시 상태를 사용할 수 있습니다. `processor-model`은 안정 MESI 상태만 다룹니다.

## 읽기 전이

다른 캐시에 복사본이 없는 라인을 코어 0이 읽으면 E를 받을 수 있습니다.

```text
core0: I --BusRd--> E
```

코어 1이 같은 라인을 읽으면 두 캐시가 S가 됩니다.

```text
core0: E → S
core1: I → S
```

M 소유자가 있는 상태에서 다른 코어가 읽으면 소유자가 최신 데이터를 제공하거나 메모리에 반영하고 S로 내려갈 수 있습니다.

## 쓰기 전이

S 상태에서 쓰려면 다른 공유자를 무효화합니다.

```text
core0: S --BusUpgr--> M
core1: S → I
```

I 상태의 쓰기 실패는 읽기 독점 트랜잭션으로 데이터와 소유권을 함께 요청할 수 있습니다.

```text
core0: I --BusRdX--> M
other copies → I
```

E 상태에서는 다른 복사본이 없으므로 로컬 `E → M` 전이가 가능합니다.

## 거짓 공유

다음 두 스레드는 서로 다른 계수기만 씁니다.

```c
counters[0] += 1;
counters[1] += 1;
```

두 값이 같은 캐시 라인에 있으면 쓸 때마다 라인 소유권이 코어 사이를 이동할 수 있습니다.

```text
core0 writes offset 0  → core1 copy invalid
core1 writes offset 8  → core0 copy invalid
core0 writes offset 0  → core1 copy invalid
```

프로그램이 공유하는 논리 단위는 8바이트 계수기지만 일관성 프로토콜은 64바이트 라인을 관리할 수 있습니다.

```sh
cd exercises/processor-model
python3 processor-model.py coherence \
  fixtures/traces/coherence-false-sharing.trace \
  --cores 2 --line-size 64
```

주소 `0`과 `8`이 같은 블록으로 계산되고 무효화가 반복되는지 확인합니다.

## 실제 공유와 거짓 공유

### 실제 공유

여러 스레드가 같은 값을 읽고 씁니다. 결과를 맞추려면 동기화가 필요합니다.

### 거짓 공유

서로 다른 값을 쓰지만 같은 캐시 라인에 배치되어 일관성 트래픽이 발생합니다.

패딩은 거짓 공유를 줄일 수 있지만 실제 공유 때문에 필요한 직렬 실행은 없애지 못합니다.

## 실제 pthread 관찰

```sh
make -C examples/false-sharing check
make -C examples/false-sharing benchmark
```

`compact`와 `padded`는 같은 횟수만큼 서로 다른 계수기를 갱신합니다. 각 계수기의 최종 값은 정확히 같아야 합니다. 실행 시간의 우열은 고정하지 않습니다.

차이가 작을 수 있는 조건은 다음과 같습니다.

- 실행 가능한 CPU가 하나뿐입니다.
- 두 스레드가 같은 코어에 배치됩니다.
- 반복 횟수가 너무 작습니다.
- 측정 중 주파수와 다른 작업량이 변합니다.
- 실제 캐시 라인 크기와 하드웨어 구성이 가정과 다릅니다.

패딩은 메모리 사용량과 캐시·TLB 작업 집합을 늘립니다. 실제로 자주 쓰는 주소가 같은 라인에 있는지 확인한 뒤 적용해야 합니다.

## 원자적 연산

일반 증가 연산은 적재, 덧셈, 저장으로 나뉩니다.

```text
load counter
add 1
store counter
```

여러 스레드가 같은 값을 수정하면 갱신 일부가 사라질 수 있습니다. 원자적 읽기-수정-쓰기는 이 세 동작을 다른 스레드가 끼어들 수 없는 하나의 연산으로 제공합니다.

결과가 정확해져도 모든 스레드가 같은 계수기를 수정하면 라인 소유권이 계속 이동할 수 있습니다. 정확성과 확장성은 별도 문제입니다.

대안은 다음과 같습니다.

- 스레드별 계수기를 나중에 합칩니다.
- 계수기를 여러 조각으로 나눕니다.
- 여러 갱신을 묶어 처리합니다.
- 한 스레드만 쓰고 메시지로 요청을 받습니다.

이 경우 읽는 값의 최신성, 합산 시점과 메모리 사용량이 달라집니다.

## 잠금 경합

여러 코어가 같은 잠금 변수를 획득하려고 반복해서 쓰면 잠금이 보호하는 데이터에 들어가기 전에도 캐시 라인이 이동할 수 있습니다.

잠금 성능을 볼 때는 다음을 확인합니다.

- 임계 구역 길이
- 대기 스레드 수
- 공정성
- 선점 여부
- NUMA 위치
- 대기 간격 조절 또는 큐 기반 잠금
- 일정 시간 뒤 대기 상태로 전환하는지 여부

“뮤텍스는 항상 커널 호출이라 느립니다”라고 단정할 수 없습니다. 경합이 없을 때는 사용자 공간의 원자적 연산으로 끝나고 경합이 생겼을 때만 잠드는 구현도 있습니다.

## 메모리 일관성

캐시 일관성이 라인 A와 라인 B 각각의 쓰기 순서를 유지해도 다른 코어가 두 라인의 쓰기를 같은 순서로 볼지는 별도 규칙입니다.

```text
core0: data = 42; ready = 1
core1: if (ready == 1) use(data)
```

올바른 메시지 전달에는 언어 수준의 release/acquire 같은 순서 보장이 필요할 수 있습니다. MESI 추적 입력만으로 잠금 없는 알고리즘의 정확성을 증명할 수 없습니다.

## 캐시 사이 데이터 전달

한 코어가 M 라인을 가진 상태에서 다른 코어가 읽으면 최신 데이터가 소유자 캐시에서 전달될 수 있습니다. 실제 경로에는 공유 캐시와 메모리 제어기가 참여할 수 있습니다.

DRAM 대역폭이 낮다는 사실만으로 일관성 트래픽이 없다고 결론 내릴 수 없습니다. 캐시 사이 데이터 전달과 무효화는 별도 연결망 사건일 수 있습니다.

## NUMA

여러 소켓 또는 NUMA 노드에서는 코어와 메모리 제어기의 거리가 다릅니다.

```text
local node memory
remote node memory
```

스레드 CPU만 고정하고 페이지 배치를 보지 않거나, 메모리만 고정하고 스레드가 다른 CPU로 이동하면 결과를 해석하기 어렵습니다.

NUMA 최적화에서는 다음을 함께 봅니다.

- 스레드 배치
- 페이지 배치
- 조각별 데이터 소유자
- 원격 읽기·쓰기 비율
- 노드 사이 동기화

작은 단일 소켓 작업량에는 복잡성만 늘릴 수 있으므로 하드웨어 구성과 프로파일을 먼저 확인합니다.

## 코어 수와 속도 향상률

코어 수를 늘려도 속도 향상률이 선형으로 늘지 않는 이유는 다음이 섞이기 때문입니다.

- 직렬 실행 구간
- 작업량 불균형
- 잠금 또는 원자적 연산 경합
- 일관성 트래픽
- 메모리 대역폭 포화
- 공유 캐시 용량
- 스케줄러와 런타임 부가 비용

```text
parallel time(N)
= useful work / N
+ synchronization
+ communication
+ imbalance
```

1, 2, 4, 8개 스레드의 추세를 확인해야 합니다. 한 점만 측정해서 확장성을 판단하지 않습니다.

## 공유 쓰기 줄이기

일관성 트랜잭션 자체가 필요하지 않도록 데이터 사용 방식을 바꿀 수 있습니다.

- 변경하지 않는 데이터 공유
- 스레드 또는 코어별 분할
- 단일 작성자
- 메시지 전달
- 추가 전용 기록 뒤 병합
- 읽기 위주 스냅샷

공유를 줄이면 병합 비용, 지연 시간, 메모리 복제와 일관성 요구가 달라집니다. 무료 해결책은 아닙니다.

## 거짓 공유 확인 순서

1. 스레드별로 자주 쓰는 주소를 찾습니다.
2. 객체 오프셋과 실제 주소를 기록합니다.
3. 캐시 라인 크기로 같은 라인인지 계산합니다.
4. 스레드가 다른 코어에서 동시에 실행되는지 확인합니다.
5. 가능한 경우 캐시 사이 전송 또는 일관성 계수기를 봅니다.
6. 패딩 또는 데이터 분할을 한 가지 적용합니다.
7. 결과, 메모리 사용량과 전체 작업량을 다시 측정합니다.

구조체 선언만 보고 할당 정렬과 배열 간격을 확인하지 않으면 실제 배치를 잘못 판단할 수 있습니다.

## 직접 확인할 문제

1. 두 코어가 같은 라인을 읽은 뒤 한 코어가 쓸 때 MESI 상태를 순서대로 적어 보세요.
2. `E → M` 전이에 버스 트랜잭션이 필요하지 않을 수 있는 이유를 설명해 보세요.
3. 거짓 공유를 줄이기 위한 패딩이 메모리 사용량과 TLB 실패를 늘릴 수 있는 이유를 설명해 보세요.
4. 원자적 계수기 하나를 스레드별 계수기로 나눌 때 최신성과 합산 방법이 어떻게 달라지는지 적어 보세요.
5. 캐시 일관성이 올바른데도 release/acquire가 필요한 메시지 전달 예를 설명해 보세요.
