# Notes API

Fastify와 Zod로 만든 메모 API입니다. HTTP 요청을 실행 중에 검증하고, 메모 생성 규칙과 저장 책임을 분리합니다. 예상한 비즈니스 실패와 예상하지 못한 내부 오류를 구분하고, 내부 구현 정보가 HTTP 응답으로 노출되지 않게 합니다.

## 제공하는 API

| Method | Path | 설명 |
|---|---|---|
| `GET` | `/memos` | 전체 메모 조회 |
| `GET` | `/memos/:id` | ID로 한 건 조회 |
| `POST` | `/memos` | 메모 생성 |

생성 본문은 다음 형식입니다.

```json
{
  "title": "회의 기록",
  "body": "결정 사항을 정리합니다."
}
```

제목은 공백을 제거한 뒤 1~80자여야 하며, 본문은 최대 500자입니다. 같은 제목은 409로 거부합니다.

## 요청 검증

TypeScript 타입만으로는 실제 HTTP 요청 본문을 신뢰할 수 없습니다. 네트워크에서 받은 값은 런타임에는 `unknown`에 가까운 외부 입력이므로 Zod 스키마로 검사합니다.

검증 흐름은 다음처럼 이해할 수 있습니다.

```text
HTTP 요청
→ JSON 파싱
→ Zod 스키마 검증
→ 검증된 값만 service로 전달
→ repository 호출
```

예를 들어 다음 입력은 서로 다른 이유로 거부될 수 있습니다.

```json
{ "title": "", "body": "..." }
```

```json
{ "title": 123, "body": "..." }
```

첫 번째는 문자열 형식은 맞지만 제목 규칙을 만족하지 않고, 두 번째는 타입 자체가 잘못되었습니다.

## HTTP 상태 코드

프로젝트에서 사용하는 주요 상태의 의미는 다음과 같습니다.

```text
200 → 조회 성공
201 → 생성 성공
400 → 요청 형식 또는 값이 잘못됨
404 → 요청한 메모가 없음
409 → 현재 서버 상태와 충돌, 여기서는 제목 중복
500 → 예상하지 못한 서버 내부 오류
```

`409`는 단순한 JSON 문법 오류가 아니라, 요청 자체는 이해했지만 현재 리소스 상태 때문에 수행할 수 없다는 뜻으로 사용합니다.

## 설치와 실행

```sh
npm install
npm run typecheck
npm test
npm run dev
```

서버는 기본적으로 `0.0.0.0:4000`에서 실행됩니다.

`typecheck`, `test`, `dev`는 서로 다른 목적을 가집니다.

```text
typecheck
→ 정적 타입 오류 확인

test
→ 실제 요청 처리와 오류 경로 확인

dev
→ 실제 포트를 열어 수동 실행
```

테스트가 통과해도 타입 검사를 대신하지 않고, 타입 검사가 통과해도 런타임 검증이 올바르다는 뜻은 아닙니다.

## 계층별 책임

이 프로젝트는 요청 처리와 저장 로직을 한 함수에 모두 넣지 않습니다.

```text
route/app
→ HTTP와 Fastify 책임

service
→ 제목 중복 같은 애플리케이션 규칙

repository
→ 메모 저장과 조회
```

이 구분의 장점은 중복 제목 같은 규칙을 HTTP 상태 코드와 분리해 표현할 수 있다는 것입니다.

예:

```text
service
→ DuplicateTitleError

HTTP route
→ DuplicateTitleError를 409로 변환
```

service가 Fastify의 `reply.code(409)`를 직접 호출하지 않으므로 HTTP 이외의 호출 경로에서도 같은 규칙을 재사용하기 쉽습니다.

## 테스트

테스트는 실제 포트를 열지 않고 `app.inject()`를 사용합니다.

`app.inject()`는 단순히 route handler 함수 하나만 호출하는 것이 아니라 Fastify 플러그인, 훅, 라우팅, 검증과 응답 직렬화 등 실제 애플리케이션 경로를 상당 부분 실행합니다.

테스트는 다음을 확인합니다.

- 빈 제목은 400
- 잘못된 JSON은 400
- 정상 생성은 201
- 같은 제목의 두 번째 생성은 409
- 없는 ID는 404
- 저장소의 예상하지 못한 오류는 500
- 내부 열 이름과 스택 정보는 응답에 포함되지 않음
- 각 테스트가 만든 Fastify 애플리케이션을 종료함

### 내부 오류 비노출

예상하지 못한 오류가 발생해도 다음처럼 내부 구현 세부사항을 그대로 응답하면 안 됩니다.

```text
SQL 문장
DB 열 이름
파일 경로
스택 트레이스
내부 라이브러리 오류
```

서버는 이러한 정보는 로그에서 추적할 수 있게 남기되, 클라이언트에는 일반적인 500 응답을 반환합니다.

```text
내부 진단 정보 → 서버 로그
클라이언트 응답 → 제한된 일반 오류
```

## 테스트 격리

메모리 저장소는 인스턴스마다 별도 `Map`을 사용합니다.

따라서 다음 구조가 되지 않습니다.

```text
test A가 만든 memo
→ 전역 Map에 남음
→ test B가 우연히 읽음
```

각 테스트가 독립된 애플리케이션과 저장소를 가지므로 실행 순서를 바꾸거나 특정 테스트만 단독 실행해도 같은 결과를 기대할 수 있습니다.

## 애플리케이션 종료

각 테스트가 만든 Fastify 애플리케이션은 반드시 닫습니다.

```ts
const app = buildApp();

try {
  // test
} finally {
  await app.close();
}
```

현재 구현은 메모리 저장소를 사용하지만, 애플리케이션 종료 규칙을 지키는 습관은 이후 DB pool, timer, WebSocket 같은 자원이 추가될 때 중요합니다.

## 코드 구성

- `src/contracts.ts`: 생성 본문 스키마와 메모 타입
- `src/repository.ts`: 저장에 필요한 함수와 메모리 구현
- `src/service.ts`: 중복 제목 검사
- `src/app.ts`: 요청·응답 처리와 오류 변환
- `src/server.ts`: 메모리 저장소를 선택하고 포트 열기

## 주요 선택

- 외부 본문은 TypeScript 타입 단언이 아니라 Zod로 검사합니다.
- 제목 중복은 HTTP 코드가 아니라 서비스 오류로 표현합니다. 라우트가 이를 409로 바꿉니다.
- 메모리 저장소는 인스턴스마다 별도 `Map`을 사용하므로 테스트가 값을 공유하지 않습니다.
- 분류하지 못한 오류는 로그 대상이며, 클라이언트에는 일반적인 500 본문만 반환합니다.
- 테스트 가능한 Fastify 앱 생성과 실제 네트워크 포트 열기를 분리합니다.

## Implementation Order

| Order | Responsibility | Primary anchor |
| ----: | --- | --- |
| 1 | Memo request schema | `src/contracts.ts` |
| 2 | Memo persistence API | `src/repository.ts` |
| 3 | Duplicate-title rule | `src/service.ts` |
| 4 | Testable Fastify app factory | `src/app.ts` |
| 5 | Memo read routes | `src/app.ts` |
| 6 | Memo creation route | `src/app.ts` |
| 7 | Network entry point | `src/server.ts` |

먼저 외부 입력 계약과 저장 API를 정한 뒤 비즈니스 규칙을 올리고, 마지막에 HTTP와 실제 포트를 연결하는 순서입니다.

## 범위와 제한

메모는 프로세스 메모리에만 저장되어 재시작하면 사라집니다. 인증, 데이터베이스, 페이지네이션, 수정과 삭제 API는 포함하지 않습니다.

따라서 제목 중복도 단일 프로세스의 메모리 저장소를 기준으로 검사합니다. 여러 서버 인스턴스나 실제 데이터베이스 경쟁 조건을 해결하는 예제는 아닙니다.
